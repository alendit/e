#+title: Prompt-cache boundary for dynamic context
#+date: 2026-08-12
#+startup: overview

* Question

Does e's distinction between stable and dynamic context preserve provider prompt
cache hits when dynamic session state changes, and can the request shape be made
more efficient?

* Current model

=e-context= orders context as =static-prefix=, =stable-context=, then
=dynamic-context=.  Capabilities preserve that order in the segment metadata.
The placement is a cache-layout declaration; it is not itself a provider cache.
Each backend must translate the stable/dynamic boundary into a request shape the
provider can cache.

This makes mutable session state such as voice-adjustment tell labels a
=dynamic-context= concern.  Putting it in =stable-context= would make a changing
value part of the promised stable prefix.  Keeping it as a short final segment
both reduces input size and leaves earlier stable material unchanged.

* Provider evaluation

| Backend | Existing translation | Effect of a changed dynamic suffix |
|---------+----------------------+------------------------------------|
| OpenAI, GPT-5.5 and earlier | All system segments are flattened into one =instructions= string, in placement order; =prompt_cache_key= is sent. | Automatic longest-prefix matching can reuse the unchanged stable prefix once it is long enough to be cacheable. |
| OpenAI, GPT-5.6 and later, explicit-capable profile | Stable system segments become developer input with an explicit breakpoint; dynamic developer input follows it and the request uses explicit mode. | The unchanged stable prefix remains reusable without writing the changing suffix. |
| ChatGPT Codex, =gpt-5.6-sol= | Stable and dynamic system segments become separate developer input without explicit cache fields. | Connection-local continuation carries the stable segment and re-emits only changed dynamic context; a new socket safely replays the complete segmented input. |
| Anthropic Messages | System segments remain blocks; =cache_control= is attached to the final static/stable block before dynamic context. | The unchanged stable prefix remains behind an explicit cache breakpoint, so later dynamic blocks do not move that boundary. |

The OpenAI GPT-5.6 behavior is documented in [[https://developers.openai.com/api/docs/guides/prompt-caching][Prompt caching]].
Explicit breakpoints are supported on Responses input content blocks, not on
the top-level string =instructions= field.  Therefore adding a field to the
current flattened request would not correctly express e's existing boundary.

* Implemented OpenAI adapter support

Feature [[../feats/81-openai-gpt56-explicit-prompt-cache/plan.org][81]] implements GPT-5.6 explicit caching as a provider-adapter feature
rather than a change to the generic context placements.

1. Preserve the stable/dynamic segment boundary in the OpenAI request renderer.
2. Represent the final stable segment as a cacheable Responses input content
   block and put =prompt_cache_breakpoint= there; place dynamic current-state
   content after it.
3. Send =prompt_cache_options= in explicit mode together with the existing
   derived =prompt_cache_key=.
4. Define continuation behavior deliberately.  A first-turn cacheable input
   item can be carried by =previous_response_id=, whereas top-level
   =instructions= are request-local; the adapter must not duplicate stable
   context on continued requests.
5. Record =cache_write_tokens= as well as =cached_tokens= so cache creation cost
   and net reuse are visible.
6. Add a credentialed end-to-end test with two otherwise identical turns whose
   dynamic segment changes.  Assert request shape and inspect provider usage;
   do not claim a hit-rate improvement from request-shape unit tests alone.

Provider support is explicit rather than inferred from the model name.  A
Responses provider opts in with =:prompt-cache-breakpoint-mode explicit=.
Credentialed probes on 2026-08-12 established that ChatGPT's Codex endpoint
requires =store=false=, rejects =prompt_cache_options= as unsupported, and
reports =prompt_cache_breakpoint= unsupported for =gpt-5.6-sol=.  The built-in
Codex profile therefore uses segmented developer input without breakpoints and
connection-local =previous_response_id= continuation.  Stable guidance is sent
once on a warm socket while changed dynamic context is re-emitted.  A new or
provider-closed socket gets complete replay.  This optimizes the primary
backend without sending unsupported fields while leaving the documented
explicit GPT-5.6 API shape available to compatible provider profiles.

* Conclusion

The generic placement model is sound, and the voice tell list belongs in
=dynamic-context=.  Anthropic and explicit-capable OpenAI GPT-5.6 profiles turn
the boundary into a provider breakpoint.  OpenAI's existing ordering remains
useful for GPT-5.5 and earlier.  ChatGPT Codex uses the same generic segment
boundary for continuation, but still needs endpoint support before e can
safely enable explicit cache writes there.
