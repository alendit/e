* DP4 correction after the acknowledgement recurrence

The correction belongs at the ACID storage boundary, not in session or Board
policy.  SQLite already decides atomically whether each mutation commits or
rolls back.  The adapter must make that outcome observable across loss of the
worker acknowledgement: give each write a durable request identity and record
that identity, an exact request fingerprint, and a result proved to fit its
complete correlated success response in the same transaction as the mutation.
After a timeout, replace the worker and replay
the same identity.  The worker returns the committed receipt when present or
executes the transaction once when absent.  A mismatched fingerprint is a
protocol error.  Reads can be retried after reopening.

Receipt retention must be bounded without weakening deduplication.  Because
the runtime has one ordered active write, acknowledgement can advance a
per-runtime durable watermark; receipts older than the acknowledged prefix can
then be removed.  A newly exclusive runtime can discard receipts belonging to
dead prior runtime identities.  These are persistence-adapter mechanics and
must not appear as per-operation recovery flags in application code.

The deterministic acceptance scenario must use the real default runtime,
session storage, and Board composition; inject a worker-side stall after
=catalog-put= submission; queue a Board transition behind it; and prove all of
the following:

- the already-committed canonical primary remains authoritative;
- the queued Board request is not lost to a global frozen state;
- the timed-out request resolves to its one durable result whether the injected
  stall occurs immediately before or after commit;
- worker replacement/reopen resumes the same ordered request stream safely;
- a subsequent canonical write succeeds; and
- neither recovery nor reconciliation duplicates a semantic side effect.

The original canonical database was only read and remains unchanged.  All
write probes used a disposable clone.
