* Status

Reproduced after a full Emacs restart; Feature 92's diagnostics now identify a
submitted =catalog-put= as the blocking request.  The request-lifecycle fixes
correctly cancelled the queued =board-pickup-transition= without misattributing

* Fresh post-restart recurrence

The fresh runtime reported request =w:83= as a submitted =catalog-put=.  Its
60-second acknowledgement timeout entered the generic fail-closed path.  A
queued =board-pickup-transition= (=w:84=) then expired before submission and
correctly named =catalog-put= as its blocker.  Later Board mutation reported
=e-board-mutation-frozen=, and subsequent store use exposed the preserved
=catalog-put= timeout as the unavailable cause.

The supported live probes found the Daily chat idle and Emacs responsive, but
one ping took about 29 seconds before the event loop answered.  Two later
bounded process samples found the main thread idle in AppKit, so this was an
intermittent synchronous stall rather than a permanent CPU loop.  The parent
process had terminated its runtime-store worker after the timeout; the
worker's diagnostic owner record and Emacs lock were consequently stale.

The exact Daily session was small: its checkpoint payload was 4,088 SQLite
bytes and its 12 records totalled 14,160 payload bytes.  The canonical database
was about 3.56 GB overall, with a 1,092,648-byte catalog projection containing
1,263 entries.  This rules out oversized replay of the resumed Daily session
as the immediate explanation for the UI stall.

Read-only extraction of the current catalog followed by production-path
measurement took about 0.53 seconds for parent encoding/preflight.  On a
disposable APFS clone of the database, direct worker =catalog-put= took about
0.36 seconds and the complete parent/subprocess protocol write took about 1.12
seconds.  Raw catalog size and the current durable contents therefore do not
reproduce the 60-second stall by themselves.  The remaining trigger involves
live concurrency, process liveness, or another timing-dependent condition; its
lower-level cause is not yet proven.

* Source evidence

=e-chat-service-create-participant= first creates the provisional session,
then installs a deferred participant binding, commits the session admission,
and finally publishes the participant.  For SQLite,
=e-session-commit-board-admission= publishes the primary records, commits the
aggregate reservation, and then attempts rebuildable catalog and checkpoint
projections.  Projection failure after the primary commit is deliberately
recorded rather than reported as an uncommitted primary mutation.  The durable
state therefore narrows the first unavailable transition to that derived
projection interval.  =catalog-put= is the awaited operation at that boundary,
but the old diagnostics do not distinguish it from a concurrently active
request that may have blocked it.

At the incident revision, =e-runtime-store-await= applied one 60-second
wall-clock deadline and froze the entire shared store when it expired.  The
timeout error recorded only the request kind (=read= or =write=), not the typed
body operation, request id, queue state, or concurrently active request.  Every
later submission replaced that cause with the generic unavailable message
shown in the report.

At the incident revision, the worker's ordinary =status= operation also ran
=PRAGMA quick_check=.
=e-session-storage-sqlite-ordered-barrier= uses that status operation as a
supposedly narrow ordering fence.  On this database the check takes about ten
seconds.  This is an independent scaling defect: explicit integrity checking
already has its own =store-integrity= operation, so an ordinary status/barrier
must not scan the database.  Current repository and project source has no
production caller of that session finalization/barrier path during Daily
admission, so it is not yet accepted as the direct cause of this incident.

* Implemented containment and diagnostics

Commit =eb091148= makes ordinary worker status constant-cost and leaves
=PRAGMA quick_check= and =PRAGMA integrity_check= under the explicit
=store-integrity= operation.  It also records typed operation and transport
kind for timeouts and worker exits, retains the first unavailable cause across
later submissions and callback errors, and exposes active operation and first
cause through bounded runtime status.

Commit =478de8bf= distinguishes an expired queued request from an ambiguous
submitted request.  It removes and fails only the unsent request, records the
active request that blocked it, and keeps the shared worker available.  The
submitted timeout path still freezes the store because its commit outcome can
be ambiguous.

Repository-side validation passed 16 runtime-store tests, 15 session SQLite
tests, 17 Board SQLite tests, and 14 default-runtime SQLite tests.  Independent
reviews found no remaining blocker in either slice.

The queued-timeout regression holds one shared-runtime write, queues a
=catalog-put=, expires that queued request, then proves the earlier write
commits, the worker remains live, and the cancelled catalog is never
published.  This contains the destructive Daily failure mode when the GUS
catalog write was queued.  It does not claim to eliminate a genuinely stalled
submitted operation.  The fresh run has now reported that cause: the
=catalog-put= itself was submitted and stalled, so queued-request containment
was insufficient.

* Why existing deterministic and graphical tests missed the recurrence

The test contract accepted the wrong boundary for this case.  Generic runtime
tests intentionally assert that every submitted write timeout freezes the
shared store because acknowledgement may be ambiguous.  They never require the
adapter to resolve that ambiguity using an identity committed atomically with
the SQLite mutation.

The session integration test for primary success with projection failure stubs
=e-session-storage-sqlite-write-catalog= to signal before transport.  It proves
the primary commit survives a local projection error, but it cannot exercise a
projection that has been submitted to the worker, times out, and triggers
global shutdown.  Projection-bound tests call =catalog-put= against temporary
databases and prove finite size, not recovery under a stalled worker.  The
large-session fixture exercises one 15,722-record paged replay, not concurrent
Daily/Board activity plus a 1,263-entry whole-catalog rewrite.

The graphical E2E suite has no Daily scenario that stalls a submitted
=catalog-put= at the worker boundary.  This is not fundamentally a redisplay
failure, so ordinary UI assertions would not discover it without deterministic
fault injection in the real default-runtime composition.  Calling the earlier
package "graphically not applicable" was too narrow because the user-visible
timer and responsiveness failure is an important composed outcome even though
the defect is owned below presentation.

* Required correction after the recurrence

The correction belongs at the ACID storage boundary, not in session or Board
policy.  SQLite already decides atomically whether each mutation commits or
rolls back.  The adapter must make that outcome observable across loss of the
worker acknowledgement: give each write a durable request identity and record
that identity, an exact request fingerprint, and a result proved to fit its
complete correlated success response in the same transaction as the mutation.
After a timeout, replace the worker and replay
the same identity.  The worker returns the committed receipt when present or
executes the transaction once when absent.  A mismatched fingerprint is a
protocol error.  Reads can be retried after reopening.

Receipt retention must be bounded without weakening deduplication.  Because
the runtime has one ordered active write, acknowledgement can advance a
per-runtime durable watermark; receipts older than the acknowledged prefix can
then be removed.  A newly exclusive runtime can discard receipts belonging to
dead prior runtime identities.  These are persistence-adapter mechanics and
must not appear as per-operation recovery flags in application code.

The deterministic acceptance scenario must use the real default runtime,
session storage, and Board composition; inject a worker-side stall after
=catalog-put= submission; queue a Board transition behind it; and prove all of
the following:

- the already-committed canonical primary remains authoritative;
- the queued Board request is not lost to a global frozen state;
- the timed-out request resolves to its one durable result whether the injected
  stall occurs immediately before or after commit;
- worker replacement/reopen resumes the same ordered request stream safely;
- a subsequent canonical write succeeds; and
- neither recovery nor reconciliation duplicates a semantic side effect.

The original canonical database was only read and remains unchanged.  All
write probes used a disposable clone.

* DP4 implementation status (repository-side)

The runtime-store scheduler now retains the immutable preflight frame for a
submitted request, fences a malformed/lost worker once, and replaces it before
replaying that same frame.  Generic SQLite writes persist a request-id,
complete semantic replay-frame fingerprint, and a result bounded against the
complete =:id= / =:ok= / =:result= success envelope in the mutation transaction;
the replacement either returns that receipt or performs the absent mutation.
Reads retry through the same bounded replacement.  A second transport failure
exhausts recovery with the first typed cause and settles owned work once.

Schema version 5 adds the private receipt and singleton runtime-state
relations.  Ordinary v4 open still rejects without mutation; the explicit
offline upgrader creates and verifies its backup, installs the v5 relations in
one transaction, and rolls back a fault.  An idle clean close now retires the
same runtime identity transactionally, so a lost close acknowledgement uses
the same replacement boundary.

Focused deterministic evidence now passes for the three transaction fault
points (before COMMIT, after COMMIT, and after response formation), exact
full-success-response receipt bounds through original emission and receipt
replay with one-over mutation rollback, receipt collision/watermark,
parent-boot/PID/process-start lifetime, live-parent refusal, prior-boot and
PID-reuse reclamation, retired replacement, repeated clean lifecycle rows, and
zero-or-owned receipt counts.  Parent boot is now an opaque host-boot token
derived from PID 1's start identity, not an Emacs-instance nonce; separate
batch Emacsen prove the same boot token with distinct PID/start identities.
Queued waiters observe the earlier active
deadline, while replacement-open loss and ownership contention exhaust once
with the original typed cause.  The real session-SQLite plus Board timer composition
uses one-shot worker-side =catalog-put= faults before and after COMMIT and continues its
queued pickup transition; the isolated graphical chat/Board witness exercises
the same path through =e2e/run-graphical-tests.sh=.  The v4-to-v5 fixture
preserves canonical records, verifies backup and ordinary-open rejection,
rolls back injected faults without either v5 table, and recovers a faulted
write after upgrade.  The fresh production-path 16 MiB retained-frame recovery
probe passed at 344,948,736 bytes peak RSS, below 536,870,912 bytes.

Exhausted close recovery now has direct deterministic evidence: a pre-COMMIT
retirement loss plus failed replacement leaves the singleton unretired and its
uncertain write receipt present until controlled prior-boot cleanup reclaims
it.  A committed lost write acknowledgement also rejects a competing
different-parent open while the original parent is live, then replays once
under that original identity and retires its receipt through the next
acknowledgement watermark.
