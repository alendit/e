#+title: e-chat board final output keeps progress investigation

* Evidence

- The captured transcript rendered the final assistant response above a live
  activity tail that continued to report elapsed thought time.
- =e-board-runtime--handle-harness-event= publishes board output only while
  handling =turn-finished=, then publishes a separate =turn-summary= activity.
- =e-chat-service--message-event= translated the output to a generic assistant
  =message-added= event and discarded the fact that the output was terminal.
- =e-chat--render-event= intentionally keeps progress active for generic
  assistant messages because those may be intermediate provider output.

* Root Cause

The board adapter erased a terminal fact at the shell boundary.  Although a
board output is created only after the harness turn has finished, its public
message event was indistinguishable from an intermediate assistant message.
The presentation therefore depended on a second board row, =turn-summary=, to
stop progress.  Bounded asynchronous delivery can separate those rows and
leave the UI presenting an impossible state: final answer plus live work.

* Acceptance Test

- A board output event is identified as terminal presentation.
- Rendering such output settles progress without waiting for the terminal
  summary event.
- An ordinary assistant =message-added= event remains intermediate and keeps
  progress active until an explicit terminal event.

* Fix

- =e-chat-service--message-event= now preserves the runtime's terminal fact as
  =:terminal-output= on board-derived assistant messages.
- =e-chat--settle-successful-turn-presentation= owns idempotent successful-turn
  settlement and is called by either the terminal output or the later
  =turn-finished= event.
- Generic assistant messages remain non-terminal, preserving intermediate
  answer and provider-retry behavior.
