#+title: Duplicated Composed Chat Composer Investigation
#+startup: overview

* Evidence

The 2026-08-05 screenshot shows one transcript followed by two panes with the
identical internal composer buffer name.  The selected composer occupies rows
75--80 and the extra composer occupies rows 80--85.

A bounded live =emacsclient= probe confirmed:

- both windows displayed the same =e-chat-composer-mode= buffer;
- the selected window's =e-chat-composer= parameter named the visible
  transcript;
- the extra window's ownership parameter was nil;
- the composer buffer's own =e-chat--surface-transcript-buffer= still named
  the correct transcript; and
- the transcript's pair cache still contained the selected composer window.

This is not a second composer buffer and not duplicate harness state.  It is a
second presentation window restored for the same internal buffer.

* Why The Previous Fix Failed

The 2026-08-03 fix handled mode reload by treating the custom
=e-chat-composer= window parameter as the live ownership source.  It rebuilt a
lost pair cache from marked windows and explicitly preserved unmarked windows
as possible manual displays.

That assumption was too narrow.  Workspace or window-state restoration can
recreate a window showing the composer buffer without restoring the custom
window parameter.  The focus/activation path then creates or retains the
proper marked composer next to the transcript, while reconciliation exempts
the unmarked restored view.  The exemption is the exact reason the duplicate
survived.

An =e-chat= composer is an internal part of one transcript surface.  There is
no supported independent/manual composer display, so the exemption modeled a
use case that does not exist and added complexity without preserving a real
contract.

* Design

The composer buffer now owns the stable in-process relationship through its
buffer-local =e-chat--surface-transcript-buffer=.  Window pairs and custom
window parameters are derived presentation state.

Reconciliation now:

1. finds every frame window displaying the transcript's composer buffer,
   regardless of its window parameters;
2. retains live cached pairs and repairs their derived ownership parameter;
3. reconstructs missing pairs from composer windows directly below visible
   transcript windows;
4. repairs the ownership parameter on reconstructed pairs; and
5. removes every deletable composer view that is not paired with a visible
   transcript window.

The existing window-configuration refresh path now reconciles before fitting
composer height.  That makes host workspace/window restoration converge without
adding another focus hook or another persistent state store.

* Architecture Self-Check

1. The slice independently restores the one-transcript/one-composer invariant.
2. It moves toward a composed chat shell whose activation is idempotent under
   host window restoration.
3. Host window metadata is uncertain and reversible; composer-to-transcript
   buffer identity is stable for the buffer lifetime and is modeled directly.
4. =e-chat= owns the behavior because it owns chat presentation windows.
5. Coupling is reduced: reconciliation no longer depends on a host preserving
   custom window parameters.
6. No dependency points from harness policy toward the presentation shell.
7. Window discovery, repair, fitting, and deletion remain at the display edge.
8. No state is added.  Existing window parameters and pair caches remain
   derived, frame-local presentation state.
9. Reconciliation scans the selected frame's bounded window list only during
   existing display/window-refresh work.
10. The composer buffer has one transcript owner; each visible transcript view
    may retain one paired composer view.
11. Workspace restoration and mode reload are supported.  Independent manual
    display of an internal composer is explicitly not a compatibility contract.
12. The obsolete distinction between marked shell windows and unmarked
    "manual" composer windows is removed.
13. Deletable duplicate windows are repaired; unexpected window errors still
    surface.
14. The regression creates the observed marked/unmarked duplicate layout and
    exercises the real window-refresh lifecycle.

* Validation

The regression first failed with two composer windows remaining after refresh.
After the fix:

- the new regression plus the adjacent buffer-switch and reload reconciliation
  tests pass: 3 passed, 0 unexpected;
- the chat suite excluding its pre-existing fixed-timeout async index-load test
  passes: 323 passed, 0 unexpected, 1 optional skip;
- the unfiltered chat suite reports only that same async index-load timeout,
  which also times out when rerun alone;
- =eldev compile -W lisp/shells/chat/e-chat.el= passes; and
- =git diff --check= passes.

The running Emacs was inspected only with bounded read-only probes and was not
reloaded.
