#+startup: overview

* Live Evidence

A bounded read-only probe of the running Emacs found two active bindings on
board =brd_01M0CM40TACCWQKE54ATDZ6EJB=:

- interactive Daily session =20260819T090231-836e450c6b4d=;
- background Org Canvas/update session =20260819T090232-04fe6b5fe275=.

Both restored bindings had =default-tags= set to =(main)=, no exact default
target, and an active =(:tags (main))= pickup subscription.  The durable record
for the second session identifies it as the Org Canvas for the same Daily file
and records the shared board ID and principal.

One visible input, =msg_5182=, consequently produced two private source turns,
one per participant.  The interactive turn had three failed provider requests
before succeeding; the update turn independently had three failed provider
requests before succeeding.  Both private turns emitted =turn-finished=, not
=turn-failed=.

The provider request lifecycle retained only =status= and elapsed time for the
failed attempts.  It did not retain the transient error detail after the
successful retry, so the exact upstream failure cannot be recovered from the
current projection.

* Source Evidence

=e-chat-service-create-participant= accepts participant-specific routing and
installs it in the process-local binding.  Grimoire creates the Daily update
participant with a =grimoire-update= pickup selector, self-only observer,
=grimoire-update= default tags, and =:self= default target.

The historical defect was that the chat service persisted =board-id=,
=principal=, and the later association role in =board-session-state=, but not
the routing policy.  On restart,
=e-chat-service--bind-session= reconstructed the binding with generic defaults:
=(:tags (main))= pickup and observer selectors, =(main)= default tags, no exact
target, and a newly generated participant identity.  The source correction now
persists one complete nested =:routing-policy= for each new binding, containing
the resolved participant id, pickup selector, observer selector, default tags,
and default target.  =e-session= validates the JSON-shaped declarative policy
before changing the association, detaches its values for JSONL, index, and
checkpoint writes, and normalizes replayed tags and message-kind values for
board matching.  The Node writer carries the complete nested board-state object
through its index/checkpoint records.

=e-chat-service= prepares this policy before attachment and resolves =:self=
to the allocated participant id.  =e-board-registry= remains the owner of
participant-id allocation.  Restoration passes the persisted policy to the
attachment boundary instead of re-inferencing it.  A malformed policy fails
before attachment; a role-bearing legacy owner remains readable with its
historical defaults, while a legacy participant record without a complete
policy fails closed instead of being silently rebound to =main=.

The background participant consequently stopped being private after every
restart and began consuming ordinary interactive chat input in the historical
failure state.  The corrected source prevents that new binding path.  The
provider-free fresh/restart recipient proof is now covered by
=e-chat-test-board-routing-isolated-after-restart-and-settles-selected-only=.

The following retry-status omission is a historical observation from before
the partial fix recorded below; it is not a current-source claim.  It was a
second presentation defect which amplified the symptom.
=e-board-runtime--visible-harness-activity-types= then published provider
request failures but omitted =turn-retrying=.  The chat shell had a dedicated
=turn-retrying= status renderer, but board-backed chat did not receive that
event.  It therefore rendered each retryable provider failure as
=Thought failed after ...= without explaining that the same turn was being
retried.  Activity from both private turns was correlated to the same causal
board input, so their retry rows appeared together.

* Conclusion

The primary defect belongs to the board-backed chat application service.  A
participant's routing policy is durable session identity: restoration must
recreate the same participant ID, pickup selector, observer selector, default
tags, and default target instead of silently substituting main-chat defaults.
This must be stored and restored by =e-chat-service=; callers such as Grimoire
should not need a restart hook that re-specializes the binding.

The retry-status omission is an independent board activity projection defect.
Exposing the existing =turn-retrying= lifecycle edge makes transient attempts
legible, but does not prevent the duplicate turn.  Preserving the routing
policy remains the correctness fix for this report.

The same open routing defect reproduced in the running Emacs after a restart.
The selected Daily root session was
=20260827T083407-654c183c5a6e=.  Its restored background participant session
=20260827T083408-6f5b5c3db895= had again acquired the generic =main= pickup
route.  One ordinary input, board message =msg_1= at =15:24:19Z=, consequently
started both of these private turns:

  =01M11X4VF847VEWKTNFDSY8E78=;
- restored participant =ptc_01M11X4823Y2WVTBZQK5ZGPAVK=, private turn
  =01M11X4VRVY03WGV3F86RCRJ25=.

The restored participant published output =msg_36= and its terminal summary
=msg_37= at =15:24:48Z=.  The selected participant remained active for another
79 seconds and did not publish its output and terminal summary until
=15:26:07Z=.  Between those terminal boundaries, at =15:25:47Z=, the user
submitted board input =msg_74= as a new conversational turn.

The board delivered =msg_74= to both participants.  The restored participant,
whose preceding turn had finished, started private turn
=01M11X7HPJN7TYVWDDEHCTCMW7=.  The selected participant was still running, so
its private journal recorded =msg_74= as =turn-steered= on
=01M11X4VF847VEWKTNFDSY8E78=.  Both participants then published answers to the
second input.

This classification was not visible user intent.  It was a disagreement
between presentation settlement and the selected attachment's execution
state:

- the root binding observes all =main=-tagged board messages, including output
  from the restored sibling participant;
- =e-chat-service--message-event= marks every runtime board output as
  =:terminal-output t= and correlates sibling output to the causal board input;
- =e-chat--render-event= passes such output to
  =e-chat--settle-successful-turn-presentation=, which stops progress, sets the
  status to =done=, and restores the composer;
- =e-chat--submit-intent= independently asks
  =e-chat-service-active-turn-p= about only the selected binding's private
  attachment.  It therefore chose =steer= even though sibling output had made
  the shared presentation look complete.

The repository's focused tests confirm both constituent contracts: board
projection keeps participant-local source turns distinct, while a terminal
board assistant message settles chat presentation before its later summary.
They do not cover the unsafe composition in which a sibling participant's
terminal output arrives while the selected participant remains active.

This incident strengthens the existing conclusion.  Durable restoration of
the participant's private routing policy prevents both duplicate execution and
the premature sibling settlement that exposed the submit-mode mismatch.  The
presentation boundary should also be made explicit: either only terminal output
owned by the selected participant may settle its composer, or settlement must
be derived from an application-level board completion contract that accounts
for every intended responder.  A generic =main=-tagged sibling output is not a
sound completion witness for the selected attachment.

* Accepted Routing Contract

The product contract for this report is explicit:

- *R1 — durable policy:* every new board-backed binding stores one complete
  routing policy inside the existing board-session-state record.  Its fields
  are the resolved participant id, pickup selector, observer selector, default
  tags, and default target, including explicit nil values.  Selectors are
  bounded JSON-shaped declarative data; predicates, functions, unknown keys,
  and unpersistable values are rejected before persistence or attachment.
  =e-session= owns schema and replay validation, =e-chat-service= owns policy
  preparation, and the registry owns participant-id allocation.
- *R2 — routing composition:* a provider-free fresh and restarted board/chat
  composition must show ordinary Daily input delivered only to the selected
  root participant and private-update input delivered only to its intended
  participant, with exact recipient and delivery identities.  The composed
  fresh/restart proof is =e-chat-test-board-routing-isolated-after-restart-and-
  settles-selected-only=.
- *S1 — selected settlement:* only output or terminal activity whose subject
  participant is the selected binding may settle that chat's progress, status,
  or composer.  Sibling output remains renderable and non-settling; a
  board-wide completion aggregator is superseded.
- *S2 — submit intent:* submit/steer is derived only from the selected
  binding's active state.  A sibling terminal event leaves steer active; the
  selected participant's terminal event changes it to submit.  This is covered
  by =e-chat-test-sibling-terminal-events-do-not-settle-selected-turn= and the
  selected-terminal half of the composed restart proof.

Role-less canonical legacy root and owner records retain their established
main defaults.  A participant-role record without a complete policy is an
explicit invalid association for implicit restore; there is no role inference,
default-main fallback, shell-local policy, Grimoire hook, or automatic
migration.  An explicit caller-supplied policy for a legacy open remains a
bounded admission upgrade only when it is complete and validated.

* Partial Fix

- =turn-retrying= is now durable audit activity.  Its normalized provider error,
  structured details, attempt number, and delay are retained through restart;
  credentials are redacted and unusually large details fall back to an
  explicitly truncated telemetry preview.
- Board runtime publishes that durable retry edge instead of filtering it out.
- Chat keeps a provider error distinct from a terminal turn failure.  When the
  harness schedules a retry, the row reads =Provider attempt failed ...; retry
  ...= and includes the retained error.  Only a terminal =turn-failed= event can
  turn the row into =Thought failed=.
- Org Canvas and the starter shell pass the same retry activity through their
  existing chat presentation path.

The candidate restored-routing correction is present in repository source.
The running Emacs was not reloaded; the core/service/session and shell changes
require a restart before they can affect that process.  The bug remains =New=
until an independent fixed-point review accepts the complete package.

* Integrated candidate closure (2026-08-28)

This candidate now has one explicit admission boundary for a board-backed
participant.  Board and routing-policy validation, participant identity, and
the exact next controller command shape are prepared before the association is
attached.  Direct, queued, and controller paths publish the complete session
admission pair only after that preparation succeeds.  The deferred participant
event is published only after successful admission; an expected rejection is
not represented by a durable participant-added event.  The application-service
rollback removes only this operation's unpublished live state, queued writes,
and retained, unacknowledged controller append work.  It does not claim to
retract an acknowledged controller command; unexpected post-submission errors
