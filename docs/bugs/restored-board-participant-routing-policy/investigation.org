#+title: Investigation: Restored board participant loses its routing policy
#+startup: overview

* Live Evidence

A bounded read-only probe of the running Emacs found two active bindings on
board =brd_01M0CM40TACCWQKE54ATDZ6EJB=:

- interactive Daily session =20260819T090231-836e450c6b4d=;
- background Org Canvas/update session =20260819T090232-04fe6b5fe275=.

Both restored bindings had =default-tags= set to =(main)=, no exact default
target, and an active =(:tags (main))= pickup subscription.  The durable record
for the second session identifies it as the Org Canvas for the same Daily file
and records the shared board ID and principal.

One visible input, =msg_5182=, consequently produced two private source turns,
one per participant.  The interactive turn had three failed provider requests
before succeeding; the update turn independently had three failed provider
requests before succeeding.  Both private turns emitted =turn-finished=, not
=turn-failed=.

The provider request lifecycle retained only =status= and elapsed time for the
failed attempts.  It did not retain the transient error detail after the
successful retry, so the exact upstream failure cannot be recovered from the
current projection.

* Source Evidence

=e-chat-service-create-participant= accepts participant-specific routing and
installs it in the process-local binding.  Grimoire creates the Daily update
participant with a =grimoire-update= pickup selector, self-only observer,
=grimoire-update= default tags, and =:self= default target.

The chat service persists only =board-id= and =principal= in
=board-session-state=.  On restart, =e-chat-service--bind-session= reconstructs
the binding by calling =e-chat-service--install-participant-binding= with only
those two fields.  That installer therefore applies its generic defaults:
=(:tags (main))= pickup and observer selectors, =(main)= default tags, no exact
target, and a newly generated participant identity.

The background participant consequently stops being private after every
restart and begins consuming ordinary interactive chat input.

There is a second presentation defect which amplifies the symptom.
=e-board-runtime--visible-harness-activity-types= publishes provider request
failures but omits =turn-retrying=.  The chat shell has a dedicated
=turn-retrying= status renderer, but board-backed chat never receives that
event.  It therefore renders each retryable provider failure as
=Thought failed after ...= without explaining that the same turn is being
retried.  Activity from both private turns is correlated to the same causal
board input, so their retry rows appear together.

* Conclusion

The primary defect belongs to the board-backed chat application service.  A
participant's routing policy is durable session identity: restoration must
recreate the same participant ID, pickup selector, observer selector, default
tags, and default target instead of silently substituting main-chat defaults.
This must be stored and restored by =e-chat-service=; callers such as Grimoire
should not need a restart hook that re-specializes the binding.

The retry-status omission is an independent board activity projection defect.
Exposing the existing =turn-retrying= lifecycle edge makes transient attempts
legible, but does not prevent the duplicate turn.  Preserving the routing
policy remains the correctness fix for this report.

* Partial Fix

- =turn-retrying= is now durable audit activity.  Its normalized provider error,
  structured details, attempt number, and delay are retained through restart;
  credentials are redacted and unusually large details fall back to an
  explicitly truncated telemetry preview.
- Board runtime publishes that durable retry edge instead of filtering it out.
- Chat keeps a provider error distinct from a terminal turn failure.  When the
  harness schedules a retry, the row reads =Provider attempt failed ...; retry
  ...= and includes the retained error.  Only a terminal =turn-failed= event can
  turn the row into =Thought failed=.
- Org Canvas and the starter shell pass the same retry activity through their
  existing chat presentation path.

The primary restored-routing defect remains open.  The running Emacs was not
reloaded.

* Partial-Fix Validation

- Harness, board-runtime, and chat suites: 551 passed, 1 skipped, 0 unexpected.
- Starter shell suite: 24 passed, 0 unexpected.  Focused Org Canvas retry and
  scheduled-render coverage: 2 passed, 0 unexpected.
- Focused graphical retry presentation: 1 passed, 0 unexpected.  The captured
  frame visibly contains the retry schedule and retained provider error and no
  =Thought failed= text.

* Presentation cleanup

The chat shell now keeps retry attempt, delay, and visible error only on the
semantic provider round that renders them.
It no longer copies those values, or structured error details, into the
derived intermittent entry where nothing reads them.
Structured error details remain in durable harness activity; this cleanup does
not discard diagnostic evidence or change retry presentation.

* Retry detail view completion

The chat shell retains the retry's structured provider details only
on its semantic provider round and renders them from the existing turn detail
view.  The compact live row remains unchanged; =d= exposes the attempt, retry
delay, reset wait, error text, and provider details without duplicating them in
the derived intermittent entry.

- Focused retry detail ERT: 1/1 passed.
- Strict =e-chat.el= compilation: passed.

* Architecture Self-Check

1. This is independently useful: retries are truthful and diagnosable even
   before the separate restored-routing defect is fixed.
2. It moves toward shell-neutral lifecycle semantics with presentation owned by
   each shell.
3. The retry decision and error are stable harness facts; wording remains local
   to chat and can change reversibly.
4. The harness owns retry policy and error normalization, board runtime owns
   publication, and chat owns rendering.  Each responsibility has one reason to
   change.
5. Coupling is reduced to the existing narrow =turn-retrying= event contract;
   shells do not duplicate retry policy.
6. Dependencies still flow from presentation toward the stable harness event
   contract, never from harness policy toward a shell.
7. Durable append and board publication remain at their existing runtime
   boundaries; chat performs no lifecycle side effects.
8. The only added state is one bounded durable audit entry per retry, owned by
   the session activity log for the session's normal lifetime.
9. Runtime cost is limited to bounded redaction and one projection on the
   exceptional retry path; ordinary turns do no additional work.
10. =turn-retrying= is a real lifecycle event already emitted by the harness,
    not a speculative interface.
11. Old histories without retry activity still render provider attempt errors;
    no compatibility branch or fallback is required.
12. The inaccurate generic =rate limited= retry label was removed.
13. Expected retry errors are retained and presented; terminal failures still
    surface through =turn-failed= rather than being swallowed.
14. Harness, board, shared chat, starter, Org Canvas, and graphical tests cover
    the behavior at their respective boundaries.
