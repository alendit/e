* Admission boundary review

The controller path does not invent synchronous physical durability.  The
accepted Feature 66 architecture requires board publication not to await the
asynchronous writer.  Within that constraint, the candidate establishes the
narrowest coherent boundary:

- =e-session-create-board-admission= detaches and validates the complete pair,
  including the exact next controller command identity and wire shape, before
  runtime attachment;
- =e-session-commit-board-admission= publishes one =append-batch= obligation,
  rather than two independently replayable appends;
- the Node writer constructs and renames one complete journal, marks both
  records with the same command id, and deduplicates retry by that id;
- only after submission succeeds does the service publish
  =participant-added=; synchronous failure discards the private binding,
  session reservation, and only the target's retained command;
- terminal writer rejection after a successful service return is an
  asynchronous persistence failure, not a retractable participant-admission
  rejection.  It remains visible through the existing persistence error path.

A real writer probe finalized and reopened one service-created participant as
=(:association-role "participant" :participant-id
"review-real-controller-participant")= with an empty outbox.  An injected
terminal response after the successful submission produced the expected
visible persistence error; it did not reveal a false claim that an already
accepted controller command could be synchronously retracted.

The board-side rollback was also inspected.  A forced synchronous commit
failure leaves no =participant-added= for the target, no registry participant,
and no active pickup or observer route.  Setup lifecycle rows that truthfully
precede cancellation are process-local board history, not a replayable
participant membership or routing authority.

* Architecture and design disposition

The package is a useful stopping point: restart preserves private routing and
sibling completion cannot settle the selected conversation.  It moves toward
session-owned durable identity with service-owned admission, registry/board-
owned routing, and shell-owned presentation.

The new boundaries are real and narrow.  Session does not depend on the board
matcher except through its pure consumer-shaped attribute validator; core does
not depend on the shell, Grimoire, or a provider.  The only new durable state is
the complete routing policy at session lifetime.  Pending admission and
selected ownership remain process-local and rebuildable.  Controller retry
uses the existing asynchronous persistence port instead of adding a second
ledger or blocking transport dependency.

Worst-case policy validation is bounded before encoding, and ordinary routing
or presentation work gains no unbounded scan.  Compatibility is explicit:
canonical root/owner records retain historical main behavior, unreconstructable
participant records fail closed, and a complete explicit upgrade is the only
legacy mutation.  Expected admission errors roll back at the owning service;
unexpected persistence errors surface at the controller.

The tests are divided at stable owners and joined by real fresh/restart and
controller/reopen compositions.  No custom Grimoire restart hook, shell-local
routing policy, board-wide completion aggregator, compatibility shim, or
speculative transaction interface remains.

* Residual risks and fixed-point disposition

- As for all accepted board-mode writes, physical controller acknowledgement
  remains asynchronous.  A later operational writer failure remains visible
  through persistence diagnostics; this review does not relabel it as a
  synchronous admission rollback or claim automatic compensation.
- Runtime-generated identifiers and timing are intentionally asserted through
  semantic ownership and replay invariants, not frozen whole representations.
- The user's running Emacs still contains its prior loaded code until a full
  restart; repository-side acceptance does not claim a live reload.
