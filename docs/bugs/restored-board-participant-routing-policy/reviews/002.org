* Findings

** P1 F003 — A failed legacy upgrade can durably wedge the participant identity

Requirement: =COMPAT= and =ATOMIC= require an explicit legacy upgrade to admit
one complete valid policy, while a conflict must fail without changing the
association.

Observed fact:

- =e-chat-service-open-board= persists the supplied upgrade at
  =lisp/core/e-chat-service.el:1007-1017= and only then attempts the runtime
  attachment at lines 1026-1039.
- The registry does not reject an occupied participant id until
  =lisp/core/e-board-registry.el:794-795=, reached from the runtime attachment at
  =lisp/core/e-board-runtime.el:1637-1639=.
- The focused compatibility test stubs the attachment at
  =test/e-modernchat-test.el:503-506=, so it cannot exercise this conflict.
- An exact-revision probe opened a legacy participant with an already occupied
  id.  The first call raised =e-board-registry-id-conflict= after persisting that
  id; a retry with an unused id then raised =e-session-error= because the stale
  durable policy is now authoritative.

Consequence: one expected board conflict converts an otherwise upgradeable
legacy participant into a durable state that ordinary API calls cannot repair.
Restart preserves the wedge.

Minimal remediation: preflight the participant-id and existing runtime/session
attachment conflicts before persisting the upgrade.  Keep the valid policy
durable before actual traffic exposure, but do not write a policy whose known
registry admission cannot succeed.  Use a public registry/runtime admission
query rather than duplicating their tables in the service.

Acceptance evidence: occupy the requested participant id, attempt the complete
upgrade, and prove the original association is byte-for-byte unchanged; then
retry with an unused id and prove one policy, participant, binding, pickup, and
observer before and after reopen.  Cover an already attached session conflict
through the same preflight boundary.

** P1 F004 — Participant rollback cannot cancel session-create or controller work

Requirement: =ATOMIC= requires a rejected participant creation to leave neither
a false root nor a later-replayable durability obligation.

Observed fact:

- =e-chat-service-create-participant= calls =e-harness-create-session= at
  =lisp/core/e-chat-service.el:1074= before entering its =condition-case= at line
  1077.  =e-session-create= publishes the session in memory at
  =lisp/core/e-session.el:3676= before the fallible record/controller submission
  at lines 3678-3687.
- The later catch calls =e-session-abort-created= at
  =lisp/core/e-chat-service.el:1095-1103=, but that API explicitly excludes an
  already submitted controller outbox at =lisp/core/e-session.el:3712-3717=.
  Controller submission retains transport-ready work for later retry at
  =lisp/core/e-session-persistence.el:319-353=.
- With controller command preparation forced to reject the session record, the
  service raised =e-session-persistence-command-error= with
  =:session-live t= and no outbox entry: the owning catch was never reached.
- With sending held and attachment forced to reject, the service removed the
  in-memory session but left two controller commands:

#+begin_example
(:outbox-count 2
 :outbox-ops (("append" "review-orphan" "session")
              ("append" "review-orphan" "board-session-state")))
#+end_example

Consequence: controller retry can persist and reindex a participant session
after the service reported that creation failed.  The earlier preparation
failure leaves an immediately visible false root.  Caller-input preflight does
not make either post-preflight failure impossible.

Minimal remediation: make session allocation, complete board association, and
controller durability one session-owned admission transaction.  Enclose
session creation in the service's failure boundary, and either keep prepared
records outside the outbox until the registry/runtime admission preflight has
succeeded or provide an ordered, idempotent controller abort that removes work
which may already have been applied.  An in-memory =remhash= alone is not a
controller rollback.

Acceptance evidence: inject failures during session-record preparation,
board-state submission, and attachment for direct, queued, and controller
stores.  For the controller case, deliver/retry every retained command after
the failure and then reopen.  Assert no target session/index/journal,
association, participant, binding, subscription, callback, outbox item, or
unsettled-write count; unrelated queued/controller work must remain intact.

** P1 F008 — Routing admission accepts attribute shapes the board matcher cannot execute

Requirement: =R1-SCHEMA= and =R2-FRESH= require every admitted selector to be a
valid board selector, not merely JSON-encodable data.

Observed fact:

- For =:attributes=, the session selector validator accepts any finite bounded
  JSON-shaped value at =lisp/core/e-session.el:2117-2118=.
- The owning board matcher accepts only nil, a keyword plist, or a list of
  key/value conses; other shapes signal at =lisp/core/e-board.el:1870-1882=.
- Exact-revision probes showed both =(:attributes [car "car"])= and
  =(:attributes (car "car"))= accepted by
  =e-session-board-routing-policy-valid-p=, while the matcher raised
  =wrong-type-argument= for each.

Consequence: the service can persist and install a policy declared valid, then
fault its subscription on the first matching attempt.  The durable codec can
faithfully preserve a policy whose routing semantics are unusable.

Minimal remediation: make the board's actual attribute-clause grammar the one
admission authority.  Admit only nil, a well-formed keyword plist, or a proper
alist of key/value conses at the top level, while retaining reversible nested
JSON-shaped values inside each clause.  Prefer one narrow pure board-owned
validator consumed by session durability over a second hand-copied grammar.

Acceptance evidence: route valid plist and alist clauses containing nested
list/vector and symbol/string values before and after JSONL/index/checkpoint
reopen.  Reject top-level vector, scalar list, odd plist, and malformed alist
before any session, association, subscription, or outbox mutation.

** P2 F005 — The structural ceiling is consulted after unbounded collection work

Requirement: =R1-SCHEMA= requires a domain bound which limits rejected as well
as accepted policy work before encoding or mutation.

Observed fact:

- Whole-policy validation first walks plist shape and every field at
  =lisp/core/e-session.el:2123-2148=.  Tag validation runs =proper-list-p= and
  =cl-every= over the complete collection at lines 2089-2096.  Only afterward
  does line 2149 invoke the whole-value budget.
- The budget walker itself pushes every element of a vector in one inner loop at
  =lisp/core/e-session.el:1954-1958= before returning to the node-count check.
  A vector far above 8192 nodes therefore allocates/traverses its whole width
  before the advertised ceiling can stop it.
- The boundary tests at =test/e-session-test.el:189-282= exercise the budget
  helper directly and a vector only one node over; they do not prove bounded
  visits through the public policy validator or a substantially oversized
  collection.

Consequence: caller-controlled rejected policies can still impose work and
temporary allocation proportional to their complete tag list/vector rather
than the declared 8192-node ceiling.  Current documentation's bounded-cost
claim is therefore stronger than the implementation.

Minimal remediation: run the whole-policy budget before plist/field scans and
make vector traversal schedule at most the remaining node allowance instead of
materializing every child task.  Field-specific grammar checks may follow only
after the global cutoff succeeds.

Acceptance evidence: instrument the public validator with substantially larger
tag lists and vectors and prove it visits at most the ceiling plus constant
overhead, invokes no JSON encoder/persistence path, and performs no mutation.
Retain exact node/byte boundary, deep finite, cyclic, and representative-policy
coverage.

** P2 F009 — Ordinary input receives different turn identity live and on replay

Requirement: =S1-IDENTITY= requires a selected conversation turn to keep one
stable presentation identity across live projection and restart/replay.

Observed fact:

- Board input has no participant subject, so the event-level ownership field is
  false at =lisp/core/e-chat-service.el:356-382=; the nested user message is
  independently hard-coded selected at lines 393-410.
- Live =message-added= rendering chooses its turn id from the event-level field
  at =lisp/shells/chat/e-chat.el:8379-8394=.  Replay instead chooses from the
  nested message field at lines 8737-8743.
- A batch probe at the exact revision rendered the same projected input first
  live and then through replay:

#+begin_example
(:after-live ("msg-input:observed:msg-input")
 :after-replay ("msg-input" "msg-input:observed:msg-input"))
#+end_example

Consequence: the live prompt is grouped under a synthetic observed record while
the selected activity/output uses the causal input id; clean reopen rekeys the
prompt.  Turn navigation, transient cleanup, and any record-owned presentation
state can therefore differ before and after replay even though sibling terminal
settlement is now isolated correctly.

Minimal remediation: give ordinary input one authoritative selected
presentation identity in both paths.  Either project the input event as
selected for non-terminal grouping or make live =message-added= use the nested
message ownership fact as replay already does.  Do not broaden terminal
settlement ownership for subjectless output/activity.

Acceptance evidence: send input through the real board observer, render it live,
then rebuild/reopen the transcript.  Assert one identical selected turn-record
key in both states, no =:observed:= input key, and unchanged sibling output and
terminal isolation under the same causal input.

* Architecture and design disposition

The intended ownership split remains sound: session owns durable association
state and persistence carriers; chat service owns application admission and
projection; registry/board owns participant identity and matching; chat owns
buffer-local presentation.  Routing policy has restart lifetime, while selected
ownership remains derived process-local state.  There is no shell-local or
Grimoire-specific compatibility policy, second routing ledger, or board-wide
completion aggregator.

F003/F004 are side-effect-ordering defects at the service/session transaction
join.  F008 shows that selector semantics need one board-owned authority rather
than two almost-equivalent grammars.  F005 is the only material performance
exception: ordinary representative validation is small, but the advertised
worst-case cutoff is not enforced before work.  F009 is a presentation identity
join; its fix should remain local to projection/rendering and add no durable
state.

If this package stopped here, it would be better than the baseline because the
historical main-route widening and sibling terminal settlement paths are closed,
but it is not a coherent shippable stopping point while admitted creation/open
can leave durable invalid state.  The final direction remains exact durable
routing plus selected-owned settlement.  The uncertain selector value domain
is local to one grammar/codec boundary; participant identity, failure atomicity,
and replay-stable presentation identity are stable requirements.  No compatibility
shim is justified beyond the accepted canonical-root and explicit-upgrade cases.
