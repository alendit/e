#+date: 2026-08-11
#+startup: overview

* Status

Resolved repository-side on 2026-08-11.  The running Emacs was not reloaded,
so the identical-task live cache-rate A/B remains pending.

The earlier in-turn provider-anchor fix is validated.  The remaining primary
defect was that =e= discarded the Responses WebSocket connection after every
provider request, losing the connection-local cache that WebSocket continuation
is designed to use.  The adapter now retains one serialized connection per
=e= session and uses incremental continuation only while its transport and
request-property invariants remain valid.  Tool-workflow amplification remains
a separate efficiency concern.

* Primary root cause: one WebSocket per provider request

=e-openai-codex--websocket-request-start= calls =websocket-open= for each
backend request.  On =response.completed= it schedules =websocket-close=.
Every tool follow-up therefore opens a new connection, sends one
=response.create= event, and closes that connection when the response settles.

The adapter still supplies =previous_response_id=, so stored-response
continuation works and the tool loop remains semantically correct.  It cannot,
however, reuse the previous response from the WebSocket's connection-local
cache because that connection no longer exists.

Current official OpenAI documentation states that Responses WebSocket mode is
a persistent connection for long-running model/tool workflows and that
=previous_response_id= uses a connection-local cache for low-latency
continuation.  It instructs clients to send incremental input items on the same
WebSocket.  If an uncached id cannot be resolved, the documented fallback is a
new turn with full input context.

Sources:

- [[https://developers.openai.com/api/docs/guides/websocket-mode][OpenAI WebSocket mode]]
- [[https://developers.openai.com/api/docs/guides/conversation-state][OpenAI conversation state]]

Codex implements that topology in
=codex-rs/core/src/client.rs=.  A =WebsocketSession= retains the connection,
last request, and last response.  Incremental reuse requires both an input
prefix and equality of non-input request properties.  The next request carries
only appended items plus =previous_response_id= over the retained connection.

This difference directly explains why the continuation fix reduced wire input
without preserving the documented connection-local warm path.  It is the
leading explanation for the cache-hit gap, but its exact share requires the
same-task A/B after connection reuse is implemented.  The intermittent =e=
hits are compatible with ordinary provider prompt-cache reuse rather than the
retained WebSocket path.

* Additional cache risks to measure

These are plausible secondary contributors, not established as the cause of
the first-turn zero-cache rounds:

** Cache-key scope

=e-harness--derived-prompt-cache-key= hashes model, project root, active layer
ids, and tool names.  It does not include the session id.  Concurrent sessions
with the same project/layers/tools therefore share one routing key after their
response chains diverge.

Codex defaults =prompt_cache_key= to its session id.  Official guidance says a
key should identify traffic with shared prefixes and recommends partitioning a
key above roughly 15 requests per minute.  A session-scoped key may improve
continuation routing, while the current project-scoped key may improve cold
cross-session instruction reuse.  This needs an A/B measurement after
persistent WebSocket reuse is implemented; changing it first would confound
the primary fix.

Source:

- [[https://developers.openai.com/api/docs/guides/prompt-caching][OpenAI prompt caching]]

** Dynamic instructions between user turns

All backend-neutral system messages become the Responses top-level
=instructions= string.  Current-state context is stable during one =e-loop=
turn, but can change before the next user turn.  Provider-anchor compatibility
intentionally excludes current-state segment fingerprints, so =e= may continue
an anchor while sending different instructions.

The API permits replacement instructions with =previous_response_id=, so this
is not inherently incorrect.  Codex is more conservative: it uses incremental
WebSocket continuation only when instructions and every other context-bearing
non-input property remain equal.  Telemetry should record these property hashes
so the cache impact can be measured rather than inferred.

* Resolution

The OpenAI backend now owns a private WebSocket-session table keyed by the
=e= session id.  Each entry retains the socket, connection identity, last
completed response id, last non-input request properties, reuse count, active
request, and idle-close timer.  This places warm transport state at the backend
adapter that gives it meaning rather than in the harness, session persistence,
or presentation layers.

A completed response no longer closes its socket.  The connection stays warm
for compatible model/tool follow-ups and closes after 300 idle seconds by
default; =e-openai-websocket-connection-idle-seconds= can change that bound.
Cancellation and transport/request errors close immediately and discard the
warm state.  A session permits only one active =response.create= at a time;
different =e= sessions have different connection owners.

Incremental input is sent only when all of these are true:

- the same socket, URL, and headers are still live;
- every non-input request property is equal to the previous request; and
- the requested =previous_response_id= is the last response completed on that
  connection.

Otherwise the adapter sends the separately constructed full request without a
provider anchor.  A closed connection reconnects with full input.  If OpenAI
rejects a connection-local response id as unavailable, the adapter invalidates
that warm state and retries once with full input.  A send failure on a reused
socket reconnects and also retries with full input.  Explicit =store=false=
behavior remains a full replay, preserving its existing contract.

Bounded request diagnostics now report =websocket-connection-id=,
=websocket-reused=, =websocket-reuse-count=, =websocket-request-mode=, and
=websocket-fallback-reason=.  They also recompute continuation and input-count
metadata from the request actually sent, so telemetry does not claim an anchor
was used after a safe fallback.

The repair intentionally does not change =prompt_cache_key= scope or tool-loop
policy.  Those are separable experiments after a live transport A/B and would
otherwise confound whether connection retention fixed the primary defect.

* Architecture self-check

1. This slice is independently useful: it removes per-request socket churn and
   has safe fallbacks even before any workflow optimization.
2. It moves toward a provider-neutral harness with provider-specific transport
   policy kept inside the OpenAI adapter.
3. The stable requirement is serialized same-session reuse.  Idle duration,
   cache-key policy, and workflow reduction remain local and reversible.
4. The OpenAI backend owns the behavior because connection-local continuation
   is an OpenAI transport concern with one reason to change.
5. Coupling is reduced: the harness passes session identity and continuation
   facts through existing options, while socket state stays private.
6. Stable harness/session policy does not depend on the WebSocket library or
   OpenAI-specific lifecycle.
7. Socket open/send/close and timers remain at the adapter boundary; no side
   effect moved into core policy.
8. Added state is ephemeral, per backend and session, bounded by cancellation,
   error, server close, or idle expiry, and is never persisted.
9. The change removes repeated handshakes and restores connection-local cache
   reuse.  Compatibility checks add only bounded request-plist comparisons.
10. The private session record names a real provider lifecycle and does not add
    a shared interface that other backends must pretend to implement.
11. Existing HTTP, injected-request, and explicit unstored behavior remains;
    the obsolete close-after-completion path was removed.
12. The old deferred per-response close timer and its bookkeeping were deleted.
13. Expected incompatibility selects full input; unresolved ids retry once;
    unexpected transport errors surface through the request error callback.
14. Unit tests isolate transport decisions, while focused integration and the
    full suite prove the harness contract did not need unrelated rewrites.
