#+title: Post-cutover startup lacked a repository-owned end-to-end gate
#+startup: overview

* Goal record

- Goal ID: =BUG-E2E-POSTCUTOVER-COVERAGE=
- Behavioral goal: repository-owned isolated E2E exercises the ordinary
  post-migration startup and first chat turn deeply enough to reject common
  root selection, eager transcript replay, and first-response curation
  acknowledgement regressions before live use.
- Direct scenarios: =S-E2E-CUTOVER-LAZY= and
  =S-E2E-CUTOVER-CURATION-ACK=.
- Owning contracts: =E2E-C01= and =E2E-C02=.
- Product authority: the admitted Feature 87 post-cutover behavior.
- Glossary: opt-out; the plan adds test evidence without changing runtime
  vocabulary.

* Report

Feature 87 owner tests proved migration, default composition, and lazy session
loading separately.  They did not run the complete operator-shaped sequence in
one isolated scenario: copy a conventional legacy root, perform the actual
offline same-root cutover, construct =:chat-default= with the environment
override absent, observe catalog-only startup, load one transcript on demand,
and repeat after a cold reopen.

That missing composition gate allowed two production regressions to reach live
use before narrower tests were connected: selecting the retired =sessions/=
child as the SQLite root, and eagerly replaying every migrated transcript at
startup.  This report scopes only the missing deterministic repository E2E; it
does not add provider, graphical, current-configuration, or live-state claims.

The new scenario also exposed one migration omission before P1 completion:
canonical session records and translated checkpoints were imported, but the
rebuildable SQLite catalog was not published.  Cold startup therefore had to
read the first record page of every session to reconstruct stubs.  The bounded
fix rebuilds and publishes only that catalog during offline migration, loading
and unloading one session at a time and leaving checkpoints unchanged.

P2 extends the same disposable cutover boundary through the normal
=:chat-default= Board/chat turn and real OpenAI Responses adapter.  A fake HTTP
transport returns a valid curation-only first response.  Both stateless and
anchored continuations must send one immediate opaque acknowledgement, produce
the final assistant answer, survive a cold reopen, and keep that wire-only
carrier out of durable messages and every later request.
