#+title: Investigation: Canvas New Session Loads an Unresumable Legacy Session
#+startup: overview

* Status

The failure is caused by an eager historical-session hydration in the generic
canvas shell.  The missing-checkpoint guard is behaving as designed; the
canvas lookup reaches it unnecessarily.  No repository fix has been applied.

* Live evidence

The supported read-only probes completed successfully.  The selected buffer
was =02-webassembly-and-clojure.md= in =markdown-mode=, with no chat session id,
status, or harness attached.  The buffer itself was therefore healthy and the
failure occurred before a new canvas session was attached.

The loaded definitions for =e-canvas-attach-current-buffer= and
=e-session--read-checkpoint= came from the installed =e= build.  No raw Emacs
evaluation or live reload was performed.

* Persisted-session evidence

The reported session =20260803T080924-d408dbc0c08b= remains in =index.json= as
an unloaded root session named =Untitled 2026-08-03T08:09:24Z=.  Its 497,665
byte JSONL journal exists, but its checkpoint file does not.  The index entry
contains no canvas attachment metadata for the current Markdown buffer.

Other current index entries demonstrate that =:context-references=, including
=chat-session= canvas attachment metadata, are already available in the
transcript-free session catalog.  Determining whether a buffer matches an
indexed canvas therefore does not require loading session journals.

* Cause

=e-canvas-open-for-current-buffer= first calls
=e-canvas--buffer-canvas-session= so an already-attached canvas can reveal its
existing chat.  That helper iterates every value returned by
=e-harness-session-list=.  For each session it calls
=e-canvas--session-canvas-attachment=, which calls
=e-chat-session-attachments=.

=e-chat-session-attachments= reads live context references through
=e-session-context-references=.  For an unloaded persistent session,
=e-session--get-live= consequently calls =e-session-load-session=.  Loading the
unrelated August 3 entry reaches =e-session--read-checkpoint= and raises
=e-session-checkpoint-missing= before the scan can continue or create the new
session.

The resume check is intentional.  Existing coverage explicitly requires
normal session loading to reject checkpoint-less journals rather than silently
performing an unbounded full replay.  Weakening that persistence boundary would
turn this presentation lookup bug into a runtime safety regression.

* Fix direction

Keep the strict checkpoint rule.  Change the generic canvas shell's existing
canvas lookup to compare the current buffer against attachment metadata from
the session-list entries themselves.  Prefer a narrow chat-session helper for
normalizing attachments from catalog metadata so =e-canvas= does not duplicate
the capability's metadata representation.

Only a session whose catalog attachment actually matches the current buffer
should be opened and hydrated.  A nonmatching legacy session with no checkpoint
must remain untouched, allowing =e-canvas-open-for-current-buffer= to create
the requested new session.

Regression coverage should use a persistent index containing:

- an unloaded unrelated legacy session with a journal but no checkpoint;
- a current buffer with no matching canvas attachment;
- an assertion that opening the current buffer creates a new canvas session
  without trying to resume the legacy entry.

A companion case should prove that a matching attachment in catalog metadata
still selects the existing session.  The present canvas tests use only loaded
in-memory sessions, so they do not exercise this boundary.

* Verification

- =e-session-test-load-requires-explicit-resume-checkpoint= passed, confirming
  the intended resume guard.
- The two focused current-buffer canvas tests passed, confirming the existing
  loaded-session behavior and its coverage gap for unloaded catalog entries.
- The supported live probes remained responsive.
- The running Emacs and persisted session files were left unchanged.
