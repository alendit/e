#+title: Investigation: Grimoire Foreground Daily Corrupts an Ordinary Composed Chat Layout
#+startup: overview

* Live and durable evidence

The user had already repaired the corrupt window tree.  A bounded read-only
=emacsclient= snapshot of the repaired frame established the intended baseline:

#+begin_example
2026-08-19.org                              height 38
*e-chat:Grimoire: Daily 2026-08-19*         height 37
 *e-chat input:*e-chat:Grimoire: Daily...*  height 5
#+end_example

The screenshot instead showed the daily document in both the upper window and
the five-row lower slot, with the transcript between them and no composer.

The affected session was =20260819T090231-836e450c6b4d=.  Its bounded durable
activity projection records the relevant calls in order:

1. The agent called =grimoire-daily-update "2026-08-19"=.  It failed with
   =Window #<window 44 on *e-chat:Grimoire: Daily 2026-08-19*> too small for splitting=.
2. It then called =grimoire-daily-tick "2026-08-19"=.  That attempt reached the
   dirty-sidecar guard and failed without a display operation.
3. After creating the missing raw directory, a final headless
   =grimoire-daily-tick= succeeded.

The corrupt layout therefore came from the first foreground display attempt,
not from the successful headless tick.

The tail of =*Messages*= contained no independent window-layout exception from
the successful tick.  It did retain unrelated =persp-mode= winner-ring save
warnings and the later bounded diagnostic error.

* Source cause

=grimoire-daily-update= opens the interactive daily canvas before starting the
durable controller.  Its display path calls
=grimoire-topic--display-doc-and-chat=, which asks
=e-window-surface-replace= for one ordinary window and then immediately starts
constructing the 2:1 document/chat split.

=e-window-surface-replace= only recognizes an Emacs atomic window root.  Commit
=573d3d81= deliberately changed composed e-chat surfaces from an atomic subtree
to two ordinary adjacent windows so =persp-mode= could save and restore them
without resize corruption.  The helper now returns the selected transcript or
composer leaf unchanged even though e-chat still treats the two leaves as one
presentation surface.

Grimoire consequently mutates only one constituent of the existing chat.  It
can duplicate the daily document into that constituent and leave the old
surface windows in place.  When =e-chat--after-display-buffer= then restores
the new chat composer, =e-chat--surface-display-composer= calls =split-window=
on the undersized partial layout and signals.  The display operation is not
transactional, so the earlier window splits and buffer replacements remain
visible after the error.  That partial state matches the screenshot.

This is a cross-shell presentation-contract regression: the generic replacement
helper still defines a complete surface in terms of atomic windows, while its
e-chat consumer now defines the complete surface by buffer ownership and
ordinary adjacency.

The earlier decision to remove the atom was based on an incomplete diagnosis.
=persp-mode='s writable window state had dropped the built-in =window-atom=
parameter because it was not registered as persistent.  e-chat's subsequent
repair hooks, rather than native atomic structure itself, raced restoration.

* Graphical reproduction

The existing Grimoire graphical regression
=grimoire-topic-graphical-test-daily-replaces-selected-chat-surface= no longer
reaches its assertion.  It fails with =void-variable
e-chat--surface-window-pairs= because the Aug 17 ordinary-window change removed
the registry used by the fixture.

A temporary current-API adaptation was run in the repository's private
off-screen graphical Emacs.  Reopening the layout with the composer selected
reproduced =Window ... too small for splitting=.  Reopening with the transcript
selected left four windows: the daily document twice, the transcript, and the
composer.  No live Emacs state was used or changed by these tests.

* Fix

The immediate cause is the foreground =grimoire-daily-update= display path
partially replacing a non-atomic e-chat surface.  The successful background
=grimoire-daily-tick= only followed that failure and did not cause or repair the
layout.

The repair is confined to the semantically changed chat shell:

- e-chat registers =(window-atom . writable)= and creates the
  transcript/composer pair with =display-buffer-in-atom-window=;
- workspace window-state restoration now preserves that native structure;
- e-chat removes its ordinary-pair deletion emulation; and
- =e-window-surface-replace= and Grimoire remain unchanged.  The existing
  generic helper again sees and replaces the complete native surface.

* Regression and closure

=e-chat-behavior-test-native-surface-replaces-as-one-unit= opens a real composed
chat beside an unrelated window, selects its composer, and calls the generic
replacement API.  It proves both chat constituents disappear, the returned
ordinary window occupies the complete former atom, and the unrelated window is
unchanged.  This is the structural operation used by the Grimoire foreground
display path.

The real =persp-mode= graphical tests additionally prove the atom survives
workspace round trips and native deletion.  Close this bug: no Grimoire,
workspace, harness, or generic surface API learned any chat-specific behavior.
The complete isolated graphical suite passed all 21 tests.  The focused
chat/surface ERT selection passed 349 tests with two optional-dependency skips,
and focused plus full compilation passed.  The user's running Emacs was not
reloaded.
