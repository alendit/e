#+title: Investigation: Board Timer Reenters a Durable Mutation Barrier
#+date: 2026-09-04
#+startup: overview

* Status

Reproduced from live evidence and explained at the ownership boundary.  This is
not a recurrence of Feature 92's lost-acknowledgement freeze: Emacs responds,
the v5 worker remains alive, and the runtime acknowledgement watermark
continues to advance.  A timer instead attempts a second durable mutation on
the same Board while the first synchronous Board storage barrier is still
servicing timers.

The exact timer producer is not proven without a Lisp backtrace.  No live
mutation, reload, signal, or process termination was performed.

* Live evidence

- =scripts/e-live-probe ping= returned =:responsive t=.
- =scripts/e-live-probe chat= found the Daily session idle with its harness
  present.
- OS inspection found the main Emacs process and one live v5 runtime-store
  worker.  The worker was sleeping at 0 percent CPU rather than missing or
  spinning.
- Read-only SQLite inspection found one live runtime identity.  Its
  acknowledgement watermark and retained receipt IDs advanced from writes 99
  to 115 during the investigation, proving that the shared store was not
  globally unavailable.
- The Board ID in the timer error had no committed =boards= row at the sampled
  instant.  The rejected timer therefore raced an in-memory/new-board durable
  transition rather than reporting a permanently frozen stored Board.
- A three-second non-signalling process sample captured the main thread inside
  =timer_check= and deep Lisp execution.  Garbage-collector stack marking was
  material, with a 317.3 MiB current footprint and 1.1 GiB recorded peak.  That
  explains why the overlap is user-visible but does not by itself identify the
  semantic timer producer.

* Source cause

=e-board--call-with-storage-barrier= sets =e-board-mutation-frozen-p= before
calling a synchronous durable operation and clears it in =unwind-protect=.
Any second Board mutation entering the same function while that flag is set
signals =e-board-mutation-frozen= with only the Board ID.  Runtime-store waits
service Emacs timers, so a timer can run on that same stack before the first
storage response releases the barrier.

The code already has the correct owner seam:
=e-board--defer-after-storage-barrier= queues an admitted callback while the
Board is frozen and =e-board--release-storage-barrier= schedules it after the
commit barrier clears.  Input-routing runtime callbacks use this seam in
=e-board-runtime--drain-input-routing=.  The live error proves that at least one
other timer-driven mutation path still enters the public mutation boundary
directly.

* Why Feature 92 E2E missed it

The focused and graphical Feature 92 tests created this topology:

1. schedule a timer that calls =e-board-pickup-start-delivery=;
2. synchronously execute session-owned =catalog-put=; and
3. inject worker loss before or after the catalog transaction COMMIT.

That proves shared runtime-store ordering and acknowledgement recovery, but
=catalog-put= does not hold the Board object's =mutation-frozen-p= barrier.
When the timer fires, it is the first mutation on that Board and cannot produce
the live error.  The graphical test copied the same topology, so it exercised a
real UI and real worker while still missing same-Board reentrancy.

The review therefore overstated “timer-driven Board composition.”  It proved a
Board timer behind a session-storage operation, not a Board timer behind
another durable operation on the same Board.  Existing tests also accept
=e-board-mutation-frozen= for deliberately reentrant callers, but do not require
every admitted production timer path to defer or fail the test on an uncaught
timer error.

* Required correction and E2E contract

- Hold a real durable mutation on one storage-backed Board at the worker
  response seam while leaving the Emacs event loop able to run timers.
- Fire an admitted production timer that performs a different durable mutation
  on that same Board while the first barrier is active.
- Make the test fail on any =Error running timer= or
  =e-board-mutation-frozen= escape; do not merely poll the eventual Board
  projection.
- Prove the timer mutation is queued behind the existing barrier, commits after
  release, and occurs exactly once.
- Cover the actual production timer owner once identified, plus a focused
  owner-level test for the generic deferral contract.
- Add an isolated graphical case with the real chat/Board composition and an
  inspectable before/during/after transition.  A worker crash is unnecessary;
  the essential seam is a delayed same-Board acknowledgement while timers are
  serviced.
- Keep latency and garbage-collection pressure observational.  The semantic
  gate must reproduce the race deterministically without depending on a large
  live database or wall-clock duration.

* Runtime disposition

The running Emacs, worker, and canonical v5 SQLite store were inspected
read-only and left unchanged.  The current Daily session was not restarted or
reloaded.
