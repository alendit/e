#+title: Investigation
#+startup: overview

* Summary

Mostly confirmed from source and durable store records.
Board behaved as designed: it cancelled the agentic worker when the Daily run's 900-second deadline passed.
The faults are in the OpenAI WebSocket adapter:
1. It opens a new connection with a blocking TLS connect on the main thread.
   That froze all of Emacs for about 150 seconds.
2. Its idle timers do not check real elapsed idle time.
   When the freeze ended, every in-flight request failed at once with a false idle timeout.
3. It has no total time limit per request and writes no durable progress while a response streams.
   So the agentic worker's request ran until the Daily run deadline stopped it.

Two points remain open: why the connect took about 150 seconds, and what the agentic request did after the connection opened.

* Source inspected

** The connect blocks the main thread

- =lisp/adapters/openai/e-openai-websocket.el=, =e-openai-websocket--session-open= (line 146) calls =websocket-open= without =:nowait=.
- The websocket package (=websocket.el= line 622) defaults =nowait= to nil.
  It then calls =open-network-stream ... :type tls :nowait nil= (line 717).
  DNS, the TCP connect and the TLS handshake all run synchronously on the main thread.
  No timer, process filter or other session can run until they finish.
- =e-openai-websocket-request-start= (line 313) opens the connection inside the call (lines 371 and 578) when no compatible connection exists.
- =lisp/core/e-loop.el= writes =provider-request-started= through =publish-provider-request= only after request start returns (lines 791, 1954, 2089).
  This is why the agentic worker's event carries 07:27:58 while its turn began at 07:25:27.

** The idle timeout fires falsely after a freeze

- The idle timeout is a one-shot =run-at-time= timer created by =arm-timeout= (line 381) and re-armed on each frame (lines 496, 518).
- When Emacs is blocked, due timers cannot fire.
  When the block ends, the timers run before the waiting socket data is read.
  Each timer fails its request without checking when the last frame actually arrived.
- This matches the six requests that all failed at 07:27:58 with a 60-second message after 150–160 seconds.

** The queued store write expires during the freeze

- =lisp/core/e-runtime-store.el=, =e-runtime-store--expire-overdue-queued= (line 1607) fails a queued write that has waited longer than =e-runtime-store-request-timeout= (60 seconds, line 74).
- The Gmail worker's write was queued during the freeze, so it expired as soon as the store's timer could run.

** The agentic request has no total time limit

- The adapter limits only the time between frames.
  There is no per-request total deadline.
- e writes nothing durable while a response streams.
  Other sessions write =token-usage= and reasoning records only at completion.
- After =e-ws-7= opened, =arm-timeout= ran (line 571) and the body was sent.
  If no frame had arrived, the timer would have fired around 07:28:58 and written an error and a =turn-retrying= event.
  Neither exists.
  The likely reading is that frames kept arriving and kept re-arming the timer, for example a long =max=-effort response while OpenAI was overloaded.
  This is an inference.
- =send-current-body= (line 481) calls =websocket-send-text= right after the blocking open returns.
  The code does not wait for the server's =101= upgrade reply.
  A request stuck before the upgrade completed cannot be ruled out.

* Live access

The WebSocket process for =e-ws-7= no longer existed when this was investigated.
No live connection state could be inspected.
The evidence above comes from durable runtime store records and the Daily run's raw outputs.

* Rejected explanations

- The collector script blocked Emacs.
  Its post-exit work is parsing a 44 KB JSON file, and it finished before the agentic turn began.
- Board mishandled the deadline.
  The cancellation happened exactly at the configured 900-second run deadline.

* Next steps

1. Open the WebSocket with =:nowait t=.
   Send the body only after the =101= upgrade completes, and add a separate connect timeout.
   This affects every session that opens a new connection, not only Daily runs.
2. Make the idle timer compare real elapsed time since the last frame before failing a request.
   Re-arm it for the remaining time when the request is not actually idle.
3. Add a total time limit per provider request.
   Write a bounded durable progress record while frames stream, so a long response is distinguishable from a hang.
4. Consider a lighter model and effort for Daily gatherers whose work is a deterministic render of already collected data.
   This is a Grimoire configuration choice, not an e bug.
