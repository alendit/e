#+title: Investigation: Board-backed Steering Does Not Settle Its Input
#+startup: overview

* Conclusion

Board-backed steering is broken as an end-to-end operation.  The active-turn
path writes the steered input into the session and gives it to the next model
request, but never emits the =input-consumed= receipt that completes its Board
delivery.  The pickup stays =claimed= at the participant FIFO head.  Later
inputs stay =pending=, even after the turn finishes.

The primary architectural defect is an incomplete steering contract across
Board claim, session input, model use, and Board receipt.  A missing receipt
turns an apparently successful steer into a permanent queue block.  Ordinary
topic reopening also lacks reconciliation of the claimed head.  SQLite
persists the claim and FIFO order correctly; this is not evidence of database
corruption.

* Execution trace

1. Plain chat submit during an active turn chooses steering
   (=e-chat--submit-intent= in =lisp/shells/chat/e-chat.el=).  The chat service
   posts a Board input with mode =inject=, claims its ready pickup, and calls
   the attached turn port's steer operation
   (=e-chat-service--sql-submit-claimed-pickup=).
2. =e-harness-attached-turn-steer= retains the prompt and delivery metadata
   as pending steering input.  =e-loop= drains it at the next provider
   boundary, appends a user message, and sends it in the next model request.
   The live session's URL message proves this path ran.
3. =e-harness-turn.el= emits =input-consumed= for a directly submitted turn
   after appending its first user message.  Neither steering drain in that
   file emits the corresponding receipt.  =e-chat-service--sql-harness-event=
   transitions a pickup to =consumed= only on that receipt.
4. =turn-finished= reports execution outcome and clears process-local delivery
   correlation, but it does not settle the pickup.  SQLite promotes the next
   FIFO item only when the claimed head reaches a terminal pickup transition
   (=e-board-sqlite-worker--board-pickup-transition=).

The direct-submit receipt is emitted after =e-session-append-message= accepts
an asynchronous write request, before its commit acknowledgement.  Adding an
equally early receipt to the steering drain would clear this observed queue in
the happy path but would still allow Board consumption to get ahead of a
failed session write.  Steering needs a commit-aware settlement boundary, not
just another optimistic event.

* Isolated reproduction and coverage gap

A disposable batch Emacs reproduction used the real harness turn and attached
port with a held fake backend.  It submitted one Board input, steered a second
Board input while the first request was active, then finished both requests.
The second input appeared in the next backend request.  The first input emitted
an =input-consumed= receipt; the steered input emitted none:

#+begin_example
(:steered-in-next-request t :first-receipt t :steered-receipt nil)
#+end_example

The existing direct-input receipt test
=e-harness-test-board-consumption-receipt-carries-endpoint-fence= covers only
initial submit.  =e-harness-test-steer-active-turn-drains-in-same-turn= proves
model delivery of steering input but supplies no Board delivery identity and
does not assert its receipt.  The Board FIFO integration tests exercise queued
follow-ups, not an =inject= pickup steered into a running turn.

* Secondary recovery gap and safety constraint

=e-chat-service--sql-resume-ready-scan= handles a =claimed= head only when its
binding has =continuation-owner-p=.  Ordinary Grimoire topic creation and
reopen call =grimoire-topic--start-agentic-session= without that flag.  The
pickup observer can therefore see the claimed head but does not settle or
retry it.  There is no scheduled claimed-head expiry in the current SQL
service.  Subsequent input admission returns successfully while its pickups
wait behind the head, which explains the misleading =queued= status with no
active turn.

The Feature 66 plan explicitly calls harness acceptance/consumption
reconciliation partial, defers scheduled expiry/rebind reconciliation, and
lists steering transfer among the remaining pickup work.  The implemented
direct-submit and queued-input paths have receipt coverage, but the active
steering path crosses that unfinished boundary.

The chat header's =Board runs: idle= is the orchestration run count, not a
pickup-liveness check.  The UI therefore gives no visible age or reason for
the blocked claimed head even as later submissions continue to say =queued=.

Blindly retrying position 2 would be unsafe: its user message and exact Board
delivery ID are already in the durable session, and the completed turn used
the URL.  Recovery must distinguish a committed consumption from an
uncommitted handoff, or record an explicit uncertain outcome.  A timeout that
simply resubmits the prompt can duplicate model execution.

* Resolution

The runtime store now performs Board head claim, session user-message append,
pickup consumption, successor promotion, and its replay receipt inside one
SQLite write transaction.  A failed append rolls the claim back.  A worker
crash before commit rolls the whole write back; a crash after commit replays
the one recorded result.  There is no application-side transaction or polling
protocol for this boundary.

Chat delivers the already committed message through its attached harness port.
It does not append it a second time.  A queued pickup remains =ready= while a
turn is busy.  At the next provider boundary, the loop waits for its async
session context refresh and includes a committed steer once.  Direct input
consumption receipts now follow append acknowledgement.  The =input-consumed=
activity event is durable so a continuation message admitted before its turn
exists can be correlated with the turn that actually ran it.

The old automatic retry of a =claimed= pickup was removed.  It could duplicate
an input already recorded in the session.  The observed live pickup predates
the transactional fix and needs a one-off offline repair.  The repair tool in
=repair-claimed-head.el= refuses the live store path, defaults to dry run, and
requires the exact Board association, FIFO shape, matching session delivery
identity and content, and finished-turn evidence.  In apply mode it uses the
Board worker's normal =consume= transition inside one SQLite transaction to
promote the next input.  It has not been applied to the user's running store.

The transaction closes the original claimed-head stranding path.  A process
loss after that commit but before harness delivery still leaves an admitted
session message whose execution is not automatically resumed; provider
execution recovery is a separate lifecycle concern.  The runtime reports a
visible delivery error if a synchronous handoff fails.  No generic claimed
head retry or UI age indicator was added to the steady-state path.

* Verification

- The real SQLite chat composition steered into a held provider turn, observed
  the steered input once in the next request, and ran a later queued input.
- Worker tests covered rollback after a failed session append, FIFO fencing,
  and worker loss before and after commit.  The replay produced one session
  message and one pickup consumption.
- Continuation tests covered ready-head deferral and outcome backfill across
  restart.  The bounded outcome query correlated a committed message with its
  durable consumption receipt.
- Repository tests passed: Board service 41/41, session worker 28/28, harness
  and loop 99/99, session async 20/20.  Changed Lisp compiled successfully;
  =e-chat-service.el= retained three pre-existing warnings under ordinary
  compilation, so warnings-as-errors did not pass.

The live Emacs and its store were not reloaded, stopped, or changed.  Core
runtime changes require an Emacs restart for new behavior.  The offline repair
remains a separate operation after a consistent store copy and dry-run review.

** Offline repair procedure

Take a consistent SQLite backup into a private directory; copying only the
main database file while its WAL is active is insufficient.  Run the one-off
tool with =E_BOARD_REPAIR_STORE_DIR= pointing to that copy:

#+begin_example
E_BOARD_REPAIR_STORE_DIR=/private/path/to/offline-copy eldev exec -R -f docs/bugs/board-steered-input-strands-fifo/repair-claimed-head.el
E_BOARD_REPAIR_STORE_DIR=/private/path/to/offline-copy E_BOARD_REPAIR_APPLY=1 eldev exec -R -f docs/bugs/board-steered-input-strands-fifo/repair-claimed-head.el
#+end_example

The first invocation only prints the exact proof.  The second changes the
copy, then refuses a second application because the FIFO shape has changed.
This dry-run/apply/refusal sequence passed on a disposable synthetic SQLite
store.  Replacing the user's live store with a repaired copy requires Emacs and
all store owners to be stopped, the original database and WAL files retained
as a backup, and a separate controlled restore.  None of those operations was
performed here.

* Design self-check

1. A stopped package fixes future steering and leaves a checkable offline path
   for the historical head; that is better than the prior stuck FIFO.
2. It moves toward one database-owned admission boundary for Board and Session.
3. The stable transaction is direct.  Provider execution recovery remains a
   separate, reversible lifecycle decision rather than a speculative adapter.
4. The runtime-store worker owns the transaction; chat owns delivery; the
   harness owns turn input; the loop owns provider request timing.
5. Coupling is limited to one session command carrying exact Board pickup
   coordinates.  The provider loop sees only committed user messages.
6. Core loop policy has no SQLite or Board dependency.  The chat adapter uses
   the Board service contract rather than issuing SQL.
7. SQLite mutation stays in the worker; the one-off repair stays outside the
   runtime modules.
8. Durable facts are the session message, pickup state, transaction receipt,
   and consumption activity.  Process-local delivery correlation remains local.
9. One bounded transaction replaces separate writes.  The durable receipt adds
   one small activity row per delivered Board input, needed to link a message
   admitted before turn creation to its actual turn.
10. The composed command names a real shared-store invariant; the committed
    message port works for submit, steer, and queue without weakening them.
11. Legacy claimed heads are handled offline.  No runtime compatibility retry
    is retained.
12. The obsolete claimed-head retry and separate pickup settlement path were
    removed.
13. Expected Board conflicts and write failures settle as visible failures;
    unexpected worker errors roll the SQLite transaction back and surface.
14. Worker, loop, harness, and real SQLite chat tests each prove their own
    boundary; the composed steering test proves the user-visible FIFO path.
