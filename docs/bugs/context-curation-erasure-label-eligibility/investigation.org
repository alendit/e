#+title: Context Curation Erase Label Lacks Eligibility Investigation
#+startup: overview

* Conclusion and status

This is a model-facing contract defect at the Feature 88 presentation boundary.
Core correctly rejects erasure of a non-tool source, but the source marker does
not tell the model which labels satisfy that restriction.  A valid decision is
therefore avoidably fragile in a mixed-source frame, and an invalid selection
fails the complete turn.

Feature 90 receipt projection is not the owner of this defect.  The owning
contract is Feature 88 Addendum 7 source presentation and carrier guidance.

Closed repository-side on 2026-09-03.  Core now derives one explicit
=erase-eligible= boolean from its trusted source kind and tool-call identity;
the detached marker renders every source as =erase-eligible= or
=erase-ineligible=.  The carrier tells the model to use =erase= only for the
former.  Strict response validation remains intact.

* Evidence

** Source inspection before the correction

=e-context-lifetime--curation-source-descriptors= retains trusted =:kind= and
=:tool-call-id= fields.  However, its model-facing marker contains only the
numeric label and estimated size:

#+begin_example
[ephemeral context source 2, ~N tokens]
#+end_example

=e-context-lifetime-curation-source-presentation= deliberately removes the
trusted fields and returns only =:label=, =:value=, =:estimated-tokens=, and
=:marker=.  Tool-result values also exclude their call identity.  The harness
places each marker immediately before its source value, so the model can
sometimes infer the source class from the following message envelope, but the
marker itself does not expose the erasure-eligibility decision already known to
core.

The OpenAI =context-curate= tool description says to use =erase= for ordinary
tool results.  Its schema accepts any positive integer in =erase= and cannot
constrain the array to frame-local eligible labels.

At response commit,
=e-context-lifetime--curation-erasure-record= requires the selected descriptor
to have =:kind= = "tool-result" and a non-empty =:tool-call-id=.  Otherwise it
signals exactly:

#+begin_example
(curation-erasure :non-tool-source LABEL)
#+end_example

The original report used label =2=.  The 2026-09-03 first-turn recurrence used
label =1=; both labels exercised the same missing eligibility distinction.

** Specification inspection

Feature 88 Addendum 7 defines =erase= as valid only for an ordinary tool-result
source.  It also requires the model to receive concise omission-versus-erasure
guidance.  The strict runtime rejection is therefore correct; the missing
model-visible eligibility is the inconsistent part of the contract.

Relaxing =erase= to non-tool sources would expand the settled product semantics
and is unnecessary: ordinary omission already removes the exact non-tool source
without creating a Feature 90 receipt.  Converting the validation failure into
silent omission would also hide an invalid semantic decision.

** Why the existing E2E stayed green

The post-cutover chat E2E did execute =new chat -> Hi -> OpenAI Responses ->
curation acknowledgement -> assistant -> Board -> SQLite reopen=.  Its fake
transport, however, always returned the hand-authored cooperative disposition
=keep:[1]=.  It asserted the successful result and durable reopen but did not
assert that the actual request described label =1='s erasure eligibility.

The lower-level test suite separately asserted that =erase:[1]= raises
=:non-tool-source=.  Both lanes were individually valid, but neither composed
the model-visible choice with the strict validator.  The missing assertion was
therefore at the request contract boundary, not at SQLite storage.

The current-configuration and live-provider tiers also failed to cover their
intersection.  =run-current-config-tests.sh= loaded the machine's normal Emacs
configuration and constructed its real =:chat-default= harness, but explicitly
sent no request.  =e-live-e2e-test-basic-assistant-response= sent a real request
through a real adapter, but that adapter came from a separate =E_E2E_CONFIG=
fixture rather than the machine's loaded configuration.  Neither test proved a
first turn through the exact adapter and profile selected by local startup.

* Correction

Keep the trusted runtime validation and make its eligibility decision visible
without exposing internal identities:

1. A source is =erase-eligible= only when its trusted descriptor is an
   ordinary tool result with a usable tool-call identity.
2. The detached model-facing marker explicitly says =erase-eligible= or
   =erase-ineligible=; it exposes no tool-call ID or other provenance.
3. The =context-curate= carrier explicitly forbids putting an ineligible label
   in =erase=.
4. The presentation and carrier identities advance to
   =context-curation-presentation-v3= and =context-curate-v6= so old anchors
   and external evidence cannot silently claim the changed contract.
5. Mixed-frame owner tests prove both labels, and the post-cutover E2E now
   asserts the literal ineligible marker and carrier prohibition on the same
   first request that later reaches the assistant, Board, and reopened SQLite
   session.
6. An explicit =live-basic= current-configuration E2E mode starts a private
   normally configured Emacs, takes the actual =:chat-default= backend adapter,
   endpoint/auth configuration, model defaults, and SQLite store into a fresh
   test-only harness, and adds one dynamic non-tool context source.  This avoids
   sending unrelated local layers, tools, or instructions.  The test requires
   one durable curation-response audit plus the first assistant response in the
   settled result, persisted session transcript, and Board output.  It does not
   constrain the model's valid disposition, and fails rather than skips when
   the path is unavailable or broken.

This deliberately does not add broad error swallowing or change the accepted
strict-invalid-response policy.  It removes the contradictory model-facing
choice that caused the production failure.  No persistence, retry,
reconciliation, or transaction protocol was added.
