#+title: Tool Call Search Char Or String Investigation
#+startup: overview

* Investigation

The screenshot showed a tool-call plist reaching a string insertion path:

#+begin_example
(:type tool_call :id "..." :name "glob" :arguments (:uri "session:///" :limit 20))
#+end_example

The real reproduction is a =session://= messages projection containing a
persisted structured =tool-call= message.  That matches the session output: the
agent searched sessions, then used =read= to inspect a candidate session's text.

Before the fix, this focused test failed with =wrong-type-argument
char-or-string-p=:

#+begin_example
rtk eldev test -f test/e-session-resources-test.el e-session-resources-test-read-stringifies-structured-message-content
#+end_example

The backtrace pointed at =lisp/layers/harness/e-session-resources.el=:

#+begin_example
(insert (e-session-resources--message-content message))
#+end_example

=e-session-resources--message-content= returned =:content= directly.  That is
valid for ordinary user/assistant text but wrong for persisted tool-call
messages, whose content is structured plist data.

No live Emacs reload or probe was run. The running editor was left unchanged; the investigation used the user screenshot, source inspection, and repository-side tests.

* Fix

The fix keeps ownership at the session resource text projection:

=e-session-resources--message-content= now returns
=e-session-resources--format-value= for either =:content= or =:text=.  This
preserves plain strings as-is and renders structured transcript content as
stable readable text for the =session://.../messages= projection.

The earlier chat-rendering fallback was removed because it hid the bad object at
the wrong layer instead of fixing the =session://= projection.

* Validation

The exact repro now passes:

#+end_example
