#+title: Investigation: collapsed attachment metadata on archived daily resume
#+startup: overview

* Finding

The August 7 daily references session
=20260807T130820-8004bfaef894=.  Its checkpoint stores chat attachments as:

#+begin_src json
{
  "attachments": {
    "uri": [
      "file:///.../daily/2026-08-07.org",
      "label", "2026-08-07.org",
      "buffer-name", "2026-08-07.org",
      "file", "/.../daily/2026-08-07.org",
      "mode", "org",
      "id", "762ac2f3a04e",
      "canvas", true
    ]
  }
}
#+end_src

Session replay exposes that as a single plist whose =:uri= value is the whole
flattened field list.  The previous shape predicate accepted it as an
attachment because it is technically a keyword plist.  URI hashing then
received a list instead of a string and raised the visible
=Invalid object argument= error.

* Live And Durable Evidence

- A bounded read-only =emacsclient= query confirmed the running Emacs exposes
  the exact collapsed =(:attachments (:uri (...)))= value for the August 7
  session.  No live state was changed.
- The first read-only inventory classified all 154 attachment-bearing
  checkpoints:
  - 95 current-reference and 47 legacy-metadata checkpoints contain collapsed
    single objects with an array-valued =uri=;
  - 6 legacy sequences contain a canonical object followed by a flattened
    ="uri"= pair;
  - 1 legacy sequence contains a flattened ="uri"= pair before a canonical
    object;
  - 5 current-reference checkpoints contain canonical one-object arrays.
- Replaying copies of the affected 4.5 MB journal and 2.1 MB checkpoint
  reproduced the screenshot error before the fix.

This showed that the August 13-specific tail repair covered only one of three
historical encodings and that the supposedly exceptional collapsed form is the
dominant persisted representation.

A later full-store dry run scanned 2,106 files and validated 1,887
attachment-bearing records.  It found 497 records requiring migration across
207 files: 456 collapsed and 41 flattened.  The remaining 1,390 records were
already canonical.  No unknown shape was accepted.

* Root Cause

Historical migration of attachment metadata crossed two ambiguous Lisp/JSON
sequence representations.  A flattened attachment could emerge either as two
array elements, ="uri"= plus a field vector, or as one object whose =uri=
property contains that same field vector.

The prior fix recognized only a flattened pair at the end of a sequence and
required both it and an earlier attachment to be canvases.  That condition was
based on the first observed journal rather than an inventory of persisted data.

* Fix

The permanent collapsed, flattened, legacy-single, and
=:context-attachments= readers were removed.  Chat-session and modernchat now
read only =:context-references/:chat-session/:attachments= as an array of
attachment objects, and the generic session schema no longer admits the legacy
metadata key.  Invalid or unmigrated data fails loudly.

The colocated =migrate-chat-attachments.py= script owns the historical formats.
It validates the complete selected store before writing, recognizes only the
inventoried field names and shapes, moves legacy metadata into the canonical
owner lane, and rewrites journals, checkpoints, and the session index.  It is a
dry run by default.  Apply mode requires an explicit confirmation that Emacs is
stopped, rejects concurrent file changes, creates timestamped sibling backups,
and atomically replaces changed files.  A record containing both legacy and
canonical attachment lanes is ambiguous and aborts the migration before any
write.

The migration is idempotent.  Applying it to a copy of the exact August 7
journal/checkpoint repaired both malformed records; a second dry run reported
zero changes, and the strict reader loaded the canvas URI successfully.

* Architecture Self-Check

1. If work stopped here, historical stores have a safe repair tool and the
   runtime has one enforceable attachment contract.
2. This moves toward explicit offline migration followed by strict steady-state
   behavior.
3. Stable decisions are string URIs and a canonical array of objects.
   Historical uncertainty is isolated in a removable one-off script.
4. =e-chat-session= owns current attachment semantics.  The migration owns old
   bytes, session storage owns generic serialization, Org Canvas requests a
   canvas, and Grimoire chooses a daily.
5. Coupling is reduced because neither Grimoire nor Org Canvas knows persisted
   attachment generations.  The public API is unchanged.
6. Dependencies still point from project/UI layers to chat-session.  Generic
   session persistence does not depend on attachment field policy.
7. Runtime decoding is side-effect free.  Migration writes are explicit,
   offline, backed up, and atomic per file.
8. No runtime state is added.  The migration changes only selected durable
   files and creates recoverable backups.
9. The hot path is cheaper because all legacy decoding is gone.  The one-off
   migration performs the necessary full selected-store scan offline.
10. The runtime has one real attachment contract; no implementation may narrow
    or weaken it.
11. No runtime compatibility remains.  The migration is limited to inventoried
    shapes and can be removed after use.
12. The legacy metadata schema entry and every attachment repair helper were
    removed.
13. Unmigrated or malformed runtime data surfaces immediately.  The migration
    validates all files before any write.
14. Core tests separately prove the strict contract and the complete offline
    migration/reload path.
