#+title: e-chat reasoning Markdown snapshot rendering investigation

* Evidence

- The supplied screenshot shows literal =**= delimiters and five adjacent
  reasoning status phrases with no separator between them.
- The persisted session journal records those phrases as five distinct
  =reasoning-delta= activity events.  Each event already contains one complete
  bold phrase; the concatenation is introduced after persistence.
- Before the fix, =e-chat-activity--record-reasoning-delta= received every
  reasoning event as an append operation, so
  =e-chat-activity--append-round-reasoning= merged distinct board publications
  into one string.
- Before the fix, =e-chat-transcript--apply-activity-region= gave transient
  activity a system face and styled activity separators, but did not apply the
  transcript's Markdown presentation.
- A supported bounded live probe reached the running Emacs, but the selected
  buffer was the Doom dashboard with no attached chat session.  The affected
  buffer was therefore not mutated or inspected through an unsafe broad eval.

* Root Cause

The shell boundary does not preserve the semantic difference between a raw
provider stream fragment and a board activity publication.  A direct harness
=reasoning-delta= is appendable stream material, while a board message is an
already coalesced presentation snapshot.  The chat service projects both with
the same payload, and the activity owner consequently concatenates every board
snapshot.

Separately, transient activity bypasses the transcript-owned Markdown
presentation used for assistant output.  Even correctly separated bold status
phrases therefore expose their delimiters.

* Acceptance Test

- Board reasoning messages are explicitly projected as snapshot content.
- Two complete board reasoning snapshots remain distinct lines in the compact
  activity block.
- Strong Markdown syntax is visually concealed and the status text receives
  the strong face.
- Direct raw reasoning deltas retain append behavior.
- An isolated graphical test exercises the real board-to-chat path.

* Fix

- =e-chat-service= now marks reasoning published through the board as
  =snapshot= content.  At this boundary, a snapshot means one complete,
  already coalesced value for presentation.
- =e-chat-activity= starts a new intermittent reasoning entry for each board
  snapshot.  Reasoning events without the marker remain appendable raw stream
  fragments.
- =e-chat-transcript= applies deterministic Markdown presentation only to the
  touched transient activity lines.  It conceals strong delimiters and keeps
  the activity base face without changing settled assistant-output behavior.

* Architecture Self-Check

1. The package is useful by itself: it fixes the reported transcript without
   depending on future work.
2. It moves toward explicit semantic data at the board-to-shell boundary and
   presentation behavior owned by the chat shell.
3. Raw provider fragmentation and board coalescing are the likely variation.
   One payload marker keeps that distinction local and reversible.
4. The chat service owns translation from board messages, activity owns
   activity composition, and the transcript owns display properties.  Each
   change remains with that responsibility.
5. Coupling is reduced because the renderer consumes a narrow content-mode
   value instead of inferring publisher behavior.
6. No stable policy depends on a concrete provider or UI.  The service emits
   semantics and the shell decides presentation.
7. Markdown text properties remain in the presentation shell; no UI side
   effect moved into the board or service.
8. No durable or process state was added.  =content-mode= lives only on the
   projected event payload and can be rebuilt from the board message.
9. The service adds one activity-kind check.  Activity Markdown work is bounded
   to the complete lines touched by the existing incremental redraw.
10. =snapshot= names a real distinction: one complete activity entry, while an
    unmarked event extends the current entry with a stream fragment.
11. Direct harness reasoning events remain compatible and append by default.
    No obsolete compatibility path was added.
12. No legacy code became removable within this narrow fix.
13. Existing unexpected errors still surface.  The change adds no catch-all or
    error swallowing.
14. Service, activity-composition, and graphical tests prove the boundary,
    composed text, text properties, and effective redisplay invisibility at
    progressively wider levels.

* Live Emacs Status

The running Emacs was left unchanged.  Because the fix changes the core chat
service as well as shell modules, using it immediately requires a full Emacs
restart; =e-dev-reload= is not sufficient for this slice.
