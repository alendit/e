* Findings

** TODO High I1: Indirect buffer aliases bypass the canvas revision guard

Contracts: C6; S5. Owner: canonical resource identity at =e-context-canvas-resource-identities= and file/buffer resource consumers.

The guard recognizes a buffer name and, only when that buffer has buffer-file-name, its visiting file (=lisp/core/e-context-canvas.el:170--202=). It never follows buffer-base-buffer. An indirect buffer shares the attached canvas's actual text but has buffer-file-name=nil. Its buffer:// URI therefore fails target intersection and is treated as an ordinary noncanvas resource.

=e-emacs-tools--write-buffer-resource= decides guarded-p from an explicit expectation or that target check (=lisp/layers/emacs/e-emacs-tools.el:428--449=). A missing expectedRevision through the indirect alias consequently reaches erase-buffer/insert and overwrites newer attached canvas text. Cheap ordinary operation dispatch does not acquire an alternative guard; the cooperative path also ultimately relies on the same file/buffer owner resolution.

Independent proof: =reviewer-risk-probes.el= creates an attached base buffer with newer user text and an indirect alias, registers the shipped buffer resource methods and ordinary resource tools, and calls the ordinary write tool through =e-tools-execute-nested-cheap-with-context= with the trusted attached-target scope and no expectation. Output:
#+begin_example
INDIRECT targeted=nil file-name=nil conflict=nil base-changed=t
ORDINARY-INDIRECT tool-status=ok conflict=nil base-changed=t
#+end_example

This is a standard Emacs view alias of the same mutable document, not an arbitrary Lisp/shell mutation excluded by C6. Current direct/file/visiting-buffer alias tests do not exercise this identity partition.

Smallest correction: resolve buffer aliases through their ultimate base buffer before deciding canonical text/file identity, in both directions when an attachment itself names an indirect buffer. Keep authorization and ordinary noncanvas semantics unchanged. A local tool-description warning or adding expectedRevision only in a fixture would leave the owning bypass intact.

Resolution evidence: attach through the base/file and mutate through an indirect buffer, and attach through an indirect buffer and mutate through the base/file. Missing/stale expectations must return conflict without changing any shared text; a current expectation must apply once. Exercise the ordinary shipped operation path, including inherited nested context, and retain a noncanvas control.

** TODO Medium I2: Narrowing turns a complete document revision into a partial-view revision

Contracts: C2/C6; S2/S5. Owners: attachment source capture plus complete resource capture/read/mutation.

=e-chat-session--attachment-content= uses point-min/point-max without widening (=lisp/layers/chat/e-chat-session.el:366--381=). If an Org user narrows to a subtree, the supposed complete snapshot contains only that accessible region. The new buffer read path labels the same restricted text full-content and hashes it as the complete resource revision (=lisp/layers/emacs/e-emacs-tools.el:409--426=). Guarded buffer precondition reads and file live-buffer reads likewise use the current restriction; file save replacement and buffer erase/insert also operate against that restriction.

Independent proof creates a 21-character buffer, narrows to 8 characters and captures it through the attachment boundary. A supported partial buffer read then reports the 8-character hash as its full revision:
#+begin_example
NARROW full-chars=21 captured-chars=8
full-revision=CC22FC02FB5ACE1BCA0D010BB36E6ED8A6207118B384C7616304FB80469DC713
read-revision=B70F8F776F6BD11B9A0049B533E2A9EFE061C704CC93CEB3988541524FBA5E48
equal=nil
#+end_example

A default full buffer read while narrowed also fails its range validation because its default absolute start is 1 below point-min; the reported successful probe uses a valid explicit range to isolate the incorrect complete-revision claim. The capture restriction predates this patch, but F99 explicitly establishes complete exact revisions rather than section checkouts; the inherited boundary is now in the selected contract and the new revision consumers rely on it.

Smallest correction: capture/hash the entire authoritative buffer under save-restriction/widen, consistently for canvas snapshots, full revisions on partial reads, guarded preconditions and complete-resource mutations. Restore the user's narrowing, point and presentation state afterwards. Retain ordinary range semantics explicitly; do not silently redefine a full resource as the current narrowed subtree.

Resolution evidence: narrow a real attached buffer, check its snapshot/full hash against a widened capture, read a valid range and default full range, then make a change outside the restriction and reject the old expected revision. A fresh guarded edit/write must produce the intended whole-resource result while restoring narrowing. Cover file and buffer aliases, including I1's shared base views.

** TODO Medium I3: Detached/replaced canvases keep exact accepted content for the harness lifetime

Contract: C5; S3. Owner: harness context chronology lifecycle.

The new canvas-chronologies hash table is strongly held by harness context state (=lisp/core/e-harness-state.el:40--45,113--119=). Source contains no remhash/clrhash cleanup for this table. =e-harness-context-runtime--canvas-project-context= immediately returns when captures are absent (=e-harness-context-runtime.el:591--600=); when captures exist, it processes current URIs without removing old session/URI keys. Commit installs full :text and operation payloads, and curation only replaces existing entries with version-only values (=725--744=).

Independent proof accepts a synthetic canvas through the projection/commit owner, then projects the same session without any canvas captures:
#+begin_example
DETACH table-count=1 retained-text="PRIVATE-DOCUMENT-A"
#+end_example

Replacing canvases or abandoning/deleting sessions can therefore accumulate exact document bodies under one long-lived harness. Per-chain patch limits do not bound the number of obsolete document entries. This violates the accepted smallest active-context lifetime and leaves removed content resident after it serves no active canvas projection.

The proof establishes retention and missing cleanup. It does not claim that later reattachment necessarily sends an unusable diff or yields stale answers: full projection can reconstruct the retained chain. Those are separate semantics, and this finding does not rely on them.

Smallest correction: give detach/replacement/session or context invalidation an explicit release path owned by chronology lifecycle, including sessions with zero captures. Prevent a pending stale completion from repopulating released content; merely deleting a hash key while an older nil-version candidate can still commit is insufficient. Preserve preview/status non-commit behavior and legitimate concurrent request ownership.

Resolution evidence: accept A, replace it with B, detach the last canvas and close/delete the session as supported. Verify exact text and payload state becomes unreachable at the corresponding accepted lifecycle boundary. Deliver an older pending completion after removal and verify it cannot restore released state. Reattachment after loss should establish a fresh snapshot. No new persistent authority is needed.

** TODO Medium I4: File guards use disk/input shortcuts instead of the authoritative pre/post-mutation text

Contract: C6's successful revision propagation, with C2's source-authority boundary. Owner: guarded file write/edit.

Two independently reproduced partitions violate the same authoritative file-result boundary:

- Before a write, =e-base-tools-file--write-file-resource= uses file-exists-p to decide whether current text exists (=lisp/layers/base/e-base-tools-file.el:1120--1133=). A new unsaved visiting buffer is authoritative even before its file exists. The current implementation substitutes empty text and rejects the valid revision captured from that live buffer.
- After successful save-buffer processing, guarded write returns the hash of requested content (=1160--1162=), and edit returns the hash of pre-save final-content (=1218--1221=). =e-base-tools-file--save-buffer-content-to-file= runs save-buffer (=274--303=), so before-save hooks can change the actual saved/live text. The success revision then identifies text that is no longer the resource.

Independent outputs:
#+begin_example
NEW-UNSAVED status="conflict"
expected=C2572E5F998A1B32A4577086765331487FBA85BDEA1FD49645F6911C80697F19
current=E3B0C44298FC1C149AFBF4C8996FB92427AE41E4649B934CA495991B7852B855
disk-created=nil

SAVE-HOOK status="ok"
reported=7AA7A5359173D05B63CFD682E3C38487F3CB4F7F1D60659FE59FAB1505977D4C
actual=CED2526BD3B34302167645DB8D4D74052035D07D2D571CA66B5FD741970A0295
equal=nil
#+end_example

The save-hook probe adds a fixture-local before-save hook that appends text; it touches no user hook/configuration. These cases cause spurious conflicts or make the next call stale immediately after a reported successful edit. Existing coherence checks do not correct either revision value.

Smallest correction: use the existing authoritative live-buffer preference even when the visited path has not yet been created; use empty text only when neither live content nor disk resource exists. Derive success revisions from the final authoritative text after save hooks and synchronization, with the same complete capture semantics as I2. Do not disable normal save hooks or hash only the requested replacement.

Resolution evidence: guarded write through a newly created unsaved visiting buffer with its captured revision must succeed without losing text. Guarded write and edit with a local save hook must return the exact post-save complete hash, and a following guarded operation using that returned value must succeed once. Keep the file:// no-live-buffer and noncanvas controls.

I3 is bounded only by harness lifetime and number of ever-seen documents. Local capture/identity/result/cleanup corrections are proportionate; no incident-frequency estimate is fabricated.

No broad physical-decomposition or alternate architecture was made part of this package. The roughly 300-line cohesive chronology cluster in the existing context owner and small provider-neutral modules have real ownership reasons. File length alone creates no finding. No architectural deferral or activated follow-up ledger is being accepted here.
