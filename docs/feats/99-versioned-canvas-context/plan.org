Planned. Implementation has not started.
The operator requested two improvements: correct canvas placement in the Anthropic adapter, and versioned canvas snapshots with diffs.
Snapshot selection uses bytes, not percentages of changed lines.
This plan records that scope; it does not authorize implementation, changing the running Emacs, or modifying a live Daily or session store.

The first implementation keeps a known snapshot, exact changes against it, and bounded snapshot fallback.
Section checkouts are a follow-up: use the existing targeted =read= operation in the meantime rather than adding a second document API.
The [[file:../../references/runtime_concepts.org][runtime vocabulary]] and the [[file:../98-growing-conversation-prompt-cache/plan.org][Feature 98 cache contracts]] remain authoritative.
This work must preserve current-state freshness, evidence provenance, curation exclusions, and the distinction between reference data and instructions.

* Goal and direct scenario

=F99-G1=: A mostly unchanged canvas remains current and usable without repeatedly replacing an early prompt prefix or appending duplicate document bodies.
Small edits should add a small exact change after the reusable conversation prefix.
The complete document must remain recoverable from the model's active context, independently of whether a provider cache hits.

Direct scenario: a Daily is open while the user changes a checkbox, the agent edits a section, and intervening tool calls leave the document unchanged.
Every request sees the correct revision, user edits survive, and unchanged conversation history retains its native prefix.
After compaction or loss of the required baseline, the next request establishes a fresh snapshot instead of delivering an unusable diff.

Success concerns both semantics and useful reuse.
Resending fewer wire bytes is not sufficient if the model loses the document; a stable-instructions cache hit is not sufficient if document changes force the whole conversation to be processed again.

- [[file:../../../lisp/adapters/anthropic/e-anthropic.el::e-anthropic--system-blocks][Anthropic system serialization]] puts system messages before conversation messages.

The read-only October 16 audit observed 170 usage-bearing requests in the October 14 Daily parent chat: 18,111,932 input tokens, including 17,453,809 cache reads, 657,763 cache writes, and 360 fresh tokens.
These whole-request counters do not isolate the canvas, establish the cause of individual misses, or prove a prospective saving.
The audited parent used the configured Opus route; the numbers do not establish another provider's behavior.

Claude's [[https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache][cache hierarchy]] orders tools, system, then messages; a changed prefix can invalidate later cached content.
The design implication is to keep changing document data out of the early instruction prefix, while retaining genuine system/developer authority.
Actual benefits on the configured gateway require fresh joined request and usage evidence.

* Contracts

| ID | Required behavior |
|----+-------------------|
| F99-C1 | Canvas contents are reference data at a stable semantic position; real instructions retain their authority and tool-call/result pairing remains valid. |
| F99-C2 | A snapshot or exact diff determines one complete current document revision, including unsaved edits, deletions, Unicode, and empty content. |
| F99-C3 | An unchanged revision contributes no new document-body observation; full stateless requests still contain the baseline and required changes. |
| F99-C4 | Diff selection compares serialized UTF-8 byte sizes; bounded chains and missing baselines cause an explicit fresh snapshot. |
| F99-C5 | Baseline eligibility follows accepted model context, branch, generation, document identity, and request outcome, not merely the last attempted send. |
| F99-C6 | Writes against an obsolete document revision fail visibly without overwriting newer user changes. |
| F99-C7 | Provider rendering preserves the reusable prefix and existing capability gates; semantic, cache-efficiency, and route-qualification results are reported separately. |

* Ownership and state

The attachment/resource boundary owns exact text capture and document identity, preferring the live buffer as it does today.
It produces a snapshot from one consistent read; revision hashing and diffing must use that same captured text.
The shell owns presentation state such as point, heading, and folds, not document history or provider policy.

The harness context layer owns snapshot/diff selection and the representation known to be present in the active context.
Keep the selection policy pure: given a captured document, an eligible baseline/chain, and limits, return a snapshot, diff, or unchanged decision.
I/O, lifecycle settlement, and provider serialization stay outside that operation.
Place the small document-specific implementation beside the existing attachment/context owners; do not introduce a general version-control service or a provider-specific canvas subsystem.

The backend adapter owns native role, ordering, framing, cache markers, and continuation compatibility.
Canvas data must not be promoted into instructions, synthesized as a fake tool call, or enabled by a fabricated capability grant.
If native encoding needs a new semantic distinction, define it narrowly in the existing context contract and cover every shipped serializer.
Do not broadly reinterpret existing system messages or reuse durable retained-context records to preserve a canvas beyond its authorized lifetime.

The actual buffer/resource remains the source of truth.
A model-context baseline is a derived, process-local chain scoped to document URI, selected branch/context generation, and compatible native layout.
Retain exact text needed to reconstruct that chain only while it serves the active context; release obsolete branches and pending requests through existing lifecycle cleanup.
Do not persist every refresh, duplicate the SQLite transcript, or require a new database schema for this package.
After restart, missing state means a new snapshot, not inferred provider memory.

Document revision is a content hash of the exact property-free source text under the existing evidence encoding rules.
Use explicit UTF-8 encoding for size calculations, with no extra whitespace or newline normalization.
URI is a separate identity component; equal text in two canvases does not share a mutable cursor.
Focus and visibility metadata neither enter the document hash nor precede reusable history as changing system text.
An effective current-state source handle must still identify the complete resulting revision, even when the request presents it through a baseline and changes.

* Snapshot and diff representation

** Logical context versus transport

A snapshot contains the exact captured text, document URI, resulting revision, and reference-data framing.
A diff names its exact base revision and resulting revision and carries deterministic, lossless changes.
Validate locally that applying the diff to the base yields the captured current text and resulting hash before it can be sent.
Use readable text hunks with exact positions and replacement content; do not use fuzzy matching or lossy model-generated summaries as the patch format.
Line-oriented hunks are acceptable for readability; their line counts never drive representation selection.

Keep the baseline and accepted changes in their original order within the derived model-context chain.
An unchanged document adds no new body; a change appends a new data observation after the reusable history prefix.
Do not rewrite an earlier snapshot to the newest document on every turn, move an old patch to the newest tail, or send a diff alongside a second full copy of its resulting document.
New snapshots supersede the previous chain in the next selected projection; they do not leave an unbounded collection of obsolete documents in model context.
A snapshot reset is an intentional cache boundary whose cost must be measured.

For a full API request, serialize the complete required baseline and change chain again unless a qualified provider continuation already supplies them.
Provider caching may reuse those prefix tokens, but it does not make the underlying context unnecessary or remove its context-window occupancy.
The unchanged decision therefore means no new observation, not omission of required context from a stateless request.

** Byte selection policy

Measure the complete backend-neutral model-facing payload encoded as UTF-8, including document identity, revision fields, patch coordinates, escaping, and framing.
Compare a diff and a fresh snapshot of the same current text using the same envelope rules.
Provider envelope differences are checked in native-request evidence; byte size is a deterministic proxy, not an exact token or billing estimate.

| Condition | Decision |
|-----------+----------|
| No eligible baseline, or current context no longer contains its exact chain | Fresh snapshot |
| Current content hash equals the eligible resulting revision | Unchanged; append no document body |
| Current document is empty | Exact empty snapshot or a valid deletion diff, selected by the same byte rules |
| Diff bytes are at least 30% of fresh snapshot bytes | Fresh snapshot |
| Appending the diff would make cumulative diff payload bytes at least the current snapshot payload bytes | Fresh snapshot |
| Appending the diff would exceed 16 patches since the baseline | Fresh snapshot |
| Otherwise | Exact diff |

The 30% ratio and 16-patch bound are proposed initial internal constants for review, not claims of optimality or user-configurable provider cache switches.
Use integer byte comparisons with explicit equality boundaries; a zero-length document must not cause division by zero.
Count all accepted patches in the active chain, even if later edits cancel earlier changes.
Also respect the existing context/resource size bounds; diffing must not bypass admission limits.
Bound diff construction work before processing pathological input, and select a snapshot when that explicit work bound is reached.
Unexpected encoding or hash failures remain visible errors rather than being hidden by a snapshot fallback.
Before implementation acceptance, record byte-size and runtime comparisons on realistic Daily edits, then retain or adjust these defaults with evidence.

** Lifecycle and concurrency

Prepare each request from immutable captured text and a baseline identity tied to the selected context projection.
Separate its pending representation from the accepted baseline cursor.
Advance eligibility only at the existing successful terminal-response and semantic-acceptance boundary; writing an HTTP body or opening a stream is insufficient.
Failure, cancellation, ambiguous settlement, or lost baseline state must not authorize a diff against an unaccepted revision.
Retries reuse a valid immutable request or rebuild from the last eligible context; they never double-advance the chain.

An older successful request cannot overwrite a newer cursor after concurrent completion or a branch/generation change.
Compaction, curation, branching, and continuation invalidation must check whether the exact baseline and required patches remain available.
If unavailable or only summarized, establish a fresh snapshot from the current authoritative resource.
Do not resurrect a source excluded by curation or claim that a summary is an exact patch base.
Reuse existing projection/layout identities to reject incompatible provider anchors after placement changes.

Carry the expected content revision through canvas-targeted edit/write operations.
Compare it with the current live resource immediately before mutation; validate and apply without an intervening asynchronous gap.
On conflict, change nothing, expose the current revision, and let the caller obtain current text and reconsider the edit.
For resource methods that cannot provide this atomic check-and-apply contract, do not advertise revision-checked writes as supported.
Keep ordinary non-canvas file operations and their authorization unchanged.

* Delivery packages

** DP1: Correct canvas placement

Separate canvas reference data from stable instructions and volatile presentation metadata.
Render current canvas data after the reusable conversation prefix in Anthropic, preserving its authority and native message constraints.
Inspect the corresponding Responses and Chat Completions seams so the semantic change remains correct across shipped adapters; do not enable an unqualified continuation or curation route.
Invalidate incompatible layout identities using existing machinery.

This package may stop with full snapshots: it must already preserve freshness and protect earlier history from canvas edits without depending on DP2.
Prove the actual native request ordering across an initial request, an unchanged follow-up, and a checkbox edit.

** DP2: Versioned snapshots and exact diffs

Implement the pure byte-selection and exact patch operations, active-context chain ownership, lifecycle settlement, and revision-checked canvas writes together.
Provide one authoritative resulting-document revision for provenance and stale-write checks.
Full requests, retries, tool follow-ups, and lost-context recovery must remain correct before enabling diffs on the ordinary path.
Remove the superseded unconditional canvas-body projection; do not leave competing snapshot and diff authorities or a permanent legacy mode.

This package closes C2–C6 on every shipped serializer, with C1/C7 as regression boundaries.
Existing ordinary targeted reads remain sufficient; a dedicated section-checkout protocol is not a prerequisite.

** DP3: Qualify useful reuse and document activation

Use isolated ordinary chat/Org Canvas entry points and provider request/usage joins, following Feature 98's exact-route evidence discipline.
Exercise repeated small edits and unchanged tool follow-ups on the configured Opus route; test other available routes separately without extending an Opus result to them.
Show preserved unchanged native prefixes, bounded representation size, correct data-dependent answers, and repeated cache-read advances where the provider makes reuse observable.
Include larger rewrites and snapshot resets so the report captures their actual costs instead of reporting warm hits only.
Any changed layout covered by an existing curation qualification requires the applicable regression and exact-route requalification before claiming restored qualification.
Unrelated unavailable routes remain explicitly unqualified.

* Validation portfolio

| Scenario | Required proof |
|----------+----------------|
| Unchanged canvas and growing tools/history | No new document body; full requests retain required context; earlier native prefix stays identical. |
| One checkbox or short paragraph edit | Exact diff reconstructs the new text and appears after reusable history; the answer uses the new value. |
| One huge line versus many tiny edits | Selection follows serialized UTF-8 bytes rather than line counts. |
| Unicode, CRLF/source encoding, deleted sections, trailing newline, empty file | Exact round trip and source-consistent hash, with no text normalization or invalid UTF-8 offsets. |
| Ratio, cumulative bytes, and chain bounds | Values immediately below, at, and above each bound produce the specified representation. |
| Repeated edits and a large rewrite | Bounded chain; snapshot supersedes old documents; no duplicate current body or unbounded reset history. |
| Unsaved user edit and stale agent write | Live-buffer revision wins; stale write changes nothing; a revised edit succeeds once. |
| Failed stream, cancellation, retry, and stale completion | No premature or duplicate baseline advancement and no cross-request mutable state leakage. |
| Branch, reopen/restart, compaction, and curation | A proven complete chain is used or a fresh snapshot is established; no excluded source is reintroduced. |
| Two canvases and multiple sessions | Identity/cursors remain isolated even when text or request ordinals match. |
| Every shipped native serializer | Genuine instructions retain authority, document data retains meaning, and tool-result adjacency and layout identity remain valid. |
| Ordinary public canvas flow | Initial submit, tool edit, user edit, follow-up, and recovery all use the current document without a synthetic privileged path. |

Use focused ERT for pure policy, projection, request settlement, and revision conflicts, plus composed native-request tests that observe later appends rather than one isolated serialization.
Use the private graphical harness for behavior involving live buffers, unsaved edits, or document synchronization; inspect its settled artifacts.

* Follow-up: section checkouts

An outline plus revision-scoped section reads can reduce context occupancy further when the task does not need the complete Daily.
It is separate from preserving an append-only cached baseline: snapshots and diffs still occupy model context even when provider caches reuse them.
Design this only after the baseline protocol is accepted and measurements show a remaining whole-document cost.
Define section identity, missing-section behavior, revision conflicts, and completeness for whole-document tasks before introducing any dedicated checkout action.

* Architecture review questions

1. Does each delivery package leave correct, useful behavior if work stops there?
2. Does the design move toward worker/task-relevant current context while preserving ordinary canvas semantics?
3. Are byte thresholds and patch encoding local, reversible decisions, with no speculative version-control framework?
4. Do source capture, revision policy, lifecycle settlement, native rendering, and presentation each have one clear owner?
5. Do consumers use narrow existing context/resource contracts rather than depending on provider or shell internals?
6. Do stable policy dependencies remain independent of concrete providers, file I/O, and UI state?
7. Are capture, mutation, and provider effects outside pure selection and patch operations?
8. Is each retained snapshot/cursor scoped to the smallest active context lifetime, released on invalidation, and rebuildable without another durable authority?
9. Does measured diff work justify its cost against avoided payload and processing, including pathological inputs and snapshot resets?
10. Can each advertised serializer/resource capability honor the same semantics without weakening a precondition or inventing provider memory?
11. Are layout compatibility and unsupported routes explicit, without a permanent old-mode shim?
12. Has the unconditional canvas-body path been removed where the new representation replaces it?
13. Are expected conflicts and missing baselines handled by their owner while unexpected errors remain visible?
14. Do independent semantic, lifecycle, native-prefix, and route-usage scenarios prove behavior without mirroring implementation details?
