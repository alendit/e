#+title: Chat Surface Composition
#+startup: overview

* Status

Done.

* Goal

Replace the monolithic chat buffer's transcript-plus-editable-composer layout
with an =e-chat= presentation surface composed of a read-only transcript buffer
and a paired editable composer buffer.  The harness and capabilities continue
to expose only generic sessions, events, resources, hooks, and prompt APIs.

* Contract

- The transcript buffer owns rendered blocks, activity, navigation, and
  transcript-window follow policy.
- The composer buffer owns draft text, point, completion, prefix handling, and
  local inline-reference presentation.
- The surface controller owns the relationship between those buffers and their
  native atomic Emacs window.  Emacs therefore applies structural window
  commands to the complete surface.  The relationship is resolved from buffer
  identity, atom membership, and adjacency; no pair cache or custom window
  metadata is stored.
- No capability, harness API, or provider adapter knows about either buffer or
  the window arrangement.
- Transcript rendering must not delete, restore, or otherwise mutate composer
  text.  Composer commands submit through existing harness/session APIs.

* Completion notes

- Interactive chat sessions now create a separate composer buffer and place it
  below each displayed transcript window.  The composer window is resized only
  after composer edits or window-layout changes.
- Durable transcript rendering does not write to the composer buffer.  Queue
  changes are the explicit exception because they update composer chrome.
- Escape transfers input ownership from the composer to transcript response
  navigation in one command, including from Evil insert state.  A complete
  transcript/composer window pair is not reactivated merely because its
  transcript window becomes selected.
- Native =C-x 0= and =C-x 1= behavior applies to the complete atomic surface.
  Chat retains only its semantic focus-cycle and external-buffer selection
  policy for =C-x o= and splits.
- Entering the surface through its transcript activates the existing composer
  input state.  Moving from composer to transcript inside the already-selected
  surface remains explicit response navigation and is not redirected.
- =window-atom= is registered in =window-persistent-parameters= with the
  =writable= policy used by =persp-mode=.  Workspace restoration therefore
  reconstructs the native atom directly; e-chat performs no structural
  reconciliation during host restoration.
- Already-open or persisted ordinary pairs from the immediately preceding
  release are upgraded once when e-chat next displays their composer.  This
  compatibility path is local to the shell and can be removed after that
  representation no longer needs migration support.
- Each transcript window owns ephemeral pinned-output state.  New turn output
  stays near the bottom while pinned, scrolling the transcript from either
  constituent unpins it, and returning the viewport to the output tail repins
  it.  Later activity redraws preserve an unpinned scrollback position.
- A short pinned transcript is bottom-aligned with a window-scoped presentation
  overlay above its output.  Unpinning removes the overlay; no spacer text is
  written to the transcript or durable session state.
- Batch, integration, and graphical tests exercise the same separate
  transcript/composer architecture as interactive sessions.
- The composer mode remains a reusable presentation component: Org Canvas
  derives its transient input/result pane from it without putting editable
  input back into a chat transcript.

* Architecture self-check

1. The first slice is useful on its own: it makes a transcript append unable
   to change a live draft.
2. This moves toward presentation-owned composition, not capability-aware UI.
3. Window-state persistence was the uncertain boundary.  Focused graphical
   evidence established that writable atom persistence is sufficient; stable
   session and harness contracts remain unchanged.
4. The chat shell owns this behavior because it is the only consumer of its
   buffers, keymaps, and windows.
5. The boundary reduces coupling: transcript rendering consumes no composer
   state, and composer editing consumes no block layout state.
6. No dependency points from harness or capabilities toward this shell detail.
7. Native Emacs owns structural split and delete effects.  Chat-specific
   focus, external split-buffer choice, and fitting remain at the shell edge.
8. Window geometry and selection are ephemeral, and the composer draft lives
   only in its buffer; durable messages remain in the session store.
9. Transcript append work no longer includes composer reconstruction or
   transcript screen-line measurement.
10. Emacs's atomic-window contract is the real structural abstraction.  No
    generic multi-pane abstraction is introduced.
11. The old monolithic protocol is not retained for normal users.  A narrow
    one-release ordinary-pair migration handles real saved presentation state.
12. The eventual cleanup removes spacer-layout and composer capture/restore
    paths from normal transcript rendering.
13. Expected host restoration uses ordinary window-state persistence;
    unexpected split and window errors surface.
14. Focused tests prove native deletion and writable state restoration;
    graphical tests prove real =persp-mode= round trips and generic replacement
    of a selected chat constituent as one complete surface.
