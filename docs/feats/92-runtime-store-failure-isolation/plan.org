* Behavioral goal

- Goal ID :: =BUG-RUNTIME-STORE-ISOLATION=
- Behavioral goal :: Multiple runtime owners can share one external persistence
  worker without corrupting ownership, making unrelated healthy persistence
  unavailable, or occupying an interactive Emacs stack while worker open,
  acknowledgement, recovery, or durable application composition is pending.
- Direct scenario :: Public Daily/chat open returns its buffer immediately.
  Session creation and participant association enqueue on one bounded worker
  FIFO without waiting for open, execution, commit acknowledgement, retry, or
  recovery.  Same-Board timer work queues behind earlier Board persistence;
  composer input and an independent heartbeat continue while the worker is
  deliberately delayed.  Releasing the worker produces one ordered visible
  result.  Killing or failing it marks only the affected session or Board
  persistence-suspect with its first bounded diagnostic, lazily restarts the
  worker, and permits an unrelated session to enqueue and persist.  Reopen or
  explicit inspection quarantines only a session whose decoded journal lacks a
  root, has duplicate identities, has an inconsistent parent chain, or has an
  invalid Board/session association.
- Product authority :: The operator's pragmatic failure-isolation direction of
  2026-09-05, which supersedes earlier unfinished DP5B--DP5D requirements where
  they conflict; accepted DP1--DP5A behavior remains available but is not
  reimplemented in application layers.
- Owning contracts :: =F92-C01= through =F92-C11= below.
- Behavioral status :: Failing.  The public Org Canvas gate proves fresh open,
  one turn, responsiveness, release, and owner-local failure, but its canned
  backend did not inspect provider context.  A live second prompt was absent
  from that context until SQLite acknowledgement and received the preceding
  answer.  The addendum's data-dependent two-turn scenario now owns minimum
  Daily acceptance.  Session quarantine, the all-domain hot-path audit, and the
  rest of the roadmap also remain unresolved.
- Mechanism status :: =F92-DP1= through =F92-DP4= remain passing and

  installed, but it is no longer the application-layer acceptance model.  The
  current slice installs one client FIFO, practical session write limits,
  session/Board owner-local suspect partitioning, async fork rejection, and the
  minimum new-Daily application wiring needed by =S92-DAILY=.  The matrix rows

* Reduced delivery packages (current authority)

** F92-DP6A: Straightforward FIFO and owner-local failure

Establish =F92-C02=, =F92-C05=, and =F92-C10= and re-prove =F92-C01=,
=F92-C04=, and =F92-C06=.  Collapse the runtime's separate client read/write
queues into one bounded client FIFO.  The singleton internal open request stays
outside that FIFO as transport control.  Remove or bypass the opt-in DP5B
per-session coordinator, reconciliation barrier, and owner lanes from default
composition; owner keys are suspect/fence metadata, not schedulers.  Submission
captures a practically bounded command, enqueues it, and returns.  Ordinary
writes remain SQLite transactions.

After DP4's one same-identity receipt recovery attempt is exhausted, the
runtime performs one queue partition.  It fails the active handle once with
the first diagnostic truncated to 1,024 UTF-8 bytes; marks that operation's
session or Board suspect; settles every already-admitted same-owner successor
as =persistence-suspect= and releases its request/byte/notification capacity;
and retains every unrelated entry in its original FIFO order.  A retained
unrelated head starts replacement when the scheduler next runs; an empty queue
waits for a later enqueue.  Session and Board identities are separate key
spaces, so a Board failure does not fence its participant session unless that
session's own write fails.

Keep the public three-argument =e-runtime-store-submit= ABI.  Domain adapters
use one private submission seam that attaches an unencoded
=(domain . owner-id)= key to the private request after protocol preflight; the
key never enters SQLite or the worker frame.  Only optimistic session/Board
mutation requests provide fenceable keys.  Reads and other-domain requests
settle their retained =e-work= or domain status on failure without creating a
session/Board fence.

The application-service =e-work= continues to represent eventual persistence,
but no UI or timer awaits it.  Successful enqueue may publish the prepared
process-local transition immediately; acknowledgement finishes the handle,
while failure leaves that optimistic state visibly suspect.  Suspect state is
process-local, keyed by domain and owner identity, and first-cause preserving.
A session fence clears only after DP6C page-bounded validation rebuilds the
canonical session and replaces failed optimistic state.  A Board fence clears
only after its associated session and Board association reload canonically;
invalid validation quarantines the session and leaves the Board warning visible.

Retain =e-runtime-store-request-capacity= at 128 client requests, counting the
active request plus queued client reads and writes but excluding singleton open
control and already-delivered notifications.  Add session limits of 1 MiB
encoded per record, 256 records per append batch, and 8 MiB encoded per complete
batch, owned respectively by =e-session-storage-record-byte-limit=,
=e-session-storage-batch-record-limit=, and
=e-session-storage-batch-byte-limit=.  Reject overflow atomically before queue
insertion.  Definitive settlement releases request count and
frame bytes; each notification reservation remains owned by its bounded outbox
entry until observer/warning delivery or explicit observer detachment, then
releases.  Encoded bytes mean =string-bytes= of the existing canonical codec
form: each record alone for the record cap and the complete append body for the
batch cap.  Do not add exact retained-object accounting, reconciliation
barriers, custom hashes, or cancellation state machines.  Async fork returns a
typed unsupported =e-work= for this release; no Daily call graph requires it.

Evidence queues an active request, a same-owner successor, and interleaved
unrelated read/write successors before killing the worker.  It proves exact
settlement/release of the first two, preserved read/write order for the latter,
replacement without a later trigger submission, and durable unrelated
readback.  Boundary/one-over tests use exactly 128 client requests, 1 MiB per
record, 256 records, and 8 MiB per batch.  Existing DP4 selected-request
recovery, C01 ownership, C04 bounds, and C06 waiter-free progress are re-run.
Bulk-failure evidence observes every failed handle/warning exactly once before
all notification tokens return to zero.
This is useful even before shell migration because one failure no longer
disables healthy runtime-store work.

** F92-DP6C: Session validation and quarantine

Superseded as an establishing package by =F92A2-DP2= in
[[file:addendum2.org][Addendum 2]].  The text below remains the unchanged
=F92-C09= behavior and evidence consumed by that package; it is not a second
delivery-package assignment.

Depends on DP6A.  Reopen returns a pending =e-work= (and public chat open still
returns its buffer) before storage activity.  A timer/callback validator reads
existing bounded pages, yields between pages, decodes records, and checks
exactly one root, unique durable record identities, parent references and chain
consistency, plus Board/session association shape.  It never scans a whole
journal on the invoking stack.

The session loader owns a process-local quarantine table keyed by session ID.
Its first diagnostic is immutable and truncated to 1,024 UTF-8 bytes.  Catalog
and list retain the entry but show =unvalidated= or =pending= until the current
process checks it, then show =quarantined= and the warning if invalid.  Ordinary
open validates before exposing the session as usable and otherwise returns a
failed work/surface.  Restart forgets the table, so entries return to
=unvalidated= until reopen/inspection reconstructs any quarantine.  Repeated
inspection preserves the first cause.
After external repair, explicit inspection or reopen clears it only after full
successful validation and canonical reload.  That reload replaces optimistic
session state and, after association validation, clears the corresponding
Board warning.  No quarantine fact, repair, or deletion is written to SQLite.
Full-database =quick_check= or =integrity_check= remains explicit operator work.

Evidence covers every validation dimension, multiple pages/yields, repeated
inspection, restart/reconstruction, repair/revalidate/clear, replacement of
optimistic state, Board-warning clear, and healthy sibling progress.  This is
useful independently because one damaged session no longer blocks catalog use.

* Architecture and aggregate design comparison

The correction retains the external SQLite worker but changes the application
contract above it.  The worker remains the side-effect adapter; the runtime
scheduler owns autonomous transport progress; session and Board application
services own straightforward enqueue order and may publish process-local state
after successful enqueue; chat owns pending and suspect surface composition.
No application ambiguity protocol or second persistence system is added.

Current aggregate after accepted DP5A: request lifetime, ownership, byte bounds,
transactional acknowledgement recovery, cold-open scheduling, dispatch,
deadlines, and terminal notification progress without an awaiter.  The current
defect is above that transport: durable session, Board, chat, and other domain
adapters still block interactive stacks.  The runtime also still has separate
read/write client queues, and the opt-in DP5B layer adds per-session lanes and
reconciliation that conflict with the reduced product contract.

Smallest faithful alternative: retain DP5A's event-driven scheduler and one
worker, collapse client reads/writes into one FIFO, remove/bypass DP5B owner
lanes from default composition, and expose narrow domain enqueue-return
operations.  Moving a synchronous call into a timer would still block the Emacs
event loop and preserve the reentrancy defect.

Decision: retain the worker and existing domain owners, but remove persistence
waits from interactive stacks.  The runtime client FIFO is the only scheduling
lane; session/Board owner IDs exist only for suspect fencing and diagnostics.
One-shot settlement observation publishes owner-local warning state.  A new
lease service, reconciliation coordinator, or second persistence worker is out
of scope.

Physical-boundary disposition:

- request state, dispatch, response correlation, and worker-replacement policy
  remain in =e-runtime-store.el= because they change together as one transport
  lifecycle;
- claim acquisition/release moves to one private
  =e-runtime-store-ownership.el= boundary because ordinary and offline workers
  must share exactly one exclusion policy while retaining separate SQLite
  operations;
- generic encoding bounds remain in =e-runtime-store-codec.el= and the two
  protocol endpoints;
- checkpoint omission and replay fallback remain in session catalog/storage
  composition because only the session owner can classify that projection as
  rebuildable;
- optimistic domain publication and suspect state remain in the session or
  Board application service; transport FIFO order remains solely in
  =e-runtime-store=; and chat readiness/warning rendering remains in chat.
  Stable domain policy does not depend on the concrete SQLite worker.

The several touched files express adapter propagation across real boundaries,
not a qualified physical-decomposition defect.  No modularization scope is
activated.

  surface.  It no longer promises synchronous durable readiness; immediate
  input queues behind the surface binding operation.
- DP5 changes no SQLite schema, worker operation semantics, receipt identity, or
  v4-to-v5 migration rule; ordinary open still rejects v4 and explicit offline
  migration remains the only upgrade path.
- Public application services use the existing =e-work= lifecycle semantics.
  Runtime-store request objects remain private transport handles.
  =e-runtime-store-await= and =e-runtime-store-call= coexist only for the
  enumerated batch/operator/offline/test entry points and reject when the
  existing interactive hot-path guard is active; interactive production code
  cannot use them as fallback.
- Feature 92 adds no persistence-specific cancellation lifecycle.  Existing
  =e-work= cancellation remains unchanged; owner-local failure settlement and
  capacity release are scheduler responsibilities, not cancellation policy.
- Under =F92-C05=, existing v4 stores require explicit offline migration and
  ordinary startup rejects them without mutation.  Their canonical stored
  values remain readable after migration.  Oversized old checkpoints are
  ignored as unusable projections; they are not rewritten or truncated during
  read.
- Existing property-bearing string encodings remain readable.  New
  property-bearing strings are rejected with bounded error metadata because
  text properties are presentation state outside the durable tagged grammar;
  core, layer, and default producers do not attach them to persisted values.
- Writes are never replayed under a new identity after timeout, worker loss, or
  protocol failure.  Recovery may resubmit the same identity because its
  receipt and mutation share one ACID transaction.
- This package does not promise that every submitted operation finishes within
  60 seconds or make wall-clock latency a deterministic gate.  It does require
  bounded recovery when a deterministically injected operation does not finish.
- It does not automatically remove an Emacs lock attributed to a live PID on
  the same boot.  A process-start mismatch is reported explicitly and remains
  fail-safe until the PID exits or the operator performs offline recovery after
  proving no runtime-store worker is live.
- It does not reload or terminate the user's running Emacs or mutate the
  canonical SQLite store.

Obsolete paths removed or bypassed by the current packages include the runtime
read/write split, the default DP5B owner-lane/reconciliation path, synchronous
hot-path adapter fallbacks, kill-hook flush/close, and the false Board barrier
claim.  Earlier accepted callback, paging, checkpoint, and owner-claim cleanup
remains historical implementation evidence.

* Design self-check

1. DP6A makes shared persistence survive one owner's failure; DP6B fixes the
   reported Daily hang; DP6C isolates damaged sessions; DP6D closes the wider
   hot-path inventory.  Each stopping point is independently useful.
2. The final direction is one external persistence worker with autonomous
   single-FIFO transport and domain-owned optimistic application operations.
3. The worker, SQLite transactions, and enqueue-return rule are stable.  The
   practical constants can change locally with measured traffic.  Quarantine
   is deliberately process-local and repair policy remains an operator choice.
4. Runtime FIFO and worker lifecycle belong to =e-runtime-store=; session and
   Board services own optimistic state and suspect fences; the session loader
   owns quarantine; chat owns visible pending/suspect composition.
5. Coupling is reduced because shells, timers, and callbacks depend on narrow
   domain =e-work= operations rather than synchronous SQLite-shaped calls.
   Owner identity is metadata, not another scheduling abstraction.
6. Stable domain policy continues to point toward its consumer-shaped storage
   port.  No session, Board, or chat policy depends on the concrete SQLite
   worker; transport recovery and queue partition remain below services.
7. SQLite process/open/send/recovery effects remain in the transport adapter.
   Application services retain only optimistic state, work observation, and
   warning publication.  Shutdown effects are reduced to detachment.
8. FIFO frames live through terminal settlement; suspect and quarantine entries
   live only in this Emacs process; chat pending state lives for the surface;
   durable records and receipts keep their existing SQLite lifetimes.  Derived
   state is rebuilt by canonical page-bounded reload.
9. Interactive stacks do less blocking work.  Async admission can retain more
   work, so the 128-request, 1 MiB-record, 256-record, and 8 MiB-batch limits
   bound practical memory and serialization.  No pathological graph proof is a
   release gate.
10. Runtime requests and =e-work= operations are distinct real contracts:
    transport implementations settle a private request; application services
    expose domain completion or retain it behind a domain result.  In-memory
    implementations may complete immediately without weakening durable behavior.
11. DP6 changes no schema or worker operation ABI.  =e-chat-open= keeps its
    buffer return but changes readiness to explicit pending state.  Blocking
    remains limited to enumerated batch/operator/offline/test callers.  Async
    fork is explicitly unsupported in this release.
12. Remove/bypass runtime read/write splitting, default DP5B owner lanes and
    reconciliation, synchronous hot-path adapters, timer mutation freeze, and
    kill-hook flush/close.  Do not extend cut-pin or bespoke cancellation code.
13. Expected capacity failures reject before enqueue.  Exhausted persistence
    failure settles the active and same-owner successor work visibly; protocol
    corruption preserves the first bounded cause; unexpected bugs still surface.
14. Runtime tests prove the FIFO, failure partition, restart, limits, and
    canonical reload independently.  The graphical public Daily scenario proves
    exact visible composition, and structural reachability prevents hidden waits
    without coupling behavior tests to private queue representation.
