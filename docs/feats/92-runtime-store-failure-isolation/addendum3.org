* Ownership and modularization

- =e-tools= owns model-tool schema validation and execution.  Observability
  adapters consume execution facts; they do not add required model arguments.
- =e-actions= owns immediate-versus-detached result delivery.  Daily does not
  introduce an action-specific await or polling surface.
- SQL Board orchestration owns terminal fact collection; chat service owns one
  continuation delivery carrying a detached consumer view.
- Grimoire Daily owns artifact-contract validation, lifecycle transitions,
  generated-section materialization, and Git publication.  Generic Board,
  resource, presentation, and runtime-store code do not learn Daily policy.
- Canvas/chat presentation owns snapshot rendering and revision display.  A
  presentation snapshot never becomes lifecycle authority.

** Concrete Daily lifecycle record seam

Daily lifecycle uses existing canonical Board facts; it does not extend the
generic orchestration vocabulary.  Grimoire appends facts through
=e-board-sqlite-publication-target-fact-start= with tags =daily-lifecycle= and
attributes containing =:daily-run-id= and =:daily-event=.  The record reference
contains a versioned Daily-owned payload.  Grimoire queries one run through
=e-board-sqlite-publication-target-record-page-start= with an exact
=:daily-run-id= attribute selector, a 32-record limit, and a one-megabyte page
bound already enforced by the Board worker.  Truncation or an invalid transition
is a visible Daily error, never a partial projection.

The pure Daily reducer accepts the monotone event sequence =started=,
=materialized=, =published=, =finalized=, plus a terminal =failed= event.  Stable
source keys are =("daily-lifecycle" RUN-ID EVENT REVISION)=.  =materialized=
carries the complete normalized generated-section map and its SHA-256 revision;
=published= carries that revision and the Git commit; =finalized= carries the
same revision, commit, finalization time, snapshot status, and bounded gaps.
Duplicate source keys are idempotent.  A different payload for the same key,
an event whose predecessor is absent, or a revision/commit mismatch is a
divergence error.  Org properties may display these values, but reads never use
them to choose lifecycle state.

** Report-admission seam

=e-subagent-spawn= accepts an optional report-admission function and retains it
only in the executing child registry record.  =subagents/:report= invokes that
function before setting =:reported=.  The function receives the detached child
assignment and proposed summary/outputs.  Daily supplies a closure over its
frozen artifact contract; a valid report is returned unchanged, while an
invalid report raises an action error back to the child and publishes no
terminal success.  No validator is persisted, reconstructed, or exposed as a
model-facing option.

** Exact repetition rule

The harness tracks only the immediately preceding model-facing tool failure in
the active turn.  Its fingerprint is the tool name plus normalized bounded
error.  The first failure is returned to the provider normally.  A second
consecutive identical failure terminates the turn with one bounded diagnostic.
Any successful tool or different failure resets the count.  Settlement discards
the counter.

** Process-report query projection and schema v7

Process-report subtype and association are durable query facts, not values for
an application-side scan to rediscover after reading an arbitrary journal
page.  Schema v7 adds the derived relation
=session_process_report_index(session_id, position, association_ordinal,
report_type, marker_id, provider_request_id)=.  Its primary key is
=(session_id, position, association_ordinal)= and its foreign key is
=(session_id, position) REFERENCES session_records(session_id, position) ON
DELETE CASCADE=.  Ordinal zero is the one required base row and has a SQL
=NULL= marker id.  Marker, triage, and extraction records additionally receive
one association row for each normalized distinct marker id, ordered
lexicographically from ordinal one.  The maximum association count is 64;
duplicates collapse before the bound is checked.  Request-shape base rows carry
their exact provider request id.  Other report types carry neither association
nor request identity.

The projection has partial indexes on
=(session_id, report_type, position DESC)= for base rows,
=(session_id, marker_id, report_type, position DESC)= for association rows, and
=(session_id, provider_request_id, report_type, position DESC)= for base rows
with a request identity.  Consumer operations are: a newest marker page that
returns each selected marker with its latest triage in one query; an exact
canonical marker read; a bounded newest triage page for one marker; a bounded
marker-associated extraction page; bounded exact request-shape lookup for the
current request-id set; and an exact marker count.  Every semantic predicate is
applied in SQL before =LIMIT=; none of these operations obtains a generic page
and filters it in Emacs.  Page results carry an explicit cursor/truncation
value.  Query results join to =session_records=, whose encoded record remains
the sole canonical payload; the projection never becomes an Emacs mirror.

The session append transaction derives and inserts these rows beside the
canonical journal record.  An explicit offline upgrade first creates and fully
verifies one backup outside the install transaction.  It then performs table
creation, complete bounded population, projection parity verification, every
required migration-row insert, and the schema-version update inside one
=BEGIN IMMEDIATE= transaction immediately before one =COMMIT=.  Any pre-commit
failure rolls back to the exact source image; a deliberately injected
post-commit failure restores and verifies the backup before returning failure.
It never rewrites canonical journal payload bytes.

The supported graph is =v6 -> v7=, =v5 -> v6 -> v7=, and =v4 -> v5 -> v6 ->
v7=.  The latter two retain each intermediate migration identity and checksum,
use the same one verified backup, and install all stages atomically.  Fault
tests cover each stage and both sides of the final commit.  Invoking the
operator on a verified v7 store is an idempotent read-only no-op that creates no
backup.  Ordinary startup rejects v4, v5, and v6 and performs no schema or data
repair.  There is no hidden v6.1, runtime payload scan, compatibility branch,
or silent schema mutation.

Migration verification requires exactly one base row per canonical
process-report record and exactly one association row per normalized distinct
marker association, with no orphan row and no association beyond 64.  Malformed
input fails with a bounded diagnostic containing only session id, journal
position, report type, and violated bound/field; it never includes the report
payload.

** Apply acknowledgement ordering

Daily =:apply= is an asynchronous action.  It validates the complete section
map and preserves protected sections, saves the materialization, then enqueues
the immutable =materialized= lifecycle fact containing the exact normalized map
and revision.  The action settles only after that fact commits.  A retry before
the fact exists reapplies the same map idempotently; a retry after it exists
compares the current generated sections to SQLite's expected revision.  The
continuation awaits the apply work reference before calling finalize.

The implementation explicitly crosses two repositories but does not activate a
whole-root physical-decomposition project.  Each changed responsibility already
has a cohesive semantic owner.  Any source unit that would gain a second
unrelated reason to change must be split at the smallest private boundary before
acceptance; file size alone does not require extraction.

* Compatibility and removals

There is no compatibility requirement for =stated_purpose=, opaque started
receipts, duplicate =run-status= lookup, file-owned Daily lifecycle, direct
whole-file recovery, or the removed synchronous session aggregate APIs.  Delete
their implementations, instructions, tests, and aliases.  Compatibility for
durable data is different from compatibility for obsolete APIs: the v6-to-v7
offline migration preserves existing canonical process-report records while
building their relational query projection.  Offline migration may also read
old Daily properties only to seed missing SQLite lifecycle facts; ordinary
runtime must never use them as authority afterward.

* Explicit non-goals

- No global file lock or generic managed-resource framework.
- No application-side Board, session, or task replica.
- No generalized workflow or distributed transaction engine.
- No synchronous wait in interactive Emacs.
- No full-history replay, catalog, checkpoint, or reconciliation scan.
- No fork work, pathological exact-accounting expansion, or unrelated Grimoire
  archive cleanup.
