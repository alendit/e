** DONE High: Lost worker acknowledgement freezes the application

*** Problem

Before DP4, the worker committed each write transaction before emitting its
response, but did not record the response correlation ID in that transaction.
On timeout the parent could not ask SQLite whether that request committed, so
the selected Feature 87 failure model killed the worker and permanently froze
the shared store.  That turned a local acknowledgement failure into
application state.

*** Evidence

The fresh trace identifies submitted request =w:83= as =catalog-put= and queued
request =w:84= as =board-pickup-transition=.  The latter was correctly
cancelled and attributed to its blocker, but the former entered global
fail-closed recovery.  The resumed Daily session was small, and the exact
1,263-entry catalog completed through the production protocol in about 1.12
seconds on a disposable clone, so projection size alone does not reproduce the
stall.

At the invalidated revision, no deterministic or graphical test injected a
stall after a real =catalog-put= had been submitted.  The projection-failure
integration fake signalled before transport, while the generic
submitted-timeout test asserted the now-disproved global-freeze policy.

The invalidated scheduler also cleared its immutable preflight frame
immediately after submission and retained a caller-owned body.  Exact
same-identity replay therefore required a bounded immutable frame lifetime
through transactional resolution, including renewed C04 memory evidence.  The
v4 schema had no receipt relation, and worker ownership alone could not
authorize old-receipt cleanup because a live parent might be replacing its
dead worker.

*** Acceptance

Record request identity, request fingerprint, and result in the same SQLite
transaction as every write.  Under deterministic worker-side stalls on both
sides of COMMIT, replace the worker and resolve the same request identity
without application policy, then commit the nested queued Board transition
exactly once.  Exercise the real default-runtime/session/Board composition and
its visible timer outcome.  Acceptance also requires the explicit v4 to v5
upgrade/rollback matrix, immutable replay under caller mutation, parent-liveness
receipt retention, a one-attempt recovery bound, and exact terminal settlement
when recovery is exhausted.

** Resolved High: Empty worker response could leave an active request pending

*** Problem

The process filter treated a newline-only worker frame as ignorable input.
Because the worker protocol has no keepalive frame, an active request could

typed fail-closed path, while the worker treats empty input as malformed rather

** Resolved High: Multibyte raw-byte characters bypassed canonical preflight

*** Problem

For Emacs multibyte raw-byte characters =#x3fff80= through =#x3fffff=, the
source representation occupies two bytes but =prin1= emits four octal ASCII
bytes.  The initial exact-size counter therefore undercounted each such value
by two bytes.  Base64 rounding meant a request could pass both the understated
canonical check and an unchanged wire ceiling.

*** Change

The counter now adds two bytes for every multibyte raw-byte character.  The
preflight contract remains expressed in final canonical bytes, independent of
the source string's internal representation.

*** Evidence

The codec test covers every raw octet 128 through 255 in multibyte text with
quote and backslash cases.  The production preflight test uses three raw-byte
characters, producing a =3k+2= canonical size, and proves rejection at the
one-byte-smaller limit even though that limit has the same derived base64 wire
ceiling.  The focused runtime-store file passes 28/28 and the complete suite
passes 2,761/2,761.

* DP4 correction evidence (accepted implementation)

** Resolved implementation finding: runtime identity could be stolen from a live parent

The initial DP4 state row named only a runtime id and could replace an
unretired predecessor, leaving its receipt without replay authority.  The
worker now receives the scheduler's bounded parent boot, PID, and process-start
identity with =open=, persists all three in the singleton, and preserves state
only for that same runtime and parent.  A different runtime replaces a retired
row, or an unretired row only after recorded-parent death, prior boot, or
process-start mismatch proves safe; it deletes that predecessor's receipts in
the same transaction before replacing the state.  Live-parent refusal leaves
both row and receipt unchanged.

The boot token is an opaque hash of PID 1's start identity, so it is stable
across separate Emacs processes on one host boot and changes when that boot
changes; it is not an Emacs PID/start/time nonce.  This makes boot inequality
valid evidence independently of the live-parent PID/start check.

=e-runtime-store-s92-runtime-state-parent-lifetime-and-clean-cycles= covers
live refusal, same-identity recovery, prior-boot cleanup, PID reuse, retired
replacement, repeated cycles, one state row, and zero-or-owned receipts.
=e-runtime-store-s92-parent-boot-is-host-stable-across-emacsen= starts two
batch Emacsen and proves equal boot tokens with distinct PID/start identities.

** Resolved implementation finding: recovery setup could strand the original request

Recovery now treats the internal replacement =open= as setup for the retained
domain request.  Worker exit, malformed output, or contention while that open
is active exhausts the single incident, retains the initiating typed cause,
and settles original active and queued work exactly once.  Cooperative queued
await also observes an earlier submitted active deadline before its own later
deadline.

=e-runtime-store-s92-replacement-open-loss-settles-original-and-queue= uses
the production worker open-loss seam; =e-runtime-store-s92-replacement-open-
contention-keeps-first-cause= covers typed ownership failure; and
=e-runtime-store-s92-queued-waiter-observes-earlier-active-deadline= provides
the deterministic scheduler clock witness.

** Resolved implementation finding: receipts did not bind all replay semantics or result size

Receipt fingerprints now hash kind, body, write prefix, and acknowledgement
prefix while the request id remains the receipt key.  Before COMMIT, receipt
results are bounded against the complete correlated =:id= / =:ok= / =:result=
success response, rather than against a bare SQLite result payload.  One-over
output therefore rolls back its domain mutation and receipt together.

=e-runtime-store-s92-receipt-collision-watermark-and-retirement= includes a
same-body changed-prefix collision; =e-runtime-store-s92-receipt-result-bound-
rolls-back-mutation= emits the exact full success response on both original
execution and receipt replay, then verifies that a one-over response leaves no
domain record or receipt.
