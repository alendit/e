* Status

Implemented in the current delivery package.  The document remains
=In-progress= in the dev-work ledger pending focused review; this is not a
Feature 92 =Done= claim.

This addendum rebaselines the remaining Feature 92 work around an RDBMS-first
runtime boundary.  SQLite is the durable authority for identity, current state,
ordering, history, associations, routing, task state, and query indexes.  Emacs
keeps only the bounded state needed to present a result or continue work that
has an explicit live owner.

The parent [[file:plan.org][Feature 92 plan]] and the
[[file:addendum.org][accepted-session projection addendum]] remain authoritative
for enqueue-and-return mutation and owner-local failure isolation.  This
addendum supersedes both their durable-state reconstruction assumptions and any
claim that ordinary mutation submission order is a semantic history guarantee.
Ordinary mutations are independent transactions; only an acknowledged commit
before a later submission, or one explicit multi-change transaction,
establishes application-visible happens-before.  This addendum also supersedes
assumptions that ordinary startup or interactive access may construct a durable
mirror, enumerate every session, or use an opaque catalog/checkpoint value as
the normal query model.

=F92A2-DP1= remains Accepted.  The implementation completes
the scoped =F92A2-DP2=--=F92A2-DP5= runtime path: public Daily and persisted
session navigation use detached bounded queries; selected provider context is
assembled from one request-scoped path result plus bounded crossing optimistic
mutations; Board uses one bounded current-state/set query; tasks query and
atomically claim runnable work; and the public graphical delay/release/failure
gate passes end to end.  No active-session generation loader, candidate
aggregate, catalog/stub mirror, checkpoint publication, or durable-state cache
is part of the ordinary v6 path.

The full repository run is retained as a regression census, not as a license to
reintroduce superseded replica behavior.  The package-relevant suites, public
graphical gate, and complete repository suite are green on the delivered
revision recorded below.

** Warning vocabulary

These terms have separate owners and must not be collapsed into a generic
"load" state:

- *transport unavailable/upgrading* is a runtime-store readiness/status
  diagnostic owned by the transport; it does not issue domain requests;
- *pending/loading* is presentation status for an explicitly requested
  asynchronous query, not a durable or process-wide session lifecycle;
- *request-local read failure* settles that detached work and is retryable;
- *invalid requested state* quarantines only the affected session under the
  retained =F92-C09= contract; a Board may show a warning but is not
  quarantined; and
- *post-publication write failure* records the first bounded suspect diagnostic
  for that mutation owner and fences only that owner.

* Reason for the RDBMS-first boundary

The external worker already provides the right durability and ordering
boundary, but older application paths still treat durable state as if it were
an Emacs-owned file-era object.  The correction is architectural:

- SQLite owns durable identity, current query state, journal order, history,
  session/Board associations, routing relations, task state, and indexes;
- Emacs owns presentation, subscribers/callbacks, timers, executing work,
  bounded optimistic mutations, detached request results, and the visible
  viewport;
- no process-wide catalog, active durable session replica, Board history copy,
  task snapshot, or hidden whole-session reconstruction is allowed; and
- a storage result is useful only when it is consumer-shaped, detached, and
  bounded.

The observed operator-sized shape remains the scaling reason for this work.
Read-only inspection on 2026-09-05 found 1,277 sessions, 596,312 session
records, a 1,139,660-byte catalog blob, and 1,275 resume checkpoints occupying
874,349,564 encoded bytes; the largest checkpoint was 27,518,128 bytes.  The
fixture is used only through a disposable copy or an equivalent generated
database.  It is not a runtime permission to materialize any of those
collections in Emacs.

* Decisions

** SQLite is the durable authority

SQLite is authoritative for durable identity, current state, journal position,
history, session and Board association, routing state, task state, and the
indexes that answer real consumer queries.  The journal is the canonical event
history and provenance.  Query rows are maintained transactionally beside the
journal; they are not an Emacs-published catalog under a new name.

Session metadata, current branch/options, exact Board association, and indexed
ordering are relational current-state values.  Recent messages and selected
provider context are bounded results.  No application-level historical paging
API is retained until a concrete presentation or inspection consumer owns it;
the worker's bounded record cursor remains an explicit test/operator primitive.

** Emacs owns bounded interactive state

Emacs retains only presentation buffers and view state, visible viewport data,
subscriber/callback registrations, timers, executing task or turn work,
bounded in-flight optimistic mutations, and detached request-scoped rows/pages.
These values have an explicit presentation, subscription, execution, or
request owner.  They are not a durable replica and are not a general cache.

There is no whole or active session replay in the interactive path, no private
candidate store, no generation loader, no active durable replica, and no
release cache.  A Daily buffer is a presentation object; it does not imply a
second durable session authority.  If a provider turn needs context, the
session service queries the selected branch/compaction path in bounded pages
and retains only the working context needed by that turn.

** Daily and session access are query-shaped

Opening Daily returns its buffer immediately and starts separate asynchronous
work for exact session metadata, exact Board association, and the visible
recent-message window.  Composer input and unrelated timers remain live while
any of those queries are pending.  A future history view must introduce its own
bounded stable-cursor request when that consumer exists; DP2 does not retain a
speculative application paging facade or allocate unloaded session objects.

Session commands consume bounded explicit current state and append the canonical
record together with its domain-derived query delta in one transaction.  A
command that needs selected context requests the required branch/compaction
path explicitly.  It must not obtain a hidden full aggregate as a convenience
for a current-state update.

** Board is a lightweight controller

Board startup uses exact current-row queries for the Board, participants, and
pickups, plus a bounded visible working-message window and set-based routing
queries.  The Board service retains live subscribers, callbacks, timers,
working messages, and executing actions only.  Existing explicit observer
continuation retains its bounded cursor contract, but no new generic Board
history facade is introduced.  Board startup never replays all Board records
and never performs one routing query per historical message.

** Task scheduling is claim-based

The task scheduler queries runnable work and atomically claims it.  Runnable
rows are detached query/claim input; Emacs retains only executing task state
and live execution handles.  Terminal history remains in SQLite; an inspection
page is deferred until an actual inspection consumer exists.  A queue startup
must not reconstruct a whole task snapshot.

** Interactive storage never waits

Every path reachable from startup, UI, timer, tool, capability action,
resource method, provider callback, turn orchestration, or shutdown enqueues
bounded work and returns.  It must not call =e-runtime-store-call= or await via
=e-runtime-store-await=, use =accept-process-output=, flush, wait for
open/commit/retry/recovery/close, or turn a storage operation into a
synchronous stack call.  Named batch, operator, offline-migration, and
focused-test APIs are the only blocking boundaries, and their names and callers
must make that authority explicit.

** Mutation ordering is transactional, not an application FIFO

The store does not promise that two independently submitted mutations commit in
submission order.  SQLite chooses the transaction order.  If a caller observes
the commit acknowledgement for A and only then submits B, B is after A.  If a
caller needs several changes to be indivisible or internally ordered without an
interactive wait, it submits one domain operation that the worker executes in a
single SQLite transaction.  Otherwise the mutations are concurrent and their
commit order is deliberately unspecified.

Emacs may retain a bounded set of unacknowledged optimistic intents so a live
surface can render immediately and attribute a later failure to its owner.  That
set is not an execution queue and confers no durable ordering.  The transport
may buffer bounded frames because one external process has finite capacity, but
that is private resource ownership rather than a session consistency contract.
Backpressure may reject admission at the bound; it must not turn an interactive
call into a wait.

** Session deltas and offline upgrade

The session domain owns exhaustive sealed-command interpretation.  The worker
reads the authoritative current row and interprets that command inside the same
SQLite transaction that commits the journal record, query row changes, deletion
control, and receipt.  Emacs does not perform a current-row read merely to
derive the next write.
Receipt replay returns its small recorded result and does not apply a delta a
second time.  No catalog/checkpoint publication is part of ordinary v6 runtime
operation.

The explicit stopped-store v5-to-v6 migration is operator-only.  It creates a
verified backup, derives query rows solely from canonical v5 journal records,
does not read or trust retired catalog/checkpoint projections, preserves journal
identity/position/payload digests, and rolls back to the verified backup on
faults.  It is the one compatibility boundary; ordinary v6 startup does not
become a dual v5/v6 runtime.

The v5 journal may contain historical record families that its aggregate
ignored and the current command grammar no longer emits.  The offline adapter
preserves those rows verbatim and advances the query row's journal high-water
without assigning them new domain meaning.  This compatibility is not exposed
to ordinary v6 writers.  A repeated legacy root retains the retired reader's
replacement semantics during derivation; current v6 writes still reject a
second root.  Canonical journal preflight runs before the potentially large
verified backup is created, while all schema writes remain backup-protected.
Rootless historical journals retain their canonical rows but receive no
fabricated session query row, matching the retired reader's behavior.

** Failure partitions remain distinct

An unavailable transport or upgrade is reported by the transport readiness and
status channel.  A failed exact/page read is request-local and retryable.  An
already-published optimistic write failure records only its owner's first
bounded suspect diagnostic and fences that owner.  Unrelated sessions, Boards,
tasks, and request work remain eligible for service.  Later post-hoc validation
must preserve those partitions without introducing a session loader or durable
mirror; it is not part of this implementation package.

* Target ownership and modularization

** Architecture scope decision

- Trigger :: Startup prewarming exposed process-wide durable mirrors and
  synchronous interactive restoration.
- Contract :: =F92A2-C01=--=F92A2-C10=.
- Durable owner :: SQLite and its worker own durable identity, current state,
  ordering, history, associations, routing, task state, and indexes.
- Process owner :: Emacs owns presentation, subscribers/callbacks, timers,
  executing work, bounded in-flight mutation, detached results, and viewport.
- Desired direction :: Transport-only startup, query-shaped async access, and
  explicit bounded working values.  There is no active durable session cache.
- Decision :: Correct through the ordered packages below.  Do not add a
  candidate store, generation loader, replay cache, background mirror, or
  renamed catalog/checkpoint projection.

* Delivery packages

** F92A2-DP1: Transport-only startup (Accepted)

DP1 establishes =F92A2-C01= and =F92A2-C02=.  The process-wide runtime
transport starts/reuses one external worker and private open control.  Default
composition supplies the final directory and bounded ports without domain
SQL, identity enumeration, row creation, or readiness wait.  Its accepted
graphical evidence is recorded in the implementation ledger above.

** F92A2-DP2: SQLite session queries, deltas, and offline upgrade (Implemented)

DP2 establishes =F92A2-C03=--=F92A2-C05= and =F92A2-C09=.  Its implementation
order is:

1. define bounded sealed commands and their pure domain interpretation;
2. expose exact/page reads and interpret each command against the authoritative
   current row inside the worker transaction;
3. verify the stopped-store v5-to-v6 upgrade from canonical journals with
   backup, witnesses, parity, rollback, and reopen; and
4. cut the public session, Daily, and provider-context consumers over to those
   bounded async operations, remove old catalog/checkpoint and synchronous
   interactive reachability, and delete unused application paging facades.

The package does not create a candidate store, replay a whole or active session,
install a generation loader, maintain an active durable replica, or add a
release cache.  Daily open returns its buffer first, then requests exact
metadata, association, visible recent messages, and selected context pages.
The package is not accepted until public consumers and obsolete paths satisfy
that boundary.

Gate: a disposable v6 fixture with at least the operator-observed 1,277-session
shape starts with zero session queries; opening one Daily reads only its exact
rows and visible page; session commands
append transactional deltas; and the installed store has no obsolete catalog or
checkpoint relations.  The disposable v5 upgrade proves journal parity,
witness-only legacy validation, affected-session diagnostics, fault rollback,
and production-v6 reopen.  No test may accept process-wide mirror allocation.

** F92A2-DP3: Bounded Board controller (Implemented)

DP3 establishes =F92A2-C06=.  Construct and initialize a lightweight Board
controller from exact current Board/participant/pickup rows, a set-based routing
query, and the bounded visible working-message window needed by current
subscribers.  Retain
callbacks, subscriptions, timers, and executing actions only.  No generic
history paging API is added without a presentation consumer.  No Board-history
replay and no N+1 routing query is permitted.

Gate: increasing unrelated Board history by an order of magnitude does not
increase retained Emacs controller state beyond the declared visible window.
Query-count, identity, visible-window, and subscriber-teardown tests pass.

** F92A2-DP4: Query-and-claim task scheduler (Implemented)

DP4 establishes =F92A2-C07=.  Query runnable work as detached claim input and
atomically claim it; retain executing task state and live handles only.  Terminal
history stays in SQLite; a page API is deferred until an inspection consumer
exists.  Do not rebuild a task snapshot or copy unrelated terminal rows into
the scheduler.

Gate: increasing terminal history by an order of magnitude does not increase
retained scheduler state beyond queue identity and executing task handles.

** F92A2-DP5: All interactive paths and public acceptance (Implemented)

DP5 establishes =F92A2-C08= and =F92A2-C10= after DP1--DP4.  Classify every
interactive storage caller, convert remaining Board/task/cron/voice/Goodnite/
raw-result/session/provider paths to bounded async owner operations, and keep
explicit blocking only in named batch/operator/offline/test boundaries.

Gate: no default interactive call graph reaches =e-runtime-store-call=,
=e-runtime-store-await=, =accept-process-output=, flush, or
open/commit/retry/recovery/close wait.  Held open/read/write leaves graphical
input, redisplay, three heartbeats, and a composer edit live.  Read failure,
and post-publication write failure produce the distinct request/owner-local
partitions above, while a healthy sibling continues enqueuing, persisting,
querying, and rendering.

* Architecture self-check

1. *Useful stopping point*: yes.  Startup, Daily/context, Board, task, and the
   remaining persistence owners now have a coherent nonblocking v6 path even if
   no further Feature 92 work is attempted.
2. *Final direction*: this moves durable/queryable facts into SQLite and leaves
   Emacs with bounded live coordination and presentation values only.
3. *Stable versus uncertain decisions*: SQLite authority, transport-only
   startup, transactional query deltas, and enqueue-return interaction are
   stable.  SQL indexes, page/window sizes, and private callback representation
   are local and reversible; no speculative framework hides them.
4. *Ownership*: transport owns worker lifecycle; session/Board/task domains own
   semantics; SQLite adapters own SQL and transactions; presentation owns
   buffers/subscribers.  Each has one primary reason to change.
5. *Coupling and interfaces*: coupling is reduced from aggregate/catalog
   reconstruction to exact-row, bounded-page, set-query, query-and-claim, and
   transactional-delta operations shaped for their current consumers.
6. *Dependency direction*: domain policy does not depend on SQL or presentation;
   adapters depend on domain-shaped commands, and shells consume application
   services.  No stable policy points toward the worker implementation.
7. *Side effects*: SQL, process I/O, file backup/install, and worker lifecycle
   remain in adapters or explicit operator shells.  Derivation and optimistic
   projection are pure domain/application work.
8. *State and lifetime*: SQLite owns durable state.  Emacs retains buffers,
   subscriptions, timers, executing handles, bounded in-flight mutations,
   request-local query cuts/results, and visible windows only for their live
   request/presentation/execution lifetimes.
9. *Performance*: startup issues zero domain SQL; interactive paths never wait;
   pages, context paths, Board windows, bounded admission, and raw-result content
   have practical bounds.  Durable history growth does not grow retained Emacs
   state outside an explicitly requested viewport.
10. *Substitutability*: the async ports promise immediately returned =e-work=
    and bounded detached values.  Named synchronous adapters are explicitly
    batch/test-only rather than pretending to satisfy the interactive contract.
11. *Compatibility*: v5 is supported by stopped-store offline migration.
    Obsolete v6 catalogs/checkpoints, whole restoration, task snapshots, and
    synchronous interactive facades are not compatibility requirements.
12. *Legacy removal*: ordinary v6 no longer reaches catalog/stub/checkpoint,
    whole-session/Board restoration, task snapshot restoration, candidate
    stores, generation loaders, or active durable replicas.  Source retained
    solely for offline/test compatibility is named as such and fails fast if an
    async v6 caller reaches it.
13. *Errors*: failed reads settle only their request; failed optimistic writes
    preserve the first bounded diagnostic and fence only their owner; unrelated
    admitted work continues through lazy replacement.  Unexpected errors surface at
    the worker/application boundary instead of being swallowed.
14. *Tests*: pure query derivation, SQLite transaction/rollback, bounded query,
    Board/task behavior, nonblocking reachability, and raw-result limit tests
    isolate core contracts.  Five graphical selectors prove startup, bounded
    existing-Daily reads, the delayed Org Canvas release/failure/sibling flow,
    the public =e-chat-new= plus interactive-composer path, and the stopped-v5
    upgrade followed by a fresh public chat without depending on the user's
    Emacs.  A service helper is not accepted as a substitute for the public
    command it claims to cover.

* Tool-continuation counterexample and transactional command correction (2026-09-07)

A real second prompt containing a =run_elisp= tool call disproved the preceding
public-gate claim.  The previous graphical stream emitted assistant text only;
it never exercised provider -> model-facing tool -> provider continuation.  Two
aggregate reads therefore survived on that exact path.  The post-tool lifetime
callback queried the durable current generation, and the continuation preflight
searched the durable selected path to recover the tool-call entry identity.
Both reached the async-v6 aggregate rejection after the tool had already run.

The request now owns both facts it creates.  A streamed tool-call message gets
its durable entry identity before optimistic append, and the active turn carries
its already-selected context generation through the tool observation.  Neither
callback queries or reconstructs a session aggregate.  The graphical stream
fixture now emits a real =run_elisp= call, terminates the first provider request
with =tool-use=, verifies the tool-call identity and result in the second wire
request, and only then returns assistant text.  It also retires the completed
provider request before terminal callbacks so a synchronously started follow-up
cannot be erased by the fixture itself.

The same counterexample exposed a deeper write-path mistake: the session
application service was reading the current query row, deriving a record and
next row in Emacs, and serializing each owner through an application FIFO.  That
made transport order part of session semantics.  It is removed.  Emacs now
submits each sealed command independently.  The session worker reads the
authoritative current row, interprets the command, and commits the journal row,
current row, and optional tool transition in one SQLite transaction.  The
process-local owner collection contains only bounded unacknowledged optimistic
intents for rendering and failure attribution; it is not an execution queue.

The ordering contract is intentionally small:

- independently submitted mutations have no promised order;
- if A is acknowledged before B is submitted, B is after A; and
- changes that must be indivisible or internally ordered without waiting are
  represented by one domain operation and one SQLite transaction.

The external worker transport still has a bounded private frame buffer because
the subprocess has finite capacity.  That buffer provides resource ownership
and admission backpressure only.  It is not a linear-history API and callers
must not infer semantic order from it.
