#+title: Addendum 2: RDBMS-Owned Durable State and Bounded Presentation Values
#+date: 2026-09-05
#+startup: overview

* Status

In-progress.

This addendum rebaselines the remaining Feature 92 work around an RDBMS-first
runtime boundary.  SQLite is the durable authority for identity, current state,
ordering, history, associations, routing, task state, and query indexes.  Emacs
keeps only the bounded state needed to present a result or continue work that
has an explicit live owner.

The parent [[file:plan.org][Feature 92 plan]] and the
[[file:addendum.org][accepted-session projection addendum]] remain authoritative
for enqueue-and-return mutation, ordered semantic publication, and owner-local
failure isolation.  This addendum supersedes their assumptions that ordinary
startup or interactive access may construct a durable mirror, enumerate every
session, or use an opaque catalog/checkpoint value as the normal query model.

=F92A2-DP1= is Accepted after the independent correction review of =aa893823=
closed with no P0--P2 findings and the prior findings resolved.  =F92A2-DP2=
is In-progress only for the implementation extent currently present: the pure
session derivation seam, v6 query/storage worker, offline v5-to-v6 work, and a
request-scoped asynchronous session read port.  Its public Daily/context
cutover and obsolete-path removal are not accepted.  =F92A2-DP3=,
=F92A2-DP4=, and =F92A2-DP5= remain not-started.  No active-session generation
loader or candidate aggregate is part of this rebaseline.

** Warning vocabulary

These terms have separate owners and must not be collapsed into a generic
"load" state:

- *transport unavailable/upgrading* is a runtime-store readiness/status
  diagnostic owned by the transport; it does not issue domain requests;
- *pending/loading* is presentation status for an explicitly requested
  asynchronous query, not a durable or process-wide session lifecycle;
- *request-local read failure* settles that detached work and is retryable;
- *invalid requested state* quarantines only the affected session under the
  retained =F92-C09= contract; a Board may show a warning but is not
  quarantined; and
- *post-publication write failure* records the first bounded suspect diagnostic
  for that mutation owner and fences only that owner.

* Reason for the RDBMS-first boundary

The external worker already provides the right durability and ordering
boundary, but older application paths still treat durable state as if it were
an Emacs-owned file-era object.  The correction is architectural:

- SQLite owns durable identity, current query state, journal order, history,
  session/Board associations, routing relations, task state, and indexes;
- Emacs owns presentation, subscribers/callbacks, timers, executing work,
  bounded optimistic mutations, detached request results, and the visible
  viewport;
- no process-wide catalog, active durable session replica, Board history copy,
  task snapshot, or hidden whole-session reconstruction is allowed; and
- a storage result is useful only when it is consumer-shaped, detached, and
  bounded.

The observed operator-sized shape remains the scaling reason for this work.
Read-only inspection on 2026-09-05 found 1,277 sessions, 596,312 session
records, a 1,139,660-byte catalog blob, and 1,275 resume checkpoints occupying
874,349,564 encoded bytes; the largest checkpoint was 27,518,128 bytes.  The
fixture is used only through a disposable copy or an equivalent generated
database.  It is not a runtime permission to materialize any of those
collections in Emacs.

* Decisions

** SQLite is the durable authority

SQLite is authoritative for durable identity, current state, journal position,
history, session and Board association, routing state, task state, and the
indexes that answer real consumer queries.  The journal is the canonical event
history and provenance.  Query rows are maintained transactionally beside the
journal; they are not an Emacs-published catalog under a new name.

Session metadata, current branch/options, exact Board association, and indexed
ordering are relational current-state values.  Recent messages and selected
provider context are bounded pages.  Historical records are addressed by
stable cursors and fetched only by a real history or context consumer.

** Emacs owns bounded interactive state

Emacs retains only presentation buffers and view state, visible viewport data,
subscriber/callback registrations, timers, executing task or turn work,
bounded in-flight optimistic mutations, and detached request-scoped rows/pages.
These values have an explicit presentation, subscription, execution, or
request owner.  They are not a durable replica and are not a general cache.

There is no whole or active session replay in the interactive path, no private
candidate store, no generation loader, no active durable replica, and no
release cache.  A Daily buffer is a presentation object; it does not imply a
second durable session authority.  If a provider turn needs context, the
session service queries the selected branch/compaction path in bounded pages
and retains only the working context needed by that turn.

** Daily and session access are query-shaped

Opening Daily returns its buffer immediately and starts separate asynchronous
work for exact session metadata, exact Board association, and the visible
recent-message window.  Composer input and unrelated timers remain live while
any of those queries are pending.  A history view requests a bounded stable
cursor page; it does not enumerate all identities or allocate an unloaded
object for each row.

Session commands consume bounded explicit current state and append the canonical
record together with its domain-derived query delta in one transaction.  A
command that needs selected context requests the required branch/compaction
path explicitly.  It must not obtain a hidden full aggregate as a convenience
for a current-state update.

** Board is a lightweight controller

Board startup uses exact current-row queries for the Board, participants, and
pickups, plus a bounded visible working-message window and set-based routing
queries.  The Board service retains live subscribers, callbacks, timers,
working messages, and executing actions only.  Older observer history is a
stable-cursor page fetched on demand.  Board startup never replays all Board
records and never performs one routing query per historical message.

** Task scheduling is claim-based

The task scheduler queries runnable work and atomically claims it.  Runnable
rows are detached query/claim input; Emacs retains only executing task state
and live execution handles.  Terminal history remains in SQLite and is fetched
through bounded inspection pages.  A queue startup must not reconstruct a
whole task snapshot.

** Interactive storage never waits

Every path reachable from startup, UI, timer, tool, capability action,
resource method, provider callback, turn orchestration, or shutdown enqueues
bounded work and returns.  It must not call =e-runtime-store-call= or await via
=e-runtime-store-await=, use =accept-process-output=, flush, wait for
open/commit/retry/recovery/close, or turn a storage operation into a
synchronous stack call.  Named batch, operator, offline-migration, and
focused-test APIs are the only blocking boundaries, and their names and callers
must make that authority explicit.

** Session deltas and offline upgrade

The session domain owns exhaustive record-to-query-state derivation.  The
SQLite adapter validates and maps the bounded delta; the worker atomically
commits journal record, query row changes, deletion control, and receipt.
Receipt replay returns its small recorded result and does not apply a delta a
second time.  No catalog/checkpoint publication is part of ordinary v6 runtime
operation.

The explicit stopped-store v5-to-v6 migration is operator-only.  It creates a
verified backup, derives query rows solely from canonical v5 journal records,
uses legacy catalog/checkpoint values only as omission/conflict witnesses,
preserves journal identity/position/payload digests, and rolls back to the
verified backup on faults.  It is the one compatibility boundary; ordinary v6
startup does not become a dual v5/v6 runtime.

** Failure partitions remain distinct

An unavailable transport or upgrade is reported by the transport readiness and
status channel.  A failed exact/page read is request-local and retryable.  A
decodable but semantically invalid requested session row or association enters
only the retained =F92-C09= session quarantine; a Board warning is presentation
feedback, not Board quarantine.  An already-published optimistic write failure
records only its owner's first bounded suspect diagnostic and fences that owner.
Unrelated sessions, Boards, tasks, and request work remain eligible for service.

* Target ownership and modularization

** Architecture scope decision

- Trigger :: Startup prewarming exposed process-wide durable mirrors and
  synchronous interactive restoration.
- Contract :: =F92A2-C01=--=F92A2-C10=.
- Durable owner :: SQLite and its worker own durable identity, current state,
  ordering, history, associations, routing, task state, and indexes.
- Process owner :: Emacs owns presentation, subscribers/callbacks, timers,
  executing work, bounded in-flight mutation, detached results, and viewport.
- Desired direction :: Transport-only startup, query-shaped async access, and
  explicit bounded working values.  There is no active durable session cache.
- Decision :: Correct through the ordered packages below.  Do not add a
  candidate store, generation loader, replay cache, background mirror, or
  renamed catalog/checkpoint projection.

* Delivery packages

** F92A2-DP1: Transport-only startup (Accepted)

DP1 establishes =F92A2-C01= and =F92A2-C02=.  The process-wide runtime
transport starts/reuses one external worker and private open control.  Default
composition supplies the final directory and bounded ports without domain
SQL, identity enumeration, row creation, or readiness wait.  Its accepted
graphical evidence is recorded in the implementation ledger above.

** F92A2-DP2: SQLite session queries, deltas, and offline upgrade (In-progress)

DP2 establishes =F92A2-C03=--=F92A2-C05= and =F92A2-C09=.  Its fixed internal
order is:

1. derive bounded query state in the session domain;
2. expose exact/page reads and transactional v6 row/record operations in the
   worker and storage adapter;
3. verify the stopped-store v5-to-v6 upgrade from canonical journals with
   backup, witnesses, parity, rollback, and reopen; and
4. cut the public session, Daily, provider-context, and history consumers over
   to those bounded async operations, then remove the old catalog/checkpoint
   and synchronous interactive paths.

The package does not create a candidate store, replay a whole or active session,
install a generation loader, maintain an active durable replica, or add a
release cache.  Daily open returns its buffer first, then requests exact
metadata, association, visible recent messages, and selected context pages.
The package is not accepted until public consumers and obsolete paths satisfy
that boundary.

Gate: a disposable v6 fixture with at least the operator-observed 1,277-session
shape starts with zero session queries; opening one Daily reads only its exact
rows and visible page; history uses stable bounded pages; session commands
append transactional deltas; and the installed store has no obsolete catalog or
checkpoint relations.  The disposable v5 upgrade proves journal parity,
witness-only legacy validation, affected-session diagnostics, fault rollback,
and production-v6 reopen.  No test may accept process-wide mirror allocation.

** F92A2-DP3: Bounded Board controller (not-started)

DP3 establishes =F92A2-C06=.  Construct and initialize a lightweight Board
controller from exact current Board/participant/pickup rows, a set-based routing
query, and the bounded visible working-message window needed by current
subscribers.  Retain
callbacks, subscriptions, timers, and executing actions only.  Page older
history on explicit navigation.  No Board-history replay and no N+1 routing
query is permitted.

Gate: increasing unrelated Board history by an order of magnitude does not
increase retained Emacs controller state beyond the declared visible window.
Query-count, identity, visible-window, and subscriber-teardown tests pass.

** F92A2-DP4: Query-and-claim task scheduler (not-started)

DP4 establishes =F92A2-C07=.  Query runnable work as detached claim input and
atomically claim it; retain executing task state and live handles only.  Terminal
history stays in SQLite and is fetched through bounded pages by its inspection
consumer.  Do not rebuild a task snapshot or copy unrelated terminal rows into
the scheduler.

Gate: increasing terminal history by an order of magnitude does not increase
retained scheduler state beyond queue identity and executing task handles.

** F92A2-DP5: All interactive paths and public acceptance (not-started)

DP5 establishes =F92A2-C08= and =F92A2-C10= after DP1--DP4.  Classify every
interactive storage caller, convert remaining Board/task/cron/voice/Goodnite/
raw-result/session/provider paths to bounded async owner operations, and keep
explicit blocking only in named batch/operator/offline/test boundaries.

Gate: no default interactive call graph reaches =e-runtime-store-call=,
=e-runtime-store-await=, =accept-process-output=, flush, or
open/commit/retry/recovery/close wait.  Held open/read/write leaves graphical
input, redisplay, three heartbeats, and a composer edit live.  Read failure,
invalid requested state, and post-publication write failure produce exactly the
distinct owner-local partitions above, while a healthy sibling continues
enqueuing, persisting, querying, and rendering.

* Public scenario portfolio

** S92A2-STARTUP

Use a disposable nonempty v6 store and an honest v5 fixture.  Arrange the
fixture, held worker open, runtime directory, and reporting channel before the
isolated graphical daemon loads =e=.  Assert startup completion with only the
private open request, at least three independently scheduled heartbeats, and a
composer edit.  Release open and observe readiness/status.  For v5, the
explicit-upgrade diagnostic settles asynchronously after release; no domain
query is issued before first owner use.

** S92A2-EXISTING-DAILY

Open one existing Daily against a nonempty disposable v6 store.  Assert the
buffer returns immediately while exact metadata, exact Board association, and
the visible recent-message window are held.  Type into the composer and let at
least three independent timer callbacks run.  Assert only the requested
session/association rows are read, no whole session or Board history is copied,
and each visible message is rendered once.  Open a new Daily in the same
fixture and assert its buffer also returns immediately.  A provider turn
requests only the selected branch/compaction path.

** S92A2-HISTORY-PAGE

Against at least 1,277 sessions, fetch one bounded newest-first page and render
it.  Fetch the next page only after explicit navigation.  Assert stable cursor
ordering, bounded rows/bytes, no identity enumeration in Emacs, and no session
object allocation for unrelated rows.

** S92A2-BOARD-SCALE

Construct and initialize one lightweight Board controller with a small current
participant/pickup set, visible working window, and large unrelated
history/routing set.  Assert exact/set query classes, no history replay, no
per-message routing query, bounded retained controller state, and on-demand
history pages.

** S92A2-TASK-SCALE

Start a queue with a small runnable/executing set and large terminal history.
Assert query-and-claim returns detached runnable input, executing state and live
handles remain live, terminal rows stay in SQLite, and inspection obtains
bounded pages.

** S92A2-READ-FAILURE

Hold or fail one Daily exact/page request after another Daily has enqueued work.
The failed request is visibly retryable and creates neither suspect nor
quarantine state.  The other Daily remains editable and another session can
enqueue, persist, query, and render successfully while the first request is
failed.

** S92A2-INVALID-STATE

Return a decodable but semantically invalid requested session row or Board
association.  Only that session enters =F92-C09= quarantine; the associated
Board may display a warning but owns no quarantine.  An unrelated session and a
standalone Board read continue.  A later canonical retry can clear the session
warning without global reload or catalog rejection.

** S92A2-WRITE-FAILURE

Fail persistence after an optimistic mutation is publicly visible.  Only that
owner receives its first bounded suspect diagnostic and fencing; another Daily
continues to enqueue, persist, and read back.  Worker restart does not trigger
global mirror reconstruction.

** S92A2-V5-UPGRADE

Run dry-run/install against a disposable v5 database containing nonempty
journals and legacy catalog/checkpoint witnesses.  Derive current rows only
from canonical journal records, verify identity/position/payload digests and
affected-session diagnostics, prove backup restoration for faults before and
after schema installation, reopen under production v6, and assert obsolete
relations are absent.

| Cooperative whole-session replay tests | Delete/replace | The target has no active replay, candidate store, generation loader, or release cache. |
| Board complete-history replay tests | Replace | Test current-row/set restore and bounded visible history pages. |
| Task snapshot restore tests | Replace | Test query-and-claim runnable state and paged terminal history. |
| Runtime FIFO, receipt, latency, and owner-local failure tests | Retain/strengthen | Their transport and failure partitions remain valid under query-delta writes. |
| Remaining synchronous cron/voice/Goodnite/raw-result tests | Retain then adapt | Bounded consumer state remains valid; interactive waits must become async. |

Tests must assert public behavior, requested identities, query classes/counts,
bounded rows/bytes, and absence of unrelated process state.  They must not freeze
private table names, callback representation, or page sizes unless that detail
becomes a correctness contract.

* Performance and observability

Acceptance is based on scale invariance and responsiveness, not a favorable
empty-fixture timing:

- startup domain-query count is exactly zero; only private transport open may
  be pending;
- Daily buffer return does not depend on exact/page query settlement;
- a history request returns at most its declared bounded page and does not copy
  unrelated rows into Emacs;
- durable history growth does not increase retained Emacs state beyond the
  requested page and visible viewport;
- Board controller query count and retained controller state are bounded
  independently of unrelated history and routing cardinality;
- task scheduler work follows runnable/executing cardinality, not terminal
  history; and
- while a test-controlled worker hold remains active, the graphical gate sees
  at least three independent heartbeats and one composer edit before release.

Heartbeat periods, test timeouts, page sizes, and wall-clock latencies are
observational or private harness defaults.  Operator-sized fixtures are always
disposable copies or generated equivalents; tests never open or mutate the
canonical store.

* Compatibility and removal ledger

- v5 compatibility is one explicit stopped-store offline upgrade, not a dual
  runtime path;
- the verified pre-upgrade backup is the rollback boundary;
- legacy JSONL/index/checkpoint inputs remain migration-source formats and
  witness values only;
- runtime catalog/checkpoint relations and any renamed opaque equivalent are
  removed from v6;
- synchronous interactive list/restore APIs are replaced by bounded async
  exact/page operations; explicit batch/operator callers may retain blocking
  observers with visible names;
- global session catalog enumeration, unloaded session stubs, whole-session
  replay, candidate stores, generation loaders, active durable replicas, and
  release caches are removed from ordinary application paths;
- Board complete-history replay and per-message routing are replaced by exact
  current/set queries and visible-window pages;
- task snapshot restoration is replaced by query-and-claim runnable state and
  terminal history pages; and
- old current-code callers that still contain these paths are tracked as
  deletion work in DP2--DP5, not as compatibility behavior.

* Explicit non-goals

- replacing SQLite or the external worker;
- moving SQL into the main Emacs process;
- adding a second worker, generic cache, ORM, repository, event bus, or CQRS
  framework;
- keeping catalog/checkpoint blobs under another name;
- whole or active session replay, private candidate stores, generation loaders,
  active durable replicas, or release caches;
- Board history replay or task snapshot restoration;
- retaining durable state in Emacs beyond presentation/subscribers/callbacks,
  timers, executing work, bounded in-flight optimistic mutations, detached
  request results, and visible viewport data;
- blocking interactive call/await, =accept-process-output=, flush, open,
  commit, retry, recovery, or close waits; and
- automatic migration/vacuum of the canonical live store or unrelated Feature
  92 recovery/fork hardening.

* Verification and acceptance

Focused validation proceeds in package order against disposable fixtures and
isolated graphical daemons.  The exact final revision must satisfy:

1. =S92A2-STARTUP= passes with held open, zero domain traffic, three
   independently scheduled heartbeats, and one composer edit; the v5 variant
   reports its diagnostic asynchronously.
2. Existing Daily returns its buffer immediately, then reads exact metadata,
   exact Board association, visible recent messages, and selected provider
   branch/compaction context without whole-session/Board state.
3. History obtains bounded stable-cursor pages only on explicit navigation and
   does not allocate unrelated session objects.
4. Board controller construction/initialization uses exact current/set queries
   and a bounded visible window, with no history replay or routing N+1.
5. Task scheduling query-and-claims detached runnable input, retains executing
   work/live handles only, and pages terminal history separately.
6. Request-local read failure, session-local invalid-state quarantine with Board
   warning only, and owner-local optimistic-write suspect fencing remain
   distinct while unrelated owners continue.
7. Static reachability finds no default interactive =e-runtime-store-call= or
   =e-runtime-store-await=, =accept-process-output=, flush,
   open/commit/retry/recovery/close wait; only named batch/operator/offline/test
   paths block.
8. v5-to-v6 upgrade passes journal parity, bounded derivation, witness/conflict,
   backup, install, reopen, fault rollback, affected-session diagnostics, and
   obsolete-relation removal checks.
9. The complete repository and graphical suites pass on the reviewed revision.

Do not claim Feature 92 completion or mark this addendum Done until the public
graphical scenarios pass against nonempty data on the exact reviewed revision.

* Term audit and residual vocabulary

The target language is intentionally RDBMS-first.  A source term from the old
architecture may remain only in one of these justified categories:

| Term | Allowed residual meaning | Required action |
|------+--------------------------+-----------------|
| restore / hydrate | A legacy/current code path identified for deletion, or an explicit offline/operator source operation. | Remove from ordinary Daily, Board, and task paths; retain only named migration or bounded current-row wording. |
| load all / whole-store | Diagnosis of the defect or a negative test description. | Delete the runtime path and reject whole-store materialization. |
| snapshot | Legacy task/checkpoint input or a negative test name. | Remove snapshot restoration from runtime; use current rows and pages. |
| rebuild / reconcile | Offline witness/verification wording or a legacy startup path to delete. | Never run as ordinary startup or Daily access. |
| catalog / stub | Legacy v5 witness or current runtime code awaiting removal. | Remove v6 publication/enumeration and unloaded stubs; SQLite pages are the authority. |
| active aggregate | Existing current code terminology or a bounded executing/presentation value being retired/renamed. | Do not use it to mean a durable replica, candidate, generation loader, or release cache. |
| replay | Canonical journal derivation during offline migration, or a negative test guarding against interactive whole-history replay. | Do not use replay to open Daily, restore Board, or start the task scheduler. |

The audit command for implementation review is:

#+begin_example
rg -n -i 'restore|hydrate|load[- ]all|snapshot|rebuild|reconcile|catalog|stub|active aggregate|replay' \
  lisp e2e test
#+end_example

Each remaining hit must be classified as offline/legacy migration, a negative
test, or current code to delete in DP2--DP5.  No hit may be accepted as an
ordinary interactive durable mirror or blocking composition path.

* Architecture self-check

1. *Useful stopping point and direction*: DP1 already makes startup safe.  DP2
   moves session identity/current state/order/history queries and mutation
   deltas into SQLite and makes offline compatibility explicit.  DP3 bounds
   Board control, DP4 bounds task scheduling, and DP5 closes remaining
   interactive waits.  Each package reduces process-wide durable state.
2. *Stable and uncertain decisions*: SQLite authority, bounded consumer queries,
   transport-only startup, and nonblocking interactive access are stable.  SQL
   indexes, page sizes, and private presentation-window limits remain local and
   revisable.
3. *Ownership*: transport owns worker lifecycle; SQLite adapters own physical
   queries/transactions; session, Board, and task services own bounded
   consumer state; presentation owns buffers and callbacks.  No service owns a
   cross-domain durable mirror.
4. *State and lifetime*: durable state stays in SQLite.  Emacs state is limited
   to presentation, subscriptions/callbacks, timers, executing work, bounded
   in-flight mutation, detached results, and visible viewport, each with a
   request/presentation/execution owner.
5. *Dependencies and side effects*: application services depend on narrow
   storage ports; SQL stays in adapters; transport does not interpret domain
   records; presentation consumes async results.
6. *Interfaces*: exact row, bounded page, query-and-claim, and transactional
   delta operations are consumer-shaped.  No speculative cache/repository layer
   is introduced.
7. *Compatibility/removal*: v5 is offline-only.  Runtime catalogs/checkpoints,
   whole session/Board replay, task snapshots, active durable replicas, and
   synchronous interactive waits are deletion targets, not compatibility paths.
8. *Errors*: transport readiness, request failure, invalid-state quarantine,
   and optimistic-write suspect fencing remain separate.  Unexpected errors
   surface at their owning boundary.
9. *Performance*: acceptance measures zero startup domain traffic, requested
   identity isolation, bounded result rows/bytes, scale-invariant Board/task
   retained state, and graphical heartbeat progress.
10. *Tests*: public graphical scenarios, exact query-count/identity checks,
    transaction/replay/migration evidence, and static reachability prove the
    architecture without freezing private callback or index details.
