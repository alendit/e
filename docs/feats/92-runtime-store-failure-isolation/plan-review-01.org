* Review corrections

** Resolved High: offline upgrade omitted from ownership scope

The first plan assigned the claim only to the ordinary runtime worker.  Source
inspection showed that the explicit offline upgrade separately checked and
deleted the same owner file before opening SQLite.

=F92-C03= and =F92-DP2= now assign one private runtime-directory claim to both
workers.  Both must acquire it before opening SQLite and release it after
closing.  The ordinary/offline race is part of =S92-OWNERSHIP=.

** Resolved High: snapshot plus rename was not conditional ownership

The first stale-recovery proposal could move a replacement pathname after
observing an older inode.  Atomic rename alone did not establish compare-and-
move semantics.

The accepted plan instead uses Emacs's cross-process file-lock primitive for
atomic acquisition, live-holder exclusion, and dead-PID/prior-boot recovery.
Bounded diagnostic metadata is subordinate to that lock and never authorizes
stealing it.

** Resolved High: same-boot PID reuse exceeded file-lock identity

Disposable batch probes confirmed that Emacs lock identity contains
host/PID/boot but not process-start identity.  A live unrelated process reusing
the PID on the same boot cannot be distinguished safely enough to steal the
lock.

The contract was constructively rebaselined: that case now fails safely with a
typed identity-conflict diagnostic and leaves the lock untouched.  Automatic
recovery occurs only after the PID is dead or through explicit offline operator
recovery after proving no worker is live.  This preserves the primary
single-owner safety outcome without claiming an unavailable primitive.

** Resolved Medium: byte domains and overflow settlement were ambiguous

The first plan compared raw content, canonical codec, base64 wire, and SQLite
TEXT measurements as though they were interchangeable.  It also omitted the
read/write distinction when a worker result cannot fit a response.

=F92-DP3= now names each byte domain, preflights complete request frames, gives
oversized reads a small correlated error, and preserves fail-closed ambiguity
when a committed write acknowledgement cannot be encoded.  The canonical
ceiling is 68 MiB and its exact derived wire ceiling is 95,070,893 bytes.

** Resolved Medium: allocation estimate was too small

The first 256 MiB claim was below the lower-bound sum of the listed live
allocations.  The final private envelope is 512 MiB.  The modeled original
input, codec copy, canonical frame, and three wire-sized allocations total
390,070,279 bytes, leaving 146,800,633 bytes of headroom before the envelope.
A disposable peak-allocation probe must validate the implementation.

** Resolved Medium: protocol recovery evidence stopped at failure

=S92-PROTOCOL= now proves that the first cause survives later submissions and
that explicit close/reopen plus canonical reload restores usability without
automatically resubmitting ambiguous work.
