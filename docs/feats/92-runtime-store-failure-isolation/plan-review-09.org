* Findings

** F92A3-PR09-01 [P1] Daily lifecycle storage is not concrete enough to implement

Contracts C05--C07 name SQL Board/domain facts, but the plan does not select the
existing persistence seam, define the record shape, identify the bounded query,
or state the transition/reduction rules.  An implementer could teach the generic
orchestration reducer Daily semantics, add a new mirror, or continue treating
Org metadata as authority while still claiming the prose.  Select plain Board
fact records through =e-board-sqlite-publication-target-fact-start=, query them
through a run-id-tagged bounded =record-page-start= selector, and define a pure
Grimoire-owned reducer plus its legal transitions and payload bounds.

** F92A3-PR09-02 [P1] Report admission lacks an executable ownership seam

C04 correctly assigns artifact policy to Daily but does not explain how the
generic child-side =subagents/:report= call reaches that policy before
=:reported= is set.  Specify a spawn-time, process-local report-admission
function retained only with the executing child record.  The generic subagent
runner invokes it before accepting a report; Daily supplies the validator.
Invalid output returns to the child as an action error and does not settle or
publish terminal success.

** F92A3-PR09-03 [P2] The error-loop guard needs an exact, narrow rule

"Identical invalid attempts" is underspecified.  Limit the rule to consecutive
model-facing tool failures with the same tool name and normalized error.  The
first failure remains ordinary tool feedback.  The second consecutive identical
failure terminates the turn with one bounded diagnostic.  A successful tool or
a different failure resets the counter.  This is turn-local coordination, not a
durable retry subsystem.

** F92A3-PR09-04 [P1] Materialization acknowledgement ordering is missing

C06 does not say when an apply can be acknowledged.  The Daily apply action must
be asynchronous: validate and save the generated sections first, enqueue the
immutable =applied= lifecycle fact carrying the exact section revision/value,
and settle only after that fact commits.  A crash before the fact leaves a
replayable idempotent materialization; a crash after the fact leaves SQLite with
the exact expected value for comparison.  Reconciliation must await apply
before invoking finalize.

* Fixed-point criterion

Address the four findings above and bind each scenario to named tests.  No
additional architecture review is required before implementation after those
changes; the package then has no acceptance-critical unknown.
