* Decision

Keep the external SQLite worker, its ordinary transactions, the existing
append-only session journal, and the runtime store's single bounded client FIFO.
Do not add a second SQLite event table, polling loop, durable subscriber cursor,
or application queue.

After a session command passes bounded preparation and the runtime FIFO accepts
its immutable SQLite operation, the session application service publishes that
command into the process-local session projection before returning.  Provider
context, presentation, and later session commands read that projection.  SQLite
acknowledgement changes persistence status; it does not first make the semantic
change visible.

In this addendum:

- an *accepted session mutation* is a validated immutable session command whose
  physical operation has entered the runtime store's bounded FIFO;
- the *effective session projection* is the live session aggregate produced by
  committed SQLite records plus accepted mutations in admission order; and
- *committed* means that SQLite acknowledged the journal transaction.

These are session-service lifecycle distinctions, not model-facing concepts or
a generic event framework.

* Reason for the addendum

The corrected graphical witness proved fresh Daily open, one turn,
responsiveness during a worker stall, release, owner-local failure, and unrelated
recovery.  Its backend response did not depend on the provider request's actual
messages.  A live second turn supplied a new counterexample: the second user
message had entered asynchronous persistence, but provider context still came
from the post-acknowledgement aggregate.  The backend received stale history and
answered the previous prompt.

#+begin_example
session append accepted by asynchronous application code
  -> durable operation waits for SQLite acknowledgement
  -> session aggregate still contains only acknowledged records
  -> harness context reads that aggregate
  -> provider request omits the new user message
#+end_example

A harness-local accepted-message list can hide this defect for one active turn,
but it creates a second session-history authority.  It does not naturally cover
the next turn, tool calls and results, context refresh, Board/session operations,
compaction, or another session consumer.  The correction belongs at the session
application boundary.

* Design

** One event path, two observable phases

#+begin_example
caller
  -> aggregate prepares immutable record + semantic result + install token
  -> session storage adapter submits the record to the runtime FIFO
  -> successful FIFO admission
  -> session service installs the prevalidated effective projection token
  -> session service emits the semantic event and returns

later, SQLite COMMIT acknowledgement
  -> session service retires pending status only

or, terminal persistence failure
  -> runtime fences the opaque owner key
  -> session service retains first bounded suspect status
  -> already-visible semantic state remains visibly suspect
#+end_example

Install the effective projection only after FIFO admission succeeds.  Before
enqueue, the aggregate must validate the bounded record and prepare a no-fail
install token containing every preallocated reference and rollback value needed
for one command.  It must not stage or copy the whole session.  Submission and
installation then complete in the same non-yielding Emacs turn: the runtime
schedules worker progress for a later timer turn, so the exact request is still
queued while installation runs.

The normal post-admission operation is only the authoritative token install; it
must not decode, validate, allocate a variable-size graph, call a subscriber, or
yield.  If an unexpected error occurs before the token's installation point,
the session service synchronously cancels that exact runtime request.  A
runtime =dropped= result proves that neither semantic nor durable state changed
and the facade returns a failed work handle.  Any result other than =dropped=
is an invariant breach: retain the first bounded suspect diagnostic for that
owner and surface the error because the request can no longer be proven
unsubmitted.  If a fault occurs after the installation point, the projection is
already authoritative and remains visible; the owner becomes suspect, and the
queued write is allowed to settle.  Fault injection immediately before and
after the installation point must prove that there is no partially installed
projection and no committed mutation hidden behind a successful facade result.

SQLite remains authoritative across process lifetime.  The effective projection
is rebuildable: restart or canonical reload replays committed journal rows and
discards process-local pending state.  Process exit may lose accepted but
uncommitted mutations; pending/suspect UI makes that durability boundary
explicit.  Interactive shutdown does not wait to eliminate the window.

** SQLite responsibilities

Use SQLite for the guarantees it already provides:

- the session-record journal is the append-only durable event log;
- SQLite owns unique row positions and typed append transactions; semantic
  record identities and parent links remain session-domain values validated on
  replay;
- ordinary transaction commit is the durability boundary;
- acknowledged records replay into the session after restart; and
- rebuildable catalog/checkpoint projections may lag the primary journal.

Do not serialize an ahead-of-commit effective aggregate into a durable catalog
or checkpoint.  A derived durable projection must be updated inside the worker
transaction from committed data or rebuilt later from committed journal rows.
It cannot become a second authority for pending state.

A transactional outbox is deliberately absent.  That pattern serves publication
that must occur after commit and durable delivery to another process.  This
contract intentionally publishes process-local semantic state before commit,
and its subscribers live in the same Emacs process.  A future external durable
subscriber would require a separate product decision.

** Projection and settlement state

The aggregate remains the one live semantic projection.  It represents accepted
session history, not a second copy of SQLite commit state.  The session service
retains only settlement metadata needed to expose =pending= or =suspect= and
correlate terminal work.  It retains neither a second transcript nor an encoded
frame: the aggregate owns live semantics and the runtime request owns the frame.

Pending metadata is bounded one-for-one by admitted runtime requests, whose
existing global capacity is 128.  No second cap or exact object-graph accounting
is required.  Successful settlement removes the exact pending entry.  Failure
atomically converts it to at most one first-cause suspect entry per session;
later failures do not add entries or replace the first diagnostic.  Store
close/reset and process restart release all process-local pending and suspect
entries.  The runtime owner fence rejects further same-owner durable mutation.
Clearing one owner by canonical reload remains deferred to DP6C under Feature
92's validation roadmap; this package does not pretend that reload path exists.

** Publication and subscribers

The session service emits semantic publication after installing the accepted
projection.  Harness/Board subscription surfaces may forward or render it, but
do not store authoritative session history.  A persistence-settled notification,
when a readiness or warning consumer needs one, is a separate status event and
cannot cause a second message, activity, or Board publication.

Delete the session terminal-token queue and timer.  Runtime observer delivery is
the sole bounded carrier.  Its session callback first performs one non-yielding
authoritative transition: remove the exact pending entry and, on failure,
retain the first bounded suspect status.  It then clears private operation links
and settles =e-work=.  Work callbacks and semantic/status subscribers therefore
run only after authoritative state and are non-gating.  An =error= or =quit=
from them cannot restore pending state, lose suspect state, strand work, or
prevent runtime request/token release.  Close/reset failures use the same
settlement path before process-local state is released.

Provider context consumes the effective projection through a consumer-shaped
session read.  It does not inspect runtime requests, worker state, pending
records, or an active-turn message cache.  Tool-loop refresh and a new turn use
the same session-owned path.

Establish =F92A-C01=--=F92A-C05=.  Simplify the session async boundary so one
prepared record and its aggregate install token enter the runtime FIFO directly.
After admission, install and publish the semantic projection before returning.
Track only bounded settlement metadata.  Acknowledgement retires pending status
without republishing; failure records session suspect state while the runtime
isolates the opaque owner.  Delete the session terminal outbox and settle from
the runtime observer only after authoritative pending/suspect state changes.

Remove the harness overlay and default-path lane/publication/reconciliation
machinery.  Move session suspect state out of the storage port.  Keep SQLite
transactions and receipt behavior private to the adapter, and the aggregate
transport-free.

Useful stopping point: every session consumer has coherent read-your-writes
semantics while SQLite remains the durable log.

Evidence proves admission rejection without publication, accepted visibility
before acknowledgement, ordered dependent mutations, acknowledgement without
duplication, install fault rollback, terminal observer isolation, owner failure,
sibling persistence, close/reset lifetime, and canonical reopen.

* Compatibility and migration

No SQLite schema upgrade is required.  Existing journal records, identities,
transactions, runtime ownership, and offline upgrade path remain valid.  Reopen
continues to expose only committed rows.

Feature 87's commit-first statement is narrowed: durable and restart-visible
state still changes only after commit; the live effective projection changes
after bounded enqueue.  Code genuinely requiring committed observation must use
an explicit batch/operator/storage boundary and cannot be reachable from
interactive context composition.

This core session lifecycle change requires a full Emacs restart.  Repository
validation must not reload or mutate the user's Emacs or canonical SQLite store.

* Performance and bounds

The correctness gate is causal, not a latency benchmark: the public call returns
and a heartbeat advances while the worker remains blocked.  Return duration is
observational; test timeouts only terminate broken runs and are not product
limits.

Pending metadata is bounded by the existing 128 admitted runtime clients.
Existing session record and frame limits remain.  Projection installation costs
one accepted command and its preallocated install token, not durable session
length.  Suspect metadata is bounded to one first-cause entry per affected
session and is released with the store.  No second transcript, polling scan,
database integrity check, or SQLite read belongs on the interactive path.

* Minimal runtime latency observability extension

** Behavioral trace

- Goal ID :: =F92-RUNTIME-LATENCY=
- Behavioral goal :: An operator inspecting a live runtime can distinguish time
  spent waiting in the bounded FIFO from time spent after worker dispatch and
  can inspect recent terminal latency without issuing another SQLite request.
- Direct scenario :: Hold one runtime operation in the external worker, inspect
  status while it is active and another operation is queued, release it, then
  inspect one terminal sample containing FIFO wait, dispatch-to-settlement, and
  end-to-end duration for the operation.
- Product authority :: The operator's 2026-09-05 request for minimal SQLite
  operation-latency observability.
- Owning contract :: Runtime-store status is nonblocking, process-local, and
  bounded; it reports transport-observed latency without claiming to isolate
  SQLite statement execution from worker or protocol overhead.
- Behavioral status :: Passing in deterministic runtime-store evidence.
- Mechanism status :: Complete.  No worker protocol or SQLite schema changed.

** Status contract

=e-runtime-store-status= and the existing owner/composition status facades now
include =:latencies=.  Its =:active= and =:oldest-queued= entries report the
operation, request kind, phase, phase age, and total age in milliseconds.
=:recent= retains newest-first terminal scalar samples with:

- =:queue-ms=: admission to first dispatch, or admission to terminal failure
  when the request never dispatches;
- =:dispatch-to-settlement-ms=: first dispatch to terminal settlement,
  including worker replacement/recovery when it occurs; and
- =:total-ms=: admission to terminal settlement.

The runtime retains at most 64 recent samples.  This is a private practical
default, not a correctness limit or performance gate.  Samples contain only
operation, kind, outcome, timestamps, and durations: no owner identity, request
payload, result, or diagnostic.  They disappear with the process-local runtime.
Collection performs no SQLite query, filesystem write, subscriber call, or
application-domain publication.  Actual SQLite statement-only timing remains a
separate possible worker diagnostic; the current value intentionally measures
the user-relevant parent-side interval through acknowledgement.

* Architecture self-check

1. DP1 is useful alone because all session consumers gain coherent
   read-your-writes; DP2 proves the reported UI.
2. It advances toward SQLite as sole durable event authority with thin,
   nonblocking application services.
3. Durability, session semantic ownership, and FIFO ownership are stable.  The
   prevalidated install-token representation remains private and reversible.
4. Session service owns accepted visibility/status; runtime owns transport and
   fencing; SQLite owns cross-restart state; harness/shells consume.
5. Deleting the harness overlay and session scheduler reduces coupling.
6. Dependencies point from shells/harness through session and adapters to the
   worker; policy does not depend on SQLite/provider detail.
7. I/O, transactions, receipt recovery, and frames remain adapter/runtime side
   effects.
8. New state is bounded process-local settlement metadata: one entry per pending
   request and at most one suspect entry per session, released on close/restart.
9. Interactive work is proportional to one command; timing is observational.
10. No new public abstraction is needed; the private async module represents a
    real lifecycle.
11. Existing SQLite records and public callers remain compatible.
12. Lane scheduling, publication outbox, reconciliation, exact pathological
    accounting, and harness history overlay become removable.
13. Admission rejection occurs before publication; a before-install fault drops
    the exact queued request; a post-install or terminal failure becomes
    owner-local suspect state; unexpected reducer/adapter errors remain visible.
14. Owner tests prove lifecycle partitions, harness integration proves the
