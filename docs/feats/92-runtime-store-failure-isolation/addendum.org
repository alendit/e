* Decision

Keep the external SQLite worker, its ordinary transactions, the existing
append-only session journal, and the runtime store's single bounded client FIFO.
Do not add a second SQLite event table, polling loop, durable subscriber cursor,
or application queue.

After a session command passes bounded preparation and the runtime FIFO accepts
its immutable SQLite operation, the session application service publishes that
command into the process-local session projection before returning.  Provider
context, presentation, and later session commands read that projection.  SQLite
acknowledgement changes persistence status; it does not first make the semantic
change visible.

In this addendum:

- an *accepted session mutation* is a validated immutable session command whose
  physical operation has entered the runtime store's bounded FIFO;
- the *effective session projection* is the live session aggregate produced by
  committed SQLite records plus accepted mutations in admission order; and
- *committed* means that SQLite acknowledged the journal transaction.

These are session-service lifecycle distinctions, not model-facing concepts or
a generic event framework.

* Reason for the addendum

The corrected graphical witness proved fresh Daily open, one turn,
responsiveness during a worker stall, release, owner-local failure, and unrelated
recovery.  Its backend response did not depend on the provider request's actual
messages.  A live second turn supplied a new counterexample: the second user
message had entered asynchronous persistence, but provider context still came
from the post-acknowledgement aggregate.  The backend received stale history and
answered the previous prompt.

#+begin_example
session append accepted by asynchronous application code
  -> durable operation waits for SQLite acknowledgement
  -> session aggregate still contains only acknowledged records
  -> harness context reads that aggregate
  -> provider request omits the new user message
#+end_example

A harness-local accepted-message list can hide this defect for one active turn,
but it creates a second session-history authority.  It does not naturally cover
the next turn, tool calls and results, context refresh, Board/session operations,
compaction, or another session consumer.  The correction belongs at the session
application boundary.

* Design

** One event path, two observable phases

#+begin_example
caller
  -> session service prepares immutable record + semantic result
  -> session storage adapter submits the record to the runtime FIFO
  -> successful FIFO admission
  -> session service installs the prepared effective projection
  -> session service emits the semantic event and returns

later, SQLite COMMIT acknowledgement
  -> session service retires pending status only

or, terminal persistence failure
  -> runtime fences the opaque owner key
  -> session service retains first bounded suspect status
  -> already-visible semantic state remains visibly suspect
#+end_example

Install the effective projection only after FIFO admission succeeds.
Preparation may use a detached aggregate stage so validation and record creation
cannot partially mutate live state.  Installation and semantic notification
complete in the same non-yielding Emacs turn before the facade returns.

SQLite remains authoritative across process lifetime.  The effective projection
is rebuildable: restart or canonical reload replays committed journal rows and
discards process-local pending state.  Process exit may lose accepted but
uncommitted mutations; pending/suspect UI makes that durability boundary
explicit.  Interactive shutdown does not wait to eliminate the window.

** SQLite responsibilities

Use SQLite for the guarantees it already provides:

- the session-record journal is the append-only durable event log;
- SQLite owns unique row positions and typed append transactions; semantic
  record identities and parent links remain session-domain values validated on
  replay;
- ordinary transaction commit is the durability boundary;
- acknowledged records replay into the session after restart; and
- rebuildable catalog/checkpoint projections may lag the primary journal.

Do not serialize an ahead-of-commit effective aggregate into a durable catalog
or checkpoint.  A derived durable projection must be updated inside the worker
transaction from committed data or rebuilt later from committed journal rows.
It cannot become a second authority for pending state.

A transactional outbox is deliberately absent.  That pattern serves publication
that must occur after commit and durable delivery to another process.  This
contract intentionally publishes process-local semantic state before commit,
and its subscribers live in the same Emacs process.  A future external durable
subscriber would require a separate product decision.

** Projection and settlement state

The aggregate remains the one live semantic projection.  It represents accepted
session history, not a second copy of SQLite commit state.  The session service
retains only settlement metadata needed to expose =pending= or =suspect= and
correlate terminal work.  It retains neither a second transcript nor an encoded
frame: the aggregate owns live semantics and the runtime request owns the frame.

Pending metadata is bounded one-for-one by admitted runtime requests, whose
existing global capacity is 128.  No second cap or exact object-graph accounting
is required.  Successful settlement removes its pending entry.  Failure removes
terminal pending ownership, preserves the first bounded diagnostic, and relies
on the runtime's owner fence to reject further same-owner durable mutation until
canonical reload clears it under Feature 92's validation roadmap.

** Publication and subscribers

The session service emits semantic publication after installing the accepted
projection.  Harness/Board subscription surfaces may forward or render it, but
do not store authoritative session history.  A persistence-settled notification,
when a readiness or warning consumer needs one, is a separate status event and
cannot cause a second message, activity, or Board publication.

Provider context consumes the effective projection through a consumer-shaped
session read.  It does not inspect runtime requests, worker state, pending
records, or an active-turn message cache.  Tool-loop refresh and a new turn use
the same session-owned path.

* Delivery packages

** F92A-DP1: Session-owned accepted projection

Establish =F92A-C01=--=F92A-C05=.  Simplify the session async boundary so one
prepared record enters the runtime FIFO directly.  After admission, install and
publish the semantic projection before returning.  Track only bounded settlement
metadata.  Acknowledgement retires pending status without republishing; failure
records session suspect state while the runtime isolates the opaque owner.

Remove the harness overlay and default-path lane/publication/reconciliation
machinery.  Move session suspect state out of the storage port.  Keep SQLite
transactions and receipt behavior private to the adapter, and the aggregate
transport-free.

Useful stopping point: every session consumer has coherent read-your-writes
semantics while SQLite remains the durable log.

Evidence proves admission rejection without publication, accepted visibility
before acknowledgement, ordered dependent mutations, acknowledgement without
duplication, owner failure, sibling persistence, and canonical reopen.

** F92A-DP2: Public two-turn Daily acceptance

Depends on DP1 and establishes =F92A-C06=.  Strengthen the Org Canvas fixture so
the backend captures and validates actual provider messages.  Complete two
different prompts while session persistence is delayed; derive the second answer
from the second prompt.  Keep tool-loop ordering in the focused DP1 harness
composition instead of expanding the graphical scenario.

Retain composer, heartbeat, same-Board timer, release, exactly-once rendering,
owner-local failure, unrelated persistence, and independent reopen assertions.
Owner partitions remain DP1 evidence rather than being debugged only through the
graphical fixture.

Useful stopping point: one deterministic public gate fails if either blocking or
acknowledgement-gated context returns.

* Scenario portfolio

- S92A-SESSION-ADMISSION :: Hold SQLite after runtime admission.  An append is
  visible before acknowledgement; exact/one-over and exhausted-FIFO rejection
  publish nothing.
- S92A-READ-YOUR-WRITES :: Accept user A, assistant A, and user B without
  acknowledgement.  Session reads and later preparation return A/A/B exactly
  once in order.  Acknowledgement does not change semantic cardinality.
- S92A-TOOL-LOOP :: Accept a tool call and result while SQLite is delayed.  The
  next provider refresh sees the complete sequence through the session API,

- S92A-SETTLEMENT :: Release, drain, reopen independently, and compare journal
  replay with the accepted sequence.  Derived projections never lead the log.
- S92A-OWNER-FAILURE :: Fail one accepted write, retain its first suspect warning

* Compatibility and migration

No SQLite schema upgrade is required.  Existing journal records, identities,
transactions, runtime ownership, and offline upgrade path remain valid.  Reopen
continues to expose only committed rows.

Feature 87's commit-first statement is narrowed: durable and restart-visible
state still changes only after commit; the live effective projection changes
after bounded enqueue.  Code genuinely requiring committed observation must use
an explicit batch/operator/storage boundary and cannot be reachable from
interactive context composition.

This core session lifecycle change requires a full Emacs restart.  Repository
validation must not reload or mutate the user's Emacs or canonical SQLite store.

* Performance and bounds

The correctness gate is causal, not a latency benchmark: the public call returns
and a heartbeat advances while the worker remains blocked.  Return duration is
observational; test timeouts only terminate broken runs and are not product
limits.

Pending metadata is bounded by the existing 128 admitted runtime clients.
Existing session record and frame limits remain.  Projection installation costs
one accepted command, not durable session length.  No second transcript, polling
scan, database integrity check, or SQLite read belongs on the interactive path.

* Explicit non-goals

- a generic SQLite pub-sub or event-bus API;
- a new =event_log= or =outbox= table;
- durable cross-process subscribers, cursors, leases, or acknowledgements;
- DP6C quarantine or DP6D all-domain completion;
- fork, source-cut pins, cross-lane protocols, or application-level ambiguous
  commit handling;
- reworking accepted worker ownership, transaction receipts, or migration; and
- broad aggregate/harness decomposition unrelated to the ownership correction.
