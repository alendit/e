* Decisions

- Approved: the reasoning mark is a static inline fenced block emitted in the model's own reply, parsed deterministically by the stop-hook and stripped before display. Not a tool call, not a session record -- no extra provider round-trip.
- Approved: the stop-hook checks are a completeness test over the parsed block's fields, never a prose-calibration judgment. Accuracy/grounding judgment is out of the default hook and belongs only to the optional subagent-reviewer variant.
- Approved: automatic per-prompt enrichment stays out of scope for this work item.
- Default resolution for the earlier open detail: use one reserved fenced block, output-mode-aware. Under the =org= output mode it is =#+begin_reasoning= ... =#+end_reasoning=; under markdown it is the equivalent fenced form (e.g. a =```reasoning= fence). Slice 2 owns defining both; if a single cross-mode delimiter proves cleaner during implementation, that substitution is allowed without a plan change.
- Approved (dependency correction): the chat shell must NOT know about the bayesian-reasoning capability in order to hide its block. A shell that filters a capability-specific block is a dependency arrow pointing shell -> capability, the wrong direction. Instead the runtime gains a core-owned *structured-block registry*: capabilities register a block kind plus a display disposition, and shells consult that registry generically. Both the shell and the capability depend on the stable core registry contract; neither depends on the other. This is now Slice 2a and is a prerequisite for the strip behavior.
- Approved (generalization now): build the structured-block registry as a real reusable core seam in this work item, not a one-off strip for the reasoning block. Any future capability that emits structured, non-prose blocks in model output (collapsible tool-plans, citations, machine-readable annotations) is a first-class consumer. The initial surface stays deliberately small -- =:kind=, =:matcher=, =:display=, optional =:parser= -- so the generalization adds a seam without speculative surface; new dispositions or fields are added only when a second real consumer needs them.

* Problem

Agents hallucinate and jump to conclusions.
Both are calibration failures: the agent commits to a single answer before the evidence warrants it, and does not revise cleanly when new evidence arrives.
Bayesian reasoning is a discipline aimed exactly at this: treat belief as a quantity that starts somewhere, moves only as much as the evidence warrants, keeps rival explanations alive, and never collapses to certainty without cause.

We want =e= to teach and, where cheap, enforce that discipline as a default part of the runtime rather than leaving it to per-prompt luck.
The hard part is placement, not content.
Guidance dropped at a random point in context, or buried in a long system-prompt passage, competes with everything else and decays into background texture after the first few turns.
The design question is: at what point in the loop does the agent have to act on the discipline, and how do we make that the cheapest path without taxing every turn.

* Goal

Add a default-enabled Bayesian reasoning capability that:

- contributes a compact, always-loaded disposition to standing context (attach a confidence to factual claims, keep at least one rival hypothesis alive, prefer "insufficient evidence" to a guess);
- exposes the full guidance -- the eight tenets, each as general principle plus agent behavior -- as one durable, fetch-on-demand reference resource, so the standing text stays small and there is a single source of truth;
- optionally lets the agent self-mark a turn as making a load-bearing factual claim, so a later enforcement point can filter cheaply;
- provides an optional conditional stop-hook that runs a short calibration checklist on turns that assert something, and sends the turn back with the specific gap named when it fails.

Explicitly out of scope for now: automatic prompt enrichment (the always-on per-prompt "consider Bayesian reasoning" nudge).
The evidence is that a blanket verbalized-confidence nudge is a weak lever on its own and mostly adds tokens, so we are deferring it deliberately, not forgetting it.

* Design

** One content source, three forms

Separate the /content/ (eight tenets + fuller guidance) from the /injection points/.
The tenets are one artifact; each point references it in the shortest form that does its job, and all forms trace back to the one document we maintain.
Do not paste the full eight into standing context, the (deferred) nudge, and the checklist -- that both floods context and drifts out of sync the moment one copy is edited.

- Canonical copy :: a single =read=-able reference resource holding the eight tenets in full. This is the thing we edit; everything else points at it.
- System context :: a two-to-three line distillation plus a pointer to the canonical resource by name. The full eight do not belong in standing context.
- Stop-hook checklist :: the tenets compiled into a few yes/no checks run over the agent's inline reasoning mark (confidence band present, at least one alternative, evidence attached or abstained), not over the reply prose and not the tenets re-injected as reading. See the Slice 3 mechanics subsection for why the checks read the parsed mark rather than the prose.

** Placement in the harness

Two of the three canvas-identified injection points are in scope:

1. System context sets disposition, not compliance. It raises the base rate of good behavior; it cannot enforce turn by turn. Keep it short and imperative and phrased as a rule the agent can be measured against.
2. The stop-hook is the only real enforcement point, and it is worth building only if it stays conditional -- it must not run its checklist on every turn.

The deferred nudge is the third point; we are not building it in this work item.

** Capability shape

Model the capability on =e-goal= (=lisp/layers/harness/e-goal.el=): a default-enabled advanced-harness capability that contributes compact instructions and a durable =refs/= reference resource, packaged by the =harness-advanced= layer and enabled through =e-default-chat-layer-ids=.
Bayesian reasoning is a general agent-runtime concern, not an OS, editor, project, or presentation concern, so =harness-advanced= is the right home and it already loads by default.

The capability contributes:

- =:instructions= :: the compressed disposition (2-3 lines) plus "read =e://bayesian-reasoning/refs/tenets.md= before concluding on a load-bearing claim." Abstention is named here as an allowed and preferred output.
- Reference resource :: =e://bayesian-reasoning/refs/tenets.md=, the eight tenets in full (general principle + agent behavior each), authored once. This is the canonical copy.
- Inline reasoning mark (static, no tool call) :: the disposition instructs the agent, when it asserts a load-bearing factual conclusion, to emit a small fixed-format annotation *inside its own output* -- a fenced block the stop-hook parses deterministically. This is deliberately not a tool call: a tool call forces an extra provider round-trip mid-turn, and we explicitly do not want that. The mark rides the reply the model was already writing. The capability does not itself touch presentation; it registers the block kind and its display disposition (=hidden=) with the core structured-block registry (below), and shells honor that registry.

** Stop-hook enforcement -- and the machinery gap

The strongest lever is a conditional stop-hook, but the current runtime cannot enforce from a turn-finished hook, and that is the main risk in this plan.

What exists today:

- =e-hooks= defines a =:turn-finished= hook point. =e-harness--run-turn-finished-hooks= reduces registered hooks over the finished turn =result= (=lisp/core/e-harness.el=). Capabilities can observe and rewrite the result value.
- =e-harness-queue-prompt= can enqueue a follow-up turn, but it requires an already-running active turn and signals =e-harness-no-active-turn= otherwise. At =:turn-finished= the turn is settling, so a hook cannot use it to send the turn back.

So a turn-finished hook can /inspect/ the assistant message and /flag/ a calibration gap, but there is no supported path for it to /re-prompt/ the agent with the gap. Building genuine enforcement means adding a narrow harness affordance: let a =:turn-finished= hook request one corrective follow-up turn (a hook-return signal the drain path honors, or a dedicated =e-harness-request-follow-up= that is valid during turn settlement). This is a real core change with its own design and test surface; it is called out as its own slice below and should not be smuggled in as a defensive tweak.

The stop-hook, once the affordance exists, is conditional and cheap:

- It fires only when the reply carries an inline reasoning mark, or when a coarse deterministic filter detects a bare assertion (a specific value, name, or date not present in the turn input). The mark is the fast path, not the only path, so an agent that omits it does not defeat the gate.
- On fire it runs the short checklist over the parsed mark, not a full re-derivation.
- Failing the checklist sends the turn back with the specific gap named, not a generic "be more Bayesian."
- The parsed mark doubles as telemetry: log marked turns and checklist outcomes so we can see whether the agent under-marks and whether the hook earns its cost.

** State

The capability is stateless: instructions and the reference resource are static content, and the reasoning mark lives inside the turn output rather than in any store.
The parsed mark and checklist outcomes are telemetry and belong in session activity/telemetry, near the runtime that owns them, not in durable capability state.
No new sidecar and no out-of-band record type is introduced.

** Slice 2a: core structured-block registry (dependency inversion, general seam)

This is a first-class, reusable core seam -- built now as generalization, not a one-off strip for the reasoning block (see Decisions).
The shell must not depend on this capability to hide its block; the correct direction is capabilities register block kinds, shells consult the registry generically, neither knows the other.

- Add =lisp/core/e-structured-blocks.el=: a registry mapping a block kind to a spec -- =:kind= symbol, =:matcher= (how to locate the block in assistant content, e.g. a fence delimiter or regexp), =:display= disposition (=hidden= | =inline= | =collapsed=), and optional =:parser= returning the block's structured fields. Keep the spec at exactly this surface; add fields only when a second real consumer needs them.
- Provide =e-structured-blocks-register=, an unregister/reset path for reload, and a read accessor. Registration flows through the capability contract the same way tools/resources/hooks do (extend =e-capability-create= with a =:structured-blocks= slot and collect it into an active registry alongside the existing hook/resource collection), so an enabled capability's block kinds are discoverable from the active capability set and refresh on layer reload.
- Provide the single core transform =e-structured-blocks-render= (name TBD): given assistant content and the active registry it returns the display-ready text (=hidden= removed, =collapsed= folded, =inline= untouched) plus the extracted structured blocks with their parsed fields. Both the chat shell and modernchat call exactly this; there is one implementation of the transform.
- Shells change once, generically: at render they ask the transform for display text instead of using raw content. A shell with no matching registered kinds gets its content back byte-for-byte, so existing behavior is unchanged until some capability registers a kind.
- Document the seam in the runtime concepts reference (=docs/references/runtime_concepts.org=) next to hooks/resources, since it is now a standing extension point other capabilities will use (collapsible tool-plans, citations, machine-readable annotations are the anticipated consumers -- listed as motivation, not built here).
- Dependency check: chat-shell -> core-registry and bayesian-reasoning -> core-registry. No arrow between shell and capability. The registry is the stable seam; both sides are consumers of it.

** Slice 2b: inline reasoning mark, parser, and its registration

- Extend the disposition (Slice 1 content) to instruct the =#+begin_reasoning= block on load-bearing claims, and define the reserved fence and field grammar precisely.
- Register the block kind with the Slice-2a registry: =:kind reasoning=, the fence matcher (output-mode-aware), =:display hidden=, and a =:parser= that reads its =key: value= fields into a plist.
- The deterministic parser is the same function the stop-hook uses; it lives with the capability and is exposed through the block spec so the shell's generic transform can strip without importing capability code.
- Verify hiding works through the registry path in both output modes (markdown and =org=), with the raw block retained in the stored transcript for audit.
- No tool, no session record, no provider round-trip: the mark is text the model already emits; this slice teaches it, parses it, and registers its display disposition.
- Justify the mark only as the cheap gate key for Slice 3; if Slice 3 is not built, the registry (2a) still stands on its own as a general seam, and teaching the mark should be re-evaluated for its output cost.

** Slice 3: conditional stop-hook enforcement (needs a core affordance)

- Add the narrow harness affordance for a =:turn-finished= hook to request exactly one corrective follow-up turn during settlement. Prefer the smallest contract that keeps the drain path the single owner of turn scheduling.
- Register a conditional =:turn-finished= hook in the capability that: runs only on marked turns or on a coarse deterministic bare-assertion filter; runs the short checklist; and on failure requests one corrective follow-up naming the specific gap.

*** Stop-hook mechanics: exactly what it reads and how feedback reaches the response

This subsection pins down the runtime behavior, because "stop-hook with a checklist" is ambiguous about what the hook sees and what "apply feedback" means.

**** What the hook receives

The hook is registered at the =:turn-finished= point and runs inside =e-harness--run-turn-finished-hooks= (=lisp/core/e-harness.el=).
It is a reduce over the turn =result=: each hook is called with =(value context)= and returns the next =value=.
The context supplied at this point already carries =:harness=, =:session-id=, =:turn-id=, and =:assistant-message= (the turn's final assistant message, from =e-harness--turn-assistant-message=).
So the hook does not parse a raw token stream; it reads the completed assistant message plist -- its =:content= text and =:metadata= -- plus, when it needs them, the turn's user input and prior messages via =e-harness-messages=.

Concretely the hook reads the assistant message =:content= for two purposes only:

- to extract and parse the inline reasoning mark, if the reply contains one -- the structured block described next;
- to run the coarse gate filter (below) against the surrounding prose and the originating user prompt.

The checks themselves run over the parsed mark, never over the free prose around it.

**** Inline reasoning-mark mechanics (no tool call)

The mark is *not* a tool call and not a session record.
It is a small fixed-format block the agent writes directly into its own reply, the way the =org= output mode already asks the model to emit specific markup.
Because it is part of the assistant message the model was already producing, it costs no extra provider round-trip -- the explicit requirement from this discussion.

The disposition instructs: when you assert a load-bearing factual conclusion, include one fenced block of a reserved kind, e.g.

#+begin_example
#+begin_reasoning
claim: <one line naming the load-bearing conclusion>
confidence: low | medium | high
alternatives: <at least one rival, or the literal insufficient-evidence>
evidence: <references -- tool-call ids, resource URIs, short quotes -- or empty>
#+end_reasoning
#+end_example

Two mechanical properties make this workable:

- *Deterministic to detect and parse.* The reserved fence delimiter is a fixed literal; the hook finds it with a regexp and reads the =key: value= lines. No natural-language understanding is involved. Presence of the fence is the machine-readable "this turn asserts a load-bearing claim" signal -- the exact role the rejected tool call would have played, now carried statically in the output.
- *Hidden through the structured-block registry, not by shell knowledge of this capability.* The capability registers the =reasoning= block kind with =:display hidden= in the core structured-block registry (Slice 2a). At render time the shell asks the registry for display-ready text and the block is removed generically -- the shell never names this capability, so the dependency runs shell -> core-registry and capability -> core-registry, never shell -> capability. The block is retained in the stored transcript/telemetry for audit. This is why the mark does not make the visible output unreadable: it is structured metadata that never reaches the screen, not confidence language woven into sentences.

"The turn is marked" means precisely: the assistant =:content= contains a well-formed =#+begin_reasoning= block.
That is a deterministic string parse, not a judgment about the prose.

**** The gate: when the hook does anything at all

The hook returns =value= unchanged and does nothing unless the turn qualifies:

1. the reply contains a =#+begin_reasoning= block (the agent self-marked) -- always on, OR
2. a coarse lexical filter over the reply trips -- a concrete value, name, or date -- *only when the opt-in flag =e-bayesian-reasoning-enable-bare-assertion-gate= is non-nil*.

Gate 2 is an intentionally dumb tripwire, not a grounding judge.
It exists only to catch turns where the agent asserted something concrete but omitted the mark.

*Reversal (implemented): gate 2 defaults OFF.* The earlier design ran gate 2 unconditionally and tuned it "conservatively" only in the sense of tolerating false positives. In practice the tripwire matches any number, date, or CamelCase name, and ordinary prose is full of those, so it fired a correction on nearly every normal answer -- the "weird message" the user hit on a grimoire chat. The default gate is now gate 1 alone (the self-emitted mark), which fires only when the model actually annotates a load-bearing claim. Gate 2 is available behind =e-bayesian-reasoning-enable-bare-assertion-gate= for callers who accept the extra false-positive follow-ups; its firing rate is telemetry.
On a trivial, hedged, or unmarked turn the hook is a no-op -- the answer to "overkill on every turn."

**** The checks: completeness of the parsed mark, never prose analysis

This is the correction to the earlier framing.
The hook does *not* parse the reply prose to decide whether it is well-calibrated -- that is model-hard and would force unreadable structured output.
Instead the checks run over the parsed =#+begin_reasoning= block's fields, which is a trivial deterministic completeness test:

- Confidence present :: =confidence= is one of the allowed bands.
- Alternative named :: =alternatives= is non-empty (a rival, or =insufficient-evidence=).
- Evidence attached or abstained :: =evidence= is non-empty, or =confidence= is =low=, or =alternatives= is =insufficient-evidence= -- i.e. a bare high-confidence claim with no cited evidence fails.

The two gate paths differ in what a failure means:

- Marked turn (gate 1): a =#+begin_reasoning= block is present, so the hook checks its field completeness. A field-incomplete block fails.
- Filter-flagged turn (gate 2): no block is present at all, so "completeness" is trivially unmet -- the failure is simply "you asserted something concrete and included no reasoning mark."

What the hook deliberately does *not* attempt: deciding whether a filled-in confidence is *accurate*, or whether the cited evidence actually supports the claim.
That semantic judgment needs a model.
It is available only through the optional subagent-reviewer variant (noted below), reserved for high-stakes outputs and gated by the same marking; the default hook is a completeness check, not a truth check.

A pass leaves the response untouched and emits a passing telemetry record.
Only a fail proceeds to feedback.

**** How feedback is applied to the response

This is the key point, and it is deliberately /not/ an in-place rewrite of the model's text.
The hook does not edit the assistant message, does not silently append a disclaimer, and does not fabricate a confidence the model did not state.
Editing the model's words would put the capability in the business of authoring the answer, which it must not do.

Instead, on a fail the hook requests exactly one corrective follow-up turn through the Slice-3 harness affordance.
The mechanism, step by step:

1. The hook leaves the original assistant message in the /stored/ transcript unchanged -- that message already happened and stands as the turn's first attempt for audit -- but flags it hidden from display (see the reversal below), so the user does not see the superseded answer.
2. The hook signals the harness (via =e-harness-request-follow-up=) to schedule one follow-up turn once the current turn finishes settling. The drain path remains the single owner of turn scheduling; the hook only expresses intent.
3. The follow-up turn's input is a system/user message naming the specific missing fields -- e.g. "Your previous answer made a load-bearing factual claim without complete calibration. Specifically: <gap>. Restate the conclusion with a complete reasoning block, or answer with =insufficient-evidence= ...". It names the failing completeness checks, not a generic "be more Bayesian," and it does not tell the model what to conclude -- only to show its reasoning or abstain. This corrective prompt is *hidden from display* -- it is a machine instruction to the agent, not something the user should read.
4. The model then produces a /new/ assistant message in the follow-up turn. The correction is authored by the model in response to a targeted prompt, and it is the only reply the user sees for the exchange.
5. The follow-up is capped at one. The corrective turn is itself marked so it does not recurse: the hook does not re-fire enforcement on the turn it generated, preventing an oscillating loop. If the corrected turn still fails, that is recorded as telemetry and left alone rather than re-prompted.

*Reversal (implemented): show only the final answer.* The earlier design (points 1 and 4 above, original wording) preserved the first attempt /visibly/ and appended the corrective prompt and the correction as ordinary visible messages. The user reported that this leaks a machine instruction ("add a reasoning block recording your confidence...") into the chat, which reads as a non-sequitur. The chosen model is now: the corrective follow-up prompt and the superseded first attempt are both hidden from display; the agent incorporates the feedback and the user reads a single clean revised reply. Provenance is preserved because both hidden records remain in the stored transcript/telemetry for audit; only their /display/ disposition changes.

Display mechanics: a message carries a =:display= disposition. The follow-up prompt is queued hidden from the start via its turn =:metadata= =(:display hidden)=; the first attempt is flipped after the fact via =e-harness-set-message-display=, which writes a durable =message-display= event so the hidden state survives replay. A shared predicate =e-harness-message-hidden-p= recognizes both the top-level =:display= (the after-the-fact flip) and the =:metadata= =:display= (the born-hidden prompt). Both shells consult it: the modernchat view model drops hidden messages from the snapshot, and the classic chat shell skips them in =e-chat--render-session= / the live =message-added= handler and re-renders the transcript on =message-updated= when a shown reply is flipped hidden.

So "feedback applied to the response" means: a single model-authored reply -- prompted with the exact calibration gap -- is what the user sees, while the first attempt and the machine prompt persist hidden for audit.

Inspecting hidden messages (implemented): hiding must not mean the record is unreachable. The classic chat's response-navigation ("chat history inspection") mode -- entered with =ESC= -- gains an =h= toggle, =e-chat-response-navigation-toggle-hidden=. It flips a buffer-local =e-chat--reveal-hidden= flag and re-renders the transcript; while set, =e-chat--render-session= emits each hidden message as a dimmed, italic audit block (=e-chat-hidden-face=, glyph =⋯=, labelled "superseded answer" or "calibration prompt") of block kind =hidden=. Because these are real navigable blocks, =j=/=k=/=RET=/=y=/=o= work on them for free; a hidden block never joins the turn's activity or finalization flow, so revealing it cannot disturb the visible answer's rendering. Revealing focuses the first hidden block; toggling off (or returning to the composer via =i=/=ESC=) clears the flag and restores the clean one-answer transcript, which stays the default reading view. The reveal is view-only -- it changes nothing in the store, so audit reads the same records the modernchat snapshot omits.

**** Why not rewrite in place

Rewriting the =value= (the turn result) or the assistant message directly is available at this hook point and is rejected on purpose:

- It would make the capability the author of factual content, which it cannot calibrate honestly.
- A machine-inserted "(confidence: 70%)" is exactly the fabricated, uncalibrated number the tenets warn against.
- Keeping the first attempt in the stored transcript (hidden from display) and adding a model-authored correction keeps provenance auditable: telemetry can compare first attempt to correction and measure whether the loop earns its cost. Hiding the first attempt from display is a presentation choice, not a mutation -- the record stands.

**** Failure and edge handling

- If the harness cannot schedule a follow-up (no valid settlement window), the hook degrades to emitting the failing checklist as telemetry/annotation and returns =value= unchanged; it never errors the turn.
- The deterministic filter (gate 2) is intentionally coarse and defaults OFF behind =e-bayesian-reasoning-enable-bare-assertion-gate=; when enabled, false positives cost one extra follow-up and its firing rate is part of the telemetry.
- Hiding depends on the harness display affordance (=e-harness-set-message-display= + =e-harness-message-hidden-p=). If the display flip fails, the follow-up is still requested; the worst case is the first attempt remains visible, never a lost correction.
