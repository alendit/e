* Goal

Make =e-work= the common lifecycle for executable operations.
Make the board event bus the single live orchestration, routing, and delivery substrate between chat, waiting invocations, runtime producers, application services, and participant sessions.
Use one subscription model for exact identity correlation and tag/condition dispatch; do not build a second callback graph beside it.

=e-loop= still owns how a provider tool call is paired with its result.
The waiting invocation installs an exact one-shot subscription before work starts, receives the terminal event through the board, and remains the only path that appends that tool result.
A later follow-up is another subscription effect that posts a board input with an exact recipient or descriptive tags/attributes.
=e-work= settles executable state; board subscribers decide what the settlement causes next.

When an agent starts work, it may wait for the result, post it later to an exact participant, or publish it for matching subscribers.
A normal tool call remains efficient because its open call can wait for the work it started.

The same board carries user input, schedule fires, file-notify triggers, operation lifecycle events, subagent completions, and task-queue events.
"The user typed something" and "the grep finished" are both ordered facts, while only the grep has an executable-operation lifecycle.

* What already exists

Most of the substrate landed in feats 55, 59, 60, and 64:

- =lisp/core/e-waitable.el= :: reference-scheme resolvers, so =subagent:sub_3=, =task:...=, and =work:<id>= all resolve to handles.
- =lisp/core/e-await-tool.el= :: the model-facing join over a set of references.
- =wait_for= on every detachable tool :: run inline for N seconds, otherwise detach and return =work:<id>=.
- =lisp/core/e-harness.el= :: per-session prompt queue, post-settlement drain, and mid-turn steering input.
- =lisp/core/e-loop.el= :: =drain-pending-input= at every provider request boundary, already a mid-turn injection channel.
- =e-session-fork= :: fork a session at a message, seeded with the source's current path.
  The mechanism branching needs already exists.
- =e-subagent-registry= / =e-subagent-actions= :: spawn, steer, read, shutdown, and a child-side =report= that sets a structured result.
- =e-harness-instances= :: several live harness instances with their own sessions, which is why the shared scope below is not just "the root session".
- =e-chat= presentation :: the shell currently derives provider wait/stream status, =Thinking= /=Thought= rows, reasoning/tool/action activity, and the navigable terminal =Turn took ...= summary from live harness events plus durable session activity; redraw/coalescing stays on =e-ui-work=.

The current runtime also has gaps this feature must close:

- =e-tools-register= accepts broad =:handler=, =:start=, and =:work= implementations, so not every executable carrier produces a canonical =e-work= handle and the non-executable =await= relation has no narrow subscription-backed contract.
- A whole agent turn has no =e-work= handle, although each backend request inside it does.
- Schedule and file-notify fires lack board event identity/routing; as facts, they correctly do not need operation handles.
- The current =wait_for= coordinator returns a result to one captured tool call instead of representing that correlation as a board subscription reusable by later effects.
- =e-harness-queue-prompt= requires a running turn, while idle delivery follows a different path.
- =e-chat= opens/prompts a session, subscribes to its harness, and reads its transcript/activity directly instead of posting to and observing one tagged board message stream.
  The board migration must replace those data sources without regressing the existing intermittent activity, terminal summary, navigation, or redraw behavior.
- No service maps a participating session id to its current live harness across harness instances.
- Subagent and task-queue registries already push change events and must remain the source of truth for their domain state.
- Detached work, subagent records, and task records need bounded retention before the board can retain related history safely.

Missing: one operation lifecycle for all executable work, one selector/subscription model for exact and condition-based routing, inspectable continuation effects, delivery that records why it happened, one ordered event log, a current-state view of outstanding work, and coordination across sessions.

* Concern: interleaved threads of work in one context

The worry is not protocol-level mismatch between a call and its result.
It is that one linear context ends up carrying several logical threads of work, spliced at arbitrary points, and the model reasons worse in that context: it loses which plan it was executing, re-reads a stale intent as current, or applies a conclusion from thread A to thread B.

** What is structurally safe

Call/result pairing is not at risk.
=e-loop= runs tool calls one at a time (=tool-queue=, =start-next-tool= gated on =active-tool=, =finish-tool= appending call and result together), and provider adapters map each pair adjacently.
A late completion therefore cannot arrive as a tool result for an already-answered call; it arrives as new turn input.
That bounds the problem to one thing: prose and events from thread B landing between the steps of thread A.

** What actually degrades

Three distinct effects, worth separating because they have different fixes:

1. *Stale intent.*  The result arrives after the agent moved on and it must recover why the work was started.
   Fixed by putting the original intent and requested follow-up in the published board input.
2. *Plan fragmentation.*  Thread A's reasoning is cut in half by thread B's event and result.
   Not fixed by better event payloads.
   Fixed by not interleaving: put thread B somewhere else.
3. *State ambiguity.*  "What is still running" has to be inferred from interleaved history.
   Fixed by a current-state view: history answers what happened, while the board answers what is true now.

Effect 2 is the one that motivates the rest of this section.

** Response: choose a selector and delivery mode

A board continuation answers two questions:

- *How is the recipient found?*  By exact identity correlation or by tag/condition matching in the common subscription router.
- *When may participant input enter a session?*  By =inject= or =queue= delivery mode.

Identity selection is intentional coupling: return this work result to its waiting invocation, or post this input to participant X.
Condition selection is discovery: post this result with tags such as =main= and let every matching participant subscription receive it.
Both are selector forms over the same board sequence, not separate direct-reply and broker subsystems.

*** Selecting exact identity or conditions

The first version supports these routing intents:

| Intent | Selector/subscription | Cardinality | No match |
|--------+-----------------------+-------------+----------|
| Return work to its open tool call | Exact =work-id= selector whose effect targets open =(turn-id, tool-call-id)= | Exactly one invocation while open | Timeout/detach closes only the invocation subscription; the terminal work event remains visible |
| Deliver input to participant X | Exact =participant-id= selector, matched by that participant's built-in identity subscription | Zero or one | Visible =unrouted= reason =target-unavailable= |
| Dispatch to whoever handles =main= | Tags/conditions matched by participant subscriptions | Zero to many | Visible =unrouted= reason =no-matching-subscription= |
| Aggregate several work results | Exact work-id conditions with =all-terminal= or =first-terminal= readiness | One subscription activation | Remains pending until its declared readiness/expiry |

A selector may combine exact fields, message/event kind, work kind/state, author, tags, visibility, and a bounded predicate function.
The first process-local version stores an ordinary predicate function directly; it does not introduce a predicate registry or version protocol.
Predicate evaluation must be bounded, non-blocking, side-effect-free, and a signalling predicate fails the subscription visibly.
Model-facing board actions accept declarative conditions only; trusted in-process application/capability code may add a predicate.

Exact delivery never requires a redundant tag.
Tag dispatch never requires the poster to know which participant currently handles that role.

*** Results in the current turn and later turns

A result can reach a turn in two ways.
If the tool call is still waiting, the result returns to that call.
Only =e-loop= and =e-tools= append this tool result to the transcript.
The board records that the work finished but does not append the result.

A later board input uses one of two modes:

| Mode | What happens |
|------+--------------|
| =inject= | Add the message only at a future safe point in an =accepting= turn for the same board; otherwise use that participant's inbox |
| =queue= | Keep the message in the session inbox until the session is idle |

The existing =wait_for= race remains until this path is built.
If work finishes within the hold window, the tool call receives its result.
If the deadline wins, the tool call receives =work:<id>= and stops waiting.
A temporary =:notify= compatibility option may still compile to a later =post-input= continuation while callers migrate.

Follow-up posts can target the same participant, a child, a sibling, or a parent participant by identity, or any matching subscriber by conditions.
Several subscriptions may use the same result.
If the follow-up requires substantial work, post it for another participant.

** Forks are sessions, not a selector kind

A fork answers plan fragmentation when the caller explicitly decides that a reaction needs context from an earlier transcript point: create the fork participant at that mark, then let later board posts reach it through ordinary exact/tag subscriptions.

The mechanism exists.
=e-session-fork= with =:at= already rebuilds a linear path up to a message; it becomes an ordinary session-producing action returning a session id, exactly like subagent spawn.
The authorized application service creates and registers the fork participant explicitly; a later subscription may then address its identity or match its declared tags.
The mark is always a session transcript entry id, never a board =message-id=; the pickup receipt records the board-message-to-transcript-entry mapping.
The first version requires callers to provide =:at=; omission is a validation error rather than an implicit choice of transcript position.

- A fork does not merge or automatically rejoin.
  If it should report back, it posts a board input containing a bounded summary, stable =source-input-key=, and either an exact parent selector or tags; normal board pickup performs delivery.
  Merging two divergent contexts is not attempted, now or later.
- The cost is real: a fork duplicates context and re-pays cache warmup, so it is explicit, opt-in, and never a routing side effect or default.
- A fork is a board participant like any other, so its work and subscriptions are visible through the board rather than through session plumbing.

Fork and child differ only in what the follow-up knows: a fork inherits the parent's history, while a spawned child starts from its type's prompt plus the posted message.
When the reaction is describable, a child is cheaper and returns a structured result.

** Where it stays genuinely hard

- *Wake storms and cost.*  Each wake is a provider request with full context.
  The board must batch nearby events, limit automatic wake-ups, and wait for a short quiet period before waking a session.
- *Cycles.*  An agent can post work whose completion causes another post that matches the same subscription lineage.
  Derived posts need a causal hop/publication limit and a visible cycle stop distinct from the provider wake budget.
- *Orphaned work.*  Detached work with no waiting invocation or continuation subscriber finishes unobserved.
  A session going dormant with unobserved terminal work must say so.
- *Fork sprawl.*  Branch-per-event is easy to overuse.
  Cap concurrent forks per session and report the cap.
- *Cross-session delivery rights.*  A continuation post can wake another session.
  Delivery must be confined to authorized board participants and record which participant requested it.
- *Future claim deadlock.*  If claimable offers are added later, an agent could await work that only it is eligible to perform.
  That belongs to the follow-up claim state machine, not the broadcast-message implementation here.

* Model

** Board messages and chat ingress

Chat connects to a board as an authorized board client, not as a session.
The connection has a board-local =client-id= and trusted local-user/requester context but no harness endpoint or transcript.
Posting from chat calls the board ingress service and creates one board-owned input message; it never calls =e-harness-prompt-async= or mutates a session inbox directly.
Chat renders the board message stream, while participant sessions keep their own transcripts as private execution context.

Each board message has =message-id=, =board-id=, monotonic posted =seq=, =kind=, qualified =author= (=client:<id>= or =participant:<id>=), optional =subject-participant-id=, bounded =tags=, optional exact =to= identity, optional =source-turn-id=, ordered causal message/delivery ids, and bounded content/reference.
Participant-pickup routing intent is unambiguous: when =to= is present, only that participant's built-in exact-address =create-pickup= subscription is eligible and tags are descriptive metadata; when =to= is absent, ordinary condition/tag pickup subscriptions are eligible.
Observer and non-pickup continuation selectors may still match =to=, tags, author, or subject as ordinary record fields.
The first version has three kinds:

- =input= :: carries =mode= and optional producer =source-input-key=; exact identity or matching participant subscriptions may pick it up as turn input.
- =output= :: requires participant =author=, equal =subject-participant-id=, a stable =source-output-key=, the producing =source-turn-id=, ordered =reply-to-message-ids= and =caused-by-delivery-ids=; it is canonical final assistant content and is observation-only unless an explicit subscription effect posts a new =input=.
- =activity= :: requires participant =author=, equal =subject-participant-id=, a stable =source-activity-key=, =source-turn-id=, =activity-kind=, ordered cause ids, and a bounded sanitized payload; it represents chat-visible turn/provider/reasoning/tool/action/terminal activity and is observation-only unless an explicit subscription effect posts a new =input=.

Only =input= is structurally eligible for =create-pickup=.
An =output= or =activity= may match observers and explicit continuation subscriptions, but merely carrying a participant-routing tag never feeds it back into a participant inbox.

Input =mode= is =inject= by default; chat's explicit queue/prefix submission uses =queue=.
The mode is frozen into each pickup envelope and follows the delivery-phase table below.
All source-key forms are board-scoped =(producer-id, producer-generation, producer-seq)= tuples; a producer allocates its strictly increasing sequence before publication and serializes its posts.
=producer-generation= is the client connection generation, the participant membership's stable posting epoch, or an application producer's explicit epoch; it is not the replaceable harness endpoint generation, and participant endpoint rebind does not change it.
A repeated producer post whose key remains in the recent map returns the existing message and pickup ids; fork summaries and other retryable producers persist one =source-input-key= before their first attempt.
The board atomically advances a per-kind, per-producer source high-watermark with the append and retains a bounded recent key-to-message map.
A key at or below that watermark whose map entry has been compacted returns explicit =source-history-expired= and never appends; a late or out-of-order key is therefore refused rather than mistaken for new input.

When a participant turn begins, its cause initializes a bounded ordered union of routing tags from the causing board input; every later board input consumed into that same turn atomically extends the union.
Every =activity= and =output= publication freezes and copies the turn's current tag union, while terminal summary/output use the final union and exact =to= remains pickup metadata only.
Thus chat input tagged =main=, the activity/summary it causes, and the participant's final output all remain selectable as one =main= conversation; a subagent or any other view uses another tag, exact author/subject/to clause, or ordinary selector condition without a different transport.

Every participant has a registry-created =create-pickup= identity subscription for =to=<its participant-id>=.
It is membership-owned and non-replaceable/non-mutable: it remains eligible while the participant membership is active or validly stale/dormant and ends only when that membership detaches, is revoked, or is removed.
Ordinary =main= and other condition subscriptions may be muted, cancelled, expired, or replaced independently.
Every subscription contains =subscription-id=, board id, owning consumer, immutable selector, class-specific state, =created-seq=, optional =start-seq=, =next-seq=, bounds, and provenance.
Orchestration subscriptions use state =active=/=muted=/=completed=/=faulted=/=cancelled=/=expired= and additionally carry a declarative effect, readiness/accumulator policy, and firing/lifetime/publication budgets; their owners include waiting invocations, participant input routes, and authorized participant/application services requesting =post-input= continuations.
Client-owned observer subscriptions use state =active=/=muted=/=faulted=/=cancelled=/=expired= and instead carry only delivery/read-through cursor and buffer bounds.
They reuse the same selector grammar and board sequence but create no activation/effect, pickup, wake, routedness change, or causal publication.
Here =observer subscription= always means a client read cursor; it is unrelated to the existing =e-work= =publication-observer= settlement hook and to the board's work-observation set.
Changing an orchestration matcher/effect or observer matcher cancels and replaces that subscription instead of adding a predicate-version protocol.
Every subscription belongs to the board registry entry, not to chat or a harness endpoint; participant-owned subscriptions survive a proven endpoint rebind while that membership exists.

On every message append, the board evaluates eligible observer subscriptions against the same immutable snapshot and exposes independent non-consuming copies in board sequence.
On every board record, it separately evaluates eligible orchestration subscriptions whose selectors admit that record and freezes all matching subscription ids/activations.
For an =input=, exact or condition subscriptions whose effect is =create-pickup= contribute to the frozen participant/pickup set; for every other record kind that effect is structurally ineligible, while an explicit continuation subscription may still apply =post-input=.
One slow/offline participant does not hold back another; a registered dormant/stale participant may retain a bounded pending pickup while its endpoint is unavailable.
If several =create-pickup= subscriptions owned by one participant match, the board creates one pickup for that participant and records every matched subscription id in its cause.
Input routedness is defined only by eligible =create-pickup= matches.
If none of those match, the message remains visibly =unrouted= with =target-unavailable= or =no-matching-subscription= until an authorized caller explicitly reroutes/cancels it; non-pickup continuation activations may still fire independently and do not make the input routed.
Adding a participant or orchestration subscription does not silently replay earlier messages; replay requires an explicit =start-seq= or reroute operation.
An initial chat observer intentionally snapshots matching retained messages from the board retention floor unless the caller supplies a later =start-seq=; reconnect resumes from its read-through cursor, and selector widening supplies an explicit retained start.

For every frozen participant match, the board creates one logical pickup envelope with stable =delivery-id= =(board-id, message-id, participant-id)=, participant id, and matched subscription ids, and tracks its state independently.
Endpoint token/generation is not part of that immutable envelope; it belongs to a replaceable physical-attempt record selected only when the pickup reaches the FIFO head.
The runtime reauthorizes membership and generation before each attempt, at acceptance, and again when a queued item starts a turn.
The participant's =message-next-seq= is the first board input not yet classified for that participant.
The harness receipt and delivery-phase contract accepts and consumes the pickup exactly once.
This is fan-out of a board message, not a claimable work offer: every frozen matching participant receives its own copy.

Pickup is FIFO per participant.
At most one pickup is =ready=, =rebinding=, =delivering=, or =accepted= for that participant; later addressed inputs remain bounded pending records and cannot overtake a retry/reset.
=message-next-seq= advances only after the input is ignored for that participant or a pickup/tombstone is committed.
Rerouting an older =unrouted= message evaluates the explicitly selected current subscription set, assigns a new =routed-seq=, and inserts matches at that current FIFO position while retaining its original =posted-seq= for audit.
A per-participant pending cap/expiry turns excess or permanently stalled pickups into explicit =overflowed= /=expired= tombstones; it never silently drops them or blocks another participant's cursor.

The normal interaction path is:

1. Chat posts an =input= message with an exact =to= or descriptive tags/attributes to the board; subscribers, not chat, own matching conditions.
2. The board records it, evaluates the common subscription router, and freezes matched subscription/participant/pickup ids.
3. Eligible sessions pick it up through =e-harness-deliver-input=; consuming it creates a board-scoped turn and one transcript input.
4. The participant posts bounded idempotent =activity= messages throughout the turn, including one terminal =turn-summary= when provider activity occurred, and posts its final assistant response idempotently as one =output= whose =source-output-key= uses the participant producer identity/generation and a persisted monotonic =board-output-seq= stored on that assistant transcript entry; =source-turn-id= correlates all of those board messages.
   It relates to the ordered set of board message/delivery ids consumed since that participant's preceding assistant output, so several injected inputs in one turn remain representable.
5. Chat's non-consuming observer subscription yields every matching =input=, =activity=, and =output= in board sequence; no session-to-chat backchannel is needed.

The common source high-watermark/recent-map rule makes output publication bounded and at-most-once: a retained duplicate returns the existing output, while a retry older than retained history returns =source-history-expired= and cannot append a duplicate.
=e-session= owns a per-session next-output counter and allocates the sequence atomically with assistant transcript append; session-store replay preserves both the entry field and counter.
Legacy entries without the field are pre-board history and are never retroactively published; loading them seeds the counter from the greatest recorded field (or zero), and the first new assistant entry receives the next value.
A repeated completion callback rereads the same entry field, so reload, output-pending retry, and recent-map eviction cannot allocate a second source identity.
Chat subscriber/render failure is isolated after board append and does not retry publication, and old runtime-generation callbacks cannot publish.
Transcript/turn settlement creates a bounded =output-pending= projection record and does not wait on chat rendering.
If board append itself fails, the runtime retries that record with the same source key or records visible =output-publication-failed= without resettling the turn.
Only the exact final assistant entry selected by successful turn completion is publishable.
Generic =message-added= callbacks, partial assistant/tool-call entries, failure, and cancellation never publish an =output=; the publishable entry persists its =source-turn-id= plus frozen originating board, participant, posting epoch, and attachment/source generation so retry never resolves against a later board or rebind.

The participant activity publisher applies the same rule independently.
=source-activity-key= always uses the common tuple: its producer sequence is one monotonic =board-activity-seq= allocated for every accepted coalesced activity publication, persisted on durable activity entries or in the pending publication record before append.
The durable session activity-entry id, or live =(turn-id, stream-id, progress-version)=, is a separate =source-event-id= used to find/reuse that frozen tuple on retry; per-stream versions never substitute for the producer high-watermark sequence.
Each append freezes originating board, participant, posting epoch, endpoint/source generation, current turn cause/tag union, normalized subtype, and sanitized payload; terminal summary freezes the final union.
Terminal =turn-summary= publication has a bounded pending/retry/failure record, and a stale callback or retry after participant move/rebind cannot resolve against a new origin.

An agent that wants another participant to act posts an =input= with an exact participant identity or descriptive tags/attributes.
Merely posting an =output= or =activity= cannot create a feedback loop; a continuation subscription must explicitly react by posting new input, and board propagation budgets bound that chain.

*** Chat is a non-consuming board observer

A board-connected chat has one input source: an ordinary board observer subscription.
Every semantic item chat can render is first accepted as an =input=, =activity=, or =output= board message with a board =seq=; chat receives no direct harness/session presentation frames and never reads session activity to reconstruct the board view.
Its default selector matches tag =main=.
Because participant activity, terminal summaries, and outputs inherit their causing turn's routing tags, this selects both the chat input sent to =main= and every board publication caused by the participant or participants that picked it up.
Following a subagent or another thread merely widens/replaces the observer selector with that tag, author, subject-participant, exact =to=, or other allowed condition; it does not install a new transport or alter participant pickup subscriptions.
When chat explicitly selects an exact participant, it installs the corresponding observer clauses before posting, so an exact-address conversation need not masquerade as =main= to remain visible.

Observation is passive.
Reading through a match advances only that observer's client cursor; it does not consume the board fact, create an activation/effect/pickup, mark an input routed, wake a participant, or change what any other subscriber can see.
Several chats may observe the same message independently.
Participant =create-pickup= subscriptions are structurally constrained to =kind=input=, so =main=-tagged activity and outputs cannot loop back into the main session.

Observer open/reconnect uses only board state.
The board installs/buffers the observer at one serialized high-watermark, returns retained matching messages plus its current bounded open-activity projection through that =seq=, drains later buffered messages in =seq= order with =message-id= deduplication, and then switches to live delivery.
Client/subscription generations fence late callbacks; retained-history expiry or non-coalescible buffer overflow requires a fresh board snapshot instead of a direct session fallback.
Participant endpoint rebind needs no observer cursor change because accepted messages already belong to the board; producer generation/source-key checks reject late publications from the old endpoint.
Open-activity projection entries contain only state plus references to their accepted board activity =message-id=/=seq= values; a snapshot never fabricates a renderable activity item.
Appending a correlated =output= or any terminal activity closes/suppresses the open projection immediately, even if =turn-summary= is delayed or permanently fails to publish; reconnect therefore cannot resurrect =Thinking=, and the missing summary remains a visible board publication failure.
Every board message is rendered idempotently by =message-id=.
When selector replacement/backfill redelivers overlap, chat reuses its board-scoped rendered-message index rather than inserting a second =main= record; a fresh snapshot rebuilds that index from the retained message set before live drain.

The normalized =activity-kind= values preserve the current visible contract: turn start/terminal state, provider request start/finish, board-safe reasoning summary/deltas, tool start/progress/finish, action start/finish/fail, steering/hook/compaction status needed by the shell, an assistant-streaming marker, and terminal =turn-summary=.
The terminal summary is an idempotent board message with structured status, duration, and tool/action counts; chat does not synthesize it from private session activity.
Raw reasoning, endpoint tokens, transcript messages, unbounded tool arguments/results, and partial final-answer text are never published; the final answer exists only as =output=.
Only animation ticks, focus, expansion, tool-list selection, and =e-ui-work= redraw/coalescing jobs remain shell-local.

Every semantic update delivered to chat has a board =message-id=/=seq=.
The participant publisher coalesces high-frequency reasoning/tool progress before append and includes a progress version/coalesced-through marker; the board retains the latest open state per =(subject-participant-id, source-turn-id)= for snapshot/reconnect.
Lifecycle boundaries and =turn-summary= remain retained board facts; superseded intermediate progress may compact after the stream is terminal and unread observer cursors no longer pin it.
A stale nonterminal message creates no spinner unless the board's retained open-activity projection still marks that participant/turn active.

The =e-chat= reducer keys simultaneous activity streams by required =(subject-participant-id, source-turn-id)=, so widening the selector to subagents requires no special UI transport.
Turn start shows the moving assistant indicator; provider start shows timed =Thinking=; reasoning and tool/action messages update the intermittent block; provider finish settles =Thought=; =turn-summary= finalizes one navigable =Turn took ..., N tool calls/actions= summary.
Failure/cancellation publishes terminal activity/status and a duration-bearing summary only when provider activity occurred, and never invents final =output= or an empty summary for a turn that never reached the provider.

Board =output= and =turn-summary= may be posted in either order, but their board sequences and shared =(subject-participant-id, source-turn-id)= correlation are authoritative.
The shell tracks independent =output-seen= and =summary-seen= facts: output owns canonical content, while summary owns terminal status/duration/activity counts.
Output-first renders once, stops the matching spinner, and retains its accumulated activity provisionally until the summary arrives; summary-first finalizes the existing activity block and waits for a later output without synthesizing one.
The reducer folds later activity messages for a turn into the activity block anchored by that stream's earliest visible board sequence, without reordering unrelated board messages; canonical =output= content always stays at its own board-sequence position, and its summary decorates by correlation rather than relocating it.
Failure/cancellation are no-output terminal activity/summary and anchor at their own board sequence when no earlier activity is visible.
Transcript callbacks and the old missed-final fallback are not board publishers, so canonical board input/output cannot duplicate.

** Executable operations

Every executable operation is an =e-work= handle.
Input facts such as user messages, schedule fires, file notifications, and annotation changes are board events without dummy work handles.

The =e-work-handle-id= is the canonical =work-id=.
There is no second execution =operation-id=; that term remains available to =e-operations= for semantic resource operations such as =read= and =write=.
Operation metadata lives in start context or in a board-owned side table keyed by =work-id=.
It includes =kind=, =owner-service=, =poster-participant-id=, =poster-endpoint-generation=, =board-id=, =intent=, =visibility=, =parent-work-id=, =root-work-id=, =caused-by-event-seqs=, optional =caused-by-activation-id=, and an optional =domain-ref=.
The =e-work-handle= structure does not gain board, session, tool, or subagent dependencies.
Executable tool carriers, turns, provider requests, task attempts, and subagent attempts all produce handles; invocation-only =await= is the explicit non-executable exception below.

=parent-work-id= expresses ownership/nesting, while event/activation causes link board input facts to the work they caused.
Ordering comes from board sequence and recorded activations, not from direct work-to-work callback edges.
They live in =e-work= start/handle metadata and the board operation projection and are never inferred from timestamps.

*** Operation identity contract

The table is normative.
It prevents invocation identity, durable domain identity, and executable-work identity from collapsing into one id.

| Runtime thing | Canonical identity | Board representation | Required relation and settlement rule |
|---------------+--------------------+----------------------+---------------------------------------|
| Executable operation | =work-id=, exactly the =e-work-handle-id= | One observed operation record and at most one terminal event | Parent/root express nesting; board event/activation causes express causal ordering; settlement is immutable |
| Agent turn | Existing durable =turn-id= plus a distinct =work-id= | The turn work record uses =domain-ref= =turn:<turn-id>= | Provider attempts and tools are child work; retry replaces a child attempt, not the turn identity |
| Tool invocation waiting for work | Pair =(turn-id, tool-call-id)= | A waiting-invocation relation, not another operation record | Its exact effect target is the invocation; its selector may watch one work id or an ordered set, and =e-loop= appends its result exactly once |
| =wait_for= inline or detached execution | The executable child's =work-id= in both cases | One operation record throughout | A deadline settles only the waiting invocation with =work:<work-id>=; it does not settle, rename, or replace the work |
| =await= join | The open =(turn-id, tool-call-id)= invocation plus its subscription id; no dummy =work-id= | One aggregation subscription whose effect target is that exact invocation | It executes no carrier work; timeout/cancel closes the invocation subscription, while watched work continues |
| Compatibility detachable wrapper | Its temporary handle id, marked =kind= =invocation-adapter= and =visibility= =internal= | Not enrolled or addressable by a subscription | It maps legacy callers to the canonical child =work-id= and is removed when Slice 2 completes |
| Task or subagent attempt | Attempt =work-id= plus existing =task:<id>= or =subagent:<id>= =domain-ref= | Work state is observed; the domain registry remains authoritative | A retry is a new child attempt; the durable task/subagent id never substitutes for a work id |
| External fact | Board =(board-id, seq)= | Event only | It may carry =caused-by-work-ids= or =caused-by-event-seqs=, but gets no dummy handle |
| Claimable offer before execution | Board-local =offer-id= | Reserved future offer state, not an operation record | Claiming would create a new =work-id= linked by =domain-ref= =offer:<offer-id>=; claim semantics belong to follow-up work |
| Rendering-local =e-ui-work= job | Its ordinary =e-work= handle id | Not enrolled by default | Buffer/window scheduling stays outside the board; only the semantic activity that caused it is a board message |

The common start path is explicitly two-phase: =e-work-prepare= allocates a prepared handle without invoking its runner, and once-only =e-work-start-prepared= invokes that runner after owner enrollment succeeds.
The names may be refined during implementation, but exposing the prepared handle and preventing early runner execution are normative.
A prepared handle may be cancelled/failed before start; =e-work-start-prepared= refuses a settled or already-started handle and can invoke the carrier at most once.
When an =e-work= publication observer is present, the board-enrolled start service enrolls that =work-id= and a terminal-publication outbox slot before starting the runner, which keeps cheap and asynchronous work on the same identity path.
The explicit exception is =visibility= =internal=: an invocation adapter is not enrolled and propagates its observation/invocation/continuation intent only to the already-preallocated canonical child.

*** Bus selector and aggregation truth table

=e-work= owns only executable identity, lifecycle, result, progress, and cancellation.
It has no =then=/=reduce=/=all=/=any=/=recover=/=finally= execution graph and produces no graph-result handles.
For live board-scoped work, settlement appends one idempotent terminal event before any routed continuation effect may run.
The board subscription reducer supplies readiness and aggregation over those serialized events:

| Readiness policy | Selector | When it fires | Effect input | Cancellation and other work |
|------------------+----------+---------------+--------------+-----------------------------|
| =on-success= | Exact work id plus =finished= | Once when that terminal event is committed | One immutable work snapshot | Cancelling the subscription does not cancel the work |
| =all-terminal= | Declared ordered work-id set | After one terminal event for every id | Snapshots in declared input order | Failure/cancellation are values; siblings are never cancelled implicitly |
| =first-terminal= | Declared ordered work-id set | On the lowest committed board sequence; declared order breaks a same-mutation tie | Winning terminal snapshot plus the frozen current ordered-set view when requested by the effect | Losers continue and remain observable |
| =on-failure= | Exact work id plus =failed= | Once on failure | Failure snapshot/reference | Finished/cancelled do not fire |
| =on-terminal= | Exact work id plus any terminal state | Once on finish/fail/cancel | Terminal outcome snapshot | Does not alter work settlement |
| =batch= | Condition selector plus bounded ordered accumulator | At declared count or maximum-delay boundary | Frozen ordered source event ids/snapshots | Expiry/cancellation stops only future firings |
| =latest-after-quiet= | Condition selector plus one latest snapshot/timer | After no newer match arrives for the declared quiet period | Latest source event id/snapshot | A newer match replaces the accumulator and resets the timer |

=all-terminal= over an empty set is immediately ready with an empty input; =first-terminal= over an empty set fails subscription installation.
These meanings intentionally match current =e-work-await-set= =all=/=any= behavior, but the live implementation is board subscription state rather than an =e-work= combinator.
An =await= tool is the intentional invocation-only exception to executable =:work= tools: it installs one aggregation subscription whose =reply-to-invocation= effect targets its own exact open call.
It gets no dummy graph-result/await-work handle, while every tool that actually executes a carrier still has one canonical =work-id=.
Its adapter freezes the declared reference order as =(ref, resolved-work-id-or-resolution-error)= entries.
At =all-terminal=/=first-terminal= readiness or timeout it builds the existing structured report from every declared entry and every resolved work's current snapshot, including still-pending snapshots in =any= mode, preserving =:settled=, =:reason=, =:mode=, =:results=, per-reference errors, and ordinary outer =e-tools= shaping.
Empty input or zero resolvable references creates one immediate activation/reply containing the empty/error report; it does not fail generic =first-terminal= installation and does not bypass the invocation effect path.

Stored/model-created effects are deliberately small:

- =reply-to-invocation= :: idempotently close one exact waiting invocation with the frozen result/outcome.
- =post-input= :: idempotently append one board =input= with bounded content/reference, =to= or tags, mode, and causal metadata.
- =create-pickup= :: for a participant-owned input subscription, create/coalesce the stable pickup for that owning participant; it cannot name a different participant.

A participant identity/tag subscription applies only =create-pickup= and routes an already-posted =input= into the common pickup machine; it never calls a destination-specific delivery path.
Ordered workflows therefore emerge from successive board publications and consumers; internal function calls inside one operation remain owned by that operation and do not become fake bus nodes.

Cancelling a subscription cancels its uncommitted activation/effect and never cancels matched work.
Cancelling work still invokes its carrier cancel function and publishes one =cancelled= event.
Turn abort fences the exact invocation subscription and cancels its owned active work through the existing harness service; it does not cancel unrelated tag subscribers.

The normative live ordering is:

1. =e-work-prepare= preallocates the canonical =work-id= without invoking the runner.
2. The board service atomically enrolls the operation, allocates its terminal-publication outbox slot, and installs any applicable exact invocation/continuation subscriptions plus a dedicated =e-work= publication observer.
3. =e-work-start-prepared= invokes the runner once; cheap work may settle before it returns.
4. Settlement freezes lifecycle/result once, invokes the dedicated =e-work= publication observer before general =on-settle=/=:on-done= coordination callbacks, and appends or records the terminal outbox item by stable source key.
5. The terminal append freezes matching subscription activations; carrier cleanup and legacy/off-board callbacks may then run.
6. Idempotent board effects are applied only after the initiating start stack unwinds.

There is no direct live-continuation fallback when terminal publication fails.
The preallocated board-registry/runtime outbox slot freezes terminal source identity =(board-id, work-id, terminal-state)= and payload on settlement.
The =e-work= state remains settled, while a pinned visible =terminal-publication-pending=/=terminal-publication-failed= projection drives retry/reconciliation; otherwise a second callback graph would silently diverge from the bus.
Its injected stable =e-work= publication-observer trampoline resolves the current registry/runtime generation at settlement, so compatible reload may replace drain callbacks without losing a later terminal event; generation-specific scheduled callbacks still become no-ops.
Board-enrolled work must not use =:on-done= or =e-work-on-settle= to advance live coordination.
Raw/off-board =e-work= remains valid for carrier internals, batch utilities, tests, and rendering-local =e-ui-work=, but it cannot advance a live board workflow.
Only the board-enrolled start service allocates the outbox/=e-work= publication observer; raw =e-work-start= never acquires one dynamically.

Matching, accumulation, and reducer commits are bounded and non-blocking.
They do not poll, sleep, call =accept-process-output=, wait interactively, or perform expensive follow-up work on the board drain.

** Event log

One serialized append-only mutation log per board, with a monotonic =seq=.
Message/fact event types are =input-posted=, =output-posted=, =activity-posted=, =output-publication-failed=, =activity-publication-failed=, =input-unrouted=, =input-routed=, and =fact-posted=.
An =input-routed= event records the original message/posted sequence, the new =routed-seq=, frozen participant set, matching subscription ids, and pickup ids so replay can reconstruct pending delivery without mutating old log entries.
State-transition event families are =subscription-transition=, =activation-transition=, =effect-transition=, =delivery-transition=, =observation-changed=, =terminal-publication-changed=, =output-pending-changed=, and =activity-publication-changed=.
A subscription transition records id, old/new state, cursor/accumulator, firing count, and budget/lifetime changes.
An activation/effect transition records the stable activation/effect id, frozen source event ids, selector decision, immutable effect bytes, causal lineage, and old/new state.
A delivery transition records source kind/id, delivery id, old/new state, immutable logical envelope, replaceable physical attempt/generation, and receipt or tombstone delta.
Delivery transition names include =input-accepted=, =input-consumed=, =input-discarded=, =input-expired=, =input-overflowed=, and =input-uncertain= for board-message pickups.
Observation, output-pending, and activity-publication transitions carry their complete bounded replacement record.
Operation event types are =posted=, =progress=, =finished=, =failed=, and =cancelled=.
Board fault types include =subscription-fault=, =routing-cycle=, =routing-budget-exhausted=, and =terminal-publication-failed=; a fault never rewrites settled =e-work= state.
Lifecycle event types include =board-created=, =participant-added=, =participant-stale=, =participant-rebound=, =participant-removed=, =board-closing=, and =board-closed=.
Terminal events append in causal order.
High-frequency provider/reasoning/tool progress is coalesced before append into bounded versioned =activity= messages, not one board append per raw provider delta.
Every semantic update exposed to chat is nevertheless an accepted board message/event with its own =message-id=/=seq=; the runtime cannot bypass board publication with a client-only frame.
Every board mutation commits its typed transition event(s) and new projection version atomically; there is no mutable subscription, cursor, activation, effect, pickup, physical attempt, wake count, observation, output-pending, activity-publication, or open-activity state that exists only outside this contract.

The session activity log may remain the runtime's internal normalization/retry source, but board messages and the board's open-activity projection are the sole chat-facing replay source.
Spinner ticks and other redraw-only state are not semantic messages and remain local to the shell.

Compaction writes an atomic typed checkpoint at =checkpoint-seq= containing board lifecycle/identity, retained messages/tombstones including terminal activity summaries, memberships, source high-watermarks, work projections, terminal-publication outbox records, subscriptions/observer cursors/accumulators, frozen match sets, activation/effect attempts and receipts, causal lineages/publication budgets, exact-invocation receipts, pickup queues, delivery ledgers, wake counts, observations, output-pending/activity-publication records, current open-activity projections, and retention pins.
Replay starts from that checkpoint and applies the typed tail after =checkpoint-seq=; a no-checkpoint board starts from =board-created=.
Old entries can be removed only after the checkpoint is committed in registry state and unread cursors/pins no longer require their payloads.

** Subscriptions and continuation effects

The common work-start API can return a result to the current tool call and also request a later board post.

#+begin_src elisp
(start-work
 :wait-for 30
 :then (list :post-input
             :tags '(main)
             :mode 'queue
             :message "run the failing test and report what broke"))
#+end_src

The example describes the common argument shape; each tool keeps its own start function and normal arguments.
If the work finishes within =wait-for=, the current tool call receives the result.
The =post-input= effect is independent and may still publish later when requested.
For an identity-coupled follow-up, =:tags '(main)= becomes =:to "ptc_000004"=; these are two selector forms in one bus, not two delivery subsystems.

Observer subscriptions carry no declarative effect and never enter activation/effect settlement.
The core stores only three orchestration effect kinds at first:

- =reply-to-invocation= :: commit a frozen one-work or aggregate outcome to the exact open =(turn-id, tool-call-id)= invocation through the =e-loop=-owned result-append seam.
- =post-input= :: append one idempotent board =input= with =mode=, bounded content/reference, and either exact =to= routing or generic descriptive tags/attributes.
- =create-pickup= :: create/coalesce a pickup only for the participant that owns the matching input subscription.

There is no destination-specific callback form and no arbitrary continuation Elisp stored in board state.
A temporary =:notify= surface is compatibility sugar that compiles to a one-shot =post-input= subscription and is removed after callers migrate.
Ordinary in-process code may sequence its own local functions after starting or awaiting work, but any live cross-turn/cross-session consequence re-enters through one of these board effects.

A selector may conjunctively match record kind/activity-kind, exact work/message/author/=to=/=subject-participant-id= identity, terminal state, =tags-all=, =tags-any=, causal fields, and an optional ordinary predicate function.
Authorization/visibility filtering runs before a predicate can see private content.
A predicate must be bounded, non-blocking, and side-effect-free; if it signals, only that subscription becomes =faulted= and the source post plus other subscriptions continue.
Model-facing actions accept declarative selector clauses only, while trusted in-process code may supply a process-local predicate closure.

Each orchestration subscription has one immutable selector, readiness/accumulator policy, declarative effect, cursor, lifetime/firing/publication budgets, owning consumer, and provenance.
Each observer subscription has one immutable selector, board-sequence cursor, client owner/generation, buffer/history bounds, and provenance, but no readiness, activation, or effect.
Changing either subscription's matcher, or an orchestration subscription's effect, cancels and replaces it; the first process-local version needs no named/versioned predicate registry.
Compatible code reload leaves the installed predicate closure in place until its subscription is explicitly replaced or cancelled; it performs no automatic migration or reinstallation, and historical match decisions remain frozen.
The canonical readiness policies are =on-success=, =on-failure=, =on-terminal=, =all-terminal=, =first-terminal=, =batch=, and =latest-after-quiet= with the truth-table meanings above.
A one-shot subscription reaches =completed= only after its effect commits; a repeating subscription returns to =active= after each committed activation.

The combined work-start application service uses the two-phase =e-work= seam: prepare the canonical handle/work id; atomically enroll it, allocate its terminal outbox, install the applicable exact invocation and optional continuation subscriptions plus stable =e-work= publication observer, and append =posted=; only after that commit start the prepared runner.
The board transaction neither allocates a handle nor invokes/advances its runner, and =e-work= has no board dependency.
If that atomic setup fails, nothing board-visible committed: there is no operation, outbox, subscription, or terminal board event.
The start service fails the prepared handle locally and synchronously returns one =e-board-enrollment-error= through the existing =e-tools=/=e-loop= setup-failure path, closing the still-local invocation exactly once before it is handed off as pending; the external runner is never invoked.
This is a pre-start setup rejection, not a direct fallback after enrolled work settles.
This ordering is required because a cheap runner may settle before =e-work-start-prepared= returns.
After runner invocation begins, later board publication/subscription faults cannot change operation settlement.
Installing a subscription for already-terminal work checks the terminal snapshot in the same mutation and creates at most one activation without rescanning unrelated history.
That activation, including an immediate empty/already-ready =await= reply, is applied only after the subscription-installing stack unwinds.
Enrollment necessarily creates the invocation receipt slot, freezes its endpoint snapshot, installs subscriptions, and allocates the outbox before runner entry.
Effect application is scheduled after the initiating start stack unwinds: no tool-result append/invocation close, queue advancement, input delivery, or new provider turn occurs before =e-work-start-prepared= returns.

Settlement order is normative: settle =e-work=, append its terminal board event, freeze/commit matching activations in board sequence, then apply each idempotent effect.
If terminal publication fails after =e-work= settles, no direct callback fallback is allowed.
The board pins a visible =terminal-publication-pending= or =terminal-publication-failed= record until retry/reconciliation succeeds or terminates.

** Board/inbox state machine

Orchestration subscription matching/effect settlement, observer delivery, and participant pickup are separate state machines over one board sequence.
The board decides which message is deliverable at each observer cursor and which effect or pickup is ready; the harness alone decides whether participant input can still join the current turn.

*** Observer subscription and cursor states

An observer subscription is =active=, =muted=, =faulted=, =cancelled=, or =expired= and never has an activation/effect state.
Its =next-seq= is the first board message not yet classified as hidden/nonmatching or read through for that observer.
An active observer may buffer bounded matching message ids while a client snapshot is being returned; read-through advances only its cursor and never the message or any other consumer.
Mute/replacement/cancellation is client-local, and explicit =start-seq= controls retained backfill when a chat widens its selector to include a subagent.
A filtered-out board sequence creates an intentional cursor gap, not lost delivery.
If retained history or the live buffer can no longer continue from the read-through cursor, the observer becomes =expired= with =resnapshot-required=; it never falls back to a harness/session stream.

*** Subscription and activation states

The table governs orchestration subscriptions.
The registry-created exact-address subscription remains =active= while its participant membership is eligible and transitions only as part of detach/revoke/remove; ordinary mutation actions cannot mute, replace, or cancel it.

| Subscription state | Meaning | Allowed exits |
|--------------------+---------+---------------|
| =active= | Scans from =next-seq= and may accumulate/freeze one activation | =muted=, =completed=, =faulted=, =cancelled=, =expired= |
| =muted= | Classifies later records as ignored; resuming observes only future records unless explicit replay/reroute is requested | =active=, =cancelled=, =expired= |
| =completed= | A one-shot effect committed | Terminal |
| =faulted= | Selector, predicate, readiness, authorization, or deterministic effect preparation failed visibly | Terminal unless an administrator installs a replacement subscription |
| =cancelled= | Owner cancelled it | Terminal; watched work is unaffected |
| =expired= | Lifetime, firing count, or declared budget ended | Terminal with a visible reason |

One frozen firing has canonical =activation-id= =(board-id, subscription-id, firing-number)= and a stable derived =effect-id=; first/last/source sequence ids are immutable activation data, not identity components.
Only one activation is in flight per subscription, preserving event order.

| Activation/effect state | Meaning | Allowed exits |
|-------------------------+---------+---------------|
| =prepared= | Source event ids, match decision, effect id, exact effect target or routing destination, bounded bytes, and causal metadata are frozen | =applying=, =cancelled=, =failed= |
| =applying= | The idempotent effect call may be in flight; a parent mute/cancel request is recorded but cannot assume non-commit | =committed=, =cancelled= only after proven non-commit, =failed=, =uncertain= |
| =committed= | The invocation receipt, board append, or pickup creation/coalescing committed exactly once | Terminal; completes one-shot or reactivates repeating subscription |
| =failed= | A deterministic effect fault was recorded | Terminal |
| =uncertain= | The call may have committed but its receipt cannot be reconciled | Terminal; never repeated under a new identity |
| =cancelled= | Cancelled before effect commit | Terminal |

Without a concurrent parent-state request, =committed= moves a one-shot subscription to =completed= and a repeating subscription back to =active= at its committed cursor.
Mute/cancel while =prepared= cancels the activation immediately.
Mute/cancel while =applying= records the requested parent state and reconciles by =effect-id=: proven non-commit cancels the activation, committed effect remains committed but the repeating parent stays =muted= or =cancelled= instead of reactivating, and unknown commit becomes =uncertain= without retry.
A one-shot effect proven committed becomes =completed= and records a concurrent mute/cancel as too late rather than misreporting the side effect as cancelled.
An activation =failed= or unrequested =uncertain= faults its subscription so the one-in-flight slot cannot remain invisibly blocked; a cancellation-requested parent remains visibly =cancelled= with any uncertain child outcome attached.

For =reply-to-invocation=, preparation freezes the original participant id, attachment token, endpoint/turn generation, turn id, tool-call id, watched work id(s), effect id, and structured outcome.
The runtime calls a narrow generation-checked idempotent invocation service owned by the harness/=e-loop=; it preserves =e-tools= result shaping and returns a local receipt after appending/closing the invocation exactly once.
Lost acknowledgement is reconciled only against that original endpoint's receipt.
The same logical effect is never re-resolved into a replacement generation; if the old endpoint may have committed and cannot reconcile, the effect becomes =uncertain=.
Turn abort first terminally closes/fences the invocation receipt, then cancels its owned active work, so the resulting work cancellation event cannot append another tool result.

=next-seq= is the first board record not yet classified as ignored, accumulated, frozen into an activation, or accounted for by a terminal subscription fault.
The cursor advances only with that classification commit; retries use the frozen activation and never rerun a historical predicate or effect preparation.
Replay consumes recorded decisions/effect bytes and never evaluates historical closures again.

*** Selector routing and participant eligibility

Exact and condition-based routing share one matcher but intentionally have different cardinality:

| Posted input | Match result | Board result |
|--------------+--------------+--------------|
| Exact =to= participant (regardless of descriptive tags) | Zero or one built-in identity subscription; generic subscriptions are not evaluated | One pickup, or visible =target-unavailable= |
| No =to=; tags/attributes | Zero to many eligible condition subscriptions | Broadcast one pickup per matching participant, or visible =no-matching-subscription= |
| Several matching subscriptions owned by one participant | Many subscription matches | One participant pickup recording every matching subscription id |
| No continuation subscriber for a terminal work/fact event | Zero activation matches | Event remains visible; it is not an unrouted input |

Visibility/authorization is checked before optional predicates and before result content enters an effect payload.
The matching participant set is frozen against one immutable source snapshot.
Later subscriptions never receive earlier input implicitly; explicit =start-seq= replay or =route-message= is a new audited decision.

| Participant/subscription condition | Eligible now? | Result |
|------------------------------------+---------------+--------|
| Active participant and active matching subscription | Yes | Create pickup |
| Dormant/stale but still valid participant membership | Yes, bounded | Create pending pickup awaiting authorized rebind until cap/expiry |
| Detaching or revoked participant | No | Exact route fails visibly; tag route omits it |
| Muted, faulted, cancelled, completed, or expired ordinary subscription | No | No match; the membership-owned exact subscription is not mutable this way |

The publisher's =input= =mode= is authoritative; subscriptions do not carry a competing default mode.

*** Participant pickup states

| Pickup state | Meaning | Allowed exits |
|--------------+---------+---------------|
| =pending= | Immutable pickup waits at its FIFO position | =ready= at the head, =cancelled=, =expired=, =overflowed=, or =failed= |
| =ready= | Head pickup has one replaceable physical attempt selected and no harness call begun | =delivering=, =rebinding=, =cancelled=, =expired=, or =failed= |
| =rebinding= | The proven-uncommitted attempt was cleared; logical pickup is unchanged | =ready= with an authorized endpoint, =cancelled=, =expired=, or =failed= |
| =delivering= | Harness call is in flight with a committed attempt binding | =accepted=, =ready= for same-endpoint retry, =rebinding= only when no mutation is proven, =cancelling=, =failed=, or =uncertain= |
| =accepted= | Harness owns one deduplicated item not yet in a transcript | =consumed=, =cancelling=, or =discarded= with acknowledgement |
| =cancelling= | Cancellation races with acceptance/consumption | =cancelled= when unconsumed, =discarded= with acknowledgement, or =consumed= when transcript consumption won |
| =consumed= | Receipt maps the pickup to exactly one transcript entry | Terminal; releases the FIFO |
| =discarded= | Harness acknowledged that the accepted item cannot be consumed | Terminal; releases the FIFO |
| =failed= | Permanent rejection or exhausted retry happened before acceptance | Terminal; releases the FIFO with a visible fault |
| =uncertain= | Endpoint vanished after possible commit and receipt cannot be reconciled | Terminal; records an ordering-gap tombstone and releases the FIFO |
| =cancelled= | Cancellation completed before consumption | Terminal; releases the FIFO with a dedupe tombstone |
| =expired= | Lifetime ended before acceptance | Terminal; releases the FIFO with a visible reason |
| =overflowed= | Bounded pending capacity refused this pickup | Terminal tombstone; never attempted |

The normative pickup id is =(board-id, message-id, participant-id)=; every retry reuses that id and immutable message bytes.
A denied participant creates no pickup.
A stale endpoint discovered before any harness call may wait for authorized rebind with the same id; revocation is permanent.
The immutable envelope stores the board participant and bytes, while each physical attempt stores endpoint token/generation separately.
Only a proven-uncommitted attempt may clear that binding and enter =rebinding=; an unknown commit becomes =uncertain= instead.

Cancelling in =pending=, =ready=, or =rebinding= is immediate.
Cancelling in =delivering= or =accepted= reconciles by the same =delivery-id=: an unconsumed item may become =cancelled= and leaves a receipt tombstone, while a consumed item wins.
Cancellation never retracts a transcript message or starts a duplicate compensating turn.
Cancelling a subscription or pickup never cancels watched work; cancelling work only emits its terminal =cancelled= event.

Board-message pickup content and participants are authorized/frozen at post/routing time.
The head pickup for a participant moves from FIFO =pending= to =ready= with its normative id and then follows the pickup table; later pickups remain =pending= until the head reaches any terminal pickup state.
Later pickups cannot overtake a head in =ready=, =rebinding=, =delivering=, =accepted=, or =cancelling=.
Every terminal state in the pickup table releases the FIFO; =uncertain= does so only after recording its visible ordering-gap tombstone, so later input can proceed without concealing the unknown outcome.

*** Harness delivery phases

"Running" is not a sufficient state.
Only =accepting= means the active turn still has a future provider-request boundary at which steering can be consumed.

| Harness/session phase | =inject= | =queue= |
|-----------------------+----------+---------|
| =idle= | Commit an inbox item and schedule its turn immediately | Commit an inbox item and schedule the same single idle drain |
| =accepting= | Commit pending steering for the next safe provider boundary | Commit an inbox item for a later turn |
| =settling= | Commit an inbox item for the next turn; never steer | Same |
| =retry-wait= | Commit an inbox item for the next turn; never mutate the already-built retry | Same |
| =aborting= | Commit to the post-abort inbox and start only after abort cleanup | Same |
| =resetting= | Return a retryable transition with no receipt or input mutation; retry the same id after reset | Same |
| generation changed before mutation | Return a retryable stale result with no receipt; board runtime re-resolves/reconciles | Same |
| =closed=, revoked, or mismatched board | Permanent rejection with no input mutation | Same |

Every immutable logical delivery envelope stores =delivery-id=, =board-id=, target =participant-id=, message id, matched subscription ids, event sequence range, mode, requester actor, and cause metadata, but no endpoint token or generation.
Its replaceable physical-attempt record alone stores the selected endpoint token/composite generation.
After acceptance, the concrete inbox/steering item and receipt store that accepted generation together with the logical fields.
=e-harness-deliver-input= deduplicates on =delivery-id= inside the same mutation and returns the prior receipt on retry.
It rejects a board id that differs from the session attachment before selecting a lane; a mismatched delivery cannot wait inside or mutate that session.
Receipt state is monotonic: =accepted= means the harness owns the item, =consumed= means it appears in exactly one turn transcript, and =discarded= records an explicit reset/close/cancellation boundary without permitting reinsertion.
The board-owned delivery ledger is authoritative across endpoint generations; the harness ledger is the local index that proves one concrete inbox/transcript mutation.
Before calling a harness, the board record commits the attempted physical endpoint and generation.
Rebind/close/detach must fence that endpoint and reconcile every =accepted= delivery to =consumed= or =discarded= before publishing a replacement or closing.
If a call may have committed but the old endpoint cannot return a receipt, the delivery becomes visible terminal =uncertain= and is never submitted to a new generation.
Only a delivery proven never submitted may wait for rebind and use the same id on the replacement endpoint.

Accepted receipts/items are pinned regardless of age until consumed, discarded, or uncertain.
Terminal harness receipt tombstones remain at least through the board's retry/cancellation lifetime; if a hard dedupe limit would be exceeded, the runtime refuses the old id visibly rather than treating it as new.
Board observer delivery/render failures are isolated after mutation and cannot turn a committed message or pickup delivery into an apparent failure or retry its producer publication.

An idle delivery starts at most one turn even when several callers retry.
The transition from =accepting= to =settling= sweeps unconsumed steering items to the inbox before the final same-turn boundary disappears.
The turn's first user message stores =:board-id= and =:caused-by= metadata; the turn work projection mirrors it in memory.
This is the first-version turn-cause representation, rather than inventing a separate durable turn record.

*** Observation and retention

The current-state view is a projection independent of retained event history.
Each terminal work record keeps a bounded stable snapshot containing state, kind, poster, terminal sequence, intent summary, and either a usable result reference or an explicit expired-result tombstone.
Active work is never evicted.

A prepared/applying effect and pending/delivering/accepted pickup pin their bounded snapshots or receipt ownership until terminal.
Terminal =turn-summary= activity remains retained with ordinary conversation history; superseded intermediate activity may compact after terminal summary and bounded observer lag permits it, while the current open-activity projection preserves the latest reconnect state.
Observer lag is bounded and eventually requires resnapshot rather than pinning progress history indefinitely.
Log compaction may replace payloads with tombstones but may not silently skip a retained unread cursor or invalidate a result reference.
Inline tool-result delivery, successful =await=, and consumption of a derived board post mark the corresponding participant as having observed the terminal work.
Resource reads do not mutate observation implicitly; an explicit action may mark work observed.
Terminal work with no waiting invocation or continuation subscription remains visible in current state.
When its board next becomes idle, the UI emits at most one warning for the newly unobserved terminal set; refreshes do not repeat that warning unless new unobserved terminal work appears, and the warning never synthesizes participant input.

All retention, tombstone, retry, subscriber-count, reconnect, idle-expiry, propagation, wake, batching, and participant bounds are explicit configuration.
The first implementation uses conservative deterministic-test defaults; Slice 6 tunes production values from measured sessions without changing the contracts.

** Choosing readiness and post content

Built-in readiness policies decide when a subscription freezes an activation without a model call.
The common one-work policy reacts when that work finishes, fails, or is cancelled.
Other policies can wait for all watched work, choose the first terminal member, batch matches, or retain only the latest match until a quiet period.
Declarative effect data can include a bounded summary or only ids/states/result references.

The first implementation ships only built-in readiness policies and declarative effects.
Trusted in-process matchers may use an ordinary predicate closure under the non-blocking/side-effect-free contract; model-authored arbitrary Elisp effects are excluded.
A readiness, predicate, or effect-preparation error faults only the subscription and records =subscription-fault=.
The runtime never silently chooses another selector, policy, target, or effect.

** Applying continuation effects

An exact =reply-to-invocation= effect commits through the =e-loop=-owned result seam using an idempotent invocation receipt.
If timeout/detach already closed that invocation, the effect records the closed outcome and never appends a late second tool result.
Slice 2 extracts that currently lexical finish path into the private generation-checked invocation service; the board never appends transcript entries or advances the tool queue itself.

A =post-input= effect succeeds when its stable =source-input-key= appends the board input.
Its success is independent of whether that input matches zero, one, or many participant subscriptions and independent of later pickup/consumption.
Exact =to= and descriptive tags are data on that same post.
Each matching =create-pickup= effect commits when the board creates or coalesces that participant's stable pickup; physical delivery settles separately.
Participant routing then calls =e-harness-deliver-input= through the pickup machine: =inject= joins only an =accepting= turn at its next safe point, while =queue= waits for an idle turn.
The board router does not create/fork/spawn a session as a side effect of zero matches.

Delivery to a session outside the board is refused and recorded as a fault.
Every delivery records which subscription/effect and requester caused it.

** The causal graph is a projection, not a second executor

Routing makes the dynamic graph implicit in who subscribes, so every causal edge must be recoverable from the board log:

#+begin_example
source event -> subscription activation -> effect -> invocation receipt -> transcript tool-result entry
                                                \-> derived post -> subscription activation
                                                                  -> effect -> pickup
                                                                               -> consumed turn
                                                                               -> caused work
                                                                               -> terminal event
                                                \-> pickup -> consumed turn -> caused work
#+end_example

Derived posts carry parent event ids, =subscription-id=, =activation-id=/=effect-id=, =root-cause-id=, hop count, bounded lineage, and remaining publication budget; an exact reply or pickup does not spend the derived-post budget.
Turns record the pickups they consumed; work records the turn/activation that caused it.
The board current-state/resource view materializes this projection for inspection, without adding runnable graph nodes or callback edges to =e-work=.

An uninterrupted router-only lineage records a deterministic cycle key over =subscription-id= and the canonical frozen effect declaration: effect kind, exact destination or sorted tags, mode, and static template fields, explicitly excluding dynamic event ids/result bytes.
The key is stored on the activation/derived post and in checkpoints.
Repeating it before any consumed turn, newly caused work, or external root records =routing-cycle= and suppresses the derived post; those boundaries start a new router-only segment in which reuse of the same subscription remains valid.
If the hard publication budget reaches zero, the board records =routing-budget-exhausted= regardless of cycle detection.
These limits bound causal propagation; the separate wake budget bounds provider turns and cost.

** Consumption: broadcast facts and claimable offers

Two classes, no broker vocabulary:

- *Broadcast facts.*  A lifecycle/message event is a fact on the board sequence.
  Every matching orchestration subscription may activate and every matching observer may expose it independently; the fact itself is never consumed.
  Chat observer delivery is this class: every matching client may see the same =input=/=activity=/=output= and only its private cursor advances.
  Everything implemented by this feature is this.
- *Claimable offers.*  A work package posted with no executor, claimed by exactly one consumer.
  This is a distinct hand-off state machine and is follow-up work, not part of this plan's implementation slices.

No exchange types, competing-consumer claims, ack/nack protocol, provider redelivery, or dead-letter queues.

** Turn cause

Every consumed board input stores =:board-id=, =:participant-id=, accepted endpoint generation, =:delivery-id=, and its typed cause on that transcript message.
A chat pickup cause is =(:message-id M :posted-seq S :subscription-ids [...])=; a derived-post cause adds =:activation-id=, =:effect-id=, and source =:event-seqs=.
The active turn work metadata accumulates the ordered delivery/message causes consumed since the preceding assistant response, rather than retaining only the turn's first cause.
The idempotent board output copies that ordered set into =reply-to-message-ids= and =caused-by-delivery-ids=.
Shells show it; the session resource exposes it.

** The one-call shortcut stays

=bash {command, wait_for: 30}= still costs one tool call and one model round trip.
Before starting the runner, the open invocation installs an exact one-shot subscription over its turn id, tool-call id, and canonical work id.
If work finishes within 30 seconds, the invocation receives that result and =e-loop= appends it once.
The board records the completion and the exact subscription effect commits the invocation result; no participant message or =main= tag is involved.
If the deadline wins, the invocation receives =work:<id>= and stops waiting for an inline result.
A later completion remains visible in the board current-state view and reaches a session only when an explicit =post-input= continuation matches one.
=wait_for: 0= returns the detached reference immediately.

Small work must never cost two tool calls.
Use =:then (:post-input ...)= for work meant to cause a later turn; =:notify= is temporary compatibility sugar only.

* The scope above sessions

The board is the top-level live interaction model.
It owns the message stream, event sequence, observed work, subscriptions/activations/effects, propagation and wake budgets, authorized clients, and the participant set through which sessions interact.
A live session is attached to exactly one active board through exactly one participant record; there are no standalone or multi-board live sessions and no turn or input without that board id.
Harnesses remain execution hosts for session state, turns, providers, and transcripts, but they do not define the outer interaction scope.

Stored session history may be dormant without a live runtime attachment.
Loading or reading a persisted session does not make it live.
The board runtime owns an explicit attachment record whose state is =active=, =detaching=, or =dormant=; accepting inbox input, holding an active turn, or being addressable as a delivery endpoint requires =active= attachment and membership.
Creating, resuming, forking, or spawning a live session must create its board attachment atomically before that session can accept input.
Removing or moving that attachment first enters =detaching=, rejects new input, and fences or drains its active turn, inbox items, and receipts before making the session dormant or atomically attaching it to the replacement board.
Durable transcript history is never deleted merely because the live attachment becomes dormant.

Recommendation: *board*.
It is plain, unused in the codebase, and names the shared interaction place without transport vocabulary: clients post messages, sessions pick them up, and executable work remains visible there.
Sessions participate in a board; =board://<board-id>/= is the top-level resource; a work package and every live turn belong to a board.
Alternatives considered: =arena= (collides with allocator jargon), =commons= (vaguer about what it holds), =ensemble= (names the participants, not the shared state).

** Board identity contract

A =board-id= is an opaque, collision-resistant id with a recognizable =brd_= prefix, generated from a neutral ULID/UUID service.
It is never copied from, defaulted to, or treated as an alias for a session or harness id.
The id generator is injectable for deterministic tests, and the registry collision-checks every generated id before publication.
Production generation makes cross-restart collision probability negligible and never intentionally reuses an id; live/retained collisions are rejected.
Durable metadata may retain a historical board id even though the process-local board no longer exists, and lookup of an absent historical id fails rather than manufacturing or aliasing a board.
Board clients and session participants receive separate board-local =cli_= and =ptc_= ids from the same injectable service.
Both are opaque, collision-checked, never aliases for a session id, and unique within their board.
A participant id is stable across an authorized endpoint rebind; a client id identifies one shell connection attachment and may change on reconnect.
A stable trusted =principal-id= (local user/profile in the first version) owns client authorization independently of any connection lifetime.
It is issued by the host identity adapter in its own namespace and is never accepted from an untrusted client payload or generated by the board from a display name.

A board event is identified by =(board-id, seq)=, where =seq= is monotonic and never reused within that board.
A subscription is identified by =(board-id, subscription-id)=.
An activation is identified by =(board-id, subscription-id, firing-number)=; its effect id is stable across retries.
A board client is identified by =(board-id, client-id, connection-generation)= and maps to an authenticated =principal-id=; it is not a session.
A participant is identified by =(board-id, participant-id)=; its registry record has a stable posting epoch and maps to a stable =session-attachment-key= plus the current =instance-id=, =harness-id=, opaque composite generation, and delivery =endpoint-token=.
The posting epoch survives authorized endpoint rebind while the composite delivery generation does not.
=instance-id= is the logical catalog id from =e-harness-instances=, while =harness-id= is the concrete =e-harness-registry= key selected by that instance.
The composite generation is =(instance-catalog-generation, harness-object-generation)=.
=session-attachment-key= is =(session-store-id, session-id)=; =session-store-id= is an opaque stable identity owned by/configured with the session store and shared by every harness exposing that store.
The generation-specific endpoint token is based on =(harness-id, harness-object-generation, session-attachment-key)= and is used only for delivery/reconciliation.
Raw session ids are therefore never sufficient cross-harness destination identities.
The registry reverse index permits at most one active board participant record for a stable session attachment key across all boards, so two harness objects over the same store/session and later replacement generations cannot attach it twice.

An exact participant selector stores only the board-local =participant-id= inside an already-resolved board and never triggers a global session search; external resources use =board://<board-id>/participants/<participant-id>=.
A qualified =session:<instance-id>/<session-id>= reference is accepted only by explicit participant add/resume operations and is normalized to a participant before any subscription is installed.
Fork/spawn is an explicit session-management operation that first creates and attaches a participant; it is never a selector destination or a zero-match routing fallback.

** Process-level board registry

=e-board-registry= is the process-level authority for board identity and lifetime.
It maps each =board-id= to one entry containing the board core, lifecycle state, principal grants, client attachments, participant/grant records, runtime-adapter generation, timestamps, and retention pins.
Board state is not owned by a root session, by one harness instance, or by a dynamic variable.

The registry exposes narrow application operations: =create=, =get=, =list=, =authorize-principal=, =revoke-principal=, =attach-client=, =detach-client=, =add-participant=, =remove-participant=, =move-participant=, =rebind-participant=, =grant-participant-access=, =revoke-participant-access=, =install-subscription=, =mute-subscription=, =resume-subscription=, =cancel-subscription=, and =close=.
Subscription mutation operations reject the membership-owned exact-address subscription; participant detach/revoke/remove owns its lifecycle.
Board creation is a host/runtime operation with an authenticated owner principal; it publishes a valid top-level board and may have no session participants.
A convenience operation may atomically create its first participant and that participant's =main= tag subscription too, but a participant failure leaves either the already-valid board or rolls the whole request back according to the caller's explicit transaction; it never exposes a standalone live session.
Session create/resume/fork/subagent paths always register participant membership before making the session live.
They use a prepare/commit attachment boundary; if current session storage has already persisted a new record when attachment fails, that record remains explicitly dormant and is never published as a live endpoint.

The pure registry stores ids and board state but does not require =e-harness=.
=e-board-runtime= is the composition adapter: it supplies qualified session lookup, create/close/rebind, input delivery, fork, clock, and scheduler ports backed by harness services.
It is composed only after the board registry and harness registry exist, keeping the board core independent of the concrete session runtime.

Configured =e-harness-instance= records gain a stable =session-store-id=, a read-only =session-catalog= port, and a narrow optimistic =session-access-store= mutation port, all usable without invoking the harness factory.
The catalog lists/reads dormant session summaries and access records; the access-store port supports only expected-version create/legacy-migrate/grant/revoke/transfer operations on those records and exposes no transcript or live-session mutation.
Several instances may expose the same store.
Registrations that share a =session-store-id= must expose compatible catalog/access-store identities or are rejected; the host catalog deduplicates them and returns each dormant =(session-store-id, session-id)= once with its explicit =eligible-instance-ids=.
Each session access record contains a durable controlling principal, discover/resume principal ACLs, and an optimistic version; resume implies discovery.
New-session creation stores it atomically with the session metadata.
The controller may grant/revoke discover/resume access, and may transfer control only while the session is dormant through an expected-version store operation; transfer revokes the old controller's implicit rights and never silently rewrites board-local private grants.
Resume names one eligible instance and the destination board; ownership/resume authorization, dormant state, access-record version, store identity, and instance eligibility are checked before any factory invocation, after which the activation service may invoke only that instance's factory and atomically attach the session.
Catalog reads themselves never call =get-or-create=, and rejected direct resume calls create no harness, grant, or attachment even when the caller supplies a hidden/stale session id.
Instances without the required catalog/access-store ports do not participate in dormant discovery/resume, and target lookup never substitutes catalog activation for an absent live endpoint.

*** Clients, participants, and authorization

Every authorized principal or participant membership has an =owner= or =member= role.
Client attachments inherit their authenticated principal's role and carry a connection generation/state.
Participant records additionally have a controlling principal, private =inspect-transcript= /=control-session= grants, an endpoint generation, attachment state =active=/=detaching=/=stale=/=dormant=/=revoked=, a set of owned subscription ids including the built-in exact-address subscription, and a =message-next-seq= cursor.
The creating principal/requester is an owner; a board may have several principal or participant owners.

- Owners may authorize/revoke principals, add or remove participants, issue cross-participant posting/control grants, rebind a stale endpoint after an intentional harness replacement, and close the board.
- Client members may post/read board messages and board-visible state, including sanitized =activity=, but never receive session input or read/control participant-private state solely from board membership.
- Participant members may post/read board-visible work and create/manage their own subscriptions.
- Exact =to= posting to another participant requires owner authority or an explicit grant stored on the target participant.
- A generic board-visible tag post needs no per-target grant: each receiving participant opted in through its own subscription, while ordinary board visibility still limits what the post/effect may disclose.
- Tags and selectors choose among already-authorized board records; they never grant visibility.
- Session-private work is visible to its poster only; a cross-participant post or a shared tag is not an implicit visibility grant.
- A participant subscription expresses routing interest but grants no new data or control authority; visibility and target freshness are checked before selector predicates or effect payloads read result content.

For a new session, the creating principal becomes its controlling principal and that identity is persisted in session metadata by the store.
Resume reads the existing controller through the trusted catalog port and requires that controller or an explicit catalog authorization; the resuming caller never replaces ownership merely by naming a dormant session id.
The participant record copies that controller and initially grants it both private rights for the new board attachment.
That controller may grant/revoke them for other principals; board ownership alone permits detach/close but does not reveal the transcript or confer session control.
=inspect-transcript= permits bounded transcript reads, and =control-session= permits rename, model, reasoning effort, output mode, compact, abort, and reset through generation-checked runtime operations.
Sanitized activity is board-visible by default and is authorized before publication; anything that cannot be exposed to ordinary authorized board readers is not posted and remains behind transcript/control boundaries.
Revoking a private grant fences new reads/calls immediately; revoking board/client read access closes that client's observer subscriptions before their next delivery, without removing already-committed board records or rolling back a control mutation.
Board-local private grants expire with the participant/board; the durable controller does not.
Legacy dormant sessions receive a synthesized access record only through the trusted local migration policy of their configured catalog, never from a client-supplied owner id.
Listing remains read-only; the first authorized explicit resume persists that access record before any harness factory runs.

The requester identity comes from a generation-checked authenticated client/principal context or participant attachment token and is never accepted as an arbitrary model-supplied id.
The board id is an address, not a credential.

Subagent, fork, and resumed-session creation use these same registry operations.
"Joins the parent's board by default" means that the spawning application service explicitly creates membership and grants as part of its transaction; it is not hidden inheritance in =e-session=.
An agent-originated child/fork inherits the source participant's controlling principal as part of that explicit transaction; it does not inherit arbitrary third-party private grants.

*** Registry and board lifecycle

| State | Accepts | Rejects | Exit condition |
|-------+---------+---------+----------------|
| =active= | Clients, participants, messages, work enrollment, events, subscriptions, activations, effects, and delivery | Stale-generation endpoints | Explicit owner close or process shutdown |
| =closing= | Receipts, activity/summary/output and terminal events causally rooted in admitted pre-close turns/work, pre-existing subscriptions matching those roots, plus retry/frozen effects/causally rooted pickup delivery+wakes/descendant-work enrollment | New clients, participants, unrelated root input/work, new subscriptions, unrelated wakes, and ordinary input | Every accepted delivery/effect/publication is reconciled and pre-close roots settle, or the close deadline aborts their board-bound turns and ends observation |
| =closed= | Bounded diagnostic tombstone reads | All mutation and delivery | Registry removes the entry after the tombstone retention window |

A board may outlive every client connection and participant session because owner grants belong to stable principals; it may temporarily have neither kind of live attachment.
An empty active board remains reconnectable by an authorized principal and is subject to a bounded idle-expiry policy rather than silent immediate destruction.
Explicit close immediately expires unrelated pending pickups/subscriptions/activations with a visible reason, stops ordinary wake/delivery timers, fences new unrelated delivery, and reconciles already-applying effects.
Subscriptions installed before =board-closing= remain eligible only for activity/output/terminal/descendant records causally rooted in turns/work admitted before close, so existing chat observers, exact invocation replies, and declared continuations are not truncated merely by entering =closing=.
Any =post-input= /=create-pickup= effect admitted by that rule may deliver and wake a participant under the same preserved root/budgets; it cannot admit an unrelated new root.
Work observers for roots enrolled before close remain attached until those roots settle or the close deadline ends work observation.
It does not cancel domain work by default; force-cancelling work is a separate authorized operation.
Operation start context therefore carries =root-work-id= into every retry and child operation.
During =closing=, only descendants, matches of preserved pre-close subscriptions, or already-frozen effects of roots enrolled before =board-closing= may enroll/post, which lets an already-running causal chain settle without admitting unrelated work.
The configured close deadline prevents nonterminating observed work from blocking forever: at the deadline the runtime aborts remaining board-bound participant turns, records =observation-ended= tombstones, and detaches their work observers.
At that deadline any still-preserved subscription/activation and any unaccepted causal pickup expire visibly before final reconciliation.
Already-started detached/domain work is not cancelled by that abort and may finish unobserved; force-cancelling it remains a separate operation.
A board cannot become =closed= while any accepted delivery is unresolved; each must become consumed, discarded with harness acknowledgement, or uncertain if its old endpoint vanished.

The first version is process-local and is not restored across Emacs restarts.
A dormant persisted session becomes live only by joining a newly created or explicitly selected live board.
Within one process, compatible code reload keeps board registry state.
=e-harness-instances= owns a monotonic generation for logical instance-to-harness mapping; =e-harness-registry= owns a separate monotonic generation for each concrete live harness object.
Re-registering the identical startup mapping/object or synchronizing metadata in place preserves the relevant generation, while remap, replacement, or clear bumps it and emits synchronous invalidation.
The board registry stores only the composite snapshot; =e-board-runtime= resolves and compares it.
Board timers and callbacks also carry a board-runtime generation; reload installs one fresh scheduler/subscription set and old-generation callbacks become no-ops.
Target resolution uses a non-creating live lookup and never calls a lazy get-or-create path for a missing harness or session.
Invalidation moves the attachment through =stale= /=detaching=, fences new ingress, and reconciles active turns/inbox receipts.
Explicit authorized rebind captures the new endpoint generation only after quiescence; there is no immediate silent takeover of a still-live old endpoint.

** Board binding and session invariants

Every ingress message/fact, turn, work enrollment, action context, and logical delivery carries =board-id=; participant-bound records also carry =participant-id=.
Only a physical delivery attempt and the accepted inbox/turn/action state copied from it carry an endpoint-generation snapshot; the logical envelope remains generation-free across a proven-uncommitted rebind.
The caused turn uses that board for dynamic context and for unqualified work references, and the runtime revalidates that it matches the session's sole active attachment.
The board runtime is the only public activation/prompt service.
On attach it installs an opaque attachment token in the harness's runtime attachment map; private harness start/delivery methods require that token and copy board, participant, and composite generation into the active entry, tool/action context, first message, and work projection.
=e-harness= validates the supplied token locally and never depends on or looks up the board registry.
=board://<board-id>/...= and board actions accept an explicit board id.
A participant turn/action may omit it because its attachment is unique; a client action may omit it only when its connection context names one board.
There is no creation-order fallback.

A live session cannot participate in several boards because that would splice independent board threads into one transcript.
Moving a dormant session, or atomically detaching and reattaching a quiescent live session, changes the binding for future turns without rewriting historical turn causes.
The transcript records the board id on every first user message and turn work metadata.
Chat shells open a board, post messages with tags (default =main=) or an explicit exact participant, and render the =input=/=activity=/=output= messages matched by their non-consuming observer subscription rather than binding either direction to one session.
The ordinary bootstrap atomically creates the first participant with a subscription matching =main=; adding another =main= subscriber intentionally broadcasts later chat posts to both.
Chat does not select a root/session by creation order and does not normally name the agent that should pick up work.
Diagnostic/session shells may select a participant transcript inside that board, but cannot prompt it outside board ingress.

Legacy APIs that create or prompt sessions directly are temporary adapters.
They require an explicit board, use an already-live session's sole attachment, or atomically create a new board for the authenticated caller; they never select by creation order.
They route input through board ingress during migration, then are removed once every shell and internal caller uses the top-level board path.

Scope rules follow from membership: =session=-scoped work is visible only to its poster, =board=-scoped work to every participant.
Cross-board delivery to a session is not a thing.
Use a distinct/forked session on the destination board, or an explicitly authorized application service that posts a bounded summary as a new destination-board message.

* Surface

Following the project's action/tool split, cheap synchronous operations are capability actions from =run_elisp=, while only operations that must hold a model turn open are tools.

- Existing tools remain the way to start executable operations.
  Their registration converges on one =:work= contract, =wait_for= chooses an inline result or a detached reference, and =:then (:post-input ...)= requests a later board post; =:notify= is migration sugar.
- =await= remains the model-facing join over work references through one narrow subscription-backed invocation contract; because it executes no carrier, it intentionally creates no dummy =e-work= handle.
- Participant turns use the =board= capability actions =close=, =principals=, =authorize-principal=, =revoke-principal=, =add-participant=, =remove-participant=, =move-participant=, =rebind-participant=, =post-message=, =route-message=, =messages=, =install-subscription=, =mute-subscription=, =resume-subscription=, =cancel-subscription=, =subscriptions=, =activations=, =events=, =mark-observed=, and =post-fact= on their sole board.
  Membership-changing actions enforce registry roles; there is no unauthenticated self-service =join=.
- Chat has no harness/action context, so =e-chat= calls authenticated =e-board-runtime= host APIs rather than keeping a harness endpoint.
  The board API covers create/list/open/close, principal administration, client attach/detach, message post/read, and board subscriptions.
  A session-catalog API lists principal-owned/granted dormant sessions from configured store ports without activating them, manages controller-owned discover/resume ACLs and dormant ownership transfer, and explicitly resumes/attaches one through a named eligible instance as a participant in the selected board; reading the catalog never lazily creates a live harness/session.
  Board-scoped participant-control APIs preserve rename, model/reasoning-effort selection, output mode, compact, abort, reset, fork/spawn, and transcript inspection for an authorized selected participant.
  The board observation API returns a selector-filtered snapshot/cursor and live continuation in board sequence; it exposes neither a harness object nor an input path, and thinking/progress/turn-summary activity reaches chat only after ordinary board publication.
  These surfaces enforce board visibility plus the participant's remaining controller/private grants, delegate to the same registry/application services and trusted actor contract, and never tunnel client identity through =e-actions-call=.
- The first slices expose built-in selector clauses, readiness policies, and declarative continuation effects; trusted in-process callers may additionally install an ordinary bounded predicate closure.
- Resource =board://<board-id>/= exposes lifecycle, messages, outstanding work, recent terminal snapshots, events, subscriptions, activations/effects, causal projections, clients, participants, grants, budgets, and per-operation detail.
- A compact dynamic-context segment shows only ids, states, counts, and bounded summaries for the current participant's attached board, outstanding work, and live subscriptions/effects; full events and results stay behind =board://<board-id>/...= resource reads.
- Chat/application entry points create or open a board first and post board messages; session-management entry points create/select participants inside that board.

Model-facing tool count does not grow.

* Ownership and dependency direction

- =lisp/core/e-id.el= owns neutral opaque ULID/UUID generation for board, client, participant, and subscription ids; it has no session, harness, or board dependency.
- =lisp/core/e-work.el= owns executable identity, lifecycle, result/progress, and cancellation only.
  It exposes prepared/start-prepared plus an injected dedicated publication-observer slot, but has no knowledge of boards, sessions, tools, turns, task queue, or subagents.
- Application services own local business sequencing and failure policy; live consequences are expressed by posting/matching on the board rather than by a second =e-work= callback graph.
  They pass an explicit =e-work= publication observer through start context instead of installing a process-global work hook.
- =lisp/core/e-board.el= owns board messages including activity/turn summaries, the event log, current/open-activity views, selector/orchestration/observer subscription reducers, observer read positions, readiness/activation/effect state, causal projection, pickup state, propagation budgets, and wake limits.
  The board core stores ids and depends on =e-work= only for observed operation state.
- =lisp/core/e-board-registry.el= owns generated board/client/participant identity, principal/participant roles and grants, client/participant attachments, lifecycle, endpoint-generation snapshots, and board lookup.
  It depends on board core and injected ports, not on =e-harness=.
- =lisp/core/e-board-runtime.el= is the application/composition adapter.
  It binds the registry to non-creating harness lookup, explicit dormant-session catalog/resume, authenticated participant controls, normalized/sanitized idempotent participant-activity publication, runtime attachment records, atomic live-session attach/detach/move, stable operation/output/activity-publication trampolines/outbox drains, timers, wake scheduling, waiting-invocation and =post-input= effect adapters, explicit forks/spawns, and input delivery.
- =e-harness-instances= retains the logical instance catalog, stable session-store/catalog/access-store ports, eligible-instance mapping, and mapping generation, while =e-harness-registry= retains concrete harness objects and object generations plus replacement/clear invalidation events.
- =e-session= owns session names, transcript/activity-entry schema, stable durable activity-entry ids, and atomically assigns/persists monotonic =board-output-seq= and =board-activity-seq= publication counters/entry fields; legacy entries remain valid without them and are not retroactively published.

* Non-goals

- No general broker semantics beyond exact/tag/condition selectors: no exchanges, wildcard routing language, competing consumers, claim leases, ack/nack protocol, provider redelivery, or dead-letter queues.
  Stable in-process delivery receipts exist only to make board-to-harness mutation idempotent.
- No durable board across Emacs restarts in the first slices.
- No standalone or multi-board live session; dormant persisted session history is activated in exactly one board at a time.
- No claimable-offer or lease state machine in this feature; agent-to-agent claiming is follow-up work after broadcast delivery is proven.
- No automatic participant creation, routing-triggered fork/spawn, or general autospawn when a generic selector matches nobody; zero matches remain visibly unrouted.
- No =e-work= execution/callback graph beside the board bus; =e-work= settles executable lifecycle and the board records/routs every live consequence.
- No concurrent tool-call execution in =e-loop=.
  Concurrency comes from detached work; sequential tool slots are what keep the transcript readable.
- No context merging.
  A fork reports back only through an explicit exact-or-tagged board input.
- No migration of synchronous local policy-hook sequencing merely to route it through the board.
- No replacement for =await=.
  Inline joining stays a tool.
- No board enrollment for rendering-local =e-ui-work=, spinner timer ticks, focus, expansion, or selection state.
- No board append per raw provider token/delta; bounded semantic activity is coalesced before publication, while every intermittent update actually exposed to chat is a board message and cannot create a pickup or wake.
- No private participant-presentation side channel or chat replay from session activity.
- No cross-machine or multi-process board.

* Validation

The board must be testable with no provider and no UI.

Pure-function level:

- identity :: table-drive every identity row and prove that principal/client, board, participant, message, event, turn, invocation, work, subscription, activation/effect, pickup, and domain ids never substitute for one another.
- source keys :: per-kind producer generations and increasing sequences advance atomically with message append; every activity uses a monotonic =board-activity-seq= tuple key while durable activity-entry id or live stream/version remains separate =source-event-id= correlation, a retained retry returns its existing message, a compacted/late retry returns =source-history-expired=, and neither path appends or advances a pickup/observer cursor twice; participant activity/summary/output requires its producing =source-turn-id= plus frozen tags/originating attachment tuple, output additionally requires the completion-selected final-entry marker, and duplicate callbacks reuse the same source identity.
- selectors :: exact =to=/author/subject/work/invocation identity, tag-all/tag-any, kind/activity-kind/state/causal fields, and combined conditions match deterministic immutable snapshots with declared zero/one/many cardinality.
- predicates :: authorization/visibility runs first; a bounded ordinary closure may refine trusted in-process matching; a signalling predicate faults only its subscription and cannot suppress the source record or other matches.
- API trust boundary :: model-facing subscription actions reject predicate closures and unknown/arbitrary Elisp effects; trusted in-process callers may install an ordinary predicate, and only the three declared effect kinds validate.
- readiness :: =on-success=, =on-failure=, =on-terminal=, =all-terminal=, =first-terminal=, =batch=, and =latest-after-quiet= produce deterministic frozen source sets, ordered accumulators, and timer decisions.
- effects :: fixed activation input yields stable =reply-to-invocation=, =post-input=, or owner-only =create-pickup= bytes/keys independent of the participant that may later pick up a tag-routed post.
- reducers :: board/orchestration-subscription/observer/activation/effect/pickup/receipt/cursor/open-activity/pin/tombstone transitions use injected ids, clock, and scheduler; checkpoint-plus-tail cuts at every nonterminal state reproduce the same projection and next transition without rerunning closures/effect preparation.

Bus selector, readiness, and effect level:

- subscription lifecycle :: orchestration install, replacement-by-cancel, mute/resume-future-only, explicit replay, completion, predicate/readiness fault, cancellation, expiry, and firing/publication limits take only declared paths; observer install/snapshot/live, mute/replace/cancel, explicit =start-seq= backfill, read-through advancement, client-generation fencing, bounded lag, and =resnapshot-required= never enter activation/effect state.
- prepared start :: prepare-without-start invokes no runner; start-prepared is once-only; pre-start cancellation/enrollment failure never runs the carrier; atomic enrollment rejection produces exactly one synchronous setup-error tool result, a locally failed prepared handle, and no board operation/outbox/terminal event; every executable =:work= and compatibility =:start=/=:handler= path exposes/enrolls the canonical id before runner entry.
- exact invocation :: installation precedes runner start; inline success/failure/cancel commits one transcript result, timeout closes only the subscription, and late settlement never appends a second result.
- exact participant :: the non-mutable membership-owned identity subscription routes active and validly stale/dormant participants; missing/revoked/detaching membership is visibly =target-unavailable= and creates/spawns nothing; descriptive tags on an exact post cannot fan out.
- generic dispatch :: zero matches is visibly =no-matching-subscription=, one match routes once, N matches broadcast, and several matches owned by one participant deduplicate to one pickup recording all subscription ids.
- eligibility :: active, dormant/stale-valid, detaching, revoked, and each subscription terminal/muted state follow the eligibility truth table; later joins do not replay implicitly.
- aggregation :: generic all-terminal/first-terminal handle empty/already-terminal/tied/late-member cases deterministically; late losers remain visible and are not cancelled implicitly; =await= additionally preserves declared ref order, resolution errors, all current snapshots in =any=, timeout/report fields, and immediate empty/no-resolvable reply semantics.
- causality :: source -> activation -> effect -> invocation receipt/transcript result or post/pickup -> turn -> work links survive projection without timestamp inference; the canonical effect-declaration cycle fingerprint excludes dynamic result bytes, survives checkpoint/replay, stops an immediate router-only repeat, and resets after declared turn/work/external-root boundaries; exhausted publication and provider wake budgets remain independent visible stops.
- ordering/isolation :: cheap and asynchronous settlement both follow settle -> terminal append -> frozen activation -> effect; a board observer/orchestration-subscription failure cannot resettle work, retry a producer message, or suppress unrelated subscriptions.
- terminal publication :: successful prepare/enroll/outbox bind precedes runner entry; lifecycle/result commit invokes the dedicated =e-work= publication observer before cleanup/general callbacks; output/activity append failure pins a visible retry/failure and never invokes a direct client/session callback fallback; compatible reload uses the stable trampoline/current runtime drain exactly once.
- effect idempotency :: reentrant calls, lost acknowledgements, restartable drains, and old endpoint generations commit one invocation receipt or one source-keyed board post; post success does not depend on downstream pickup.
- non-blocking :: controlled callbacks/fake scheduler prove matching, reduction, and effect scheduling return without long work; structural checks forbid polling, =accept-process-output=, sleep, interactive waits, and wall-clock test thresholds.
- lifecycle :: a turn handle settles once across append failure, provider retry success/exhaustion, compaction fallback/failure, tool failure, active abort, delayed abort, reset, and late callbacks.

Board identity, registry, and top-level interaction level:

- identity :: trusted principal identifiers and generated client/board/participant ids occupy distinct namespaces, a board id is never a session alias, collision injection is rejected, compatible reload preserves live ids, and absent historical ids fail instead of resolving to new state.
- namespace :: equal session ids under distinct store ids remain distinct, multiple harness views over one store/session resolve to one stable attachment key, participant ids survive authorized quiescent endpoint rebind, and duplicate active attachment across boards/generations is rejected.
- catalog :: listing configured dormant stores invokes no harness factory, compatible duplicate store ports yield one session row with every eligible instance, conflicting same-store port registrations fail, and unauthorized legacy/private sessions are absent; direct resume with a hidden/stale session, wrong store/version, denied principal, active session, or ineligible instance fails before any factory/grant/attachment, while an authorized resume invokes only the named eligible instance and persists any legacy access migration before atomic attachment.
- catalog access :: the narrow access-store port performs versioned create/migrate/grant/revoke/transfer without activating a harness or exposing transcript mutation; durable controller/discover/resume ACLs survive board removal/restart, ownership transfer is allowed only while dormant, and the old controller loses implicit catalog rights without rewriting expired or unrelated board-local grants.
- atomicity :: a board may publish with an owner principal and no session; every session create/resume/fork/subagent operation publishes participant membership, attachment token, and live endpoint together or exposes neither.
- invariant :: loading history stays dormant; every live session has exactly one active attachment; logical envelopes record board/participant but no endpoint generation, while each physical attempt and accepted inbox/turn/action/tool/work projection records the composite generation; detach/move cannot lose queued input, rewrite history, or leave a promptable unbound session.
- chat boundary :: structural tests forbid =e-chat= from =e-actions-call=, retaining/subscribing to a harness endpoint, reading transcript/session activity/active-turn state, or direct session prompting; authenticated host APIs attach a client/principal, open a board, default input and the observer selector to tag =main=, optionally address/observe explicit participants or tags, preserve dormant-session discovery/resume plus selected-participant controls, and render only matched board messages.
- board activity :: every visible provider wait/stream transition, timed =Thinking=/=Thought= boundary, board-safe reasoning update, tool start/progress/finish, action start/finish/fail, turn failure/cancellation, and navigable =turn-summary= has one board message/source identity/sequence; raw reasoning/transcript/final-answer deltas are absent, final text appears only once as =output=, and spinner ticks remain local.
- non-consuming observation :: two clients matching the same activity/summary both render it; read-through changes only their own cursors and creates no activation/effect/pickup/wake/routedness/consumption or new board record; =create-pickup= rejects every non-=input= kind even when it carries =main=.
- main and extension :: the default observer sees tagged chat-to-=main= input plus every causally tag-inheriting activity/summary/output and excludes unrelated subagent traffic; widening it by explicit =start-seq= plus tag/author/subject/to includes the subagent stream without a new transport, overlapping redelivery reuses the rendered =message-id= index instead of duplicating main records, and hidden board sequences are filter gaps rather than loss.
- observer lifecycle :: installing/buffering before the serialized board high-watermark snapshot and draining by =message-id=/=seq= gives a gap-free replay/live handoff; every open-projection entry references accepted board messages rather than synthesizing one, retained open activity restores =Thinking=, correlated output or terminal activity suppresses stale starts even before/missing a summary, expired history/bounded lag requires resnapshot, and buffer kill/client disconnect/filter replacement/board close/read revocation release the cursor while late client generations cannot repaint or retry publication.
- activity terminal states :: provider failure and turn cancellation post terminal activity, settle the visible thought, and retain their status plus duration-bearing =turn-summary= when provider activity exists, while a turn that never entered provider activity creates no empty summary or fabricated output.
- activity reconciliation :: independent =output-seen= /=summary-seen= facts make both summary-before-output and output-before-summary yield one board answer and one correctly associated summary using only =(subject-participant-id, source-turn-id)= board messages; reconnect between output and delayed summary cannot resurrect =Thinking=, permanent summary-publication failure leaves a settled answer plus visible failure rather than an open stream, failure/cancellation are no-output terminal activity/summary, simultaneous main/subagent streams do not collide, transcript callbacks cannot duplicate canonical input/output, and board =seq= rather than timestamps orders unrelated records.
- lifecycle :: an authorized principal can reconnect to an empty board; idle expiry is bounded; closing rejects unrelated roots/input but preserves pre-close subscriptions for terminal/descendant effects of admitted roots, reconciles accepted receipts/effects, aborts only board-bound turns at its deadline, records observation tombstones for remaining domain work, and cannot close with unresolved acceptance.
- endpoint :: identical startup registration/sync preserves both generation components; logical remap/concrete clear/replacement bumps the correct component, invalidates callbacks/attachments, fences old receipts, and resolution never lazily creates a session/harness.
- rebind :: pre-call stale delivery may wait; accepted/consumed/lost-ack cases reconcile on the old endpoint; unknown commit becomes =uncertain= and is never redelivered to the new generation.
- authorization :: principal/participant owner/member roles, trusted generation-checked requester context, cross-target grants, session-private work, controlling-principal/private grants, and authorization before publication/selector/effect preparation prevent unauthorized posting, delivery, transcript reads, controls, and result/intent leakage; tags never grant access, and board-read revocation closes client observers without undoing already-committed records.
- private grants :: a matrix proves =inspect-transcript= and =control-session= authorize only their named surfaces; board membership grants neither private right, selective revoke leaves the other intact, and a child/fork copies the controller but no third-party grant.
- binding :: participant context always resolves its sole board, client context is explicit, a mismatched board delivery is rejected, and moving a session changes only future turn binding.
- dependency :: board core and registry load/test with fake runtime ports and no harness/provider/UI dependency.
- restart/reload :: old runtime-generation callbacks cannot deliver twice, historical board ids never resolve to new boards after restart, and resumed persisted sessions attach before becoming live.

Board message, subscription/effect, and retention level:

- pickup :: one board input creates one opaque-id delivery per frozen matching participant using the message's =inject=/=queue= mode; exact input reaches only its target, tagged input broadcasts to subscribers, later joins do not replay implicitly, and an unrouted message remains visible.
- pickup FIFO :: one nonterminal head per participant prevents overtaking, including while rebinding; old-message routing appends =input-routed= with =routed-seq=; ready cancellation, permanent/exhausted failure, accepted discard, consumption, expiry/overflow, and uncertain ordering-gap tombstone each take their declared terminal path and release the FIFO while other participants continue.
- output :: repeated completion callbacks/runtime reload/board-append retry/render failure still yield one source-keyed output or one visible publication failure without resettling the turn; retry after recent-map eviction returns =source-history-expired= and appends nothing; ordered reply/delivery sets represent several injected inputs, and output creates no direct pickup or feedback although an explicit matching =post-input= continuation may deliberately create a new input.
- activity :: provider/turn callbacks produce one idempotent source-keyed normalized activity/summary publication or one visible publication failure; stale endpoint generations append nothing, progress versions are monotonic/coalesced before append, terminal activity or correlated output suppresses open state, and activity creates no direct pickup or feedback although an explicit matching =post-input= continuation may deliberately create a new input.
- observation :: matching board facts remain globally unconsumed; two observer cursors advance independently, filtering =main= excludes unrelated subagent records, selector widening can replay retained subagent records from an explicit =start-seq=, and observer delivery produces no orchestration state.
- ordering :: pickup and observer delivery use =seq= order and a batch never reorders; filtered sequence gaps are intentional, and interleaved participant/turn activity remains independently correlated.
- batching :: one =batch= subscription that accumulates N matching completions emits one post/pickup and at most one resulting wake; independent subscriptions may intentionally emit independently.
- cheap settlement :: invocation receipt/endpoint snapshot plus outbox/subscription installation precede runner start and bind failure invokes no runner; cheap finish/fail/cancel publishes and freezes its activation exactly once inline, while no effect application, invocation close/result append, queue advance, delivery, or provider turn occurs before =e-work-start-prepared= returns; later observer failure cannot suppress operation completion.
- existing terminal :: installing against already-terminal work uses its snapshot without rewinding unrelated history and activates exactly once.
- subscription states :: every active/muted/completed/faulted/cancelled/expired transition and illegal terminal transition is covered, including repeating committed-to-active and budget stop after reconciliation.
- activation/effect states :: every prepared/applying/committed/failed/uncertain/cancelled path reuses identical source ids/effect bytes; replay never reruns the predicate or effect preparation.
- idempotency :: failures before mutation retry one frozen id; failures after mutation, reentrant calls, interrupted acknowledgement, and old-harness rebind return/reconcile one receipt and create at most one inbox/transcript item.
- cursors :: an orchestration =next-seq= classifies every ignored, accumulated, frozen, or terminally failed event exactly once, while an observer cursor classifies filtered or read-through messages without consuming them; both survive batching/compaction or fail explicitly with =resnapshot-required=.
- lifetime :: one-shot subscriptions include declared finished/failed/cancelled matches once; repeating subscriptions respect firing/publication budgets and expiry.
- failure :: selector/readiness/effect-preparation failure faults only the subscription and records =subscription-fault= without changing the source event or work state.
- cause :: every consumed input records board/participant/generation and typed cause; the turn initializes then monotonically extends a bounded ordered routing-tag union as injected inputs are consumed, each activity freezes the current union, and terminal summary/output preserve the final tags plus ordered cause set since the preceding assistant response.
- budget :: a self-feeding routing cycle and publication exhaustion each stop with their own visible reason; provider wake exhaustion remains distinct.

* Accepted implementation defaults and deferred follow-ups

The first-version choices are normative and leave no architectural question blocking Slice 0:

- Context receives ids, states, counts, and bounded summaries; full events and results remain behind =board://<board-id>/...= reads.
- Sanitized participant activity and terminal summaries are ordinary board-visible messages; raw reasoning, transcript content, and unbounded payloads are never published, and tags select but never authorize.
- Chat's default observer selector matches =main=; each participant activity snapshots the turn's current monotonic routing-tag accumulator and terminal summary/output use its final value, while subagent/other views widen the same selector explicitly.
- Compatible reload retains each installed predicate closure until explicit replacement or cancellation; there is no registry, version protocol, or automatic migration, and historical matches remain frozen.
- Fork requires an explicit transcript-entry =:at=.
- Newly unobserved terminal work remains in board current state and produces one warning when the board next becomes idle; it never becomes synthetic participant input.
- Every resource and scheduling limit is explicit configuration with conservative deterministic-test defaults; Slice 6 tunes production values from measurements.

The following are explicitly deferred and do not block this plan:

- Durability of board messages, subscriptions/activation receipts, and memberships across Emacs restarts after the process-local lifecycle proves itself.
- Claimable offers, leases, exactly-one executor competition, and general autospawn if selector-routed/tagged broadcast messages later prove insufficient for agent hand-off.
- Final production retention, tombstone, retry, subscriber-count, client reconnect, empty-board idle-expiry, propagation, wake, batching, and participant-limit values.

* Required self-check (design-sensitive)

1. *Better off if stopped here?*  Slice 0 gives executable work one stable identity/lifecycle without adding a callback graph.
   Slice 1 then establishes a real board identity/registry, common selector/subscription core, tagged =main= ingress, and one board-bound session.
2. *Final direction?*  The board is the only top-level live interaction context and live routing/observation substrate: chat/producers post there, observer subscriptions read without consuming, orchestration subscriptions correlate or discover consumers, sessions pick up only matched input, =e-work= settles execution, and participant activity/summaries/outputs return to the board.
3. *Likely to change vs stable?*  Principal/client/board/participant/work/message/subscription identity, exactly-one-board attachment, exact-vs-generic cardinality, input-only pickup, non-consuming observation, effect settlement, board ownership, receipts, and cursor semantics are stable.
   Tag conventions, predicate closures, budget values, retention limits, batch size, and readiness defaults remain local and reversible.
4. *Owning component?*  Application services own local business sequencing; board core owns messages/facts including activity, selectors, observer/orchestration subscriptions, open-activity/readiness/activation/effect/causal/pickup reducers; registry owns board identity/authorization, clients/cursors, attachments, lifecycle, and cross-generation delivery state; session stores own durable dormant-session access records and internal activity; board runtime owns composition/effect/delivery plus normalized activity-publication adapters; harness owns concrete inbox receipts, transcripts, turns, and raw live activity; chat owns only the board-message activity reducer and buffer-local view state; domain services keep domain policy.
5. *Coupling?*  =e-work= gains no board dependency.
   Posters depend on board data contracts rather than concrete consumers; exact selectors retain intentional identity coupling only where correlation/addressing requires it; chat observes by tags/conditions without producers naming it, and observation cannot call back into routing or settlement.
6. *Dependency direction?*  Stable lifecycle and board contracts do not depend on tools, shells, task queue, subagents, or provider adapters.
7. *Side effects outward?*  External execution stays in existing carriers.
   Board reducers only freeze decisions/state; the runtime adapter performs invocation commits, board posts, harness delivery, and explicit session creation.
8. *State?*  =e-work= state lasts through executable settlement/retention.
   Board registry entries own bounded messages/history, observer/orchestration subscriptions and cursors, open-activity projections, accumulators, frozen activations/effects/lineages, principals/clients/participants, grants, pins, and authoritative delivery state; session stores own stable identity/access/publication counters plus internal durable activity; harnesses own concrete inbox items, local receipts, turns, transcripts, and raw current activity; the runtime owns publication retry/source-generation state; chat owns transient animation/render/focus/expansion state; domain registries remain authoritative.
9. *Performance?*  Cheap work may settle inline and the one-call exact path remains.
   Terminal transitions are immediate, raw progress is coalesced before bounded board activity append, superseded progress compacts after terminal/cursor safety, rendering ticks do not inflate board history, matching/drains/effect bytes/projections are bounded, and deterministic storms justify selector, observer-lag, propagation, wake, and retention defaults before rollout.
10. *Abstractions real?*  =e-work= represents execution; board records represent facts; selectors choose records; orchestration subscriptions add readiness and one declarative effect; exact invocation receipts represent result correlation; pickups/receipts represent participant input ownership/consumption.
    Orchestration subscriptions add readiness/effects, while observer subscriptions are effect-free read cursors over the same facts; neither can substitute for consuming input pickup, and none of these contracts substitutes for another.
11. *Compatibility?*  Legacy tool forms, =:notify=, and direct session entry points receive temporary adapters, then leave runtime execution after callers migrate.
    Stored session history remains resumable, but only by attaching it to a board before activation.
12. *Legacy to remove?*  Remove =:handler=/=:start= tool branches, the detachable wrapper, =:notify= surface, direct chat/session prompt creation, duplicate session-input paths, and any destination-specific callback continuation after migration.
    Keep task and subagent registries because they own domain state and already push change facts.
13. *Errors?*  Expected work failures/cancellation settle handles; selector/readiness/effect, terminal/activity/output publication, observer cursor/expiry, routing-cycle/budget, delivery/receipt/discard, and uncertain faults become visible board state without duplicate execution or message publication.
    Unexpected errors surface through the owning operation or runtime adapter.
