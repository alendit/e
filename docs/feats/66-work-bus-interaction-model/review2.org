* Review summary

The remediation makes the board the sole live interaction substrate:

- chat creates or opens a board, owns independent observer clients, and renders
  bounded board DTOs rather than private transcript/activity state;
- every live harness port is private and attachment-token checked, while the
  former tokenless start/control and generic presentation-subscription symbols
  are absent;
- default, tag, and exact dispatch share authenticated ingress; subagents join
  the parent board; bundled producers choose observable fact versus
  dispatchable input explicitly;
- quiescence covers every deferred owner when explicitly requested, while
  ordinary startup admits board creation without a historical-session gate;
- retained envelopes are frozen, identities/lifecycle are registry-owned, and
  nil/stale/revoked requester contexts fail closed; and
- routing, observation, await materialization, and persistence have fixed
  cardinality/byte budgets with asynchronous or scheduled completion.

All ten High findings and the Medium regression-coverage finding are closed.

** DONE High: Standalone sessions still bypass the board-only product and its admission fence

*** Expected

The accepted product invariant is that boards are top-level and there are no
standalone sessions.  Plan lines 505--508, 1392--1414, 1585--1608, 1742--1743,
and 1752 require every live session to exist as an attached participant and
require the one-go cutover to remove direct live create/prompt/queue/steer/abort
paths.

*** Observed

=e-harness-create-session= remains public at =lisp/core/e-harness.el:685--690=.
Direct queue, steer, prompt, and abort entry points remain at 1541--1609,
2853 onward, and 3168--3189.  =test/e-test.el:450--465= explicitly preserves
those APIs.  =e-chat-service--bind-session= at
=lisp/core/e-chat-service.el:199--232= takes an existing session and creates a
board around it; =e-chat-service-create-session= at 275--280 creates the
session first.

A bounded batch harness probe created a session and called
=e-harness-prompt-async= directly.  It finished with assistant content
="standalone answer"= without any board attachment.  After closing
=e-board-runtime= admission, another direct prompt still finished with
="after fence"=.

#+begin_example

 :attachment nil)

(:admission (:state closed :epoch 1)
 :status done
 :result (:status done :reason stop :assistant-content "after fence"))
#+end_example

The current structural guard at =test/e-cutover-structure-test.el:17--59=
only rejects old symbol names in selected consumers.  It deliberately allows
the old root APIs to exist and therefore cannot prove the board-only invariant.

*** Why it matters

Boards cannot be the top-level authorization, routing, quiescence, lifecycle,
or observability boundary while a second live root can start work independently.
The admission fence is not a cutover fence if direct sessions ignore it.

*** Smallest corrective direction

Create narrow private harness delivery/start/control ports that require a
current board attachment token.  Move board runtime delivery to those ports,
then delete the direct live session create/fork/prompt/queue/steer/abort APIs,
their session-first service wrappers, and compatibility tests.  Session storage
and transcript APIs may remain as private participant execution context; they
must not remain live interaction roots.

*** Verification required

- Structural tests prove every retired root symbol/path is absent, not merely
  absent from a short caller list.
- A behavioral test proves no live turn starts without a current board,
  participant, and attachment token.
- Closing board admission prevents every new root, including custom capability
  and internal service paths.

*** Resolution

The public prompt, follow-up, queue, steer, and abort roots were removed.
Their replacements are private harness ports which require the exact opaque
token of the current board attachment before they can start or control work.
The board runtime is the production authorizer and supplies a fresh token for
both qualified and direct attachments; queued and settlement follow-ups retain
that token for their later turn.  A bare session record can still exist as
dormant storage and model context, but it has no public operation that can make
it live.

Chat reload now preserves an admitted board-bound harness instead of attaching
a second endpoint to the same durable session.  Test-only direct harness use is
isolated behind an explicit support adapter whose synthetic authority never
overrides a real production attachment.

*** Evidence

- =test/e-cutover-structure-test.el= asserts that every retired public live-root
  symbol is absent and that a forged private-port token cannot start a turn.
- =test/e-test.el= no longer treats direct prompt, follow-up, queue, steer, or

- =test/e-board-runtime-test.el= proves current attachment tokens fence normal

** DONE High: Chat is still session-first and cannot operate the top-level board model

*** Expected

Plan lines 505--513 and 576--583 define chat as an authorized board client.
The default post uses the descriptive =main= tag, but chat must also support
generic tags/attributes and optional exact =to=.  Lines 607--625 require
selector widening/replacement and independent observation.  Chat must be able
to open an existing board rather than manufacture one around a session.

*** Observed

The =e-chat-service-binding= at =lisp/core/e-chat-service.el:43--60= is keyed
by harness and session id.  Binding at 199--232 creates a new board, client,
participant, fixed =(:tags (main))= pickup subscription, and fixed
=(:tags (main))= observer for one existing session.  Posting at 311--333 always
uses =:tags '(main)= and exposes neither arbitrary tags nor exact destination.

The chat shell still stores harness/session buffer identity and its public open
and submit functions are session-oriented.  The bounded live probe found no
board-local identity and only the hidden per-session =brd_1= binding.  There is
no public board open/list/selector-widen flow and no =board://= resource or
equivalent board-facing shell surface.

*** Why it matters

The current service preserves the old one-chat/one-session product while using
a private board as an implementation detail.  It cannot express the intended
indirection between poster and picker, cannot show a multi-participant board,
and cannot let a user follow subagents by widening an observer.

*** Smallest corrective direction

Make the application service board/client based.  Create/open the board
independently, attach participant sessions to it, and store board/client/observer
identity in the chat buffer.  Expose board-first post operations with generic
tags/attributes and optional exact participant destination, plus observer
replace/widen/backfill operations.  Keep =main= only as the default selector,
not as a hard-coded transport.

*** Verification required

Exercise opening an empty board, reconnecting to an existing board, default
=main= posting, arbitrary tagged posting, exact posting, zero-match visible
unrouted state, two matching participants, and widening the same chat observer
to a subagent stream.

*** Resolution

The application service exposes board-first create/open, bounded list,
participant creation, generic tagged and exact posting, and selector
replacement APIs.  Each subscription owns an independently attached registry
client and observer; subscriber failure faults that lane without advancing its
cursor.  The chat shell can now open an existing board, create its private
participant session when needed, list boards through the bounded registry page,
and retains the board, client, and observer identities as explicit buffer-local
public interaction context.  Session identity remains the private execution
attachment rather than the shell's only product identity.

*** Evidence

- =e-chat-service-test-opens-existing-board-and-routes-generic-posts= covers
  reconnecting two participants, tagged routing, exact routing, and visible
  zero-match state.
- =e-chat-service-test-board-list-is-bounded-and-continuable= covers bounded

- =e-chat-service-test-independent-observers-preserve-board-identity= and the

  widening with backfill.
- =e-chat-test-buffer-owns-explicit-board-client-observer-identity= proves the

** DONE High: Bundled work producers publish inert facts and task completion is false

*** Expected

Facts are observation-only.  A producer that requests work must post an
=input= with descriptive tags/attributes or trigger an explicit declarative
=post-input= continuation.  The task domain should preserve FIFO dispatch,
retry/concurrency, and settle only when the requested work reaches its terminal
outcome.  Zero matching subscribers must leave work visibly unrouted rather
than pretend it completed.

*** Observed

=e-board-runtime-producer-publish-fact= at
=lisp/core/e-board-runtime.el:382--447= only appends observation facts.
=e-task-queue-default-runner= at =lisp/core/e-task-queue.el:560--584= publishes
such a fact and immediately calls =on-settle= with =done=.  Its regression test
at =test/e-task-queue-test.el:285--316= explicitly accepts done with zero
participants.

Cron, background file notification, annotation answer, and related producer
paths likewise publish facts.  A lifecycle fact can be correct for a domain
notification, but it is not dispatchable work merely because it carries tags.

*** Why it matters

The implementation collapses “work requested” into “notification recorded.”
No subscribed session picks the task up, and durable task state can claim
success when no agent acted.

*** Smallest corrective direction

Classify each bundled producer as either a domain fact or a work request.  Keep
facts as facts.  For work requests, post a board input with stable source key,
generic tags/attributes, and optional exact target, or install an explicit
fact-to-input continuation.  Retain the task as running until the causally
identified board work settles; record visible unrouted/failed/cancelled states.

*** Verification required

For every bundled producer, prove either its intentional observation-only
contract or its input/pickup/settlement path.  In particular, prove task
unrouted, one subscriber, broadcast, retry, cancellation, and terminal result
instead of only successful fact append.

*** Resolution

Trusted producer bindings now own an attached, generation-fenced board client;
their separately named =e-board-runtime-producer-publish-input= API retains that
client actor and posts dispatchable input with a stable source key.  Producer
work remains in the runtime unsettled projection through routing and every
causally identified participant turn.  Zero matches settle =unrouted=, broadcast
waits for every pickup, terminal failures dominate the aggregate result, and
cancellation fences queued or in-progress routing.

The task queue now publishes work input and stays =running= until the board
outcome settles.  It records =unrouted= visibly instead of claiming =done=.
Annotation-answer dispatch and background triggers are work inputs.  Cron
=:publish= and subagent lifecycle changes remain deliberately observation-only
facts: their domain contract is recording a scheduled notification or lifecycle
edge, not claiming that an agent completed work.

*** Evidence

=e-board-runtime-test-producer-input-settles-from-causal-turn= proves a trusted
non-nil client actor, routing, pickup consumption, terminal-turn correlation,
and quiescence accounting.  The broadcast and cancellation tests prove
all-pickup aggregation and both cancellation fences; the existing source-key
retry regression remains green.  Task, annotation, background, cron, and
subagent selections classify and exercise their intended fact-versus-input
contracts.

* Architecture review

The completed dependency direction matches the intended ownership:

- registry owns durable board identity, lifecycle, principals, clients,
  participants, subscriptions, and cursor/retention state;
- board ingress owns immutable append and bounded routing preparation;
- board runtime owns token-checked physical delivery and publication adapters;
- harness/session owns only private participant execution and model context;
- each chat shell owns a client plus observer cursors and renders board DTOs;
- producer/domain services decide fact versus work input before crossing board
  ingress; and
- writer adapters own serialization/I/O and expose pending/finalize handles to
  quiescence.

No compatibility requirement applied.  The old tokenless live-session roots,
generic presentation subscription, session-presentation wrappers, synthetic
identity/authorization fallbacks, raw attach, and blocking durability APIs are
absent.  Private harness execution remains an adapter detail behind exact
attachment-token ports.

* Design self-check

1. *Useful stopping point?*  Yes.  The product has one interaction substrate,
   with independently useful bounded registry, observation, activation, and
   durability contracts.
2. *Final direction?*  One board-first product in which sessions are private
   participants and every interaction, observation, and work dispatch crosses
   the same bus.
3. *Stable versus uncertain?*  Board top-level ownership, immutable causal
   messages, exact/tag dispatch, passive observers, attachment fencing, and
   async bounded carriers are stable.  Selector UI and future autospawn policy
   can remain local and deferred.
4. *Owner?*  Registry owns identity/lifecycle/membership; board owns immutable
   messaging/routing/observation; runtime owns harness delivery/publication;
   chat owns board DTO presentation; writers own durability.
5. *Coupling?*  Coupling is reduced: shells and producers depend on board/chat
   contracts, while concrete harness/session access is confined to the runtime
   adapter and named diagnostics.
6. *Dependency direction?*  Stable board policy has no dependency on harness,
   UI, provider, or storage implementations; the runtime adapter points inward
   to board contracts and outward to private harness ports.
7. *Side effects outward?*  Physical writes, delivery, callbacks, and UI work
   sit in workers/scheduled adapters outside core board mutation.
8. *State lifetime?*  Board identity, messages, causal ids, membership,
   subscriptions, and accepted cursor positions are durable board state.
   render focus/spinners stay local.  Private transcript remains session state.
9. *Performance?*  Routing uses O(1) FIFO accumulation and fixed pages/caps;
   observer replay, await materialization, writer commands/snapshots, and close
   reconciliation all have explicit bounds.  No regression was accepted.
10. *Real abstractions?*  Board/client/participant/subscription/pickup and the
    private participant execution port are narrow, consumer-shaped contracts;
    no implementation weakens them with unsupported operations.
11. *Compatibility?*  None was requested, so the migration kept no public

12. *Legacy removal?*  Direct live start/control, generic presentation

13. *Errors?*  Unrouted input, denied/stale requester, subscriber fault,

    surface as explicit states or errors; unexpected failures are not swallowed.
14. *Tests?*  Core tests isolate reducers/bounds, while the retirement manifest
