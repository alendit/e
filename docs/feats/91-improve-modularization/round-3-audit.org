#+title: Feature 91 Round 3 Runtime-Control Audit
#+startup: overview

* Scope and status

This is the accepted evidence for the Feature 91 Round 3 runtime-control
family.  It covers =F91-OWNER=, =F91-RUNTIME=, =F91-TOPOLOGY=, and
=F91-PRESERVATION=: the harness runtime owners, the board attached-turn
boundary, their direct/composed tests, and the affected context/provider/chat
consumers.  Parent acceptance was completed on 2026-08-30.

The public harness facade remains =lisp/core/e-harness.el=.  The runtime
implementation is now split into explicit state, capability, activity,
turn-state, context-runtime, and turn-composition owners.  Board attachment
uses one bound =e-harness-attached-turn-port= object; there is no process-wide
attached callback slot.  The public behavior target is unchanged: turn and
tool ordering, admission and settlement, abort/error visibility, context
generation/provider anchors, activity persistence, board routing, and restart
effects retain their accepted Feature 88/90 and Feature 91 Round 1/2
contracts.

No provider external evidence was required.  The running Emacs was not
queried, reloaded, signaled, or otherwise changed.  Core state and attached
port record-shape changes require a restart before an already-running process
can use this source; no compatibility shim was added for that restart
boundary.

* Performance and I/O disposition

No new synchronous writes or repeated scans were introduced.  Activity
projection retains its existing bounded payload normalization and session

* Mechanical-equivalence and restart notes

- Public command/mode names, session APIs, event order, JSON/durable shapes,
  retry/cancellation/error behavior, provider option semantics, and board
  publication/admission semantics have no intended change.
- The root harness record now contains named owner substates and an immutable
  process-local identity token.  The token prevents a mutable aggregate from
  changing its =equal= hash identity while an attachment registry is live; it
  is not durable or model-visible.
- The attached port is a new internal/public adapter contract for board
  consumers.  It carries the same endpoint token and calls the existing turn
  composition paths, so no additional queue or persistence path exists.
- Core record/substate changes require a restart under =AGENTS.md=.  No live
  reload or compatibility alias was used.

* Feature 91 self-check

1. If this package stopped here, the project is better off: harness and board
   behavior remains green while runtime changes can be localized to named
   owners and direct tests, with the previous private callback bridge removed.
2. The work moves toward the final direction of stable application services,
   explicit owner state, narrow adapter contracts, and acyclic module/test
   topology.
3. Stable decisions are the harness/session/board behavior and existing event
   formats.  Uncertain decisions are limited to owner placement and the
   attached adapter boundary; they are local in the new owner files and can
   change without changing durable formats or shell behavior.
4. Each extracted component has one primary reason to change: capability
   derivation, activity recording, turn/queue state, context policy, or turn
   side-effect composition.  The facade owns lifecycle and composition.
5. Coupling is reduced: callers consume semantic projections and the concrete
   attached port, while cross-owner private references and duplicate
   operational copies are absent.
6. Dependencies point downward from composition/policy toward state and core
   contracts.  No owner depends on the facade; =e-context-budget= now points
   to context-runtime rather than hiding a reverse budget/facade cycle.
7. Side effects remain outward where their meaning is clear: provider
   invocation/work/timers are in turn composition, durable activity append is
   in activity, and board publication/attachment effects remain in board.
8. Added state is process-local runtime state at the existing turn/harness
   lifetime: named substates, queues, active entries, subscribers, and
   provider candidates.  Durable session activity and context facts remain in
   the session store.  No shared mutable record crosses activity/context/turn
   owner boundaries without a semantic copy or setter.
9. Performance stays bounded: queue/active observations are constant-time,
   activity writes retain existing batching/flush points, and no new repeated
   context or catalog scan is introduced.  Smoke timings and consumer gates
   are recorded above.
10. The attached-turn port is semantically real and substitution-tested: a
    replacement port double authorizes, submits, observes, queues, steers,
    publishes, aborts, and propagates errors without implementing board
    internals.  Unsupported operations are not part of the port.
11. Compatibility expectations are explicit: documented public APIs and
    formats are preserved; private compatibility aliases and process-global
    callbacks were removed.  Core shape changes require restart.
12. Removed legacy code includes the monolithic harness implementations,
    private attached callback slots, private board reach-through, and stale
    private consumer/test bridges.  No duplicate turn/activity implementation
    remains.
13. Expected provider/attachment errors are handled at their existing
    application boundaries and surfaced through the same conditions/events;
    unexpected errors continue to signal rather than being swallowed.
14. Direct owner contracts prove substates, activity observation, port
    substitution, queue/turn transitions, and errors independently.  Composed
    harness, board, preservation, provider, and graphical suites prove the
    unchanged end-to-end behavior.  The test topology therefore changes with
    the owner boundary rather than requiring unrelated test rewrites.
