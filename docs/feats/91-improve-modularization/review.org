** TODO Medium: Runtime board-stage completion loses the exact invocation lease

*** Expected behavior

=F91-RUNTIME= requires the invocation authorized after =+1= notification to be
the same invocation that board Work commits and error rollback retires.  A
same-key replacement has a distinct attachment generation and must neither
receive the old Work nor be cancelled by the old admission.

*** Observed behavior

=e-board-runtime--register-invocation= returns only =target= at
=lisp/core/e-board-runtime.el:1406=.  =--enroll-work= stores that equal list at
lines 1823-1829 and passes it to board enrollment, but it does not retain the
exact invocation object or revalidate it after the board call at lines
1830-1838.  On error, lines 1848-1853 call =gethash= again and terminalize
whatever invocation currently owns that descriptive key.

Two real-harness probes replaced the attachment and invocation from the
post-mutation publication-observer boundary after the =+1= check:

- when the lower-owner call then signaled, outer rollback marked the new
  invocation =cancelled=, removed its new attachment-local/global entries, and
  decremented its count; and
- when it returned, enrollment reported success with Work hooks still capturing
  the old dormant attachment while the board invocation's effect target key
  resolved to the new attachment's invocation.

*** Why it matters

The first path deletes authority owned by a replacement transaction.  The
second can route old Work settlement to a new callback generation.  Both are
the exact cross-generation behavior that the attachment/invocation design is
meant to prevent.

*** Smallest corrective direction

Carry one exact runtime invocation lease/object, not just its equal key, from
registration through board commit and rollback.  Revalidate that exact global
and attachment-local value plus active attachment after the board stage before
reporting success; if authority was lost, abort only this admission's board
token.  Error cleanup must terminalize only the captured invocation object.
Do not add an id lookup fallback or make board inspect runtime-private state.
Add real runtime enrollment regressions for signaling and returning board-stage
replacement.

** TODO Medium: Post-mutation board event failure escapes the admission inverse

*** Expected behavior

The board-owned admission token must name every event created by an attempt
before a later step can signal.  Rejected callback and callbackless enrollment
must expose no =posted= or =subscription-added= history, event-count index, work
map, invocation map, observer, or classifier lease.  Event sequence remains
monotonic; rollback must not reuse sequence numbers.

*** Observed behavior

=e-board--append-event= at =lisp/core/e-board.el:485-498= increments sequence,
links the event/tail, and indexes its message count before returning.  Board
enrollment assigns =e-board-work-posted-event= only around the returned value at
lines 1790-1793, and assigns the invocation subscription event only at lines
1912-1916.  If the append boundary signals after its mutation, those fields
remain nil.  =e-board--discard-work-admission= at lines 1725-1734 can remove
only recorded event objects.

The callbackless witness left
=(participant-added posted)= after the error, including the =posted= sequence
entry in =event-message-count=; retry produced a second =posted=.  The callback
witness left =participant-added subscription-added= with no work or invocation
map; retry appended a new =posted= and another =subscription-added=.

*** Why it matters

The public board event log asserts that Work or a reply subscription existed
when every owning relation and observer was rolled back.  Replay/projection
consumers can observe false process history, and retry makes the contradiction
permanent for the board lifetime.

*** Smallest corrective direction

Have the board admission token acquire the exact event object before any
fallible append phase can expose it, then remove that object, its list cell/tail
effect, and event-message-count entry on abort.  Preserve monotonic =next-seq=
rather than rewinding across possible interleaving.  Do not scan by event type,
sequence range, work id, or invocation id.  Add direct board-owner tests for
post-mutation =posted= and =subscription-added= failures, exact tail/index
cleanup, repeated abort, and clean retry; retain one runtime composition case.

** TODO Medium: Failed board index inverse is swallowed after its retry authority is removed

*** Expected behavior

If a staged invocation index was inserted, board abort must either remove that
exact lease or retain exact authority to retry.  Preserving the initiating
admission error does not permit reporting cleanup success while an unreachable
index entry remains.

*** Observed behavior

=e-board--discard-work-admission= removes the exact invocation map entry first
at =lisp/core/e-board.el:1703-1708=.  Only inside that successful map-removal
branch does it call =e-board--remove-indexed-work-subscription=, and lines
1709-1714 swallow any error.  A repeated abort then skips the entire branch
because the map no longer contains the token's invocation object.

The real-enrollment witness let forward indexing complete, failed the following
subscription-event append before mutation, and made the index inverse signal.
All runtime targets/counts, Work hooks, board maps, observers, and events were
removed, but the invocation id remained in the work index.  After the inverse
was restored, normal retry appended the same id again; the index contained two
equal classifier entries.  Repeating the existing token could not repair the
first entry once its exact map gate was gone.

*** Why it matters

The supposedly opaque exact inverse loses its own recovery authority and hides
that loss from the caller.  A failed attempt can retain unbounded stale local
classifier work across retries even though no board relation owns it.

*** Smallest corrective direction

Stage the exact index lease and keep its retry gate until the index inverse has
acknowledged completion.  Board abort must not delete the only exact authority
or claim completion while that inverse remains outstanding.  Preserve the
initiating error without swallowing an unowned cleanup failure; do not repair
by a global/index-wide scan or descriptive-id deletion that could remove a
replacement.  Add direct board-owner failure tests before/after index mutation,
inverse failure, repeated abort, same-id replacement, and clean retry.

* Architecture review

** Ownership, dependency, and aggregate-design comparison

The physical owner choices remain right.  Work owns prepared-handle observers
and dispatch policy.  Board owns work/invocation relations, sequence/event log,
local classification indexes, and their exact inverse.  Runtime owns
attachment generation, invocation callback/table/index/count, notification,
and application composition.  Registry, chat service, session, presentation,
provider, persistence, and transport ownership are unchanged.

The graph is acyclic and calls point downward through public Work and board
operations.  Board has no runtime dependency; chat/service code reaches no new
runtime-private state.  Side effects remain at their existing adapter/shell
edges.

The aggregate design now spans three owners because the accepted behavior
already spans prepared Work, exact runtime callback authority, and board
relation/history.  The smallest faithful alternative is still those three
cohesive owners plus one application transaction.  Collapsing maps into runtime
or board would mix lifetimes; a generic transaction framework would add surface
without removing the causal boundaries.  The correction should therefore make
the three current leases exact and staged, not add a fourth coordinator.

** State lifetime, interfaces, compatibility, and errors

Work observer identities last one prepared-handle admission.  A board admission
token lasts until board commit is accepted or every inverse completes.
Invocation object/index/count lasts from accepted runtime registration through
terminalization.  Board events last the board process lifetime and their
sequence is monotonic.  All are reconstructible process state; no new durable
format is justified.

The Work inverse APIs are narrow and substitutable.  The board token is a real
consumer-shaped inverse, but its event/index completion contract is currently
weaker than its documentation.  Runtime's equal target is a useful descriptive
key but is not a substitute for the exact invocation lease across replacement.

No wire/durable compatibility path is needed.  Obsolete id-only teardown,
global invocation retirement scans, replacement-port fallback, and private
bridges should remain absent.  Unexpected initiating errors correctly surface,
but cleanup errors may not be swallowed after exact authority has been lost.
The original condition may remain primary while cleanup state remains owned and
retryable.

** Test topology, documentation, and sequencing

The added runtime tests are substantive and preserve historical names, but they
cover new lower-owner public semantics only through runtime composition.
Direct Work tests should own exact remove/substitution partitions; direct board
tests should own token/event/index abort partitions.  Runtime tests should own
the composed notification/replacement/retry contract.  This split would let a
board inverse redesign change board tests narrowly rather than expanding the
3,845-line runtime suite.

created event/index, remains retryable after failure, and preserves
replacements.  The five witnesses contradict those claims at this exact
revision.  This review is the finding authority; the implementation/audit docs
must be corrected with the remediation rather than edited during this pass.

* Design self-check

1. *If this package stopped here, would the project be better off?*  Yes.  The
   original orphan, global retirement scan, and non-exact Work cleanup are
   materially improved.  It cannot be accepted with three new transaction
   gaps.
2. *What final direction does this move toward?*  Stable facades over cohesive
   owners, with one exact admission lifetime from prepared Work through runtime
   callback authority and board relation/history.
3. *Which decisions are stable, uncertain, or likely to change?*  Exact
   lifetime, visible initiating errors, atomic pre-run failure, monotonic board
   sequence, downward dependency, and durable formats are stable.  Token/lease
   representation is owner-local and reversible; no speculative framework is
   needed.
4. *What component owns this behavior, and why?*  Work owns handle observers,
   runtime owns attachment/invocation/count, and board owns relation/event/index
   state.  Each inverse belongs with the same mutable state it removes; runtime
   composes but must retain exact leases.
5. *Does this change increase or reduce coupling?*  Static coupling is reduced
   by public exact operations and an attachment-local index.  Temporal coupling
   remains because runtime drops object identity and board records event/index
   completion too late.
6. *Did a dependency start pointing the wrong way?*  No.  The 709-edge graph is
   acyclic, board does not depend on runtime/service/provider/UI, and production
   has zero new cross-owner private references.
7. *Could any side effect move outward?*  Provider, persistence, display, and
   I/O effects remain outward.  Work mutation, board event/index mutation, and
   runtime notification belong at their current owner edges; moving rollback to
   chat or registry would weaken ownership.
8. *What state is added or mutated, who owns it, and how long should it live?*
   Work closures last admission, board token/event/index leases last commit or
   complete abort, and runtime invocation/index/count lasts exact callback
   authority.  Ghost events/index cells currently outlive their failed attempt,
   while replacement invocation authority can be shortened incorrectly.
9. *What is the performance impact?*  Successful admission adds constant local
   object/hash work and retirement removes a global scan.  Event/index inverse
   is proportional only to this admission's local entries.  Corrections need no
   global scan, persistence write, or unbounded drain.
10. *Are abstractions real and implementations substitutable?*  Exact Work
    removers and the board admission concept are real.  The board inverse is not
    substitutable under its claimed failure contract until event/index authority
    survives partial failure; an equal runtime key is not an exact invocation
    substitute across generations.
11. *What compatibility expectations apply?*  Preserve public commands,
    successful event order, durable session/board association, provider
    semantics, pending retained messages, and visible errors.  New process-local
    record fields require restart; no compatibility alias or id fallback is
    appropriate.
12. *What legacy code can be removed now?*  Keep the global invocation scan and
    id-based board rediscovery removed.  Replace the outer rollback's current
    =gethash target= rediscovery and the swallow-after-gate-loss path with exact
    lease completion.
13. *Where are expected errors handled, and where do unexpected errors
    surface?*  Invalid/stale/replaced states are rejected at owner boundaries.
    Initiating notification/board errors remain visible.  The board index
    inverse currently swallows an unexpected cleanup error after losing retry
    authority, which is a finding.
14. *What tests prove core behavior independently?*  Direct owner ERT,
    runtime/service/composition suites, full fixture-enabled ERT, graph/static/
    compile checks, retained graphical evidence, and twelve independent probes
    cover common and adversarial behavior.  Missing direct board/Work
    regressions must prove event/index partial failure, repeated abort, exact
    removal substitution, replacement preservation, and retry.
