The cumulative Feature 91 owner direction remains substantially sound:

=e-board= is still the correct owner of event sequence, board relations,
subscription indexes, routing, and settlement.  =e-board-runtime= is still the
correct adapter owner for attachment generations, exact invocation leases,
pending admission composition, pickup/activity/producer state, and harness
delivery.  The defects do not justify a new generic transaction layer or a
reverse dependency.  They show that the exact receipts and pending transaction
lifetime inside those existing owners are incomplete.

The candidate's exact Work path is a real improvement.  Runtime registration
returns =e-board-runtime-invocation-lease=, board stores that opaque lease as the
effect target, the Work admission path checks the same lease after board return,
and apply/drop operate only on its captured invocation object.  Same-key
replacement during count notification or board admission cannot be applied or
cancelled by the old Work attempt.  The committed return/signal tests and an
independent stale-lease probe confirm this.

The board receipt design closes only whole-operation gaps.  The current event
and index receipts are constructed after list mutation, and their inverses set
=removed-p= after multiple mutations.  Independent probes at the individual
mutation boundaries strand state without retry authority.  Two-token probes
also show that a raw predecessor cell can be detached while retaining a =cdr=
that points at the target; the inverse then reports success without unlinking
the live target, corrupting tail/count or queue state.  These are exact owner-
state failures, not speculative allocation concerns: the review contract
explicitly requires before/after-mutation faults, interleaved unrelated events,
tail removal, repeated abort, and exact replacement preservation.

The runtime pending slot is scoped too narrowly.  A board call may reenter
attachment retirement and replacement before returning its error.  The outer
handler then writes the unfinished board token onto the already-dormant old
attachment.  That object is no longer in the runtime catalogs, so later public
enrollment, retirement of the replacement, re-ensure, and submit never retry
the token.  Durable session/board association remains intact, but process-local
board relations can remain stale until an out-of-band holder of the old object
calls a private retry helper.

Aggregation reveals the same missing transaction boundary outside prepared
Work.  It registers an exact invocation lease, calls the nontransactional board
aggregation API, and returns without rechecking the lease.  A reentrant
replacement can therefore make the old call report success with a stale board
route; a postcommit signal drops the runtime lease but leaves the aggregation,
work index, event, and possible timer/classifier authority behind.

All earlier attached-turn, drain, graph, staged retirement, invocation
terminalization, pickup generation, producer/activity, subscription-token, and
grouped-classifier findings remain resolved.  The chat presentation, session,
harness, OpenAI, MCP, base, context-estimate, and public Round 5 seams were not
changed by this candidate and remain supported by the cumulative source audit
and the independently passing full suite.  No credentialed provider call was

** TODO Medium: Event receipts can lose or falsely acknowledge exact log authority

*** Expected behavior

An admission token must own the exact event before the first visible event-list
mutation.  Repeated abort must complete after a fault at any before/after-
mutation boundary, preserve unrelated/replacement events, keep head/tail and
message-count consistent, and leave sequence allocation monotonic.  A raw cell
that is no longer part of the board's live list must not authorize mutation or
successful acknowledgement.

*** Observed behavior and evidence

=e-board--append-event= mutates predecessor/head at
=lisp/core/e-board.el:512-516= and tail at line 517, then constructs and pushes
the receipt at lines 518-521, then writes message-count at lines 522-523.  A
constructor/push fault therefore leaves a linked event with no receipt.

=e-board--remove-event-receipt-exact= at lines 533-565 unlinks the exact cell,
possibly updates tail, removes message-count, and only then sets =removed-p=.
A failure after unlink leaves the receipt nonterminal but destroys the head/
predecessor proof needed by retry.  Its predecessor branch at lines 540-543
checks only =(eq (cdr previous) cell)=; it never proves that =previous= is still
in the live board list.

Independent witnesses reproduce all three failures.  Forward receipt failure
leaves one =posted= event with no count/receipt and retry appends another.
Inverse message-count failure leaves an empty event list plus a stale count and
an unacknowledged receipt that repeated abort rejects.  With two interleaved
tokens, aborting the earlier token detaches the later token's predecessor;
aborting the later token marks every receipt removed while its event remains
live, tail points at the detached predecessor, and the live event's count is
removed.

Committed tests at =test/e-board-test.el= cover a wrapper fault only after the
whole append returns and a non-removing interleaved event.  They do not inject
faults after head/tail mutation or detach the recorded predecessor.

*** Why it matters

The board event log is the causal source for projections, continuation,
activity, routing, and diagnostic replay.  A ghost or falsely removed event can
be replayed without its count/index facts, disappear from the tail chain, or
leave board maps/Work observers alive after a rejected pre-run attempt.  This
contradicts =F91-OWNER=, =F91-RUNTIME=, =F91-PRESERVATION=, and the current
=architecture.md:242-251= claim that the inverse is exact and idempotent.

*** Smallest corrective direction

Create and register exact event receipt authority before the first list
mutation.  Make forward and inverse progress explicitly retryable at each
mutation boundary.  Replace the unproven raw-predecessor authority with a
board-owned live exact link/node design that can distinguish a live predecessor
from a detached one in constant time.  Acknowledgement must record each
completed stage before any later fallible callback can obscure it.  Preserve
monotonic =next-seq=, unrelated event order, and no-scan/no-id-fallback behavior.
Add direct tests for every head/link/tail/count boundary, two-token abort order,
unrelated events, repeated abort, replacement board objects, and idempotence.

** TODO Medium: Index receipts can lose or falsely acknowledge exact queue authority

*** Expected behavior

The admission token must own an exact work-index cell before insertion becomes
visible.  Abort must retry from every partial inverse state, preserve a same-key
replacement queue, and remove only its live exact cell.  A detached predecessor
must not authorize a successful removal.

*** Observed behavior and evidence

=e-board--index-work-subscription= obtains/creates the queue at
=lisp/core/e-board.el:1423-1424=, mutates head/link at lines 1427-1429 and tail
at line 1430, then creates/pushes the receipt at lines 1431-1437.  A receipt
construction fault leaves an indexed id with no inverse authority.

=e-board--remove-indexed-work-subscription= at lines 1451-1484 unlinks the
cell, updates tail, optionally removes the queue hash entry, and only then sets
=removed-p=.  A fault removing the empty queue leaves a mapped empty queue and
a receipt whose predecessor/head proof is already gone.  Its previous-cell
branch at lines 1465-1471 also trusts =previous.cdr= without proving
=previous= belongs to the current queue.

Independent probes show receipt-construction failure followed by retry produces
duplicate equal ids; inverse map-removal failure cannot be completed by repeated
abort; and two interleaved tokens can both report removed while the second id
remains live with a detached tail.  The candidate correctly preserves an
entire replaced queue object; that does not repair partial mutation within the
same live queue.

*** Why it matters

Invocation and aggregation classifiers consume these FIFO indexes.  Duplicate,
ghost, or falsely removed ids can activate a stale lease, classify twice,
strand board maps, or block same-id retry.  The failure violates the exact
receipt and substitutability promises in =F91-OWNER= and =F91-RUNTIME=.

*** Smallest corrective direction

Register a board-owned exact queue-cell receipt before mutation and represent
live link ownership so it survives predecessor removal without scanning by id.
Stage/acknowledge head, link, tail, and map progress so repeated inverse resumes
after any individual fault.  Keep the current exact queue-object replacement
fence.  Add direct one-cell and multi-cell tests for both abort orders,
construction failure, each inverse boundary, duplicate prevention, repeated
abort, same-key queue replacement, and normal FIFO behavior.

** TODO Medium: Internally created board admission tokens become unreachable on cleanup failure

*** Expected behavior

Public board operations must either finish their exact rollback before
signaling or retain/expose the same opaque token through a real owner seam until
rollback completes.  The initiating error must remain the surfaced error.  A
caller that did not supply a runtime token must not be left with ghost board
state it cannot name or retry.

*** Observed behavior and evidence

=e-board-enroll-work= creates a private token when =:admission= is absent at
=lisp/core/e-board.el:1862-1864=.  Its error handler calls discard directly at
lines 1898-1900, so a cleanup fault replaces the initiating error and the local
token is lost.

=e-board-subscribe-invocation= always creates a local admission at lines
1915-1920.  Its error handler at lines 1940-1944 swallows cleanup failure,
resignals the initiating error, and loses the only token while map/index state
remains.  =e-board-enroll-invocation-work= likewise creates a local token when
none is supplied at lines 1965-1968 and swallows incomplete cleanup at lines
2025-2029.

Independent direct public-call probes reproduce masked primary error plus a
ghost =posted= event/Work observer, and preserved primary error plus a ghost
invocation/index whose same-id retry raises =e-board-id-conflict=.  Source
inspection proves the same loss in combined enrollment without external
=:admission=.

*** Why it matters

These are public, consumer-shaped board APIs, not runtime-private helpers.  A
direct caller has no way to recover the exact token after a signaled call, so
the documented retryability is conditional on an unstated stronger
precondition.  That makes the APIs non-substitutable and leaves board state
that can affect later classification and retry.

*** Smallest corrective direction

Give internally staged calls the same exact recovery lifetime as externally
staged calls.  Either keep unfinished internal tokens in a board-owned pending
transaction catalog that is checked before related mutation, or require and
return one explicit staged token through a consumer-shaped API and remove the
unsafe convenience path.  Preserve the initiating condition while surfacing
that cleanup remains pending; do not swallow an unreachable lease, reconstruct
by id, or scan globally.  Test every direct API without an external token,

* Architecture review

** Ownership, dependency, and aggregate-design comparison

The source layout still matches semantic owners:

- Work owns prepared/running/terminal carrier state and exact observer/hook
  identity operations.
- Board owns event sequence, event/index membership, work/invocation/
  aggregation relations, classifier scheduling, and their inverses.
- Board runtime owns attachment-generation authorization, invocation leases,
  unsettled accounting, harness-facing Work enrollment, and cross-owner
  transaction composition.
- Registry owns board/client/participant catalogs and exact route retirement.
- Chat service owns presentation clients and delegates terminal runtime cleanup;
  presentation shells do not mutate runtime/board private maps.

The complete graph confirms stable direction: runtime depends on registry and
board; board depends only on Work; no stable domain owner depends on chat,
provider, persistence, or transport.  The candidate adds no =require= edge and
no private cross-owner production call.  A generic shared transaction module
would be speculative and would split owner state.  Corrections should stay in
board/runtime with narrow opaque tokens.

The retained large production roots still have causal proofs.  Board's sequence
and relation transitions must commit together; runtime's attachment generation,
queues, invocation counts, and retirement must reconcile together.  Session
aggregate and presentation roots keep their already extracted pure/adapter/
component owners.  The only newly unproved large root is the direct runtime
test file, not a production owner.

** State lifetime, interfaces, side effects, compatibility, and errors

The new invocation lease is process-local and correctly owned by runtime for
one callback authority.  Event/index receipts are process-local and correctly
owned by board for one admission, but their actual authority begins too late
and ends too early.  Pending cross-owner cleanup currently lives on one
attachment object; the failing reentry shows its required lifetime is the
runtime admission transaction, which can outlive that attachment's catalog
membership.  Aggregation admission needs the same exact lease/board-transaction
lifetime as prepared Work.

Core policy remains isolated from provider, filesystem, network, display, and
session-storage side effects.  Event/index/hash/timer mutation is itself board
owner state and should not move outward.  Runtime notification and harness
delivery remain adapter-side.  The correct fix is stronger owner-local
mutation staging, not error swallowing in a higher shell.

The lease/token interfaces are semantically real and narrow.  Their current
implementations are not fully substitutable: direct board callers have a
stronger hidden precondition (supply/retain an external token), event/index
receipts cannot satisfy their retry contract after partial mutation, and
aggregation accepts less exactness than Work.  Correct those semantics rather
than adding broad callbacks, bags, unsupported operations, or id fallbacks.

Compatibility requirements are unchanged public commands, successful event
order, durable session/board association, retained pending messages, provider
request semantics, and visible initiating errors.  No durable session/board/
wire record changed; the added structs/fields are process-local.  Loaded core
record/function definitions require a normal Emacs restart after eventual
acceptance.  No compatibility shim is appropriate.

Expected stale/revoked/replaced states should produce bounded domain errors.
Unexpected receipt/inverse faults must remain visible while exact retry
authority stays reachable.  Current direct Work enrollment masks the initiating
error; invocation/combined board paths and runtime preserve it by swallowing
cleanup, but then lose or mis-scope the token.  Neither outcome is acceptable.

* Design self-check

1. *If this package stopped here, is the project better off?*  Yes.  Feature 91
   has real owners, smaller facades, an acyclic graph, exact Work inverses, and a
   materially safer invocation lease.  It is not complete because five owner-
   state contracts and one topology disposition remain actionable.
2. *What final direction does it move toward?*  Stable domain owners with
   presentation, provider, transport, persistence, and runtime adapters around
   them; one exact, retryable authority for each mutable lifetime.
3. *Which decisions are stable, likely to change, or uncertain?*  Board owns
   event/index relations and runtime owns attachment/invocation composition;
   those are stable.  Exact node/progress representation is local and
   reversible.  No speculative generic transaction framework is warranted.
4. *What component owns each changed behavior, and why?*  Board owns receipt
   acquisition/inverse and direct board recovery because it alone mutates those
   structures.  Runtime owns admission transaction reachability and lease
   postchecks because it alone knows attachment generations and unsettled
   callbacks.  Tests own only proof.
5. *Does coupling increase or decrease?*  The cumulative feature decreases
   coupling.  Opaque leases/receipts are narrow.  Current direct APIs narrow
   behavior incorrectly when no external token exists; closing that defect can
   stay owner-local without a new dependency.
6. *Did any dependency point the wrong way?*  No.  The reproduced graph is
   163/709/acyclic, production cross-owner private refs are zero, and the
   candidate adds no require edge.
7. *Could a side effect move outward?*  Provider, persistence, transport, and UI
   effects already remain outward.  Event/index/hash/timer mutation is board
   state and invocation notification is runtime adapter state; moving either to
   chat/service would weaken ownership.
8. *What state is added or mutated, who owns it, and how long should it live?*
   Runtime invocation leases live for one exact callback.  Board receipts live
   from before first mutation through complete abort/commit.  Pending admission
   records must live for the cross-owner transaction even if its original
   attachment retires.  All are process-local/rebuildable; durable association
   remains session-owned.
9. *What is the performance impact?*  Current success adds constant object/hash/
   list work; owner smoke is stable.  Receipt correction can remain O(1) per
   owned cell and recovery O(number of this transaction's cells).  No global
   scan, unrelated-history walk, or synchronous durable write is justified.
10. *Are abstractions real and implementations substitutable?*  Work observer
    inverses, invocation leases, and board admission receipts are real.  Event/
    index receipts, direct internal-token calls, and aggregation admission are
    not yet substitutable under their promised fault/retry preconditions.
11. *What compatibility expectations apply?*  Preserve public commands,
    successful event order, durable/wire formats, session/board association,
    pending retained messages, provider behavior, replacements, and initiating
    errors.  Core process-local shape changes require restart, not shims.
12. *What legacy code can be removed now?*  Keep global invocation scans,
    id-based receipt reconstruction, private receiver fallbacks, forwarding test
    roots, and obsolete 707-edge claims removed.  Replace unsafe internal-token
    convenience behavior if it cannot meet the public contract.
13. *Where are expected and unexpected errors handled?*  Stale/replaced/revoked
    authority is rejected at exact owner boundaries.  The initiating board/
    notification error must surface.  Unexpected cleanup errors must keep an
    exact reachable pending token and remain diagnosable; they must neither mask
    the primary error nor be swallowed after authority is lost.
14. *What tests prove the core independently?*  Direct board/registry/runtime/
    Work suites, the affected 466-case composition batch, full 2,614-case ERT,
    compile/read/graph/private/duplicate checks, and eleven isolated probes cover
    current behavior.  Remediation needs direct mutation-stage, detached-link,
    internal-token, replaced-attachment, and aggregation tests, plus independent
    discovery after the test split/disposition.
