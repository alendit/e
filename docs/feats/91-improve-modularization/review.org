** TODO Medium: Invocation admission notification failure leaves an unreachable live target

*** Expected behavior

=F91-RUNTIME= and the ownership guidance require one process-local owner for an
invocation target, its table entry, its unsettled count, and its board
relation.  If an unexpected notification error surfaces, the initiating
enrollment must either have completed with usable authority or have rolled
back to a retryable state.  Quiescence must not count work that no board
operation or caller can settle.

*** Observed behavior

=e-board-runtime--register-invocation= at
=lisp/core/e-board-runtime.el:1325-1351= inserts the exact target at line 1338
and calls =e-board-runtime--adjust-unsettled-count= at line 1350.
=--adjust-unsettled-count= at lines 313-332 increments the invocation count
and then calls fallible transition observers.  If an observer signals, the
register function exits without returning its target.

The actual caller =e-board-runtime--enroll-work= at lines 1689-1723 installs
work hooks first and binds =target= by calling the register function at lines
1715-1716.  Its rollback =condition-case= begins only at line 1717, after that
binding succeeds.  A notification fault therefore never reaches
=--drop-invocation= at line 1721.

The independent actual-enrollment probe observed:

#+begin_example
runtime invocation table: exact open target remains
runtime invocation count: 1
board observed work: absent
board invocation relation: absent
quiescence blockers: ((runtime.invocations . 1))
same enrollment retry: fails before adopting/removing the target
#+end_example

Attachment retirement can later discover and cancel the orphan by scanning its
exact invocation records, but that unrelated terminal action is not a retry or
rollback for the failed enrollment.

*** Why it matters

A bounded monitoring/quiescence observer fault turns a rejected tool or
aggregation enrollment into live runtime state with no corresponding board
owner and no returned target.  It blocks controlled quiescence indefinitely
until the attachment is retired and leaves the prepared work handle partially
configured.  The unexpected error is visible, but the owner state is neither
committed to the caller nor retryable.

*** Smallest corrective direction

Make invocation admission one staged owner transition across work-hook setup,
runtime target/count installation, and board enrollment.  On a notification
error before the target reaches the caller, remove only that exact invocation,
restore its count exactly once, and unwind any just-installed work observer
state before re-signaling.  Do not swallow the notification, rediscover by
session/id, or weaken the target uniqueness precondition.  Add a regression
through the real harness work-enrollment function that injects both the private
transition callback and later hook faults and proves: no runtime target, count
zero, no board work/invocation, no quiescence blocker, and a clean retry.

* Architecture review

** Ownership, dependencies, and side effects

The physical ownership model remains appropriate.  Board owns participant,
subscription, classifier, pickup, routing, and retained message state.  Runtime
owns attachments, endpoint generations, producer/FIFO adaptation, activity,
invocations, reconciliation, timers, and harness-event translation.  Registry
owns live board/client/participant catalogs.  Chat service owns bindings,
clients, observer cursors, presentation subscriptions, and service timers.
Session owners retain only durable association, journal, identity, metadata,
provider-anchor, board policy, and storage state.

The literal require graph is acyclic, and new calls point from runtime toward
the stable board semantic.  Board does not depend on runtime.  No service
reaches runtime-private maps; no provider, persistence, transport, display, or
tool side effect moved into core policy.

The open defect is transition ordering inside the existing runtime owner.  It
does not justify a coordinator module, callback registry, service locator,
generic transaction abstraction, or reverse board dependency.

** Mutable state, interfaces, and compatibility

Classifier routes and authorized maps live for one bounded input transaction.
Pickup participant lifetime lives until that process-local pickup becomes
terminal.  Pickup scheduler generation lives for the runtime process and
fences retained callbacks.  Invocation records/counts live from admitted work
through exact terminalization.  These are the smallest intended lifetimes.

The terminal transition now keeps invocation state/table/count together, but
admission can still expose count/table state without returning authority or
creating the board relation.  That is the sole remaining ownership mismatch.

=e-board-pickup-route-current-p= is narrow and consumer-shaped.  Exact
attachment/participant/subscription retirement and attached-turn operations
remain substitutable across current, closing, closed, stale, and replacement
objects.  Invocation enrollment is not yet substitutable under a fallible
transition observer because its error postcondition is narrower than the
normal caller contract.

No durable/wire compatibility path is needed.  Obsolete id-only teardown,
manual partial route cleanup, replacement-port fallback, and private bridges
remain removed.  Unexpected errors should continue to surface; the corrective
work must make the already-mutated owner state resumable or rolled back before
re-signaling.

* Design self-check

1. *If this package stopped here, would the project be better off?*  Yes.  The
   modular owners, exact terminal transitions, scheduler generation, and
   classifier lifetime fence are material improvements.  It cannot be accepted
   as complete with one non-retryable admission state.
2. *What final direction does this move toward?*  Stable application facades
   over cohesive owners, with one exact lifetime from presentation binding
   through runtime attachment/operation, registry membership, and board route.
3. *Which decisions are stable, uncertain, or likely to change?*  Exact
   lifetime, downward dependency, durable formats, error visibility, atomic
   routing, and quiescence accuracy are stable.  Provider/storage/canvas policy
   remains local.  The rollback mechanics for a fallible invocation admission
   observer are owner-local and need no speculative framework.
4. *What component owns this behavior, and why?*  Runtime owns invocation
   target/table/count because they share attachment generation and quiescence.
   Board owns classification/pickup route state because it shares one atomic
   routing transaction.  The open correction belongs in runtime admission.
5. *Does this change increase or reduce coupling?*  Static coupling is reduced:
   runtime consumes one board boolean semantic, and board knows no runtime
   record.  Hidden temporal coupling remains only between work-hook setup,
   runtime invocation registration, notification, and board enrollment.
6. *Did a dependency start pointing the wrong way?*  No.  The 709-edge graph is
   acyclic; no changed board source depends on runtime/service/provider/UI, and
   no new cross-owner private production reference exists.
7. *Could any side effect move outward?*  Provider, I/O, persistence, display,
   and harness delivery effects remain at adapters/shells.  Timer scheduling
   and invocation callbacks are runtime edges; route commit is board state.
   Moving the open rollback into chat or board would weaken ownership.
8. *What state is added or mutated, who owns it, and how long should it live?*
   Route objects/maps last one classifier; participant lifetime lasts one
   pickup; scheduler generation lasts the process; invocation table/count lasts
   one admitted invocation.  All are reconstructible.  Only failed admission
   currently lets invocation state outlive its usable authority.
9. *What is the performance impact?*  Route validation is bounded by existing
   fixed caps, stale settlement is one map lookup, and timer validation is one
   integer comparison.  Retirement remains proportional to exact owned work.
   The correction can remain constant/local; no global scan or durable write is
   justified.
10. *Are abstractions real and implementations substitutable?*  Board
    route-current, exact retirement, and scheduler generation represent real
    variation and preserve their preconditions.  Invocation enrollment is not
    fully substitutable under a signaling observer until failure leaves the
    same clean/retryable postcondition as other rejected admissions.
11. *What compatibility expectations apply?*  Preserve public commands,
    durable events/session files, pending retained messages, association,
    provider semantics, and explicit errors.  Core struct changes require
    restart.  No compatibility alias, id fallback, or weakened precondition is
    appropriate.
12. *What legacy code can be removed now?*  Previously removed id-only/manual
    teardown and private bridges stay absent.  The correction should remove any
    partial registration state on failure, not add a legacy recovery path.
13. *Where are expected errors handled, and where do unexpected errors
    surface?*  Stale/revoked/detached/closed/replaced states are handled at
    owner boundaries.  Callback and notification faults remain visible.
    Terminal invocation faults now leave coherent state; admission notification
    faults surface before rollback and are the open finding.
14. *What tests prove core behavior independently?*  Direct owner ERT,
    attached-turn/service/composition tests, full fixture-enabled ERT,
    graph/private/duplicate/static checks, retained graphical evidence, and ten
    independent phase/callback probes cover the design.  The missing committed
    regression is an actual work-enrollment notification fault proving clean
    runtime, board, handle, and quiescence state plus retry.
