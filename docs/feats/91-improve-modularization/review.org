* Review summary

The cumulative architecture direction remains sound:

#+begin_example
e-chat-service -> e-board-runtime -> e-board-registry -> e-board -> e-work
#+end_example

=e-board= remains the semantic owner of board sequence, relations, routing,
classification, and settlement.  =e-board-runtime= remains the application
owner of attachment generations, exact invocation leases, cross-owner pending
admissions, and harness delivery.  The remediation should preserve those state
owners.  Physical ownership no longer justifies keeping all implementation in
one file, however: =e-board.el= grew from 4,237 to 5,371 lines and now contains
a large, separately changing receipt/admission subsystem.  The same staged
linked-list protocol was implemented four times with different retry
semantics, and the independent boundary probes fail in all four families.
That is concrete evidence for a board-specific private subowner, not a request
for a generic transaction framework.

The event and work-index receipt changes close the original acquisition and
detached-neighbour gaps.  They do not make every inverse stage resumable.  A
fault after a middle physical unlink but before neighbour repair leaves a list
that is physically correct but receipt metadata that can never pass the retry
precondition.  A fault later at the event prefix-count or empty-queue map
removal has the same terminal result because one =inverse-stage= field is
overwritten as the inverse advances.  Terminal-classifier and deadline
receipts have no stage fields at all; forward and inverse failures strand
their tokens and routing counts.

Event rollback also removes the sequence-to-message-prefix checkpoint.  Since
sequence allocation is intentionally monotonic, that sequence becomes a gap.
An observer explicitly starting at the gap is initialized at message index
zero and replays messages older than its requested cursor.

Both pending-admission catalogs have real ownership but incomplete transaction
semantics.  The Board catalog stores only =t=, so a nested public Board call can
recursively abort the admission still executing on the outer stack; the outer
call then reports success with an object absent from the Board map.  Runtime
catalog publication and completion mutate a primary table and two secondary
indexes without stages.  A fault can leave either an undiscoverable primary
record and invocation lease or permanent secondary index entries.  The
aggregation path publishes that catalog record outside its error handler.

Aggregation admission captures its map, work indexes, events, classifier,
deadline, timer, and activation, but not the pending effect queue and scheduler
authority created for an already-ready aggregation.  If the effect scheduler
signals before accepting the drain callback, abort removes the aggregation but
leaves one unsettled effect and =effects-scheduled=t=.  Later healthy
aggregations append behind that stranded bit and never schedule a drain.

The new test split is sound.  The runtime and admission roots discover
independently, neither is forwarding-only, support contains fixtures rather
than tests, and the union preserves all 100 historical runtime test names plus
one new regression.  Full ERT is green with fixtures.  Those suites do not
exercise the individual mutation gaps above; the twelve independent probes do.

** TODO Medium: Receipt inverses and classifier/deadline queues are not resumable at individual mutations

*** Expected behavior

=F91-OWNER=, =F91-RUNTIME=, =F91-PRESERVATION=, the candidate plan, and
=docs/architecture.md:252-265= require exact authority before mutation and an
idempotent retry after a fault immediately before or after every map, list,
head, link, neighbour, tail, count, scheduler, or routing mutation.  A retry
must neither scan by descriptive id nor touch a replacement.

*** Observed behavior and evidence

- Event inverse accepts an already-unlinked cell only while
  =inverse-stage= is =unlinking= or =unlinked=
  (=lisp/core/e-board.el:966-1012=).  The physical unlink occurs at
  =:1051-1060=, neighbour metadata is repaired later at =:1087-1100=, and the
  same stage field is then overwritten for tail, count, and unregister at
  =:1103-1138=.  A =setcdr= that mutates and then signals leaves the physical
  list correct but neighbour metadata stale; retry can never prove the
  intermediate state.  The older count-removal witness also remains green:
  after event unlink, a fault at =event-message-count= removal cannot resume.
- Work-index inverse has the same structure.  Raw-unlinked proof is limited to
  =unlinking/unlinked= at =lisp/core/e-board.el:2218-2238=, physical unlink is
  =:2288-2299=, neighbour repair is =:2314-2326=, and =inverse-stage= is
  overwritten by tail/map/unregister at =:2338-2369=.  Both the middle
  post-=setcdr= witness and the older empty-queue =remhash= witness remain
  unrecoverable.
- =e-board-terminal-classification-receipt= at
  =lisp/core/e-board.el:224-229= and
  =e-board-aggregation-deadline-receipt= at =:324-329= have no forward or
  inverse stage.  Classifier queueing mutates both work indexes, node index,
  list links, tail, routing count, and scheduler at =:2380-2441=; its inverse
  mutates links, neighbours, tail, index, flags, and count at =:2443-2518=.
  Deadline queue/inverse do the analogous work at =:1978-2018= and =:509-570=.
  Independent before-node-registration and after-middle-unlink probes strand
  classifier and deadline receipts; retry still signals and routing remains
  nonzero.
- The direct 195-test suite covers whole-wrapper return/signal, either abort
  order, detached predecessor, and one link-ack gap.  It does not cover these
  primitive boundaries.  The architecture/audit claim that all four receipt
  families have resumable stages is therefore inaccurate at this revision.

*** Why it matters

The new pending catalogs cannot recover a token whose lower-owner receipt has
lost its own progress proof.  A single unexpected callback/map/list fault can
permanently block later Board mutations, leak routing/quiescence counts, or
leave indexes and lists disagreeing.  Exact replacement fencing alone is not
enough if the captured old transaction can never terminate.

*** Smallest corrective direction

Give each independently fallible Board mutation its own idempotent stage or
postcondition, including neighbour repair and map/count removal.  Do this in a
Board-specific receipt owner, not a generic transaction framework.  Apply the
same complete protocol to event, work-index, terminal-classifier, and deadline
queues.  Add a table-driven owner test that injects before and after every
primitive boundary and verifies head/tail/link/neighbours/map/count/scheduled
bits, repeated abort, either abort order, and exact replacement preservation.

** TODO Medium: Removing a staged event destroys a valid observer sequence checkpoint

*** Expected behavior

Event sequence allocation is monotonic across rollback.  An explicit observer
=start-seq= is a retained-history cursor, so a removed non-message sequence gap
must still map to the number of messages at or before that sequence.  It must
not replay older messages.

*** Observed behavior and evidence

Event inverse removes the sequence's prefix count at
=lisp/core/e-board.el:1116-1124=.  =e-board--message-count-through-seq= returns
zero for a missing sequence below the high watermark at =:3587-3592=.
=e-board-observer-subscribe= stores that result as =next-index= at
=:3594-3628=, and page preparation begins at =next-index + 1= at
=:3813-3860=.

The independent public-cursor witness posts one old output at sequence 1,
stages a non-message event at sequence 2, appends a later event, removes the
staged event, and subscribes with =start-seq= 2.  The observer is initialized
with =next-index= 0 and returns the old sequence-1 output.  The requested
cursor was strictly after that message.

*** Why it matters

Observer and chat drain cursors are public retained-history contracts.  A
rollback sequence gap can cause duplicate old delivery even though event
ordering and the sequence allocator appear correct.  This is a preservation
regression outside the admission caller itself.

*** Smallest corrective direction

Preserve a monotonic prefix-count checkpoint for consumed sequence values, or
provide another exact monotonic sequence-to-message-index mapping that covers
gaps.  Do not inverse that checkpoint with the removable event cell.  Add
direct Board and composed observer tests for gaps before, between, and after
messages, including page acceptance and restart-neutral behavior.

** TODO Medium: The Board pending catalog can abort an admission still executing on the outer stack

*** Expected behavior

An internally owned direct Board admission must remain reachable without
allowing a nested callback/public call to recursively mutate the transaction
still executing.  Reentry should fence or reject; the outer stack should
postcheck and perform its exact inverse before returning success.

*** Observed behavior and evidence

=e-board--begin-admission= stores only =admission -> t= at
=lisp/core/e-board.el:376-385=.  =e-board--recover-pending-admissions= snapshots
and aborts every token at =:400-425=.  Public aggregation calls recovery before
staging at =:2719=, with the same gate on Work/invocation entrypoints.

The independent witness uses the unsettled-count callback from an outer empty,
ready aggregation to invoke a nested public aggregation.  Nested recovery
aborts the outer token while =e-board-subscribe-aggregation= is still on the
stack.  The outer call then returns an =e-board-aggregation= object that is no
longer in =e-board-aggregations= and whose admission postcondition is false.
The catalog is empty and two effect closures are queued, so no later recovery
knows the outer success was invalid.

*** Why it matters

A successful public Board return is an authority handoff.  Returning a stale
object lets a direct consumer retain a cancellation/settlement handle that the
owner has already retired.  Recursive inverse also risks duplicate callbacks,
counts, and queue mutations on the active call stack.

*** Smallest corrective direction

Store an explicit in-flight/cancel-requested state in the Board catalog, as the
runtime catalog already does.  Nested related entry must fence or signal rather
than call the inverse recursively.  Every direct outer admission must postcheck
its exact token after fallible callbacks and abort before reporting success.
Test returning and signaling reentry from count, scheduler, publication, and
timer callbacks for Work, invocation, combined, and aggregation admissions.

** TODO Medium: Aggregation admission omits pending-effect queue and scheduler authority

*** Expected behavior

Ready and empty aggregation admission is one exact transaction.  If staging or
scheduling fails, the initiating error remains visible and no effect cell,
unsettled count, scheduled bit, callback authority, or Board relation survives
unless an accepted callback has exact fenced responsibility for draining it.

*** Observed behavior and evidence

=e-board--settle-aggregation= creates the activation and calls
=e-board--schedule-effect= at =lisp/core/e-board.el:2650-2682=.
=e-board--schedule-effect= appends the cell, increments unsettled effects, and
then calls the scheduler at =:1960-1968=.  The aggregation admission fields at
=:311-322= contain no effect receipt, cell, or scheduler generation, and abort
at =:573-657= cannot remove or reschedule an exact pending effect.

In the independent witness, an empty all-terminal aggregation is immediately
ready and the injected effect scheduler signals before retaining its callback.
The initiating error surfaces and map/index/event/activation cleanup completes,
but the Board retains one pending effect, =unsettled effects= 1, and
=effects-scheduled=t=.  After replacing the scheduler with a healthy one, a
second successful ready aggregation schedules no callback; both effects remain
stranded with count 2.  The audit claim that the ordinary drain will settle
this state is false when no callback was accepted.

*** Why it matters

This wedges Board quiescence and every later effect behind a stale scheduled
bit.  Runtime may have already dropped the exact invocation lease, so the
admission appears cleaned while its owner remains permanently nonterminal.

*** Smallest corrective direction

Make effect scheduling atomic around scheduler failure, or give the admission
an exact effect-cell/scheduler-generation receipt.  On a pre-acceptance signal,
remove only that cell, decrement once, and clear/reschedule the bit for any
surviving FIFO.  If a callback was accepted before signaling, retain a fenced
generation that cannot apply a replacement.  Test scheduler return/signal
before and after callback retention, FIFO neighbours, repeated abort,
cancellation, later healthy admission, and old/new callback order.

** TODO Medium: Runtime pending-admission catalog publication and completion are not exact transactions

*** Expected behavior

The runtime catalog's primary entry and exact Board/attachment indexes must be
published and removed atomically or resumably.  Any later enroll, retire,
re-ensure, or submit must discover the same token without a process-wide scan,
and original-error precedence must not leak a runtime invocation lease.

*** Observed behavior and evidence

=e-board-runtime--remember-board-admission= writes the primary table at
=lisp/core/e-board-runtime.el:1125=, then the Board index at =:1126-1130=, then
the attachment index at =:1131-1136=.  It has no stage or rollback, and its
existing-record branch at =:1105-1119= does not repair or assert either
secondary index.  Completion removes the primary first and then both indexes
at =:1139-1161=; it rediscovers all cleanup authority from the primary.

Aggregation calls =remember= at =lisp/core/e-board-runtime.el:2182-2183=
before its =condition-case= begins at =:2184=.  The Work path places the same
operation inside its handler.

Two independent witnesses prove both directions:

- a fault creating the Board secondary index leaves one primary record, no
  Board or attachment index, one unsettled invocation lease, and no Board
  aggregation.  Board recovery and attachment retirement cannot discover the
  record; retirement drops the lease but the primary record remains forever;
- a post-mutation fault removing the primary during completion leaves both
  secondary buckets holding the record.  Repeating completion is a no-op
  because the primary is gone, so both entries remain forever.

*** Why it matters

The catalog is the only recovery authority added to solve the prior orphaned-
attachment finding.  Partial publication recreates that orphan at the catalog
level and can leak invocation quiescence; partial completion leaks Board and
attachment objects and can trigger stale recovery attempts later.

*** Smallest corrective direction

Use a staged runtime-owned catalog record whose exact primary and secondary
memberships can be proved and repaired independently.  Put lease registration,
catalog publication, Board admission, postcheck, and cleanup under one
initiating-error handler for both Work and aggregation.  Completion should
carry the exact record/index authority through removal rather than rediscover
it only from the primary.  Existing-record entry must repair or reject missing
indexes.  Add before/after-mutation tests for all primary/bucket/record insert
and remove boundaries, both recovery scopes, retirement/replacement, retry,
and catalog garbage collection.

** TODO Medium: The new Board admission subsystem needs a physical private owner and bounded committed-state lifetime

Hot-path memory growth requires a first-principles justification.

*** Observed behavior and evidence

=e-board.el= grew from 4,237 to 5,371 lines in this one commit: 1,314 inserted
and 180 removed.  It now contains at least four independently changing clusters:
Board/event/admission state and inverses (roughly lines 1-1,192), Work and
settlement (1,193-3,164), subscriptions/observers (3,165-4,506), and
message/routing (4,507 onward).  Receipt/cross-owner admission mechanics change
for failure/retry reasons distinct from ordinary selector, observer, message,
or routing policy.  Four handwritten variants already diverge in stage
semantics, producing Finding 1.

Every ordinary event now allocates a 15-field =e-board-event-receipt= and keeps
it in =event-node-index= for the event-log lifetime
(=lisp/core/e-board.el:51-62= and =:843-925=).  Baseline ordinary events had no
receipt object.  There is no normal pruning/finalization path.  Every
aggregation also retains its =admission= at =:203-207=; committed tokens retain
event/index/classifier/deadline/activation transaction fields while the
aggregation remains in the Board map.  The three timing samples show no
immediate CPU regression but do not justify this permanent memory increase.

The current audit's old =e-board= colocation proof predates the 1,134 net-line
growth and says extraction would split sequence/admission state.  Physical
extraction need not transfer that state: a Board-private owner can operate on
the same aggregate behind the existing facade.

*** Why it matters

Feature 91 exists so maintainers can change one semantic owner through a
bounded module and owner-level tests.  A 5,371-line root with a new duplicated
transaction subsystem fails that goal and has already hidden correctness and
static-boundary gaps.  Permanent receipt/admission retention adds cost to every
ordinary event and completed aggregation, not only rare rollback paths.

*** Smallest corrective direction

Extract a Board-specific private receipt/admission owner behind the existing
=e-board= facade.  If cycle-free access requires it, first place Board record
and owner-local value definitions in a lower =e-board-state= contract; do not
invent a generic transaction, callback bag, or cross-domain framework.  Keep
Board sequence/routing/observer policy and all state authority in the Board
domain.  Move direct receipt/admission mechanism tests with the new owner while
retaining public behavior tests in =e-board-test.el=.  Add an explicit commit/
finalize step that drops transient rollback fields, and use a smaller permanent
link node only where later exact neighbour repair truly requires it.

** TODO Low: Runtime inspects owner-private fields of tokens documented as opaque

*** Expected behavior

Board admission tokens are consumer-shaped opaque contracts.  Runtime may pass
them to public enroll/abort/postcondition operations, but it must not depend on
generated Board record accessors or private representation.  The static gate

=e-board-work-admission-token= says callers must not inspect captured Board
objects at =lisp/core/e-board.el:1149-1153=.  Nevertheless runtime calls
=e-board-work-admission-cleanup-complete-p= at
=lisp/core/e-board-runtime.el:2150= and the explicitly private
=e-board-aggregation-admission--cleanup-complete-p= at =:2197= and =:2212=.
=e-board-runtime--abort-board-admission= already returns a boolean completion
result at =:1061-1082=.

The existing private/duplicate scanner reports zero because its owner table
omits both =e-board--= and =e-board-runtime--= families.  Direct source search
finds these three cross-owner token-representation references.

*** Why it matters

The representation breach couples runtime to the exact Board struct layout and
lets the two cleanup paths drift, as they already do between Work and
aggregation.  A false-zero architecture gate can allow the same class of
dependency to recur after extraction.

*** Smallest corrective direction

Use the public abort result to decide catalog completion, or expose one narrow
public Board-owned completion predicate if a second check is semantically
required.  Remove runtime access to generated/private fields.  Extend the
static owner map to include Board/runtime and the extracted admission owner,
then run it over production and composed-suite boundaries.

*** Why it matters

Dead fallback paths expand the state space that every drain and retirement

Remove the receiptless and id-only private branches.  Treat a missing receipt

* Architecture review

** Ownership and dependency direction

The semantic ownership direction is still correct.  Board queue, event,
observer, routing, and settlement state belongs to =e-board=; attachment,
invocation, and cross-owner recovery lifetime belongs to =e-board-runtime=;
Work hook/carrier identity belongs to =e-work=.  The 163/709 literal require
graph is acyclic and no new reverse =require= was introduced.

There is nevertheless one wrong-way representation dependency: runtime reads
Board admission internals.  Acyclic loading is necessary but not sufficient for
stable dependency direction.  The extracted Board admission module should sit
below the =e-board= facade, with only Board-owned opaque operations visible to
runtime.  It must not depend upward on runtime or presentation.

The Board-specific extraction in Finding 6 preserves one semantic owner and
one aggregate.  It rejects both bad extremes: leaving unrelated change reasons
in a 5,371-line root, and inventing a generic transaction service detached from
Board invariants.

** State lifetime, side effects, interfaces, compatibility, and errors

The new node indexes, receipts, pending catalogs, and generations are correctly
process-local and rebuildable; durable session/Board association and wire
records remain unchanged.  Their detailed lifetime is not yet minimal:
ordinary event receipts and committed aggregation tokens retain transient
rollback state for the aggregate lifetime, and partial catalog removal can
retain Board/attachment objects indefinitely.

Timer/scheduler/notification functions remain injected side-effect edges, and
normal reducers do not synchronously enter the harness.  The aggregation effect
scheduler fault shows the owner has not made the edge atomic: it publishes
queue/count/scheduled state before learning whether a callback was accepted.
Expected validation errors still surface, and most admission handlers preserve
the initiating error.  Unexpected inverse errors are currently swallowed at
some outer cleanup boundaries while leaving an unreachable or non-resumable
token, so the claimed error contract is incomplete.

The public Board enrollment/abort/current predicates are real, narrow
operations.  Runtime's private field checks weaken that contract.  The
receiptless/id-only fallbacks are not a supported substitution contract; they
narrow exact-generation guarantees solely for obsolete private shapes.

No durable migration or public compatibility shim is required.  Because the
candidate changes core process record shapes, using it requires a normal Emacs
restart.  That is preferable to retaining old private classifier/deadline
records in a running process.

* Design self-check

1. *If work stopped here, is the project better off?*  Partly.  Exact
   acquisition, neighbour identity, replacement recovery, aggregation token,
   and test split are improvements, but the candidate cannot be accepted while
   retry, cursor, quiescence, and catalog defects remain.
2. *What final direction does this move toward?*  One semantic owner per
   mutable lifetime, stable facades, Board-specific exact inverse operations,
   and cross-owner composition in runtime.  The next step is a bounded private
   Board admission owner plus complete transaction semantics.
3. *Which decisions are stable or uncertain?*  Board/runtime state ownership,
   durable formats, and public facades are stable.  Exact receipt-stage layout
   is still changing and should stay private/local.  A generic transaction
   abstraction is neither required nor justified.
4. *Who owns the behavior and why?*  Board owns event/index/classifier/
   deadline/effect mutation because those determine Board ordering and
   settlement.  Runtime owns attachment-scoped invocation and recovery
   composition.  Physical receipt code needs one Board-private owner because
   failure/retry is its cohesive reason to change.
5. *Does coupling increase or decrease?*  Exact tokens and Board/attachment
   indexes reduce descriptive lookup and scans.  Runtime's private accessor
   reads and the monolithic receipt implementations increase representation
   coupling; Findings 6 and 7 remove it.
6. *Did a dependency point the wrong way?*  The require graph remains acyclic,
   but runtime now depends on Board-private/generated token accessors.  That is
   a wrong-way representation edge even without a literal =require= cycle.
7. *Could side effects move outward?*  Scheduler/timer adapters are already at
   the edge.  Board must make its state change atomic with adapter acceptance;
   the scheduler call itself should stay injected rather than move into core
   policy or runtime.
8. *What state was added or mutated?*  Event/index/classifier/deadline node
   receipts, Board/runtime pending catalogs, stages, and scheduler/count state
   are process-local.  They should live only through rollback/recovery, except
   a minimal permanent link node needed by the append-only event list.  Current
   receipt/token and partial-index lifetimes are too long.
9. *What is the performance impact?*  Ordinary paths remain constant-time and
   three bounded samples are stable; there is no new ordinary global scan.
   CPU smoke does not justify one 15-field receipt per event, committed token
   retention, or permanent partial catalogs.  The scheduler defect can also
   turn a constant-time path into permanent non-progress.
10. *Are abstractions real and substitutable?*  Public Board token operations
    are real.  Runtime field inspection violates opacity, and legacy id-only
    drains weaken exact replacement behavior.  A Board-specific receipt owner
    is real; a generic transaction interface would be speculative.
11. *What compatibility expectations apply?*  Public commands, event ordering,
    durable session/Board formats, error visibility, and supported provider
    contracts must remain compatible.  Private process records require restart
    and have no compatibility promise.
12. *What legacy code can be removed now?*  Receiptless deadline/classifier
    drains, the id-only aggregation classifier branch, runtime token field
    reads, and committed transient admission fields after finalization.
13. *Where are errors handled?*  Validation remains at Board/runtime owner
    boundaries and initiating errors are usually preserved.  Unexpected
    primitive/scheduler/catalog errors currently expose non-resumable or
    unreachable state; fixes must surface the original condition while keeping
    exact cleanup authority reachable.
14. *What tests prove core behavior independently?*  Direct owner and split
    suites prove ordinary behavior and whole-operation faults; preservation and
    full ERT prove broad compatibility.  The twelve independent probes prove
    the missing mutation/reentry/catalog scenarios.  Remediation needs those
    witnesses converted into owner tests plus a complete before/after boundary
    matrix, so future design changes remain localized.

* Unresolved

Eight actionable findings remain:

1. four receipt/queue families are not resumable at individual mutation

2. event rollback deletes an observer sequence checkpoint;
3. Board catalog recovery recursively aborts an in-flight direct admission;
4. aggregation admission omits exact effect queue/scheduler authority;
5. runtime catalog publication/completion are not resumable transactions;
6. the new Board admission subsystem requires physical extraction and bounded
   committed-state lifetime;
7. runtime crosses the opaque Board token boundary; and
8. obsolete receiptless/id-only private compatibility paths remain.

There is no deferred architecture follow-up standing in for these defects.

for Features 87, 88, and 90 remains closed.
