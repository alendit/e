** TODO Medium: Terminal binding retirement does not fence the complete runtime lifetime

*** Expected

Repairable cancelled/faulted/expired main observers under unchanged
authorization must retain their pending cursor; a detached still-authorized
main client may be replaced coherently.  Terminal revoked, externally replaced,
muted/non-repairable, or closed receiver paths must terminate and release every
process-local lifetime owned by or admitted for that binding: harness/session
and board/log catalogs, exact main and subscriber clients/observers, scheduled
callbacks/timers, runtime attachment/session/endpoint entries, participant, and
ordinary subscriptions.  Durable session/board association must remain.  A
later explicit ensure/bind and submit must recover where the public contract
allows, and retirement must not mutate a replacement lease it does not own.

*** Observed

The positive repair half meets that contract.  The terminal half does not:

1. =e-chat-service--retire-binding= at
   =lisp/core/e-chat-service.el:331-372= clears chat-service catalogs and
   registry presentation clients but never releases the binding's
   =e-board-runtime= attachment, session/endpoint map entries, participant, or
   ordinary subscriptions.  Normal re-ensure re-enters
   =e-board-runtime-attach=, whose admission checks at
   =lisp/core/e-board-runtime.el:1549-1588= and 1685-1723 reject the retained
   session entry as busy.  Muted, revoked-then-restored, and fully closed cases
   reproduce this failure while preserving the durable board id.
2. The board-to-binding removal uses =puthash= with an empty list at lines
   362-365, retaining a nil-valued catalog key rather than removing every
   relevant catalog entry.
3. The binding stores only an =observer-drain-scheduled= boolean and the
   scheduler discards the timer handle.  Retirement cannot cancel a queued
   callback, and =e-chat-service--drain-observer= at lines 852-880 has no
   current-binding generation/epoch check.  A callback queued before retirement
   repairs the retired object and attaches one active orphan client afterward.
4. Main and subscriber detach calls identify clients only by id.  When an
   external actor has replaced the same id with a higher generation, retirement
   detaches the replacement rather than only the binding's exact lease.
5. The public drain at lines 1509-1532 calls retirement only when the binding is
   still live.  A board that independently entered =closing= therefore returns
   nil while retaining both service catalogs, log ownership, clients, and the
   active independent subscription.

The committed tests at =test/e-modernchat-test.el:1519-1751= cover repairable
cancelled/detached/expired paths and immediate service-close client cleanup.
They do not complete close and re-ensure, exercise muted/revoked/external
replacement, invoke a queued callback after retirement, assert runtime-owner
catalog/participant/subscription cleanup, or test an externally closing board.

*** Why it matters

This is the remaining cross-owner lifetime boundary.  A terminal presentation
lease can leave a process-local runtime admission permanently busy, so a
durably associated session cannot be reopened through its public application
service.  A stale callback can recreate a resource after ownership ended, and
id-only teardown can destroy somebody else's current lease.  Full ERT stays
green because its new lifecycle tests stop at immediate service catalogs and
clients rather than checking the complete runtime lifetime and recovery.

Severity is Medium: the ordinary healthy and authorized-repair paths work, but
terminal receiver/close paths can leak state, block recovery, or mutate the
wrong receiver and therefore cannot be accepted as a fixed point.

*** Smallest corrective direction

Give chat binding termination one explicit, idempotent lifecycle operation
coordinated with the board-runtime owner.  Either retain and deliberately reuse
the existing runtime attachment through a real recovery contract, or call an
owner-supported runtime retirement operation that removes its attachment,
session/endpoint entries, participant, and ordinary subscriptions before a
fresh ensure; do not reach into runtime-private maps or add a compatibility
fallback.  Preserve only the durable session/board association.

Fence deferred work with a cancellable timer handle and/or current-binding
generation so a callback for a retired object is a no-op.  Detach only the exact
client lease/object and generation still owned by the binding, remove empty hash
entries with =remhash=, and make the externally-closing path run the same
idempotent cleanup.  Add a table-driven regression covering repairable pending
cursor preservation plus muted, revoked/restored, external replacement,
external closing, completed close/re-ensure, independent subscribers, queued
callbacks, all runtime/service catalogs, and successful later submit where
allowed.  No durable-format or provider behavior change is needed.

* Architecture review

** Ownership, state, and side effects

Durable facts remain in session/board owners; process-local execution state
remains in harness/board runtime; provider/process/transport state stays in
adapters; buffer/window state stays in presentation owners.  Storage, network,
process, board publication, and display effects remain at edges.  Session value
policies and context estimation remain pure.

The repairable path now has a clear owner and smallest lifetime: chat service
repairs its presentation receiver while retaining the board-runtime attachment.
The terminal path ends only the chat-service portion.  Runtime attachment maps,
participant, subscriptions, queued callback, and registry clients can disagree
about whether the same binding lifetime exists.  The timer boolean is not an
ownership token, and a client id is not sufficient identity after replacement.

Cleanup side effects belong at owner boundaries.  Chat service should
coordinate through a board-runtime lifecycle API, while board runtime owns
mutation of its attachment catalogs/participant route.  Neither the service nor
tests should manipulate runtime-private maps as the production fix.

** Dependency direction and interfaces

The 709-edge local require graph is acyclic.  Facades depend on owners, owners
do not call facades; session values do not depend on aggregate/storage; context
lifetime points toward the pure estimator; MCP capability is transport
independent; OpenAI wire and transport are separate; Bash does not depend on the
file owner.

The remaining wrong direction is dynamic rather than a require edge: a
presentation service assumes that dropping its registry clients ends an
admission whose stable lifetime is owned by board runtime.  The correction
should be one narrow consumer-shaped end/reuse contract, not a generic lifecycle
framework.  Existing Round 5 seams remain semantically real and have direct
consumers/preconditions.

No durable or wire format changed.  JSONL/index/checkpoint order, session

* Design self-check

1. *If this package stopped here, would the project be better off?*  The owner
   decomposition and repairable lifecycle are better, but the package must not
   stop because terminal states leak runtime admission, block recovery, and can
   mutate a replacement lease.
2. *What final direction does this move toward?*  Stable application facades
   over bounded semantic owners, with one coherent lifetime operation across a
   chat binding's presentation lease and runtime admission.
3. *Which decisions are stable, uncertain, or likely to change?*  Durable board
   association, exact receiver identity, repairable states, and owner boundaries
   are stable.  Future SQLite, canvas, permission, and provider decisions remain
   local.  Terminal end-versus-reuse must be chosen explicitly from current
   public behavior, not hidden behind a speculative abstraction.
4. *What component owns the behavior, and why?*  Chat service owns presentation
   binding/subscription orchestration; board runtime owns attachment admission
   and its catalogs; board registry owns concrete clients/observers.  The missing
   operation is coordinated by chat service through those owner contracts.
5. *Does coupling increase or decrease?*  Physical coupling decreases overall.
   Terminal cleanup exposes hidden temporal coupling between chat catalogs,
   registry clients, runtime maps, and callbacks; one narrow lifecycle contract
   reduces it.
6. *Did a dependency point the wrong way?*  No static load reversal or cycle
   remains.  Dynamically, chat teardown bypasses the stable runtime owner of the
   attachment it expects to end; the fix must call inward to that owner rather
   than mutate its private state.
7. *Could side effects move outward?*  Existing I/O/display effects are already
   at adapters/shells.  Detach, participant removal, callback cancellation, and
   catalog mutation are teardown effects and should occur in their owning
   service/runtime boundary.
8. *What state is added or mutated?*  No durable state is added.  Repair mutates
   reconstructible process-local client/observer state.  Terminal paths mutate
   service maps but leave runtime maps, participant/subscriptions, or callbacks
   alive.  These must share one process-lifetime end/reuse decision while the
   durable association remains.
9. *What is the performance impact?*  Healthy drains stay page-bounded and the
   33-message probe shows no regression.  Exact teardown is proportional to the
   binding's owned clients/subscriptions, which is necessary work; a global scan
   or durable rewrite is not.
10. *Are abstractions and interfaces real and substitutable?*  Repairable
    receiver predicates and bounded drains are real and substitutable.  Current
    retirement cannot satisfy its claimed later-ensure postcondition, and
    id-only detach narrows identity guarantees.  A narrow runtime end/reuse
    operation is semantically real.
11. *What compatibility expectations apply?*  Preserve durable/wire/public
    behavior and the durable board id.  Remove process-local obsolete state;
    do not add a replacement fallback, alias, or unsupported-operation branch.
12. *What legacy code can be removed now?*  Remove nil board-map keys, unfenced
    scheduled work for retired bindings, and id-only lease teardown.  Previously
    removed private reach-through, callback globals, and duplicate policy remain
    absent.
13. *Where are errors handled?*  Exact receiver rejection and public terminal
    drain states are handled before progress.  Runtime busy after service
    retirement and silent wrong-client detach show expected lifecycle errors at
    the wrong layer; make teardown idempotent and let unrelated errors surface.
14. *What tests prove core behavior independently?*  Owner/mechanism suites,
    public composition, restart/storage, exact-port regression, 41-case chat
    service, 172-case board/runtime focus, graph/private/duplicate scans,
    graphical evidence, and full 2,566-case ERT are broad.  A table-driven
    terminal matrix must additionally prove every service/runtime catalog,
    participant/subscription/client/observer/timer postcondition and later
    recovery, including a queued callback and an external same-id replacement.
