* Findings

** DONE Medium: Prepared aggregation cancellation never completed its settlement admission

*** Expected behavior and historical failure

Cancelling an aggregation in =prepared= state must fence the queued external
reply.  Once the retained effect callback consumes its exact queue cell, the
Board must also have no pending admission for that cancelled settlement, the
aggregation must no longer retain the settlement token, and the activation
must retain no receipt graph.  Repeated cancellations must not accumulate
false pending authority.  This is an ordinary production path: the runtime's
aggregation cancellation closure calls =e-board-cancel-aggregation= directly.

At =dff11fab=, =e-board-cancel-aggregation= changed the aggregation to
=cancelled= before gating cleanup with =e-board-admission-current-p=.  That
projection predicate rejects cancelled aggregations, so the cleanup block could
not run.  The later stale callback released the consumed activation receipts
but could not remove the pending admission or owner token because the token had
never completed.

The independent public-path witness created a Board with captured classifier
and effect schedulers, enrolled and finished cheap Work, subscribed an
aggregation, drained classification to =prepared=, cancelled it, and invoked
the retained effect callback twice.  At =dff11fab= the single case reported
=pending=1= and the three-cancellation case reported =pending=3=, with zero
external dispatches.  That established an owner/resource-lifetime defect, not
duplicate external behavior.

*** Closure at =81148322=

The fix is at the owning Board settlement boundary:

- =e-board-cancel-aggregation= captures the exact retained token and evaluates
  =e-board-admission-active-p= before the terminal state transition
  (=lisp/core/e-board.el:1821=--1832=).
- After the cancellation events, it finishes that captured token, calls the
  exact settlement abort/completion path, and releases the aggregation and
  activation holders (=lisp/core/e-board.el:1851=--1858=).
- =e-board--settlement-abort-admission= rechecks exact token membership before
  completing the committed admission (=lisp/core/e-board.el:1431=--1437=), so
  reentry cannot complete another lifetime or perform a duplicate inverse.
- =e-board--settlement-release= clears the event receipt and completed owner
  token immediately, but deliberately retains a still-queued effect receipt
  until the stale callback consumes it (=lisp/core/e-board.el:1439=--1465=).

The strengthened facade regression captures the original admission and proves
the immediate postcondition: zero Board pending admissions, nil aggregation
owner token, completed captured admission, nil activation event receipt, and a
still-live queued effect receipt (=test/e-board-test.el:1454=--1488=).  It then
invokes the captured stale drain twice and proves nil activation receipts and

** Side effects and failure semantics

Scheduler, timer, Work, publication, and invocation-dispatch effects remain at
Board/runtime application edges.  Core route/readiness policy is side-effect
free except through injected callbacks.  The =applying= state is the one-way
boundary before external invocation dispatch; success is committed before an
optional diagnostic event, and a signalling dispatcher is terminal rather
than retried.  Count-observer and successor-scheduler errors stay visible while
object/generation checks fence retained callbacks.

Unexpected implementation errors are not broadly converted into success.
Diagnostic =effect-committed= or =effect-failed= history is deliberately
best-effort only after the external effect outcome is already known; this does
not authorize replay of the external operation.  The closure handles the normal
cancellation cleanup condition directly and adds no error swallowing or
journaling.

* Design self-check

1. *If work stopped here, is the project better off?*  Yes.  The source/test
   topology is substantially more navigable and the speculative transaction
   machinery is gone.  The corrected cancellation lifetime removes the sole
   terminal blocker without adding a new owner or mechanism.
2. *What final direction does this move toward?*  One semantic Board aggregate
   over stable state and exact admission owners, plus one attachment runtime
   over a small exact runtime-lifetime index.
3. *Which decisions are stable, uncertain, or likely to change?*  Exact object
   authority, callback generations, and at-most-once dispatch are stable.
   SQLite durability is future Feature 87 work.  Arbitrary primitive recovery
   was correctly removed rather than abstracted speculatively.
4. *Who owns the behavior and why?*  Board owns sequence/routing/settlement;
   admission owns short-lived relations; state owns values/counts; runtime
   admission owns exact runtime indexes; runtime owns attachment generation.
   The closure correctly stays in Board settlement and uses admission's exact
   lifetime predicate rather than moving policy into the lower owner.
5. *Does coupling increase or decrease?*  It decreases.  Raw receipts,
   catalogs, harness internals, provider details, and presentation state do not
   cross owners.  Interfaces are narrow and consumer-shaped.
6. *Did a dependency point the wrong way?*  No.  Require and semantic call
   graphs are acyclic; lower Board owners never import/call the facade, and
   runtime uses public Board/registry seams.
7. *Can side effects move outward?*  They already sit at Board/runtime injected
   scheduler, timer, Work, publication, and invocation-dispatch edges.  Moving
   settlement outward would weaken its one-way state/effect ordering.
8. *What state is added or mutated, who owns it, and how long should it live?*
   Receipt/token state is process-local and should end with admission or the
   stale callback that owns its queue cell.  Runtime records end with exact
   admission completion/retirement.  Cancellation now completes the token and
   owner lifetime immediately while the activation retains only its queued
   effect receipt until consumption.
9. *Performance impact?*  No new global scan or synchronous I/O.  Relation
   operations remain bounded, and 10,000 event/index checks complete with
   linear cardinality and zero payload-bearing receipts.  Prepared
   cancellations now release independently instead of accumulating pending
   tokens.
10. *Are abstractions semantically real and substitutable?*  Yes.  State,
    admission, runtime admission, attached-turn, provider, MCP, and base seams
    map to real consumers and do not require unsupported operations or weaker
    behavior.
11. *What compatibility applies?*  Public commands, events, durable formats,
    provider requests, and ordering remain compatible.  Core record changes
    require restart; no compatibility shim is justified.
12. *What legacy code can be removed now?*  The candidate correctly removed
    compact/root transaction nodes, arbitrary primitive recovery stages, six
    runtime catalogs, receiptless/id-only bridges, and their synthetic tests.
    No additional legacy production path was found.
13. *Where are errors handled or surfaced?*  Expected stale/cancelled callbacks
    are fenced locally.  Scheduler/count/dispatcher errors remain visible or
    become explicit terminal failure; post-effect diagnostics are best-effort
    only after irreversible outcome.  The normal cancellation postcondition is
    now handled directly through the exact active token.
14. *What tests prove the core independently?*  Direct state/admission/runtime
    owner suites, Board/runtime/registry composition, Modernchat consumers,
    production-path probes, full ERT, fresh loads, graph/private/name scans,
    and bounded shape checks.  The Board facade test now covers immediate and
    post-callback cleanup, repeated callback idempotence, and three independent
    cancellations without unrelated rewrites.
