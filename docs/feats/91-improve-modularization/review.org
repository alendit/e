* Findings

** TODO Medium: Stale attached-turn receiver bypasses its own authorization

*** Expected

=plan.org:499-503= requires a public attached-turn port shaped around attachment
authorization and concrete submit/steer/queue/abort/observation/output behavior.
=round-3-audit.org:44,59,117,151-161= further records one port per attachment,
stale-generation rejection, and mutation through that bound port.  The concrete
receiver therefore must be the port authorized for every mutating port method.

*** Observed

=lisp/core/e-harness-turn.el:177-210= implements
=e-harness-attached-turn-port-follow-up= and
=e-harness-attached-turn-port-publish-follow-up= by passing only the receiver's
harness/session values.  The inner functions at
=lisp/core/e-harness-turn.el:331-371= then call
=e-harness-turn--require-attached-port= without that receiver.  The helper at
=lisp/core/e-harness-turn.el:54-68= silently selects the active turn entry's
current port and authorizes it instead.

The focused reproduction above installed a valid current =good= port and called
both methods on a =stale= port whose authorizer always rejects.  Follow-up still
queued one item, and publish invoked the =good= publisher.  The existing direct
test at =test/e-harness-runtime-owner-test.el:137-191= covers rejected submit and
a positive publisher double, but not replacement/stale receiver fencing.

*** Why it matters

The port is an attachment-identity boundary, not a request to find any current
port for the same harness/session.  Ignoring the receiver lets an old attachment
mutate the replacement attachment's queue or publication lane.  It contradicts
the claimed stale-generation fence and makes port implementations non-
substitutable under their advertised precondition.

*** Smallest corrective direction

Thread the receiver port into the two inner follow-up operations and require
=e-harness-turn--require-attached-port= to authorize that exact object/token,
as submit, steer, queue, and abort already do.  Publish through the authorized
receiver's publisher rather than a rediscovered port.  Add direct regressions
with a valid current replacement and a rejected stale receiver, proving that
both calls signal =e-harness-board-attachment-required= before queue or
publisher side effects.  Rerun the direct owner, board/runtime/Bayesian, 485-case
preservation, and full ERT gates.

** TODO Medium: Faulted public drain reports work that can never progress

*** Expected

The Round 5 public API map and
=lisp/core/e-chat-service.el:1316-1346= define one bounded synchronous drain:
non-nil means another page remains, so embedding/performance consumers may call
it in a =while= loop.  A call that retires its subscription must terminate that
contract or signal a documented error; it cannot report progress that the same
subscription is no longer allowed to perform.

*** Observed

=e-chat-service--drain-subscription= at
=lisp/core/e-chat-service.el:632-663= retires a subscription when its callback
signals and deliberately does not accept the page.  The public wrapper at
=lisp/core/e-chat-service.el:1332-1346= then ignores
=e-chat-service-subscription-active-p= and returns only whether the unchanged
observer index is behind the board message count.  The reproduction returned
=t= with =:active nil=, a faulted state, cursor 0, and one message.  Repeated
calls cannot advance because the private drain is a no-op for an inactive
subscription.

The existing test at =test/e-modernchat-test.el:1428-1481= proves that a faulty
subscriber is retired without advancing another subscriber, but it does not
assert the public return.  Current =e-dev-perf= callers use the return value as
the =while= condition.

*** Why it matters

The new public seam has a false termination signal.  A synchronous shell,
fixture, or performance runner following its documented contract can loop
forever after a callback error, and the API gives no state change by which that
loop could recover.

*** Smallest corrective direction

Return non-nil only when the subscription remains active after the bounded
drain and its cursor is behind.  Apply the corresponding liveness rule to the
binding drain so both public pumps have the same terminal contract.  Add
regressions for callback-faulted, detached, unsubscribed, and stale/closed
inputs, including a bounded =while= consumer.  Rerun modernchat/chat-service,
performance smoke, preservation, and full ERT gates.

* Architecture review

** Ownership, state, and side effects

The decomposition generally follows the architecture rules.  Durable state
remains session-owned; process-local board/harness state remains with its
state-machine owner; request/transport state stays in adapters/Work; and
buffer/window state stays in presentation owners.  Storage, provider/network,
process, board-publication, and Emacs display side effects remain at the edges.
The new session policies and context estimator are pure value owners.

The attached-turn finding is not a reason to introduce another abstraction.
The concrete port is the correct owner boundary; its existing receiver identity
must simply be enforced on every mutating method.  The drain finding likewise
belongs in the current chat-service application boundary: termination must
reflect the service-owned subscription state.

** Dependency direction and interfaces

The complete 709-edge local graph is acyclic.  Facades depend on their owners;
owners do not call their facades.  MCP capability is transport-independent,
session value owners do not depend on aggregate/storage, and context budget and
lifetime point to the lower estimator.  The Round 5 seams are backed by real
consumers and do not form a service locator or generic callback bag.

Interface width is otherwise consumer-shaped: board messages cross as detached
envelopes; live attachments cross as buffer projections; temporary resource
writers request a validated path; and synchronous chat consumers request one
bounded drain.  The two Medium findings are precisely where implementation
preconditions fail to match those narrow interface claims.

** Compatibility and legacy removal

No new durable/wire format or provider behavior was found.  JSONL ordering,
replay, checkpoint/index behavior, session identity/metadata, board journal,
OpenAI/MCP wire behavior, and public command surfaces remain covered.  Removed
private names have no compatibility promise, and no private aliases, fallback
facades, duplicated estimators, or process-global adapter callbacks remain.
Feature 87 remains the sole owner of future SQLite migration/cutover.

* Design self-check

1. *Would the project be better off if work stopped here?*  The decomposition
   is materially better, but work must not stop at this revision because two
   new public/internal seams violate their own control/termination contracts.
2. *What final direction does this move toward?*  Bounded semantic owners behind
   stable application facades, with provider/storage/presentation variation at
   explicit edges and no shared private representation.
3. *Which decisions are stable, uncertain, or likely to change?*  Current
   ownership, durable compatibility, and port/drain semantics are stable enough
   to enforce directly.  SQLite, richer canvas state, permission policy, and a
   generic shell lifecycle remain local Planned/unconfirmed work; no speculative
   abstraction was added for them.
4. *Who owns each behavior?*  The source maps each state and side effect to a
   cohesive owner.  Harness turn owns attached execution; chat service owns
   binding/subscription drains.  The findings require those owners to enforce
   their declared semantics.
5. *Does coupling increase or decrease?*  It decreases overall through private
   edge removal and owner-local tests.  Rediscovering a replacement port from a
   receiver method weakens that reduction and must be removed.
6. *Did a dependency point the wrong way?*  No cycle or facade-to-owner reversal
   remains in the 709-edge graph.  The 707-edge documentation must be corrected
   so this conclusion stays reproducible.
7. *Could side effects move outward?*  They are already at storage, provider,
   process, board, and shell edges.  Follow-up authorization and drain
   termination are owner policy, not side effects to move elsewhere.
8. *What state was added or mutated?*  No durable state shape was added.  New
   public operations expose existing process-local port, cursor, attachment,
   and default/session-tmp behavior.  The port bug mutates the wrong attachment
   lane; the drain bug fails to reflect retired cursor state.
9. *What is the performance impact?*  No decomposition regression is established
   by the bounded smoke/full tests.  A faulted public drain can nonterminate,
   which is an unjustified regression in the new API and must be corrected.
10. *Are abstractions/interfaces real and substitutable?*  The owner boundaries
    are real, but the attached port and drain are not yet substitutable under
    their documented preconditions.  No unsupported-operation interface was
    found in OpenAI, MCP, or base owners.
11. *What compatibility expectations apply?*  Public behavior and durable/wire
    formats must remain stable; old private names need no shim.  Remediation
    should only enforce the already-documented port/drain contracts.
12. *What legacy code can be removed now?*  The feature already removed private
    consumer reach-through, callback globals, duplicate estimators/policies, and
    mixed mechanism copies.  No additional legacy path is required to fix these
    findings.
13. *Where are errors handled?*  Expected storage/provider/board errors remain
    owner-handled and unexpected errors surface.  The drain correctly retires a
    faulty callback but then misreports liveness; the port incorrectly avoids a
    receiver authorization error.  Both should surface/terminate at the owner.
14. *What tests prove the behavior independently?*  Direct owner/mechanism,
    public composition, restart/storage, preservation, graphical, and full ERT
    evidence is broad.  The two focused reproductions identify the missing
    independent regressions needed before acceptance.
