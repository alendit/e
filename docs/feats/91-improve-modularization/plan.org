* Goal

Make the physical Emacs Lisp modules reflect =e='s established semantic
components so developers and coding agents can understand, change, test, and
review one owner without loading unrelated responsibilities or depending on
another component's private state.

Preserve the existing macro architecture: the harness owns agent lifecycle,
sessions own durable conversation state, capabilities own semantic behavior,
layers package capabilities, backend adapters own provider behavior, and shells
own presentation.  Improve the physical decomposition and the interfaces
between those owners rather than introducing a new framework or changing
product behavior.

** Scenario portfolio

- =F91-S-FRESH-OWNER=: fresh-load each facade, exercise an owner-level public
  operation and its realistic composition, and search for forbidden private or
  reversed dependency edges.  It localizes a failure to load topology, owner
  behavior, or composition.
- =F91-S-PRESENTATION=: focused chat and Org Canvas ERT plus isolated graphical
  composer, transcript, activity, window, focus, and replay transitions.
- =F91-S-RESTART=: append and replay representative chat, board, context, and
  metadata records through the public session API, restart, and compare the
  recovered aggregate and current durable files with the baseline contracts.
- =F91-S-ATTACHED-TURN=: run ordinary and board-attached submit, steer, queue,
  abort, activity, and settlement partitions through public services.
- =F91-S-ADAPTERS=: compare existing OpenAI request/stream fixtures, both MCP
  transports, and base file/bash public tools before and after decomposition.
- =F91-S-RESIDUAL=: independently inventory every affected root and test root,
  challenge each retained material cluster with its smallest plausible complete
  private boundary, and verify the resulting dependency graph.

All required acceptance evidence is repository-controlled.  Live provider
capability evidence is not applicable because this package changes no provider
contract.  Load time and relevant hot-path measurements are observational
unless they reveal an actual regression against the baseline comparison.

** Large implementation rounds

The persistent implementer receives five owner-level rounds.  Internal moves
within a round are not separate acceptance cycles unless they expose a new

1. Presentation family: chat facade and five components, Org Canvas and other

2. Session family: aggregate, codec/replay, checkpoint/catalog, current JSONL

3. Runtime-control family: attached-turn port plus harness capability,

The order makes the session boundary stable before harness extraction and lets
the harness facade depend on that accepted lower-level contract.  Provider and
capability decomposition follows because it must preserve the accepted harness
and session composition, but does not define either owner.

* Blocking prerequisite

The operator selected this work as a prerequisite for all further
implementation.  No new slice, continuation slice, review remediation, or
opportunistic implementation in another feature may begin until this feature
is =Done=.

Features that are already =In-progress= or =In-review= keep those statuses
because the index records their factual lifecycle.  Their accepted commits and
tests become the baseline for this behavior-neutral decomposition; their
implementation lanes are paused.  After Feature 91 is complete, each affected
feature must rebaseline its source anchors and resume from its last accepted
semantic state.

* Why now

The conceptual architecture is stronger than the current source topology.
Several established components are compressed into very large files, and some
consumers extend them by reaching through private =--= symbols instead of a
narrow owner-shaped interface.

At the review baseline =986e3a8adc06=:

- production Lisp contains 84,124 lines across 128 files;
- the six largest production files contain 30,206 lines, about 36 percent of
  production Lisp;
- the six largest test files contain 39,892 of 92,837 test lines, about
  43 percent of the test tree;
- =e-chat.el= contains 10,687 lines and about 665 function or macro
  definitions;
- =e-org-canvas.el= references 38 distinct private =e-chat--*= symbols; and
- =e-board-runtime.el= references 11 distinct private =e-harness--*= symbols
  and installs two private harness callbacks.

These counts prioritize review; they are not architectural proof by
themselves.  The actionable defects are distinct change reasons hidden in one
physical unit, private cross-component dependencies, misplaced semantic
knowledge, and central dispatch that every variant must modify.

The source and test monoliths also impose a practical agent cost.  A focused
chat change may require navigating more than 22,000 source-and-test lines, while
harness and OpenAI changes each span more than 10,000 lines across their main
source and test files.

* Current assessment

** What is already good

- Core, capability, layer, shell, and backend-adapter responsibilities are
  conceptually distinct.
- Capabilities, resources, hooks, tools, context providers, layers, shell
  manifests, stores, and backend adapters are real extension seams with current
  consumers.
- Provider-specific auth, request mapping, streaming, retry, timeout, and
  cancellation policy remain behind backend adapters.
- =e-board= and =e-context-lifetime= contain substantial cohesive state-machine
  and domain-model behavior; their length does not justify mechanical helper
  extraction.
- Feature 70 established behavioral separation between chat transcript and
  composer state, even though that separation is not yet represented by
  physical modules and public component APIs.

** Confirmed modularization gaps

1. =e-chat.el= owns surface/window composition, composer editing, context
   references, transcript rendering, block navigation, activity rendering,
   session replay, overview rows, and workspace unread presentation in one
   feature.
2. Org Canvas reuses chat presentation by subclassing chat modes, mutating
   chat-private buffer state, and calling chat-private functions.  The intended
   reusable composer and transcript components therefore do not have stable
   consumer-shaped interfaces.
3. =e-harness.el= combines capability/layer derivation, resource-operation tool
   construction, activity projection and persistence, prompt queues, session
   options, compaction, context lifetime, provider-anchor acceleration, and
   top-level turn orchestration.
4. =e-board-runtime.el= invokes private harness operations for attached prompt,
   steering, follow-up, abort, activity, and final-output behavior.  It also
   mutates private global adapter slots, making the boundary implicit and
   process-global.
5. =e-session.el= combines the in-memory aggregate, concrete feature metadata
   vocabulary, record normalization and replay, checkpoints, JSONL/index I/O,
   board journals, context records, and public session mutation/query APIs.
6. =e-openai.el= combines profiles, auth, two wire APIs, two Responses
   transports, request mapping, SSE parsing, diagnostics, provider compaction,
   and harness construction.  =e-mcp.el= similarly combines helper-process and
   HTTP transports with catalog, tool, resource, context, and capability
   composition.
7. =e-base-tools.el= combines the file resource/coherence/search owner with the
   independent shell-process and streamed-output collector owner.
8. Physical placement obscures some dependency direction.  Core modules load
   the layer and shell registries from implementation-oriented directories,
   and =e-chat-service= in core depends on the concrete
   =e-chat-output-mode= capability.
9. Test topology mirrors the largest production files, so production-only
   extraction would leave the agent and review cost largely unchanged.

* Principles

- Split by cohesive semantic owner and independent change reason, not by line
  range, function count, or an arbitrary maximum file size.
- A retained large root requires a residual-topology inventory: responsibilities,
  dependencies, state, transactions, callers, and tests, plus the causal
  invariant that prevents each plausible complete private boundary.
- Extract complete boundaries.  Do not create forwarding-only modules, shared
  bags of helpers, type-only dumping grounds, or circular =require= graphs.
- Keep one clear owner for every piece of mutable state.  Presentation modules
  own their buffer-local state; harness and session subcomponents own explicit
  runtime substate rather than sharing an unstructured plist.
- Cross-component consumers call narrow non-private APIs.  A module may keep
  =--= helpers private to its own feature, but another component must not depend
  on them.
- Preserve public commands and stable runtime contracts during behavior-neutral
  extraction.  Remove obsolete private paths when their callers migrate; do
  not add compatibility wrappers for internal APIs without a real requirement.
- Keep dependencies pointing toward core/domain contracts.  Shells, layers,
  adapters, and application services may depend on core; core must not depend
  on a concrete shell, provider, or capability implementation.
- Preserve live reloadability for shell, layer, default, and capability
  modules.  Core record-shape changes may require a restart and must not acquire
  compatibility shims solely to avoid that requirement.
- Split owner-level tests with their production modules.  Keep composed tests
  only for public interaction among owners, and do not freeze private
  decomposition into integration assertions.
- Measure load, hot-path, allocation, and test-runtime effects.  A source split
  must not add repeated scans, copying, dispatch, or synchronous I/O.

* Target module boundaries

** Chat presentation

Keep =e-chat.el= as the public shell facade and mode/command composition root.
Move complete presentation owners behind it:

- =e-chat-surface= owns transcript/composer window membership, activation,
  fitting, split behavior, and surface-local state;
- =e-chat-composer= owns editable input, submission extraction, inline
  completion, and context-reference editing;
- =e-chat-transcript= owns durable entry, structured block, navigation, and
  transcript replay rendering;
- =e-chat-activity= owns progress, reasoning/tool/action projection, transient
  activity blocks, and redraw scheduling; and
- =e-chat-overview= owns session rows, read markers, workspace unread state,
  active-session previews, and overview commands.

Each component exposes only the operations needed by =e-chat= and Org Canvas.
Org Canvas must stop initializing chat-private registries and progress state.
Its input pane may derive from a public composer mode and consume a public
transcript/activity presenter, but it must own its canvas-specific state and
commands.

** Harness application services

Keep =e-harness= as the application-service facade and lifecycle authority.
Extract cohesive owners for:

- effective capability/layer/resource/tool derivation;
- durable activity projection and recording;
- active-turn and prompt-queue state;
- compaction and context-lifetime orchestration, including provider-neutral
  anchor acceleration; and
- top-level turn submission, settlement, abort, reset, and wait composition.

Introduce a public attached-turn port shaped for =e-board-runtime=.  It covers
attachment authorization, submit, steer, queue, abort, activity observation,
and final assistant output without exposing harness-private functions or
process-global callback variables.  It is not a generic dependency-injection
framework.

Subcomponents receive the smallest required owner or callback interface.  Do
not move all harness internals into a shared =e-harness-internal= module that
merely recreates the same coupling across more files.

** Sessions and storage

Separate the stable session aggregate and typed domain operations from record
codec/replay, checkpoint policy, and physical storage.  Candidate owners are:

- session aggregate, identity, path navigation, and semantic mutation;
- durable record codecs and replay;
- catalog/checkpoint projections; and
- the session storage adapter.

Feature 91 runs before Feature 87 implementation.  It separates the stable
session aggregate, record codec/replay, checkpoint/catalog policy, and current
JSONL storage adapter behind the owner-shaped =e-session-storage= direction
already selected by Feature 87.  This is the preparatory boundary that makes
the later SQLite replacement local; it must not introduce a competing storage
port or migrate durable data.

Feature 87 continues to own SQLite transactions, migration, cutover, and the
eventual removal of JSONL, checkpoint, and index paths.  Feature 91 extracts
only current behavior and deletes obsolete in-file/private coupling that is no
longer needed after the extraction.

Concrete shell, subagent, task-queue, board-orchestration, and MCP state should
use owner-shaped typed operations, capability state, or domain records rather
than requiring every new feature to extend one central session metadata list.
Keep schema registration deterministic and available before replay; do not add
a load-order-sensitive plugin registry.

** Backend and protocol adapters

Keep =e-openai= as the public OpenAI-like backend facade.  Separate provider
profiles/auth, Responses mapping, Chat Completions mapping, HTTP transport,
WebSocket transport, stream decoding, provider compaction, and backend
composition.  Wire and transport variants implement narrow contracts selected
by the facade instead of adding branches throughout one file.

Separate MCP client semantics from helper-process and HTTP transports, then
keep capability/tool/resource/context composition in its own module.  Both
transports must remain substitutable for the supported MCP operations without
unsupported-operation stubs.

Consider a shared cancellable URL-stream transport only after direct comparison
of the OpenAI and Anthropic implementations proves a common contract.  Provider
request shapes, auth, retries, timeouts, and response semantics remain adapter
owned.

** Base tools and secondary shells

Split file/resource/coherence/search behavior from shell-process execution and
the streamed bash-output collector.  Compose both into the existing base
capability without changing its model-facing tools or resource semantics.

After the chat presentation boundary exists, split Org Canvas session/canvas
commands from its transient input/result presentation.  Do not create a second
chat renderer or composer implementation.

** Large cohesive roots

Do not split =e-board=, =e-context-lifetime=, =e-loop=, =e-tools=, or =e-work=
merely because they are large.  Evaluate them during this feature against the
current accepted Feature 88/90 behavior and Feature 87's selected architectural
direction, and retain them only with residual topology evidence.  Later
semantic work must build on that accepted physical boundary rather than
postponing the modularization decision.

Plausible complete boundaries such as board observer cursors, pickup lifecycle,
or routing classification may be extracted only when the new owner can preserve
the aggregate's ordering, admission, commit, retry, and settlement invariants
without duplicating board state or weakening atomic transitions.

* Test and verification strategy

- Run focused ERT for each extracted owner before its old implementation is
  removed.
- Compare public command behavior, tool schemas, request bodies, durable record
  shapes, and event ordering before and after extraction.
- Run =eldev compile= with warnings treated as errors at each coherent slice.
- Run the complete repository suite once per accepted package, not after every
  mechanical move.
- Use =bash e2e/run-graphical-tests.sh= for chat surface, composer, window,
  viewport, focus, and Org Canvas behavior.  Capture isolated transition
  artifacts for failures; do not inspect the user's live desktop.
- Run current-config E2E only for the final composed presentation gate and only
  against isolated state.
- Measure package load time and the relevant harness/session/chat hot paths
  before and after their slices.  Source modularization does not justify extra
  runtime work.
- Keep tests contract-shaped.  A different correct internal decomposition must
  be able to pass owner tests without reproducing the old private call graph.

* Acceptance criteria

- The public architecture remains harness/core, capabilities/layers, adapters,
  application services, and presentation shells with dependencies pointing
  toward stable contracts.
- Each selected production module has one cohesive responsibility and one
  primary reason to change.
- No shell or layer reaches into =e-chat--*=, =e-harness--*=, or
  =e-session--*= symbols owned by another component.
- Chat surface, composer, transcript, activity, and overview behavior have
  explicit owners and focused tests.
- Org Canvas reuses public presentation components without duplicating chat
  state initialization or rendering policy.
- Board runtime depends on a narrow public attached-turn contract rather than
  harness-private functions and callback variables.
- Harness activity, queue, context-runtime, and turn-orchestration state have
  explicit owners; the facade does not remain a renamed god module.
- Session aggregate, record codec/replay, checkpoint/catalog policy, and the
  current physical storage adapter are distinct before Feature 87 begins.
- OpenAI wire APIs and transports, MCP transports, and base file/bash behavior
  are independently testable behind their existing facades.
- Source and test decomposition align; no extracted owner remains buried in a
  monolithic mirror test file.
- Every retained large root has a current residual-topology justification.
- Feature 91 is =Done= before implementation or review remediation resumes in
  Feature 87, 88, 90, or any other feature; each resumed feature records a
  source-anchor rebaseline.
- No compatibility wrapper, fallback path, generic plugin framework, or shared
  helper module remains solely to make extraction easier.
- Focused tests, compilation, relevant graphical tests, the complete batch
  suite, and performance comparisons pass without changing the user's running
  Emacs or live durable store.

* Non-goals

- No product feature, command redesign, visual redesign, provider behavior
  change, persistence migration, or context-lifetime semantic change belongs in
  a behavior-neutral extraction slice.
- No arbitrary universal maximum file length.  File size is a navigation and
  review signal; cohesive algorithms and state machines may remain large with
  explicit evidence.
- No one-function-per-file layout, types-only package, miscellaneous helper
  library, service locator, dependency-injection container, or speculative
  plugin system.
- No public compatibility promise for existing private =--= symbols.
- No duplicate chat renderer, composer, session store, board store, HTTP stack,
  or transport abstraction.
- No full E2E expansion beyond the composed behavior affected by a slice.
- No automatic reload or restart of the user's running Emacs.

* Legacy removal

- Remove cross-component calls to =e-chat--*=, =e-harness--*=, and
  =e-session--*= symbols when their public owner-shaped replacements land.
- Remove =e-harness--attached-port-authorizer= and
  =e-harness--attached-follow-up-publisher= after the attached-turn contract is
  active.
- Remove manual Org Canvas initialization of chat-private registries, progress,
  block, focus, and status state.
- Remove central transport branches that become facade composition over
  independent OpenAI or MCP implementations.
- Move JSONL/checkpoint/index behavior out of the session aggregate into the
  current storage adapter.  Feature 87 removes that adapter at SQLite cutover;
  Feature 91 does not retain duplicate in-aggregate paths.
- Remove tests whose only contract is the old file placement or private call
  graph; retain and relocate their stable behavioral assertions.

* Risks and mitigations

- *Circular load dependencies*: define the owner contract before moving its
  implementation, keep facade composition one-way, and verify fresh batch load
  order after every slice.
- *Shared mutable state disguised by extraction*: move state with its semantic
  owner or introduce an explicit owned subrecord; do not pass a generic state
  plist among modules.
- *Behavior drift during large moves*: compare public outputs and event order,
  use small semantic commits, and delete the old path in the same slice.
- *Conflict with active features*: pause their implementation lanes, preserve
  their last accepted behavior, and require source-anchor rebaselining only
  after Feature 91 reaches =Done=.
- *Slower runtime through extra abstraction*: keep composition direct and
  measure load and hot paths; reject added scans, copies, timers, or synchronous
  work without a first-principles requirement.
- *Tests freeze the new decomposition*: assert public owner behavior and
  composed contracts, not module filenames or internal forwarding calls.
- *Cosmetic file-count success*: require private-consumer removal, dependency
  correction, explicit state ownership, and residual-topology review in
  addition to smaller source units.

* Design self-check

1. Each slice leaves a usable component boundary, fewer private dependencies,
   and matching focused tests even if later slices stop.
2. The feature moves toward the existing capability-first runtime with physical
   modules that match semantic owners.
3. Storage and context semantics may later change under Features 87 and 88.
   Feature 91 freezes their current accepted behavior, localizes the uncertain
   implementation behind owner-shaped boundaries now, and lets later work
   replace those implementations without reopening unrelated modules.
4. Every target component has one named owner and primary change reason; the
   facade owns composition rather than all implementation details.
5. Coupling decreases by removing private cross-component calls and replacing
   them with narrow consumer-shaped interfaces.
6. Dependencies continue to point from shells, layers, adapters, and services
   toward core/domain contracts; physical placement is corrected where it
   currently obscures that direction.
7. UI, filesystem, process, network, and durable-storage effects remain in
   shells or adapters rather than moving into policy modules.
8. Presentation state remains buffer-local, harness runtime state remains
   process-local, and durable session/board state stays at the smallest correct
   storage lifetime.
9. The intended performance effect is neutral apart from cheaper agent and
   maintainer navigation.  Any runtime regression must be measured and
   justified from first principles.
10. Chat components, the attached-turn port, wire mappers, transports, and
    storage APIs are real current contracts.  Implementations must substitute
    without narrowed preconditions or unsupported-operation errors.
11. Preserve public commands and accepted durable formats until their owning
    feature changes them.  Private APIs receive no compatibility shim without
    a real caller requirement.
12. Remove private bridges, manual state initialization, central variant
    branches, obsolete storage paths, and mechanism-coupled tests as their
    replacements land.
13. Expected errors remain with the component that can decide them; extraction
    must not add broad condition handling or swallow unexpected failures.
14. Owner-level tests prove behavior independently, while focused integration
    and graphical tests prove only the public composition among owners.
