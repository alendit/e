* Durable, wire, and restart equivalence

No durable file, record schema, provider request contract, MCP wire format,
base tool schema, ordering, atomic write, retry, cancellation, timeout,
recovery, or error visibility was intentionally changed.  OpenAI mapping keeps
Responses and Chat Completions as separate variant owners and preserves
provider profile/auth selection.  MCP keeps helper-process and streamable HTTP
session lifetimes and uses the same supported client operations.  Base file
coherence and bash collector limits remain at their prior bounds.

The WebSocket completion status includes a bounded response-id field so the
facade/E2E composition can observe the existing response identity without a
private session hook; existing callbacks ignore additional status fields.  The
stdio transport seam accepts a lexical test function and strips it before wire
arguments; normal runtime calls continue to use the real helper.  These are the
only interface-shape exceptions from mechanical movement.  No compatibility
bridge was added for removed private names.  A fresh Emacs process is required
to use the changed core/provider definitions in an already running process;
the user's running Emacs was not queried or reloaded.

* Required design self-check

1. *Would stopping here improve the project?*  Yes.  The three adapter roots
   are bounded composition points, transport and protocol changes are local,
   and fresh owner contracts catch accidental facade loading.
2. *What final direction does this move toward?*  One semantic owner per
   provider policy, protocol variant, transport, decoder, client, capability,
   file, and process concern, with stable facades composing them.
3. *Which decisions are uncertain or stable?*  Existing wire formats,
   auth/retry behavior, helper/HTTP support, and tool schemas are stable.
   Responses-vs-Chat variation and future transport replacement are real
   variation points kept local; no speculative common adapter was added.
4. *Who owns each behavior and why?*  The matrices above place profile policy
   in profile, wire shape in its protocol owner, side effects in transport,
   decoding in decoder, catalog semantics in client, composition in
   capability, and file/process behavior in their respective base owners.
5. *Coupling direction and interface width?*  Coupling is reduced from each
   monolith to downward owner contracts.  Public operations are consumer-shaped;
   raw records and implementation constructors remain private.
6. *Did a dependency point the wrong way?*  No.  The MCP capability no longer
   depends on concrete HTTP classification, and bash no longer depends on the
   file owner.  No owner requires/calls its own facade.
7. *Could side effects move outward?*  They already do: HTTP/WebSocket/helper
   process and file writes stay in transport/resource owners; profile,
   protocol, decoder, and client policy remain testable value operations.
8. *What state was added or mutated?*  State was relocated, not expanded:
   HTTP/WS/helper/session caches and process-local diagnostics keep their
   existing lifetimes; protocol/mapping/decoder values are rebuildable and
   stateless; file buffer coherence remains buffer/file scoped.
9. *Performance impact?*  Pure mapping and value smoke timings are bounded,
   and static scans show no new sync I/O in pure owners.  Existing cache,
   async, retry, and collector bounds are retained; no extra repeated scan or
   write was introduced.
10. *Are abstractions semantically real and substitutable?*  Yes.  Responses
    and Chat mappings are separate real protocols; MCP helper/HTTP expose only
    list/call/refresh semantics both support; explicit test transport input
    satisfies the same narrow stdio request result without implementing files.
11. *What compatibility expectations apply?*  Existing public facade names,
    request/response formats, errors, ordering, and tool schemas are retained.
    Private names have no compatibility promise and were removed.  Core
    definitions require restart rather than steady-state shims.
12. *What legacy code can be removed now?*  Monolithic moved implementations,
    old private prefixes, the MCP global transport callback, public raw HTTP
    response construction, and duplicate facade bridges were removed.
13. *Where are errors handled?*  Expected provider/MCP transport failures are
    normalized at diagnostics/client boundaries while corrupt or unexpected
    values signal visibly; file coherence and process errors retain their
    existing top-level propagation.
14. *What proves core behavior independently?*  The three direct owner suites
    load and exercise owners without facades; focused facade/fixture suites
    prove composition and preservation; fresh loads, check-parens, compile,
    static sweeps, and the recorded 485 selector cover topology and regression
    risks.  A future internal decomposition can satisfy the semantic owner
    contracts without reproducing the moved private names.
