#+title: Feature 91 Round 1 Presentation Audit
#+startup: overview

* Scope

This audit records the corrected Round 1 presentation boundary for
=F91-OWNER=, =F91-PRESENTATION=, =F91-TOPOLOGY=, and =F91-PRESERVATION=.
The scope is the chat presentation family, its facade, Org Canvas adaptation,
the chat starter/debug/canvas/dev consumers, and their tests.  The source
baseline is the accepted Feature 91 worktree baseline; this worktree was not
committed by the implementer.

The public chat commands, modes, buffer names, event order, session formats,
and graphical behavior are intended to remain unchanged.  Internal owner ports
were narrowed where a facade-only forwarding alias or representation-shaped
operation had no semantic consumer; mechanism assertions now call only the
owning private helper.  No compatibility alias for an owner-private symbol
was introduced.

* Dependency direction

The static call audit in =/tmp/f91-graph-round1-summary-correction-final.log= resolves each exact
call to the file that defines its target, rather than classifying every legacy
=e-chat-*= name as a facade call.  The final actual graph is:

#+begin_example
surface -> (stable core only)
transcript -> surface
composer -> surface, transcript
activity -> surface, transcript
overview -> surface, transcript
facade -> surface, transcript, composer, activity, overview
#+end_example

The counted owner edges are:

| Edge | Call sites |
|------+------------|
| transcript -> surface | 14 |
| composer -> surface | 11 |
| composer -> transcript | 5 |
| activity -> surface | 14 |
| activity -> transcript (semantic ports only) | 17 |
| overview -> surface | 5 |
| overview -> transcript | 11 |
| owner -> facade | 0 |

Overview owns candidate selection and row/preview policy.  Its
=e-chat-overview-session-selection= operation returns a value describing the
selected harness/session/instance; the facade's =e-chat-overview-open-session=
command consumes that value to construct, attach, and subscribe the composed
chat surface.  There is no overview-to-facade runtime edge.  No owner calls
another owner's private =--= symbol.  The facade-to-owner edges are composition
and event dispatch, so the owner graph remains acyclic.

The corresponding state dependencies are:

| Consumer | Reads/mutates through | Does not reach |
|----------+-----------------------+---------------|
| Composer | Surface role/window/output-follow ports; transcript navigation/protected insertion | Surface/transcript private variables; facade state |
| Transcript | Surface identity/output-tail ports | Composer/activity registries; facade state |
| Activity | Transcript participant/turn identity and semantic activity projection ports; surface viewport/status ports | Transcript records/registries/ids/markers/bounds; composer/overview/facade state |
| Overview | Surface selection and transcript preview/replay ports | Composer/activity private variables; facade state |
| Facade | Public owner ports and its own subscription/identity state | Owner-private registries, progress cells, block indexes, or composer markers |
| Org Canvas and external production consumers | Public facade/component ports | Any =e-chat--*= or owner-private symbol |

Activity/transcript state is intentionally split.  Activity's
=e-chat-activity--turn-registry= is buffer-local and contains provider rounds,
reasoning/tool/action records, timing, failures, message details, transient
state, and redraw state.  Transcript's =e-chat-transcript--turn-registry=
contains only durable separator/navigation projection metadata; its block
registry owns physical block ids, markers, bounds, protection, and navigation
capture/restore.  Activity sends a fresh semantic descriptor to
=e-chat-transcript-project-activity= and receives only a scalar rendered size.
The transcript deep-copies descriptor child/tool data before storing it.  No
mutable activity record or transcript block record crosses that port.

The facade dispatches every board event once through
=e-chat-activity-handle-event=.  Activity classifies activity-only events and
updates its own state; the facade only composes durable message insertion and
shell actions from the returned semantic result.  Adding a provider/tool
activity event therefore changes the activity owner and its direct tests, not
a central per-record mutation table in the facade.

* Public API audit

The fresh public inventory is =/tmp/f91-public-api-map-round1-correction-final.log= and the
consumer map is =/tmp/f91-public-api-consumers-round1-correction-final-tab.log=.  It contains 60
surface, 31 composer, 41 transcript, 25 activity, and 31 overview public
definitions (188 total, including commands/modes and owner ports).  The count
is a report, not a target: each retained operation is either a command/mode,
facade composition port, embedding-shell port, or semantic downstream-owner
port.  In particular:

- Surface exposes membership, activation, status, viewport/follow, and
  pairing operations used by the facade, Org Canvas/debug/dev consumers, and
  the graphical presentation boundary.
- Composer exposes editing, submission, completion/reference, and mode
  operations used by the facade, Org Canvas, starter, and debug shells.
- Transcript exposes durable rendering, navigation commands/queries, preview
  rendering, and the semantic activity projection port.  It does not expose
  raw block records, registries, marker/bounds mutation, or block-id
  allocation to activity.
- Activity exposes one event transition operation, replay/display queries,
  progress/redraw lifecycle ports, and the rendered-message settlement port.
  Record classification and transitions are private to activity.
- Overview exposes commands, candidate/preview rendering, read-marker and
  selection-intent ports.  Selection returns a value; overview does not call
  the facade.

The cleanup removed facade-bounce wrappers and representation aliases that
had no semantic consumer (including the old public activity prepare/reconcile/
settle/tool-message helpers) and renamed component implementation helpers into
unambiguous owner-private namespaces.  The current API map records the exact
consumer files, including the small set of graphical/integration component
ports whose contract is observable window or buffer behavior.  No documented
chat command, mode, buffer name, event format, or session format changed.
The 28 rows without a separate production consumer are intentional owner
commands/keymap operations or observable embedding/test ports (for example,
surface activation, overview navigation, transcript glyph/separator queries,
and semantic activity state); they are not raw registry, marker, bounds, or
record accessors.  Their owning mode, facade composition, embedding shell, or
direct semantic contract is recorded in the consumer-map evidence.

* Status and residual risks

- Parent acceptance: Round 1 was accepted on 2026-08-29 after independent
  ownership, dependency, API, and test-topology review.  The acceptance pass
  also removed a duplicate activity-separator definition found during source
  inspection and re-ran the direct owner and separator integration contracts.
- F91-GOAL behavioral status: focused repository behavior is preserved by the
  485-case gate (483 expected passes, two expected skips), and the isolated
  graphical chat/workspace gate passes 27/27.
- F91-GOAL mechanism status: the corrected owner boundary, activity/transcript
  state split, directional graph with zero owner-to-facade edges, semantic API
  map, private namespace sweeps, fresh owner loads, and test topology are
  complete.
- Mechanical-equivalence exceptions are limited to owner load order,
  overview's direct preview-buffer initializer (needed to keep preview
  construction local), the explicit transcript output-mode require for
  standalone rendering, deep-copying activity projection descriptors at the
  transcript boundary, and metadata-only preview fallback when a service has
  no loaded messages.  These preserve the old public projection while removing
  reverse runtime dependencies and shared mutable records.
- Known repository warnings are the expected
  =visual-fill-column unavailable= fallback in batch tests.  No unresolved
  source blocker is known.  The async submit status assertion passed in both
  final 485 runs; earlier retries showed timing sensitivity in an existing
  test, so it remains a low-risk CI watch item rather than a product-status
  change.
- Independent negative checks pass: zero cross-owner private production
  references, zero owner-private references in composed/integration tests,
  no shared mutable activity/transcript record, and no representation-shaped
  transcript port consumed by activity.
- Residual topology is deliberate: the monolithic chat implementation is
  removed; each five-owner source and its direct contract/mechanism suite is
  retained; composed chat/window behavior remains in the facade/integration
  suites; Org Canvas retains only canvas/session/focus state; starter/debug/
  canvas/dev consumers use public owner/facade ports; no compatibility bridge
  or duplicate renderer/composer remains.
- The user's running Emacs was not queried, reloaded, signaled, or otherwise
  changed.  A manual reload/restart is intentionally not part of this proof.

* Design self-check

1. If stopped here, the project is better: each presentation responsibility
   has an owner, direct contracts, and a measurable preservation gate.
2. This moves toward a facade that composes stable owner ports and toward the
   later session/runtime/adapter rounds without importing chat-private state.
3. Stable behavior is represented directly; uncertain reload/preview details
   are local to the owner and reversible.  No speculative registry or DI layer
   was introduced.
4. Ownership follows the five cohesive reasons to change listed above.
5. Coupling is reduced from the complete mutual graph to a directional graph;
   the remaining interfaces are consumer-shaped.
6. No dependency points from a stable core contract toward a concrete sibling
   or provider; presentation dependencies point to lower owners/stable core.
7. Window, redraw, and provider-side effects remain behind surface/activity or
   existing service adapters; the facade composes them.
8. State remains at buffer, window, workspace, or scheduled-job lifetime as
   required; no cross-owner state mirror was added.
9. The split adds no repeated scans or synchronous I/O; existing bounded
   projection and scheduling paths remain in their owners.
10. The remaining ports have real consumers and do not require unsupported
    operations or narrowed preconditions.
11. Public commands/modes/formats remain compatible; obsolete private aliases
    were removed rather than wrapped.
12. Removed now: the monolithic implementation copies, facade-bounce owner
    aliases, unused owner ports, and Org Canvas chat-private initialization.
13. Expected presentation errors remain at their existing boundaries;
    unexpected errors surface through the facade/test runner.
14. Direct owner tests prove contracts independently; composed tests prove
    only cross-owner behavior, so another correct decomposition can satisfy
    the same owner suites.
