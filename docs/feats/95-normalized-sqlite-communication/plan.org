* Behavioral goal

** Goal record

- Goal ID :: =F95-NORMALIZED-COMMUNICATION=
- Behavioral goal :: A reopened SQLite-backed chat, Board, pickup queue, and
  task queue expose one coherent participant identity and one coherent mutable
  state without depending on duplicated values inside opaque payloads.
- Direct scenario :: Create an owner and participant, route input, transition
  its pickup, publish participant output and context curation, settle a task,
  close the store, and reopen it.  Board/session association, participant
  labels, record selectors, pickup state, and task state agree through the
  ordinary bounded public reads after reopen.
- Product authority :: The =e= runtime-store, Board, session, chat, and task
  owners under the repository architecture guidance.
- Owning contract :: The matrix in this file.
- Behavioral status :: Available.  Schema v8, its explicit offline upgrade,
  and the direct reopen scenarios passed repository-side validation.

The implementation must preserve SQLite as the only durable authority.  It may
materialize bounded query indexes when one source row owns their derivation and
they can be rebuilt; it must not retain two independently readable copies of a
semantic identity or mutable state.

* Scope and non-goals

In scope:

- normalize the Board/session/participant association;
- resolve participant display attribution from the participant relation;
- remove duplicate Board record aliases and separate record content from its
  relational envelope and selector values;
- make relational pickup and routing rows authoritative for identity and
  mutable state;
- remove the unused Board session-admission ledger;
- make relational task and attempt rows authoritative for their mutable state;
- add one explicit stopped-store v7-to-v8 upgrade with verified backup,
  rollback, integrity, provenance, and parity checks;
- update affected callers, fixtures, documentation, and focused tests; and
- remove obsolete compatibility branches, fields, schema objects, and tests.

Out of scope:

- changing the journal-derived session current-state projection, the process
  report index, or runtime idempotency receipts merely because they are
  materialized projections;
- changing voice, cron, Goodnite, raw-result, or temporary-resource behavior;
- automatic startup migration, dual writes, read-time legacy fallbacks, or a
  second durable store;
- preserving historical participant display-name snapshots.  Display names
  are current participant facts; immutable authorship remains represented by
  participant identity; and
- reloading or mutating the user's running Emacs during implementation.

* Normalized ownership design

** Board association and participants

One explicit Board association relation links exactly one session to one
participant in one Board generation.  Its participant identity is a relational
column, not a member of the encoded routing policy.  The relation references
the session query row and Board participant row.  The Board supplies the
trusted principal, the participant row supplies role and current display name,
and the association supplies only association-owned routing policy.

=session_query_state= keeps session-derived state only.  It no longer stores
=board_id=, =principal=, =association_role=, or =routing_policy=.  Consumer
reads preserve their current detached association DTO by joining and
reconstructing it inside one bounded SQLite read snapshot.

Participant fields with independent query or mutation meaning are relational
columns.  The stored participant representation does not repeat its key,
Board principal, role, state, publication flag, subscription identity, or
display name inside an opaque payload.

** Board records and selectors

The relational Board record envelope owns Board/generation/position, record
identity, record kind, source identity, creation time, author, subject
participant, and other stable selector identity.  Tag and attribute child rows
remain the normalized selector authority.  The encoded payload contains only
kind-specific content which has no relational query responsibility.

One reconstructed record DTO is returned to callers.  It uses
=:record-kind=, =:seq=, =:tags=, and =:attributes= as its canonical names.
=:kind=, =:durable-position=, =:selector-tags=, and
=:selector-attributes= are removed rather than retained as aliases.

Bounded record queries fetch envelopes, tags, and attributes as bounded sets;
they must not introduce a query per record or an unbounded aggregate.

** Routing, pickups, and admission

The routing row's relational state is authoritative.  Its encoded payload
contains only state-specific result detail which is not already represented by
the routing and pickup relations.  Pickup membership is derived from pickup
rows rather than retained as a second list of pickup identities.

Pickup relational columns own delivery identity, FIFO position, state,
revision, and attempt.  The encoded pickup body contains only immutable
delivery content and transition detail.  Every pickup read reconstructs the
same DTO from those sources; no read returns a stale embedded state.

=board_session_admissions= is removed.  Pickup acceptance and its session/lane
detail are already represented by the pickup state and immutable pickup event;
no consumer reads the additional ledger.

** Tasks and attempts

Task relational columns own task identity, queue position, queue-lifecycle
status, revision, enqueue time, requested harness selector, retry policy/count,
and a nullable latest-attempt reference.  Encoded values remain only for
genuinely opaque task content such as prompts and caller metadata.

An attempt row exclusively owns execution facts: attempt number and state,
actual harness instance and session, start/settlement timestamps, outputs, and
error.  Those facts do not also live on the task row.  Task status and attempt
state are distinct: the former decides queue eligibility and terminal task
state, while the latter records one execution's history; retry may return a
task to queued while retaining a settled prior attempt.  The current task DTO
derives latest execution detail through the latest-attempt reference, and
attempt history is reconstructed directly from attempt rows.

Dispatch and snapshot reads reconstruct the same task DTO.  Enqueue, claim,
transition, import, and reopen cannot select state from different copies.

* Scenario portfolio

** F95-S1: participant attribution and Board reopen

Create an owner plus named child participant, publish child output and
context-curation activity, and observe both through the immediate public chat
projection.  Close and reopen, then consume the ordinary chat and Board
projections again.  Both entries resolve the same child name from the
participant row in live and reopened paths; association identity and selectors
remain exact; no event payload contains =:participant-name=.  The stale-name
migration partition in =F95-S4= separately proves participant-row precedence.

** F95-S2: pickup transition agreement

Route two messages to one participant, exercise pending/ready/claimed/accepted/
terminal promotion and retry paths, and compare canonical append, pickup-page,
event, and reopen results.  Identity, revision, attempt, and state agree across
every public result.

** F95-S3: task transition agreement

Enqueue, claim, retry or settle, inspect the bounded snapshot, close, reopen,
and claim the next task.  A new v8 retry leaves the task queued while preserving
the failed attempt and its execution facts as the latest attempt.  Dispatch
choice and returned task/attempt DTOs agree at every boundary, including
failed/interrupted legacy import.

** F95-S4: explicit v7-to-v8 upgrade

Upgrade a copied v7 store containing owner/child associations, mixed Board
records, routing and pickup history, admissions, and tasks.  Its output record
contains a stale embedded participant name that disagrees with the current
participant row, and its task fixtures include v7 queued-after-retry and
queued-after-resume rows whose last attempt was destructively rewritten to
=queued=, plus retry followed by a later claim and settlement, leaving an older
historical attempt persisted as =queued=.  Verify the v8 live/reopen projection
uses the participant-row name and retains no event copy.  Map every recognized
v7 attempt row persisted as =queued= to the explicit historical state
=legacy-requeued=, whether it is latest or historical; attempt rows were created
only by claim, so that state is the destructive-requeue witness.  Preserve its
available execution facts without inventing a settlement time or cause.  A
still-queued task retains the mapped row as latest, while a later claimed or
settled attempt remains latest and the mapped older row remains history.  Verify
those semantics together with backup, lineage, foreign keys, semantic parity,
obsolete-object removal, idempotent v8 no-op, and exact restoration after
faults before and after commit.

* Migration and corruption policy

Schema v8 is a clean cut.  The stopped-store upgrader reconstructs normalized
relations in one transaction and changes the schema-version/provenance rows
only after parity succeeds.  Fresh stores create only the v8 shape.

Where a v7 row contains duplicate values, migration validates their agreement
before dropping a copy:

- association participant, role, principal, and Board generation must join;
- record key/kind/position/tags/attributes must agree with envelope/index rows;
- routing state and pickup membership must agree with routing/pickup rows;
- pickup identity/state/revision/attempt must agree with relational columns;
- task/attempt identities and attempt numbers must agree with relational rows;
  active and terminal v7 task/attempt combinations must match their recognized
  topology; and every v7 attempt persisted as =queued= maps deterministically
  to =legacy-requeued= with no invented settlement timestamp or
  retry-versus-resume cause, including historical attempts superseded by a
  later claim.  Other contradictory or non-derivable combinations fail with
  the task and attempt keys.

Migration fails with the smallest identifying key when duplicates conflict; it
does not guess, silently prefer one copy, or preserve a permanent compatibility
branch.  Successful migration discards event-carried participant names and the
unread Board session-admission ledger under the accepted current-name and
single-ledger contracts above.

* Acceptance and repository policy

Repository-side focused validation and the complete gate run outside the
user's Emacs.  Because core runtime, session record shape, and schema change,
using the behavior in the running Emacs requires a full restart; =e-dev-reload=
is intentionally insufficient and will not be run.

Implementation and review follow =AGENTS.md= and
=docs/references/dev_work.org=; this feature artifact does not redefine their
review, commit, evidence, or status-transition workflow.
