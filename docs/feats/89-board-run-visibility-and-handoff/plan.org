#+title: Board Run Visibility and Completion Handoff
#+startup: overview

* Status

In-progress.

* Goal

Make asynchronous board runs visible and understandable from the chat that owns them.
The initiating turn may finish while the run continues, and the composer must become ready for more input.
The chat must still show that work is active.
Board activity must also offer a visual, run-focused view of the work behind that status.
Every later model turn must receive a bounded projection of that work in context.
When the run finishes, the same session must receive one durable completion input at a safe idle point.

Foreground and background describe whether work outlives the current turn.
They do not name different sessions, boards, or coordinators.
One chat has one canonical session participant and one board.
Interactive dispatch and later headless triggers publish to that same board.
The daily integration's =E_UPDATE_SESSION= property and update-session routing are legacy state to remove.

* User story

A user asks the main chat to start work that expands into a board run.
The main session publishes the run and ends its turn without waiting for the full graph.
The composer becomes ready at once.
A persistent status area shows that the run is active and provides a bounded summary.
On an xwidget-capable graphical Emacs, opening that status shows the selected run's tasks and participants in a visual Board activity view, including tasks that have not admitted a participant yet.
If the user sends another message, the model receives the same active-run summary in context and therefore knows that work is still pending.
When the required work settles, the board queues one completion input for the same session.
That input waits while a model turn is active and starts only after the session reaches an idle boundary.
The status remains visible until the coordinator turn finishes successfully,
including across restart.  A failed or cancelled turn remains visible as
attention.

* Terms

- Run :: The durable board orchestration group defined by feature 82.
  It includes the manifest, selected task attempts, reports, terminal projection, and continuation claim.
- Owner chat :: The canonical session participant and board association that accepted or created the run.
- Active run :: A run with required work still pending, optional work still active, or a completion continuation without a non-conflicting successful coordinator outcome.
- Run projection :: A bounded reducer output used by both chat presentation and model context.
- Completion input :: The one keyed board input that asks the owner session to consume the terminal run result.
- Idle boundary :: A point after an active turn finishes where the participant FIFO may start the next queued input.

A run may represent a full work graph assembled by a capability.
The chat depends only on the bounded run contract.
A run is not the initiating turn, one process-local =e-work= handle, a worker session, or a shell-owned progress object.

* Required behavior

** One owner board

One chat has one canonical session and board association.
The run manifest is published to that existing board.
The completion destination is the same session participant.
Worker tasks may use normal execution isolation, but they do not become another coordinator or own a shadow board for the run.

A headless trigger with an existing owner association reuses it.
A headless trigger with no existing association may create the sole canonical owner once.
It must not create a parallel update session.

The implementation removes =E_UPDATE_SESSION= metadata, update-session creation helpers, and routing that sends background work to another coordinator session.
Existing stored =E_UPDATE_SESSION= values are obsolete metadata, not identities to migrate into feature 87.

** Dispatch and chat readiness

The owner session commits a run manifest with a stable run id, bounded label, stable publication key, task identities, and required or optional policy.
Selected queue tasks carry the same run, task, and attempt identities.
The initiating turn may finish as soon as dispatch is durable.
The run lifetime is independent of the turn that created it.
The composer becomes ready while the run remains active.

The board and task queue have separate authorities.
Restart reconciliation must enqueue a selected task whose queue record is missing without creating a duplicate.
A restored =running= task must be reconciled before the runtime retries it or classifies it as missing.

** Shared bounded run projection

One session-scoped reducer projection drives both the chat status and the model-context block.
It includes:

- every nonterminal run;
- every terminal run without a non-conflicting successful coordinator outcome;
- every run with optional tasks still active.

Runs are ordered by actionable state, latest durable board event, and run id.
Record and byte budgets cap detailed entries.
An omitted count and bounded run-query action preserve access when the budget hides older runs.

Each detailed entry contains:

- run id and bounded label;
- required task totals by state;
- optional task totals by state;
- latest durable event time;
- conflict or deadline evidence;
- completion delivery state and separate coordinator execution outcome.

The projection does not copy worker transcripts, prompts, tool results, or reasoning into the owner session.
The reducer publishes change notifications.
The chat shell and context provider subscribe to those notifications instead of polling storage, task sessions, or worker transcripts.

** Chat presentation

The chat shows a persistent active-run indicator outside the turn transcript.
The indicator remains visible while the composer accepts input.
It is derived from the shared run projection rather than from process-local work handles.
Chat-turn status and Board-run status name different scopes: the initiating
turn can be idle while its run remains active.  The display labels those scopes
explicitly, and =active= counts runs rather than executing workers.

The compact state shows the number of active runs, the lifecycle and bounded
label of the most actionable run, and an obvious action to open Board activity.
It uses the selected run already present in the shared projection and stays
bounded when more runs exist.  A user can open the one Feature 82 Board
activity surface focused on that run from the indicator.
The chat does not render the full task graph inline.

The indicator distinguishes at least these states:

- =dispatching= while durable task assignment is being reconciled;
- =running= while required work remains active;
- =finishing= when required work is terminal and the completion input is waiting or pending;
- =attention= when the run has a conflict, deadline, failed publication, or missing task;
- =restoring= while board or task-queue reconstruction is incomplete.

The presentation must not report no active work from incomplete restore evidence.
It must not disappear merely because the turn that dispatched the run ended.

Board activity is the detailed surface for the selected run.  It shows the
durable disposition of each selected task and its attempt, including admission
pending, retry scheduled, or terminal dispatch failure before any participant
has been admitted.  Related participant rows expose committed outcomes and
optional exact live progress and controls.  A task without a participant is
not represented by a fabricated participant row.  The Board-owned run and
observation services supply one run-focused, bounded activity page whose task
and participant facts describe a coherent Board generation and revision.
The shell owns only that detached page, focus, and presentation.  Opening the
view does not block the composer.

** Visual Board activity

Board activity offers an =emacs-egui= visualization of the same Board-owned
run-focused page as its native text view.  The chat status opens the selected
run in this one activity surface.  The visual renderer occupies a normal
Emacs xwidget buffer; a user can choose the text renderer on a build without
xwidgets or when they prefer keyboard-oriented rows.
Adding the repository-root =emacs-egui= submodule and building the Board WASM
app are part of this feature's visual slice.  The submodule is shared with
Feature 62 rather than copied into a second UI runtime.

The visual view has a compact active-run selector, a selected-run workspace,
and an inspector.  The selector shows the bounded run labels, lifecycle,
required and optional counts, and omitted count from the shared projection.
When runs are omitted, a =Show more= action invokes the bounded run query.
The workspace groups selected tasks by required or optional policy.  Each task
card shows its durable disposition, selected attempt, and an admitted
participant when one exists.  A pending admission or failed dispatch remains
a task card without a fabricated participant.  Completion delivery,
conflicts, deadlines, and restore state have visible text labels as well as
color or motion cues.  Selecting a task reveals its exact Board coordinates,
latest bounded outcome or progress, and only the controls available for its
current participant.  Board-wide participant navigation remains available so
an ad-hoc child does not disappear behind the run-focused layout.

The layout takes the glanceable status and attention cues of
[[https://github.com/nohzafk/emacs-workspace-hud][emacs-workspace-hud]], while using the
larger activity view for task detail.  It draws only relationships recorded
by the Board: run to task, task to selected attempt, and attempt to admitted
participant.  The current manifest does not define dependency edges, so the
view does not invent a directed task graph or offer graph editing.  The
compact chat status stays outside the transcript and never covers its
composer; a floating child frame is not needed for the detailed view.

Board observation supplies a bounded, coherent page for the selected run;
the visual adapter maps that detached page into a narrow JSON view model.
The run selector can update ahead of that page; the workspace shows its own
revision and loading state until its detail refresh completes rather
than combining task and participant facts from different revisions.
Rust owns only selection, expansion, layout, and rendering.  Elisp handles
semantic events such as selecting a run, opening a participant chat, or
requesting an available control through existing Board and subagent services.
The handler validates the current Board identity and live control availability
before acting on a possibly stale click.  Board notifications schedule
bounded refreshes; neither renderer polls worker sessions or builds a second
run or participant inventory.  Refresh preserves the selected run and task
when their durable identities still exist.

The owner chat remains a chronological observer of canonical Board messages.
The dispatch path places its existing typed run, task, and attempt coordinates
on each run-bound child input when it submits that canonical Board message.
Child session metadata alone is insufficient for the Board observer: the
current =e-subagent-direct-runner= calls =e-chat-service-submit-session= without
=:metadata=.  For inputs carrying those coordinates, the transcript labels
long automated assignments and initially folds their bodies.  The complete
input remains available on expansion or in the participant chat,
with its Board message identity and order intact.  Ordinary human prompts
retain their =You= presentation; missing assignment metadata is not inferred
from prompt prose.  Activity such as =Context curated= remains chronological
activity, not a source of task status.

Direct scenario (Feature 89, operator authority): a Daily owner turn has ended,
one run is dispatching, and long Calendar and Slack assignments appear in the
chat.  The idle chat visibly names the separate turn and run states, identifies
the selected run, and opens Board activity to show each task's disposition and
any admitted participant.  Full assignment text remains accessible without
dominating the default transcript.  A separate admission-boundary case keeps a
selected task visible there even before it has a participant row.  The
observed screenshot and current source establish only partial behavior: the
run indicator exists, but its text omits the selected label and the
participant-based activity page cannot show an unadmitted task.  Run-bound
child input also lacks the typed assignment metadata needed for labeling.

** Model context

Every model turn for the owner session receives the same bounded run projection.
The context block appears even when no run event is present in the visible transcript.
The agent can therefore answer new input with knowledge of outstanding work.
It can inspect or steer the run through existing actions without guessing whether work still exists.

The context provider states whether completion publication is waiting, pending,
published, or failed, and reports the separate coordinator execution outcome.
It includes omitted counts when the detailed budget is exhausted.
It does not instruct the model to wait blindly.

** Required and optional completion

The manifest declares which tasks are required and which are optional.
The run becomes terminal when all required tasks settle under that policy.
Unfinished optional tasks remain visible in the run projection and completion payload.
The first terminal transition advances one continuation under the stable publication key.

Completion publication state is explicit:

- =waiting= before terminal policy is satisfied;
- =pending= after the board records the publication claim;
- =published= after the board accepts the keyed completion input;
- =failed= when publication cannot complete and requires attention.

The matching =input-consumed= receipt establishes delivery into a coordinator
turn.  It does not establish execution success.  A separate durable continuation
outcome records =done=, =failed=, or =cancelled= after the coordinator turn and
its completion hooks settle.  A terminal run without a non-conflicting =done=
outcome remains active; failed or cancelled outcomes require attention.

A pending claim is recorded before publication.
The completion input uses a stable source-input key.
The published claim is recorded only after the board accepts that input.
A crash between any two steps retries with the same keys and cannot append a second completion input.

This contract guarantees one durable completion input.
It does not guarantee that the provider turn started by that input will produce a successful answer.

** Idle completion delivery

Completion never interrupts an active model turn.
=e-board-runtime= accepts the queued input while the owner attachment is busy.
It does not start pickup until the attachment is idle after =turn-finished= or another explicit idle boundary.

If a user turn reaches that boundary first, the participant FIFO preserves normal ordering.
The run projection continues to show terminal completion through delivery and
the coordinator turn until its durable successful outcome.  Failed or cancelled
outcomes remain visible as attention.

** Restart behavior

Board restore replays run facts, keyed inputs, publication claims, and consumption receipts before the chat binding reports ready.
Task-queue restore reconciles durable task assignments before a task is retried or classified as missing.
The shared reducer projection is rebuilt before the chat status or model context reports an empty state.

Feature 87 supplies the durable storage path for these records.
This feature owns their run semantics, projection, presentation, and delivery behavior.
Feature 92's [[file:../92-runtime-store-failure-isolation/addendum2.org][SQLite-only Board cutover]] removed the alternate in-memory Board;
focused tests use isolated SQLite state.

* Ownership

- =e-board-orchestration= owns manifests, run reduction, required and optional terminal policy, conflicts, continuation intent, and continuation claims.
- The dispatching capability owns run-specific task policy, the bounded label, and the bounded reconciliation prompt stored in the manifest.
- The task-queue bridge owns durable run, task, and attempt assignment plus idempotent dispatch reconciliation.
- The subagent dispatch path passes its already-known assignment coordinates into child input submission; =e-chat-service= carries them as typed Board input attributes without interpreting the prompt.
- =e-chat-service= owns the one session and board association plus generic keyed publication to the owner participant.
- =e-board-runtime= owns participant FIFO delivery, busy-session deferral, and consumption receipts.
- A session-scoped context provider emits the bounded run block for model input.
- The chat shell renders the compact status from that projection and opens the one Board activity surface.
- Board orchestration owns run/task dispositions.  Board observation maps one consumer-shaped run-focused activity page with those dispositions and related participant rows; Board activity renders it as native text or through a narrow =emacs-egui= view model and decorates exact participants with optional live controls.
- The Board activity presentation owns its WASM app, semantic UI event mapping, and rebuildable visual selection; neither =emacs-egui= nor the Feature 62 chat shell owns Board policy or durable state.
- The chat transcript shell owns assignment labels and folding from typed Board message metadata; it does not change Board ordering or durable input content.
- =e-session-storage= persists typed board facts and receipts but does not own run policy, context wording, or rendering.

* End-to-end proof

One scenario dispatches required and optional tasks from a main chat turn.
The turn ends while the run continues.
The composer is ready, the status is visible, and the next unrelated user turn receives active-run context.
Long Calendar and Slack assignment inputs coexist in the owner chat while the
run is dispatching.  The idle-chat indicator names the active run and opens
Board activity, where the task dispositions are visible.  A separate boundary
in the same graphical proof leaves a selected task pending admission with no
participant row; Board activity still identifies it.  The transcript keeps
the ordered assignment inputs accessible without showing their full bodies by
default.
On a graphical build, the same status opens the =emacs-egui= Board view: the
pending task has no participant card, the running task links to its admitted
participant, and the selected task survives a Board notification.  The native
text renderer shows the same durable dispositions when xwidgets are absent.
A later headless trigger reuses the same session participant and board.
No update session, private coordinator session, or shadow board is created.

The scenario crashes between manifest commit and task-queue persistence and then reconciles without duplicate dispatch.
It also restores a =running= task before deciding whether to retry it.

The required tasks settle while an optional task and another owner-session turn remain active.
The completion input does not interrupt that turn.
The optional task remains visible in the status, context, and completion payload.
One keyed completion input starts after an idle boundary; its delivery receipt
and later coordinator outcome remain distinct.

The scenario restarts before publication, after publication but before delivery,
after delivery but before the coordinator outcome, and after that outcome.
No restart loses or duplicates the completion input.
The status and context never report no work while restore is incomplete.

* Acceptance criteria

- The initiating turn can end while its board run continues and the composer is ready for more input.
- The owner chat shows a persistent board-run indicator derived from durable board state.
- The indicator distinguishes chat-turn idleness from an active Board run,
  names the most actionable run, counts runs rather than workers, and opens
  the one Board activity surface focused on that run.
- Board activity exposes selected task dispositions even before participant
  admission and retains related participant outcomes and exact live controls
  in one coherent bounded page without a second durable inventory.
- The =emacs-egui= Board renderer visualizes that page as grouped task cards
  and an inspector, with active-run selection from the shared bounded
  projection.  Its text labels distinguish task state, attempt, participant,
  and completion delivery; it never infers unrecorded task dependencies.
- The Board WASM app builds from the shared =emacs-egui= submodule.  Its
  semantic actions validate current identities and control availability;
  notification-driven refresh retains focus.  The native text renderer
  remains usable on Emacs builds without xwidgets.
- Metadata-identified automated assignments are labeled and initially folded
  in chat; their complete canonical Board messages remain accessible and
  ordered.  Dispatch supplies the typed coordinates on run-bound inputs;
  ordinary human prompts retain their normal presentation.
- Every later model turn receives the bounded run projection while required work, optional work, or completion delivery remains active.
- The visual status and model context use the same reducer projection.
- Interactive and headless dispatch use the same canonical session participant and board.
- No =E_UPDATE_SESSION= metadata, update-session coordinator, or shadow board remains in production routing.
- Required and optional terminal policy is explicit.
- Unfinished optional work remains visible after required work triggers completion.
- Terminal completion creates one bounded keyed input for the owner session.
- Completion does not interrupt an active turn and is delivered at an idle
  boundary; its coordinator outcome is recorded after the turn settles.
- Dispatch, publication, delivery, outcome, and restart boundaries cannot lose
  or duplicate the completion input.
- Incomplete restore is visible as =restoring= or =dispatching= rather than an empty state.
- Detailed run inspection remains bounded and available through Board activity
  from the chat status, including a dispatch-pending task with no participant.
- Graphical and current-config tests prove the user-visible behavior without touching the live user store.

* Non-goals

- A generic visual editor for arbitrary board topology.
- Rendering the full task graph inside every chat transcript.
- Creating a second Board authority or a separately queried run, task, or
  subagent inventory for the visual renderer.
- Copying worker transcripts, prompts, tool results, or reasoning into the owner session.
- Making process-local =e-work= handles the source of durable run status.
- Creating a second coordinator session for background work.
- Making feature 87 own run policy or presentation.
- Guaranteeing success of the provider turn triggered by the completion input.

* Design self-check for the presentation correction

1. If work stops after Slice 2, is the project better off?  Yes: the owner
   chat can identify its active run and reach truthful task detail while its
   turn is idle.
2. What final direction does it serve?  One Board-native chat and one Board
   activity surface with text and visual renderers, with durable Board facts
   as the authority.
3. Which decisions may change?  Assignment fold length, card layout, and
   colors are local presentation choices.  Run/task identity, status, and
   ordering use existing typed Board contracts; =emacs-egui= is the chosen
   visual runtime and adds no speculative Board extension seam.
4. Who owns each behavior?  Board orchestration owns task disposition, Board
   observation maps the run-focused detail page, and chat and Board activity
   own their presentation.  The =emacs-egui= app renders Board activity only.
5. Does coupling change?  Shells consume narrow detached Board projections;
   neither joins task state from worker sessions nor reads private SQL layout.
6. Do dependencies point the right way?  Core run policy does not depend on
   chat, Board activity, =emacs-egui=, or transcript rendering.
7. Can side effects move outward?  The coherent query stays behind Board
   application operations; opening, focusing, and folding stay in shells.
8. What state is added?  Existing durable Board inputs gain bounded assignment
   coordinates already known at dispatch.  Focus, fold, and visual layout are
   rebuildable presentation state; durable task and message facts remain in
   SQLite.
9. What is the performance cost?  The header and run selector reuse the
   subscribed projection.  Each run-bound input adds only bounded coordinates.
   Both detail renderers use the same bounded set read on view open or
   notification-driven refresh, with no per-message, per-participant, or
   polling read.  The visual app adds local WASM rendering only when opened.
10. Are interfaces semantically real?  The existing run projection and Board
    observation contracts have distinct consumers and do not require an
    unsupported operation from either.
11. What compatibility applies?  Inputs without typed assignment metadata
    keep ordinary message presentation.  Emacs without xwidgets uses the
    native Board renderer; no legacy Board path is restored.
12. What legacy code can be removed?  No retired run or subagent shell returns,
    and the visual renderer adds no alternate Board query path or compatibility
    alias to remove later.
13. How do errors surface?  Expected bounded Board read failures appear in the
    activity view, and missing xwidget or WASM support reports a clear
    presentation error with the native view available.  Unexpected errors
    retain their normal top-level failure.
14. What proves the behavior?  Focused status, Board-query, transcript, visual
    view-model, and semantic event tests prove each owner independently; the
    graphical idle-owner scenario proves both renderers' public composition
    and composer responsiveness.
