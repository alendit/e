* Goal and authority

=F98-G1=: Ordinary chat and tool-heavy turns should reuse unchanged conversation
history as it grows, including between provider requests inside one user turn.
Adapters should maximize useful reuse according to API capability, without
cache-policy options that can weaken it.  Context curation is available only
where the effective adapter/API can support it efficiently alongside caching.
A stable-prefix hit alone is insufficient.

The product authority is the operator's 2026-10-05 instruction: nothing should
cache only through the stable prefix or only through fixed explicit boundaries;
adapters should maximize the probability of doing the right thing.  The operator
further clarified that cache behavior is driven only by adapter/API capability,
with no options that can break it, and that inefficient cache-plus-curation
combinations must not expose curation.  The contracts below own those
requirements.  This supersedes Feature 81's
explicit-only cache policy and Feature 97's deferral of conversation boundaries.
Their unrelated replay, transport, and reasoning contracts remain applicable.
Feature 88's current context-curation effects and continuation semantics remain
authoritative when the capability is available; its availability is now governed
by F98-C6.  Older Feature 81 descriptions of Codex continuation are not
evidence of the current profile, which disables continuation.

Direct scenario: submit through the ordinary chat/Org Canvas harness, execute
tools that add substantial results, and ask a data-dependent follow-up.  Earlier
unchanged history becomes reusable in later subturns; the answer still uses the
required current context.  In a curation-capable session, curate an earlier
result, then continue: the next request obeys the curated projection and
subsequent unchanged history becomes reusable.  In a session without efficient
cache-plus-curation support, curation is absent and ordinary chat still works.
Cache hits must not preserve content excluded by an accepted projection.

Behavioral status: the historical fixed ceilings remain comparison evidence.
Independently reviewed committed code demonstrates growing reuse in the
configured Opus and Codex tool probes; the read-only Board audit also verifies
actual Opus main-chat reuse.  The Board was not rerun and its historical Codex
cause remains unknown.  Anthropic minimal-shape and public OpenAI API external
benefit remain unconfirmed.  Remediation mechanisms are complete; production
curation remains unavailable pending P3.

* Supporting design

** Adapter-owned policy and capability-gated curation

F98-C1/C2 use the existing adapter/API capability seams.  Core continues to own
semantic segments and curation effects; adapters own provider cache policy and
syntax.  API endpoint/model/auth configuration identifies the actual capability;
it does not offer cache-policy selection.  The smallest useful design changes
request rendering, removes caller policy controls, and closes the existing
curation capability boundary.  It adds no durable cache state, second
history authority, cache coordinator, or universal breakpoint configuration API.
Derived boundaries live only for the request; provider caches remain disposable.

The fixed-boundary alternative leaves the observed growing suffix repeatedly
uncached.  Merely choosing a rolling boundary without a stable guard can lose
the otherwise reusable static prefix after a legitimate late-context change.
The proposed automatic/implicit path plus a supported stable guard addresses
both cases with existing segment identities.  It does not rearrange semantic
history to manufacture a hit.

For F98-C6, extend the existing backend context-capability declaration only as
needed to represent efficient cache-plus-curation support.  Derive the carrier
and its model-facing affordances from that trusted declaration, including at
direct adapter entry points.  A request-supplied =:reserved-effect-carrier= or
copied capability map cannot grant support.  Internal closure of an already
consumed frame remains a lifecycle decision; it cannot enable an unsupported
capability.  Gate tool/schema publication, instructions, frame preparation,
reserved-call admission, and effect application consistently.

Capability support comes from accepted adapter/API evidence, not runtime hit
heuristics or a provider probe on every turn.  Validation freshness does not
create a session expiry timer.  A transient cache miss or TTL expiry does not
toggle curation availability.  An unsupported combination simply runs without
curation; it does not require a new fallback workflow.  Accepted keep/summary/
erase effects remain part of session truth even after a capability change.

** OpenAI Responses API

For F98-C1/C2/C4, separate support for explicit markers from the policy that
disables implicit caching.  Remove selection of the fixed explicit-only policy.
Retain a stable developer marker when the endpoint/model supports it while
allowing implicit boundaries over growing messages and tool results.  The
documented combination preserves a stable guard without capping conversation
reuse.  Keep segmented developer-input layout and cache-key routing independent
of cache policy; a missing key must not select a restrictive cache policy.

Use the effective endpoint/model capability, not a model-name guess alone, to
emit optional fields.  Existing =explicit= profile settings represent the old
coupling of capability and policy: remove that option and derive marker support
from the adapter/API declaration.  Remove obsolete renderer defaults and
mechanism tests that require explicit-only mode.  Derive cache routing identity
and supported retention internally; callers cannot rotate the key or shorten
retention on subturns.  F98-C6 also applies to Responses: the ability to carry a
reserved call alone does not establish efficient curation support.

For F98-C3/C4, review the material layout/anchor identity when the wire shape
changes.  Continued requests and full replay must use the same effective cache
policy, but continuation admission remains a semantic decision.  A retained
response ID is not evidence of a cache hit.

** Anthropic Messages

For F98-C1/C4, derive automatic top-level caching from API support and preserve
an explicit stable system guard alongside the moving conversation boundary when
supported.  Remove the cache enable/disable and mode options.  Select compatible
TTL, provider breakpoint limits, and block lookback behavior inside the adapter.
The configured factory no longer chooses those values.

For F98-C2, verify automatic-plus-explicit support on the actual configured
gateway.  If that endpoint lacks automatic caching but supports explicit
breakpoints, use a stable guard plus an advancing eligible conversation block;
do not degrade to the stable guard alone.  Resolve this compatibility choice
with a bounded capability probe and an adapter/API declaration, not broad
error-catching retries on real turns.  If neither path is available, expose
the limitation under F98-C2.

The configured Opus 5.5 gateway accepted top-level automatic caching but fresh
P2 read only the same 26,875-token stable prefix as tool history grew.  The
compatible native Messages shape therefore includes an explicit marker on the
latest eligible conversation block on every request, plus a preceding user
boundary to preserve lookup of the prior written history when an append crosses
the 20-block lookback window.  Keep the stable system/tool guard and supported
top-level automatic field; all markers use the same adapter-owned TTL and at
most three explicit slots.  Derive these temporary boundaries from the current
serialized projection, with no durable cache owner or caller policy setting.
Do not explicitly mark thinking/redacted-thinking or mutate replay inputs.

The [[https://platform.claude.com/docs/en/build-with-claude/prompt-caching][native API documentation]] permits combined automatic/explicit controls;
a same-TTL marker on the last eligible block makes the automatic field a no-op.
The bounded gateway diagnostic with last-two-user markers produced advancing
reads and suffix writes.  That diagnostic selects the compatibility design;
fresh committed-code public P2 now confirms growing reuse for its configured
tool/thinking shape.  The separate minimal repeated request accepts fields and
creates entries but has no observed reads; its qualification remains unconfirmed.
Both observations are retained under =external-evidence/= and independently
dispositioned in =review.org=.

For F98-C3, choose only provider-eligible blocks.  Never insert explicit cache
markers into signed thinking or change native replay order.  Exercise enough
tool blocks to challenge lookback behavior, and match stable/moving TTLs so the
hybrid request is valid.

** Codex, older Responses models, and Chat Completions

For F98-C1/C2/C4, the known first-party ChatGPT Codex Responses API keeps
compatible implicit caching and derives its =session-id= transport header and
=prompt_cache_key= body value from the same nonempty ordinary session identity.
The request policy selects supported affinity once from the effective known
first-party base URL, Responses API and managed-auth capability, then supplies
that one identity to the body and header owners.  Provider labels, display names
and the WebSocket-only built-in profile predicate are not capability proof.
Configured aliases reaching the same effective API receive the same policy;
effective third-party overrides do not.  Selection is independent of model
version and applies to HTTP and WebSocket requests.

The identity remains stable through tool subturns, later turns, reconnect and
HTTP fallback; distinct ordinary sessions remain distinct.  Request-local
context, history growth and tool changes cannot rotate it.  Retired caller cache
controls cannot alter it.  A direct request without a usable session identity
retains the compatible implicit path and receives neither an invented random
per-request affinity key nor an identity shared with real sessions.

Known session affinity is distinct from optional explicit cache controls.
Do not send unqualified =prompt_cache_options=, explicit markers, retention or
continuation fields to Codex.  Preserve the existing compatible older Responses,
third-party and Chat Completions policy.  Test request evolution and effective
defaults, including profiles without counters; missing counters establish neither
a hit nor a miss.  Any API-specific advancing boundary remains an adapter choice
supported by endpoint proof, rather than a caller mode.

For F98-C6, neither Codex nor a compatible third-party Responses endpoint inherits
curation availability from the wire API name alone.  Establish support through
P3 or leave the feature unavailable.  The same rule applies to Chat Completions
if it gains a curation carrier later.

** External compatibility evidence

=P1: Endpoint capability= is separate from semantic composition.  On each
configured cache-capable endpoint/model family, send the smallest valid repeated
request above that provider's cache minimum and prove the selected cache fields
are accepted and their boundaries work.  This covers F98-C2/C5.  Record actual
gateway/profile, model, protocol/headers, material options, UTC completion time,
accepted commit, response status, and ordered usage counters without credentials
or prompt contents.  Official API documentation is design evidence, not gateway
compatibility evidence.

=P2: Growing-history reuse= covers F98-C1/C3/C5 through the public harness.
Hold model, endpoint, tools, stable prefix, and routing identity constant.  Use
at least three append-only requests: establish a baseline; append a substantial
tool result; then append another exchange so the earlier result is reusable.
Size that result to exceed the endpoint's documented cache granularity/minimum,
and retain a content digest to identify the unchanged suffix.  Run immediately
within the TTL and record every subturn, including reads and creation where
available.  Separate a static-prefix control from the growing-history case.
The public tool probe may conservatively bound static input by the entire first
request, captured before any tool result.  Two later cache-read advances must
exceed that initial total; warming within it cannot establish history reuse.

The positive predicate is cache reads attributable to the earlier conversation
suffix beyond the stable-only control, with provider granularity accounted for.
A nonzero read alone cannot pass.  Constant reads at the stable ceiling while
the controlled eligible suffix grows fail this predicate.  Creation counters
are supporting evidence where available, not a requirement for providers that
omit them.  Repeat the curation transition as a separate phase: semantic
projection must pass, a changed prefix may miss, and unchanged rebuilt history
must become reusable again.  Assess the TTL-expiry control separately from a
warm reuse failure.

=P3: Efficient cache-plus-curation capability= covers F98-C6 separately from
basic growing reuse.  Run repeated state-only/keep curation while the history
projection stays unchanged, then summary and erase transitions followed by
further tool subturns and curation.  Use P2's append-only control, request digests,
and per-subturn counters to identify unchanged history and affected boundaries.

The efficiency predicate is continued cache reads attributable to unchanged
conversation history through repeated projection-preserving curation, plus reuse
of the rebuilt history after a material summary/erase change.  A genuine history
mutation can miss at the changed boundary.  Merely refreshing request-local
state or offering/accepting a keep projection cannot repeatedly turn otherwise
unchanged conversation history into uncached input.  A static-prefix-only hit,
or one warm hit after curation stops, cannot pass this gate.  If the adapter/API
cannot satisfy this predicate, declare curation unavailable rather than narrow
the feature, weaken its semantics, or accept inefficient replay.  Missing valid
evidence leaves this capability unconfirmed and unavailable.

Initial P1/P2 evidence is required for each deployed adapter/API whose cache
benefit is claimed.  Reuse evidence only for the same endpoint/team, model
family, protocol, material shape, and accepted revision within 24 hours; this
uses Feature 97's existing evidence window.  Any relevant change requires a new
probe.  Authentication/configuration failure, provider/infrastructure failure,
inconclusive timeout, unavailable counters, and stale evidence leave capability
unconfirmed.  A valid controlled contradictory run is a product-contract
failure.  Adapters without observable cache counters retain an explicit unknown
benefit status rather than blocking independent ordinary-chat release gates or
receiving a fabricated cache pass.  Initial P3 evidence is required before that
combination can advertise curation; an unconfirmed P3 does not block release of
ordinary chat with curation unavailable.
