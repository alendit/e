#+title: Retained context without history cache relocation
#+date: 2026-10-08
#+startup: overview

* Scope and authority

In-progress. The user requested the corrective implementation across all
adapters after the Opus P3 failure. F98-G1 and F98-C1–C6 in [[file:plan.org][plan.org]] remain
the behavioral authority. This supporting design supersedes F88 addendum 4's
literal system-role choice for retained facts and summaries; values, provenance,
authorized retention and erasure remain authoritative.

The direct scenario is two keep cycles followed by later turns: retained facts
remain usable and unchanged prior durable history stays in its native prefix.
Summary and erase must remove their excluded source content; the resulting
projection must support reuse after its actual changed boundary. Implementation
and endpoint qualification have separate evidence status.

The Opus failure combines two placement errors. Core projects retention as
system instructions, which Anthropic moves ahead of history. Session projection
also appends all promotions after the current history tail, so a later turn can
move earlier retained content again even after correcting its role.

* Supporting design

Core owns retained context semantics. Extend the closed portable role vocabulary
with =context=, meaning retained reference data rather than instructions or a new
user utterance. V3 exact/summary and readable v2 promotion records project to
that role. Their canonical content stays unchanged; provenance remains in the
records. Real instructions and request-local source markers retain their roles.

The session semantic projection places retention after its existing
=response-entry-id= anchor, in journal order for multiple records at one anchor.
Resolve that anchor in the selected canonical journal path before filtering
semantic messages. A curation-only response can be an audit-only control entry;
an ordinary tool response can anchor a tool-call entry excluded from the durable
tail. Both still establish an insertion position without inventing a message.
Normal and detached projections share the same pure ordering operation. Message
entry identities remain aligned, with nil identities for derived retention.
The existing bounded SQLite selected-path query supplies content-free anchor
path positions before filtering, including audit-only response entries. Keep
its existing selected-branch, record and byte bounds and lazy aggregate behavior;
no separate store or runtime registry is introduced.
Fork seeds and portable compaction consume that ordering instead of rebuilding
a separate appended tail. Missing eligible anchors are invalid projection data,
not permission to place retention arbitrarily. Covered promotions belong to the
checkpoint and must not be inserted again.
For a partial compaction, partition retention by canonical anchor position
relative to the selected covered-session boundary. Absorb covered items exactly
once; preserve later items' role, content, anchor, order and eligibility after
the generation changes, including records authored in an older generation.
Do not rewrite the journal or pull later facts into an earlier checkpoint.
Existing optimistic preparation/frontier and staleness validation still apply.

Adapters map =context= to native user content at its existing position, with a
short reference-data framing that distinguishes it from a user instruction.
Anthropic must serialize structured canonical values into supported text
content; Responses and Chat Completions use their respective text encoders.
HTTP and WebSocket share Responses translation. Genuine system/developer
instructions remain in their existing channels. Do not synthesize tool calls,
rewrite every system message, or introduce cache policy options.

Existing v2/v3 journals replay with the new semantic role without journal
mutation. New checkpoints preserve =context= through JSON decode, compaction,
fork and reopen. Old system-only checkpoints have no reliable item provenance;
retain their roles rather than guessing which instructions were facts. A changed
portable/native layout invalidates incompatible continuation anchors through
the existing projection/layout identity; no new compatibility mode is added.
That identity must cover retained-role, ordering and adapter framing changes
independently of curation-carrier availability and optional segmented/cache
wire controls. Older/flattened Responses profiles and unavailable-carrier
routes still render accepted records. Prove old-layout rejection and new-layout
continuation compatibility for both qualified-candidate and unavailable routes.

Adapter capability gates remain authoritative. Correct serialization alone
does not enable curation. Unconfirmed routes retain no carrier. Requalification
and wrapper-free production acceptance follow the existing P3 protocol; the
configured gateway route cannot qualify public Anthropic or OpenAI endpoints.

Replace tests that prescribe system-role retention or appended-tail placement.
Retain and strengthen assertions for exact values, provenance, exclusions,
branch/checkpoint identity and forced-call negatives. Native ordering regressions
must observe a later appended turn, not just the first retained fact. Do not
weaken P3 read-retention predicates to obtain a pass; changed-boundary declines
remain inconclusive unless attribution supports a stronger conclusion.

* Validation and delivery

The repository-side implementation can be accepted when R1–R4 and the required
gates pass on the reviewed revision. R5 records capability status independently;
a valid layout/semantic failure returns to remediation. A missing credential or
provider failure does not qualify a route. Availability restoration, if earned,
uses the separately reviewed exact-route normal-source P3 sequence in plan.org.

Commit scoped changes using the repository identity. Do not push, auto-sync,
restart/reload the user's Emacs, or mutate any Board or live SQLite store.
Core/adapter changes require a manual restart before the running Emacs uses them.
