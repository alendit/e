#+title: Responsive Persistence and Scheduled Chat Projection
#+startup: overview

* Done

The 2026-07-30 profile recorded two synchronous session flushes of 481 ms and
544 ms.  The existing timer deferred writes by only 50 ms, then rewrote the
entire session catalog in Emacs's event loop.  Token-usage updates also forced
mode-line redisplay at roughly 55 ms each.

* Direction

Session mutation owns in-memory state and emits durable commands.  A persistence
controller owns the unacknowledged outbox and writer lifecycle.  The bundled
writer process owns JSONL I/O and derived catalog checkpoints.  The journal is
authoritative; the catalog is reconstructible cache state.

Chat presentation will reduce harness events into buffer-local view state and
use =e-ui-work= for coalesced, budgeted rendering.  Terminal events remain
ordered; token usage and progress remain latest-value updates.

* Slices

1. DONE: Move the default persistent store to a Node writer process and keep an
   acknowledged outbox in Emacs.  Preserve JSONL format and reconcile journals
   absent from a stale catalog.
2. DONE: Token usage now enters a coalesced =e-ui-work= projection job.  Hidden
   buffers retain dirty status until a window displays them; unchanged status
   text does not force a mode-line redraw.
3. DONE: Route progress start, steering, hook-audit, and intermittent activity
   through the existing coalesced activity projection.  Terminal transcript
   updates remain ordered and immediate.  Validate replay, writer retry/order,
   hidden-buffer behavior, and a representative event-burst profile.
4. DONE: A later live profile found that a terminal =message-updated= event
   still replayed the complete transcript when a claim-validation correction
   changed a message's display disposition.  The chat buffer now owns a
   transient durable-message-to-block projection.  Ordinary hidden/visible
   changes update that one block and its adjacent layout locally; the explicit
   audit-reveal view retains its separate full replay because it deliberately
   uses a different representation.
5. DONE: Provider text chunks are still accumulated by the core loop for the
   final durable assistant message, but the chat presentation now handles only
   the first chunk in each provider response.  That first event changes the
   status to =streaming=; repeated chunks cannot change the visible shell and
   are suppressed until the next =provider-request-started= event.
