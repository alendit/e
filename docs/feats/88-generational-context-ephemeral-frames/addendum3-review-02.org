** INCOMPLETE P2-03: external timeout classification has no declared bound

The remediation correctly adds:

- separately reportable minimal and tool-heavy external scenarios;
- provider, endpoint, transport, model, profile, layout, cache-key derivation,
  request-shape, timestamp, and revision identity;
- seven-day freshness and immediate invalidation rules;
- distinct availability and product-failure statuses; and
- observational classification for ratio, latency, and warm/cold frequency.

However, =addendum3.org:148= classifies a “bounded timeout,” while the mandatory
record at =:132-136= contains neither the predeclared timeout nor elapsed
duration.  No scenario definition supplies the bound.

Consequently, two executions can apply =inconclusive-timeout= at different
unstated boundaries, and a later reviewer cannot reproduce or audit that
status.  This is an incomplete closure of P2-03, not an external product
failure.

*** Exact correction

Replace the paragraph beginning “Each record contains” with:

#+begin_example
Each record contains provider/profile ID, exact base-URL identity, Responses
WebSocket transport, store mode, native requester identity, exact model ID,
prompt-layout revision, prompt-cache-key derivation revision, material request
shape, scenario name, timestamp, repository revision, total input tokens,
cached input tokens, the scenario's predeclared total timeout, elapsed duration,
and result.

Each scenario runner declares its total timeout before sending the first
request.  The timeout is private execution configuration rather than a durable
F88A3 contract number: it bounds evidence collection but does not change the
required provider outcome or capability identity.  A run that does not conclude
before its declared bound is inconclusive-timeout.  Every other result retains
the failure classification below.
#+end_example

This keeps the timeout local and revisable while making the external result
auditable.  It does not require adding another normative numeric limit to the
matrix.

* Current implementation feasibility

Current source does not implement Addendum 3, but its ownership boundaries can
support it without speculative architecture:

- the adapter already consumes semantic segment identity, renders system
  messages as developer-role Responses input, and owns breakpoint placement;
- changing affected profile delivery to =inherited= naturally leaves
  current/dynamic segments in explicit input;
- harness selection and persistence already treat inherited observations as
  contaminated;
- loop ownership already distinguishes immediate tool continuation from
  durable candidate acceptance;
- the WebSocket owner already has a complete-body recovery path and one-retry
  state that can be narrowed from historical ledgers to latest causal state;
- both =response.failed= and top-level =error= can be normalized at the adapter
  boundary without changing core policy; and
- the historical ledger, eviction, branch-position, and Codex-specific idle
  cluster is localized in the OpenAI adapter and its tests.

The intended frontier reorder may be implemented from harness-owned segments;
it does not require changing durable session order or teaching core about
OpenAI fields.
