* Findings

** P1-08: Mutable request properties can rewrite a completed response's compatibility identity

The contract permits an older response only when the current invariant request
properties equal those recorded for the request that produced it
(=addendum2.org:147-159,167-178=).  The implementation does not preserve that
historical fact:

1. Request start removes three top-level keys but otherwise retains the
   original plist values at =lisp/adapters/openai/e-openai.el:2255-2264= and
   binds that shallow result as =properties= at =:2402-2403=.
2. The request is serialized and sent at =:2576-2580=.
3. Only after an asynchronous completed event does settlement pass the still-
   shared =properties= object into the ledger at =:2529-2537=.
4. Ledger insertion recursively copies hash tables, vectors, and conses at
   =:2015-2034,2122=, but its default branch returns strings unchanged.  Emacs
   strings are mutable.

A one-shot batch reproduction against the exact archive mutated the request's
model string after =websocket-send-text= captured the wire JSON and before the
completion callback.  It then mutated the retained original again after
completion.  The evidence was:

#+begin_example
shared-string=t recorded-model="Xpt-test" compatible-after-mutation=t
#+end_example

The response was actually produced under the pre-mutation model string, yet a
later request using the mutated value was authorized to send that response ID.
The same alias class applies to mutable strings nested in tool schemas and
response-shape objects.  The existing JSON-property test at
=test/e-openai-test.el:3960-3979= checks value equality between independent hash
tables; it never mutates the properties of an active or recorded request.

Classification: Addendum 2 compatibility-authority defect.  Impact: an
incompatible request can be sent incrementally from a response created by a
different wire identity, producing endpoint rejection or semantically invalid
continuation.

Owning correction: at request start, before the first serialization/send,
create one fully detached snapshot of the invariant JSON-like properties,
including copied strings, and record that start-time snapshot on completion.
Add a regression that mutates model and nested tool-schema strings both while
the request is active and after completion; it must preserve the literal sent
identity and make the changed request select full reconstruction.  Copying only
at ledger insertion is insufficient because mutation can occur between send
and completion.

** P1-09: Private-endpoint older-clean-anchor acceptance remains unproved

The addendum says only credentialed built-in Codex evidence establishes that
the private endpoint accepts an older clean response ID on the same socket.  It
defines the semantic scenario at =addendum2.org:309-319= and makes that evidence
an exit condition at =:327=.  The implementation includes a materially useful
live scenario at =e2e/e-live-e2e-test.el:782-997=, but it was not run: the
checked-in handoff records that =/Users/dvorona/.codex/auth.json= is absent and
that the provider semantic claim remains unmeasured at
=addendum2.org:429-434=.  This review had no credentialed alternative and did
not access the user's running Emacs.

The deterministic composed scenario is genuine: it exercises the real
harness/session/context/tool/renderer/adapter chain, substantive tool-started
and tool-finished events, =R1= follow-up, later =R0= selection, current
instructions, absence of raw tool/replay/result material, and connection-loss
full fallback at =test/e-provider-continuation-integration-test.el:1025-1474=.
Its WebSocket and endpoint responses are nevertheless fakes.  It cannot prove
the private provider's undocumented response-cache semantics.

Classification: blocking Addendum 2 acceptance-evidence gap.  Impact: the
package's central optimization may be rejected by the only initial production
endpoint even though all local branching tests pass.

Owning correction: on a remediation revision with available credentials, run
the fast built-in-Codex older-clean-anchor tool-chain scenario and preserve the
literal request, semantic response, socket-reuse diagnostics, and exact command
as durable evidence.  If the endpoint rejects the older response ID, retain the
safe full fallback and return to design rather than declaring acceptance from a
mock.

** P2-10: =response.incomplete= emits =done= without settling the WebSocket request

The ledger contract excludes partial response IDs at
=addendum2.org:177-179,462-465=.  A terminal incomplete response must also
release the active request so the socket lifecycle can proceed.  Instead:

1. =response.incomplete= maps to a backend-neutral =done= item at
   =lisp/adapters/openai/e-openai.el:2978-2981=.
2. The WebSocket handler recognizes only =response.completed= and
   =response.done= as terminal settlement events at =:2600-2602=.
3. It emits the incomplete =done= item but calls =settle-complete= only for that
   narrower completed predicate at =:2614-2623=.
4. Consequently =active-request= remains owned, no idle-close timer is armed,
   and the next request signals =e-openai-websocket-busy= at =:2464-2465=.

The exact-object reproduction reported:

#+begin_example
done-count=0 active-request=t item-types=(done) ledger-count=1 incomplete-recorded=nil
#+end_example

Here =done-count= is the completion-callback count; the one ledger entry was a
pre-existing valid response, and the incomplete response ID was correctly not
admitted.  The named partial-response test does not cover this state
transition: its =partial= arm emits only =response.output_text.delta= at
=test/e-openai-test.el:3763-3771= and then explicitly cancels at =:3822-3840=.

Classification: inherited baseline lifecycle defect now inside Addendum 2's
explicit partial-response and connection-lifecycle acceptance surface.  The
same handler shape exists at =44c1692f=, so this is not attributed as a newly
introduced regression.  Impact: output-limit and other incomplete responses
can leave a session permanently busy until timeout, cancellation, or transport
failure.

Owning correction: give terminal incomplete its own settlement path.  It must
emit the existing incomplete reason, invoke completion exactly once, clear the
active request, never admit the incomplete ID, preserve any valid prior ledger
entries on a healthy socket, and establish the intended idle-close lifecycle.
Add a real =response.incomplete= regression that asserts all of those effects
and proves a following request can start without manual cancellation.

** P2-11: Mandatory 301-second wall-clock acceptance is an avoidable five-minute test

The accepted text requires a pause greater than 300 and less than 600 seconds
at =addendum2.org:321-327=.  The live test defaults that pause to 301 seconds at
=e2e/e-live-e2e-test.el:999-1011= and implements it with literal =sleep-for= at
=:1074-1076=.  This makes one acceptance observation consume more than five
minutes, adds wall-clock and network flakiness, and slows every future attempt
to close the feature without increasing proof of the locally owned policy.

The adapter's 600-second ownership boundary is already controllable without
waiting: =test/e-openai-test.el:3566-3634= intercepts scheduling, proves the
resolved value is exactly 600, proves the socket and ledger remain live before
the callback, then fires the callback and proves one close plus complete ledger
cleanup.  A deterministic fake clock/scheduler can also advance from 301 to
600 instantly while retaining the real request and connection state machine.

Classification: acceptance-design and test-performance defect.  Impact: the
specified gate is prohibitively slow, flaky, and discourages repeatable fixed-
point validation.

Owning correction: amend the accepted addendum and remove the long wall-clock
sleep requirement.  Use deterministic test-only scheduler/clock control or a
backend mock to prove the 300/600 policy boundary immediately.  Retain a fast
credentialed semantic/socket-reuse E2E if it remains useful, but do not require
it to idle for five minutes.

** P2-12: Required transport, token, and latency measurements are not implemented

The observability acceptance requires separate transport input count, provider
input tokens, cached input tokens, request latency, connection ID, reuse count,
and fallback reason at =addendum2.org:485-490=.  The performance contract then
requires deterministic request-body input count and serialized bytes plus live
provider input tokens, cached input tokens, and latency at =:514-524=.

The deterministic composed test inspects semantic request contents and scalar
diagnostics at
=test/e-provider-continuation-integration-test.el:1360-1474=, but neither
counts the request input items nor serializes and measures warm-versus-full
request bytes.  The credentialed scenario captures bodies, handles, response
IDs, semantic output, connection ID, reuse count, and fallback diagnostics at
=e2e/e-live-e2e-test.el:782-997=, but it does not extract or report provider
input tokens, cached input tokens, or request latency.  The implementation
handoff contains no measured values and explicitly says the live run did not
occur at =addendum2.org:429-434=.  Thus credentials alone would not make the
current evidence satisfy the measurement contract.

Classification: Addendum 2 acceptance-evidence and instrumentation gap.
Impact: the package cannot substantiate its claimed wire-work reduction or
separate continuation from cached-input pricing, and it has no measured live
latency tradeoff.

Owning correction: make the deterministic composed scenario report exact input
item counts and =string-bytes= of the literal serialized warm and full request
bodies.  Make the fast credentialed scenario report provider usage fields and
elapsed request latency separately from connection/reuse/fallback diagnostics.
Record missing provider fields explicitly as unavailable rather than inferring
cache savings from =previous_response_id=.

* Architecture self-check

1. The package is useful at this stopping point because it adds bounded older-
   anchor support with safe full fallback, but it is not acceptance-complete.
2. It moves toward provider-neutral generational context with transport-local
   continuation capability.
3. The stable semantic contract remains in the harness; uncertain private-
   endpoint behavior remains in the adapter and credentialed evidence lane.
4. The harness owns clean-anchor selection.  The OpenAI adapter cohesively owns
   WebSocket connection state, request-property compatibility, and ledgers.
5. Coupling is reduced by keeping response IDs and ledger representation out of
   core and public diagnostics.
6. No dependency points from stable harness policy into the concrete OpenAI
   ledger.  The adapter consumes the selected anchor through the existing
   request contract.
7. Socket open/send/close, timers, and provider response handling remain at the
   adapter boundary; no new core side effect is warranted.
8. Added ledger state is connection-local, bounded 256+256, rebuildable, and
   cleared by its connection owner.  P1-08 must make each entry an immutable
   historical snapshot rather than aliased caller state.
9. Fixed-cap lookup and maintenance are independent of durable session length.
   P2-11 identifies the unjustified verification-time regression; P2-12 marks
   the missing measured wire/latency evidence.
10. No speculative shared graph interface was added.  The direct private
    representation satisfies the one concrete adapter contract.
11. Unknown, stale, cross-connection, evicted, incompatible, and endpoint-
    rejected anchors retain full reconstruction compatibility paths.
12. The obsolete scalar compatibility authority is absent; ledger lookup is
    the single compatibility owner.
13. Expected mismatch and unavailable-response errors receive bounded fallback.
    Transport and provider failures surface.  Terminal incomplete currently
    falls between those owners and must be corrected by P2-10.
14. Core behavior has narrow deterministic tests, and the composed test uses
    the real harness/tool chain.  Missing mutation, incomplete-terminal,
    measurement, and credentialed-provider evidence are precisely the narrow
    additions required by the findings.

* Fixed-point verdict

No fixed point was reached at
=d9a7249b2b9acf72920ad04b40be63ac6689e656=.  P1-08 and P2-10 prevent semantic
and lifecycle closure.  P1-09 and P2-12 prevent the accepted provider and
performance evidence closure.  P2-11 requires correcting the acceptance design
itself rather than spending five minutes asleep in a test.

Ordered remediation should first fix and prove request-property snapshot
ownership and terminal-incomplete settlement, then replace the slow acceptance
with deterministic time, add the missing measurements, and finally capture the
fast credentialed private-provider semantic evidence.  A fresh independent Tick
must review the exact remediation revision; later commits are not implicitly
accepted by this artifact.
