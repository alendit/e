* Finding

** P1 F88.10: ambiguous execution can disappear or unblock follow-up without resolution

The plan calls =outcome-unknown= terminal, retains only nonterminal obligations
in resume checkpoints, and separately requires explicit resolution.  Acceptance
allows follow-up when every call is “terminal or explicitly resolved,” so an
ambiguous call can satisfy the first branch, disappear, and unblock the model.

No append-only resolution record or public resolver is specified.  The optional
idempotency/resume declaration also lacks a registration surface, key admission
point, persisted representation, and recovered invocation propagation.  Current
=e-tools-register= has no such contract.

*** Owning correction

=admitted= and =dispatch-started= are nonterminal; =outcome-unknown= is blocked
and nonterminal; =finished=, =failed=, and =resolved= are terminal.  Checkpoints
retain every nonterminal obligation with normalized call, provider linkage, and
persisted idempotency key.

Recovery turns =dispatch-started= without a terminal record into acknowledged
=outcome-unknown=.  It neither redispatches nor permits provider follow-up until
an allowed persisted-idempotency retry or explicit resolution.

Add consumer-shaped =e-harness-resolve-tool-execution=.  It accepts session id,
execution id, and a bounded normalized finished/failed result; appends one
=execution-resolved= record and provider-linked tool result; acknowledges that
prefix; opens the result frame; and then releases follow-up.  Identical repeated
resolution is a no-op; conflicting resolution errors.

For the initial feature add one optional =:idempotency-key-function= to
=e-tools-register=.  It receives normalized arguments and stable execution id
before admission.  Persist a nonempty returned key and pass that exact key in
execution context on every attempt.  Only a persisted key permits automatic
retry after =dispatch-started=.  Defer a broader resume interface.

Required E2E assertions:

- =outcome-unknown= survives checkpoint/restart;
- no redispatch or provider follow-up occurs before resolution;
- the public resolver appends and acknowledges one linked terminal result before
  follow-up;
- identical resolution is idempotent and conflicting resolution fails; and
- the idempotency-key function runs before admission and its persisted key is
  reused on recovered retry.

Exact record/key encoding is mechanism evidence; the public resolver and
restart scenario are contract evidence.
