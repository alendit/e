* Findings

** OPEN P1 =F88A5.I1=: a declared scenario timeout is misclassified and can leave its request active

Contract cells: =F88A5-ADOPTION= external outcome/finalization, joined to
affected =F88A3-CACHE= external execution.

Observed fact: =e-live-e2e--prompt-batch-before-deadline= passes the remaining
scenario budget directly to =e-board-e2e-prompt-batch=
(=e2e/e-live-e2e-test.el:1052-1058=).  When that wait consumes the budget,
=e-board-e2e-wait-batch= signals =E2E turn did not settle within ... seconds=
(=e2e/e-board-e2e-support.el:127-142=).  The finalizer recognizes a timeout only
when the error text contains =inconclusive-timeout= and otherwise records
=provider/infrastructure-failure= (=e2e/e-live-e2e-test.el:987-1016=).  A batch
reproduction with the actual finalizer and the wait helper's error text produced:

#+begin_example
(:condition error :recorded-result "provider/infrastructure-failure")
#+end_example

The adoption runner attempts request cancellation only after the finalizer returns
(=e2e/e-live-e2e-test.el:2633-2675,2869-2871=).  Because the finalizer re-signals
the original condition, timeout and provider-error paths skip this cancellation.
Moreover, capture lists are newest-first (=e2e/e-live-e2e-test.el:2322-2369=),
so =(car (last request-handles))= selects the oldest handle, not the latest one.
The surrounding E2E harness cleanup removes its activity sink and temporary
directory but does not abort the active turn or request
(=e2e/e-live-e2e-test.el:2275-2320=).

Consequence: exceeding the declared deadline emits the wrong normative outcome,
and external I/O may continue after the runner has declared the scenario over
and deleted its temporary session directory.  The record therefore does not
enforce the accepted deadline or failure-side-effect boundary.

Minimal correction: represent expiry of the shared scenario deadline with a
dedicated bounded condition and classify that condition as
=inconclusive-timeout=; do not infer it from arbitrary provider error text.  Put
active-request cancellation in an =unwind-protect= that encloses the external
scenario finalizer, or equivalently make the E2E harness cleanup abort the active
turn before deleting its state.  Resolve the active/newest handle rather than
reusing the current oldest-handle expression.  Apply the same cleanup rule to the affected
cache selectors; do not add an adapter-specific runtime timeout.

Acceptance evidence: force the board wait to consume the remaining scenario
budget after a request handle exists.  Assert exactly one content-free record
with =result inconclusive-timeout=, preservation of the original timeout
condition, exactly one cancellation, no later callback mutation, and no request
after the deadline.  Inject a non-timeout provider error separately and assert
=provider/infrastructure-failure= plus cancellation of the newest/active handle,
not an older completed handle.  Retain success,
configuration, semantic, cache, and skip finalization cases.

** OPEN P1 =F88A5.I2=: carrier evidence is taken from any request instead of the source-bearing continuation

Contract cell: =F88A5-ADOPTION= carrier/model-selection localization.

Observed fact: after the ordinary tool finishes, the runner declares the
carrier present when =context-curate= appears in any captured first-turn body
(=e2e/e-live-e2e-test.el:2781-2790=).  It does not identify the request that
contains the ordinary =function_call_output= and its ephemeral-source marker.
If the initial request contains the carrier but the source-bearing continuation
loses it, =carrier-present-p= is still true.  The resulting zero curation records
then take =model-selection-failure= and become =product-contract-failure=
(=e2e/e-live-e2e-test.el:2725-2731,2791-2798=).

Consequence: a repository composition regression can falsely disprove autonomous
model adoption for an external capability identity.  This crosses the explicit
boundary that only a valid ordinary-tool source and carrier presentation may
produce =product-contract-failure=.

Minimal correction: locate exactly one chronological source-bearing request by
the ordinary call/output linkage and the matching ephemeral marker, then require
the reserved carrier in that request's =:tools=.  Keep the initial request and
other continuations out of this gate.  Carrier absence must remain
=semantic-failure= with =failure-stage carrier=; only a valid localized carrier
followed by no valid effect may become =product-contract-failure=.

Acceptance evidence: add request-boundary regressions in which (1) only the
initial request has the carrier and (2) only the source-bearing continuation has
it.  The first must record carrier semantic failure and never a product failure;
the second must clear the carrier gate.  Retain the passing exact/summary paths
and prove that the evidence record still contains no source or model content.

** OPEN P2 =F88A5.I3=: a later provider failure discards an already established adoption result

Contract cell: =F88A5-ADOPTION= independent adoption/composition results.

Observed fact: =adoption-result= and =composition-result= start as =unavailable=
and are copied verbatim by the failure capture
(=e2e/e-live-e2e-test.el:2624-2674=).  The runner verifies one preserving v3
curation and records its disposition before the second user request
(=e2e/e-live-e2e-test.el:2791-2814=), but it does not set =adoption-result= to
=pass= there.  It updates both subresults only in a final semantic classification
after the second provider turn, or on an ERT assertion failure
(=e2e/e-live-e2e-test.el:2675-2734,2814-2868=).  A timeout or provider error in
that second turn therefore emits =adoption-result unavailable= even though the
captured curation record and disposition already prove adoption.

Consequence: the supposedly independent fields lose the exact model-selection
observation when later infrastructure prevents composition evidence.  Such a
record cannot distinguish “model adopted, follow-up unavailable” from “model
adoption never became observable.”

Minimal correction: checkpoint =adoption-result pass= immediately after the one
valid preserving effect and its audit linkage are established, while leaving
=composition-result unavailable= until the next-turn checks settle.  A later
provider or timeout outcome should retain that adoption result and disposition
while its top-level result remains the appropriate availability class.

Acceptance evidence: inject a provider error and a scenario timeout at the
second-turn request after a valid exact effect, and repeat with a preserving
summary.  Each case must emit exactly one record with =adoption-result pass=,
the actual disposition, =composition-result unavailable=, no semantic failure
stage, the correct top-level availability result, and the preserved original
condition.

initial ordinary-tool request, its one linked tool-output continuation, and its
one linked reserved acknowledgement; a duplicate of any stage must consume a
matching retry event.  Assert exactly one curation record for that tool turn.
Do not add a general replay ledger.

Acceptance evidence: cover exact zero/one retries at the initial, ordinary-tool
follow-up, and reserved-ack stages; fail one-over-event, two acknowledgements,
an acknowledgement in the first/warm turn, a second curation record, a changed
body, and wrong call/output linkage.  Retain the current five-request HTTP

* Architecture review

The production change respects the architectural boundary: core owns neutral
source lifetime presentation, the OpenAI backend adapter owns its Responses
function description, the model selects a disposition, and existing
core/harness/session code validates and persists it.  No production dependency
points from stable policy toward the adapter, and no new state or speculative
interface appears.

The open architecture defect is confined to the E2E application boundary.
Failure cleanup is placed after a re-signalling finalizer rather than in an
outer cleanup boundary; evidence classification uses a scenario-wide presence
test where a causal request-boundary join is required; and the retry helper
accepts an acknowledgement category without accounting for its cardinality or
retry provenance.  The minimal remediations belong in the E2E runner and its
tests, not in core curation policy or the OpenAI runtime adapter.  No broader
architectural follow-up is justified.
