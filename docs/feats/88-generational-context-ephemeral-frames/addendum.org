#+title: Addendum: Proven Request-Local Observation Delivery for ChatGPT Codex
#+date: 2026-08-25
#+startup: overview

* Status

Ready.  Design Tick 3 accepted this addendum with zero P0--P3 findings.  This
addendum reopens one narrow adapter-conformance package after
Feature 88: expose the existing kind-scoped observation-delivery interface from
the built-in ChatGPT Codex profile, and preserve the canonical OpenAI API
profile's already-supported behavior.

Design and implementation each require their own normal, non-fast Tick/Tock
fixed point before this addendum is Done.  The parent Feature 88 design remains
authoritative except where this addendum changes the built-in Codex capability
claim and its acceptance evidence.

* Decision

Use the interface Feature 88 already provides:

#+begin_src elisp
(e-backend-context-capabilities backend options)
(e-backend-observation-delivery-for-kind capabilities kind)
#+end_src

Do not add a second capability, provider predicate, harness switch, or OpenAI
wire field to core.  The OpenAI adapter will expose its proven semantics through
the existing =:observation-delivery= capability.  The preferred returned value
is the explicit kind-scoped map:

#+begin_src elisp
(:observation-delivery
 ((:kind current-state :mode request-local-replaceable)
  (:kind dynamic-context :mode request-local-replaceable)
  (:kind tool-result :mode inherited)
  (:kind trace :mode inherited)
  (:kind retrieved-excerpt :mode inherited)))
#+end_src

The built-in ChatGPT Codex profile may advertise this map only for the exact
profile and effective wire identity whose behavior has been proved.  The
canonical OpenAI API profile must continue to advertise the same semantic map.
The harness resolves each frontier item with
=e-backend-observation-delivery-for-kind= and remains unaware of
=instructions=, =previous_response_id=, ChatGPT auth, or provider profile
names.

The adapter-private profile declaration may remain the compact proof flag
=:observation-delivery request-local-replaceable=.  The adapter capability
resolver, not callers, expands that proof into the public kind-scoped map.
=inherited= remains the conservative profile default.  This is one interface
with an adapter-owned declaration and a provider-neutral resolved value, not two
capability systems.

These are static adapter/profile declarations.  Resolution reads the normalized
configured profile current at each existing profile lookup and capability
query; it never learns support by making a provider request, running a probe,
or consulting a discovery registry/cache.

* Scope

This package covers only replacement of =current-state= and =dynamic-context=
on a normal request.  For an eligible Responses continuation, their complete
current values are rendered in the new request's top-level =instructions=.

It does not claim replacement for:

- =tool-result=;
- =trace=;
- =retrieved-excerpt=;
- a function call, replay item, and result bundle; or
- any other inherited request or response item.

Missing map entries resolve to =inherited=.  A mixed frontier with replaceable
current state and any inherited ephemeral item remains contaminated as a whole.
It must hold the prior clean anchor or use stateless reconstruction; it must not
advance through the mixed response merely because its canvas was replaceable.

No runtime capability discovery/probe, discovery registry/cache, persistence,
lifecycle journal, transaction, crash recovery, compaction, UI, generic provider
framework, new context state, or speculative replacement mechanism is part of
this addendum.  In particular, it adds no interim machinery ahead of the
separately planned SQLite ACID persistence boundary.

* Evidence baseline

The following is existing evidence, not completion evidence for this addendum:

1. =lisp/core/e-backend.el= already validates kind-scoped
   =:observation-delivery= and provides
   =e-backend-observation-delivery-for-kind=.  Missing kinds are inherited, and
   the legacy scalar is deliberately limited to =current-state= and
   =dynamic-context=.
2. The canonical =openai= profile already declares
   =request-local-replaceable=.  Its effective capability is gated by the
   canonical first-party endpoint and Responses WebSocket transport.
3. The built-in =codex= profile currently omits the declaration and therefore
   resolves to =inherited=.  Consequently
   =e-live-e2e-test-openai-codex-store-false-continues= deliberately expects a
   held anchor, full replay, and no =previous_response_id=.
4. =e-openai--normalize-model-providers= recognizes the canonical built-in
   Codex profile and =e-openai-provider-profile= reapplies normalization on
   every lookup.  The current Doom configuration redefines that same canonical
   profile shape after package load, so lookup-time normalization is the owning
   compatibility boundary; the host configuration must not need a duplicate
   capability declaration.
5. The 2026-08-12
   [[../../bugs/openai-websocket-cross-turn-instructions-replay/investigation.org][OpenAI WebSocket cross-turn instructions investigation]]
   includes a credentialed live-provider E2E.  It proved that the ChatGPT Codex
   Responses WebSocket accepted changed top-level instructions together with
   =previous_response_id= on one retained socket.  It did not connect that
   transport fact to Feature 88's anchor-advancement policy.
6. The first-party [[https://developers.openai.com/api/reference/resources/responses/methods/create][OpenAI Responses create reference]] states that when
   =instructions= is used with =previous_response_id=, the previous response's
   instructions are not carried into the next response.  This documents the
   canonical OpenAI API claim.  It does not by itself document the private
   ChatGPT endpoint; that claim remains grounded in credentialed conformance
   evidence.

Completion therefore requires new evidence that the exact built-in ChatGPT
profile resolves the static capability and drives the existing generic harness
and WebSocket request path safely, plus renewed credentialed endpoint evidence.
The existing provider-neutral canvas-replacement E2E remains the effective-
context and anchor-policy proof; passing the old adapter transport test alone is
insufficient.

* Semantic and wire protocol

Let =C= be stable developer input, =D1= and =D2= durable/user deltas, and =E1=
and =E2= successive current-state or dynamic-context observations.

For an eligible clean ChatGPT or OpenAI continuation:

#+begin_example
request 1:
  input        = [C, D1]
  instructions = E1
  previous_response_id absent
                         -> response R1, clean anchor candidate

request 2:
  input        = [D2]
  instructions = E2
  previous_response_id = R1
                         -> response R2, clean anchor candidate
#+end_example

=E1= must be absent from request 2's literal =instructions= and =input=, and
=E2= must be present once.  Provider-neutral disappearance from effective model
context and the corresponding anchor policy remain proved by
=e-context-lifetime-e2e-test-canvas-replacement-profiles=; this addendum does
not create another provider-context simulator.  Stable input already owned by
=R1= is not resent on the warm continuation.  ChatGPT retains its existing
=store=false=, encrypted-reasoning, segmented developer-input, and
no-explicit-breakpoint shape; enabling semantic replacement must not send
=prompt_cache_options= to that endpoint.

=R2= may replace =R1= as the clean anchor only when all request and response
frontier items are replaceable or durable.  A tool call/result/replay bundle or
other inherited ephemeral ancestry keeps the existing Feature 88 contamination
rules unchanged.

* Provider identity and fallback

The built-in ChatGPT proof is bound to all of these facts:

- provider id =codex=;
- profile name =ChatGPT Codex=;
- profile base URL
  =https://chatgpt.com/backend-api/codex=;
- =:wire-api responses=;
- =:responses-transport websocket=; and
- ChatGPT/Codex authentication via =:requires-openai-auth=.

=e-openai--builtin-codex-profile-p= remains the single adapter owner of that
profile identity.  =e-openai--normalize-model-providers= adds the built-in proof
to that exact profile when it is absent, alongside the existing mandatory
Codex wire requirements.  An explicit =inherited= declaration is a conservative
opt-out and is not overwritten.  Because provider lookup normalizes every time,
the checked-in default and a later canonical redefinition such as Doom's obtain
the same behavior.

=e-openai--profile-context-capabilities= must also validate effective identity.
The following cases are normative:

| Profile/effective request | Resolved delivery | Continuation consequence |
|---------------------------+-------------------+--------------------------|
| exact built-in =codex=, canonical endpoint, Responses WebSocket, native requester | current/dynamic replaceable; all other kinds inherited | existing linear continuation remains eligible |
| built-in =codex= with effective base-URL override | inherited | =none=; stateless fallback |
| built-in =codex= with HTTP/transport override | inherited | =none=; stateless fallback |
| built-in =codex= with injected request function | inherited | =none=; treat it as an unproved transport |
| noncanonical profile under the reserved =codex= id | inherited unless it is restored to exact built-in identity | no built-in proof |
| distinct custom profile without an explicit proof declaration | inherited | its separately declared continuation cannot authorize replacement |
| distinct custom profile with explicit proof and matching configured/effective endpoint and transport | current/dynamic replaceable; all other kinds inherited | its declared continuation may be used |
| custom profile with an effective endpoint or transport override | inherited | =none=; stateless fallback |
| exact canonical =openai= API profile and native Responses WebSocket | current/dynamic replaceable; all other kinds inherited | existing linear continuation remains eligible |
| canonical =openai= with endpoint, transport, or requester override | inherited | preserve the existing stateless fallback |

A custom profile's explicit declaration is evidence supplied by that profile's
owner; similarity to an OpenAI URL, model name, auth mode, or JSON shape is not
proof.  A named custom profile may retain the existing injected requester path
for its own deterministic conformance tests, but the two built-in first-party
claims may not cross such an override.

All rows describe static configuration resolution.  None authorizes runtime
probing, provider negotiation, learned capability state, or a cache of discovery
results.

   boundary to run the exact built-in =codex= and canonical =openai= profiles
   without =:request-function=.  Assert the resolved five-kind map, literal

   retained newest clean anchor.  Keep
   =e-context-lifetime-e2e-test-canvas-replacement-profiles= as the
   provider-neutral effective-context and anchor-policy proof; do not add

* Acceptance

** Deterministic owner tests

- Core resolves =current-state= and =dynamic-context= to
  =request-local-replaceable= and resolves =tool-result=, =trace=, an omitted
  kind, and =retrieved-excerpt= to =inherited=.
- Missing capability declarations remain fully inherited; malformed or unknown
  declarations fail visibly.
- A stale canonical Codex profile matching the current Doom redefinition is
  normalized on lookup to the built-in proof without changing Doom config.
- A noncanonical or custom profile is not modified merely because its endpoint
  resembles ChatGPT or OpenAI.  An explicit custom proof works only for its
  matching endpoint/transport.
- Explicit built-in =inherited= remains an opt-out.
- Effective base-URL, transport, and built-in requester overrides resolve to
  inherited delivery and no continuation.  This must be proved for both
  built-in ChatGPT and the existing canonical OpenAI profile.
- The canonical OpenAI API profile still resolves both current kinds as
  replaceable and all other kinds as inherited.

** Harness and adapter composition

Use two existing proof layers; do not add another stateful provider/effective-
context simulator.

The credential-free
=e-context-lifetime-e2e-test-canvas-replacement-profiles= remains the
provider-neutral proof of effective-context equivalence, old-canvas
disappearance, per-kind conservatism, stable-prefix fencing, and clean-anchor
advancement for none, linear, branchable, and replaceable profiles.

Minimally extend or parameterize the existing Responses WebSocket integration
at the socket boundary for the exact built-in =codex= and canonical =openai=
profiles.  It crosses the real harness, session, context assembly, static
capability resolver, OpenAI renderer, and existing anchor admission without
=:request-function=.  It must prove:

1. the resolved capability is the five-kind map: =current-state= and
   =dynamic-context= are replaceable while =tool-result=, =trace=, and
   =retrieved-excerpt= are inherited;
2. request 1 contains =OBSERVATION-OLD= only in current top-level
   =instructions= and contains no =previous_response_id=;
3. response =resp-1= becomes an eligible clean anchor;
4. request 2 uses =previous_response_id= =resp-1=, sends only its fresh input
   delta, and contains =OBSERVATION-NEW= exactly once in =instructions=;
5. =OBSERVATION-OLD= is absent from the complete literal request 2;
6. the socket/request mode is incremental and response =resp-2= safely advances
   the clean anchor;
7. ChatGPT request bodies remain =store=false=, request encrypted reasoning,
   preserve segmented stable input, and omit explicit prompt-cache fields;
8. the same scenario against the canonical OpenAI profile preserves its
   explicit-cache request shape and replacement semantics.

The existing
=e-provider-continuation-integration-test-ephemeral-bundle-does-not-contaminate-anchor=
remains the required mixed-frontier gate: an inherited tool-result frontier
cannot advance the clean anchor even beside replaceable current state.  The
built-in socket scenario does not duplicate that tool lifecycle because the
capability map and anchor decision are already covered at their owning
boundaries.

** Credentialed ChatGPT E2E

Run the exact built-in ChatGPT Codex profile over its real Responses WebSocket.
The revised =e-live-e2e-test-openai-codex-store-false-continues= must require:

- exact canonical profile identity before making a claim;
- one reused WebSocket and an incremental second request;
- a second-request =previous_response_id= matching the first completed
  response;
- before turn two, an explicit assertion that both the first assistant response
  and its durable canonical session message contain no =OBSERVATION-OLD=;
  either leak fails the probe as ambiguous rather than continuing or skipping;
- =OBSERVATION-NEW= in fresh =instructions= and no =OBSERVATION-OLD= anywhere
  in the second literal request;
- a second-turn answer that reports =OBSERVATION-NEW= and rejects
  =OBSERVATION-OLD=;
- =request-local-replaceable= diagnostics, a present replaceable frontier, and
  =advance-eligible= anchor safety;
- the newest clean response becoming the retained anchor; and
- continued absence of =prompt_cache_options= and explicit breakpoints.

The asserted first-turn no-leak condition makes the model-visible second-turn
marker check an unambiguous renewal of endpoint conformance.  The existing
canvas-replacement E2E remains the non-probabilistic provider-neutral
effective-context proof, and the minimal built-in socket integration proves the
literal adapter path.  A credential or endpoint skip must be reported as a
skip, not a live pass.

* Performance and compatibility

The normal path adds only a small profile field/map expansion and existing
per-kind lookups.  It removes repeated full transcript input for clean ChatGPT
turns whose only changing ephemeral frontier is current state.  No additional
provider call, capability probe, discovery lookup, model call, history scan,
persistent write, or UI work is allowed.

The public core accepts the legacy scalar, so third-party adapters remain
compatible.  OpenAI changes to the preferred explicit map; consumers must use
=e-backend-observation-delivery-for-kind= instead of assuming the capability is
a scalar.  Explicit inherited profiles and all unproved identities retain the
safe current behavior.  The only obsolete path removed is the built-in Codex
default that treats its already-conformed request-local instruction channel as
inherited and therefore forces full replay.

* Architecture self-check

1. *Useful stopping point?* Yes.  The package turns an already-proved ChatGPT
   wire behavior into safe generic anchor advancement while retaining stateless
   fallback.
2. *Final direction?* Provider-neutral semantic lifetime policy accelerated by
   narrow adapter conformance claims.
3. *Stable and uncertain decisions?* Kind-scoped replacement and conservative
   fallback are stable.  Private endpoint behavior is empirical and therefore
   isolated in one exact profile/identity gate with a renewable E2E.
4. *Owner?* Core owns the delivery vocabulary and lookup; the OpenAI adapter
   owns endpoint evidence and wire projection; the harness owns frontier and
   anchor policy.  Each has one reason to change.
5. *Coupling?* Reduced: the harness consumes only the existing semantic helper,
   and neither core nor tests need a ChatGPT-specific policy switch.
6. *Dependency direction?* The provider adapter depends on the stable backend
   contract.  Core gains no dependency on OpenAI, WebSocket, profile, or auth
   details.
7. *Side effects outward?* Network and socket behavior remain in the adapter;
   capability resolution and projection remain pure before send.
8. *State?* No state is added.  Capabilities are derived from static
   configuration; request/frontier data is turn-local; anchors remain
   disposable existing optimization state.
9. *Performance?* Capability lookup is bounded by five kinds.  Eligible warm
   turns replace full replay with one continuation delta; fallback cost is
   unchanged.
10. *Real substitutable interface?* Yes.  Every adapter may truthfully return
    inherited; proven adapters return the same kind map without weakening any
    non-current observation semantics.
11. *Compatibility?* Legacy scalar declarations remain accepted, explicit
    opt-out remains available, host canonical-profile redefinitions are
    normalized on lookup, and unproved overrides become stateless.
12. *Legacy removable now?* Remove only the built-in Codex inherited default
    and scalar assumptions in OpenAI-specific expectations.  Keep generic
    scalar compatibility.
13. *Errors?* Unknown declarations remain configuration errors.  Expected
    identity mismatch selects explicit conservative fallback; transport errors
    continue through the existing backend path.
14. *Independent proof?* Core owner tests prove kind semantics; the existing
    canvas-replacement E2E proves provider-neutral effective disappearance and
    anchor policy; a minimal built-in socket integration proves profile/request
    mapping; credentialed E2E proves the private endpoint after an asserted
    no-leak precondition; canonical OpenAI tests and docs prove non-regression.
