#+title: Generational Context with Ephemeral Frames
#+startup: overview

* Status

In-progress.

* Goal

Make model context a provider-neutral state projection with three explicit
model-visible lifetimes: an immutable checkpoint for one generation, an
append-only durable tail, and one-transition ephemeral observation frames.
Large addressable data remains outside model context behind existing resource
and context-reference handles until explicitly retrieved; that delivery mode is
not a fourth frame state.

The result should preserve hot reusable prefixes on ordinary turns, prevent
canvas snapshots and bulky tool observations from becoming permanent causal
history, and pay the cold-cache cost only at deliberate generation boundaries.

* Problem

The current context model distinguishes stable and dynamic placement, but not
durable and ephemeral lifetime.

Today a request is approximately:

#+begin_example
[static][stable][current canvas][durable transcript]
#+end_example

That ordering gives a provider a cache-friendly stable prefix.  It does not
make =current canvas= replaceable in the provider's retained causal state.  If
an adapter advances =previous_response_id= after a request containing canvas
snapshot =E1=, a later request containing =E2= is effectively:

#+begin_example
A -> B -> E1 -> response-1 -> | provider anchor |
                                  \
                                   E2 -> response-2
#+end_example

The instruction that =E2= supersedes =E1= helps model behavior, but does not
remove =E1= from the transformer's inherited context.  Tool results have the
same problem more directly: their complete bodies are journaled as transcript
messages and remain in later model projections until compaction.

Existing compaction is useful but solves a different problem.  It occasionally
replaces an old transcript prefix with a readable continuation summary.  It
does not prevent high-volume observations from entering that prefix in the
first place, and running it every turn would sacrifice cache reuse and add a
summary call to the hot path.

The missing protocol is therefore:

#+begin_example
observe -> consume -> promote selected information -> forget observation
#+end_example

rather than:

#+begin_example
observe -> append forever
#+end_example

* Context lifetime model

The names describe logical model-context lifetime.  They do not describe how
long an audit record remains on disk, and =ephemeral= here is unrelated to a
provider's prompt-cache =cache_control= vocabulary.

| Lifetime | Meaning | Examples |
|----------+---------+----------|
| =CHECKPOINT= | Immutable semantic baseline for one generation | compacted continuation, current goal, established decisions |
| =DURABLE= | Append-only delta reused by later invocations in the same generation | user intent, assistant decisions, promoted facts |
| =EPHEMERAL= | Observation available to one reasoning transition and then absent unless promoted | tool output, trace, canvas snapshot, large source excerpt |
| =EXTERNAL HANDLE= | Existing resource/reference delivery mode, not a frame lifetime; resolving a handle creates a bounded ephemeral observation | full traces, source indexes, runtime objects |

The three lifetimes classify session-derived causal context.  They do not
replace the accepted request-time =static-prefix= and =stable-context=
segments.  The complete semantic request is:

#+begin_example
active static-prefix + active stable-context
+ generation checkpoint + durable tail + open observation frame
#+end_example

=e-capabilities= continues to rebuild =static-prefix= and =stable-context= from
the active capability set for each request.  They are not copied into generation
records or promotions.  Their fingerprints participate in anchor compatibility:
a changed capability instruction or stable provider segment appears on the next
request and invalidates or rebuilds an incompatible anchor without requiring
compaction or mutating the generation checkpoint.  Current-state segments move
to the ephemeral observation frontier.

=e-session= remains the canonical audit history.  A consumed ephemeral record
may remain in the journal for replay, diagnosis, or export while being absent
from future model context.  Storage durability and model-context durability
must not be represented by one overloaded flag.

Within generation =G17=, logical state is:

#+begin_example
G17
  checkpoint: C17
  durable tail: D81 D82 D83
  open frame: E20                 ; at most the observations for one transition
  resource handles: trace:t19 value:v72 test-run:r14
#+end_example

Normal evolution is monotonic:

#+begin_example
request 1: [C17][D81]
request 2: [C17][D81][D82]
request 3: [C17][D81][D82][D83]
#+end_example

An observation is attached only at the frontier:

#+begin_example
[C17][D81 D82 D83][E20]
                       |
                       v
                 promote Delta84

[C17][D81 D82 D83][Delta84]
#+end_example

=E20= is not part of the second request.  If no selected information is
promoted, forgetting it is intentional.

* Required invariants

1. Local session and resource state remain authoritative.  Provider state is a
   disposable acceleration and can always be rebuilt from the local semantic
   projection.
2. A generation's checkpoint never changes.  Durable state in that generation
   is append-only.
3. An ephemeral frame is visible only while open and to the single reasoning
   transition that consumes it.  Closing the frame removes its observations
   from ordinary future projections.
4. Promotion is explicit and small.  A promotion records facts or decisions,
   not an unreviewed copy of the observation.
5. The audit journal may retain the original observation, frame lifecycle, and
   promotion provenance without making those records model-visible forever.
6. A provider anchor is reusable only when its inherited provider state is
   semantically clean: it contains checkpoint and durable material, but no
   observation that the next request is supposed to forget.
7. Missing provider capabilities reduce optimization, not correctness.  The
   universal fallback is stateless reconstruction from local state.
8. Compaction creates a new generation and is deliberately rare.  It is not
   the mechanism for closing ordinary observation frames.

* Anchor rule

** Provider without a replaceable context channel

Let =H= be the latest clean provider anchor:

#+begin_example
C -> D1 -> D2 -> H -> | we are here |
                       \
                        E1 -> R1
#+end_example

The observation-bearing response =R1= must not replace =H= as the clean anchor.
The harness consumes =E1=, persists selected durable delta =Delta3= locally,
and builds the next invocation from =H=:

#+begin_example
C -> D1 -> D2 -> H -> | clean anchor stays here |
                       \
                        Delta3 -> E2 -> R2
#+end_example

=E1= is absent.  If the provider cannot branch from =H=, the adapter sends a
stateless replay instead:

#+begin_example
[C][D1 D2 Delta3][E2]
#+end_example

This is what “the anchor must not advance across the observation-bearing
invocation” means.  Advancing would make =E1= an inherited ancestor that the
harness can no longer remove.

** Provider with a proven replaceable context channel

A provider may advertise a channel whose prior value is not inherited by
continuation.  Then observation delivery does not contaminate the anchor:

#+begin_example
H -- replaceable=E1 --> R1 -> | safe new anchor |
R1 -- replaceable=E2 --> R2
#+end_example

This exception is capability-driven and covered by an adapter conformance
test.  Merely appending a newer system/developer message does not qualify as
replacement.

For OpenAI Responses, the public API documents that top-level =instructions=
from the prior response are not carried forward with =previous_response_id=.
An eligible OpenAI adapter can therefore render current canvas state in the
request-local =instructions= channel while keeping stable developer input and
durable history in the reusable response chain.  Profiles that do not prove
this wire behavior use the clean-anchor or stateless path.

* Promotion contract

The core protocol needs a provider-neutral durable delta, not a provider-owned
summary format.

- User messages and normal assistant messages keep their existing durable
  semantics.
- Raw tool results, traces, large retrieved excerpts, and replace-current-state
  snapshots are ephemeral by default for new records.
- Tool intent and arguments remain in the audit journal.  Their future context
  projection is governed by frame state rather than by the fact that they were
  journaled.
- A reserved core =context-promote= effect accepts facts/decisions plus source
  frame ids.  Its model-facing syntax may use a tool-call-shaped response item,
  but it is not processed as an ordinary observation-producing tool.
- The effect validates that every source belongs to the currently consumed open
  frame and that the payload satisfies explicit limits.  The initial limits are
  one promotion effect per consuming response, at most 16 facts, and at most
  8 KiB of normalized UTF-8 content; rejection occurs before session mutation.
- Promotion records are committed as part of frame settlement.  Any subsequent
  provider request is projected from checkpoint plus durable tail plus its new
  frame: it includes the promotion and a bounded acknowledgement, but excludes
  the consumed observation.
- If the same consuming response also emits ordinary tool calls, those calls and
  required provider replay items become durable transition records; their tool
  results open the next frame.  The adapter must reconstruct required call/result
  linkage without continuing from an anchor contaminated by the prior frame.
- Provider adapters render this effect but never select or validate promoted
  facts.

The loop buffers reserved effects and ordinary tool calls until the provider
response is complete.  It validates the complete promotion and tool-call set
before dispatching any tool.  It then persists and receives acknowledgement for
the consuming response, accepted promotions, and =frame-settled=.  Only after
that acknowledgement may ordinary tools execute.  Validation or durable-write
failure dispatches no tool, records the failed attempt, and leaves the frame
retryable.  Completed tool results are persisted with the next =frame-opened=
before any follow-up provider request.

The initial implementation should keep the protocol strict and observable.
Do not add an automatic per-observation summarizer as a fallback: that would
restore cost and latency on the hot path and blur whether a fact was selected.

** Frame state and durable settlement

Frame state is derived from append-only session records, not from one mutable
status flag.  One frame records its generation id, observation entry ids,
consumption-attempt ids, consuming response entry ids, promotion entry ids, and
terminal settlement.

Every admitted observation has a restart-stable provider-neutral reference.  A
journal-backed observation references the durable entry containing its exact
payload.  A request-time current-state observation instead records its owning
provider, durable source reference, source version or content fingerprint,
render-layout revision, and rendered fingerprint; mutable buffer objects are
not durable references.  Before retry, replay rebuilds the current-state
observation and compares fingerprints.  A match retries the same frame.  A
mismatch or unavailable source appends an explicit =frame-aborted= record and
opens a new frame from newly captured state; it never silently substitutes new
bytes into the old frame or marks the old observation consumed.

- Persist =frame-opened= with its observations before those observations are
  eligible for a provider request.
- Persist =frame-consumption-started= with a unique attempt id before dispatch.
  Provider failure or cancellation before a consuming response is durably
  accepted records a failed attempt and leaves the frame eligible for explicit
  retry.  Consumption is at-least-once across ambiguous provider failures, not
  falsely exactly-once.
- Settle in this order: consuming assistant/tool-call records, validated
  promotions, then one =frame-settled= record referencing them.  The session
  persistence boundary must acknowledge that ordered prefix before the loop
  excludes the frame, starts another provider request, or advances a clean
  anchor.  This acknowledgement remains asynchronous; it must not add blocking
  filesystem I/O to the hot path.
- Replay derives closure from =frame-settled=.  A started attempt with no durable
  consuming response becomes retryable.  A durable consuming response and
  promotions with a missing settlement record are completed idempotently without
  presenting the observation again.
- The Feature 78 checkpoint manifest retains the active generation, every
  unsettled frame, its referenced observations, and the settlement records
  needed to make that derivation without scanning pre-checkpoint history.

** Tool execution state and recovery

Each accepted ordinary tool call has a stable execution id and durable execution
state separate from frame settlement.  =admitted= and =dispatch-started= are
nonterminal states; =outcome-unknown= is a blocked, nonterminal recovery state;
=finished=, =failed=, and =resolved= are outcome kinds, not independently
terminal records.  Only a final =execution-settled= record makes an execution
terminal.  The resume checkpoint retains every execution lacking that marker,
the normalized call and provider linkage, and every partial result record needed
to finish or resolve it without scanning pre-checkpoint history.  It also
retains settled result identities and any partial aggregate-frame record until
the transition's aggregate result frame is durably acknowledged.

The loop durably acknowledges =dispatch-started= before invocation.  On
recovery, an admitted call with no =dispatch-started= record may dispatch.  A
=dispatch-started= call with neither a durable normalized result nor
=execution-settled= first appends and acknowledges =outcome-unknown=.  It neither
redispatches nor permits provider follow-up until it is explicitly resolved.
Feature 88 never automatically redispatches an execution after
=dispatch-started=.

A live =finished= or =failed= outcome uses one ordered per-execution transaction:
first persist the normalized provider-linked tool result, then append one
=execution-settled= commit marker that names the outcome kind and references the
result identity.  The loop must durably acknowledge that complete prefix before
clearing the active execution or starting the next tool.  Per-execution
settlement does not open an observation frame.  Failed or withheld
acknowledgement starts nothing.

Replay derives terminality only from =execution-settled=.  If a durable result
exists but its marker is missing, recreate the marker with the same identity and
acknowledge the completed prefix idempotently; a known durable result never
degrades to ambiguity.  Only =dispatch-started= without a durable normalized
result becomes =outcome-unknown=.  A retry after failed acknowledgement
resubmits the same record identities.

After every admitted execution has an acknowledged =execution-settled= marker,
append exactly one deterministic aggregate =frame-opened= record for the
transition.  It references every normalized result identity once in
admitted-call order.  Acknowledge that frame before provider follow-up.  Replay
opens the same frame exactly once when all executions are settled, or resubmits
the same record identity when persistence succeeded but acknowledgement was
lost.  It opens no result frame while any execution remains nonterminal.

Add the consumer-shaped core operation =e-harness-resolve-tool-execution=.  It
accepts a session id, execution id, and one bounded resolution: a normalized
finished result or normalized failed result.  It uses the same per-execution
result and =execution-settled= transaction as live completion.  If this settles
the last outstanding execution, the recovery service creates and acknowledges
the one aggregate frame before releasing follow-up.  Repeating the same
resolution is a no-op; a conflicting resolution is an explicit error.
Presentation may expose this operation but does not own its policy.

*** Pending-transition recovery service

=e-session= derives and checkpoints a provider-neutral pending-transition
descriptor containing the transition and turn identities, consuming response,
ordered execution ids and settled result ids, deterministic aggregate frame
identity, provider replay linkage, and next durable action.  It contains no
process-local callbacks, promises, or tool objects.

=e-harness-resume-pending-transition= is the sole application service that
turns this durable descriptor back into live work.  Session resume calls it
after replay and before accepting a new prompt.  It claims the descriptor in the
active-turn registry, is idempotent on repeated calls, dispatches only calls
proven not to have reached =dispatch-started=, exposes =outcome-unknown= as a
blocked state, and reconstructs exactly one provider follow-up after every
ordered execution-settlement prefix and the aggregate result frame are
acknowledged.  A reconstruction mismatch fails visibly and leaves the
descriptor recoverable.

=e-harness-resolve-tool-execution= persists the bounded resolution, then
delegates release to that service.  Feature 88 adds no generic idempotency-key
hook and no automatic retry after =dispatch-started=.  A later feature may add a
versioned resume contract for a concrete tool adapter that actually transmits a
stable key to a deduplicating external operation.

* Generational compaction

Eventually the durable tail contains superseded or retracted facts:

#+begin_example
C0 + D0
   |
   | deliberate compact boundary
   v
C1

C1 + D1 + D2 + ...
#+end_example

The existing readable compaction summary becomes the portable checkpoint for
the next generation.  Compaction input contains the old checkpoint and durable
tail, not consumed ephemeral frames.  Promoted facts are included because they
are durable.

The compaction record should identify:

- prior and new generation ids;
- the covered durable boundary;
- the readable portable checkpoint;
- the first retained durable entry;
- source and resulting token estimates;
- provider projections associated with the same boundary;
- fingerprints needed to reject stale provider state.

The original journal remains append-only audit history.  A generation switch
changes the model projection and resume checkpoint; it does not rewrite or
delete the journal.

* Provider capability contract

Core policy must reason in semantic terms and ask the adapter to render a
logical transition.  It must not branch directly on
=previous_response_id=, OpenAI item types, Anthropic cache controls, or another
provider's field names.

The core backend contract exposes a pure query:

#+begin_src elisp
(e-backend-context-capabilities backend options)
;; =>
(:continuation branchable
 :observation-delivery request-local-replaceable
 :prefix-cache explicit
 :provider-compaction opaque
 :reasoning-state replayable)
#+end_src

The selected adapter resolves this contract from its profile, transport, model,
and effective options when the backend is created or queried.  Core recognizes
only these semantic values:

| Capability | Values | Core consequence |
|------------+--------+------------------|
| =continuation= | =none=, =linear=, =branchable= | whether only the latest anchor or an older clean anchor can be reused |
| =observation-delivery= | =inherited=, =request-local-replaceable= | whether an advancing response inherits the observation |
| =prefix-cache= | =none=, =implicit=, =explicit= | acceleration only; never lifetime semantics |
| =provider-compaction= | =none=, =opaque= | optional provider checkpoint projection |
| =reasoning-state= | =none=, =replayable=, =provider-managed= | required durable replay treatment |

Missing capabilities select stateless reconstruction.  Unknown values are
configuration errors, not silent downgrade.  OpenAI alone maps
=request-local-replaceable= to top-level =instructions=; no core module branches
on that field name.  Avoid a shared interface whose implementations throw
“unsupported operation.”

* Ownership and dependency direction

** =e-context= / new context-lifetime policy module

- Own the logical =CHECKPOINT + DURABLE + EPHEMERAL= projection.
- Open, consume, close, and project frames with pure helpers where possible.
- Exclude consumed observations without deleting audit records.
- Produce provider-neutral fingerprints and generation identity.

If the lifecycle is large enough to deserve a module, use a core name such as
=e-context-lifetime.el=.  Do not put provider request fields in it.

** =e-session=

- Persist generation, frame lifecycle, promotion, and provider-anchor records.
- Keep the journal authoritative and append-only.
- Restore the active generation and any recoverable open frame through the
  Feature 78 resume-checkpoint manifest.
- Derive and checkpoint the provider-neutral pending-transition descriptor used
  to resume tool work without retaining process-local callbacks.
- Treat pre-feature session messages conservatively as durable unless an
  explicit migrated lifetime record proves otherwise.

** =e-harness= / =e-loop=

- Orchestrate one transactional observation transition.
- Commit consumer output and promotions before closing its frame.
- Ask the adapter for a rendering strategy from semantic context plus declared
  capabilities.
- Advance, retain, or discard provider anchors according to the returned anchor
  safety decision.
- Own =e-harness-resume-pending-transition= as the single idempotent bridge from
  a durable pending-transition descriptor to claimed live work.
- Emit bounded lifecycle and cache diagnostics without observation bodies.

** Tool and resource boundaries

- Tool execution produces an ephemeral observation record by default.
- External resources return stable handles when full content need not enter the
  next invocation.
- Tools with a real durable-result contract may opt in explicitly; “all tool
  results are durable” is not a compatibility fallback.

** Backend adapters

- Map semantic segments and frames to provider wire shapes.
- Advertise only capabilities proven for that profile and transport.
- Own provider ids, opaque items, cache controls, retries, and rejection
  fallback.
- Return normalized diagnostics and anchor candidates; do not decide which
  facts become durable.

** Presentation

Presentation may show generation/frame status and manual compaction progress.
It does not own frame lifetime, promotion policy, or provider fallback.

* OpenAI projection

For eligible Responses profiles:

- Keep stable instructions/policy in stable developer input before the cache
  breakpoint.
- Render current-state canvas and similar replaceable observations into
  top-level request-local =instructions= and resend the complete current value
  on every request.
- Continue durable history with =previous_response_id= only when the selected
  anchor is clean and all stable/generation fingerprints match.
- Preserve stateless encrypted reasoning replay for =store=false= and fallback
  paths.
- Keep =prompt_cache_key= and explicit breakpoint behavior independent of
  logical lifetime.

The adapter must not assume every OpenAI-shaped endpoint behaves like the
public API.  ChatGPT subscription profiles, gateways, HTTP, and WebSocket
transports advertise and prove their own capabilities.

OpenAI =POST /responses/compact= is an optional accelerator at a generation
boundary, not the canonical compaction implementation.  From the same durable
boundary, produce two projections:

#+begin_example
portable:  S1 = readable e checkpoint
provider:  K1 = opaque OpenAI compaction output
#+end_example

=S1= is stored in the normal compaction/generation record and is sufficient for
every backend.  =K1= is stored as disposable provider state keyed by provider,
model, boundary, prompt-layout revision, and fingerprints.  The adapter passes
it back unchanged, never parses it, and discards it on rejection or mismatch.

Consumed canvas snapshots, tool output, and diagnostics must not enter the
input used to create =K1=.  Otherwise provider compaction would preserve exactly
the obsolete material this feature is intended to forget.

Use the endpoint only when the selected profile explicitly advertises support.
If a ChatGPT subscription endpoint or gateway has not been proven to implement
it, keep using =S1= and do not probe speculatively during an ordinary turn.

Implementation should recheck these official API contracts rather than treating
this plan as a frozen provider specification:

- [[https://developers.openai.com/api/reference/resources/responses/methods/create][Create a model response]] for =instructions= and
  =previous_response_id= semantics;
- [[https://developers.openai.com/api/reference/resources/responses/methods/compact][Compact a response]] for the opaque provider projection;
- [[https://developers.openai.com/api/docs/guides/context-management][Context management]] for the supported stateless continuation shape.

* Observability

Add bounded events/diagnostics sufficient to explain context behavior:

- generation id and checkpoint boundary;
- frame opened, consumed, promoted, closed, failed, or recovered;
- tool execution admitted, dispatch-started, execution-settled,
  settlement-prefix-acknowledged, outcome-unknown, recovery-claimed, or
  explicitly resolved, keyed by bounded execution id;
- aggregate result frame opened or acknowledged, keyed by bounded transition and
  frame ids plus result count, never result bodies;
- observation and promoted token/character estimates, never full content;
- provider anchor held, advanced, rebuilt, or discarded, with reason;
- rendering strategy: stateless, clean-anchor branch, or replaceable channel;
- portable and provider compaction success/fallback;
- cached, uncached, and cache-write token counters when a provider reports them.

Diagnostics must make the central safety property auditable: for every request,
one can tell whether an observation was placed in inherited or replaceable
provider state and why the chosen anchor is safe.

* Implementation slices

1. *Lifetime model and shadow projection.* Add the semantic backend capability
   query, generation/frame/promotion record shapes, pure projector tests,
   resume-checkpoint retention, asynchronous settlement acknowledgement, and
   diagnostics.  Keep request behavior unchanged behind an opt-in so recorded
   comparisons can prove what would be retained or forgotten.
2. *Replaceable current-state delivery.* Move canvas/current-state rendering to
   the semantic observation frontier.  Implement the OpenAI =instructions=
   projection for profiles that prove it, and the clean-anchor/stateless path
   for profiles that do not.  Replace the existing E2E assertion that appends
   changed dynamic developer input to a chain containing the old snapshot.
3. *Ephemeral tool frames, promotion, and tool recovery.* Make new raw tool
   results ephemeral by default, add the reserved core promotion effect,
   transactional ordered frame settlement, durable tool execution states and
   recovery, and deterministic multi-tool tests.  Preserve old sessions
   conservatively.
4. *Generational portable compaction.* Extend existing compaction records and
   context reconstruction with generation identity; summarize only checkpoint
   plus durable tail; update auto-compaction to cross one explicit generation
   boundary without changing its threshold policy.
5. *Optional provider compaction.* Add a provider-neutral opaque-checkpoint
   slot and implement capability-gated OpenAI =/responses/compact=.  Rejection,
   expiry, profile change, or model change falls back to the portable checkpoint.
6. *Presentation and operator controls.* Show bounded generation/frame state in
   existing context diagnostics and make manual compaction report portable and
   provider projection outcomes without exposing opaque contents.
7. *E2E, performance evidence, cleanup, and review.* Run the mandatory tests
   below, compare cached/uncached frontier size, remove the superseded dynamic
   continuation path, and complete the architecture review.

Each slice is a semantic commit with focused tests and ledger updates.  Core
record-shape, harness, loop, session, and adapter changes require a full Emacs
restart; do not add live-reload compatibility shims for them.

* Acceptance criteria

** Core behavior

- Session-history reconstruction is exactly
  =checkpoint + durable tail + open frame=.  A complete request prepends the
  active request-time =static-prefix= and =stable-context= segments without
  copying them into the generation.
- A unique sentinel present only in a consumed observation is absent from the
  next model request; a promoted fact derived from it is present.
- The audit journal still contains the observation, its source/frame identity,
  and the promotion link.
- Cancellation and restart cannot silently close an unconsumed frame or include
  a consumed frame forever.
- A retry of request-time current state either reproduces the admitted rendered
  fingerprint or explicitly aborts that frame before capturing replacement
  state.
- An invalid one-over promotion emitted beside an ordinary tool call dispatches
  zero tools and leaves the frame retryable.  Withheld or failed settlement
  acknowledgement also dispatches zero tools; successful acknowledgement
  dispatches each admitted tool once per live execution attempt and opens one
  next frame containing its results.
- After restart, a durably admitted but provably undispatched call may resume.
  A =dispatch-started= call without a durable normalized result becomes
  blocked =outcome-unknown= and remains checkpoint-retained.  It is not
  automatically redispatched.  A durable result with a partial settlement
  prefix is completed idempotently with the same identities.  No provider
  follow-up occurs until every admitted call has an acknowledged
  =execution-settled= marker and their one aggregate result frame is
  acknowledged.
- =e-harness-resolve-tool-execution= appends and acknowledges exactly one linked
  result/settlement transaction.  If it settles the last outstanding execution,
  the recovery service opens and acknowledges the same one aggregate frame
  before releasing follow-up.  Repeating an identical resolution is a no-op and
  a conflicting resolution fails explicitly.
- =e-harness-resume-pending-transition= is invoked through the real
  session-resume path before a new prompt is accepted, claims recovered work at
  most once, blocks on ambiguity, and reconstructs exactly one follow-up from
  durable records after all execution-settlement prefixes and the aggregate
  result frame are acknowledged.
- A changed canvas replaces the prior snapshot.  It does not become another
  durable transcript item and does not force stable-prefix invalidation.
- A provider anchor never advances across inherited ephemeral input.  It may
  advance across a proven replaceable channel.
- Providers with no lifetime capabilities produce the same semantic context by
  stateless replay.
- Compaction starts a new generation from durable state only.  Portable
  checkpoint reconstruction works without any provider artifact.
- OpenAI opaque compaction, when enabled, is disposable and produces identical
  local semantics when removed before the next turn.

* Performance contract

- Ordinary turns append only small durable deltas and reuse the generation's
  stable prefix.
- Consumed observation bytes are not retransmitted on later requests.
- Updating a canvas changes only the request-local/ephemeral frontier, not the
  stable prefix fingerprint.
- The harness does not run a summary model call for every observation.
- Cold prefill is expected at a deliberate generation boundary and on safe
  fallback after provider state loss.
- Context projection must not add an unbounded full-journal scan to each turn;
  resume checkpoints retain the active generation and bounded open-frame state.

Review evidence must report exact first-turn, warm-turn, observation-turn, and
post-compaction input/cached token counts for at least one capable profile.  A
cache regression needs a first-principles justification; existing code layout
is not sufficient justification.

For an observation-bearing and a multi-tool transition, evidence also reports
frame-settlement and tool-terminal-prefix record count and bytes, their separate
acknowledgement waits, and end-to-end time from provider completion to first tool
dispatch and from each tool completion to the next tool dispatch.  Report the
aggregate result-frame record count/bytes, acknowledgement wait, and
last-tool-to-provider-follow-up time separately.  The acknowledgement paths
perform work proportional to their prefixes, never scan the full journal, and
perform no synchronous filesystem I/O on the Emacs main thread.  Any material
latency regression requires first-principles justification.  A controlled-writer
acknowledgement gate is contract evidence; queue/outbox microtests are mechanism
evidence.

* Compatibility and migration

- Existing journals load without rewriting.  Messages lacking lifetime
  metadata remain durable, preserving pre-feature behavior.
- Legacy tool calls without execution records keep the existing replay behavior;
  they are not retroactively classified as safely undispatched or retried.
- New lifetime behavior starts at a recorded generation boundary or explicit
  session migration point; do not reinterpret old tool results silently.
- Existing provider anchors without the new layout/generation revision are
  incompatible and fall back to full replay once.
- Backends that ignore new capabilities remain correct through flat stateless
  messages.
- Prompt-cache placement, provider continuation, and logical lifetime remain
  independently configurable.
- Branches inherit the selected generation checkpoint and durable path, not
  consumed frames from another branch.
- Export and audit views continue to show full historical tool evidence even
  though model context does not.

* Non-goals

- Do not delete or rewrite the append-only audit journal.
- Do not make OpenAI =previous_response_id=, =instructions=, or opaque compaction
  items part of the core state model.
- Do not parse or display the contents of provider opaque compaction items.
- Do not claim that a provider forgot data merely because e omitted it from a
  later request; the claim requires a documented replaceable channel or a
  stateless/clean-anchor path.
- Do not automatically promote every observation or summarize every tool result.
- Do not make the canvas itself durable conversation history.
- Do not require every backend to implement branching, replacement, cache
  controls, or provider compaction.
- Do not use compaction as a substitute for bounded tool/resource output.
- Do not add a second external-resource registry or persist external payloads in
  generation/frame state.  This feature only classifies the bounded observation
  produced when an existing handle is resolved.
- Do not promise exactly-once external side effects for arbitrary tools or add a
  speculative generic idempotency interface.  Feature 88 never automatically
  retries after =dispatch-started= without a terminal result.

* Risks and explicit mitigations

- *The model fails to promote a needed fact.* Make the lifetime contract visible
  in instructions, expose an explicit promotion operation, keep audit evidence
  retrievable, and test multi-tool transitions.  Do not silently retain all
  observations as insurance.
- *A provider claims replacement but retains prior values.* Gate the capability
  per profile/transport, require conformance and live E2E evidence, and fall back
  to clean-anchor/stateless reconstruction.
- *Reasoning state is lost when an observation branch is abandoned.* Normalize
  replayable reasoning items and include them in the durable delta when the
  provider contract requires it; otherwise retain the last clean anchor.
- *Dual compactions drift.* The portable checkpoint is canonical.  Provider
  opaque state is accepted only at the same boundary/fingerprint and can always
  be discarded.
- *Crash recovery duplicates or forgets a frame.* Journal frame open, consume,
  promotion, and close transitions idempotently; resume from the last committed
  state.
- *Crash recovery duplicates an external tool side effect.* Persist execution
  admission and dispatch-started separately; commit terminality only with a last
  =execution-settled= marker; idempotently finish known partial results; never
  automatically rerun an ambiguous tool; and require an explicit durable
  resolution before resuming the transition.
- *Cache optimization leaks into semantic policy.* Keep provider capabilities
  and rendering in adapters, and prove core projection with a backend-free test.
- *Journal size still grows.* This feature bounds model context, not audit
  storage.  Retention/export policy is separate work.

* Architecture self-check

1. *If work stopped here, is the project better off?* Yes.  The first behavioral
   slice fixes stale canvas inheritance with a safe stateless fallback; later
   slices independently remove raw tool observations and add generational
   compaction.
2. *Final direction?* A harness-owned logical state machine whose provider
   adapters accelerate, but do not define, context semantics.
3. *Stable and uncertain decisions?* The three model-visible lifetimes, the
   existing external-handle delivery mode, the clean-anchor invariant, and the
   portable checkpoint are stable.  Provider wire capabilities and the exact
   promotion UI are likely to change and remain local to adapters or one narrow
   core operation.
4. *Owner?* Core context policy owns lifetime; session owns durable audit;
   harness/loop own transactions; adapters own wire realization; presentation
   only renders status.
5. *Coupling?* Reduced: core no longer relies on OpenAI continuation semantics,
   and adapters consume a narrow semantic projection rather than session internals.
6. *Dependency direction?* Unstable provider code depends on the stable logical
   context contract.  Core never imports an OpenAI request shape.
7. *Side effects outward?* Provider calls, journal writes, and external resource
   retrieval stay at adapter/session/tool boundaries; projection is pure where
   practical.
8. *State lifetime?* Generations and promotions are durable; open frames are the
   smallest restart-safe state; provider anchors and opaque checkpoints are
   disposable; presentation/cache state remains runtime-local.
9. *Performance?* The design removes repeated observation bytes and preserves
   monotonic prefixes, with an explicit cold cost only at compaction or fallback.
10. *Real abstractions?* Every capability corresponds to a distinct request
    strategy.  Missing capabilities select a valid fallback instead of weakened
    behavior or unsupported-operation errors.
11. *Compatibility?* Old records remain durable, old anchors invalidate once,
    and no legacy rewrite path is added.
12. *Legacy removable now?* Remove the path that treats refreshed dynamic
    developer input as sufficient replacement while continuing through an
    anchor that contains the prior snapshot.
13. *Errors?* Expected anchor rejection and opaque-state expiry fall back through
    the adapter.  Journal corruption, invalid frame transitions, and mismatched
    boundaries surface as explicit errors.
14. *Independent tests?* Pure projector/state-machine tests prove lifetime;
    adapter tests prove wire mapping; the mandatory E2E proves their integration
    through the real harness/session/tool path.
