* Purpose

Feature 88 now separates durable context from consumer-bound ephemeral frames.
Addendum 3 uses canonical later-request reconstruction and immediate causal
tool continuation; Addendum 4 adds provider-neutral source presentation,
model-directed =context-curate=, and version-3 durable curation records while
retaining read-only version-2 records.  The historical live experiments below
remain useful background, but their old optimization mechanisms are not current
acceptance requirements.  The remaining external limitation is the
profile-specific built-in ChatGPT Codex WebSocket behavior:

1. retained/replaced-socket cache behavior and response availability have not
   been exercised at the current evidence revision; and
2. a =store=false= response lineage remains connection-local, so canonical
   replay is the correctness fallback after a socket or response loss.

The experiments further distinguish provider continuation from provider
prompt-cache accounting.  An incremental request can send only one new input
message while the provider still reports and bills the preceding chain as
input tokens.  A successful =previous_response_id= continuation therefore
does not imply a large =cached_input_tokens= value.

This distinction matters for remediation.  The following are separate
properties:

#+begin_example
semantic visibility
  what current state and tool observations the model can see

anchor eligibility
  whether a response is safe to retain as a future continuation point

transport continuation
  whether the next request can send only its delta with previous_response_id

prompt-cache accounting
  how many input tokens the provider reports as cached

response retention
  whether a response ID remains resolvable after connection loss
#+end_example

* Confirmed behavior to preserve

Later remediation must preserve these working properties:

1. Current-state and dynamic-context are resolved through the static,
   kind-scoped adapter capability rather than runtime discovery.
2. Attached canvas contents are visible as a complete request-local
   observation and can change between continued requests.
3. Tool call, replay, and result bundles are visible to their matching
   follow-up and absent from the following ordinary turn.
4. A tool-producing response ID is used only for its immediate matching
   follow-up.
5. Neither that response ID nor its contaminated descendant becomes a durable
   anchor.
6. A clean tool-free response can advance and persist an anchor despite a
   changing canvas.
7. A retained ChatGPT Codex WebSocket can use that anchor incrementally with
   changed top-level instructions.
8. Stateless/full reconstruction remains available when no usable anchor
   exists.
9. The canvas avoids the large read/discovery tool loop observed without an
   attached document.

* Current tool-continuation boundary

Tool-producing responses are used only for the matching function-call-output
follow-up.  The inherited =tool-result= frame keeps the call, replay, and
result bundle available for that causal request; the response ID and its
descendant are not durable semantic anchors for the following ordinary turn.

The accepted sequence is:

#+begin_example
ordinary request
  → tool call and matching result
  → immediate causal continuation
  → curation, if requested, commits while the frame is live
  → next ordinary request is canonical durable state plus new frontier
#+end_example

That ordinary request excludes the raw tool bundle, response lineage, replay
metadata, and consumed source values.  Generic provider-neutral anchor
infrastructure remains available to unaffected profiles, but this package no
longer retains a historical ChatGPT response graph or older-anchor ledger.
When no compatible remote response exists, one bounded canonical full replay is
the correctness fallback.  Deterministic coverage is provided by
=e-provider-continuation-integration-test-canonical-observe-curate-forget=
and =e-context-lifetime-e2e-test-tool-observe-curate-forget=.  The named live
tool-heavy selector remains unavailable locally because credentials are
missing; that is an external-evidence limitation.

* Historical experiment: tool descendants cannot advance the cross-turn anchor

The dominant limitation is not an exceptional lifecycle.  Useful agent turns
normally call tools.

Feature 88 deliberately treats =tool-result= as inherited.  A provider
response that emits a tool call may be used for the immediate matching
follow-up.  The tool result then exists in the provider response chain.  The
final assistant response descending from that result remains contaminated even
after the raw bundle disappears from the next local semantic projection.
Neither response can safely become a durable anchor because ordinary causal
transformer state cannot remove the inherited observation.

The resulting bootstrap path, when no earlier compatible clean anchor exists, is:

#+begin_example
full request R
  → model emits a tool call in response A
  → immediate follow-up uses A
  → tool result enters the A → B provider chain
  → final assistant response B descends from the tool result
  → neither A nor B becomes a durable anchor
  → next user turn performs full reconstruction
#+end_example

The first adjusted turn demonstrates that even a routine =process_marker=
call is sufficient.  Its result was only =ok=, but its presence made the final
descendant ineligible.  The edit turn demonstrates the same behavior for
substantive tools.

Thus the local ephemeral projection works while the tool-descended provider responses remain ineligible as new anchors.
Calling this merely a cache miss understates the mechanism because the harness cannot advance through the tool chain.
The experiment does not prove that every tool-bearing turn forces full reconstruction.

The harness already retains an older compatible clean anchor and can send the durable transcript delta from that anchor after the tool frame is consumed.
The provider-neutral integration test =e-provider-continuation-integration-test-ephemeral-bundle-does-not-contaminate-anchor= covers this path for =linear= plus =request-local-replaceable= delivery: the later request selects =resp-clean= and rejects the tool-producing =resp-A= and its descendant =resp-B=.
The six-turn live experiment did not exercise that path because its tool-bearing turns occurred before the first clean anchor was created.

For a tool-heavy harness, reaching the first clean anchor can still be uncommon.
The live sixth-turn success required deliberately constructed tool-free turns three, four, and five before the incremental turn.

** Historical remediation direction

Keep =tool-result= ephemeral and =inherited=.
A function-call output is causal provider state required by its matching follow-up, and the Responses continuation interface does not provide a request-local replacement channel for that bundle.
Classifying the bundle as replaceable would permit an anchor whose effective provider context still contains a tool observation that the local semantic projection has removed.

Use the last compatible clean anchor as the recovery point after a tool-bearing turn.
The next request should reference that clean response ID and send only the durable messages, promotions, and current request-local observations added since its covered session entry.
The contaminated tool-producing response and its final descendant must remain immediate-follow-up artifacts and must not be persisted as anchors.

Do not special-case =process_marker= merely because its result is =ok=.
Its function-call arguments and replay item still belong to the provider tool bundle, so retaining its descendant would make provider context differ from the local semantic projection.
A later tool-level =retention-safe= distinction may be useful for effects proven to add no future semantic state, but it should remain separate from the observation's ephemeral lifetime and should not be introduced without endpoint evidence and measured need.

Before changing policy, prove this path against the real ChatGPT Codex WebSocket:

1. Create a clean =resp-clean= anchor.
2. Run a substantive tool turn through =resp-A → tool result → resp-B=.
3. Confirm that neither =resp-A= nor =resp-B= is persisted.
4. On the next turn over the same socket, require =previous_response_id= to equal =resp-clean=.
5. Require incremental request mode, the changed canvas in current =instructions=, and only the durable or promoted delta in =input=.
6. Require the raw function call, replay item, and result to be absent from the literal request.
7. Force socket loss and require safe full reconstruction instead of reuse of an unavailable clean response ID.

This acceptance test separates two cases that the current document combines.
An existing clean anchor can bypass the contaminated descendant if the real endpoint accepts that branch on the retained socket.
A session whose first useful turn calls a tool still has no clean response to branch from and needs full reconstruction until a clean anchor is created.
Do not add a hidden model call merely to seed or rebase an anchor unless measurements show that this bootstrap case justifies the extra latency, token cost, and semantic risk.

** Historical priority assessment

High-priority acceptance gap, but not release-blocking.
The provider-neutral recovery path already exists, so do not begin by changing the lifetime classification.
First prove or disprove older-clean-anchor reuse on the real retained ChatGPT Codex socket after a complete tool chain.
If it succeeds, the remaining ordinary costs are the no-clean-anchor bootstrap case and connection loss.
If it fails, retain correct full reconstruction while evaluating an explicit rebase mechanism.
Escalate rebase work only if measured replay latency, cost, or context pressure justifies its extra provider request and semantic risk.

* Current ChatGPT continuation limitation

The built-in ChatGPT Codex profile uses Responses WebSocket mode with
=store=false=. Its latest response ID is retained only for the matching
immediate continuation on that connection.  Connection close, transport
failure, cancellation, or an unavailable response clears the usable lineage;
the adapter then performs at most one canonical full retry.  General
configurable socket idle policy remains, but the built-in profile has no
private 600-second override and no response-ID ledger.

The durable local session record does not make this provider lineage durable.
The current configured Responses HTTP run proves warm cache accounting for
=eng-ai-gateway-gpt=, but does not prove this built-in ChatGPT Codex
WebSocket's retained/replaced-socket behavior or response availability.  The
deterministic tests prove the fallback and ownership state machine; the
ChatGPT/WebSocket retention claim remains unconfirmed.

* Historical experiment: the ChatGPT continuation is connection-local

The ChatGPT Codex profile uses Responses WebSocket mode with =store=false=.
Its useful response lineage is held in the connection-local provider cache.
The historical six-turn experiment below ran with the then-current global
adapter policy:

#+begin_example
e-openai-websocket-connection-idle-seconds = 300
#+end_example

The implementation measured by this historical experiment kept that global
value as the fallback and gave the exact built-in ChatGPT Codex profile an
adapter-private 600-second value.  It also owned bounded completed-response and
eviction ledgers.  Addendum 3 subsequently removed that profile override and
both ledgers; the current implementation uses the general socket policy and
retains only the latest response needed for an immediate causal follow-up.

After five idle minutes, the adapter closes the socket.  Turns four and five
show that a locally persisted anchor can still be selected after that close,
but the selected response ID cannot be used by the new socket.  The adapter
records =provider-anchor-present: true= and then falls back to a full request
with =new-connection=.

The five-minute close is local adapter policy.  The provider's documented
WebSocket lifetime can be longer, but any connection loss still clears the
connection-local cache.  The first-party
[[https://developers.openai.com/api/docs/guides/websocket-mode][Responses WebSocket mode guide]]
states that a new connection can recover a stored response by ID; when the
prior response is unavailable, the caller must provide full input context.
The ChatGPT Codex profile's =store=false= behavior therefore cannot rely on
stored-response recovery after the connection-local cache disappears.

The historical effective capability window was:

#+begin_example
clean tool-free anchor
  + next turn before the five-minute idle close
  + same healthy WebSocket
  = request-local incremental continuation
#+end_example

Network failure, backend replacement, Emacs restart, or the provider's own connection limit can end that window earlier or later than the local idle timer.
A durable local anchor record does not make the remote response state durable.

** Historical remediation direction

This direction was superseded by Addendum 3's canonical reconstruction and
general socket policy.  It is retained only to explain the experiment that led
to that correction.

Retain the exact built-in ChatGPT Codex WebSocket beyond the historical
five-minute idle window using its implemented 600-second profile policy.
Prefer keeping it until provider close, transport failure, backend replacement, explicit session teardown, or another bounded resource policy requires eviction.
This improves the common pause-prone workflow without treating connection-local response state as durable.

Keep full reconstruction as the required fallback after any connection loss or rejected =previous_response_id=.
A locally persisted clean anchor may guide selection while its socket remains alive, but it must not authorize reuse on a different ChatGPT Codex connection.
The adapter should record why continuation was unavailable and discard or bypass the unusable remote anchor without changing the session's durable semantic state.

Do not make =store=true= the primary remediation for the ChatGPT Codex profile.
Its current =store=false= contract makes continuation connection-local, so the adapter must remain correct without cross-connection response recovery.
Evaluate stored responses separately for canonical OpenAI profiles that support them, with explicit review of retention policy, privacy, cost, and response-deletion requirements.
That profile-specific option must not weaken the full-reconstruction fallback or be represented as a shared semantic capability.

Validate the longer retention policy deterministically before adding a rebase
call or stored-response dependency.  Track socket lifetime, continuation
success, full-fallback frequency, request latency, and transport failures when
the fast credentialed semantic test is available; do not introduce a wall-clock
idle-duration test.
Deterministic coverage now covers the 600-second timer boundary, provider-forced
socket loss, explicit teardown, and unavailable response IDs.  Credentialed
same-socket older-anchor reuse remains a fast explicit acceptance gate, not a
completed measurement.  The package does not require a wall-clock pause test.

* Limitation: continuation and prompt-cache savings are different

The sixth request proves transport continuation: its body contained one new
input message and =previous_response_id=.  Its provider usage still reported
15,660 input tokens, of which only 2,560 were cached.

The first-party
[[https://developers.openai.com/api/docs/guides/conversation-state][conversation-state guide]]
states that previous input tokens in a =previous_response_id= chain continue
to be billed as input tokens.  The connection-local response cache supports
stateful, low-payload continuation; =cached_input_tokens= separately reports
ordinary prompt-cache accounting.

Consequently Feature 88 currently proves:

- smaller incremental request bodies;
- provider lineage reuse while the socket is alive; and
- replacement of request-local instructions without inherited stale canvas
  content.

It does not currently prove:

- that previous-chain tokens receive cached-input pricing;
- a particular provider KV-cache implementation;
- lower billed input tokens for a continued chain; or
- a latency improvement independent of output and provider variance.

The fifth and sixth exact-response requests both completed in approximately
three seconds.  That workload is too small to demonstrate a latency difference.

* Limitation: full fallback showed weaker prefix-cache hits

The adjusted and earlier canvas sessions used the same number of requests and
tool calls and processed nearly identical total input tokens.  Their observed
prompt-cache reuse differed:

| Cache source | Adjusted canvas | Earlier canvas |
|--------------+-----------------+----------------|
| Tool-follow-up cached input | 64,512 | 64,512 |
| Top-level cached input | 2,560 | 22,528 |
| Total cached input | 67,072 | 87,040 |

The within-turn tool-follow-up cache total was exactly unchanged.  The entire
observed reduction came from top-level full requests.

The provider cache is opaque and the delays differed, so this experiment does
not establish a single cause.  The result is consistent with a changed
request-local =instructions= value breaking the reusable prefix earlier when
full reconstruction is required.  Provider cache expiry and load may also
contribute.  The third adjusted turn received zero cached input after an
8-minute-52-second pause, while the earlier canvas run received 8,704 cached
tokens after an 11-minute-20-second pause, demonstrating that elapsed time
alone does not explain the variance.

The practical issue is still observable: when a tool-bearing turn removes the
anchor and the next turn falls back to a full request, the request-local layout
did not preserve the strong top-level prompt-cache hits seen in the earlier
canvas run.

* Limitation: one semantic capability covers different retention behavior

Both canonical OpenAI and ChatGPT Codex can accept changed request-local
=instructions= with =previous_response_id=.  They do not necessarily have the
same response-retention lifetime.

The public =request-local-replaceable= capability accurately describes
observation semantics.  It does not describe whether a response ID is:

- connection-local;
- stored and recoverable on a new connection;
- unavailable after =store=false= connection loss; or
- subject to a short adapter-owned idle close.

The live experiments therefore establish request-local semantic conformance
for ChatGPT Codex only while its connection-local response exists.  They do not
establish substitutable continuation durability across the ChatGPT Codex and
canonical OpenAI profiles.

* Historical acceptance gap: the warm path only

The credentialed addendum acceptance test proved changed instructions and
=previous_response_id= on one retained native WebSocket.  That test was valid
for the claimed warm-socket behavior, but it did not cover the conditions that
dominate the later live experiment:

- a normal turn that uses at least one tool and then starts another user turn;
- a routine =process_marker=-only tool turn;
- a forced idle close before the next clean turn;
- a new WebSocket with a locally selected but remotely unavailable anchor;
- the distinction between one-message transport input and billed input-token
  accounting; or
- the prompt-cache behavior of full reconstruction with changed request-local
  instructions.

The original three-turn live acceptance also stopped immediately after
creating its first clean durable anchor.  It did not send the following turn
that would consume that anchor.  Turns four through six supplied that missing
evidence and exposed the connection-lifetime boundary.

* Historical remediation handoff requirements

Remediation work should begin from the observed state above.  It must account
for all of these ordinary paths rather than treating tool use as an edge case.
Retention pauses are represented by deterministic scheduler advancement; no
acceptance test waits in wall-clock time.

At minimum, later acceptance evidence needs to distinguish and exercise:

1. a clean turn followed immediately by a changed-canvas turn on the same
   socket;
2. deterministic fake time at 301 seconds without close, followed by the
   600-second boundary that closes the socket and clears its ledger;
3. a substantive tool-bearing turn followed by another user turn;
4. a =process_marker=-only turn followed by another user turn;
5. a forced socket loss independent of the idle timer;
6. a stored canonical OpenAI response on a new connection, when credentials
   are available;
7. a ChatGPT Codex =store=false= response on a new connection;
8. literal request shape, provider continuation diagnostics, and persisted
   anchor state for each path; and
9. transport input size, total input tokens, cached input tokens, request
   latency, and full-fallback frequency as separate measurements.

The handoff must preserve the boundary already established for Feature 88:

- session remains the sole durable semantic body source;
- runtime observation frames remain consumer-bound;
- provider wire behavior remains in the adapter;
- no crash-recovery transaction system, journaling protocol, exactly-once
  machinery, or interim ACID abstraction is added ahead of the planned SQLite
  persistence work; and
- an optimization failure continues to fall back to correct full
  reconstruction rather than stale or incomplete context.

This document does not select the remediation mechanism.  It records the
behavior that mechanism must change and the evidence required to show that the
normal tool-heavy, pause-prone workflow improved.
