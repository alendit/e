Findings:

- P0: none.

The central direction is sound.  Responses requests should explicitly opt in
to =reasoning.summary: "auto"=, with =detailed= reserved for diagnosis; returned
summaries are not raw reasoning and have no semantic decision power.  A strict,
structured =drop= disposition is also the necessary distinction between a
source the model considered and rejected and a source it never noticed.  More
generic narration is neither required nor permitted.

Implementation is blocked by an escape hatch that can omit the required
summary request, an incomplete option/compatibility contract, an exhaustive
partition that current frames with more than 16 sources cannot express, and a
drop-only durability promise that contradicts the existing checkpoint owner.
The negative scenario also fails to prove current-turn use, and the proposed
slice order advertises =drop= before core can accept it.

No Addendum 6 external success is claimed.  Both configured Responses HTTP and
exact built-in ChatGPT/WebSocket evidence for the new material identity remain
=capability-unconfirmed=.  This is required future evidence, not a repository
finding.

* Findings

** TODO P1-01: =F88A6-R1= permits omitting =auto= and does not define its existing option join

*** Contract cell

=F88A6-REASONING-SUMMARY= request option, compatibility, identity, and external
failure classification.

*** Observed source fact

The matrix requires OpenAI Responses requests to explicitly send
=reasoning.summary: "auto"= (=addendum6.org:47=), but the decision permits an
option to disable summaries when a provider capability requires it
(=addendum6.org:57-61=).  This conflicts with the corrected requirement: a
profile that rejects =auto= is unconfirmed for this contract, not a reason to
silently omit it.

The current adapter also has two established effort inputs.  An explicit
=:reasoning= plist replaces the entire default object, while otherwise
=:reasoning-effort= or the adapter default constructs =(:effort ...)=
(=lisp/adapters/openai/e-openai.el:1532-1543=).  Existing tests protect that
whole-object precedence (=test/e-openai-test.el:1509-1525=).  Addendum 6 says
only “request/profile option” and “option/default precedence”; it does not
define how summary selection composes with this public input, which values are
valid, what wins, whether =:reasoning nil= remains legal, or how the effective
choice enters request/continuation identity.  Current harness fingerprints
=:reasoning= and =:reasoning-effort= but has no summary option
(=lisp/core/e-harness.el:3553-3569=).

*** Consequence

Two conforming-looking implementations can send different wire bodies: one can
drop the required opt-in through the disable escape or an explicit
=:reasoning= plist, while another overwrites caller effort.  A reused provider
anchor or external record can then claim the wrong material request shape.
An endpoint that rejects =auto= also has no precise capability classification.

*** Minimal correction

Replace =Request reasoning summaries explicitly= with:

#+begin_quote
Every OpenAI Responses request contains =reasoning.effort= and
=reasoning.summary=.  The effective summary value is ="auto"= unless the
request explicitly selects ="detailed"= for diagnosis.  ="auto"= and
="detailed"= are the only valid values; nil, false, omission as an override,
and unknown values fail before transport.  A profile may supply the diagnostic
=detailed= default, but may not disable the field.  Request choice overrides
profile choice, which overrides the adapter default =auto=.

The existing =:reasoning= request plist remains the highest-precedence source
for =effort=.  Its other supported fields are preserved, but an absent
=summary= is filled with the effective value above and a present =summary= must
obey the same two-value contract.  State explicitly whether the diagnostic
profile field is normalized into that plist or has one named adapter option;
there must be one effective authority.  Chat Completions behavior is unchanged.

The effective effort and summary value participate in HTTP request identity,
WebSocket request-property/continuation compatibility, captured diagnostics,
and external evidence identity.  A configured Responses endpoint that rejects
the required =auto= request is =unavailable= and remains
=capability-unconfirmed= for that identity; it is not retried without the field
and is not a product-contract or repository-semantic failure.  A successful
response with a present, empty, or absent returned summary remains semantically
eligible because returned summary content is diagnostic only.
#+end_quote

*** Acceptance evidence

- literal HTTP and WebSocket bodies cover default =auto=, request diagnostic
  =detailed=, profile diagnostic =detailed=, request-over-profile precedence,
  explicit =:reasoning= effort preservation, invalid/disable rejection, and
  unchanged Chat Completions;
- anchor/request/evidence identity changes with the effective summary value;
- parser tests accept present, empty, and absent returned summary arrays without
  changing semantic results or copying prose into evidence; and
- a minimal configured Responses probe separately classifies accepted =auto=,
  explicit unsupported capability, configuration failure, provider failure,
  and timeout before the composed adoption/cache scenarios run.

** TODO P1-02: =F88A6-D1= cannot exhaustively partition a current frame with more than 16 sources

*** Contract cell

=F88A6-DISPOSITION= exact bounds and current-source feasibility.

*** Observed source fact

Addendum 6 requires the union of =keep=, =summaries[*].sources=, and =drop= to
equal every presented label and describes =drop= as an array “like =keep=”
(=addendum6.org:47-49,70-84=).  The inherited Addendum 4 ceiling is 16 distinct
labels with dispositions (=addendum4.org:235-247=).

Current frame construction creates one curatable source for every independently
rendered observation and does not cap the source count
(=lisp/core/e-context-lifetime.el:592-672,721-807=).  Core then rejects more
than 16 submitted labels (=lisp/core/e-context-lifetime.el:840-902=), while an
owner test deliberately constructs a 17-source frame and proves that its 17
labels are rejected (=test/e-context-lifetime-test.el:624-638=).

*** Consequence

A valid current request may present labels =1= through =17=, but no Addendum 6
effect can cover them all.  No call becomes a product-contract failure in the
new external scenario, while any attempted complete call becomes a repository
semantic failure.  The model therefore has no successful protocol action for a
state the repository already permits.

*** Minimal correction

Replace the bound language with:

#+begin_quote
The inherited limit of 16 applies to labels retained across =keep= and
=summaries[*].sources=, not to labels explicitly dropped.  =drop= must contain
every remaining presented label and has no independent fixed cardinality; its
maximum is the exact number of labels in the live frame.  Core validates one
linear complete partition, rejects duplicate/unknown/missing labels, rejects
more than 16 retained labels, and continues to measure only the prepared
exact/summary promotion record against 8,192 bytes.  Because dropped labels
produce no durable record item, they do not consume the retained-source or
prepared-record limits.  The schema and revision identity must reflect these
distinct bounds.
#+end_quote

If a fixed total-partition bound is preferred instead, the proposal must first
define and justify the same bound at frame construction/presentation and state
what happens to observations beyond it; silently presenting undisposable
sources is not acceptable.

*** Acceptance evidence

- exact 16/17 retained-label tests preserve the inherited boundary;
- a substantially larger frame can validly drop every label, and a mixed call
  can retain 16 while dropping all remaining labels;
- missing, duplicate, unknown, and one-over-retained partitions fail before
  session or frame mutation; and
- partition work is linear in the presented source count and does not copy
  dropped source bodies into the normalized effect, record, diagnostics, or
  evidence.

** TODO P1-03: =F88A6-D2= promises a durable drop audit that existing checkpoints discard

*** Contract cell

=F88A6-DROP= state lifetime, audit semantics, reopen, and cleanup.

*** Observed source fact

The proposal says the durable combination of reserved response control, absent
promotion, and consumed matching frame distinguishes explicit retain-nothing
and requires restart/reopen evidence (=addendum6.org:49,91-103=).

Frames are runtime-only and only generation/promotions enter the context
checkpoint (=lisp/core/e-session.el:1315-1353=).  The activity tail retains at
most 64 events, and a curation response control is pinned beyond that tail only
when an active version-3 promotion names its response ID
(=lisp/core/e-session.el:117-119,1355-1425=).  A drop-only response deliberately
has no such promotion.  Its control and =context-frame-consumed= activity can
therefore both age out at checkpoint, and no live consumed frame is rebuilt on
reopen.

*** Consequence

The stated durable relation cannot be implemented with the promised unchanged
session schema and no negative ledger.  An implementer must either add or pin
durable negative state contrary to the non-goal, or satisfy only short-tail
tests while the specification continues to claim durable reopen evidence.

*** Minimal correction

Replace “durable combination” and the associated evidence wording with:

#+begin_quote
For drop-only, the existing reserved response control and matching
=context-frame-consumed= activity form a persisted, content-free audit relation
while both remain in the existing bounded activity tail.  They distinguish the
live run and an immediate reopen from no invocation, but they are not promoted,
pinned, or promised after checkpoint-tail eviction.  The separately finalized
bounded E2E evidence record is the durable acceptance artifact for an observed
external run.  No session schema, negative ledger, drop label, source body, or
new checkpoint retention rule is added.
#+end_quote

Change =restart/reopen absence= to “immediate reopen with absent promotion and
present bounded-tail audit relation, plus checkpoint-tail eviction without
semantic residue.”

*** Acceptance evidence

- drop-only pure preflight precedes every mutation; invalid effects append no
  control/event/record and leave the frame live;
- valid commit appends exactly one control and one matching consumed event, no
  promotion, then consumes the presented frame without overwriting a newer
  descendant;
- immediate reopen reconstructs the same content-free tail relation;
- exact 63/64 and one-over tail tests show the declared bounded retention and no
  special pin; and
- clean fork and later projection contain no control, dropped label/body,
  promotion, or negative ledger.

** TODO P2-04: =F88A6-E2= proves a drop call but not that the source was useful in the current answer

*** Contract cell

=F88A6-ADOPTION= negative scenario semantics and failure localization.

*** Observed source fact

The contract calls the negative source useful only in the current turn
(=addendum6.org:50,105-112=), but its pass gates require only the ordinary tool,
carrier request, valid drop effect, audit/consumption, and content-free evidence
(=addendum6.org:114-131=).  They never assert that the visible answer used the
tool result.  A model can ignore the source, emit =drop=, and pass the claimed
current-use scenario.

*** Consequence

The run would prove structured rejection after presentation, but not the more
naturalistic and stronger boundary the proposal claims: use for the current
answer followed by explicit rejection of future retention.  A wrong current
answer also has no independent repository-versus-model failure stage.

*** Minimal correction

After the negative-scenario prompt paragraph, insert:

#+begin_quote
The prompt requires one deterministic, bounded transformation of the ordinary
tool sentinel in the current visible answer, without naming any curation term,
field, label, or reasoning summary.  The runner asserts that exact answer before
redaction.  A missing or wrong visible answer is =semantic-failure= with
=failure-stage current-answer=; it is not model non-adoption.  A pass records
=adoption-result pass=, =composition-result pass=,
=adoption-disposition drop=, and =failure-stage none=.  The evidence record
contains only those bounded classifications, never the sentinel, prompt,
answer, source, or returned reasoning-summary text.
#+end_quote

Add the current-answer assertion as a gate between source-bearing continuation
and finalization.  Retain the case-insensitive prompt negative inventory,
including =drop= and every other argument field after ordinary-tool
substitution.

*** Acceptance evidence

- the exact substituted prompt contains an ordinary current-answer task but no
  carrier, curation, argument, label, numeric-label, or reasoning-summary term;
- partitions cover correct answer/drop, wrong answer/drop, correct answer/no
  call, malformed/incomplete drop, configuration/provider failure, and timeout;
- one exactly-once finalizer preserves independent adoption/composition results
  and the original failure stage; and
- raw prompt, sentinel, answer, source, authentication, and reasoning-summary
  prose are absent from the record on every outcome.

* Architecture and design self-check

The final direction remains beneficial: it replaces ambiguous omission with an
explicit model decision while keeping provider diagnostics outside stable
context policy.  The real stable contracts are the frame-local complete
partition and atomic consume; summary mode and scenario wording remain
adapter/E2E-local variation.  The proposed owners are cohesive, interfaces stay
narrow, and side effects remain outside pure core preparation.

P1-02 must prevent a legacy selected-source bound from becoming an accidental
total-frame bound.  P1-03 must state the smallest true lifetime instead of
introducing unbounded negative audit state.  P2-05 must restore dependency
order so core semantics exist before provider exposure.  With those corrections
the change adds no durable runtime state, reverse dependency, speculative
abstraction, provider fallback, compatibility shim, or unsupported operation.

Partition validation should remain linear in presented labels and must not
visit dropped bodies after trusted label presentation.  Reasoning-summary
generation can add provider work, but it is an explicit product requirement;
token/cache/latency observations remain diagnostic until a thresholded contract
exists.  Existing v2/v3 read compatibility remains real; omission-as-decision
guidance and tests become removable.  Expected malformed partitions and
unsupported endpoint capability receive named failures; unexpected owner and
parser defects remain visible.  Narrow core, adapter, harness/session, and E2E
tests localize future design changes without broad rewrites.
