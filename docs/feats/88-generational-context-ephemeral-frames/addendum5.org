This addendum extends Addendum 4 without changing its curation semantics.  It
adds a model-facing affordance contract and a naturalistic external adoption
scenario.  Addendum 4 remains authoritative for frame-local labels, exact and
summary dispositions, omission-as-drop, atomic completion, bounds, durable
records, and compatibility.  Addendum 3 remains authoritative for canonical
request layout, inherited observation delivery, continuation, cache evidence,
and cleanup.  Where wording conflicts, this addendum supersedes only Addendum
4's assumption that exposing the reserved carrier is sufficient guidance for
spontaneous model use.

The matrix below is this addendum's sole normative authority.  Other sections
explain its rows or name their evidence; they do not create additional
requirements.

* Motivation and evidence baseline

The curation mechanism is operational, but current model-facing presentation
does not explain its lifetime or decision.  The OpenAI adapter describes
=context-curate= only as “Keep or summarize bounded values from ephemeral
context.”  Core presents a source with a marker such as =[1, ~120 tokens]=.
The description names operations but not when they are useful, the marker does
not identify the following value as an ephemeral source, and neither surface
connects a user's future-use intent to the reserved effect.

The 2026-08-27 Grimoire Daily session is observational motivation, not an
acceptance gate.  Across 15 provider requests the configured model received the
curation carrier and ephemeral source presentation but made zero
=context-curate= calls.  That session also reproduced an unrelated restored
board-participant routing defect, so it cannot serve as a controlled adoption
test.  It establishes only that carrier availability does not by itself imply
autonomous use.

Existing credentialed acceptance explicitly tells the model to call
=context-curate= and supplies the exact =keep= and =summaries= arguments.  It
proves carrier and curation mechanics, not spontaneous selection.  This
addendum retains that mechanism evidence and adds a separate isolated scenario
whose prompt expresses a future-turn need without naming the curation carrier
or its schema.

* Decision

Make the existing affordance self-explanatory instead of adding automatic
retention policy.  The late source marker identifies the value that follows as
an ephemeral context source and carries its existing local label and size hint.
A representative rendering is:

#+begin_example
[ephemeral context source 1, ~120 tokens]
<exact source value>
#+end_example

The marker remains a detached provider-neutral system message immediately
before its source.  It does not contain durable, frame, generation,
observation, request, provider, or backing-object identity.  It does not tell
the model whether the value deserves retention; it only makes the value's
lifetime and label legible.

The Responses =context-curate= description explains the decision at the
carrier that performs it.  Its meaning is:

- call after using an ephemeral source when the user or task is likely to need
  its exact value or a compact replacement in a later turn;
- use =keep= for exact retention and =summaries= for smaller durable
  replacement text;
- a source omitted from a successful call is dropped; and
- make no call when nothing from the frame should remain available.

The implementation may refine the sentence structure, but it must preserve all
four meanings without adding hidden policy, automatic selection, or another
instruction authority.  The strict Addendum 4 JSON schema remains unchanged
and continues to provide field-level shapes.

The marker is late-frontier input.  The reserved-tool definition is stable
request material.  Both changes revise the applicable presentation or schema
fingerprint so an earlier anchor or cache-evidence record cannot silently
claim the new shape.

* Naturalistic adoption scenario

=responses-autonomous-curation-adoption= runs in an isolated session with the
configured compatible Responses profile and the existing deterministic E2E
tool.  The first user prompt has this semantic shape:

#+begin_quote
Use the deterministic lookup tool to obtain the current adoption sentinel.
I will ask about that value in my next message.  Do not reveal it yet; reply
only READY.
#+end_quote

The actual prompt may name the ordinary deterministic tool so the source is
reproducible.  It must not contain =context-curate=, =curate=, =keep=,
=summary=, =summaries=, =source label=, or a numeric source reference.  The
ordinary tool returns a unique bounded sentinel as one curatable source.
The negative inventory is applied case-insensitively to the actual prompt after
the ordinary-tool name is substituted.

The valid first turn must call the ordinary tool and then autonomously emit one
valid reserved curation effect disposing that source.  Either exact retention
or a summary that preserves the sentinel is acceptable; the model still owns
that choice.  The final visible answer is =READY= and does not reveal the
sentinel.  The runner records the selected disposition and verifies the
curation record's existing audit/control linkage.

A second ordinary user turn asks for the retained sentinel without naming the
carrier.  Its captured request must contain the durable exact or summary item,
must not contain the consumed raw tool-result envelope or presentation marker,
and the assistant must return the exact sentinel.  This proves adoption and
the existing semantic composition separately from mere function-call
serialization.

The scenario emits one bounded, content-free, identity-complete evidence
record.  The record carries bounded =adoption-result= and
=composition-result= fields plus a bounded =failure-stage=.
=adoption-result= classifies whether, after a valid ordinary-tool source and
carrier presentation, the model emitted one valid effect whose exact or summary
replacement preserves the sentinel.  =composition-result= independently
classifies prompt control, carrier presence, audit linkage, commit, next-turn
projection, raw-source exclusion, and the follow-up answer.  =failure-stage=
is one of =none=, =ordinary-tool=, =prompt-control=, =model-selection=,
=carrier=, =commit=, =projection=, =raw-exclusion=, or =follow-up-answer=; it
contains no prompt, sentinel, or model content.

A valid run has one of these top-level outcomes:

| Result | Meaning |
|--------+---------|
| =pass= | The model autonomously curated the source and the follow-up semantic assertions passed. |
| =product-contract-failure= | An identity-complete run validly presented the ordinary-tool source and carrier, but the model emitted no valid reserved effect or chose a replacement that did not preserve the sentinel. |
| =semantic-failure= | A prompt-control, carrier, audit, commit, projection, raw-exclusion, or follow-up assertion failed; the bounded subresults and =failure-stage= identify the boundary. |
| =unavailable= | Required capability identity or request/curation capture was absent.  Missing token or cache usage leaves those observational fields unavailable without changing an otherwise conclusive adoption result. |
| =configuration-unavailable= | The request could not start with valid authentication or provider configuration. |
| =provider/infrastructure-failure= | External provider or infrastructure health prevented a valid observation. |
| =inconclusive-timeout= | The scenario exceeded its declared deadline. |

Only =pass= confirms autonomous adoption for the recorded capability identity.
Only =product-contract-failure= disproves the contract.  Availability failures
leave it unconfirmed.  The record carries captured endpoint, store mode, model,
transport, native requester, material request identity, revision, and result,
but never the sentinel or model content.

One canonical successful observation is sufficient for initial capability
confirmation, matching the existing Feature 88 external capability policy.
Population-level invocation frequency, exact-versus-summary distribution,
token usage, cache usage, and latency remain observational until a separate
contract supplies a population, baseline, and decision threshold.

Adoption evidence inherits Addendum 3's seven-calendar-day freshness window.
Reuse requires equality of provider/profile, effective endpoint/base URL,
transport, store mode, native requester, model, material request shape,
affordance/presentation revisions, and scenario prompt identity, with no
changed core, harness, loop, backend-adapter, or runner owner in the scenario's
dependency cone.  Otherwise the evidence is =stale=; a non-success availability
class leaves autonomous adoption =capability-unconfirmed=.

* Implementation slices

** Slice 1: Self-explaining source and carrier affordances

Revise the provider-neutral source marker and the OpenAI reserved-tool
description at their existing owners.  Fence the changed presentation and
request shape, retain the strict schema, and add owner plus captured-request
tests for =F88A5-AFFORDANCE=.  Do not add another context provider, durable
instruction, automatic policy hook, or adapter-to-core dependency.  Accepted at
=3fdcf799=.

** Slice 2: Naturalistic adoption evidence

Add one isolated configured Responses selector and shared bounded evidence
capture for =responses-autonomous-curation-adoption=.  Reuse the ordinary
deterministic tool and existing curation/audit/request instrumentation.  Keep
the user prompts free of carrier and schema vocabulary, classify all external
outcomes exactly once with independent adoption/composition subresults and a
bounded failure stage, retain the shared runner's established result spellings,
and keep sentinel/content data out of the evidence record.  Implemented at
=317be237=; the configured Responses HTTP run is recorded above.

** Slice 3: Configured validation and evidence refresh

Run the new adoption scenario and the inherited canonical warm-prefix and
tool-heavy scenarios against the configured compatible Responses profile.
Record request-derived capability identity and revision-specific results.
Update Addenda 3 and 4, their implementation review, =limitations.org=, and the
Feature 88 status only where their distinct evidence or completion state
changes.  Preserve the separate exact ChatGPT/WebSocket status.

* Non-goals

This addendum does not add heuristic or automatic curation, force a curation
call on every frame, choose exact retention versus summarization for the model,
change curation bounds or durable records, add a second context-management
tool, create a board storage class, define population-level adoption rates, or
claim that one external success predicts all prompts or future model versions.

* Architecture self-check

1. The package is useful independently: it makes an already-operational
   curation mechanism discoverable and supplies direct evidence of autonomous
   use.
2. It moves toward model-directed bounded context lifetime without moving the
   semantic decision into UI, board, or provider code.
3. Guidance wording and the external prompt may change and remain local;
   curation semantics, owners, and durability remain stable.
4. Core owns source lifetime presentation, the OpenAI adapter owns its wire
   tool description, the model chooses a disposition, and existing core/
   harness/session owners enforce it.
5. It adds no interface.  Existing marker and reserved-carrier surfaces become
   more legible.
6. Stable policy does not depend on an adapter; the adapter continues to
   serialize the existing provider-specific carrier.
7. External execution and evidence capture remain in E2E adapters rather than
   core policy.
8. No runtime state is added.  Evidence is bounded and revision-scoped under
   the existing runner policy.
9. Runtime cost is limited to changed prompt text and one optional external
   scenario; no additional provider request is added to ordinary turns.
10. The affordance describes the real existing curation contract and does not
    create an unsupported operation.
11. Addendum 4 compatibility remains unchanged; prior cache evidence is
    invalidated rather than silently reused across material prompt text.
12. No legacy path becomes necessary.
13. Expected external failures are classified at the runner; unexpected core
    and carrier failures remain visible.
14. Deterministic tests cover request construction; the naturalistic external
    scenario tests model choice and composed behavior without freezing one
    private implementation.
