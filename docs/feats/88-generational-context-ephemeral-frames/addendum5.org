#+title: Addendum 5: Explicit Tool-Output Context Erasure
#+date: 2026-08-27
#+startup: overview

* Status

Planned.

* Decision

Add an explicit =erase= disposition to Feature 88 context curation for an
ephemeral tool-result source that must leave no automatic trace in later model
context.

Erasure is a model-context decision, not deletion.  The transcript, durable
activity history, and session-scoped temporary details remain unchanged.  A
later explicit read of that stored history is a new observation; it does not
make the erased source part of ordinary context again.

This addendum owns erasure because Feature 88 owns semantic model-context
lifetime.  [[file:../90-tool-invocation-receipts/plan.org][Feature 90]] owns invocation receipts and temporary details, but it
only consumes Feature 88's erasure authority when deciding whether a receipt is
eligible for context projection.

* Why omission is no longer sufficient

Addendum 4 defines omission as dropping the exact ephemeral source.  That is
sufficient while no other context projection is derived from the source.

Feature 90 introduces a distinct compact receipt projection.  Under that
feature, omitting a tool source still drops its exact arguments and result, but
normally leaves a receipt containing the tool, status, stated purpose, and
temporary details URI.  The receipt is useful by default, but it means omission
can no longer express "leave no trace in later model context."

=erase= restores that explicit choice.  It does not duplicate a generic drop
list: it suppresses derived context projections that ordinary omission
deliberately permits.

* Model-facing contract

The reserved =context-curate= effect accepts exactly the optional keys =keep=,
=summaries=, and =erase=.  Feature 88 exposes this contract independently of
whether Feature 90 receipt projection is active.

#+begin_src json
{
  "keep": [1],
  "summaries": [
    {"sources": [2], "text": "The retained semantic conclusion."}
  ],
  "erase": [3]
}
#+end_src

=erase= is an ordered array of positive integer frame-local source labels.  An
omitted key is an empty list.  Unknown keys remain invalid.

Every label in =erase= must identify an ordinary tool-result source in the
active consumer-bound frame.  Erasing a non-tool source is invalid because
ordinary omission already removes it without producing a receipt.  The model
submits only frame labels; core derives the tool call identity and all durable
provenance.

A source has at most one disposition:

- =keep= retains its exact bounded model-visible value;
- a =summaries= entry retains submitted replacement text;
- =erase= retains no source-derived model-context value;
- omission drops the exact source but permits separately owned derived context,
  including a Feature 90 receipt.

Labels may not overlap across =keep=, any summary's =sources=, and =erase=.
Unknown, repeated, overlapping, or non-tool erase labels reject the entire
curation before durable or frame mutation.

An erase-only effect is valid.  After normalization, at least one distinct
source must have a keep, summary, or erase disposition.  The existing maximum
of 16 disposed labels includes erased labels.  The existing 8,192-byte prepared
record bound includes exact values, summary text, and erasure provenance.

This addendum supersedes only Addendum 4's exact =context-curate= object shape,
its statement that a separate drop list has no meaning, and its requirement
that at least one source be kept or summarized.  All other Addendum 4
presentation, provenance, atomicity, compatibility, and bound rules remain.

* Erasure semantics

For each successfully erased tool source, every later ordinary model-context
projection excludes:

- the tool call and its arguments;
- the tool result and result metadata;
- any Feature 90 invocation receipt;
- the stated purpose;
- the temporary details URI;
- any count, summary, latest-item marker, or other aggregate whose only evidence
  is the erased source.

The source remains available during the provider invocation that consumed it.
Erasure cannot retroactively alter an already-sent request or the immediate
tool-result continuation that made the decision possible.

Erasure does not delete or rewrite:

- transcript tool-call or tool-result entries;
- durable tool activity records;
- any temporary invocation-details resources;
- provider audit or replay metadata already retained under its independent
  transport lifetime;
- user-visible shell history.

Consequently, "completely" means complete absence from automatically assembled
future model context.  It does not mean storage destruction or audit erasure.

An explicit later transcript, activity, session-resource, or =tmp://= read may
surface the stored details again.  The read result is a new ephemeral
observation with its own Feature 88 lifetime and does not revoke the original
erasure record.

* Durable erasure authority

Core prepares one durable =context-erasure= record for a successful curation
that contains erased sources:

#+begin_src emacs-lisp
(:record-version 1
 :type context-erasure
 :id ERASURE-ID
 :frame-id FRAME-ID
 :generation-id GENERATION-ID
 :consumer-request-id CONSUMER-ID
 :response-entry-id RESPONSE-ID
 :sources
 ((:source-observation-id OBSERVATION-ID
   :source-ref SOURCE-REF
   :source-fingerprint SOURCE-FINGERPRINT
   :tool-call-id TOOL-CALL-ID)))
#+end_src

The record contains no source value, arguments, result, purpose, receipt,
temporary URI, provider item, replay envelope, or backing object.  Core derives
every identity from the matching live frame; the model cannot submit durable
identifiers.

=context-erasure= is semantic suppression authority, not transcript content or
an activity event.  It has no direct model-visible projection.  Context
providers query the canonical session projection for erased tool-call
identities and exclude matching derived values.

The record survives reopen, branch selection, checkpointing, and compaction for
as long as a matching durable receipt or other derived projection could
otherwise reappear.  Implementations may prune an erasure only after proving
that no eligible context projection can reference its subject.  They must not
infer safety merely from temporary-resource expiry.

When one curation contains exact, summary, and erase dispositions, preparation
validates all of them before mutation.  Harness/session append the version-3
=context-promotion= record when exact or summary items exist and the
=context-erasure= record when erase items exist, then consume the frame.  A
failure in either append follows the existing curation failure boundary; no
partial curation becomes visible.

* Receipt integration boundary

Feature 90's receipt provider receives the canonical erased-tool-call set from
the harness/session context projection.  It filters receipts before ordering,
counting, byte budgeting, omitted-count calculation, or latest-item selection.
An erased receipt therefore leaves no indirect aggregate mark.

Feature 90 does not parse =context-curate=, derive erasure identities, write
=context-erasure= records, or decide whether erasure is allowed.  Feature 88
does not generate receipts, invocation details, or temporary resources.

This dependency flows from the optional receipt projection toward Feature 88's
stable semantic-lifetime contract.  Feature 88 core remains independent of the
receipt implementation.

* Provider and cache identity

Adding =erase= changes the reserved =context-curate= schema and therefore the
material tool-schema and prompt-layout identity.  Existing anchors and cache
evidence recorded against the Addendum 4 schema are not valid evidence for this
shape.  Schema fingerprints must invalidate incompatible anchors, and the
configured cache scenarios must be rerun after implementation.

This requirement is about request-shape identity and semantic correctness, not
wire-size reduction.  No request-byte target is introduced.

* Implementation slices

** Slice 1: pure erase preparation

Extend the core curation schema and preparation logic with =erase=.  Validate
tool-source eligibility, exclusivity, the shared 16-label bound, the prepared
8,192-byte bound, and core-derived provenance without mutating frame or session
state.

** Slice 2: durable erasure record

Add the versioned =context-erasure= codec, session append/replay, branch,
checkpoint, compaction, and retention behavior.  Expose a narrow canonical
query for erased tool-call identities without projecting the record as model
content.

** Slice 3: atomic curation application

Join promotion and erasure preparation at the existing provider-completion
boundary.  Prove keep-only, summary-only, erase-only, mixed valid, mixed
invalid, append failure, and duplicate-effect behavior.

** Slice 4: derived-context integration

Make Feature 90 receipt projection consume the canonical erased identity set.
Prove filtering happens before every bound and aggregate.  Preserve transcript,
activity, and temporary details exactly.

** Slice 5: end-to-end and cache evidence

Run one credential-free tool turn for ordinary omission and one for explicit
erasure.  Refresh material schema identity and the configured cache evidence
after deterministic repository validation passes.

* Acceptance criteria

- =context-curate= accepts an optional =erase= list of active frame-local
  ordinary tool-result labels.
- Keep, summary, and erase dispositions are mutually exclusive per source, and
  an erase-only effect is valid.
- Ordinary omission still removes the exact source but permits a Feature 90
  receipt; explicit erase permits no source-derived automatic context value.
- Later context after erase contains no tool call, arguments, result, receipt,
  purpose, details URI, or aggregate mark derived solely from that source.
- Transcript, durable activity, shell history, and temporary details remain
  unchanged and inspectable.
- A later explicit read creates a new ephemeral observation rather than
  silently restoring the erased source.
- The durable erasure record contains only core-derived identity and provenance,
  never source content or provider artifacts.
- Erasure survives reopen, branch selection, checkpointing, and compaction while
  any matching derived projection remains eligible.
- Mixed curation appends promotion and erasure authority atomically before frame
  consumption.
- Receipt filtering occurs before ordering, budgets, omitted counts, and other
  aggregates.
- Provider continuation and anchor cleanliness remain conservative; erasing a
  later projection does not make a tool-contaminated response a clean anchor.
- Schema identity invalidates Addendum 4-era anchors and cache evidence, and
  fresh deterministic and configured evidence is recorded.

* Non-goals

- Deleting transcript, activity, temporary resources, or provider audit state.
- Providing a model-controlled privacy or audit-erasure operation.
- Changing exact keep or summary content semantics.
- Treating ordinary omission as explicit erasure.
- Making erased tool descendants eligible as clean provider anchors.
- Adding an erasure option to ordinary tools or Feature 90's invocation
  envelope.

* Design self-check

1. This addendum preserves useful default receipts while restoring a precise
   way to leave no source-derived mark in later model context.
2. It moves toward explicit, provenance-backed context lifetime without
   conflating context projection with transcript storage.
3. Erasure semantics and provenance are stable.  Retention pruning remains
   local and conservative until a real safe condition is proven.
4. Feature 88 owns the decision because it owns semantic context lifetime;
   Feature 90 only consumes the result.
5. The interface is one additional curation disposition and one narrow erased
   identity query, not a tool-specific callback.
6. Core policy does not depend on a provider adapter, receipt renderer, shell,
   transcript store, or temporary-resource implementation.
7. Transcript and resource side effects stay with their existing owners; pure
   curation preparation remains side-effect free.
8. Erasure adds only compact durable suppression provenance.  Full details stay
   at their existing transcript and temporary lifetimes.
9. Filtering adds one bounded identity lookup per candidate receipt.  Cache
   evidence is refreshed because schema shape changes, not because wire size is
   an objective.
10. =erase= has one substitutable meaning: no source-derived automatic future
    model context.
11. Existing v2/v3 promotion records remain readable.  New erasure records are
    additive and do not reinterpret stored history.
12. No existing transcript or temporary-detail path is removed.
13. Invalid erasure fails through the existing curation boundary; unexpected
    append, replay, or projection errors surface visibly.
14. Pure preparation, session codec, atomic harness, receipt integration, and
    E2E tests isolate the changed contracts.
