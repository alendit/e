* Finding

** P1 F88.14: per-execution frame opening conflicts with one aggregate result frame

The plan requires every execution to persist its own =frame-opened= before its
=execution-settled= marker, while the lifetime invariant and acceptance criteria
require one next frame containing all results from the reasoning transition.
For multiple tools this either opens multiple frames, mutates an append-only
frame, or delays settlement past the acknowledgement-before-next-tool boundary.

*** Owning correction

Use a two-stage transaction.  Each tool persists its normalized provider-linked
result followed by =execution-settled= referencing that result, and acknowledges
that prefix before the next tool.  Per-execution settlement opens no frame.

After every admitted execution is settled, append and acknowledge exactly one
deterministic =frame-opened= record referencing all result entry ids in admitted
order.  The pending-transition descriptor retains those ids and the aggregate
frame identity.  Replay completes partial execution prefixes first, then creates
or re-acknowledges the same aggregate frame exactly once.  Manual resolution
uses the same per-execution prefix; when it settles the last call, the recovery
service creates the aggregate frame before follow-up.

E2E acceptance needs at least two admitted tools and must prove per-execution
ordering, one ordered result frame, cut-point recovery around all markers and
the aggregate frame, mixed settled/ambiguous resolution, and no follow-up before
aggregate-frame acknowledgement.  Performance evidence must separate aggregate
frame bytes, acknowledgement wait, and last-tool-to-follow-up time.
