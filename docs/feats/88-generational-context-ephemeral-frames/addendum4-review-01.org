* Findings

** TODO P1-01: =F88A4-BOUNDS= has no aggregate correctness or resource boundary

*** Contract cell

=F88A4-BOUNDS=.

*** Observed source fact

Addendum 4 calls each exact source “bounded” and recommends bounded previews,
but defines no maximum selected-source count, output count, summary size, or
aggregate durable size (=addendum4.org:59-60= and =addendum4.org:75-84=).

The superseded contract accepted 1--16 facts and at most 8 KiB of normalized
UTF-8 payload (=plan.org:293-305=).  Current core implements those limits at
=lisp/core/e-context-lifetime.el:63-70= and
=lisp/core/e-context-lifetime.el:250-275,775-813=, with exact-limit tests at
=test/e-context-lifetime-test.el:200-255=.

*** Consequence

A label-only keep request can select aggregate source content much larger than
the wire arguments, and summary text is presently unlimited.  A conforming
implementation could append unbounded session state and repeat it in every
later request, while another could silently reuse the old limits.

*** Minimal correction

Core must accept a curation only when at least one source has a keep or summary
disposition, no more than 16 distinct frame labels have dispositions, every
summary has at least one source and non-empty text, and the canonical prepared
durable record is at most 8,192 UTF-8 bytes.  The measurement must include exact
values, summary text, and core-derived provenance.  Exactly 16 labels and 8,192
bytes are accepted; 17 labels or 8,193 bytes reject before semantic mutation.
Changing either limit must change the contract, boundary tests, schema
fingerprint, and cache-evidence identity together.

*** Acceptance evidence

- exact-bound and one-over core tests for both limits;
- proof that exact values, summaries, and provenance participate;
- large-handle proof that only the bounded preview can fit; and
- prompt/schema fingerprint fencing when a limit changes.

** TODO P1-02: =F88A4-ATOMIC= does not define multiple-call, failure, or wire-continuation behavior

*** Contract cell

=F88A4-ATOMIC= joined to inherited =F88A3-TOOL=.

*** Observed source fact

Addendum 4 rejects malformed or duplicate dispositions and permits at most one
successful call per frame, but does not define two valid calls, interaction
with ordinary streamed tool calls, or whether invalid input stops later
dispatch (=addendum4.org:65-73=).

The inherited contract requires invalid promotion to use the existing failure
path without later dispatch or semantic mutation (=addendum3.org:46-53=).
Current loop code rejects a second reserved effect and retains an opaque
immediate acknowledgement (=lisp/core/e-loop.el:847-875=).  The original
contract preserves already-streamed calls while stopping later calls
(=plan.org:307-320,857-861=).  Frame completion drops observation bodies
(=lisp/core/e-context-lifetime.el:746-773=), while the harness currently
completes the frame before resolving promotion effects
(=lisp/core/e-harness.el:3090-3140=).

*** Consequence

Implementations could commit the first call or reject both, dispatch different
ordinary-tool subsets, lose an exact source by consuming the frame too early,
or leave an unmatched provider function call.

*** Minimal correction

More than one =context-curate= effect in one complete response must reject the
entire curation before durable or frame mutation.  Invalid curation preserves
already-streamed ordinary calls, dispatches no later calls, and appends no
curation record.  At provider completion, core validates and prepares the
complete curation against the still-live consumer-bound frame.  The harness
appends it and consumes the frame before any later provider request.  No valid
effect means consume and drop the frame.  A provider-required acknowledgement
may survive only as opaque replay metadata for the matching immediate
continuation.

*** Acceptance evidence

- zero, one, and two-effect response tests;
- invalid-before/between/after ordinary-tool orderings;
- both provider-done/tool-result orderings;
- preparation before source-body removal; and
- immediate acknowledgement with later semantic and lineage exclusion.

** TODO P1-03: =F88A4-DURABLE= and inherited compatibility do not define the new record or old-record behavior

*** Contract cell

=F88A4-DURABLE= joined to =F88A3-COMPAT= and =F88A3-SEM=.

*** Observed source fact

Addendum 4 says the runtime creates durable IDs/schema revision and that audit
records may retain provenance, but gives no item schema, ordering, projection,
migration, or removal contract (=addendum4.org:46-55,124-136=).

Current version-2 promotion records contain flat facts and promotion-wide
source arrays (=lisp/core/e-context-lifetime.el:698-739=).  Session replay,
ownership, projection, and append explicitly recognize =context-promotion=
(=lisp/core/e-session.el:159-160,3145-3196,3708-3776=).  Existing tests prove
v2 reopen and projection (=test/e-session-test.el:29-110,2737-2803=).

*** Consequence

An implementation could drop active durable facts on reopen, attach all
sources to every replacement, persist presentation metadata, or retain dual
model-facing writers.

*** Minimal correction

Keep the persisted session family =context-promotion= for compatibility, but
make new writers emit version 3 with ordered =:items=.  Exact items contain one
detached canonical value and one source’s core-derived ID/ref/fingerprint;
summary items contain model text and one or more sources’ parallel provenance.
Exact items follow =keep= order and then summary items follow submission order.
The record contains no frame labels, token hints, provider acknowledgement,
backing object, live frame body, settlement, or retry state.  Projection emits
only the exact value or summary text.

Version-2 records remain readable and model-visible on the active generation,
and remain audit-only when covered.  V2 and v3 may coexist across reopen,
branching, and compaction.  New code writes only v3.  Remove the old
model-facing =context-promote= tool, decoder, encoder, fingerprint, and writer;
the v2 reader is the sole compatibility path.  The generation codec remains
version 2.

*** Acceptance evidence

- exact and multi-source-summary v3 codec round trips;
- strict malformed/mismatched provenance rejection;
- mixed v2/v3 reopen, projection, branching, and compaction;
- exact projection excludes metadata and backing values; and
- negative source tests find no old carrier or dual writer.

** TODO P2-05: =F88A4-PRESENT= does not define the mandatory approximate token count

*** Contract cell

=F88A4-PRESENT= and =F88A4-COST=.

*** Observed source fact

Addendum 4 mandates an approximate token count for every ephemeral input but
does not define the value counted, estimator, rounding, fallback, owner,
durability, or cache-fingerprint effect (=addendum4.org:88-106,122-126=).
Core already has a provider-neutral estimator using configurable UTF-8 bytes
per token, a 4.0 fallback, and upward rounding
(=lisp/core/e-context-budget.el:52-87=).

*** Consequence

Adapters could count different wrappers, annotations could contaminate the
retained exact value, and material prompt changes could evade cache fencing.

*** Minimal correction

Core must estimate each exact canonical source value before adding its label or
annotation, using the existing configurable bytes/token ratio, upward rounding,
and 4.0 fallback.  Tests inject the ratio.  A late-frontier marker such as
=[1, ~120 tokens]= participates in prompt-layout/schema fingerprints, but is
not retained or persisted.  Optional monetary guidance belongs to an outer
owner and must record all pricing assumptions; absent assumptions yield only
source sizes and the qualitative warning.  Cost never changes semantic
acceptance.

*** Acceptance evidence

- injected-ratio per-item rounding and fallback tests;
- label/count exclusion from exact durable values;
- cache-identity change when presentation changes; and
- absent pricing leaves semantics unchanged.

* Evidence and implementation feasibility

The replacement fits the existing owners: core has runtime bodies and trusted
provenance; harness owns composition; loop owns reserved streaming effects;
session owns strict durable codecs/replay/branches; and OpenAI owns only wire
schema and opaque acknowledgement.  The material change is to prepare exact
selections while the frame body is live, add a version-dispatched durable item
codec, replace the reserved wire schema, and reuse existing response/projection
boundaries.  No provider policy, board state, or persistent frame recovery is
required.

* Architecture self-check

1. The package is a useful stopping point: it makes lifetime choice expressive
   without requiring compaction or tool-result redesign.
2. It moves toward canonical durable context selected at an ephemeral frontier.
3. Pricing and future compaction remain local; keep/summary/drop is the stable
   semantic operation.
4. Core owns rewrite semantics and limits; session owns durability; harness
   owns commit composition; loop owns streaming control; adapters own wire.
5. The model-facing interface narrows to labels and summary text.
6. Dependencies continue from adapters toward provider-neutral core.
7. Acknowledgement, pricing, transport, and cache effects remain outward.
8. Only selected values, summaries, and provenance are durable.
9. Aggregate bounds make validation linear in one bounded frame.
10. Adapters do not weaken the core contract or own alternate limits.
11. Historical v2 records require a reader; the old writer and carrier do not.
12. Old =context-promote= helpers and tests become removable.
13. Expected validation errors use the existing response failure boundary.
14. Owner tests can change narrowly at core, loop, session, harness, and adapter
    boundaries.
