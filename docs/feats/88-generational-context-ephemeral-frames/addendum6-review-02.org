* Review 01 finding dispositions

** DONE P1-01: =F88A6-REASONING-SUMMARY= has one mandatory effective request value

Every Responses request now requires effective effort plus summary; =auto= is
the default, =detailed= is the only diagnostic alternative, and nil, false,
omission as an override, and unknown values fail before transport
(=addendum6.org:47,57-71=).  A profile cannot disable the field.

The adapter-owned =:reasoning-summary= resolution is request over profile over
=auto=.  A present =:reasoning :summary= is the effective request choice; when
absent, the resolved value fills the existing plist without replacing its
highest-precedence effort or other supported fields.  Explicit =:reasoning nil=
is rejected for Responses, while Chat Completions is unchanged
(=addendum6.org:57-71=).  This exactly dispositions the current adapter's
whole-plist-versus-effort join at
=lisp/adapters/openai/e-openai.el:1532-1543=.

Effective effort and summary enter HTTP identity, WebSocket
request-property/continuation compatibility, diagnostics, and external evidence
identity.  An endpoint rejection is =unavailable= and is never retried after
removing or changing the required field (=addendum6.org:73-79=).  Returned
summary presence or prose remains diagnostic only (=addendum6.org:81-84=).
P1-01 is closed.  The new probe's own record/freshness omission is the distinct
P2-06 below.

** DONE P1-02: complete disposition is feasible beyond 16 presented sources

The old 16-label ceiling now applies only to labels retained across =keep= and
=summaries[*].sources=.  =drop= exhaustively contains every remaining presented
label and has the live-frame source count as its dynamic maximum.  Core validates
the partition linearly without copying dropped values or provenance, and only
the exact/summary promotion record is measured against 8,192 bytes
(=addendum6.org:48,98-107=).

This is feasible against current source: frame construction and presentation
allow more than 16 sources, while the existing 16-source and 8,192-byte
retention limits have cohesive core owners
(=lisp/core/e-context-lifetime.el:592-672,721-807,840-1025=).  The named 16/17
retained boundary, large drop-only and mixed partitions, exact complete-set
validation, and no-copy constraint cover the changed limit semantics.  P1-02
is closed.

** DONE P1-03: drop-only audit has the smallest truthful lifetime

** TODO P2-06: the summary-capability probe has no reusable evidence contract

*** Contract cell

=F88A6-REASONING-SUMMARY= external identity, result, freshness, and reuse.

*** Observed source fact

The matrix and portfolio newly require
=responses-reasoning-summary-capability= before composed scenarios and say an
endpoint rejection is =unavailable=/=capability-unconfirmed=
(=addendum6.org:47,73-79,168-179=).  They do not define the probe's bounded
record fields, exactly-once finalization, positive result, summary-presence
diagnostic, age, identity-equality reuse, or invalidating owner cone.

Addendum 5's seven-day rule is explicitly for adoption evidence and includes
its scenario prompt and affordance identities (=addendum5.org:167-173=).
Addendum 3's identity/freshness rule belongs to its named cache scenarios
(=addendum3.org:198-238=).  The new minimal summary-capability probe is neither
of those scenarios, so inheritance does not determine its reusable evidence.

*** Consequence

One runner may call any accepted response a permanent capability pass, while
another may require returned summary text or omit endpoint/requester identity.
A stale or cross-profile observation could then authorize the composed runs, or
a successful request with an empty/absent diagnostic summary could be rejected
despite the semantic contract saying content has no decision power.

*** Minimal correction

Insert after =Request reasoning summaries explicitly=:

#+begin_quote
=responses-reasoning-summary-capability= emits exactly one bounded,
content-free record per invocation.  It records scenario, provider/profile,
effective endpoint/base URL, Responses transport, store mode, native requester,
model, effective effort and summary value, material request identity, probe
request identity, timestamp, repository revision, declared timeout, elapsed
duration, bounded summary-presence =present=/=empty=/=absent=, and result.  It
contains no prompt, response text, returned summary text, authentication value,
or header.

A terminal successful response to the smallest valid =summary: "auto"= request
is =pass= and confirms the capability for that exact identity whether the
returned summary is present, empty, or absent.  An explicit endpoint rejection
of the required field is =unavailable= and leaves that identity
=capability-unconfirmed= without fallback.  Authentication/configuration,
provider/infrastructure, and deadline failures use
=configuration-unavailable=, =provider/infrastructure-failure=, and
=inconclusive-timeout=.  Missing/mismatched captured identity or a request that
does not contain the resolved effort plus =summary: "auto"= is
=semantic-failure= and cannot confirm endpoint capability.  Exactly one record
preserves the original outcome on every path.

Probe evidence inherits a seven-calendar-day freshness window.  Reuse requires
equality of every recorded capability and request identity field and no changed
OpenAI adapter, native requester, capture, finalizer, or probe-runner owner in
its dependency cone; otherwise it is =stale=.  Run and report the selector
separately for configured Responses HTTP and exact ChatGPT/WebSocket identities;
one profile or transport never confirms the other.
#+end_quote

* Cleared joins, architecture, and external status

The remediation preserves the authoritative user correction.  It does not
strengthen generic narration: the revised carrier is concise and
schema-directed, while stable instructions, markers, ordinary prompts, and
returned summary prose gain no curation authority.  A structured exhaustive
=drop= remains the only evidence of considered-and-rejected; no-call is still
operational drop without a model-decision claim.

The design moves toward explicit model-directed lifetime decisions with the
smallest correct owners.  Summary request/profile variation stays in the
OpenAI adapter.  Complete partition and retained-source bounds stay in core.
Pure no-record preparation precedes harness/session effects.  Runtime frames
and dropped data die at frame consumption; bounded activity-tail controls are
not promoted or pinned.  E2E evidence is external audit state, not session
semantic state.  These choices reduce ambiguity without a second carrier,
provider-specific core branch, durable negative ledger, broad retention rule,
or compatibility shim.

Partition validation has linear work in presented labels and copies no dropped
body or provenance.  The mandatory summary opt-in may add provider work, but
token, cache, latency, and returned-summary observations have no threshold and
remain non-gating telemetry.  Existing v2/v3 read compatibility, projection,
compaction, branches, ordinary tools, retry behavior, and Chat Completions stay
unchanged.  Obsolete omission/no-call guidance and its exact witnesses are
removed when the new carrier is exposed.

Repository-controlled implementation has not begun.  All earlier Addendum 5
adoption/cache records are stale for Addendum 6 because the reasoning field,
carrier schema/guidance, prompt, and affected owners change.  Configured
Responses HTTP and exact ChatGPT/WebSocket capability must be recorded
separately after implementation; current absence is
=capability-unconfirmed=, not a pass, product failure, or repository finding.
