#+title: Addendum 3: Canonical Context with Warm Prefix Reuse
#+date: 2026-08-26
#+startup: overview

* Status

In-progress.

This addendum corrects the performance objective used by Addendum 2.  The
Feature 88 semantic lifetime model remains authoritative: observations are
runtime-only, consumer-bound, visible to the matching invocation, promotable
through the core-owned validation path, and absent from later context unless
selected information was promoted.

Where this document conflicts with Addendum 2's clean-anchor branching,
connection-local retention, request-size performance contract, or acceptance
criteria, this document supersedes Addendum 2.  For every profile adopting
=F88A3-LAYOUT=, this addendum also supersedes the first addendum's
current-state/dynamic-context =request-local-replaceable= claim and its
top-level-instructions wire contract.  Profiles that retain that proven wire
contract remain governed by the first addendum.

Implementation is not authorized merely because this plan exists.  The
=docs/feats/index.org= entry remains the compact status authority.

* Goal

Make correct canonical context reconstruction with a warm provider prefix the
ordinary Feature 88 path.  The performance goal is provider-reported
prefix-cache reuse for canonical requests with a long common prefix and a short
changing frontier.  Reducing serialized bytes or input-item count is an
explicit non-goal.

Delete complexity whose only justification was smaller wire requests:
Addendum 2's historical response graph, eviction history, Codex-specific
socket retention, older-anchor diagnostics, and byte-size acceptance.

* Rationale and corrected vocabulary

Canonical replay submits the complete current semantic context derived from the
session and current runtime frames.  Continuation submits a delta using
=previous_response_id=.  Warm prefill means provider usage reports
=cached_input_tokens > 0= for the declared fixture; cold prefill means a valid
run reports explicit zero.  A stable prefix is the longest byte- and
order-stable request prefix before the changing frontier.  The frontier holds
current user input, current-state observations, dynamic context, tool output,
and other request-local material expected to change.

Do not use =full replay= as a synonym for cache miss.  A canonical replay can
have a warm prefill.  The intended shape is:

#+begin_example
request 1: [stable A B, frontier C]
request 2: [stable A B, frontier D]

desired provider work:
  [cached A B] [uncached D]
#+end_example

Provider caches may retain obsolete prefixes or tool-descended state.
=F88A3-SEM= evaluates local semantic context and the literal next request, not
provider cache contents.  Socket retention is a resource policy rather than
cache correctness.  =F88A3-CLEANUP= restores the general idle-close policy; a
replacement socket is not a cold prefill without provider usage evidence.
Public named streams may support response-chain forks, but =F88A3-COMPAT= keeps
them outside this package because wire reduction is not a semantic need.

* Delivery and continuation design

For every Responses profile adopting =F88A3-LAYOUT=, current-state and
dynamic-context observations are rendered as late developer-role input and are
therefore inherited under =previous_response_id= continuation.  The adapter
must resolve those kinds to =inherited= for that effective profile identity.
The =request-local-replaceable= claim remains valid only for a profile that
keeps the complete current observation in top-level instructions.

An observation-bearing response and every contaminated descendant are
immediate-followup-only and must not become durable cross-turn anchors.  The
existing linear continuation path remains available for the latest
tool-producing response and its matching function-call output, because
inheritance is required within that one successful turn.  A later ordinary
request uses canonical reconstruction unless a semantically exact clean
continuation with no inherited ephemeral frontier is independently eligible.
No new core capability, provider predicate, or profile-specific harness switch
is introduced.

Stable harness guidance and durable context precede the frontier.  The late
provider item preserves the observation's instruction authority; it does not
demote an instruction to user text.  ChatGPT Codex keeps its stable
session-derived =prompt_cache_key=.  Canonical OpenAI profiles that support an
explicit breakpoint place it at the end of the proven stable prefix.  These are
implementation consequences of =F88A3-LAYOUT= and =F88A3-DELIVERY=, not
additional contracts.

* Evidence baseline, classification, and freshness

The 2026-08-26 exploratory ChatGPT Codex WebSocket probe used a 5,450-token
request with a long stable prefix and a short divergent suffix.  The first
request reported zero cached tokens; the second reported 4,864 cached tokens.
The result repeated after deliberately replacing the socket while retaining
the cache identity.  A separate same-lane experiment could continue only the
latest response; reusing the older response produced
=previous_response_not_found=.  These observations motivated the design but
lack the identity record below and are stale for acceptance.

=F88A3-CACHE= has two separately reportable external scenarios:

1. =chatgpt-canonical-warm-prefix=: the smallest canonical =[A B C] -> [A B D]=
   pair, run once on a retained socket and once after a deliberate replacement
   socket; and
2. =chatgpt-canonical-tool-heavy=: one real tool-producing response, its
   matching immediate function-call-output continuation, and the following
   canonical ordinary request.

Each record contains provider/profile ID, exact base-URL identity, Responses
WebSocket transport, store mode, native requester identity, exact model ID,
prompt-layout revision, prompt-cache-key derivation revision, material request
shape, scenario name, timestamp, repository revision, total input tokens,
cached input tokens, the scenario's predeclared total timeout, elapsed duration,
and result.

Each scenario runner declares its total timeout before sending the first
request.  The timeout is private execution configuration rather than a durable
F88A3 contract number: it bounds evidence collection but does not change the
required provider outcome or capability identity.  A run that does not conclude
before its declared bound is =inconclusive-timeout=.  Every other result retains
the failure classification below.

The freshness window is seven calendar days.  Reuse is allowed only when every
identity field and material request shape match and no affected adapter,
projection, capability, cache-key, or scenario owner changed.  Evidence older
than seven days is stale; any endpoint, model, protocol, or layout change makes
it stale immediately.

A valid second request with =cached_input_tokens > 0= is =current= or
=reusable= external success.  Explicit zero without identity change, expiry,
or declared invalidation is =product-contract-failure=.  Missing usage is
=unavailable=.  Authentication/configuration failure,
provider/infrastructure failure, and bounded timeout retain distinct statuses
and do not become product findings.

Deterministic gates prove literal canonical context, stable-prefix byte/order
equality, authority-preserving frontier role, stable cache identity, breakpoint
placement, semantic disappearance, promotion, continuation lifetime, retry
convergence, and targeted cleanup.  They do not require credentials.

Cached-input ratio, provider latency, and live warm/cold frequency are
observational telemetry.  The historical 4,864/5,450 result is an observational
baseline, not a percentage gate.  The package may reach
=deterministic-fixed-point= while external execution is unavailable, but
remains =capability-unconfirmed= and is not =Done= until both initial external
scenarios are =current= or =reusable=.  A valid =product-contract-failure=
returns =F88A3-CACHE= to design or remediation.

| Freshness field | Record |
|-----------------+--------|
| Correctness role | private endpoint/cache behavior can drift independently of repository code |
| Workload basis | two fast bounded scenario pairs per review window; no long-idle wait |
| Resource estimate | a small fixed number of credentialed requests |
| Exact/one-over consequence | age at or below seven days with matching identity may be reused; older evidence is stale |
| Revision trigger | measured endpoint stability or materially changed execution cost may justify revising the window |

* Scope and non-goals

The package implements =F88A3-SEM= through =F88A3-COMPAT=.  It moves changing
OpenAI context to the frontier, makes delivery capability truth match the new
wire layout, preserves immediate tool continuation, measures cached-token
reuse, and removes the narrow Addendum 2 optimization cluster.

It does not reduce wire size, add arbitrary ChatGPT branching, introspect or
delete provider caches, discover capabilities at runtime, add generalized
response graphs, change the promotion schema, redesign compaction, introduce a
socket lifecycle framework, add crash recovery or interim persistence ahead of
Feature 87, or change presentation.

* Implementation slices

** Slice 1: Stable-prefix and frontier projection

Establish =F88A3-LAYOUT= and =F88A3-DELIVERY=.  Change the affected profile's
capability truth and adapter projection together.  Use literal request and
anchor-safety evidence from =stable-prefix-frontier-pair=.

** Slice 2: Canonical tool-heavy loop

Establish =F88A3-SEM= and =F88A3-TOOL=, and confirm the inherited
=F88A3-PROMOTION= contract.  The observable boundary is a complete
tool-producing turn followed by a canonical ordinary request.

** Slice 3: Remove obsolete continuation machinery

Establish =F88A3-CLEANUP= while preserving =F88A3-COMPAT=.  Delete the
historical ChatGPT response ledger, eviction history, older-anchor branches and
diagnostics, Codex-specific 600-second idle override, and directly dead helpers.
Retain only immediate causal response state, one safe canonical retry, and the
general socket resource policy.

** Slice 4: Cache acceptance and documentation

Complete deterministic evidence for all rows, add the two separately reported
external scenarios for =F88A3-CACHE=, update =limitations.org= and
=docs/architecture.md=, and run focused and repository gates.

* Compatibility and migration guidance

=F88A3-COMPAT= introduces no session schema migration.  Persisted ChatGPT
provider-anchor records may remain in historical JSONL sessions but must be
ignored by the new cross-turn policy.  Do not add cleanup transactions or
compatibility shims for already-open connections.

Canonical OpenAI profiles may retain stored-response, compaction, or branch
behavior with an independent semantic consumer.  They must not force ChatGPT
to retain an unusable response graph.

* Risks and responses

- A wire-only move would leave false replacement capability and dirty anchor
  admission.  Change =F88A3-LAYOUT= and =F88A3-DELIVERY= together.
- Moving current state later could change instruction authority.  Preserve its
  provider role and prove it in literal request bodies.
- Provider cache retention can expire.  Keep semantic gates independent and
  report external cache status with identity and freshness.
- Deleting historical state could break the immediate tool follow-up.  Retain
  the causal path and prove both completion orderings plus canonical retry.
- Tests can inherit earlier provider cache state.  Use a unique identity for
  each cold baseline and share it only within its intended warm pair.

* Architecture self-check

1. If this package stopped here, Feature 88 would keep correct ephemeral
   context while pursuing measured prefix-cache reuse through a simpler path.
2. The direction is canonical semantic context plus provider-agnostic stable
   prefix policy, with cache mechanics confined to adapters.
3. Observation lifetime, promotion provenance, and session ownership are
   stable; private cache behavior is external and renewable.
4. Core owns lifetime and promotion, session owns durable meaning, harness owns
   composition, and the adapter owns request layout and immediate response
   availability.
5. The package reduces coupling by deleting the response graph, eviction
   diagnostics, timer plumbing, and older-anchor composition.
6. Stable policy does not depend on ChatGPT internals; adapter capability truth
   flows through the existing backend contract.
7. Provider connection, retry, and cache side effects remain in the adapter.
8. No durable state is added; immediate response state has turn/socket lifetime
   and provider cache state is external.
9. Canonical replay can transmit more bytes, but provider work is the measured
   objective and deterministic semantics do not depend on cache behavior.
10. =request-local-replaceable= remains semantically real only where the full
    observation is actually replaced rather than inherited.
11. Historical records remain readable and ignored where ineligible; no shim
    or migration is introduced.
12. The historical ledger, eviction history, older-anchor diagnostics,
    Codex-specific retention, and wire-size tests become removable.
13. One canonical retry handles expected continuation loss; unexpected
    projection, transport, and provider errors remain visible.
14. Contract tests protect semantics and ownership; obsolete mechanism tests
    are replaced or deleted according to the appendix.
