* Tick 01 findings

** P1 F88.I1.1: cross-generation observations can enter a projection

The projector checks record types but not that the frame's =generation-id=
matches the active generation.  A stale frame can therefore place an old
observation inside a new generation.

*** Owning correction

Reject mismatched generation/frame pairs at the pure projector boundary and add
a negative projector contract test.

** P1 F88.I1.2: malformed lifetime records survive replay

Replay normalizes wire strings but bypasses the append validator, and append
validation covers only a subset of required fields.  A frame with no generation
and an unknown state can enter resume state instead of surfacing corruption.

*** Owning correction

Use one strict validator for append and replay.  Validate plist shape, record
version/type, required identities, lifecycle state/status, and generation
ownership.  Resume reduction must reject a frame without one active matching
generation.

** P2 F88.I1.3: projection fingerprints are not restart-stable

Fingerprints hash raw printed Lisp values while JSON replay changes nested
symbols such as roles into strings.  Identical logical context can therefore
change its fingerprint and adapter-facing representation after restart.

*** Owning correction

Define one canonical provider-neutral persisted representation and fingerprint
it.  Prove exact projection and fingerprint equality across persistent replay.

** P2 F88.I1.4: settlement acknowledgement is store-global

The acknowledgement helper ignores its session on the success path and calls
the global session finalizer.  One frame can scan or wait on unrelated dirty
sessions, violating prefix-proportional work and placing session side effects in
lifetime policy.

*** Owning correction

Add a session/prefix-specific asynchronous durability barrier at the session
boundary and leave harness/loop orchestration to call it.  A controlled-writer
test with two dirty sessions must prove only the named prefix gates progress.

** P1 F88.I1.5: absence of an outbox mapping can be mistaken for acknowledgement

A context append mutates and indexes the live session before writer-command
preflight.  If preflight rejects the command, the entry remains known but has no
outbox mapping.  The barrier currently treats no mapping and no cached failure
as already durable.  Failure-cache eviction creates the same ambiguity.

*** Owning correction

Track authoritative per-entry durability at the session/persistence boundary,
or make submission transactional.  The barrier succeeds only for explicit
acknowledgement, remains pending for an active command, and fails for preflight
or terminal failure.  Absence of a mapping is never positive durability
evidence, and bounded cache eviction must not turn failure into success.

- Focused lifetime/persistence tests remained 47/47 green, demonstrating the
  missing partition rather than contradicting the finding.
- Worktree remained clean; no approval, edit, runtime mutation, or live Emacs
  interaction occurred.

** P1 F88.I1.6: a stale command response can settle a superseded record barrier

The persistence state update ignores a response whose command is no longer
current for the logical record, but callbacks attached by an earlier barrier
still run unconditionally.  A record can be resubmitted under a new command,
then a stale success or failure from the old command incorrectly settles the
barrier while the authoritative command remains active.

*** Owning correction

Bind every barrier callback to its record key and expected command identity.
Before success or failure, verify that command remains authoritative.  A
superseded response must neither satisfy nor fail the logical-record wait;
rebind to the current command or fail closed through an explicit superseded
state.  Add controlled stale-success and stale-failure tests for same-key
replacement.

** P1 F88.I1.7: rejected replacement does not fence its predecessor

A same-key replacement sets the logical record to =pending= before preflight,
but preflight rejection changes only the state to =preflight-failed=.  The old
command remains mapped as current.  Its later success may therefore overwrite
the newer failed attempt with =acknowledged=, and the active logical watcher
incorrectly completes the barrier for the rejected replacement.

*** Owning correction

Advance logical-record attempt ownership before replacement preflight.  A
rejected replacement must terminally reconcile active logical watchers and
fence every predecessor response from changing the newer attempt's state.  The
old physical command may still complete its own callback and outbox lifecycle,
but it must not satisfy or overwrite the newer logical record state.  Add stale
success and stale failure predecessor tests after replacement preflight
rejection.
