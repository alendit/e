* Findings

** TODO High P1 =F88A7.S1=: the proposed schema revision is already Addendum 6's identity

Contract cell: =F88A7-IDENTITY=.

Observed fact: Addendum 7 says the fourth key advances =context-curate-v3= to
=context-curate-v4= and later asks evidence to refresh under =v4=
(=addendum7.org:213-220,270-275,305-308=).  Current core already defines
=e-context-lifetime-curation-schema-revision= as =context-curate-v4=, and its
owner test asserts that literal identity
(=lisp/core/e-context-lifetime.el:73-80=;
=test/e-context-lifetime-test.el:790-799=).  The current OpenAI carrier still
has only keep, summaries, and drop (=lisp/adapters/openai/e-openai.el:1631-1668=).

Consequence: following the specification would change the wire schema without
changing its material revision.  Existing anchor and cache identities could be
accepted for an incompatible carrier, directly contradicting the proposal's
invalidation rule.

Minimal correction: replace every Addendum 7 =context-curate-v4= target with
=context-curate-v5= and replace “advances from =context-curate-v3=” with
“advances from the implemented =context-curate-v4= identity.”  Feature 90 and
Feature 88 link text should refer to =F88A7-IDENTITY= rather than copy the
literal revision.

Acceptance evidence: literal core and adapter identity tests, HTTP and
WebSocket request bodies, anchor mismatch tests, captured request identity, and
all Addendum 7 external records agree on =context-curate-v5=.  Addendum 6
=v4= records remain historical and are not reusable.

** TODO High P1 =F88A7.S2=: two independent session appends cannot satisfy mixed-curation atomicity

Contract cells: =F88A7-ATOMIC= and =F88A7-DURABLE=.

Observed fact: the proposal requires a mixed curation to append a version-3
promotion and a version-1 erasure, then states that failure in either append
makes no partial curation visible (=addendum7.org:186-193,255-261,301-302=).
The current harness appends at most one promotion through
=e-session-append-context-curation= before consuming the frame
(=lisp/core/e-harness.el:3268-3312=).  Session persistence accepts and writes one
record at a time (=lisp/core/e-session.el:640-649,873-890=), while checkpoint
and replay dispatch each record independently
(=lisp/core/e-session.el:1522-1543,2200-2242=).

Consequence: adding a second ordinary append leaves a concrete failure window.
If the first semantic record persists and the second append fails or replay
sees only the first, reopen exposes a partial curation even though the frame was
not validly consumed.  Reversing append order only reverses which half leaks.

Minimal correction: replace =addendum7.org:186-193= with:

#+begin_quote
Core prepares one detached curation package containing an optional version-3
promotion component and an optional version-1 erasure component.  Session
accepts that package through one atomic commit boundary and makes both semantic
components visible and durable together or neither visible.  Persistent direct,
queued, controller-backed, checkpoint, and replay paths encode one commit unit;
they must not implement a mixed curation as two independent record appends.
Validation, write, flush, or replay failure leaves both semantic projections
absent and the frame unconsumed.  The inherited audit-only response-control
rule remains separate and cannot commit either semantic component.
#+end_quote

The implementation appendix may select a compound journal record or explicit
transaction envelope, but must preserve the two semantic codec identities and
one session-owned commit boundary.

Acceptance evidence: test keep+erase and summary+erase across direct, queued,
and controller-backed persistence; inject failure before and between component
publication; truncate or reject replay before commit; reopen/checkpoint after
each failure; and prove both-or-neither semantic visibility, no frame
consumption, and a clean retry.

** TODO Medium P2 =F88A7.S5=: erasure visibility is not defined for selected heads, siblings, and clean forks

Contract cell: =F88A7-DURABLE=.

Observed fact: the proposal says erasure “survives branch selection” and exposes
a canonical erased-tool-call query, but does not say which selected head the
query uses or what a sibling branch and clean fork inherit
(=addendum7.org:175-184,246-253,299-300=).  Current semantic projection is
explicitly current-path/head scoped (=lisp/core/e-session.el:3202-3213,3238-3272=),
and a clean fork rebuilds portable meaning without copying source-session
anchors or curation controls (=lisp/core/e-session.el:3016-3088=).

Consequence: an implementation that scans all session erasure records can
suppress a receipt on a sibling whose selected path predates the erase.  An
implementation that drops every erasure at checkpoint or fork can let a copied
eligible derived projection reappear.  Both satisfy the current vague wording.

Minimal correction: insert under Durable erasure authority:

#+begin_quote
The erased-tool-call query is evaluated for a session and selected head.  An
erasure is effective only when its committed record lies on that head's
canonical path and its generation/subject remains eligible for an automatic
projection.  A sibling head before the erasure does not observe it; a descendant
head does.  Checkpoint and compaction preserve the erasure and its inherited
response-audit dependency while the subject remains eligible.  A clean fork
copies neither receipt nor erasure when it copies no eligible derived
projection; if a future fork contract copies such a projection, it must carry
equivalent suppression authority in the same portable boundary.  Never apply a
session-global erasure set across unrelated branches.
#+end_quote

Acceptance evidence: selected-head before/after, sibling, descendant, clean
fork, 63/64 audit-tail boundary, checkpoint reopen, compaction, and safe-prune
tests agree on exactly one path-scoped identity set.

** TODO Medium P2 =F88A7.S7=: the new 8,192-byte erasure-package limit lacks its own justification

Contract cell: =F88A7-DURABLE=.

Observed fact: Addendum 7 makes 8,192 canonical UTF-8 bytes a separate normative

(=addendum7.org:92-101,169-173,238-244,285-287=).  Addendum 4 justifies 8,192

provenance (=addendum4.org:238-253=).  Addendum 7 supplies no erasure workload

label-only tool frames.

Consequence: a large live frame can be completely disposable but impossible to
erase for an unexplained identifier-package threshold.  Tests at 8,192/8,193
would freeze the number without proving that it bounds the right workload.

Minimal correction: either classify the byte cap as an implementation default
until measured, or add this complete justification beside the normative limit:

#+begin_quote
The erasure-package limit is a distinct resource ceiling.  Record the maximum
representative tool-source fan-out, measured canonical bytes at that workload,
per-record and per-session storage/query cost, exact-limit acceptance and
one-over rejection, and the consequence when an otherwise valid complete erase
does not fit.  Revise the limit only with new workload evidence and update the
schema identity, boundary tests, and cache-evidence identity together.  The
Addendum 4 retained-value measurement alone does not justify this cap.
#+end_quote

Until those measurements exist, exact-limit justification is a required
unknown and the 8,192 value cannot be a stable acceptance contract.

* Architecture review

The intended ownership is sound: core decides semantic erasure, session owns
path-scoped durability, harness owns orchestration, the adapter owns the wire
carrier, and Feature 90 owns receipt projection.  The current proposal does not
yet preserve that direction as a useful package.  Slices 1--3 would add durable
state, schema migration pressure, and future coupling without a consumer, while
the actual adapter exposure is unowned.  This is a current package-boundary
finding, not a deferrable architectural follow-up; no follow-up ledger was
created or changed.

The smallest non-speculative direction is one dependent package whose internal
Feature 88 preparation remains hidden until the real Feature 90 receipt
consumer exists, followed by one explicit carrier-exposure slice and composed
acceptance.  That keeps Feature 90 from parsing curation or writing erasure
records and keeps Feature 88 from owning receipt ordering or aggregation.
