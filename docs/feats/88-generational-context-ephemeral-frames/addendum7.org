This post-rebase addendum extends Feature 88's accepted Addendum 6 contract.
Feature 88 remains =In-review= with configured Responses HTTP evidence

* Decision

Add an explicit =erase= disposition to Feature 88 context curation for an
ephemeral tool-result source that must leave no source-derived value in later
automatically assembled model context.

Addendum 6 already requires the reserved carrier to contain exhaustive
=:keep=, =:summaries=, and =:drop= arrays.  This addendum extends and
supersedes Addendum 6 only where needed to add =:erase= as a fourth required
disposition.  Every presented label is assigned exactly once across the four
arrays.  Addendum 4's provider-neutral presentation, provenance, atomicity,
durable version-3 promotion record, and compatibility foundations remain
authoritative; this addendum does not reopen or replace them.

Erasure is a model-context decision, not deletion.  Transcript entries,
durable activity history, session-scoped temporary details, and provider audit
state remain unchanged.  A later explicit read of that stored history is a new
observation; it does not make the erased source part of ordinary context again.

Feature 90 owns invocation receipts and temporary details.  Feature 88 owns
the erasure authority and a narrow query for erased tool-call identities.
Feature 90 may consume that query when its planned receipt projection exists,
but no Feature 90 projection proof is claimed by this addendum.

* Why drop is no longer sufficient

Addendum 6's =drop= disposition removes the exact ephemeral source while
permitting a separately owned derived projection, such as a Feature 90
invocation receipt.  That behavior is useful by default, but =drop= cannot
express "leave no source-derived mark in later model context."

=erase= restores that explicit choice.  It suppresses the derived context
projections whose evidence is the erased tool source while leaving transcript,
audit, and temporary-resource storage intact.  There is no omission or
implicit-disposition semantics in the current carrier: all four disposition
keys are required, although any individual array may be empty.

* Model-facing contract

The reserved =context-curate= effect accepts exactly the required keys =keep=,
=summaries=, =drop=, and =erase=.  All four values are arrays and may be empty.
Unknown or omitted keys remain invalid.  This is the only model-facing shape
change from Addendum 6.

#+begin_src json
{
  "keep": [1],
  "summaries": [
    {"sources": [2], "text": "The retained semantic conclusion."}
  ],
  "drop": [],
  "erase": [3]
}
#+end_src

=erase= is an ordered array of positive integer frame-local source labels.
Every erased label must identify an ordinary tool-result source in the active
consumer-bound frame.  Erasing a non-tool source is invalid because its exact
value is already removed by =drop= without a tool-derived receipt projection.
The model submits only frame labels; core derives the tool-call identity and all
durable provenance.

A source has at most one disposition:

- =keep= retains its exact bounded model-visible value;
- a =summaries= entry retains submitted replacement text;
- =drop= removes the exact source but permits a separately owned derived
  projection;
- =erase= removes the exact source and suppresses source-derived automatic
  projections.

The four arrays must form one non-empty, duplicate-free, complete partition of
the labels presented by the live frame.  Labels may not overlap across =keep=,
any summary's =sources=, =drop=, and =erase=.  Unknown, repeated, missing,
overlapping, or non-tool erase labels reject the entire curation before durable
or frame mutation.

At most 16 labels may be retained across =keep= and
=summaries[*].sources=.  =drop= and =erase= have no independent retained-label
ceiling; each is bounded by the number of labels in the live frame.  The
stable erasure resource contract is that an erase-containing curation is
bounded by a measured committed ceiling over the complete canonical UTF-8
version-1 erasure record/package.  An implementation may use a local,
non-normative, reversible 8,192-byte default while measuring, but that number
is not the acceptance contract.  Before carrier exposure, the implementation
must measure representative maximum tool-source fanout, canonical bytes at
that workload, per-record and per-session storage/query cost, exact-limit
acceptance and one-over rejection, and the consequence when an otherwise-valid
complete erase does not fit.  The measured ceiling, tests, and material
identity must then be committed together.  The existing version-3 promotion
record retains its separate measured/accepted bound over exact values and
summary text; Addendum 4's retained-value measurement alone does not justify
the erasure ceiling.  Neither bound copies dropped or erased source bodies.

The carrier-local guidance remains concise and schema-directed.  After using
presented ephemeral context sources, the model calls the carrier once to
partition every presented label exactly once: =keep= retains an exact value,
=summaries= writes a compact durable replacement, =drop= removes the source
while allowing a separately owned derived projection, and =erase= removes an
ordinary tool-result source with no source-derived automatic projection.  Stable
instructions, source markers, and generic narration do not change.

* Erasure semantics

For each successfully erased tool source, every later ordinary model-context
projection excludes:

- the tool call and its arguments;
- the tool result and result metadata;
- any Feature 90 invocation receipt;
- the stated purpose;
- the temporary details URI; and
- any count, summary, latest-item marker, or other aggregate whose only evidence
  is the erased source.

A source assigned to =drop= has the same exact-source exclusion but may retain
a separately owned receipt or other derived projection.  The distinction is
the semantic purpose of =erase=.

The source remains available during the provider invocation that consumed it.
Erasure cannot retroactively alter an already-sent request or the immediate
tool-result continuation that made the decision possible.

Erasure does not delete or rewrite:

- transcript tool-call or tool-result entries;
- durable tool activity records;
- temporary invocation-details resources;
- provider audit or replay metadata retained under its independent transport
  lifetime; or
- user-visible shell history.

Consequently, "completely" means complete absence from automatically assembled
future model context.  It does not mean storage destruction or audit erasure.

An explicit later transcript, activity, session-resource, or =tmp://= read may
surface the stored details again.  The read result is a new ephemeral
observation with its own Feature 88 lifetime and does not revoke the original
erasure record.

* Durable erasure authority

Core prepares one durable version-1 =context-erasure= record for a successful
curation that contains erased sources:

#+begin_src emacs-lisp
(:record-version 1
 :type context-erasure
 :id ERASURE-ID
 :frame-id FRAME-ID
 :generation-id GENERATION-ID
 :consumer-request-id CONSUMER-ID
 :response-entry-id RESPONSE-ID
 :sources
 ((:source-observation-id OBSERVATION-ID
   :source-ref SOURCE-REF
   :source-fingerprint SOURCE-FINGERPRINT
   :tool-call-id TOOL-CALL-ID)))
#+end_src

The record contains no source value, arguments, result, purpose, receipt,
temporary URI, provider item, replay envelope, or backing object.  Core derives
every identity from the matching live frame; the model cannot submit durable
identifiers.  The complete canonical version-1 record/package is subject to the
measured committed erasure-package ceiling above.

=context-erasure= is semantic suppression authority, not transcript content or
an activity event.  It has no direct model-visible projection.  Feature 88
context providers query the canonical session projection for erased tool-call
identities and exclude matching derived values.

The record survives reopen, branch selection, checkpointing, and compaction for
as long as a matching derived projection could otherwise reappear.
Implementations may prune an erasure only after proving that no eligible
context projection can reference its subject.  They must not infer safety
merely from temporary-resource expiry.

The erased-tool-call query is evaluated for a session and its selected head.
An erasure is effective only when its committed record lies on that head's
canonical path and its generation/subject remains eligible for an automatic
projection.  A sibling head before the erasure does not observe it; a
descendant head does.  Checkpoint and compaction preserve the erasure and its
inherited response-audit dependency while the subject remains eligible.  A
clean fork copies neither receipt nor erasure when it copies no eligible
derived projection; if a future fork contract copies such a projection, it must
carry equivalent suppression authority in the same portable boundary.  Never
apply a session-global erasure set across unrelated branches.

When one curation contains exact, summary, drop, and erase dispositions,
preparation validates all of them before mutation.  Core prepares one detached
curation package containing an optional version-3 =context-promotion=
component and an optional version-1 =context-erasure= component.  Session
accepts that package through one atomic commit boundary and makes both semantic
components visible and durable together or neither visible.  Persistent direct,
queued, controller-backed, checkpoint, and replay paths encode one commit unit;
they must not implement a mixed curation as two independent record appends.
Validation, write, flush, or replay failure leaves both semantic projections
absent and the frame unconsumed.  The inherited audit-only response-control
rule remains separate and cannot commit either semantic component.  A
drop-only effect appends no promotion or erasure semantic record, consistent
with Addendum 6, while its existing audit/control behavior remains intact.

* Receipt integration boundary

Feature 88 can implement the version-1 erasure authority and its narrow
canonical erased-tool-call query without importing Feature 90 or generating
receipts.  Feature 90's planned receipt provider is the only consumer that may
turn that query into receipt filtering.

=F88A7-F90-JOIN= is accepted only by the Feature 90 model-context projection
contract.  Feature 88 supplies the path-scoped erased-tool-call query defined
by =F88A7-DURABLE=; it does not restate Feature 90's receipt ordering,
budgeting, aggregation, or rendering policy.  Feature 90 does not parse
=context-curate=, derive erasure identities, write =context-erasure= records,
or decide whether erasure is allowed.

Slices 1--3 below are internal preparation slices, not an independently
shippable Feature 88 package.  Feature 88 must not expose =erase= in a backend
carrier or claim the Addendum 7 package accepted until a real eligible derived
projection consumer exists.  When Feature 90's receipt provider is ready,
Feature 88 first accepts the provider-neutral codec/query and atomic session
boundary, then adds a distinct carrier-exposure slice with concise guidance,
the strict HTTP and WebSocket schema, =context-curate-v5= identity, and
literal adapter tests.  The final package stopping point includes the real
Feature 90 consumer and a drop-versus-erase composition; no speculative
fixture satisfies it.

* Provider, reasoning, and cache identity

Adding =erase= changes the reserved =context-curate= schema.  The material
schema revision therefore advances from the implemented =context-curate-v4=
identity to =context-curate-v5=.  Existing anchors and cache evidence recorded
against the Addendum 6 shape are not valid evidence for this shape.  The durable
=context-promotion= record remains version 3, and the new
=context-erasure= record is version 1.

Every OpenAI Responses request still carries its effective reasoning effort and
=:summary= value, =auto= or =detailed=, as required by Addendum 6.  Returned
reasoning summaries remain diagnostic only and never authorize or prove an
erase decision.  The material prompt/layout, tool-schema, continuation, and
captured-request identities include the new schema revision; per-frame labels,
values, erase contents, and internal IDs do not enter those stable identities.

The current configured Responses HTTP reasoning-summary, positive exact/drop,
and cache records are valid for the Addendum 6 identity only.  They are not
evidence that the configured provider supports =erase= until the Addendum 7
schema is implemented and the scenarios are refreshed.  The exact built-in
ChatGPT/WebSocket carrier, continuation, and retained/replaced-socket scope
remain capability-unconfirmed and unexercised.

* Implementation slices

** Slice 1: pure erase preparation (internal)

Extend the core curation normalizer and preparation logic with the required
=erase= array.  Validate all four keys, the complete live-frame partition,
tool-source eligibility, exclusivity, and the 16-label retained bound without
mutating frame or session state.  Keep core-derived provenance detached and do
not copy dropped or erased bodies.  The erasure-package ceiling is the measured
committed resource bound described by =F88A7-DURABLE=, not an Addendum 4
retained-value limit.

** Slice 2: durable erasure record and query (internal)

Add the version-1 =context-erasure= codec, session append/replay, branch,
checkpoint, compaction, and retention behavior.  Expose only the narrow
canonical erased-tool-call query needed by the real Feature 90 receipt
provider; do not implement its receipt projection or add a speculative shared
interface.  Existing version-3 promotion records and their readers remain
unchanged.

** Slice 3: atomic curation application

Join promotion, drop, and erasure preparation at the existing
provider-completion boundary.  Prove keep-only, summary-only, drop-only,
erase-only, mixed valid, mixed invalid, append failure, and duplicate-effect
behavior.  A successful mixed effect commits all applicable semantic records
through the one session-owned commit package before frame consumption and later
provider dispatch.  Direct, queued, controller-backed, checkpoint, and replay
paths must make the package visible together or not at all.

** Slice 4: Feature 90 consumer and carrier exposure

After Feature 90 supplies its real receipt consumer, connect the path-scoped
query and prove its drop-versus-erase composition.  Then expose =erase= through
the concise reserved carrier, strict literal HTTP and WebSocket adapter paths,
and the =context-curate-v5= material identity.  Preserve transcript, activity,
temporary details, and ordinary drop receipts exactly.  Feature 88 alone cannot
claim this projection proof.

** Slice 5: end-to-end and cache evidence

After deterministic implementation, the Feature 90 dependency, and the carrier
exposure are ready, run one isolated ordinary-drop turn and one explicit-erase
turn.  Refresh the =context-curate-v5= material identity and configured cache
evidence.  Keep Addendum 6 records as historical baseline and report exact
ChatGPT/WebSocket capability separately.

* Acceptance criteria

- =F88A7-DISPOSITION= requires all four keys and one non-empty complete,
  duplicate-free partition; keep, summary, drop, and erase are mutually
  exclusive, and erase labels are ordinary tool-result labels only.
- =F88A7-DISPOSITION= retains at most 16 labels across keep and summary
  sources; drop and erase are bounded by the live frame.
- =F88A7-ERASURE= removes every automatic source-derived projection for erase,
  while transcript, durable activity, shell history, provider audit, and
  temporary details remain inspectable; an explicit later read is new context.
- =F88A7-DURABLE= contains only core-derived identity/provenance, is
  current-path scoped, survives eligible reopen/branch/checkpoint/compaction,
  and is bounded by a measured committed erasure-package ceiling.
- =F88A7-ATOMIC= commits optional version-3 promotion and version-1 erasure
  components together or neither before frame consumption and later dispatch.
- =F88A7-F90-JOIN= is not accepted until the real Feature 90 consumer exercises
  the query before its own bounds and aggregates; drop retains its receipt and
  erase suppresses it.
- =F88A7-IDENTITY= requires =context-curate-v5= to invalidate Addendum 6-era
  anchors/cache evidence while preserving mandatory Responses reasoning
  summary and separate HTTP/WebSocket capability decisions.
- Provider continuation and anchor cleanliness remain conservative; erasing a
  later projection does not make a tool-contaminated response a clean anchor.

* Non-goals

- Deleting transcript, activity, temporary resources, or provider audit state.
- Providing a model-controlled privacy or audit-erasure operation.
- Changing exact keep, summary, or exhaustive drop semantics.
- Treating a missing disposition as drop or erase.
- Making erased tool descendants eligible as clean provider anchors.
- Adding an erasure option to ordinary tools or Feature 90's invocation
  envelope.
- Owning Feature 90's receipt-projection policy in Feature 88; the final
  package depends on the real Feature 90 consumer while keeping its
  implementation in Feature 90.
- Adding a second model-facing tool, durable promotion shape, or automatic
  retention/drop policy.

* Design self-check

   way to leave no source-derived mark in later model context.
2. It moves toward explicit, provenance-backed context lifetime without
   conflating context projection with transcript storage.
3. Erasure semantics and provenance are stable.  Retention pruning remains
   local and conservative until a real safe condition is proven; the stable
   resource contract is a measured committed ceiling, with any provisional
   numeric default local and reversible.
4. Feature 88 owns the decision because it owns semantic context lifetime;
   Feature 90 only consumes the result after its planned consumer exists.
5. The interface is one additional curation disposition and one narrow erased
   identity query, not a tool-specific callback or speculative cross-feature
   interface.
6. Core policy does not depend on a provider adapter, receipt renderer, shell,
   transcript store, or temporary-resource implementation.
7. Transcript and resource side effects stay with their existing owners; pure
   curation preparation remains side-effect free.
8. Erasure adds only bounded suppression provenance.  Full details stay at
   their existing transcript and temporary lifetimes.
9. Receipt filtering adds bounded identity lookup per candidate only after the
   Feature 90 consumer exists; the erasure ceiling is measured against
   representative fanout, canonical bytes, and storage/query cost before
   carrier exposure.  Cache evidence is refreshed because schema shape changes,
   not because wire size is an objective.
10. =erase= has one substitutable meaning: no source-derived automatic future
    model context.
11. Existing version-2 and version-3 promotion records remain readable.  New
    erasure records are additive and do not reinterpret stored history.
12. No existing transcript or temporary-detail path is removed.
13. Invalid erasure fails through the existing curation boundary; unexpected
    append, replay, or projection errors surface visibly.
14. Pure preparation, session codec, atomic harness, real Feature 90 receipt
    composition, carrier exposure, and E2E tests isolate the changed
    contracts; the final package cannot stop at an internal-only slice.
