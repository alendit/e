* Findings

** TODO Medium P2 =F88A9.S1=: accepted-package scope is contradicted by broader “every decision” wording

Contract cells: =F88A9-PROJECTION=, =F88A9-LANGUAGE=,
=F88A9-ORDERING=, and =F88A9-PRESERVATION=.

The authoritative data contract attaches =:curation= only when a curation
package was accepted and requires a positive keep, summarized, or erased count
(=addendum9.org:82-101=).  Addendum 7 nevertheless accepts all-label omission
while storing no promotion, erasure, or package (=addendum7.org:62-69=).
Surrounding Addendum 9 prose says “every successfully committed curation” and
“each accepted frame decision,” which can be read to include that package-free
case.  Current preparation confirms that the case returns nil package and zero
retained/erased counts (=lisp/core/e-context-lifetime.el:974-1042=).

Make the scope uniformly “successfully committed non-empty curation package.”
State that no-call, failed preparation, and valid all-label omission produce no
=context-curated= activity.  Retain the current all-empty real-adapter scenario
as negative preservation coverage rather than acceptance of Addendum 9.

** TODO High P1 =F88A9.S2=: the numbered implementation steps are not a bidirectionally complete delivery package

Contract cells: all nine Addendum 9 contracts.

=* Implementation package= contains seven numbered steps but has no stable
package identity, contract-to-package relation, entry or closure state, useful
stopping point, or split/combine tradeoff (=addendum9.org:217-241=).  A partial
core, Board, or one-shell slice could therefore be mistaken for an accepted
package although =F88A9-ACTIVITY= remains unavailable.

Replace the section with one owner-complete package, =F88A9-DP1=, establishing
all nine contract IDs.  Its internal steps may form semantic commits but are
not accepted packages.  The package closes only when the non-empty real-adapter
composition reaches both shells; smaller core, Board, or one-shell packages
leave the goal unavailable, while a larger package would mix Addendum 8,
provider material, or manual controls into unrelated policy.

* Architecture review

The proposed direction matches the accepted Feature 91 architecture:

#+begin_example
context lifetime -> harness activity -> Board runtime -> chat service
                                                    -> classic activity
                                                    -> ModernChat view model -> Rust view
#+end_example

Core does not depend on Board or a shell.  Board does not reinterpret curation
arguments.  Shells consume only the bounded public projection.  Presentation
failure stays outside semantic commit; a process loss before Board publication
remains an explicit limitation rather than a hidden transaction guarantee.

The smallest faithful alternative is the same integrated package.  Reading
private session curation records from a shell would reverse dependency
direction and duplicate semantic policy.  No architecture follow-up ledger is
required before plan remediation.

* Design self-check

1. The complete package is a useful stopping point; the current unmapped steps
   are not yet one.
2. It moves toward observable provider-neutral context lifetime.
3. Styling and prose remain local; package success and safe counts are stable.
4. Context lifetime owns facts, harness completion, Board public activity, and
   each shell presentation.
5. The bounded projection reduces coupling to private session records.
6. No stable policy dependency points toward a provider or UI.
7. Semantic mutation stays inward; publication and rendering stay outward.
8. No semantic state is added; Board activity has its existing bounded life.
9. Work is constant; no scan, polling, redraw, or provider request is added.
10. Counts and =context-curated= have substitutable meanings across shells.
11. Older sessions remain readable; provider/carrier compatibility is unchanged.
12. Synthetic identity-only coverage can be replaced by service evidence.
13. Expected invalid curation keeps the existing failure path; malformed public
    projections fail at their owning adapter or renderer.
14. Owner, real-adapter, shell, Rust, graphical, privacy, and preservation
    evidence can fail narrowly once the portfolio is added.
