* Findings

** P1 F88.10: ordinary terminal results can race the next dispatch

The plan acknowledges =dispatch-started= and manually resolved results, but only
says live tool results are persisted with the next frame.  An asynchronous
append may still be outstanding when the next tool or provider follow-up starts.
A crash can lose a known result after later irreversible work began and replay
the completed call as =outcome-unknown=.

*** Owning correction

A live =finished=/=failed= outcome, provider-linked result, and =frame-opened=
form one ordered terminal prefix.  Acknowledge it before clearing the active
execution or starting any later tool/follow-up.  Failed/withheld acknowledgement
starts nothing.  Live retry resubmits the same record identities; after crash,
absence of an acknowledged terminal prefix yields =outcome-unknown=.

Acceptance needs failed/withheld/successful terminal-prefix partitions and
separate prefix count/bytes, acknowledgement wait, and completion-to-dispatch
metrics.

** P1 F88.11: recovery has no application-service owner after restart

Feature 78 restores durable records, not the old process-local loop callbacks,
tool queue, active request, or follow-up gate.  The plan names no owner that
claims a recovered transition once, blocks new prompts, dispatches provably
undispatched calls, exposes ambiguity, and reconstructs follow-up.

*** Owning correction

=e-session= derives and checkpoints a provider-neutral pending-tool-transition
descriptor with transition/turn identity, consuming response, ordered execution
ids, provider replay linkage, and next durable action.  It contains no callbacks.

=e-harness-resume-pending-transition= is the sole application service.  Session
resume invokes it before accepting a new prompt.  It claims the descriptor in
the active-turn registry, is idempotent on repeated calls, dispatches only
provably undispatched calls, exposes =outcome-unknown= as blocked, and rebuilds
follow-up from durable state after all terminal prefixes are acknowledged.
The public resolver delegates release to this service.  Reconstruction mismatch
fails visibly and leaves the descriptor recoverable.

The E2E must cross the real session-resume route, prove idempotent claims and
blocked new prompts, resolve ambiguity, and observe exactly one rebuilt
follow-up.

** P1 F88.12: a key generator is not an idempotency contract

=:idempotency-key-function= only produces a string.  It does not prove that the
external operation consumes or deduplicates it, nor that the registration after
restart matches the persisted contract.  Its only planned consumer is synthetic.

*** Owning correction

Remove automatic post-=dispatch-started= retry and the key hook from Feature 88.
Every ambiguous execution remains blocked until explicit durable resolution.
A later feature may add retry for a concrete tool whose adapter actually sends a
stable key to a deduplicating operation and persists a versioned contract
identity.
