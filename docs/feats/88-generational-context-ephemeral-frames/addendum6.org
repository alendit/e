#+title: Addendum 6: Explicit Curation Dispositions and Reasoning Summaries
#+startup: overview

* Status

Planned.  This candidate requires an independent specification review before
implementation.

This addendum extends Addendum 5 and supersedes it only where Addendum 5 treats
stronger generic carrier narration or omission as evidence that the model
considered a source.  Addenda 3 and 4 remain authoritative for request layout,
curation durability, continuation, cache evidence, and compatibility except
where this addendum explicitly changes the reserved curation arguments.

* Problem

Addendum 5 made the ephemeral-source marker and reserved carrier description
more explanatory.  A successful positive adoption scenario can show that a
model retained or summarized a source, but a missing curation call is still
ambiguous: the model may have considered the source and rejected retention, or
it may never have noticed the source-lifetime choice.

More generic narration cannot remove that ambiguity and risks restoring
repetitive checkpoint noise.  Reasoning summaries improve diagnostic
visibility, but the API does not expose raw reasoning and a summary cannot
prove what the model considered.  The protocol therefore needs an explicit
negative disposition.

* Evidence boundary

The official OpenAI reasoning guide documents the Responses request shape
=reasoning: {effort: ..., summary: "auto"}=.  It says =auto= selects the most
detailed summarizer available for the model, while summary output is returned
in the reasoning item's =summary= array only when explicitly requested:
[[https://developers.openai.com/api/docs/guides/reasoning#reasoning-summaries][OpenAI reasoning summaries]].

This addendum treats a reasoning summary as diagnostic output only.  It may
explain a model decision, but its absence, wording, or completeness is not
semantic evidence.  A valid structured =drop= disposition is the only new
evidence that the model explicitly evaluated a presented source and chose not
to retain it.

* Decisions

** Request reasoning summaries explicitly

The OpenAI Responses adapter must emit a reasoning object containing both the
selected effort and =:summary "auto"= by default.  An explicit request/profile
option may select ="detailed"= for diagnosis or disable the summary only when a
real provider capability requires it.  The option belongs at the existing
adapter request boundary; it is not a core context-lifetime setting.

The returned reasoning summary remains ordinary provider output handled by the
existing reasoning parser and presentation path.  It must not be searched for
curation vocabulary, copied into the external evidence record, or used to
upgrade =unavailable=, =product-contract-failure=, or =pass=.

** Replace omission semantics with an exhaustive disposition

The reserved carrier arguments become:

#+begin_example
{
  "keep": [1],
  "summaries": [{"sources": [2], "text": "compact durable fact"}],
  "drop": [3]
}
#+end_example

All three top-level keys are required and reject additional properties.  Their
arrays may be empty, but their combined labels must be non-empty and must equal
the complete set of source labels presented with the consumed frame.  A label
may occur exactly once across the three dispositions.  Summary text remains
non-empty and bounded by the existing complete-record limit.

This is intentionally stricter than Addendum 5.  Omitted labels are no longer
silently interpreted as a model decision.  Existing stored version-2 and
version-3 durable records remain readable because =drop= is an input effect,
not a new durable promotion item.

** Keep negative disposition out of durable semantic state

For a drop-only call, core validates the complete partition but prepares no
context-promotion record.  The harness still appends the existing reserved
response control and consumes the frame.  The durable combination “reserved
response control exists, no promotion record exists, matching frame consumed”
is sufficient to distinguish an explicit retain-nothing response without
persisting source labels or model prose.

For mixed calls, only exact and summary items enter the existing promotion
record.  Dropped labels are validated against the live frame and then vanish
with it.  No new session record version, drop ledger, or provider-specific core
state is introduced.

** Separate positive and negative adoption evidence

Keep =responses-autonomous-curation-adoption= for positive exact/summary
retention.  Add =responses-autonomous-curation-drop= in a fresh isolated
session.  Its first prompt may name the ordinary deterministic tool and state
that the result is useful only for the current answer, but it must not name the
reserved carrier, curation, source labels, reasoning summaries, or argument
fields.

The negative scenario passes only when all of the following are true:

1. The ordinary tool runs exactly once and the source-bearing continuation is
   identified causally.
2. That exact continuation carries the reserved schema and explicitly requests
   =reasoning.summary: "auto"=.
3. The model emits one valid drop-only reserved effect covering every presented
   source label.
4. The existing reserved response control and frame-consumed event link to the
   same response, and no durable promotion record is appended.
5. The bounded evidence record reports =adoption-result pass=,
   =adoption-disposition drop=, and contains no prompt, source, summary, model
   output, or authentication content.

No call is =product-contract-failure= for this identity-complete scenario, not
evidence of a negative decision.  Invalid or incomplete partitioning is a
repository semantic failure.  Provider/configuration/timeout outcomes retain
their established unavailable spellings.

* Implementation slices

** Slice 1: Request visibility and strict disposition schema

Add the Responses reasoning-summary option/default at the OpenAI adapter
request boundary.  Replace the reserved carrier's omission semantics with the
required exhaustive =drop= schema.  Advance every material schema/layout
revision affected by those request changes.  Keep the carrier description
concise and schema-directed; do not add repeated generic guidance to stable
instructions, source markers, or ordinary prompts.

** Slice 2: Provider-neutral drop semantics

Extend core argument normalization and frame-bound preparation with the exact
complete-partition invariant.  Represent drop-only preparation without a
semantic record while preserving the existing reserved response control,
atomic commit, and frame consumption.  Retain existing durable record codecs
unchanged.

** Slice 3: Adoption and regression evidence

Update positive adoption for the exhaustive arguments and add the isolated
negative scenario.  Preserve the evidence-integrity remediations from Addendum
5 implementation review: typed timeout cleanup, causal carrier localization,
independent adoption checkpoints, and stage-aware retry cardinality.  Add
content-free explicit-drop classification and reasoning-summary request-shape
checks.  Do not inspect reasoning summary prose.

** Slice 4: Configured validation and ledgers

Rerun positive adoption, negative drop adoption, canonical warm-prefix, and
canonical tool-heavy scenarios against the configured Responses HTTP profile
after all runner and material-identity changes.  Update Addenda 3–6,
=limitations.org=, the E2E guide, implementation review, and feature index with
exact profile-scoped results.  Keep exact ChatGPT/WebSocket status separate.

* Compatibility and cleanup

- Stored version-2 and version-3 promotion records remain readable and retain
  their existing meaning.
- Old provider calls that omit =drop= are rejected after the schema revision;
  no compatibility shim is required because the effect is frame-local and
  model-generated for the current request schema.
- Remove Addendum 5 wording and tests that describe omitted source labels or a
  no-call as an observable negative decision.
- Do not persist reasoning summaries, dropped source labels, a negative-decision
  ledger, or a second curation carrier.

* Non-goals

- Exposing raw chain-of-thought or treating reasoning summaries as proof.
- Increasing generic checkpoint narration or repeating source-lifetime policy
  in stable instructions.
- Automatic harness-side retention/drop policy.
- A new UI, board owner, durable record type, or provider-specific core branch.
- Claiming exact ChatGPT/WebSocket compatibility from a configured Responses
  HTTP run.

* Risks and mitigations

- A model may fail the stricter exhaustive schema.  Treat that as an observable
  contract result; do not weaken validation or infer missing labels.
- Reasoning summaries may be empty, unsupported, or worded unpredictably.
  Keep them diagnostic and keep semantic evidence structural.
- Drop-only handling can accidentally create an invalid empty promotion record.
  Make “validated effect with no semantic record” explicit in the pure preflight
  result and cover it before session mutation.
- Both request changes invalidate cache and adoption identities.  Fence them and
  rerun rather than reusing earlier provider evidence.

* Design self-check

1. This package is useful alone because it makes negative curation decisions
   observable without adding durable semantic content.
2. It moves toward model-directed, explicit lifetime decisions with evidence
   that separates selection from composition.
3. Summary verbosity and scenario wording remain adapter/E2E-local; complete
   disposition and frame consumption are stable core semantics.
4. The adapter owns Responses request fields and schema translation; core owns
   frame-bound validation; the harness owns atomic commit; E2E owns evidence.
5. One =drop= field narrows ambiguity without adding another carrier or broad
   runtime interface.
6. Stable core policy does not depend on OpenAI reasoning summaries.
7. Provider output and request options remain at the adapter/presentation edge.
8. No runtime durable state is added; dropped labels live only through effect
   validation and can be rebuilt only from the live frame.
9. Production cost is the provider's optional summary generation and a bounded
   label-partition check; cache effects require measurement.
10. The carrier remains one real strict contract; drop-only implementations do
    not weaken existing exact/summary behavior.
11. Existing promotion record compatibility is preserved; obsolete omission
    semantics are deliberately removed.
12. Remove verbose omission/no-call guidance and stale evidence after the new
    material identity ships.
13. Invalid partitions surface through the existing curation failure path;
    external availability remains independently classified.
14. Core partition/drop behavior, adapter request shape, harness atomicity, and
    external adoption each have narrow evidence owners.
