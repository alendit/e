* Implementation Tick 1 findings

** P2 F88.I1: custom proof exposed the provider-neutral legacy scalar

The adapter expanded =request-local-replaceable= to the preferred five-kind
map only for built-in providers.  An identity-compatible custom Responses
profile with the same explicit proof still exposed the legacy scalar through
=e-openai--profile-context-capabilities=.  That made the adapter's public
representation depend on provider identity even though the semantic proof was
the same.  The scalar compatibility form belongs only to the provider-neutral
=e-backend= boundary for adapters that have not migrated.

Required correction: every identity-compatible Responses profile whose static
configuration explicitly declares =request-local-replaceable= must return a
fresh copy of the same five-kind map.  Unproved profiles and effective
endpoint/transport overrides remain conservative.

** P2 F88.I2: the credentialed Codex test observed request-start state

The revised live test captured the proposed literal body, but obtained
transport diagnostics from the durable =provider-request-started= event.  An
incremental request can later retry as a full request on the same native
request handle, updating its final metadata.  Therefore the start event could
pass while the completed transport path had already fallen back.

Required correction: retain both native request handles returned by
=e-openai-codex--websocket-request-start= and inspect the second handle after
the turn settles.  Its final metadata and the correlated finished event must
prove successful incremental completion, no fallback, the prior response id,
socket reuse, and reuse count.  Existing literal request and marker assertions
remain required.

* Implementation Tick 2 finding

** P2 F88.I3: live completion correlation treated request ordinal as session-global

The parent-owned credentialed ChatGPT Codex run reached the expected provider
behavior.  The second native request handle's final metadata reported
=incremental= mode, a present previous response id, socket reuse count one, an
explicit nil fallback reason, =request-local-replaceable= observation delivery,
and =advance-eligible= anchor safety.  The live test failed only because it
expected the second turn's =provider-request-ordinal= to be 2.

Provider request ordinals are local to one top-level turn.  Each of these two
=prompt-batch= calls owns a distinct turn, so the second turn's only provider
request correctly has ordinal 1.  Taking the last session-wide finished event
and expecting ordinal 2 was therefore an invalid and potentially ambiguous
cross-turn correlation in the test, not an adapter failure.

Required correction: capture the settled second prompt entry's turn id, select
the durable =provider-request-finished= event with that exact =:turn-id=, and
then compare its successful terminal diagnostics with the second native request
handle.  Do not use request ordinal as a cross-turn identity.
