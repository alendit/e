#+title: Plan: Session Context Resources
#+date: 2026-08-11
#+startup: overview

* Status

Planned.

* Goal

Give each session a small, durable, writable resource namespace whose current
contents are added to model context as a cache-efficient current-state suffix.

Use =session-context://plan.org= as a convention, not as a separate plan data
model.  Stable guidance should tell the agent to create and maintain that
resource for complex work, much as Codex guidance tells a model when a plan is
useful.  The ordinary resource operations are the update interface; there is
no bespoke =update_plan= tool, plan schema, or checklist state owner.

The scheme uses =session-context= rather than =session_context= because the
current URI parser follows standard URI scheme grammar and does not accept
underscores.

* Problem

=e= has storage and context mechanisms near this requirement, but the current
feature plan combined too many of them into a new workspace subsystem:

- =tmp://= is writable and session-scoped, but deliberately ephemeral and not
  standing model context.
- =file://= is durable, but puts agent working state into a project or an
  invented private filesystem location.
- =buffer://= exposes presentation/process state rather than session-owned
  semantic state.
- =session://= is a read-only cross-engine history projection.
- transcript messages retain every old plan rendering; they do not identify a
  single current version.
- the Goal capability is a controller protocol with success/blocker semantics,
  not a general current-context resource.

The previous direction proposed a generic sidecar workspace, a structured
=update_plan= facade, a JSON plan schema, workspace-change events, and a custom
chat checklist projection.  None is required for the core behavior.  A
session-owned writable resource which already participates in context is the
smaller and more general primitive.

* Direction

Add a =session-context://= resource scheme owned by the session runtime:

#+begin_example
session-context://plan.org
session-context://notes.org
session-context://hypotheses/cache-churn.md
#+end_example

Every resource in this namespace means "small current state the model should
know."  Content which should not enter standing context belongs in =tmp://=,
=file://=, or another explicit resource scheme.

Register the existing generic =read=, =write=, =edit=, =glob=, and =search=
operations.  The ordinary =write= operation atomically creates or replaces a
resource.  The ordinary =edit= operation remains available for shells and
precise changes, but guidance should prefer rewriting a small plan in full:

- the complete new plan is unambiguous;
- the tool call itself carries the new version in the append-only request tail;
- no plan-specific patch language or schema is needed;
- stale plan versions remain cacheable history rather than changing an earlier
  reusable prefix.

The context provider emits resource snapshots as backend-neutral input/context
items after stable instructions and policy.  They must not be flattened into
top-level provider instructions: changing a plan must not invalidate stable
request properties or force a new OpenAI WebSocket chain.

* Core contracts

** Session ownership and persistence

Store resources as bounded typed current state in =e-session=.  Persist a
successful mutation as an ordinary durable session event and fold replay to
the latest value.  Do not introduce a parallel workspace manifest or sidecar
store for this first small-resource contract.

Initial lifecycle rules:

- each session owns an isolated resource map;
- a resource survives restart and ordinary resume;
- subagent sessions start with their own empty map;
- explicit session reset clears the map;
- session deletion removes it with the session;
- branch rewinds do not silently select an older resource revision in the first
  version; these are session-current values;
- per-resource, aggregate byte, resource-count, and path-depth limits are
  explicit and small.

Paths are relative and normalized.  They cannot escape the namespace.  Values
are text plus a content type; binary and large-output storage remain out of
scope.

** Revision and authority

Each successful mutation assigns a monotonically increasing revision within
that resource.  Resource metadata and mutation results contain =:uri=,
=:revision=, =:bytes=, and =:content-type=.  Model context contains the URI,
revision, and content, but not volatile timestamps.

The standing interpretation rule is:

#+begin_quote
For a session-context URI, the highest revision is authoritative and
supersedes every lower revision.  Absence of a newer revision does not revoke
the current one.
#+end_quote

That rule is part of stable capability guidance.  It lets a provider response
chain contain an older snapshot followed by a newer one without ambiguity.

=write= accepts an optional expected revision and atomically replaces the
resource.  =edit= requires an expected revision.  Conflicts return the current
revision and ask the caller to read before retrying.  Mutation results are
compact and never echo the complete content.

** Plan convention

Stable guidance references =session-context://plan.org= directly:

- create it for complex, multi-step, dependent, ambiguous, or multi-part work;
- skip it for simple tasks;
- keep it concise and operational;
- use ordinary Org text, headings, and checkboxes/status markers as useful;
- rewrite it when the approach or status materially changes;
- remove it when it is no longer relevant to the session.

The plan format is intentionally not validated beyond the text-resource bounds.
The agent can use prose, checkboxes, dependencies, evidence links, or a compact
table as the task requires.  A future consumer may parse conventional Org, but
the resource stays authoritative even when no parser or custom renderer exists.

There is no =update_plan= model-facing tool.  Adding one would duplicate the
generic resource mutation contract and its schema would be another mutable
prefix/tool-definition concern.

** Context projection

On a full context build, emit exactly the latest snapshot of each current
resource, ordered deterministically by URI.  Wrap each snapshot in a stable,
provider-neutral envelope equivalent to:

#+begin_example
Session context resource: session-context://plan.org
Revision: 4 (supersedes lower revisions)
<current content>
#+end_example

The envelope format and guidance are stable.  Resource names, revisions, and
contents form a bounded current-state/dynamic suffix, not stable instructions.

On a provider continuation request:

1. Record, in provider-neutral anchor compatibility data, the highest revision
   of each session-context URI already visible to that response chain.
2. If the resource is unchanged, emit nothing; the provider chain already has
   that revision.
3. If the agent just updated the resource through =write= or =edit= and that
   tool call/result are in the request delta, treat the successful result's
   revision as covered.  Do not immediately duplicate the same content in a
   second context item.
4. If a shell, user action, resumed session, or background operation changed
   the resource outside the visible delta, append the complete latest snapshot
   as a new context item.
5. If coverage cannot be proved after compaction, reconnect, anchor loss, or a
   full replay, emit the latest snapshot once.

Thus an agent-authored full rewrite is the efficient re-emission.  The tool
call carries the new content, its compact result marks the revision, and later
requests reuse that tail.  Explicit context re-emission exists for changes the
model did not already observe and for rebuilt context boundaries.

Deleting a resource emits a revisioned tombstone when an existing provider
chain may still contain an older version.  The stable rule says a tombstone at
revision N supersedes lower content.  A full context build omits deleted
resources because no older provider state exists in that request.

* Cache-preservation contract

- Keep capability guidance and generic resource tool definitions stable.
- Do not include resource contents, revisions, names, or fingerprints in
  top-level instructions, =prompt_cache_key=, active-layer identity, or tool
  schemas.
- Put session-context snapshots after stable cached context as ordinary input
  items.
- A revision change is an append/replace-current-state delta, not a reason to
  invalidate an otherwise compatible provider anchor.
- Do not echo full content in mutation results.
- Do not duplicate a snapshot when the successful mutation call already makes
  that revision visible in the same provider chain.
- On full local reconstruction, project only current resources; persistence
  history is not itself a context provider.
- Keep historical tool calls as ordinary transcript history.  Provider prompt
  caching and continuation can reuse those old prefixes; ordinary compaction
  may later summarize them without a plan-specific rule.

For OpenAI Responses, this design allows a retained WebSocket to append a new
resource revision without changing non-input request properties.  For
Anthropic, the stable cache breakpoint remains before the dynamic resource and
transcript suffix.  Correctness never depends on either provider cache.

* Relationship to existing facilities

- =e-session= owns persistence and revision folding.
- =e-resources= supplies the existing generic operation contract.
- =e-context= owns deterministic current-state projection and provider-neutral
  revision coverage.
- Provider adapters consume context items and opaque anchor compatibility; they
  do not implement plan semantics.
- =tmp://= remains disposable storage for large outputs.
- =session://= remains a read-only history/resource projection.
- Goal remains a distinct controller protocol.
- Shells may open a resource in an ordinary editable buffer, but buffers and
  canvases are not the state owner.

* Implementation slices

** Slice 1: Session current-state resources

- Add bounded typed session state and durable mutation events.
- Register =session-context://= read/write/edit/glob/search methods.
- Return compact revision metadata from mutations.
- Cover path safety, limits, conflicts, replay, reset, deletion, and isolated
  session ownership.

This slice is independently useful as a generic small session context resource.

** Slice 2: Context projection and plan guidance

- Add stable guidance naming =session-context://plan.org= and when to use it.
- Project current resource snapshots as a deterministic dynamic input suffix.
- Add revision/tombstone envelopes and highest-revision-wins semantics.
- Detect when a successful resource mutation in the visible transcript delta
  already covers the latest revision, avoiding duplicate emission.

This slice provides Codex-like planning behavior using only generic resources.

** Slice 3: Continuation and cache gate

- Carry resource revision coverage in provider-neutral anchor metadata.
- Append changed/out-of-band snapshots without changing stable instructions or
  non-input provider properties.
- Re-emit latest state after compaction, reconnect, resume, or lost coverage.
- Test OpenAI incremental continuation and Anthropic stable-prefix caching.
- Measure request input, cached input, uncached input, and duplicate bytes on a
  repeated complex task.

* Deferred canvas question

A revisioned latest-snapshot-wins projection may also be more efficient for
canvas and Org Canvas current state than invalidating provider continuation on
every edit.  That requires separate decisions about edit frequency, snapshot
size, debouncing, user-versus-agent authority, and whether stale canvas content
may remain in a provider chain.  Do not broaden this feature to canvas; record
it as a separate research/feature candidate after the session-context contract
is measured.

* Non-goals

- No bespoke =update_plan= tool or plan JSON schema.
- No custom checklist renderer or chat-owned plan state.
- No generic durable workspace sidecar or manifest in the first version.
- No automatic inclusion of =tmp://=, =file://=, or arbitrary buffers.
- No binary or large-resource storage.
- No collaborative merge protocol.
- No branch-relative resource histories in the first version.
- No canvas/Org Canvas context redesign in this feature.
- Do not implement this plan while its status is =Planned=.

* Verification plan

- Focused ERT for session persistence, revisions, tombstones, conflicts,
  resource bounds, and generic operations.
- Context tests proving full builds contain one latest snapshot per URI in
  deterministic order.
- Delta tests proving a model-authored write is not immediately duplicated,
  while an out-of-band higher revision is re-emitted.
- Compaction/reconnect/resume tests proving the latest snapshot is restored
  once and lower revisions cannot regain authority.
- Request-shape tests proving resource updates do not change instructions,
  tool definitions, prompt cache keys, stable fingerprints, or non-input
  WebSocket properties.
- OpenAI continuation tests proving a higher revision appends on the retained
  connection.
- Anthropic tests proving the cache breakpoint stays before session-context
  state and cache usage remains observable.
- Full repository gate and =git diff --check= before review.

Repository-side tests are sufficient during implementation.  Do not reload the
running Emacs unless the operator explicitly asks.

* Design review

1. *Better if stopped here?* Slice 1 already gives sessions a small durable
   context resource through existing operations.
2. *Final direction?* Session-owned current state, projected through the common
   context model and independent of provider and shell implementations.
3. *Likely to change?* Envelope wording and future parsed conventions may
   evolve.  Revision authority, bounded state, generic resource mutation, and
   suffix placement are stable requirements.
4. *Owner?* =e-session= owns state and revision; =e-context= owns projection;
   resources own mutation dispatch.  No plan-specific owner is needed.
5. *Coupling?* This removes the proposed plan tool/schema/UI stack and reuses
   existing narrow contracts.
6. *Dependency direction?* Providers and shells consume context/resources;
   session state does not depend on either.
7. *Side effects outward?* Durable appends remain in session persistence;
   context formatting and coverage comparison stay pure.
8. *State lifetime?* Small resources are durable session-current facts.  Old
   revisions survive only as persistence/transcript history, not current
   context snapshots.
9. *Performance?* Full small-resource rewrites add one tail tool call and avoid
   mutable-prefix invalidation.  Coverage prevents immediate duplicate
   snapshots and bounds prevent large standing context.
10. *Real abstractions?* A session current-context resource and monotonic
    revision are concrete semantics.  No speculative plan facade remains.
11. *Compatibility?* Existing schemes keep their meanings; the new valid URI
    scheme is additive.
12. *Legacy removable?* The unimplemented =update_plan= facade and checklist
    projection are removed from the plan before they create legacy code.
13. *Errors?* Invalid paths, bounds, stale revisions, and malformed mutations
    are expected resource errors.  Persistence and invariant failures surface.
14. *Independent tests?* Session/resource/context tests require neither live
    providers nor presentation; adapter shape tests require no network.
