#+title: Agent Process-Reporting Tool
#+startup: overview

* Goal

Give the task-performing agent a first-class way to place small process markers into the session while the relevant judgment is fresh.
A marker is a terse observation, not a finished report or diagnosis.
Process marking is a pure observability and learning function.
It does not help complete the current task, so every token, provider request, delay, tool result, and context entry it causes is additional cost that later learning must repay.
The marker lands in a durable, reviewable store with stable pointers back into the session.
Later offline extraction gathers surrounding context and may turn one or more markers into a bug, runtime fix, missing capability, skill, script, cron job, guidance edit, or no action.

* Problem

The agent today has no durable channel for observations about its own work process.
A broken tool call, repeated correction, successful workaround, missing operation, or reusable sequence is either worked around silently or narrated in chat, where it is hard to find and easy to lose.
The same rough edge or useful method can therefore be rediscovered in later sessions without becoming tracked work or reusable guidance.
We want the agent's lived experience of the runtime and task process to feed back into improving both.

Framing the capture tool as =bug_report= makes the agent classify the cause and remedy too early.
A report may reveal a runtime defect, but it may instead show missing guidance, a capability gap, a recurring procedure worth codifying, a deterministic sequence worth scripting, or a one-off misunderstanding.
The capture step should preserve evidence and intent; triage should decide what the evidence means.

* Design

** A lightweight process-marker tool

- The default capture path is a small model-facing =process_marker= tool called directly by the task-performing agent.
  The parent already has the process judgment in context; capture should preserve that judgment rather than pay another model to reconstruct it.
- A matching =e-actions-call= action gives runtime code and later extraction agents the same semantic write path.
- The marker records events such as a failed operation, correction, workaround, repeated multi-step sequence, missing affordance, performance problem, or notably effective method.
- Capture stays descriptive.
  It does not require the caller to name the final work item or assert that the runtime has a bug.
- The descriptor and default guidance must be extremely small.
  Guidance should explain in one compact rule when a marker is worth the interruption and should discourage narration or duplicate markers.
- Arguments rely on auto-attached context and contain only the agent judgment that telemetry cannot infer.
- The model-visible result is the smallest protocol-valid acknowledgement and never repeats the marker or attached context.
- A normal tool call still interrupts generation and causes a follow-up provider request.
  This is accepted as the direct capture cost and measured against the hypothetical session without marking.

** What a process marker captures

The model-supplied payload should fit in one short tool call:

- =signal= :: a descriptive hint from a small vocabulary such as =failure=, =correction=, =workaround=, =repetition=, =success=, =missing-operation=, or =performance=.
- =note= :: one short sentence naming what mattered.

The runtime attaches everything it already knows:

- marker id, session id, turn id, project root, and timestamp;
- relevant capability, tool, or action name;
- triggering tool-call or action-call id;
- redacted argument, outcome, error, and telemetry references when available.

Do not ask the parent agent for detail, impact, expected-versus-actual restatement, recurrence evidence, or a proposed remedy in the capture call.
Offline extraction can recover surrounding evidence through =session://= and can ask a later model to produce a richer report only when the marker proves useful.

** Where reports land

- A process-reporting capability owns an append-only store that is cheap to write and easy to inspect.
- The capability exposes stable =list= and =read= actions or resources so human review and later extraction passes do not scrape private storage files.
- Reports use narrow persisted schemas and a shared best-effort redaction boundary.
  Arguments previews and error text reuse the telemetry-preview path rather than dumping raw payloads, and arbitrary tool metadata is not copied.
  Because free text can contain unknown secret forms, the first slice does not claim mathematically secret-free persistence; operators must apply the same retention and access controls used for session telemetry.
- The original report remains immutable.
  Triage decisions and links to resulting work append separate records so provenance is preserved.

** Triage and outcomes

Triage interprets a process report and routes it to zero or more durable outcomes:

- *Runtime defect* :: create or link bug investigation and fix work.
- *Missing capability* :: create or link feature work.
- *Recurring judgment-shaped procedure* :: propose a skill or =AGENTS.md= guidance edit.
- *Deterministic procedure* :: propose a script, tool, or action.
- *Recurring unattended work* :: propose a cron schedule or task-queue workflow after the procedure is proven.
- *Project fact or policy* :: propose a scoped guidance or configuration edit.
- *Duplicate, understood, or not actionable* :: close or reject without creating work.

The first slice needs only a small triage record: outcome kind, optional target reference, decision note, and status.
It does not need to implement every downstream workflow.
A content-keyed evidence identity should prevent rejected or already-routed observations from being raised again until the evidence changes.

** Relationship to telemetry and session learning

- Action telemetry from feat 44 records action outcomes mechanically.
  A process report records the agent's judgment that an event is worth retaining and explains why.
  A report can reference the telemetry call that supplies mechanical evidence.
- Session learning reads process reports as high-precision anchors into =session://= history.
  Broader session mining can then corroborate recurrence, find related unreported episodes, and propose the right durable artifact.
- Explicit reports and implicit mining cover different blind spots.
  Reporting depends on the agent noticing significance, while mining can find repeated patterns nobody reported.

** Why capture stays in the parent

The parent already has both the task context and the process judgment when it decides a marker is worth preserving.
A child would spend another model request to reconstruct that judgment from a partial session projection.
For a payload as small as a signal plus one sentence, that duplication is unlikely to beat the direct tool call even if the child uses a cheaper model or cached prefix.
A child also risks losing the tacit reason the parent considered the event important.

Therefore feature 52 should not spawn a child for marker capture, enrichment, or immediate triage.
The marker call stays in the parent and pays one measured interruption.
Its result is minimized and should be removed from later model context when the provider and transcript protocol allow that without breaking tool-call validity.
If it must remain in context, retain only a compact acknowledgement.

=session://= begins to matter after capture.
Offline extraction uses the marker's session id, turn id, and call references to fetch surrounding messages and activity only when needed.
That separates the cheap online judgment from the expensive context gathering and synthesis.
It also lets extraction batch markers across sessions, apply recurrence tests, and amortize model startup over work that has enough evidence to justify it.

A terminal side-channel that lets the parent emit a marker alongside its final answer without a follow-up request remains worth investigating.
It could be cheaper than an ordinary tool call, but it needs a real harness/provider protocol and cannot be assumed in the first slice.

Children or queued background sessions belong to later offline extraction, not first-line capture.
Those workers should use their own stable small prefix and bounded =session://= evidence.
They should not inherit the parent transcript merely to improve prompt-cache hits.
Cached tokens still cost money and consume context capacity.

** Counterfactual cost accounting

Because process reporting cannot improve the current task, all of its direct and induced costs count as overhead against a hypothetical execution without process reporting.
The primary metric is therefore incremental cost relative to that counterfactual, not merely the percentage of observed tokens occupied by report artifacts.
Keep accounting post-hoc and derived where possible rather than adding mutable counters to each report.

Separate three online capture costs:

1. *Passive surface overhead* :: tokens and cache effects from the tiny tool descriptor and default guidance on every main-session provider request, including requests where no marker is created.
2. *Active marker overhead* :: output tokens used to emit the signal and note plus input tokens for the acknowledgement and retained call record.
3. *Interruption overhead* :: the extra provider round trip, repeated prompt prefix, latency, and any changed task output caused by stopping generation for the marker call.

Later offline extraction has its own cost ledger.
Do not charge extraction to one marker until the extraction batch records which markers and unmarked session evidence it consumed.

#+begin_example
online marker overhead = cost(main with marker surface) - cost(main without marker surface)
relative online overhead = online marker overhead / cost(main without marker surface)
#+end_example

Runtime persistence CPU and latency also count, but should be reported outside model-token cost.

Use two levels of counterfactual measurement:

- *Request-shape counterfactual* :: reconstruct each backend-neutral request value and a paired value from the same snapshot with process-marker descriptors, guidance, calls, and results removed.
  Persist revisioned hashes and UTF-8 byte measures for the actual, passive-free, active-free, and fully paired values.
  This gives a deterministic direct context delta while holding the rest of the observed session fixed.
  Canonical provider serialization and provider-tokenizer integration are deferred deliberately; the persisted backend-neutral shape measures preserve post-hoc attribution but must not be described as exact provider-token cost.
- *Behavioral counterfactual* :: replay from the checkpoint immediately before marking with the process-marker surface disabled, or randomly enable marking across comparable sessions.
  Compare total provider tokens, request count, wall time, task quality, and completion outcome.
  Repeated trials are needed because model output is stochastic.

The request-shape comparison measures attributable bytes or tokens but cannot estimate how the model would have continued instead of emitting the marker call.
Only replay or controlled A/B data can estimate interruption overhead and changed behavior.
The plan should report direct context deltas and behavioral estimates separately rather than presenting one as the other.

The provider already supplies request totals for input, cached input, output, reasoning output, and total tokens, and =e= stores them as durable =token-usage= events.
Tool and action lifecycle events already preserve turn ids, tool-call ids, action-call ids, parent tool-call ids, argument previews, result previews, and elapsed time.
Preserve or add the following data so both counterfactuals remain possible:

- A stable provider-request id or request ordinal on =provider-request-started=, =provider-request-finished=, and the corresponding =token-usage= event.
  Event order within a turn is a fallback, not a durable join contract, because a tool turn can issue several provider requests.
- Revisioned, secret-safe hashes and byte measures for the actual backend-neutral request and its passive-free, active-free, and fully marker-free pair.
  Exact provider payload retention is not part of the first slice because it would duplicate arbitrary model-visible content into telemetry.
- A checkpoint or reconstructable session state immediately before a marker invocation.
- The =process_marker= tool-call id, nested process-reporting action-call id, and resulting marker id.
- Provider, model, model parameters, prompt-cache state where available, tokenizer revision, request timing, and task completion outcome.
- Original byte or character lengths for redacted model-visible arguments and results when exact text cannot be retained.

A post-hoc report can then show:

- direct incremental main-session tokens per request and per session;
- extra main-session provider requests and wall time caused by marking;
- overhead for sessions where the marker surface was available but unused;
- online overhead per marker;
- separate offline extraction cost per consumed marker batch;
- combined cost per useful downstream outcome, such as a confirmed bug, accepted skill, or guidance change.

Use the provider tokenizer when one is available.
Otherwise record the estimation method and use one stable approximation, such as UTF-8 bytes or characters converted to estimated tokens.
Never call provider-reported request totals alone the tool's cost.
Those totals are the denominator and validation evidence; the counterfactual delta is the cost estimate.

** Surfacing

- A =list=/=read= path, and optionally a picker, lets the human review open reports and their triage decisions.
- A later inbox-triage or grimoire integration may turn routed outcomes into project work.
  Keep that integration out of the first slice; first make capture, evidence, and routing reliable.

* Non-goals

- Not automatic promotion of every error into a marker.
  A failed tool call is telemetry, not automatically process evidence.
  The task-performing agent decides when an event carries a judgment worth marking.
- Not limited to failures.
  Successful workarounds and repeated useful procedures are valid evidence.
- Not a full issue tracker.
  Assignment, comments, and rich workflow stay in the downstream system selected by triage.
- Not autonomous self-modification.
  Skills, scripts, schedules, and guidance remain proposals until reviewed.
- Not user-facing reporting.
  This is an observability channel for process evidence.
- Not a current-task aid.
  Do not justify context, latency, or token overhead as helping the task in which the observation occurred.

* Acceptance

- A small =process_marker= tool is present in the parent session with a minimal descriptor and one compact guidance rule.
- The model-supplied payload is limited to a signal and one short note.
- The runtime auto-attaches session, turn, project, action/tool, redacted argument, result/error, and telemetry context when available.
- The model-visible result is the smallest protocol-valid acknowledgement and does not repeat marker data.
- Marker capture does not spawn a child or gather session context.
- Each marker stores stable references that later extraction can resolve through =session://=.
- A stable =list=/=read= path lets humans and extraction agents review markers later.
- Triage can append an outcome and optional target reference while leaving the original marker unchanged.
- Bug work is one supported triage outcome rather than the identity of the marker tool.
- Durable telemetry can join each marker invocation to its provider requests and =token-usage= events through stable ids rather than event-order inference.
- A post-hoc report can compare revisioned actual and marker-free backend-neutral request shapes, calculate direct incremental byte cost, and preserve stable request joins for later provider-specific measurement.
- Replay or controlled A/B measurement can estimate interruption overhead relative to sessions without marking.
- Offline extraction cost is tracked separately and linked to the marker batch it consumed.
- Every estimate names its tokenizer or approximation and does not claim behavioral overhead from request-shape accounting alone.

* Design self-check

1. The first slice is useful by itself because it preserves high-signal evidence and supports human triage before downstream automation exists.
2. It moves toward a closed learning loop from explicit capture through session corroboration to reviewed durable artifacts.
3. The stable decision is neutral append-only capture; signal vocabulary, triage states, storage location, and review UI remain local and reversible.
4. A process-reporting capability owns capture, storage, and report access; downstream systems own bugs, features, skills, scripts, schedules, and guidance.
5. The design reduces coupling by exposing narrow report and triage records instead of binding capture to an issue tracker or extractor.
6. Policy does not depend on concrete UI or storage adapters; those implement the capability-owned contracts.
7. Redaction, persistence, and presentation remain side effects at the capability and shell boundaries.
8. Reports and appended triage decisions are durable facts; derived groupings, rankings, and review views should remain rebuildable.
9. The default path adds one deliberately tiny model-facing surface and pays a provider round trip only when the parent emits a marker; enrichment, clustering, and cross-session mining stay offline.
10. The capture contract applies to every signal without weakening behavior or requiring unsupported outcome fields.
11. The original =bug_report= idea remains compatible as the runtime-defect triage outcome, while the bug-only tool name and schema are removed.
12. No separate bug-report store or bug-specific capture path should remain once process reporting exists.
13. Expected validation and routing errors return to the caller; unexpected persistence and redaction failures must surface rather than be swallowed.
14. Focused tests should prove neutral capture, context attachment and redaction, immutable evidence, appended triage, and stable list/read behavior without a full shell.
