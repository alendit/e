* Findings

** DONE High: The durable store is stale and unsafe under concurrent writers

*** Expected

The plan requires a durable, append-only store with stable list/read behavior, content-keyed suppression, and realistic repeated use.
Durable facts and duplicate decisions must remain correct when more than one harness, store object, or Emacs process uses the configured directory.

*** Observed

=e-process-reporting-ensure-loaded= loads a store only once at =lisp/layers/harness/e-process-reporting.el:149-154=.
Every later list, read, duplicate check, triage, and append trusts that private in-memory index.
=e-process-reporting--append-file= at lines 87-93 appends without a file lock, refresh, record transaction, or incomplete-tail recovery.

A probe created two store objects over one directory, loaded both, then appended through each.
The second store did not see the first marker, and the first store did not see the second marker.
A fresh reload saw both.
This means list/read results, unknown-marker checks, and terminal-evidence suppression depend on which store object handled the call.
Two processes can both pass suppression and append the same evidence.
A killed or interleaved write can also leave a malformed line that makes the next full load fail.

The current test covers restart after serial writes through one store.
It does not cover two loaded stores, process concurrency, stale reads, duplicate races, or a partial final record.

*** Why this matters

This is correctness and provenance failure in the feature's owning store.
Markers can disappear from a live review view, duplicate suppression can fail, and triage can reject a marker that exists on disk but not in one process's index.

*** Smallest fix direction

Give one component exclusive ownership of each records file, or serialize refresh/check/append with an inter-process lock.
Under that lock, ingest records appended since the last known offset before every decision that depends on current state, then append one complete record and update the index.
Define recovery for an incomplete final line without accepting malformed records in the middle of the log.
Add tests with two store instances and at least one separate-process contention probe covering marker append, triage, and terminal-evidence suppression.

*** Resolution

The store now serializes every refresh/check/append transaction with an atomic
lock directory shared across Emacs processes. Each transaction reloads durable
state before validation. Marker suppression, triage existence checks, and
appends therefore use one current view. A dead local owner can be reclaimed.
Loading truncates only an incomplete final line under the lock and still rejects
a malformed complete line.

*** Evidence

=e-process-reporting-test-two-store-writers-refresh-and-recover-tail= proves
cross-store list/read/triage and final-tail recovery.
=e-process-reporting-test-terminal-suppression-is-atomic-across-stores= proves
that terminal evidence written through one store suppresses a peer store write.

A fresh-process contention probe started two =emacs -Q --batch= writers against
one directory. Both exited zero and the resulting JSONL contained two complete
records: =statuses=0/0 lines=2 ids=['one', 'two']=.

** DONE High: Persisted telemetry is not secret-safe by construction

*** Expected

The plan says reports never contain secrets by construction and that marker evidence reuses a safe telemetry-preview path.
The implementation handoff also claims that shared telemetry redaction prevents raw argument, result, or error payloads from being copied.

*** Observed

The redactor in =lisp/core/e-telemetry.el= is a key-name and regular-expression heuristic.
It cannot establish that arbitrary note, error, result, or metadata text is secret-free.
More concrete leaks remain in the touched persistence paths:

- =e-actions--error-payload-fields= at =lisp/core/e-actions.el:206-210= persists the raw =e-work-error-message= as =:message= in =action-failed= activity.
  A batch probe raised =token=super-secret action failed= and found the exact secret in durable session activity.
- =e-harness--compact-tool-result-for-activity= at =lisp/core/e-harness.el:951-979= copies the complete result =:metadata= before adding preview fields.
  Tool metadata therefore bypasses =e-telemetry-preview=.
- =e-process-reporting-mark= stores the model-supplied =:note= verbatim at =lisp/layers/harness/e-process-reporting.el:359=.
  The schema and guidance do not prevent a credential from appearing there.
- =e-process-reporting-record-extraction= at =lisp/layers/harness/e-process-reporting.el:453-476= stores caller-supplied session evidence, request ids, token usage, and estimation method without a persistence-boundary projection.

The process marker re-redacts a selected trigger preview, but that does not remove the raw secret already written to session telemetry.
The current tests cover one keyed argument and one inline token form only.

*** Why this matters

The durable observability channel can preserve credentials indefinitely.
This directly violates the plan's security invariant and the implementation's documentation claim.

*** Smallest fix direction

Define a narrow persisted schema for each activity and process-reporting record instead of copying arbitrary metadata or error values.
Run every retained free-text field through one public redaction boundary, including action errors and marker notes.
Drop tool metadata by default and allow only named safe fields.
If arbitrary notes cannot be guaranteed secret-free, change the claim from “by construction” and add an explicit redaction/retention policy before acceptance.
Add regression tests for action errors, tool metadata, marker notes, extraction fields, nested maps/vectors, authorization headers, URL credentials, and common provider key formats.

*** Resolution

The persistence boundary now uses narrow schemas. Action errors retain a
redacted bounded preview instead of a raw message. Durable tool results retain
only named scalar metadata. Marker notes, triage text, extraction references,
and estimation text cross the public string redactor. Extraction token usage is
projected onto named numeric fields. README and plan claims now describe a
redaction policy rather than an impossible guarantee for arbitrary free text.

*** Evidence

Focused tests cover raw action-error tokens, unknown and nested tool metadata,
marker notes, extraction text, authorization forms, API-key forms, nested
containers, and URL credentials. No test fixture secret remains in the durable
serialized values.

** DONE High: The request-shape report does not implement the claimed counterfactual

*** Expected

The plan requires a request-shape counterfactual that reconstructs each actual provider request and a paired request with process-marker descriptor, guidance, calls, and results removed, then tokenizes both with a named provider tokenizer or stable approximation.
It requires passive surface, active marker, and interruption costs to remain distinct.
Provider totals are evidence and denominator values, not the marker cost itself.

*** Observed

=e-loop--request-shape= at =lisp/core/e-loop.el:79-143= stores Emacs =prin1-to-string= hashes and byte counts for broad values.
It does not store the canonical provider-visible payload, a reversible component map, provider serialization revisions, or enough content to rebuild the exact paired request after descriptors or guidance change.
The separate marker fields are also measured from Emacs Lisp representations, not the provider request payload.

=e-process-reporting-cost-report= at =lisp/layers/harness/e-process-reporting.el:478-512= adds descriptor, guidance, call, and result bytes across all requests, labels the sum =:passive-surface-bytes=, divides it by four, and labels the result =:estimated-passive-surface-tokens=.
The call and result are active overhead, not passive surface.
The function does not construct paired requests, calculate their delta, use provider-reported usage as validation, report per-request values, or name a provider tokenizer.

The two-request probe made the category error concrete.
The first request had descriptor/guidance bytes only.
The induced follow-up had descriptor/guidance plus call/result bytes.
The report merged all four fields from both requests into one passive total.

README and =plan.org='s implementation evidence overstate this as request-shape counterfactual support.
The code only provides a rough attribution inventory.

*** Why this matters

The report can present active overhead as passive overhead and cannot support the acceptance claim that a paired request was reconstructed.
This is a core feature contract, not a documentation detail.

*** Smallest fix direction

Preserve or reproducibly resolve the canonical provider-visible components and serialization/tokenizer revisions for each request.
Build an explicit paired payload with marker components removed, and report actual-versus-paired bytes or tokens per request.
Keep passive descriptor/guidance, active call/result, extra request count, and behavioral estimates in separate fields.
Until that exists, rename the current output to an attribution inventory and remove claims that it reconstructs or calculates the counterfactual.
Add a two-request marker-turn test that proves each category and paired delta.

*** Resolution

The loop now derives actual, passive-free, active-free, and fully marker-free
backend-neutral request values at request time and persists revisioned hashes
and UTF-8 byte measures. The cost report exposes per-request direct, passive,
and active byte deltas, provider usage joins, and explicit marker follow-up
counts. It no longer labels active bytes as passive or invents token counts.

Canonical provider serialization and provider tokenizers are deliberately
deferred. The plan, acceptance text, README, and report now state that this
slice measures backend-neutral serialized bytes, not exact provider payloads or
tokens. This retains enough post-hoc data for the stated measurement need: the
stable request ids, model/cache fields, paired revisioned measures, usage joins,
checkpoint, and explicit follow-up cause support later provider-specific
calibration without persisting arbitrary prompt content.

*** Evidence

=e-process-reporting-test-request-shape-report-preserves-paired-measures= proves
per-request passive, active, paired, and follow-up categories.
=e-loop-test-followup-request-carries-tool-cause= proves the paired second
request and usage event have stable cause joins.

** DONE Medium: Nested action context is lost behind the enclosing tool

*** Expected

The runtime should auto-attach the relevant capability, tool, or action name and triggering call id when available.
This matters most for actions invoked from =run_elisp=, because action telemetry is the mechanical evidence behind the parent agent's judgment.

*** Observed

=e-process-reporting--latest-trigger-event= at =lisp/layers/harness/e-process-reporting.el:196-205= selects one latest non-reporting lifecycle event.
For a direct action followed immediately by =:mark=, it selects the action correctly.
For an action called inside a =run_elisp=-style tool, the enclosing tool finishes after the action, so a later marker attaches only the outer tool.
The probe returned =run_elisp_probe/tool-finished/run-1= rather than =outer/:run= and its action-call id.

The action event remains elsewhere in session activity, but the marker does not preserve the stable relation needed to select it without searching and guessing.

*** Why this matters

Offline extraction loses the most specific evidence for the common action-through-tool path.
The marker points at a generic execution carrier rather than the operation the agent judged significant.

*** Smallest fix direction

Attach a trigger chain rather than one latest event.
At minimum preserve the latest relevant action plus its =:parent-tool-call-id= and enclosing tool event when both exist.
Use explicit call relationships, not timestamp proximity.
Add tests for direct tool, direct action, action inside =run_elisp=, nested =e-tools-call=, failure, and a marker with no prior operation.

*** Resolution

Markers now retain a =:trigger-chain=. It puts the latest relevant action first,
keeps its explicit =:parent-tool-call-id=, and includes the enclosing tool event.
Direct tool/action and empty histories still produce the smallest valid chain.

*** Evidence

=e-process-reporting-test-trigger-chain-preserves-nested-action= proves the
action id, parent tool id, and enclosing tool are all retained after the outer
tool finishes.

** DONE Medium: Marker-to-provider attribution omits the induced follow-up request

*** Expected

Each marker invocation should join to its provider requests and token-usage events through stable ids rather than event-order inference.
The producing request and the induced follow-up request are both part of online marker overhead.

*** Observed

The loop correctly gives start, finish, and token-usage events one stable id per request at =lisp/core/e-loop.el:275-306= and lines 473-484.
A complete marker-turn probe confirmed both token-usage joins.

The marker record stores only =e-process-reporting--current-request-id=, which is the latest request-started id.
For the model tool path this is the request that emitted the marker call.
The follow-up request created after the acknowledgement has no marker id or causing tool-call id in its lifecycle payload.
Linking it back to the marker therefore requires event-order inference.

The helper also never checks whether the selected request has finished.
A direct runtime =:mark= action after a completed request attached that stale finished request id.

*** Why this matters

The implementation cannot make the stable join required to count the marker's extra request and its token usage.
It can also claim provider attribution for an action that ran outside any active provider request.

*** Smallest fix direction

Track active request state explicitly.
Persist the producing request id on the marker only while that request is active.
When the loop starts a follow-up because of a tool result, add a stable =:caused-by-tool-call-id= or marker id to the new request lifecycle and token-usage join path.
Add a full two-request process-marker test and a direct action test after provider completion.

*** Resolution

The loop carries the completed tool call into the next provider request as
=:caused-by-tool-call-id= and =:caused-by-tool-name= on started, finished, and
token-usage payloads. Marker capture now returns a producing request id only
while that request is active, so direct runtime actions cannot inherit a stale
finished request.

*** Evidence

=e-loop-test-followup-request-carries-tool-cause= proves both lifecycle and
usage joins for a two-request marker turn.
=e-process-reporting-test-completed-request-is-not-current= proves stale request
attribution is absent.

** DONE Medium: The runtime does not enforce the two-field marker payload

*** Expected

The model-supplied payload is limited to =signal= and =note= so capture remains small and later requests do not retain extra marker narration.

*** Observed

=e-process-reporting--marker-parameters= at =lisp/layers/harness/e-process-reporting.el:514-520= does not set =additionalProperties= to false.
The shared tool coercion path preserves unknown keys, and process reporting ignores them only when writing its own record.
A probe passed an extra =:impact= field; the tool returned =ok= and wrote a marker.
The extra field remains in the model transcript and in durable tool-started telemetry.

The focused test checks required fields but does not test rejection of unknown fields.

*** Why this matters

The store remains small, but the parent context and telemetry do not.
Extra narration increases the exact online overhead this feature is meant to constrain and can carry sensitive text.

*** Smallest fix direction

Set =additionalProperties= to false for provider schema generation and enforce an exact key set at the runtime boundary because not every backend guarantees schema enforcement.
Return a normal tool error for unknown keys.
Add a regression test that proves no extra field reaches the action, transcript, or durable telemetry.

*** Resolution

The marker schema sets =additionalProperties= to false. The shared tool runtime
and action dispatcher both reject unknown arguments rather than relying on a
provider to enforce JSON Schema. A rejected call returns a normal tool error and
does not reach marker persistence.

*** Evidence

=e-process-reporting-test-marker-rejects-extra-fields-before-handler= proves an
=:impact= field is rejected and no marker is written.

** DONE High: Stale-lock recovery can destroy a live owner's lock

*** Expected

The reopened durable-store finding requires an inter-process transaction that
preserves mutual exclusion while refreshing, checking, recovering a partial
tail, and appending. Stale recovery must not delete a lock after another
process has replaced the stale owner.

*** Observed

At =lisp/layers/harness/e-process-reporting.el:158-160=, a contender reads the
owner and then recursively deletes the lock directory if that snapshot looks
stale. The delete has no identity check. Another contender can delete the same
stale directory and acquire a new lock between the first contender's check and
delete. The first contender then deletes the new live lock and acquires its own.
At lines 169-175, either owner also deletes whichever lock directory happens to
exist at cleanup, without proving that it still owns it.

The independent two-process probe widened only the stale-check race. Process B
entered its three-second critical section first. Process A then deleted B's
live lock, entered concurrently, and deleted the lock directory while B still
ran. Both exited zero. The overlapping timestamps above prove that the claimed
transaction is not exclusive.

*** Why this matters

Concurrent refresh/check/append operations can interleave after stale recovery.
That reopens duplicate suppression races and permits one process to read or
truncate a partial write while another process is writing. The current serial
and ordinary-contention tests do not exercise lock replacement during reclaim.

*** Smallest fix direction

Give every acquisition a random owner token. Reclaim and cleanup must atomically
rename or otherwise remove only the exact lock instance whose token was read.
If the platform cannot conditionally remove a directory, use an advisory lock
primitive or a lock file protocol with ownership verification after reclaim.
Add a deterministic three-process stale-reclaim race and prove that critical
sections never overlap and one owner cannot remove another owner's lock.

*** Resolution and evidence

The store now holds =lockf= or =flock= through a live helper process for the
full transaction. The kernel releases the lock on process exit, so no cleanup
path removes another owner's identity. Focused tests prove a second acquisition
fails while a holder is live and succeeds after release. The macOS adapter also
rounds =5.0= to the valid =lockf -t 5= spelling.

** DONE High: Trigger chains are corrupted by JSON encoding

*** Expected

The resolved nested-action finding requires the explicit action/tool chain and
its stable call relationships to remain available after restart through the
durable store.

*** Observed

=e-process-reporting-mark= stores =:trigger-chain= as a Lisp list of plists at
=lisp/layers/harness/e-process-reporting.el:508-550=. =json-encode= interprets
that shape as an alist/object rather than a JSON array. A two-entry chain is
written as one object with duplicate =activity-event-id= keys whose values are
flattened plist arrays. Reloading it yields a malformed plist, not a list of
trigger records.

The fresh reload probe saw a valid list of length two before persistence and a
plist of length four after persistence. Normal =:read= therefore cannot return
the nested chain documented by the resolution.

*** Why this matters

The durable evidence loses its action/tool structure across the first reload.
Offline extraction cannot reliably recover the action call, enclosing tool, or
parent relation from the marker record.

*** Smallest fix direction

Encode repeated records as vectors or otherwise force JSON arrays, and validate
record shapes while loading. Add a write/reload/read test for direct actions,
action-inside-tool, and deeper nested tool/action chains. Assert the exact
post-restart call ids and parent ids, not only the in-memory return from =mark=.

*** Resolution and evidence

Marker serialization now forces =:trigger-chain= to a JSON array and validates
its entries on reload. The nested-action test reloads through a fresh store and
asserts the exact action id, parent tool id, enclosing tool id, and event type.

** DONE High: Durable telemetry still has secret-redaction bypasses

*** Expected

The prior finding's narrowed contract says persisted free text crosses the
shared redaction boundary and durable activity uses named safe schemas. It must
not imply that naming a field makes arbitrary string content safe.

*** Observed

The shared string redactor does not recognize common standalone provider key
forms such as GitHub =ghp_= tokens, OpenAI =sk-proj-= keys, or AWS access key
ids. Fresh probes returned all three unchanged.

More directly, =e-harness--safe-tool-result-metadata= at
=lisp/core/e-harness.el:951-960= copies the named string fields =:tmp-uri= and
=:resource-uri= verbatim. A probe retained URL userinfo and query secrets
exactly in durable =tool-finished= activity. These fields bypass the redactor
because the allowlist is treated as content-safe.

The compaction function at lines 992-1000 also returns an unprojected payload
when =:result= is not recognized as a structured tool result. A malformed or
legacy event probe persisted raw =token= and authorization metadata. This is a
general telemetry regression introduced by making only one expected result
shape safe.

*** Why this matters

Resource URLs commonly contain credentials or signed query strings. These
values now persist indefinitely in session telemetry despite the documented
redaction boundary. Marker trigger previews can then link to that compromised
activity.

*** Smallest fix direction
