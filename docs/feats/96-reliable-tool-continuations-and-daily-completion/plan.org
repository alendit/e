* Behavioral goal

** Goal record

- Goal ID :: =F96-RELIABLE-COMPOSED-TURNS=
- Behavioral goal :: A Board-run worker can execute an admitted tool, continue
  its provider turn, and converge through one durable terminal transition.  A
  Daily coordinator can then edit the exact target with ordinary tools and have
  the successful turn save and commit that edit without a Daily-specific
  publish, reconcile, or completion protocol.
- Direct scenario :: Start a Daily run containing a large-output Bash worker,
  an eager-MCP Slack worker, a Bash-backed calendar worker, and the final
  direct-write coordinator.  Tool results survive invocation-detail archival
  and provider continuation.  An intentionally failed child publishes its
  original failure durably before its Work is retired, even when progress
  projection fails and a deadline later fires.  The coordinator writes the
  exact =file://= Daily; the ordinary successful turn saves and commits only
  that file and admitted artifacts.
- Product authority :: Generic =e= tool archival and subagent lifecycle
  contracts, composed by the project-local Grimoire Daily extension.
- Owning contracts :: =F96-C01=--=F96-C06= below.
- Behavioral status :: Not yet available.  The 2026-09-21 run exposed a
  reproducible large Bash archival failure, child failures which appeared only
  as later deadlines, a calendar assignment without executable CLI guidance,
  and an unsaved =buffer://= coordinator edit.

This feature repairs each behavior at its semantic owner.  It does not create a
Daily lifecycle or make the Daily controller inspect session journals.

* Authority and prerequisites

- Feature 55 remains authoritative for the generic Work lifecycle.
- Feature 82 remains authoritative for Board-native supervision and requires a
  durable terminal report before local Work settlement and live retirement.
- Feature 93 Addendum 3 remains authoritative for direct Daily writing.  This
  plan strengthens ordinary save/commit composition; it does not restore
  reconciliation, model acknowledgement, target echo, section submission, or
  a Daily publication tool.
- Feature 94 remains authoritative for canonical JSON: adapters decode once,
  core carries typed values, and wire adapters serialize once.  Its canonical

No legacy behavior identified below is a compatibility requirement.

** Child terminal split

=e-subagent-direct-runner= observes progress and terminal session events in one
subscription callback.  It invokes the consumer progress callback before
terminal cleanup/settlement.  If progress projection throws, the chat service
faults that subscription, so the only terminal observer can disappear.  The
current settlement path also starts asynchronous Board terminal publication
without awaiting its Work and can retire local state first.  A later deadline
then becomes the visible failure even though the session already recorded the
original cause.

The repair spans the actual two owners.  The direct runner isolates progress
projection and delivers one terminal proposal.  The surrounding subagent
coordinator owns child Work, Board target, assignment, and live state, so it
installs one narrow asynchronous Work terminal gate before the handle starts.
The gate latches the first proposal, publishes its idempotent durable terminal
report, awaits that publication Work, and only then commits the proposed Work
terminal state and retires live state.  The existing Work deadline still owns
expiry and provider cancellation; expiry proposes =e-work-deadline-exceeded=
through the same gate instead of bypassing it.

If publication itself fails, the gate commits a typed persistence-suspect Work
failure containing both the original child proposal and publication error, then
retires process-local state.  No automatic retry or promise to reconstruct the
original session cause after a crash is added.  On reopen, a terminal fact which
did commit wins idempotently.  Otherwise existing Grimoire recovery remains
authoritative: an orphaned running attempt 0 advances through a durable
=attempt-selection= to attempt 1; an orphaned running attempt 1 becomes a
terminal orphan failure; and only a pending selected attempt is redispatched
without changing its attempt identity.

** Daily composition gaps

Calendar already selects =fast-tool-user=, which admits Bash.  The defect is
only its vague assignment: unlike the working CLI-backed sources, it does not
name the bounded =gog calendar events primary --from <start> --to <until>=
operation or require a typed unavailable result on authentication/nonzero exit.
No worker-profile or Gmail change is justified.

The direct-write coordinator already owns an exact closed =:daily-commit-files=
set.  The normal turn-finished commit hook stages disk bytes, but a model may
legitimately edit a visiting buffer whose generic write reports =saved=false=.
The application hook must noninteractively save modified buffers visiting only
those exact paths before exact-path Git bookkeeping.  Coding-system/write
errors fail the coordinator turn; unrelated buffer semantics and repository
dirt remain untouched.

* Smallest faithful design

The selected design is four independent owner-local packages:

1. correct invocation-detail metadata projection and delete the zero-production-
   consumer callback compatibility constructor;
2. add an asynchronous terminal gate at the generic Work settlement seam,
   supplied by the subagent coordinator that owns Board convergence, while the
   direct runner isolates progress observers;
3. make the existing calendar assignment executable through its already
   admitted Bash/CLI capability; and
4. make exact Daily save an explicit precondition of the existing exact-path
   commit hook.

These packages compose only in the final Daily scenario.  They do not depend on
each other's implementation.

Rejected alternatives:

- relaxing duplicate-key rejection or deduplicating arbitrary plists at the
  serializer would hide owner corruption;
- reworking accepted typed provider continuation without a failing counterexample
  would duplicate Feature 94 and broaden this feature speculatively;
- polling session journals from the Daily controller would create a second
  terminal projection;
- settling local Work before the durable report acknowledges would violate
  Feature 82; a second outer Work would also leave cancellation with the wrong
  semantics, so the existing enrolled Work receives a narrow terminal gate;
- swallowing Board publication, save, coding, or Git errors would replace the
  causal failure;
- changing generic =buffer://= writes to save files would violate their live
  resource contract; and
- another Daily =publish=, =complete=, or =reconcile= action would recreate the
  obsolete protocol already removed by Feature 93.

* Owner profiles

** Invocation details

The archival adapter maps domain metadata to canonical JSON.  It must classify
containers by their declared/domain shape: a resource-usage collection is an
array of records, each record is an object, and each resources field is an
array.  It must not infer "alist object" merely because every list element is a
cons.  The mapping remains detached and streaming; provider, session, and tool
owners are unchanged.

Because =e-tools-callback-work= has no production consumer, remove it rather
than preserving or repairing its second request-adoption protocol.  Test
fixtures needing callbacks use a test-local Work spec.  Production exposes one
Work contract, not a compatibility constructor used only by tests.

** Child terminal convergence

The existing enrolled child Work remains the one caller-visible lifecycle.
=e-work= gains one narrow optional terminal-gate seam installed before start,
parallel to its existing enrollment observers.  Ordinary Work without a gate is
unchanged.  For a gated Work, =finish=, =fail=, and =cancel= first propose an
immutable terminal state; the gate asynchronously authorizes the internal
terminal commit after its owner-side durability operation.  First proposal
wins.  The core does not import Board types or publication policy.

The subagent convergence coordinator, not the low-level direct runner, owns the
gate state machine because it holds the enrolled Work, Board target, assignment,
and live entry:

1. =running=: observe session lifecycle; project progress in an isolated
   best-effort boundary;
2. =publishing=: atomically latch the first terminal cause and start one
   idempotent Board terminal report;
3. =publication-failed=: commit one typed persistence-suspect Work failure
   carrying the proposed cause and publication error, then retire live state;
   or
4. =settled=: after publication Work succeeds, commit child Work from the
   latched cause, unsubscribe, cancel deadline, and retire the live entry.

All post-admission terminal inputs use the same transition: session
completion/failure, cancellation, synchronous runner failure, and deadline.
Reentrant/late inputs are no-ops after latching.  The Work deadline
continues to fire at the exact runtime-owned instant and cancels the provider,
but its terminal commit waits for the Board report acknowledgement.  A failed
publication is not retried inside the process and is never turned into deadline,
cancellation, or success.  On process reopen there is deliberately no attempt
to recover a lost process-local proposal from the session journal: Grimoire's
existing recovery first observes any idempotently committed terminal fact,
otherwise advances an orphaned initial running attempt to its one durable
successor, terminalizes an orphaned successor, or dispatches an already-pending
selected attempt unchanged.

Public =interrupt= and =shutdown= enter this same coordinator transition.  They
invoke provider cancellation promptly and once, propose =cancelled= through the
enrolled Work gate, and do not directly settle Work or remove live state.  A
held terminal publication therefore retains Work/live ownership until
acknowledgement; publication failure yields the composite persistence-suspect
failure instead of a cancelled Work.  For a run-bound cancellation while Board
participant admission is still pending, the coordinator first removes the
startable reservation as an immediate fence.  The admission Work is best-effort
only—its SQLite child may finish later, but every completion branch observes the
absent reservation and cannot install live state or invoke the runner.  A
detached gate closure, not a second startable reservation, retains the prepared
child Work, terminal proposal, assignment, and dispatch-settlement callback
while it publishes the idempotent =cancelled= terminal report.  Acknowledgement
commits the child Work cancellation and finishes the separate run-bound
dispatch Work with a bounded cancelled result; publication failure commits and
propagates the same composite persistence-suspect failure to both Works.  An
ad-hoc pending admission has no durable run task: it fences the reservation
immediately and retains local cancellation/retirement semantics.

The reservation check encloses the entire asynchronous admission settlement,
not only success.  Once fenced, late =finished=, =failed=, or =cancelled=
admission may perform request-local cleanup only: it cannot touch the prepared
child Work, call =on-failure=, publish a competing terminal report, settle the
dispatch Work, install live state, or invoke a provider.  The gate is the sole
remaining settlement owner.  Grimoire's dispatch fan-in consumes its bounded
=:status cancelled= result explicitly: it increments =:cancelled= and sets the
overall start/recovery state to =attention= when either failed or cancelled
dispositions are present, instead of silently omitting cancellation from all
totals.

The direct runner separately owns progress safety.  It never invokes a terminal
progress projection before delivering the terminal proposal, and wraps all
consumer progress callbacks so their errors become bounded diagnostics rather
than subscription faults.

** Calendar assignment

Grimoire owns task-to-prompt mapping.  Calendar remains a =fast-tool-user= and
uses its admitted Bash tool to invoke =gog=.  The assignment supplies exact
start/end timestamps already owned by the run manifest, commands the primary
calendar query, and defines the typed unavailable outcome.  It does not change
Gmail, Slack, worker profiles, or capability readiness.

** Exact Daily save and commit

The topic commit application service already owns exact-path bookkeeping.  It
normalizes and validates the closed file set, finds only live buffers whose
visited files are members, and saves modified ones with an explicit
noninteractive coding policy before staging.  It never saves unrelated buffers
or interprets model prose.  Any save or coding failure aborts before Git; any
Git failure remains the turn failure.  File-tool writes need no buffer save.

* Scenario portfolio

** F96-S1: large Bash metadata archives and continues

A production Bash call emits more than the inline threshold and supplies two
=resource_usage.resources= entries.  Invocation details stream the full output,
archive =tool-usage= as an array containing one record whose resources are an
array of two objects, return the bounded tool result, persist the transcript,
and build the next OpenAI request.  Encoding/decoding the archive is exact.
An explicitly malformed duplicate-key canonical object still fails.  Accepted
Feature 94 nested typed arguments, immediate continuation, and full replay
regressions also pass.

** F96-S2: terminal report precedes retirement under adversarial callbacks

A child with a future deadline emits nonterminal progress and then
=turn-failed=.  The supplied progress callback throws for both classes of event.
Terminal observation still proposes the original cause.  With Board publication
held beyond the child Work's actual deadline, the deadline cancels execution
but cannot commit a competing Work failure: the first proposal remains latched,
Board report Work remains active, and child Work/live ownership remain.  After
publication succeeds, the report is queryable before child Work commits and the
live entry disappears.  Duplicate/late callbacks change nothing.

In the failure branch, publication Work fails.  The child Work then fails once
with a typed persistence-suspect condition containing both the original child
proposal and the publication error, without a false terminal Board fact.  A
real process reopen covers three existing recovery partitions: a terminal fact
which committed despite an ambiguous acknowledgement wins; otherwise orphaned
running attempt 0 publishes =attempt-selection= for attempt 1 and dispatches
that successor, while orphaned running attempt 1 publishes one terminal orphan
failure.  A separately pending selected attempt is the only branch redispatched
without changing identity.  No new retry command or session-journal
reconstruction is introduced.

The cancellation partition invokes public =interrupt= and =shutdown= while
terminal publication is held.  Provider cancellation happens promptly and
once; the cancelled proposal wins; Work and live ownership remain until
acknowledgement, then Work commits =cancelled= and ownership retires.  When the
publication Work fails, Work instead commits the composite persistence-suspect
failure.  A run-bound pending-admission cancellation similarly acknowledges one
cancelled terminal report, but removes its startable reservation before
publication begins.  While publication is held, force participant admission to
finish, fail, and cancel both before and after terminal acknowledgement.  Every
ordering is inert with respect to child Work, =on-failure=, terminal facts, and
dispatch Work; none may install live state or start a provider.  Terminal
acknowledgement alone settles the separate dispatch Work as cancelled and
produces one cancelled terminal fact; terminal publication failure alone fails
it with the composite condition.  Daily fan-in reports =:cancelled 1= and
=:state attention= for the bounded cancelled disposition.  An ad-hoc pending
cancellation remains local because no durable assignment exists.

** F96-S3: executable calendar assignment

A fresh calendar worker keeps =fast-tool-user=.  Its assignment includes
=gog calendar events primary --from <start> --to <until>= for the manifest's
frozen window and instructs the worker to classify missing auth or nonzero exit
as typed source unavailability.  A fixture proves the exact command and both
success/unavailable result shapes.  Gmail and Slack assignments are unchanged.

** F96-S4: direct Daily save and exact commit

The coordinator receives bounded fan-in and an exact =file://= target.  A test
model edits a visiting Daily buffer and ends the turn while it is modified.
The turn-finished application hook saves that exact buffer noninteractively,
then commits only it and admitted artifacts.  The on-disk bytes and commit match
the buffer; unrelated dirty/staged files and buffers remain untouched.  Invalid
coding/write and Git failures each fail the coordinator turn without hanging.
A file-tool write still succeeds.  Structural checks find no Daily reconcile,
publish, complete, content-gate, target-echo, or lifecycle-stamp operation.

* Compatibility, state, and performance

No SQLite migration is required.  Existing session, Board, and Grimoire file
state remain authoritative.  The archival correction changes only malformed
metadata projection.  Terminal convergence preserves Work-owned deadline and
cancellation while delaying only the terminal commit for Board-enrolled Work;
it uses the existing stable report identity and adds process-local state only
while publication is in flight.  Publication failure and crash recovery reuse
the existing persistence-suspect and bounded attempt-advance/orphan-terminal
policy.  Calendar adds no capability.  Daily saving inspects only a
closed file set.  No unbounded scan, polling loop, wire-text duplicate, or
durable mirror is introduced.
