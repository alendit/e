* Vocabulary and identity decision

The definitions of =board=, =participant=, =session=, and =shell-facing action=
come from =docs/references/runtime_concepts.org=.

The Daily document persists one runtime identity: its Board id.
It does not persist an owner session id, participant id, work handle, run id, or
live-execution identity.
The Board is the durable collaboration, routing, observation, and run-history
boundary.
Main is the Board's owner participant; its current session remains an internal
runtime association that the chat service resolves from SQLite.

An absent =E_BOARD= on a legacy Daily permits a one-time migration from a valid
=E_SESSION= association, after which =E_SESSION= is removed.
A present =E_BOARD= is authoritative.
If that Board cannot be resolved, the workflow fails visibly instead of silently
changing the document to a different collaboration history.

* Problem and causal evidence

Today's Daily stores only =E_SESSION=, so every entry point resolves the runtime
session before deriving the Board.
The Board remains an implementation detail even though it owns the durable run.

The configured Grimoire Daily controller was not migrated with Feature 82.
It still queries the removed public subagent registry and passes that retired
registry into spawn.
The manifest and =started= lifecycle commit before this call, so the missing
symbol aborts dispatch before the first worker while leaving the Board apparently
active.

The model-facing =daily-run/:start= adapter registers a cheap action but returns
a plist containing a raw =e-work= handle.
The handle is not registered as the top-level =work:= result required by the
action contract.
Main therefore received =preparing=, could not await the nested handle, retried,
and made unsupported progress claims.

Main also received no bounded projection of the already-started run.
Board observation was discoverable only through poorly described
=subagents/:list= and =:list-runs= actions, while the configured Daily activity
command still called the two shells removed by Feature 82.

* Aggregate design comparison

** Current aggregate

The Org document persists a session id.
Grimoire derives a Board binding from it, implements its own owner recovery,
starts a second process-local work object from a cheap action, consults a removed
registry before spawning, and sends observation through deleted shells and a
=subagents= namespace.
Durable start and ephemeral dispatch failure cross different reporting
boundaries.

** Smallest faithful alternative

Persist the Board id once.
Derive a stable Daily creation key, let =e-chat-service= atomically and
idempotently admit its deterministic private owner tuple, and persist the
returned Board id only after acknowledgement.
Let =e-chat-service= also own one consumer-shaped Board-to-owner resolution
operation.
Let the Grimoire controller receive the resolved binding, publish manifest and
dispatch state to that Board, and expose its asynchronous work directly through
the action dispatcher.
Let one bounded Board run-set projection value feed chat context and status.
Let the =board= capability route participant/activity actions to Feature 82's
Board observation service and run-list/run-status actions to the Board
orchestration projection service; let the Board activity shell continue to
consume the bounded participant/activity page.
Keep only executing handles and controls behind runner-owned consumer
operations; Grimoire and Board services never receive the private
live-execution owner.

** Decision

Use the smallest faithful alternative.
Do not add a second document property, compatibility alias, session cache,
Board mirror, or fallback inventory.

* Ownership and boundaries

- =e-chat-service= owns stable-key owner admission, Board-to-owner session
  resolution, and exact live-binding installation because it already owns
  session/Board associations and bindings.
- SQLite session and Board services own the bounded authoritative query.
- The Grimoire Daily controller owns note-to-Board mapping, run policy,
  dispatch, retry, and lifecycle facts.
- =e-board-orchestration= owns run reduction and the Board run-set projection
  schema.
- A session-scoped projection composition owns only the current bounded value
  and change notification; Main context and chat status are independent
  consumers of that value.
- The Board observation service owns the distinct participant/activity page
  consumed by Board actions and the activity shell.
- =subagents= owns spawning and runner-mediated live participant controls only.
- The Board activity shell owns detached display state and interaction.

* Compatibility and removals

Legacy Daily =E_SESSION= has one bounded migration requirement only when
=E_BOARD= is absent; it is migration input, never a steady-state routing
identity.
There is no requirement to retain either session property after successful
migration or to retain durable observation aliases under =subagents=.
Migrate all in-tree and configured Grimoire callers, documentation, keymaps,
generated autoload inputs, and tests; add no action alias, shell alias, or
fallback inventory.
Generic non-Daily topic/project session properties are outside this addendum and
remain unchanged.
Existing SQLite Board, session, participant, pickup, and orchestration records
require no schema or data migration.

** Package relation

F93A1-DP1 is the reusable e-owned prerequisite and depends only on accepted
runtime and Feature 82 Board contracts.
It establishes the Board-addressed owner, observation, and active-run
context/status surfaces before any configured consumer is migrated.
DP1 provides and independently gates the e-owned admission primitive required
by F93A1-C01; DP2 alone establishes F93A1-C01 end to end by composing that
accepted primitive with Daily document persistence and migration.

F93A1-DP2 consumes only accepted DP1 contracts and closes the Grimoire-owned
Daily document, startup, dispatch, failure, recovery, activity, and
configured-consumer composition.
Splitting identity migration from dispatch/failure truth would expose an
accepted Daily that opens under =E_BOARD= while still executing retired dispatch
behavior; combining DP1 and DP2 would erase the independently useful e/Grimoire
compatibility boundary.
