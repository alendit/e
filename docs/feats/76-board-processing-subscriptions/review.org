* Review summary

Commit =0d453e44= establishes the processing subscription fields and immutable
record types, but Slice 1 does not yet meet its exit criteria.  Invalid
replacement can cancel a valid subscription, processing records can collide in
the shared durable journal, the registry replacement API cannot change the new
policy fields, and deterministic priority ordering is not represented or tested.

* Findings

** DONE High: Validate replacements before cancelling the active subscription

=e-board-replace-subscription= cancels the old subscription at
=lisp/core/e-board.el:2190=, then delegates validation and creation to
=e-board-subscribe= at line 2194.  An invalid replacement contract therefore
throws after the valid old route has already become terminal.  Slice 1 requires
validation at replacement without damaging existing behavior.

Validate the complete replacement declaration before transitioning the old
subscription, or construct the replacement transactionally and publish it only
after every check passes.  Add a regression test that an invalid replacement
leaves the old subscription active.

** DONE High: Give processing records collision-safe durable identities

Chains and results reject duplicate IDs only within separate board tables at
=lisp/core/e-board.el:523= and line 562.  The session journal deduplicates every
board envelope solely by =:id= at =lisp/core/e-session.el:2432=.  A chain and
result with the same explicit ID, or a processing record colliding with a
message ID, silently drops the later durable envelope.  Replay can then lose a
committed record.

Use a journal identity that includes record kind, or enforce one board-wide ID
namespace shared with persisted messages.  Add session-backed persistence and
restart tests for colliding raw IDs.

** DONE Medium: Expose processing policy through registry replacement

=e-board-registry-install-subscription= forwards =:delivery=, =:priority=,
=:self-delivery=, and =:failure-policy= at
=lisp/core/e-board-registry.el:1056=.  The matching registry replacement API at
line 1096 accepts and forwards only =:effect= and =:state=.  Registry clients
cannot replace a normal subscription with a processing subscription or change a
processing policy through the registry boundary.

Add supplied-p arguments for all four fields and forward only explicitly
provided values, matching the core replacement API.

** DONE Medium: Represent and test deterministic processing order

The implementation validates and stores priority at
=lisp/core/e-board.el:1541= and line 1631, but it defines no ordering helper or
comparator.  The Slice 1 exit criterion explicitly requires ordering tests,
including stable subscription-ID ordering for equal priorities.  The three new
tests cover defaults, invalid declarations, and record envelope replay only.

Add a pure ordering function over processing subscriptions and tests for
descending priority plus stable subscription-ID tie-breaking.  Slice 2 can then
consume that contract without redefining it.

* Architecture review

The records live in the board, which matches the plan's ownership rule.  The
chat service adapts board notifications to session persistence, which keeps
persistence side effects outside board policy.  The shared journal identity
contract is the main boundary defect: board-local record tables and the session
journal currently disagree about uniqueness.

* Resolution evidence

- Invalid replacement validates the complete inherited and supplied declaration
  before cancelling the active route.  The regression test proves a normal
  subscription remains active after an invalid processing-only priority.
- The session board journal now deduplicates on =(record-type . id)=, with
  =board-message= as the ordinary message namespace.  A persistent restart
  test retains a message, chain, and result that use the same raw ID.
- Registry replacement accepts supplied-p =:delivery=, =:priority=,
  =:self-delivery=, and =:failure-policy= fields and forwards only fields the
  caller supplied.  The regression test replaces a normal route with a
  processing route and verifies all four stored policy values.
- =e-board-order-processing-subscriptions= defines descending priority then
  ascending durable string subscription-ID ordering.  The regressions cover
  priority ordering, equal-priority ID tie-breaking, reverse input order, and
  rejection of IDs without a persistent total order.
- Processing chain and result records deep-copy every retained identity.  The
  ledger stores them only in private slots; creation, notifications, public
  accessors, and exported envelopes return detached copies.  The mutation
  regression verifies caller-owned timestamps and every public record path
  retain their pre-mutation values.
- Processing subscription IDs are copied durable strings.  Equal-priority
  processing order therefore has a replay-stable total key, while normal
  subscriptions retain their legacy identifier compatibility.

* Third fix-point resolution evidence

- Normal subscriptions accept legacy symbol IDs unchanged.  Processing
  subscriptions alone require durable string IDs, which preserves the existing
  deterministic priority and ID ordering contract.
- Processing record persistence runs before board ledger publication.  The
  chat-service regression covers an error after the journal append, then proves
  a retry creates one in-memory record and retains one deduplicated envelope.

* Independent re-review findings

** DONE High: Freeze all processing record identities

=e-board-record-processing-chain= and =e-board-record-processing-result= now
deep-copy every retained identity, including record, board, chain, subscription,
participant, candidate, and replacement IDs.  The mutation regression changes
the caller-owned strings after commit and verifies both retained records and
exported envelopes preserve their original identities.

** DONE Medium: Define a total ordering for heterogeneous subscription IDs

=e-board-order-processing-subscriptions= now orders equal priorities by a
canonical key containing both ID type and printed representation.  The
regression verifies string ="a"= and symbol =a= produce the same fixed order
when supplied in either direction.

* Fix-point re-review findings

** DONE High: Keep retained processing records immutable through public access

The ledger now retains records only in private board slots.  Record creation,
notifications, public ledger accessors, and journal envelope export each return
detached deep copies.  =created-at= passes through the same freezing boundary as
all other retained fields.  The regression mutates the caller timestamp,
returned record, notification record, listed record, and exported envelope, then
verifies the retained ledger remains unchanged.

** DONE Medium: Constrain IDs or define a truly total persistent ordering key

Processing subscription IDs are durable strings, copied on entry before
retention.  Processing order uses that stable string identity after priority, so
no process-local identity tie-breaker is needed.  Normal subscriptions retain
their legacy IDs.  The regression rejects processing symbols and numbers,
proves caller mutation cannot alter a retained ID, and verifies reversed
equal-priority inputs sort to the same order.

* Third fix-point re-review findings

** DONE High: Preserve ordinary subscription ID compatibility

The durable string requirement now applies only to =process= delivery.  Normal
subscriptions retain their existing ID contract, including symbol IDs.  The
processing ordering function accepts only processing subscriptions and keeps
its deterministic string-ID tie-breaker.  The regression proves a normal symbol
ID is retained unchanged and remains findable.

** DONE High: Make processing-record persistence failure atomic or retryable

The board invokes the processing-record persistence callback before appending
the in-memory ledger record and event.  A callback failure therefore leaves the
ledger ID available for a retry.  The chat-service adapter persists through the
session journal's record-type-and-ID identity, so a retry after an uncertain
post-append callback failure is idempotent: it commits the ledger record without
duplicating the durable envelope.  The regression simulates that failure through
the chat-service adapter, then retries and verifies one durable envelope and
one ledger record.

* Fourth fix-point re-review findings

** DONE High: Reject divergent duplicate durable processing envelopes

The session journal now retains the frozen envelope for each typed processing
identity.  An identical retry remains a no-op, while a different envelope with
the same record type and ID signals =e-session-board-message-conflict= before
the board commits it.  The post-append failure regression retries first with a
divergent candidate ID and proves no ledger record is published, then retries
the original fixed-timestamp envelope and proves it commits once.  The session
regression covers the same typed-journal conflict directly.

** DONE High: Reserve processing record IDs across persistence callbacks

The board reserves the typed processing ID before notifying persistence and
releases it with =unwind-protect= after success or failure.  A reentrant callback
therefore receives =e-board-id-conflict= rather than committing the outer ID.
The regression proves the outer call emits exactly one ledger record and one
processing event.  The uncertain-persistence retry also proves a failed callback
releases its reservation for the subsequent identical retry.
