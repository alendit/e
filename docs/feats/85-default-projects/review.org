* Review loop

** DONE Medium: Startup priming initially preceded byte-recompile policy

*** Problem

Grimoire moved from project-entry priming to startup priming, but
=e-project-local-auto-byte-recompile= was still assigned in Doom's
=use-package! e= =:config= block.  Package startup runs before =:config=, so
the first implementation could load Grimoire without applying the documented
stale-bytecode policy.

*** Change

Moved both =e-default-projects= and
=e-project-local-auto-byte-recompile= into the =:init= block.  Grimoire is no
longer duplicated in =e-project-local-allowed-roots= because default-project
membership is itself the explicit trust declaration.

*** Evidence

The real-project batch startup loaded the Grimoire topic layer and exposed both
=grimoire-daily= and =grimoire-topic-open=.  Retangling =config.org= regenerated
the committed =config.el=, and the file reads completely in batch Emacs.

* Architecture review

The harness owns only stable root policy and its pure projection.  The
project-local layer owns trusted code loading and startup side effects.  The
machine-specific Grimoire path remains in user configuration.  No session
record, compatibility path, or fallback loader was added; roots are derived
from current configuration on demand.

The design self-check in =plan.org= remains accurate.  The only review finding
was the configuration timing issue above, which is resolved.

* UX and performance playthrough

There is no new interactive surface.  Startup with one real default project
completed in the isolated batch process and made Grimoire commands available.
Workspace-root composition remains a linear pass over short configuration
lists, with focused tests covering ordering and de-duplication.

* Live reload

The user's running Emacs was left unchanged.  =e-harness.el= is core runtime
and the Doom setting must exist before package startup, so a full Emacs restart
is required; =e-dev-reload= is not an applicable completion step.
