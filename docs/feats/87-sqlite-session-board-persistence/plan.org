* Goal and boundary

One =<e-state-directory>/store.sqlite3= becomes the only ordinary persistent
authority for all e-owned mutable runtime state:

- sessions, catalog and resume projections, message display, and durable tool
  follow-up classification;
- Board records, routing outcomes, pickup FIFO/lifecycle, and replay progress;
- task queues, attempts, cron cadence and firing claims;
- voice tells and Goodnite demand events;
- =raw-result://= and e-managed session =tmp://= resources, including complete
  tool-invocation details.

SQLite owns durable facts and transition arbitration.  Domain modules own
meaning and policy.  Memory holds provisional intent, caches, executable
subscriptions, callbacks, timers, live handles, endpoints, and presentation
state.  Every durable transition is commit-first.

Files remain when file identity is the product or protocol: user-authored files,
explicit exports and backups, migration reports, screenshots, diagnostics, and
subprocess artifacts that genuinely require a pathname.  Such artifacts are
not a second runtime-state authority.

Feature 89 owns chat-visible Board-run status and completion handoff.  Feature
90 owns the meaning and publication of complete tool-invocation details.
Feature 87 supplies their durable storage and restart boundaries without taking
over their product policy.

* Accepted decisions

The matrix incorporates these operator decisions:

- one physical database and one e runtime per state directory;
- every database read and write goes through the worker;
- durable state is commit-first rather than an asynchronous mirror of mutated
  Lisp state;
- stable Board routing and pickup state is durable, while executable predicates,
  callbacks, endpoint objects, timers, and Feature 91 admission tokens are not;
- task and cron work is claimed durably before action;
- e-managed =tmp://= and raw-result content moves into SQLite;
- session, Board, task, and cron audit remains until explicit owner deletion;
  expired resources are physically deleted, and Goodnite cleanup follows an
  acknowledged consumer checkpoint;
- session deletion purges private state but not shared Board history or old
  operator backups;
- committed routing outcomes are final; historical rerouting is explicit;
- typed composite transactions exist only for accepted cross-owner invariants;
- =synchronous=NORMAL= is sufficient; host/power-loss preservation of the latest
  acknowledgement is not promised;
- migration and schema upgrades are explicit offline actions;
- backups are explicit except for the verified backup created by the explicit
  schema-upgrade operation; deletion creates no automatic backup;
- restrictive local permissions are required for the store and every
  operator artifact; encryption/key management is not;
- the first resource implementation uses one BLOB and a generous private limit,
  not chunk streaming;
- shells may display pending intent, but agents and durable projections see only
  committed state; cancellation drops work only before submission.  Once sent,
  worker loss fails the operation and requires close/reopen plus owner reload;
  the runtime never resubmits an ambiguous write.

On 2026-09-02 the operator simplified the accepted mechanism without changing
semantic ownership or package scope.  Stable command identities, reconciliation
hashes, the durable writer-command ledger, ordinary expected-revision/CAS, and
automatic worker restart/resubmission are no longer part of Feature 87.  The
single worker serializes ordinary owner operations; natural positions,
generations, attempt identities, and SQLite constraints remain.  A missing ACK
is storage-unavailable, not evidence of rollback or permission to retry.

* Package boundary rationale

P1 combines infrastructure with its first full consumer so it does not stop at
an unused adapter.  P2 remains separate because Board publication/routing and
the one real Board/session atomic composition have a distinct owner and failure
surface.  P3 groups smaller existing file stores because they share the same
mechanical migration pattern but retain separate semantic ports; splitting them
would create small repetitive cycles without changing a design decision.  P4
combines migration and cutover because neither is a safe stopping point alone:
the default changes only after every owner and rollback proof is complete.

* Acceptance decision

Feature 87 becomes =Done= only when:

- every =F87-C*= contract is established by its mapped package;
- S1-S11 pass on the same reviewed revision;
- all four packages and their focused gates are complete;
- the complete repository and isolated graphical gates plus the current-config
  compatibility runner pass against disposable SQLite stores; any Feature

- migration proof used only a copy of operator state and the running Emacs was
  not opened, migrated, reloaded, or restarted by repository validation;

Implementation progress and behavioral progress remain separate.  Passing
owner/mechanism tests does not make =F87-GOAL= pass before S1 succeeds.

* Non-goals

- Persisting active turns, provider requests, callbacks, timers, work handles,
  executable Board subscriptions, exact admission tokens, endpoint objects,
  Lisp predicate closures, focus, windows, overlays, render caches, or other
  process/presentation state.
- Exactly-once execution of arbitrary external effects.  Ambiguous worker
  acknowledgement and in-flight external work fail visibly; deliberate owner
  action may inspect canonical state but the runtime never retries them.
- Latest-acknowledgement survival after host failure or sudden power loss.
- Generic SQL, transaction builders, or cross-owner mutation ports exposed to
  agents, shells, capabilities, resources, or domain owners.
- Chunk-streaming resource storage before observed sizes justify it.
- Encryption at rest or key management.
- Full-text search, cloud sync, shared network storage, concurrent multi-runtime
  consumption, or a generic capability-projection framework.
- Automatic startup migration, permanent JSONL dual write, runtime legacy
  replay, format fallback, or deletion of preserved legacy sources.
- Treating one session as the owner of a Board shared by several participants.
- Rewriting operator-created historical backups during live deletion.

* Compatibility and operator boundary

Cutover requires Emacs 29.1 or newer with built-in SQLite support.  Ordinary
startup may create a new current schema, but an older legacy or SQLite schema
reports a targeted migration-required error.  For legacy state, that error
names the common e root and the explicit copied-source, sibling-backup cutover
command.  Defaults identify the common root from the conventional
=<root>/sessions= layout only; operators with a custom session-directory leaf
must set =E_RUNTIME_STATE_DIRECTORY= to the actual common root.  Legacy
migration, same-root rotation, and future schema upgrades are explicit offline
operations.  Backups are explicit except for the preserved legacy-root backup
made by cutover and the verified pre-upgrade backup made by the upgrade
command.

Repository validation uses disposable stores and never opens or migrates the
operator's live store.  Running Emacs remains untouched.  Core runtime, worker,
session, Board, and record-shape changes require a full Emacs restart when the
operator chooses to use the new implementation; =e-dev-reload= is insufficient.

* Design self-check

1. *Useful stopping points*: Each package closes owner semantics, durable state,
   recovery, public composition, and focused evidence; none is only a helper or
   checkpoint.
2. *Final direction*: One SQLite authority replaces every hidden runtime-state
   file and duplicate durable in-memory Board collection.
3. *Stable versus uncertain*: Ownership, commit-first visibility, exact value
   shape, recovery classifications, retention classes, migration, and failure
   boundaries are stable.  Table names, private limits, page sizes, worker
   framing, checkpoint cadence, and chunking remain local and revisable.
4. *Ownership*: Session, Board, task, cron, voice, Goodnite, and resources keep
   their semantic ports.  The adapter owns only physical storage and typed
   composite execution.
5. *Coupling*: Sharing one database removes duplicated persistence while narrow
   ports and one use-case-specific composition prevent representation coupling.
6. *Dependency direction*: Domain policy defines commands/projections; the
   SQLite adapter depends on them.  Policy does not depend on SQL or tables.
7. *Side effects*: Database, migration, backup, export, and maintenance work is
   in the worker/adapter; shells request application operations only.
8. *State lifetime*: Durable facts and accepted recovery state persist by owner
   retention; rebuildable projections are indexed; live objects remain local.
9. *Performance*: Main Emacs performs no SQL; reads are bounded and yield to
   commits; the known large-session fixture and graphical timer prove the hot
   paths.
10. *Substitutability*: Owner ports contain only supported owner operations;
    there is no generic SQL, fake alternative backend, or unsupported method.
11. *Compatibility*: One explicit importer and upgrade path replace runtime
    fallback; preserved sources remain inactive rollback material.
12. *Removal*: Node/JSONL, checkpoints, derived index, sidecar stores, Board-log
    proxy, persistence callbacks, and duplicate durable indexes are deleted
    after proof.
13. *Errors*: Owner validation and SQLite constraints surface visibly.  Worker
    loss fails outstanding requests once and requires explicit reopen/reload;
    corruption, schema/value/identity conflicts, and uncertain effects are not
    swallowed or automatically retried.
14. *Tests*: Pure policy tests remain storage-independent; disposable-SQLite
    owner, composition, migration, restart, graphical, and system scenarios
    fail at narrow boundaries.
