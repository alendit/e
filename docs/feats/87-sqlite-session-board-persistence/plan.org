#+title: SQLite Runtime State Persistence
#+startup: overview

* Status

Planned.

* Goal

Make one SQLite database the durable authority for all e-owned mutable runtime state.
This includes sessions, boards, session-owned lifecycle facts, task queues, cron cadence, voice-adjustment tells, Goodnite demand events written by e, and raw-result resources.
Keep each component's state semantics with that component, keep live process and presentation objects out of persistence, and preserve asynchronous writes and bounded cooperative loads so storage work does not stall Emacs redisplay.

The completed feature replaces the JSONL journals, per-session resume checkpoints, derived =index.json=, task-queue snapshots, cron and voice-adjustment state files, e-written Goodnite access JSONL, and the raw-result file directory.
It persists the state-machine facts needed to classify and resume an interrupted tool follow-up.
For boards, it persists canonical records, ordering, identity constraints, and the indexes needed for bounded live reads and restart replay.
It does not persist live harness objects, endpoint attachments, callbacks, timers, processes, Lisp predicate closures, focus, windows, or rendering state.
User-authored files, explicit exports and backups, migration reports, screenshots, and disposable subprocess files remain files because their file identity is part of their interface or they are not durable state.

[[file:../89-board-run-visibility-and-handoff/plan.org][Feature 89]] owns chat-visible board-run status, model-context projection, and quiescent completion handoff.
This feature persists the board facts and participant-authored completion records that feature 89 needs for restart-safe behavior, but it does not own that user experience.

* Why now

The current format has accumulated three representations of related state:

- one append-only JSONL journal per session;
- one lossy resume checkpoint per session;
- one rebuildable global session index.

That split made ordinary resume fast, but it also made correctness depend on retention policy, byte offsets, JSON shape, and a periodically rebuilt catalog.
The recent orchestration restart failure showed both classes of risk: ordinary JSON did not preserve nested Lisp type identity, and a bounded board tail could retain terminal facts after evicting the manifest needed to interpret them.

SQLite gives the runtime one physical durability boundary and direct, indexed access to every durable runtime projection.
It removes the need to encode semantic correctness into checkpoint tails, rebuild catalogs by scanning files, or maintain separate atomic-replacement and append-only writers for each component.
A new durable runtime value therefore adds a schema migration and an owner-shaped storage operation instead of another sidecar file.

* Current constraints to preserve

- =e-session= owns session identity, entry ancestry, current-path semantics, metadata classes, compaction boundaries, and provider-anchor compatibility.
- =e-board= is the central interaction plane.
  Sessions, =e-chat=, hooks, reducers, and deterministic scripts attach as participants and exchange board data only through board publication, subscription, pickup, and settlement operations.
- =e-board= owns board identity, validation, routing semantics, process-local participant attachments and subscriptions, and notification of those participants.
  Participant reducers own the meaning of their derived projections.
- Every durable publication enters through =e-board=, and the SQLite transaction is the publication.
  The transaction allocates the position, enforces identity and source-key constraints, inserts the canonical record and its query indexes, and commits.
  A successful commit wakes =e-board= with the committed position.
  =e-board= reads the canonical row and notifies matching participants in process.
  There is no second in-memory append, source-key index, or durable routing ledger beside the database.
- =e-chat= and each session are separate board participants.
  =e-chat= publishes input and receives output only through =e-board=; it does not communicate with =e-session= or use session persistence as a transport.
  =e-chat-service= is only the board-facing adapter for the chat presentation endpoint.
  It does not attach or proxy the session participant, route board data around =e-board=, or own persistence.
  Multiple session participants and presentation participants may attach to one board.
- =e-board-storage= owns durable board commits and board replay.
  =e-session-storage= separately owns each session's private durable state and resume projections.
  Neither port routes the other domain's writes.
- The shared SQLite adapter owns the acknowledged outbox, worker lifecycle, retry classification, and physical finalization barrier.
  Each semantic port owns aggregate-specific faulting and exposes its own ordered barrier.
- Durable writes stay outside the Emacs UI event loop.
  Reads performed in the main process must be indexed, paged, and bounded per scheduler step.
- Durable values must round-trip with exact supported Lisp shape.
  Symbols, keywords, strings, lists, vectors, nil, and JSON false may not collapse into one another.
- Durable board facts may not be lost because unrelated activity is noisy.
- Tool admission, dispatch, result, follow-up, and settlement facts that cross a restart boundary are session-owned durable state.
  Live tool handles, callbacks, timers, and provider requests remain process-local.
  SQLite may make the local state transition atomic and idempotent, but it cannot claim that an arbitrary external effect ran exactly once without tool-specific reconciliation.
- Unexpected corruption, unsupported values, schema mismatches, and revision conflicts must surface.
  Persistence must not guess or silently fall back.
- Every e-owned durable mutable runtime value uses the shared SQLite database.
  A component keeps its own schema meaning and storage API; sharing the adapter does not make one component own another component's state.
  New sidecar state files are not allowed.
- Unit tests and explicitly ephemeral harnesses use disposable SQLite stores.
  They do not require a second storage implementation.

* Direction

Use one database at =<e-state-directory>/store.sqlite3=, where =e-state-directory= defaults to the existing e state root under =user-emacs-directory=.
Expose owner-shaped storage APIs over one SQLite adapter.
=e-board-storage= serves the board aggregate.
=e-session-storage= serves session aggregates and each session participant's private state.
Task queue, cron, voice adjustment, Goodnite demand tracking, and raw-result resources each keep their own typed storage boundary over the same adapter.
No component exposes SQL or accepts mutations owned by another component.

A long-lived =emacs --batch -Q= worker, launched from the same Emacs installation, owns the writable SQLite connection.
It loads only the bundled storage worker and its codec.
This reuses Emacs's built-in SQLite bindings and avoids a native Node package or command-line SQL interpolation.
The shared adapter keeps the acknowledged outbox and sends newline-delimited, preflighted commands.
The worker serializes each aggregate command in one SQL transaction and acknowledges it only after commit.

For board communication, =e-board= is the public bus and SQLite is its canonical log.
A publish call does not first append to an in-memory board.
=e-board-storage= executes one transaction that deduplicates the source key, inserts the canonical record and its indexed selector values, and advances board position and revision.
Commit is publication.
The commit wake carries only the committed position, and =e-board= reads that row before notifying its live subscribers.
Notification is an in-process function call or scheduled callback, not a second durable delivery protocol.
A missed wake is recovered by scanning forward from the process-local high-water mark; after restart, participants reattach and replay committed rows through bounded reads.

SQLite replaces the current in-memory message/event indexes and source-key history.
=e-board= retains participant attachment, subscription matching, reducer orchestration, and other policy that depends on live Lisp state.
=e-board-runtime= retains endpoint attachment, current authorization, harness invocation, callbacks, and scheduler integration.
Live subscriptions may use Lisp predicates because they are process-local and are rebuilt when participants attach.
Indexed SQL selectors support bounded reads and replay; they do not define a second subscription system.

Session and participant-owned state does not travel through =e-board=.
=e-session= sends its typed mutations directly to =e-session-storage= and restores them through session projections.
A participant may persist its own transcript, configuration, metadata, board association, and recovery cursor without publishing those private values to the board.
There is no cross-domain commit API that combines a board publication with a session mutation.

The main Emacs process owns a separate read-only connection with =query_only= enabled.
Startup performs only the schema check and the bounded reads needed by components activated at startup.
The session catalog, task queues, cron cadence, and other component projections load independently through indexed queries.
Session and board restoration use indexed pages scheduled through the existing request lifecycle.
Synchronous load remains available only for batch callers and tests; interactive shells use cooperative load.

Persistent runtime storage requires an Emacs build for which =sqlite-available-p= is true.
The cutover raises the declared minimum Emacs version to 29.1 and still performs the runtime feature check because SQLite is an optional build feature.
There is no JSONL fallback or second store implementation.
Ephemeral harnesses create a disposable SQLite database and delete it after use.

** Current implementation delta

The current code does not yet have the planned semantic storage APIs.
=e-board= is a process-local aggregate with optional message and processing-record notification callbacks.
Ordinary messages are appended to in-memory event, message, source-key, and selector indexes before the message callback runs, while processing records use a separate pre-append callback path.
Input routing then runs through bounded in-memory classification queues, creates in-memory pickup objects and participant FIFOs, and hands those pickups to =e-board-runtime= for endpoint delivery.
The current code therefore implements append, persistence notification, subscription fan-out, pickup queuing, and delivery receipts as separate transitions with different failure boundaries.

=e-chat= already submits prompts and receives presentation events through board-backed service operations.
See [[file:../../../lisp/shells/chat/e-chat.el::(defun e-chat-submit][=e-chat-submit=]], [[file:../../../lisp/shells/chat/e-chat.el::(defun e-chat--subscribe][=e-chat--subscribe=]], and [[file:../../../lisp/core/e-chat-service.el::(cl-defun e-chat-service--post][=e-chat-service--post=]].

The current =e-chat-service= binding still combines two peers that the target architecture keeps separate: an =e-chat= board client/observer and an =e-board-runtime= attachment for one harness session.
It also elects the first combined binding as =e-chat-service--board-log-owners=, persists board envelopes by calling =e-session-append-board-message= on that binding's session, and reconstructs the board from that session on restart.

This coupling is current implementation debt, not the target ownership model.
The target gives =e-chat= its own board-facing binding and leaves harness-session attachment and restoration with the session participant runtime.
Neither peer uses the other as its communication or persistence path.

Session mutations already have an independent path.
=e-session--append-record= sends a session record to its persistence controller without board publication.
See [[file:../../../lisp/core/e-session.el::(defun e-session--append-record][=e-session--append-record=]].

The current tool-follow-up lifecycle is not restart-safe.
=e-context-lifetime-frame= is runtime-only, and legacy =context-frame= and =context-frame-settlement= records are ignored on session replay.
=e-tools-start= keeps settlement, the active request, and its deadline timer in local variables.
=e-harness--lifetime-tool-observation-frame= creates the paired call/result observation frame in memory, while =e-harness--lifetime-commit-response= completes the frame and appends promotions through separate session operations.
See [[file:../../../lisp/core/e-context-lifetime.el::(cl-defstruct (e-context-lifetime-frame][=e-context-lifetime-frame=]], [[file:../../../lisp/core/e-session.el::(defun e-session--replay-record][=e-session--replay-record=]], [[file:../../../lisp/core/e-tools.el::(cl-defun e-tools-start][=e-tools-start=]], [[file:../../../lisp/core/e-harness.el::(defun e-harness--lifetime-tool-observation-frame][=e-harness--lifetime-tool-observation-frame=]], and [[file:../../../lisp/core/e-harness.el::(defun e-harness--lifetime-commit-response][=e-harness--lifetime-commit-response=]].

The target removes both the board-log-owner proxy and the combined chat/session binding from =e-chat-service=.
It also removes the persistence notification callbacks and the authoritative in-memory message/source indexes.
=e-board-storage= makes canonical record insertion the publication commit, and =e-board= notifies its attached participants from the committed row.
The current live subscription, pickup scheduling, and endpoint code remains in process; this feature does not translate it into SQL tables, leases, or receipt machinery.
=e-chat= remains on board publication and observation APIs, while =e-session-storage= remains private to each session participant.

** Proposed architecture

=e-board= is the central interaction plane for shared application data.
Sessions, =e-chat=, hooks, reducers, and deterministic scripts are peer participants around it.
They publish and receive shared data only through board operations.
=e-chat-service= adapts the =e-chat= presentation endpoint to board publication and observation APIs.
It does not adapt, attach, or persist a session participant.

SQLite sits inside the board publication path as the canonical log and query engine.
It is not a second bus and does not model remote consumers.
A board publish operation commits one canonical row and then notifies the board's currently attached participants from that committed row.
Participant callbacks, Lisp predicates, and scheduler state stay in the process.
A participant's private state still passes through its own storage API without entering =e-board=.

Commit is publication.
The commit wake identifies committed positions rather than carrying the submitted Lisp object as a second authority.
=e-board= reads those rows and performs ordinary in-process notification.
If a wake is missed, the board scans forward from its process-local high-water mark.
After restart, participants reattach and replay the committed rows they need.
There are no durable delivery intents, claims, leases, or receipts for these in-process calls.
A participant that needs restart-safe progress persists its own cursor or derived state through its own storage API.

* Ownership and dependency direction

** =e-session=

Owns each live session aggregate and its private durable state.
Its public callers create sessions, append typed entries, change configuration, set message display, clear a transcript, record the session's board association, and query current state.
It emits typed session mutations directly to =e-session-storage=.

It does not publish private state through =e-board= and does not know table names, SQL, WAL settings, migration files, or worker protocol details.

** =e-harness=, =e-loop=, and =e-context-lifetime=

=e-harness= and =e-loop= own the live provider/tool follow-up lifecycle and decide how an interrupted transition may recover.
=e-context-lifetime= owns generation, frame, observation-consumption, and promotion semantics.
They submit typed session-lifecycle mutations through =e-session= and =e-session-storage=; they do not write SQL or persist callbacks, timers, requests, or tool handles.

A local commit can prove which lifecycle facts are durable and which transition revision won.
Only a tool-specific contract can reconcile an external effect that may have occurred before a crash.

** =e-board=

Owns the central interaction aggregate: board identity, validation, participants, live subscriptions, processing, routing policy, and source-key semantics.
All session, chat, hook, reducer, and deterministic-script participants publish and receive shared data through this boundary.

For publication, it submits one validated record through =e-board-storage=.
The storage transaction inserts the canonical row and commits it as published.
=e-board= reads the committed row and immediately applies its process-local subscriptions and callbacks.
It does not append the candidate to an authoritative in-memory ledger, accept session mutations, or coordinate participant-owned persistence.

=e-board= does not expose SQL to participants.
The storage port expresses board operations, while the SQLite adapter supplies ordering, identity enforcement, indexed lookup, and replay.

** =e-chat-service=

Provides =e-chat='s board-facing adapter.
It gives the presentation endpoint board publication and observation operations.
=e-chat= sends input to =e-board= and receives output from =e-board= like every other participant.
It does not address, attach, or call a session participant as part of that exchange.

The session participant has a separate board attachment owned by the participant runtime and a separate private-state path through =e-session= and =e-session-storage=.
=e-chat-service= does not read or write that private state, elect a session as board-log owner, persist board records through =e-session=, route participant data directly, or own a cross-domain commit.

** =e-board-storage=

Defines the board-owned boundary:

- publish one validated board record with an expected board revision;
- return the committed position and canonical identity after commit;
- page committed records by board, generation, position, and indexed selector fields;
- read bounded replay and audit projections;
- finalize board commands submitted before a barrier;
- expose bounded board persistence health.

Publication atomically inserts the canonical record and advances board order and revision.
The write contract is asynchronous.
It does not persist process-local subscriptions, callbacks, pickup queues, or delivery attempts.
It has no session mutation, generic =execute-sql=, or generic =append-record= operation.

** =e-session-storage=

Defines the session-owned boundary:

- submit one typed session commit with an expected session revision;
- list bounded session headers;
- read one paged session resume projection, including incomplete tool-follow-up state;
- finalize session commands submitted before a barrier;
- expose bounded session persistence health.

The write contract is asynchronous.
It has no board publication, board replay, generic =execute-sql=, or generic =append-record= operation.

** Other runtime-state owners

=e-task-queue=, =e-cron=, voice adjustment, Goodnite demand tracking, and raw-result resources each own their durable state contract.
Each submits typed mutations and bounded reads through a small owner-shaped storage API.
They share the worker, codec, migration system, backup path, health reporting, and finalization machinery.
They do not share domain tables or call one another's storage API.

** =e-storage-sqlite=

Implements every runtime-state storage API over one database.
It owns schema mapping, queries, transactions, PRAGMAs, schema migrations, command deduplication, database errors, and the read-only connection.
It translates validated owner commands to SQL and implements board ordering, source-key constraints, indexed selector fields, and paged reads.
It does not define live subscription semantics, endpoint policy, session paths, queue transitions, cron recurrence, voice-tell policy, Goodnite ranking, raw-result retention, reducer meaning, or presentation policy.

** =e-storage-sqlite-worker=

Owns the writable connection and the ordered command loop.
It is shared physical infrastructure, not a domain storage port and not a second implementation of any component's policy.
Each command targets one owner through one semantic storage API.

* Storage model

The schema keeps identity and query fields relational.
Nested domain values use one exact, versioned codec.
Storing the entire current system as opaque JSON blobs would retain the shape bugs and would not provide useful indexed access; fully normalizing capability-owned payloads would make persistence own their schemas.
The mixed boundary below avoids both errors.

** Store metadata

=schema_migrations=

- schema version, migration name, checksum, and applied timestamp;
- one row per applied migration;
- unknown newer versions are a hard open error.

=writer_commands=

- stable command id as the primary key;
- canonical command hash;
- committed timestamp and encoded result, including new revisions;
- inserted in the same transaction as the command's mutations.

A retry with the same id and hash returns the stored result.
Reusing an id with different bytes is a terminal protocol error.

** Runtime state inventory and boundary

The default is uniform: every e-owned durable mutable runtime value uses this database.
The value of a cache or telemetry stream does not justify a separate persistence mechanism.
Sharing a physical database and transaction engine is not domain coupling.
Coupling would come from one component owning another component's schema or policy, so each owner keeps a typed storage API and its own tables or projections.

The current production stores are:

- The session store spreads authority across the JSONL journal, resume checkpoint, and =index.json= in [[file:../../../lisp/core/e-session.el::(cl-defstruct (e-session-store][=e-session-store=]] and the Node writer.
  These become session and board tables plus indexed projections.
- The task queue persists selected task fields by replacing =records.eld= after a debounce.
  It excludes live handles and normalizes restored =running= tasks back to =queued=.
  See [[file:../../../lisp/core/e-task-queue.el::(cl-defstruct (e-task-queue][=e-task-queue=]], [[file:../../../lisp/core/e-task-queue.el::(defun e-task-queue--persistable-record][=e-task-queue--persistable-record=]], [[file:../../../lisp/core/e-task-queue.el::(defun e-task-queue--start-async-write][=e-task-queue--start-async-write=]], and [[file:../../../lisp/core/e-task-queue.el::(defun e-task-queue-load][=e-task-queue-load=]].
  Its durable queue, task, attempt, status, and output facts move to SQLite while live work handles and callbacks stay in memory.
- Cron cadence state writes =:last-fire= and =:anchor= through atomic file replacement in [[file:../../../lisp/core/e-cron.el::(defun e-cron--state-write][=e-cron--state-write=]].
  Those values move to SQLite while timers and action closures stay in memory.
- Voice adjustment stores a capped LRU list of tells through atomic file replacement in [[file:../../../lisp/layers/writing/e-voice-adjustment.el::(defun e-voice-adjustment--write][=e-voice-adjustment--write=]].
  The tell key, label, description, count, recency, and cap enforcement move to SQLite.
- Goodnite resource access appends e-owned demand events to =daydream_access.jsonl= in [[file:../../../lisp/layers/goodnite/e-goodnite-resources.el::(defun e-goodnite-resources--record-access][=e-goodnite-resources--record-access=]].
  Those events move to SQLite.
  If the external Goodnite miner still requires JSONL, an explicit export or bridge supplies it; the JSONL file is not a second authority.
- Generic raw-result resources use expiring files in [[file:../../../lisp/core/e-raw-results.el::(cl-defun e-raw-results-write][=e-raw-results-write=]].
  Their content, metadata, expiry, and cleanup state move to SQLite so the =raw-result://= interface uses the same storage lifecycle.

Files remain appropriate when the file itself is the product or protocol rather than a hidden runtime authority.
This includes user-authored source and Org files, explicit exports, verified backups, migration reports, browser screenshots, and subprocess streams that must be exposed through a pathname.
Session-scoped =tmp://= workspaces and anonymous process collectors remain disposable and provide no restart guarantee.
Developer profiling artifacts remain files because they are explicit diagnostic outputs, not product runtime state.

Live board registry objects, subscriptions, predicate closures, harness instances, active turns, tool handles, callbacks, timers, endpoint attachments, scheduler queues, pickup handles, shell buffers, and presentation caches are process state.
Durable board communication is represented by canonical board records.
Participant-specific replay progress or derived state belongs to that participant's own storage boundary.

[[file:../88-generational-context-ephemeral-frames/plan.org][Feature 88]] is the important scope correction.
It explicitly removed tool admission, dispatch, result, frame-settlement, recovery-state, and transactional-outbox work from that feature because the planned SQLite persistence and atomic-transition work would own it.
The previous version of this plan excluded active turns and tool requests too broadly and therefore did not satisfy that dependency.

This feature now persists only the lifecycle facts needed to classify and recover an interrupted follow-up.
=e-harness= and =e-loop= keep ownership of tool execution and recovery policy.
=e-context-lifetime= keeps ownership of frame and promotion semantics.
=e-session-storage= commits the typed lifecycle records and current recovery projection as part of the session aggregate.
No live process object moves into storage, and no generic external side effect gains an exactly-once guarantee merely because its local record committed.

[[file:../89-board-run-visibility-and-handoff/plan.org][Feature 89]] is already inside the board-storage scope.
Its run facts, keyed completion inputs, publication claims, and consumption receipts are board records.
Its queue assignments remain task-queue state and reconcile by stable identity after both stores restore.

** Sessions

=sessions= stores the current durable session root and catalog projection:

- session id, root entry id, current head id, and revision;
- created and updated timestamps plus the local update sequence;
- explicit name, current branch, and turn options;
- exact encoded metadata;
- current transcript epoch;
- optional board id, participant id, association role, and participant-owned recovery cursor;
- message count, first-user summary, last-message timestamp, and latest assistant marker.

The catalog columns are updated in the same transaction as the record that changes them.
They are not authoritative duplicate files and never require a reindex scan after an ordinary write.

=session_records= is the ordered immutable session history:

- session id and monotonically increasing per-session position;
- record type;
- optional entry id and parent entry id;
- transcript epoch and created timestamp;
- exact encoded payload and codec version.

Identity-bearing session events, messages, activity entries, branch summaries, compactions, provider anchors, and process reports use entry and parent ids.
Configuration changes, message-display changes, and transcript clears remain ordered records even where they do not introduce a new model-path entry.
Partial unique indexes enforce entry identity without inventing ids for records that do not have one.

=message_displays= is a rebuildable current projection keyed by session and message id.
A display change appends its audit record and updates this row in the same transaction.
Loading does not scan every historical display change.

=tool_followups= is the current recovery projection keyed by session, turn, provider request, and tool-call identity.
It records the latest durable lifecycle state, paired call/result message ids, frame and consumer identities, external idempotency key when the tool contract provides one, last session-record position, and error or reconciliation state.
The immutable admission, dispatch-claim, result, follow-up, promotion, and settlement facts remain in =session_records=.

=tool_dispatch_outbox= is the durable handoff from an admitted tool call to =e-tools-start=.
It is keyed by the same session, turn, provider-request, and tool-call identity and references the immutable admission record plus the exact validated call payload.
Admission creates the pending outbox row in the same session transaction.
The runtime claims that row through another revision-checked session commit and starts the external tool only after the claim commits.
Recording a result appends the result fact and retires the outbox row in one session transaction.

This outbox closes the crash window in which an external effect could start before any durable dispatch evidence existed.
It cannot close the window between starting the external effect and recording its result.
A committed =dispatch-claimed= row without a result therefore means the effect may or may not have happened.
Restore retries it only when the tool contract supplies a safe idempotency or reconciliation rule; otherwise the row becomes explicit attention state.

The current model path is selected from =current_head_id= through indexed parent links.
The current transcript epoch and explicit path eliminate full journal replay.
Activity and process-report retention remain application resume policy expressed as bounded queries; the complete audit rows remain in =session_records=.

** Boards

=boards= makes the board a first-class durable aggregate independent of any session chosen to persist its records:

- board id;
- exact encoded trusted principal;
- revision and current generation;
- next durable position and restored retention floor.

Session-to-board association is session-owned state stored with the session aggregate.
It is not a board table and is not written through =e-board=.
Several sessions may independently refer to the same board id and restore their own participant endpoints.

Board records belong to the board aggregate and are written once through =e-board-storage=, rather than through a designated session log owner.

=board_records= stores immutable board messages, processing chains, and processing results:

- board id, generation, and monotonically increasing durable position;
- record namespace and record id;
- ordinary board sequence when present;
- stable selector columns such as kind, author, target, subject participant, source turn, activity kind, and created timestamp;
- canonical source keys where the board contract requires idempotency;
- exact encoded frozen envelope and codec version.

The canonical row does not embed a live recipient list, pickup ids, or callback outcomes.
When such an outcome is shared application data, the responsible participant publishes it as another board record.

The key is board, generation, record namespace, and record id.
This preserves the existing separation between ordinary messages, processing chains, and processing results.
A second unequal processing record with the same key is a conflict.
The database position preserves the exact interleaving of all three record namespaces even though processing records do not have ordinary board sequence numbers.

=board_record_tags= normalizes tags for indexed =all= and =any= selector clauses.
=board_record_attributes= normalizes exact attribute clauses as canonical key/value hashes without interpreting capability meaning.
Capability payloads remain in the encoded envelope, and no capability-specific orchestration columns belong in the base schema.

Live subscriptions, predicate closures, callbacks, pickup queues, and delivery attempts are not database rows.
They are in-process parts of =e-board= or =e-board-runtime= and are rebuilt when participants attach.
SQLite indexes the stable board fields used by bounded history and replay queries, but it does not duplicate the live subscription registry.

A participant that needs restart-safe progress stores its own cursor or derived projection through its own storage boundary.
A durable acceptance, completion, failure, or handoff is an ordinary participant-authored board record when it is shared application data.
It is not a generic broker receipt maintained by the storage layer.

Clearing a board increments =boards.generation= in one transaction.
New records use the new generation and ordinary restore reads only that generation.
Older generations remain available as audit history.
This preserves the current clear semantics without deleting evidence or requiring a special checkpoint-cleared marker.

** Other runtime state

=task_queues= stores queue identity, revision, sequence, ordering, pause state, and bounded status metadata.
=task_records= stores the current durable task projection, while =task_events= records ordered status and attempt transitions when audit or restart classification requires them.
The schema preserves the current durable field allowlist and restores interrupted =running= work through an explicit recovery transition rather than silently rewriting a snapshot.
Live work handles, callbacks, and harness instances are not stored.

=cron_state= is keyed by schedule id and stores =last_fire=, =anchor=, and revision.
One transaction advances cadence state after a fire decision.
Schedule definitions, guards, action closures, and timers remain owned by the active layer and process.

=voice_tells= is keyed by normalized tell key and stores label, description, count, last-use time, and LRU position.
The voice-adjustment owner enforces the configured cap in the same transaction as an insert or refresh.

=goodnite_access_events= stores the demand events currently appended by e: kind, entry URI, scrubbed query, session id, turn id, engine, and timestamp.
An external miner reads through a bounded query or explicit export instead of treating JSONL as another authority.

=raw_results= stores resource id, content bytes, owner, preview fields, redaction policy, cleanup lifetime, metadata, creation time, last-access time, and expiry.
The =raw-result://= resource method reads this table, and cleanup deletes expired rows in bounded transactions.
Large-value limits and measured database-growth policy apply before replacing file spills.

** Exact value codec

Add one shared =e-storage-value-codec-v1= for nested persisted values and the worker protocol.
It uses tagged canonical JSON bytes with explicit forms for:

- nil and false;
- integers and finite floats;
- strings;
- symbols and keywords;
- proper and dotted lists;
- vectors;
- supported string/symbol-keyed maps where a domain contract already allows them.

The codec rejects cycles, non-finite numbers, buffers, markers, processes, functions, arbitrary records, and unrecognized mutable objects before a command enters the outbox.
Node and byte budgets remain preflight checks.
Canonical key order and byte representation make hashes and migration comparison deterministic.
Each encoded column carries or inherits a codec version; an unknown version is an explicit load error.

This codec replaces local JSON workarounds for metadata and orchestration facts.
Domain validators still own allowed value shapes.
The storage codec only preserves the shape it is given.

* Transaction and concurrency contract

Each writer command targets one owner through its typed storage API.
Board, session, and task-queue commands use aggregate revisions.
Cron, voice, telemetry, and raw-result commands use owner-specific keys and conflict rules.
The worker performs the following in one =BEGIN IMMEDIATE= transaction:

1. Look up the command id and verify its canonical hash.
2. Check the target owner's expected revision or conflict precondition.
3. Insert that owner's immutable records where the contract has an event history.
4. Update only that owner's current projections.
5. Advance the relevant revision or version.
6. Insert the command result and commit.

A board publication transaction has one additional fixed contract:

1. Resolve duplicate identity and source-key retries against committed rows.
2. Allocate the next board position.
3. Insert the canonical board record and normalized selector values.
4. Advance board revision.
5. Commit the record as published.

No message exists before that commit.
After commit, =e-board= reads the canonical row and applies the live subscription registry in process.
That notification does not create another durable board transition.

The shared worker serializes commands from every storage API.
A command normally changes one owner.
A multi-owner transaction is added only when the application defines a real invariant that must commit atomically; sharing the database alone does not invent such an invariant.
A participant that derives private state from a board row records the committed board position as a causal reference and persists its own state through =e-session-storage=.
That session update is independently retryable and must be idempotent; it is not part of board routing.

The response is emitted only after commit.
Constraint and revision conflicts are terminal.
=SQLITE_BUSY= and worker transport failures are retryable with a bounded backoff.
A terminal aggregate conflict faults persistence for that session or board; later writes for the aggregate do not continue over an unreconciled in-memory state.

Revision checks permit separate Emacs processes to use different sessions in one database while making same-session lost updates visible.
This is the supported concurrency boundary.
Automatic last-writer-wins merge and silent lease takeover are not supported.

The connection enables foreign keys and WAL mode.
Use =synchronous=FULL= for the durable writer.
If measured commit latency needs amortization, the worker may group adjacent independent commands into one transaction, but it may acknowledge none of them before the group commit.
Durability is not weakened to accommodate the current implementation.

Each storage API exposes an ordered barrier for its submitted commands.
System quiescence waits for every barrier in the operation's scope.
Because every acknowledged commit is already durable, a barrier does not build a checkpoint or force a WAL checkpoint.

* Read and restore contract

** Startup

Opening a store performs a bounded schema/version check and starts the writer.
Each active component then reads only its indexed root projection.
Session headers come directly from =sessions= in recent-message order; task queues, cron cadence, voice tells, telemetry consumers, and raw-result cleanup use their own bounded queries.
Startup does not scan immutable history tables.

The worker must report schema readiness before the read-only connection opens.
Full =integrity_check= is an explicit diagnostic and migration gate, not an unbounded startup task.

** Session load

=e-session-load-session-start= remains the interactive entrypoint.
It pages indexed rows and yields between pages.
It reconstructs:

- the session root and current configuration;
- the current model path from the latest valid compaction boundary, or the complete current path when no compaction exists;
- compatible provider anchors on that retained path;
- the existing bounded activity and process-report resume projections;
- current message display state;
- the session-owned board association and participant recovery cursor;
- incomplete tool-follow-up projections and the durable facts needed to classify them.

The recovery owner handles each incomplete follow-up by durable state.
An admitted tool with a pending outbox row may be claimed and then started after the claim commits.
A dispatch claim without a durable result requires tool-specific reconciliation or explicit operator attention and is never blindly rerun.
A durable result whose provider follow-up was not settled may resume the provider follow-up from the paired call/result evidence.
A settled transition requires no recovery action.

After session reconstruction, the attachment layer requests the referenced board from =e-board-storage=.
The session projection does not contain or replay board records.

The database replaces checkpoint materialization; =e-session= still decides what a valid compaction and provider anchor mean.
SQL supplies candidates in stable order and never chooses semantic compatibility.

** Board load

Board restore has two explicitly different products:

- a bounded recent message/activity page for presentation and ordinary context;
- a complete semantic replay stream for durable facts and processing records needed by reducers and restart reconstruction.

Both come from indexed pages in current-generation order.
After participants attach, =e-board= replays the committed rows they request and then continues from the live commit high-water mark.
Semantic facts are never limited by the recent presentation tail.
Reducers consume their stream incrementally, so correctness no longer requires retaining every fact in the chat buffer or one checkpoint object.
The binding remains =restoring= until semantic replay is complete; callers must distinguish that state from a definitively missing run or child.

Indexed board columns, normalized tags, and canonical exact-attribute hashes support bounded reads.
Capability-specific interpretation and live predicate matching remain in the owning participant after decoding.
A later feature may persist reducer-owned projections once a specific projection contract is stable; this feature does not add a generic projection table.

** Audit and export

Audit resources page immutable session or board rows without hydrating the live aggregate.
There is no per-session backing file after cutover.
Remove the misleading session =:file= field from catalog entries and use the existing session resource identity for runtime access.
Add an explicit export command for operator-readable JSONL when a file artifact is needed for debugging or sharing.

* Migration and cutover

Migration is explicit and offline.
Do not dual-write JSONL and SQLite and do not make startup choose whichever copy happens to parse.

Add =scripts/e-migrate-state-store= with these phases:

1. Verify that no active legacy writer owns a source store, inventory every e-owned durable state file, and record source sizes and hashes.
2. Parse complete session JSONL journals through the existing legacy normalization and domain validators.
   Checkpoints and =index.json= may supply diagnostics but are not import authorities because they are derived and intentionally lossy.
3. Extract legacy board envelopes from session journals, group them by board identity and generation, and import each canonical board record once into the independent board tables.
   Equal duplicates across session journals collapse by canonical identity; unequal envelopes for one identity abort migration.
4. Parse task-queue snapshots, cron cadence, voice tells, Goodnite access events written by e, and unexpired raw-result resources through owner-specific validators.
5. Build a temporary SQLite database with the current schema and import every owner in deterministic order.
   The importer is restartable by source hash but never exposes a partially imported database as current.
6. Compare owner-specific semantic manifests.
   Session and board manifests cover identity, ordering, current projections, canonical payload hashes, and the exact journal-to-board extraction map.
   Queue, cron, voice, Goodnite, and raw-result manifests cover their durable identities, values, order where relevant, and canonical payload hashes.
7. Run foreign-key checks and =integrity_check=, checkpoint the temporary WAL, close all connections, and atomically install =store.sqlite3=.
8. Write a migration report naming exact repairs, warnings, skipped legacy fields, and failures.
   Preserve every imported legacy state file as read-only rollback material.

Any unexplained record loss, missing root, conflicting typed board record, or non-round-tripping value aborts the whole cutover.
Known legacy normalization may be accepted only when the report states the exact transformation.
Missing historical facts are not invented.

On startup, the final SQLite backend behaves as follows:

- a valid =store.sqlite3= is opened;
- a legacy-only directory produces a targeted migration-required error;
- both formats present after migration use SQLite and report legacy files as inactive backup material;
- an invalid or newer SQLite schema is a hard error, never a JSONL fallback.

Deletion of legacy files is a separate, explicit future cleanup after the SQLite store has been used and backed up.
This feature does not delete them.

* Backup, recovery, and observability

- Add an explicit worker-owned backup operation using SQLite's online backup API or =VACUUM INTO= after capability validation.
  Never copy a live database and WAL pair with ordinary file copy.
- Expose schema version, database path, writer liveness, pending command count, oldest pending age, last committed command, retry state, read-page state, WAL size, and last error through the existing bounded persistence status.
- Add explicit =quick_check= and full =integrity_check= diagnostics.
  They are operator actions, not implicit UI work.
- A corrupt database is left untouched and errors with recovery instructions.
  Recovery means restoring a verified backup or explicitly rerunning the legacy importer against preserved sources.
- Temporary databases, backups, and migration reports use restrictive file permissions consistent with the session directory.

* Implementation slices

Each slice is a coherent commit and leaves the project in a useful state.
The SQLite backend remains opt-in until the migration and cutover gates pass.

1. *Storage contracts and exact codec*
   - Add separate typed mutation/read boundaries for =e-board-storage= and =e-session-storage=.
   - Keep the existing JSONL session path temporarily while the new ports are introduced, but do not model it as a valid board-storage implementation.
   - Add the shared tagged value codec, budgets, canonical hashing, and property tests for exact round trips and rejection.
   - Convert metadata and orchestration fact persistence to the shared codec without changing their domain schemas.
   - Gate: session callers use only the session port, board callers use only the board port, and neither caller emits generic JSON records.

2. *SQLite schema and worker*
   - Add schema migrations, the batch Emacs worker, writer protocol, WAL/foreign key settings, command deduplication, aggregate revisions, and bounded status.
   - Test empty creation, reopen, duplicate command, hash mismatch, revision conflict, busy retry, worker restart, kill-before-commit, and kill-after-commit-before-ack.
   - Gate: the SQLite adapter passes focused transaction tests without changing the default backend.

3. *Session writes and catalog reads*
   - Map every session mutation to typed SQL transactions and update catalog projections transactionally.
   - Load only session headers at store startup; remove reindex work from the SQLite path.
   - Run the semantic contract suite against disposable SQLite stores.
   - Gate: create, metadata/config changes, branches, compactions, anchors, displays, transcript clear, list ordering, and finalization survive restart with exact values.

4. *Cooperative session resume and tool-follow-up recovery*
   - Implement paged current-path and bounded auxiliary projection reads.
   - Add typed admission, dispatch-claim, result, follow-up, promotion, and settlement mutations plus the =tool_followups= recovery projection and =tool_dispatch_outbox=.
   - Commit admission with its pending dispatch row, require the claim commit before =e-tools-start=, and retire the row with the durable result.
   - Commit each local lifecycle transition atomically with its related session messages and projection update.
   - Restore incomplete transitions without recreating live callbacks, timers, provider requests, or tool handles.
   - Keep compaction and provider compatibility decisions in =e-session=, tool execution and recovery policy in =e-harness= and =e-loop=, and frame/promotion semantics in =e-context-lifetime=.
   - Replace checkpoint-based interactive loading in the SQLite path.
   - Gate: the 15,722-record/38 MB regression fixture resumes without a full record scan and is no slower than the approximately 0.07-second checkpoint baseline on the same machine, unless a measured, first-principles reason is recorded and approved.
     Kill-before-claim, kill-after-claim-before-start, kill-after-start-before-result, kill-after-result, and kill-before-settlement tests restore to the correct classified state without blind replay of an uncertain external effect.

5. *SQLite board log and indexed reads*
   - Move board identity, messages, facts, and processing records into board tables with generation and position semantics.
   - Implement the publish transaction that deduplicates the source key, allocates board order, inserts the canonical record and indexed selector values, and commits it as published.
   - Implement bounded presentation pages and complete incremental semantic replay from committed positions.
   - Remove the authoritative in-memory message, event, and source-key indexes that SQLite replaces.
   - Gate: no message is visible before commit; noisy activity cannot hide a required fact; clear, duplicate, conflict, indexed-read, processing-record, and orchestration restart cases pass without checkpoint retention rules.

6. *In-process board notification and participant independence*
   - Replace the =e-chat-service= board-log-owner callbacks and both persistence notification callbacks with commit wakes that contain only committed position ranges.
   - Have =e-board= read each committed row, match its live subscriptions, and notify attached participants through ordinary in-process calls or scheduled callbacks.
   - Keep live predicates, callbacks, pickup scheduling, and endpoint invocation in =e-board= and =e-board-runtime= rather than modelling them as durable broker work.
   - Recover a missed wake by scanning forward from the process-local high-water mark, and recover a restart through bounded replay after participants attach.
   - Split the current combined chat/session binding so =e-chat= and the harness session remain independent peers attached to =e-board=.
   - Keep =e-chat= input, output, and observation on board APIs; do not resolve communication through =e-session=.
   - Keep participant-owned transcript, configuration, metadata, association, replay cursor, and recovery state on =e-session-storage= or the participant's own storage boundary.
   - Gate: commit is publication, every live notification originates from a canonical SQLite row, no generic durable intent/claim/receipt protocol exists for in-process calls, no board record uses a session log owner, and session writes do not pass through =e-board= or =e-board-storage=.

7. *Remaining runtime-state stores*
   - Move task queues, cron cadence, voice tells, e-written Goodnite demand events, and raw-result resources onto their typed SQLite APIs.
   - Preserve each owner's current semantic rules while replacing its file writer, loader, error swallowing, and cleanup path.
   - Add bounded reads, status, barriers, retention, and owner-specific contract tests.
   - Gate: no production path writes =records.eld=, =cron-state.eld=, =voice-tells.eld=, =daydream_access.jsonl=, or raw-result files, and restart preserves every supported durable value.

8. *Offline importer and verification*
   - Add dry-run, import, semantic manifest comparison, integrity checks, deterministic reports, and atomic installation.
   - Exercise clean, malformed, legacy-shape, missing-root, board-clear, and orchestration fixtures.
     Run a dry migration of a copy of the current user store; never modify the live store as part of repository tests.
   - Gate: repeat import produces the same manifest and any unexplained mismatch prevents installation.

9. *Cutover and legacy removal*
   - Make SQLite the only persistent backend, add the migration-required startup error, raise the declared Emacs minimum, and update architecture and E2E documentation.
   - Remove the JSONL writer, checkpoint manifests and retention limits, checkpoint loader/migrator, index rebuild, direct/queued file write modes, and per-session file exposure.
   - Retain only the offline legacy reader used by the migration command.
     It is not linked into ordinary startup or load.
   - Gate: source search finds no production sidecar runtime-state writer and no implicit compatibility fallback.

10. *System, current-config, and performance proof*
   - Run focused storage, session, board, chat-service, orchestration, resource, and restart suites; then the complete batch suite.
   - Run graphical E2E in isolated mode and =E_E2E_EMACS_CONFIG=current= mode against temporary SQLite stores.
   - Measure startup catalog load, session resume, board semantic restore, append/commit latency, finalization latency, database/WAL size, and Emacs main-thread time under a representative event burst.
   - Perform crash recovery and verified backup/restore playthroughs.
     Record all results in =review.org= before any live user-store migration.

* Performance requirements

- No SQL write or migration runs in the main Emacs event loop.
- No interactive read step decodes more than its configured row/byte budget.
- Store startup is proportional to session headers returned, not total transcript or board history.
- Session resume is proportional to the selected model path and bounded auxiliary projections, not total audit history.
- Board semantic restore may read every required fact, but does so in bounded pages and does not retain unrelated activity merely to preserve facts.
- Session list ordering uses an index over catalog timestamps and stable tie breakers.
- Board indexes cover generation plus durable position, kind, ordinary sequence, normalized tags, attributes, and source keys.
- A lost commit wake causes only delayed notification; scanning forward from the process-local high-water mark recovers it without a second publication path.
- Writer batching, if added, must preserve command order, revision checks, and acknowledgement-after-durability.

* Test strategy

** Core contract tests

Keep pure =e-session= tests and pure =e-board= validation, live subscription matching, and endpoint-policy tests independent of physical storage.
Run every board publication, ordered-read, indexed-query, and replay contract against disposable SQLite databases because SQLite is the board's canonical log, not an optional side store.
Cover identity, ancestry, branch selection, clear semantics, metadata ownership, provider anchors, display state, board record namespaces, exact duplicate handling, conflict behavior, and strict separation between the board and session ports.
There is no second in-memory board-store implementation for these tests.
The tests should fail narrowly when domain semantics change and should not assert SQL text.

** Adapter tests

Test schema migrations and SQL constraints directly with disposable databases.
Cover command deduplication, canonical hashes, revisions, foreign keys, transaction rollback, busy classification, worker death boundaries, atomic board insertion, indexed selector reads, page positions, unknown codec/schema versions, and read-only connection enforcement.

** Migration tests

Use immutable legacy fixtures and semantic manifests rather than regex checks of generated SQL.
Include the known list/vector/symbol ambiguity, retained orchestration facts, checkpoint-only omissions, missing roots, typed board-id collisions, clears, and journals with an incomplete final line.

** System tests

One restart scenario must create several independent session participants plus an =e-chat= participant on one board, branch and compact one session, install several live subscriptions, publish ordinary and processing records plus orchestration facts, change a message display, clear and reuse a board id in a new generation, kill the worker, reopen, reattach the participants, and prove exact session and board reconstruction through bounded replay.
It must also prove that each session's private commits remain in =e-session-storage= and never enter board publication.

One board-publication scenario must stop before commit, after commit before wake delivery, and after wake delivery.
It must prove that commit is the only publication boundary, live notification uses the committed row, a lost wake resumes from the process-local high-water mark, and restart replay does not depend on a durable broker-delivery protocol.

One tool-follow-up scenario must crash before dispatch claim, after claim but before tool start, after tool start but before durable result, after durable result, and after provider-follow-up settlement.
It must prove that no tool starts before its claim commits, safe automatic continuation occurs where the durable state and tool contract permit it, and an uncertain external effect becomes explicit attention state when it cannot be reconciled safely.

One load scenario must keep an interactive timer responsive while paging a large session and board.
The existing graphical/current-config matrix must use temporary state and must never open or migrate the user's live database.

* Acceptance criteria

- =store.sqlite3= is the only ordinary persistent authority for all e-owned durable mutable runtime state.
- Task queues, cron cadence, voice tells, e-written Goodnite demand events, and raw-result resources use the shared SQLite substrate through owner-shaped APIs.
- Adding durable runtime state requires a schema migration and storage operation rather than a new sidecar file.
- Session headers are listed without transcript replay or a rebuilt index file.
- Sessions resume from indexed records without checkpoint files or byte offsets.
- An interrupted tool follow-up restores to a durable classified state: safe to start, requires reconciliation, ready for provider follow-up, settled, or explicit attention.
- Each local tool-lifecycle transition commits its immutable facts and current recovery projection atomically with the related session records.
- No external tool starts before its durable dispatch claim commits.
- Board facts required by reducers survive regardless of unrelated activity volume.
- Live board communication is decoded from committed SQLite rows rather than forwarded from submitted in-memory objects.
- The board publication transaction atomically inserts the canonical record, allocates its order, and commits it as published.
- =e-board= notifies live participants from the committed row, and a missed wake is recovered by scanning forward from the process-local high-water mark.
- No authoritative in-memory message index or source-key map duplicates the SQLite board log.
- Session and board nested values round-trip with exact supported Lisp shape.
- Participant-owned state persists independently through =e-session-storage=.
- Restore never blindly repeats a dispatched external effect whose outcome is unknown.
- Duplicate publication with the same identity is idempotent; conflicting command ids, record ids, and aggregate revisions fail visibly.
- Writes remain asynchronous and interactive loads remain bounded and cooperative.
- Legacy migration is explicit, verified, atomic at cutover, and preserves the source files.
- Store opening fails clearly when SQLite support, the expected schema, or a required migration is absent.
- Repository, isolated graphical, and current-config E2E validation pass against disposable SQLite state before any operator-owned store is touched.

* Non-goals

- Do not persist live active-turn objects, provider requests, callbacks, timers, work handles, board subscriptions, pickup queues, endpoint attachments, Lisp predicate closures, focus, windows, overlays, render caches, or other process/presentation state.
  Persist canonical board records and the session lifecycle facts and current recovery projection needed to classify an interrupted tool follow-up.
- Do not promise exactly-once execution of arbitrary external tool effects.
  Automatic retry requires a tool-specific idempotency or reconciliation contract.
- Do not make SQLite a model-facing tool or capability action.
- Do not expose generic SQL to agents, shells, capabilities, or resources.
- Do not add full-text search, cloud sync, shared network storage, or a generic capability projection framework in this feature.
- Do not treat one session as the storage owner of a board shared by several session bindings.
- Do not keep permanent JSONL dual-write, runtime legacy replay, or automatic format fallback.
- Do not delete the user's legacy store during implementation or migration.

* Risks and explicit mitigations

** SQLite availability

Built-in SQLite is optional even on a new Emacs.
Persistent construction checks it before creating state and reports how to obtain a compatible build.
Tests and ephemeral harnesses create disposable SQLite databases rather than switching to another storage implementation.
CI must exercise the declared minimum and current supported Emacs with SQLite enabled.

** Worker startup cost

A batch Emacs is heavier than the current Node writer.
It starts once per store, with =-Q= and a small load path.
Measure cold and warm startup.
If it is material, share one worker across stores through the storage adapter rather than moving writes onto the UI thread.

** Database growth

SQLite retains complete audit rows.
WAL size is observable and checkpoints are worker-owned maintenance.
Retention/deletion needs a separate policy feature; this migration does not silently discard history.

** Main-process reads

Even read-only SQL can block.
All interactive queries require covering indexes, row and byte limits, and request-lifecycle yielding.
An unbounded convenience query is a test failure, not an accepted implementation shortcut.

** Partial in-memory failure

Session state may change before asynchronous durability is acknowledged, but durable board communication remains pending until commit.
A terminal board commit or revision failure prevents delivery of that record and faults the aggregate; any other terminal aggregate failure blocks dependent writes until explicit reload or reconciliation.
The runtime must not present pending or later state as durably saved.

** Missed commit wake

The worker commit acknowledgement is only a wake-up signal for in-process notification.
=e-board= tracks the highest committed position it has drained and scans forward after every wake.
A missed or coalesced wake delays notification but cannot lose the canonical record.
After restart, participants reattach and request bounded replay rather than resuming a durable broker queue.

** Live subscription boundary

Subscriptions may contain Lisp predicates, callbacks, timers, and endpoint references.
They remain process-local and are rebuilt when participants attach.
SQLite indexes stable board fields for bounded reads, but it does not duplicate the live subscription registry or attempt to persist executable behavior.

* Legacy removal list

After verified cutover, remove from production:

- =lisp/core/e-session-writer.mjs= and its Node tests;
- JSONL append, scan, suffix replay, and per-session file helpers;
- =index.json= loading, refresh, rebuild, and dangling-file reconciliation;
- resume checkpoint files, manifests, byte offsets, dirty-id tracking, and all checkpoint retention limits;
- direct and queued filesystem write modes;
- local JSON array/plist repair paths that the shared exact codec supersedes;
- catalog =:file= fields that imply one session equals one backing file;
- =e-chat-service--board-log-owners= and the board message/processing persistence notification callbacks;
- authoritative in-memory board message and source-key indexes replaced by indexed SQLite rows.

Keep the legacy decoder only under the offline migration entrypoint until a separate deprecation removes it.

* Design self-check

1. *Useful stopping point*: The adapter and exact codec are useful before cutover; the opt-in SQLite backend can be proven independently; the importer and final cutover each leave a coherent system.
2. *Final direction*: One physical SQLite authority replaces journals, checkpoints, catalog files, and the board's duplicate in-memory durable ledgers.
   =e-board-storage= and =e-session-storage= preserve separate domain boundaries while SQLite acts as the board data plane inside the central =e-board= interaction boundary.
3. *Stable versus uncertain*: Session/board identity, ancestry, immutable facts, lifecycle ordering, canonical board order, and exact value shape are stable.
   Page sizes, WAL maintenance thresholds, worker sharing, live notification scheduling, and tool-specific reconciliation are tunable or contract-specific.
   Reducer-specific projections and live subscription predicates remain outside the durable board schema.
4. *Ownership*: Session semantics and participant-owned state stay in =e-session= behind =e-session-storage=.
   Shared interaction stays in =e-board=, whose storage port commits canonical records and supplies indexed reads through =e-storage-sqlite=.
   =e-chat-service= adapts only the chat presentation participant; =e-board-runtime= owns live endpoints; =e-harness= and =e-loop= own tool execution and recovery policy; =e-context-lifetime= owns frame and promotion semantics.
5. *Coupling*: SQL is behind narrow owner-shaped ports, but the board port deliberately uses relational transactions as its implementation rather than rebuilding a database beside an in-memory router.
   The design separates the current combined chat/session binding, removes the =e-chat-service= to =e-session= board-log proxy, and does not add a second ephemeral storage implementation.
6. *Dependency direction*: The SQLite adapter depends on domain mutation/read contracts.
   Stable domain policy does not depend on SQL, the worker, presentation, or provider adapters.
7. *Side effects*: Writable connections, migrations, backups, WAL maintenance, and filesystem changes live in the worker/adapter boundary.
   Shells only request application operations.
8. *State lifetime*: Immutable session and board facts, user intent, stable references, lifecycle facts needed for restart classification, and current durable roots persist.
   Catalog, display, and tool-follow-up rows are rebuildable projections.
   Board subscriptions, pickup queues, endpoint attachments, callbacks, timers, requests, tool handles, predicate closures, focus, and rendering state remain process- or presentation-local.
9. *Performance*: Writes remain off-thread; reads are indexed and paged; SQLite performs source-key lookup, board ordering, selector-field lookup, and replay scans instead of repeated in-memory reconstruction.
   Startup no longer scans files, and resume no longer materializes a checkpoint plus suffix.
   FULL durability cost is paid in the worker and measured explicitly.
10. *Real interfaces*: =e-board-storage= and =e-session-storage= are separate, consumer-shaped contracts over the same SQLite adapter.
    Neither has generic SQL, cross-domain mutation operations, or unsupported-operation escape hatches.
11. *Compatibility*: Legacy data has one explicit offline importer.
    Runtime fallback and dual-write are rejected.
